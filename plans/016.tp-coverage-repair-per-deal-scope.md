# 016 — plan: per-deal scoping for `BOT_TP_COVERAGE_REPAIR`

Spec: `specs/016.tp-coverage-repair-per-deal-scope.md`.

## Build order

1. **`core/src/bot/dca/tpCoverageReconcile.ts`** — add the pure parse. This
   module is already the decision half of this feature and imports nothing
   (spec 013's purity note), so the parse lands beside the logic it gates
   rather than in a new file:
   - `TpRepairScope` — discriminated union `off | fleet | deals | invalid`,
     same shape style as the existing `TpCoverageProbe` union.
   - `parseTpRepairScope(raw: string | undefined): TpRepairScope` (§4.1, §4.2).
   - `tpRepairAllows(scope, dealId): boolean` — the per-deal question the
     caller asks.
   - `describeTpRepairScope(scope): string` — the startup line (§4.3).
2. **`core/src/bot/dcaHelper.ts`** — replace the module-level boolean
   `tpCoverageRepairArmed` with `tpCoverageRepairScope`, emit the startup log
   (§4.3), and in `checkTpCoverage` swap the single `if (!tpCoverageRepairArmed)`
   for the per-deal `tpRepairAllows(...)`, with the two-reason `left as is`
   line (§4.4).

Nothing else. The correction body below that branch is untouched (§3).

## Contract decisions the spec left open

- **Where the parse lives** — `tpCoverageReconcile.ts`, not a new module and
  not inline in `dcaHelper.ts`. It is a pure decision, it belongs with the
  other pure decisions for this feature, and it gets tested with no mocking.
- **`invalid` is a distinct union member, not folded into `off`.** They behave
  identically (never repair) but must log differently — §1.3 is the entire
  reason this distinction exists.
- **Duplicate / whitespace-padded ids** are tolerated (trimmed, de-duplicated
  by the `Set`). An operator pasting a list from a Telegram card should not
  have a run rejected over a stray space.
- **Startup log level** — `logger.info` for a recognised scope, `logger.warn`
  for `invalid`. A rejected arming value is an operational error.

## Blast Radius

1. **Other call sites of the changed symbol.** `tpCoverageRepairArmed` is
   module-private and referenced at exactly one place
   (`dcaHelper.ts`, the `if (!tpCoverageRepairArmed)` in `checkTpCoverage`) —
   verified by grep before editing. The new exports in
   `tpCoverageReconcile.ts` are additive; no existing export changes shape.
2. **`core/` submodule.** Yes — this is `main-app-sh`, shared by every
   consuming service. Mitigated by the change being purely additive to the
   module's export surface: no existing type, signature or return shape is
   altered, so no consumer can break. `BOT_TP_COVERAGE_REPAIR` is read only
   here.
3. **Documented cross-service contracts** (root `CLAUDE.md` Danger List).
   None touched: no GraphQL schema, no `/api/v2` shape, no socket.io event, no
   Redis channel, no RabbitMQ queue, no shared Mongo collection field. The
   change is confined to how one process-local env var is interpreted.
4. **Other tests on this path that must stay green.**
   `tpCoverageReconcile.spec.ts` (the pure decision) and
   `tpCoverageReconcile.harness.spec.ts` (the real `checkTpCoverage` over the
   recorded production deals). The harness arms via `'1'`, which §4.1 keeps
   meaning exactly what it means today — so it must stay green **unmodified**,
   and that is the regression proof for the fleet path.
