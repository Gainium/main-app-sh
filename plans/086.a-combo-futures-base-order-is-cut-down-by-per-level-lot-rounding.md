# Plan 086 — carry the lot-step residual across combo minigrid levels

Spec: `specs/086.a-combo-futures-base-order-is-cut-down-by-per-level-lot-rounding.md`

## Solution

One branch in `MainBot.generateGridsOnPrice` (`src/bot/main.ts`), the per-level
sizing for `profitCurrency === 'quote' && orderFixedIn === 'base'`.

Today every level takes `floor(baseAmount)` independently. Instead, for a combo
**futures linear** minigrid, each level takes

```
floor(baseAmount × (levelIndex + 1))  −  (what the earlier levels actually took)
```

The cumulative target is floored, so every prefix sum stays at or below the
unrounded prefix (spec §4.2 — never over-commits). The subtraction is against
the quantity each earlier level *actually got* — read off `grid.qty` at push
time, after the venue-minimum and min-notional clamps — so a level the venue
forced upward is repaid by the levels after it rather than compounding
(spec §5.3).

Nothing else moves: the routine's `baseAmount`, `lastGridSizing` reporting,
minimum clamps, step alignment and slicing are untouched.

### Gate

`combo && this.futures && !this.coinm`:

- `combo` (`botType === BotType.combo`) — a grid bot never floored here (§5.2).
- `this.futures` — on spot the floor is load-bearing (§5.1), and only the
  futures branch of `getBaseOrder` copies the grid sum onto the position.
- `!this.coinm` — coin-margined sizing is overwritten two statements later by
  the `this.coinm && !this.isBitget` branch; excluding it keeps the carry from
  tracking a quantity it did not decide.

### Reuse

No new helper. The arithmetic is `this.math.round(x, precision, true)` — the
same floor the line already called. There is no residual-distribution utility in
`core/src/utils` or `core/src/bot` to wire up (grepped `residual|carry|
cumulative`); adding one for a single call site would be the duplicate this
repo's rules forbid.

### Rejected alternatives

- **Round to nearest instead of flooring for combo futures.** One line, but it
  over-commits: 5 × `round(0.0159)` = `0.10` against a `0.08` budget. Violates
  spec §4.2 and the brief's stated constraint.
- **Fix it in `comboHelper.getBaseOrder` by raising the base order back to the
  configured notional.** Treats the symptom and breaks the invariant the futures
  overwrite exists for — the position would no longer equal the ladder that
  unwinds it, leaving a remainder the grid can never close.

## Blast Radius

1. **Other call sites of `generateGridsOnPrice`** — `comboHelper.ts` lines 373,
   511, 870, 2694, 3908, 4572 and `helper.ts:1075`. `helper.ts` is the grid bot
   (`combo` false — unaffected). All six combo call sites size a minigrid from a
   budget and want exactly this behaviour; the base-grid one (4572) is the
   reported path and the safety-order one (3908) is its twin.
2. **`core/` submodule** — yes. `src/bot/main.ts` ships to every service that
   embeds `main-app-sh`, and to self-hosted installs. The reporter is on a
   self-hosted install, which is how this fix reaches them.
3. **Cross-service contracts (root Danger List)** — none touched. No GraphQL
   shape, no socket event, no queue payload, no Mongo field, no `BaseReturn`.
   The change is arithmetic inside one method; the `Grid` shape is unchanged.
4. **Other tests on this path that must stay green** — `gridBudgetRefusal.spec`
   and `gridBudgetGuard.spec` (spec 068) drive the same routine for a grid bot
   and assert `lastGridSizing`; `qtyStepGuard.spec`, `zeroSizeOrderRefusal.spec`,
   `comboGridCancelLedger.spec`, `gridPositionValue.spec`. Full suite is the
   gate.
