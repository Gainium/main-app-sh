# Plan 053 — a refused deal close leaves the position with nothing on the book

Spec: `specs/053.a-refused-deal-close-leaves-the-position-with-nothing-on-the-book.md`.

## Build order

1. `restoreCloseAfterRefusal` — a new protected method on the DCA helper, next
   to the other close-path bookkeeping. It re-reads live state, decides whether
   a restore is needed, re-arms through `getTPOrder` + `placeOrders`, and
   answers whether a close is on the book afterwards.
2. Call it from `closeDealById`'s terminal-refusal branch, after
   `handleOrderErrors` and the existing trailing-disarm handling — so nothing
   about today's reporting or trailing behaviour moves.
3. §4.2 reporting, inside the same method: when the answer is "still nothing on
   the book", warn with a greppable line and `processError(..., force)`.
4. `dealOwnBasePosition` — a thin wrapper over the existing pure
   `trackedPosition`, and the third term of adaptive close's `Math.min`.

## Contract decisions the spec left open

- **The restore reuses `getTPOrder` + `placeOrders`,** the exact pair
  `tpCoverageReconcile`'s correction already calls (`dcaHelper.ts:10955-10985`).
  No new sizing path, no new helper: `getTPOrder` is the one function that knows
  how this deal's take-profit is sized, and a second opinion about it is what
  spec `014` had to unwind last time.
- **`restoreCloseAfterRefusal` returns `boolean`** ("is there a close on the
  book now?") rather than reporting internally and returning void, so the §4.2
  branch is a plain `if` at one call site and the method stays testable.
- **The §4.2 report is a bot message, not a new deal field.** `processError`
  with `force` is already user-visible and already renders; a new
  `closeBlocked` deal field would need a V2 GraphQL fragment change to be seen
  at all (spec §6.1), which is a different repo. Deferred, not silently
  dropped.
- **`setError: false`** on that report. The deal needs attention; the bot does
  not need to be stopped, and erroring it would be a heavier behaviour change
  than the defect warrants.
- **JIT tier: 0 for `closeDealById`.** It is 500 lines of interleaved decision
  and I/O, and it is on the causal path — but the radius actually touched is one
  `else` branch and one `Math.min`. Extracting the enclosing method is a
  modernization task, not something to spring on a money-path bug fix. The new
  logic is pulled out into its own named methods instead, which is tier 1 for
  the code being added.

## Blast Radius

1. **Other call sites.** `restoreCloseAfterRefusal` and `dealOwnBasePosition`
   are new — no existing callers. `closeDealById` itself is called from many
   places (trailing, stop-loss, manual close, combo), but the change is confined
   to the branch reached only after the venue has REFUSED the close and the
   slippage-retry and position-already-closed branches have both returned. Every
   path that closes successfully is untouched, which is why the "still lets the
   wallet cap the close" test passes both before and after.
2. **`core/` submodule.** Yes — both files are under `core/` (`main-app-sh`),
   shared with every consuming service and deployed platform-wide. The submodule
   pointer needs bumping deliberately.
3. **Documented contracts.** None crossed. No GraphQL shape, no socket event
   name, no queue payload, no `BaseReturn<T>`, no shared Mongo field is added or
   changed. `processError` and `placeOrders` are called with their existing
   signatures. The `'Not enough balance'` subType already exists and already
   defaults `showUser: true`.
4. **Other tests on this path that must stay green.** The close path is heavily
   pinned: `tpCoverageReconcile.spec`, `tpCoverageReconcile.harness.spec`,
   `tpCoverageContractUnits.harness.spec`, `tpCoverageRepairScope.spec`,
   `trailingTpCloseRetry.harness.spec`, `trailingTpCloseTrigger.harness.spec`,
   `trailingTpBreakEvenFloor.harness.spec`, `trailingCloseRetry.spec`,
   `unactionedClose.harness.spec`, `tpDustClose.harness.spec`,
   `tpSizingFromPosition.harness.spec`, `tpSizingAfterPartialTp.harness.spec`,
   `notEnoughBalanceReasons.spec`, `resizeCancelPromotion.spec`. The whole
   `core` suite is the exit criterion for gate 6.

### The one real risk, and what holds it shut

The restore places an order on a path that today places nothing. If it fired
when a close were actually in flight, it would double up on the position. Three
things prevent that, all read from LIVE state at the moment of the restore
rather than from the stale locals the refusal branch is holding:

- the deal is re-fetched and must still be `open`;
- it must have **zero** `NEW`/`PARTIALLY_FILLED` orders;
- `placeOrders` is itself idempotent about resizing and is the same call the
  reconcile correction makes.

If the venue in fact accepted the close and only the response was lost, the
deal's own order map will show the resting order and the restore declines —
which is what the "does not place when a resting order survived the cancel"
test pins.
