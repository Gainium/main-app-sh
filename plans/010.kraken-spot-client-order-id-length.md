# 010 — Kraken spot client order ids are too long for the venue to carry

Plan for `specs/010.kraken-spot-client-order-id-length.md`. Issue #657.

## 1. Build order

This is a **two-repo change**. The other half is `exchange-connector`
(`core/specs/003`, amended): a three-way discriminator on the incoming id —
txid → `QueryOrders`; **≤18-char free text → `cl_ord_id` verbatim**; 35-char
legacy → the existing sha32 `cl_ord_id` plus the `userref` fallback.

Order is **not** load-bearing, deliberately:

- **Connector first** — it accepts free text, main-app is not emitting any yet:
  pure no-op until this half lands.
- **main-app first** — the running connector hashes the new short id to
  sha32 at submit *and* at lookup, consistently. Correct, just not yet the
  improvement.
- The connector's free-text branch matches a row carrying **either** the
  verbatim id **or** `sha32(id)` (spec 003 §4.9.3), so the orders placed inside
  a split-deploy window stay resolvable after the second half lands. Without
  that bridge those orders would go "not found in history" — which main-app
  reads as a venue denial and retires a live order as a phantom.

Within this repo:

1. `core/src/bot/main.ts` — `getOrderId()`: add the Kraken spot arm.
2. Nothing else. `venueOrderId()`, `cancelOrderOnExchange()` and the two
   `krakenSpot` branches are audited in spec §5.1–§5.3 and stay as they are.

## 2. Contract decisions the spec left open

- **The budget is a per-venue `maxLength`, not a new code path.** `getOrderId()`
  already carries `maxLength` (36 default, 32 for okx/mexc) and derives the
  random tail from it. Kraken spot is one more value — `18` — so the shape,
  the alphabet and the prefix handling are the ones already in the function and
  there is no second id generator to keep in step. Reuses `utils.id()`
  (`core/src/utils/index.ts:25`), whose alphabet is already `[A-Za-z0-9]`.
- **`this.krakenSpot`, not `exchange === kraken`.** The getter already exists
  (`main.ts:8333`) and is what every other Kraken-spot branch in the file reads,
  so futures/paper cannot drift into the arm by accident.
- **No stored mapping, no migration.** A Kraken order's resolution path is
  decided by the shape of its own id, at read time, in the connector.

## 3. Blast radius

1. **Other call sites.** `getOrderId()` is called from 30 sites across
   `main.ts`, `helper.ts`, `comboHelper.ts`, `dcaHelper.ts` — every bot engine.
   All of them take the string and put it in `newClientOrderId`/`clientOrderId`;
   none parses it, and none assumes a length. The change is gated on Kraken spot,
   so every other venue's id is byte-for-byte what it is today (§4.5, tested).
   The one other definition, `dca/multiTpCompletion.harness.ts:125`, is a test
   stub and is not the class under change.
2. **`core/` submodule.** Yes — this is `main-app-sh`, shared with every
   consuming service and with self-hosted installs. The pointer in `main-app`
   must be bumped with it. A self-hosted install running an **older connector**
   is the case the length change has to be safe for: an old connector sha32-hashes
   whatever it is given, short ids included, and resolves them by that same hash
   — so it keeps working, it just does not get the improvement.
3. **Documented contracts.** None touched. The client order id is not part of
   the GraphQL schema shape, a socket event name, a queue payload or a
   `BaseReturn`. It is a *value* inside `orders.clientOrderId`, which stays a
   string of the same alphabet. Readers that match on the family prefix
   (`D-`/`CMB-`/`GRID-`/`GA-`) still match (§4.2, tested).
4. **Mongo `orders`** — read directly by legacy main-dash and admin-app. The
   field's type and prefix grammar are unchanged; only its length varies, and it
   already varies by venue today (31 on MEXC, 32 on OKX, 34 on Hyperliquid, 35
   elsewhere).
5. **Tests that must stay green.** The whole `core` mocha suite; in particular
   `src/bot/orderNotFound.spec.ts` (the Kraken reconcile wording) and
   `src/bot/dca/multiTpCompletion.spec.ts` (the other `getOrderId` definition).

## 4. Legacy tier (Part 4 of the dev-flow skill)

**Tier 0 → Tier 1 is not warranted.** `getOrderId()` is already a pure
function of `this.data.exchange` + `this.brokerCode` + the prefix: no DB, no
queue, no HTTP. The causal path has no I/O mixed into it, so there is nothing
to extract; the smell the runbook targets is not present. It is driven off the
prototype in the test with no mocking at all, which is the property extraction
would have bought.

## 5. Traceability

| Spec § | Test |
|---|---|
| §4.1 length ≤ 18 | `krakenOrderId.spec.ts` — "never exceeds Kraken free-text length, for any prefix in use" |
| §4.2 prefix preserved | "keeps the whole prefix, so existing readers still match it" |
| §4.3 ASCII alphabet | "emits only characters Kraken free text accepts" |
| §4.4 entropy bound | "leaves at least 8 random characters for the longest prefix" + "does not repeat itself across a bot-sized population" |
| §4.5 other venues untouched | `describe('getOrderId on every other venue is untouched')` — default / Binance broker code / OKX / MEXC / Hyperliquid |
| §4.1 spot only | "applies to Kraken SPOT only, not futures or paper" |
| §4.6 legacy ids untouched | Connector side: `specs/003` §4.9, `kraken/cl-ord-id.spec.ts` legacy-vs-new resolution |
| §5.1–§5.3 no other main-app change | Enforced by the diff: `main.ts` has exactly one changed hunk |

The prefix list the bounds run over is **read out of the source** rather than
hardcoded, so a future prefix longer than `GRID-STAB` fails §4.4 instead of
silently eating the random tail.
