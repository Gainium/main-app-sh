# Plan 105 — A Combo reload duplicates a safety order whose ladder price moved

Spec: `specs/105.a-combo-reload-duplicates-a-safety-order-whose-ladder-price-moved.md`.

## Solution

Change Combo's `getDiffForCheckOrders` (`src/bot/comboHelper.ts`). It still
computes the diff through `findDiffCombo` as before, and then removes from
`new` every `dealRegular` level whose `side@dcaLevel` matches a resting
`dealRegular` order in `activeRegularOrders` (§4.1). A level with no `dcaLevel`
on either side is unaffected (§4.2). Nothing is cancelled, and the ladder
builder is not touched (§4.3).

Pairing is done here rather than in `findDiff` (`main.ts`) or in `checkOrders`
(`dcaHelper.ts`), because both of those are shared with DCA and Grid. DCA ladder
levels carry no `dcaLevel` (§5.2), and the fill and minigrid paths depend on
`findDiff`'s price matching to cancel and replace.

### Why keep the resting order and not replace it

- The spec's goal is one order per level. Keeping the order meets it with no
  venue calls. Replacing it costs a cancel and a place per affected level on
  every reload, and the cancel can race a fill.
- A resting order that differs from the model by one tick is benign.
  `processFilledOrder` settles a fill by the order's own `dcaLevel`. The fill
  and minigrid paths (`findDiffCombo` against the resting orders mapped to
  grids) cancel and replace it when the ladder next reprices.

JIT tier: **0**. The change is a filter on the return value of one method that
is already Combo-specific. No extraction is warranted.

## Blast Radius

1. **Call sites.** `getDiffForCheckOrders` has one caller: `checkOrders`, in the
   restart branch (`this.serviceRestart || partiallyFilled`). It runs on cold
   restarts, keep-orders reloads (settings saves), and the user-start
   partially-filled pass. On all of them the only effect is that a level
   already resting an order is not placed again.
2. **`core/` submodule.** The file is in `main-app-sh`. Combo bot workers
   (`botCombo`, `botHedgeCombo`) pick it up after a pointer bump. No other
   service executes Combo's `getDiffForCheckOrders`.
3. **Contracts.** None. No GraphQL, REST, socket, queue or Mongo shape changes.
4. **Other tests.** Run the whole core mocha suite (`npm test`), in particular
   `comboPartialBaseEntry.spec.ts`, which drives the same mixin.
