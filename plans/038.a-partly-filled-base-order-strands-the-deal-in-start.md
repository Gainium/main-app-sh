# Plan 038 — A partly filled base order strands the deal in `start`

Spec: `specs/038.a-partly-filled-base-order-strands-the-deal-in-start.md`.

## Solution

Fix the root cause the spec's §3 names: `PARTIALLY_FILLED` has no handler in
either `checkBaseOrder` branch, and the enter-market branch — the deal's last
scheduled check — returns having cleared the only other timer.

1. **`core/src/bot/dca/partialBaseEntry.ts` (new).** The pure decision,
   `shouldSettlePartialBaseEntry({orderStatus, dealStatus, hasPendingCheck})`.
   Same shape and for the same reason as `bot/limitOnlyEntry.ts`, which was
   extracted from this exact method for issue #505: the branch condition is the
   whole defect, so it is testable without compiling the 22k-line module.
2. **`core/src/bot/dcaHelper.ts` — `settlePartialBaseEntry` (new method).**
   Orchestration only: log, `cancelOrderOnExchange(order)`, and if the row comes
   back `FILLED`, hand it to `handleUnknownOrder`. Warn and return otherwise.
3. **`core/src/bot/dcaHelper.ts` — two call sites**, one per branch, each
   placed AFTER the existing `hyperliquid` early return so §4.5's exemption is
   untouched:
   - the `dealId` branch (enter-market) passes `hasPendingCheck: false` — it has
     just cleared the reposition timer and is itself the timer that fired;
   - the `id` branch (reposition / restore) passes
     `hasPendingCheck: this.dealTimersMap.has(dealId)`.

### Contract decisions the spec left open

- **How "nothing else will look at it again" is read.** `dealTimersMap.has(id)`,
  not `!!entry.enterMarketTimer`. A fired `setTimeout` handle is not nulled, so
  the field stays truthy after the enter-market check runs and cannot be used to
  mean "still coming". `has()` is decisive for the two cases that matter:
  `placeBaseOrder` sets the entry the moment it arms anything, and a freshly
  started process holds no entry at all.
- **Nulling the fired `enterMarketTimer` was considered and rejected.** It would
  make `placeBaseOrder`'s `!dealTimer.enterMarketTimer` guard arm a *second*
  enter-market timer after the first fired, which is a live behaviour change
  (repeating market-entry attempts) that this defect does not need.
- **No new sizing/averaging code.** §4.4's chain is the one the engine already
  runs whenever a cancel races a fill; `startDeal` reads `executedQty`.

## Reuse check

Grepped `core/src/bot` and `core/src/utils` before writing anything:

- `cancelOrderOnExchange` (`bot/main.ts`) already cancels and promotes a
  cancelled-with-fills row to `FILLED` at its executed quantity — the promotion
  is skipped only for `dealTP` rows (`setFilledInsteadOfCanceled`), so a
  `dealStart` row takes it. **Used, not reimplemented.**
- `handleUnknownOrder` → `processFilledOrder` → `startDeal` is the existing
  route from a `FILLED` base order to an open deal, and the `id` branch already
  calls exactly this pair for a cancel that raced a fill. **Used as-is.**
- `dca/executedFill.ts`, `dca/baseOrderQty.ts`, `dca/partialTp.ts` were checked
  and do not fit: the first two answer "how much did this row execute", which
  `startDeal` already asks, and the third is take-profit-specific.
- No existing predicate covers "is another check scheduled for this deal", hence
  the one new module.

## Blast Radius

1. **Other call sites of `checkBaseOrder`:** four —
   `dcaHelper.ts` `placeBaseOrder`'s reposition timer (`id` set) and
   enter-market timer (`id` unset), `dcaHelper.ts` `restoreWork` (both set), and
   `comboHelper.ts`'s restore twin (both set). All four are covered by the two
   branches; combo bots inherit this method. No other repo calls it —
   `src/bot/index.ts`'s `checkBaseOrder` hits are an unrelated local variable.
2. **`core/` submodule:** yes. This is `main-app-sh`, shared and deployed
   platform-wide, so the parent pointer is bumped deliberately.
3. **Cross-service contracts (`core`/main-app `CLAUDE.md`):** none touched. No
   GraphQL shape, no REST route, no socket.io event name, no RabbitMQ queue, no
   Mongo schema field. The change writes only through existing order/deal save
   paths. The deals it opens emit the `bot deal update` the dashboards already
   consume — a deal moving `start` → `open` is the normal transition, not a new
   one.
4. **Other tests on this path that must stay green:** `limitOnlyEntry.spec.ts`
   (same method, #505), `resizeCancelPromotion.spec.ts` and
   `evidenceFreeFilledPromotion.spec.ts` (the cancel/promote behaviour this
   depends on), `cancelNoExchangeOrderId.spec.ts`, plus the full core suite.

## JIT legacy tier

**Tier 2** for the decision (pure module, no I/O, no framework import) and
**Tier 1** for `settlePartialBaseEntry` (a named method that still calls the
exchange and the order map). Not Tier 3: `checkBaseOrder` is not being given
ports and adapters on the back of a stranded-deal fix, and the repo already has
the Tier 2 shape for this method in `limitOnlyEntry.ts`.
