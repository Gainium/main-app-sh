# Plan 305 — warn on opposite-direction spot bots sharing one account's coins

## Build order

1. `src/bot/opposingSpotBot.ts` — pure decision (`opposingSpotPairs`) and the
   message (`opposingSpotBotWarning`), plus the subType constant.
2. `errorRulesCache.ts` — register the subType as per-pair.
3. `dcaHelper.ts` — `warnOpposingSpotBots()`: the four reads (dca/combo bots,
   dca/combo open deals), then `reportPerPairWarning` per pair.
4. Hook it after `checkSettingsPairs()` in core `start()` AND in the parent
   main-app `src/bot/dcaHelper.ts` `start()` override (the cloud bot workers
   run the parent's; combo inherits it).
5. `reloadBot` sets `warnOpposingSpotOnStart = rebuildIndicators` so a
   settings save, which reaches `start(false, true)`, warns as well.

## Decisions

- Warning only, per the brief. Reserving or refusing (the alternative fix) is
  a product decision and is not made here.
- No `ConditionLatch`. The check runs only on a user start/save, so it cannot
  repeat on its own; each save that still has the conflict reminds the user.
- Opposite bot counts if running, or stopped with an open deal (the reported
  case: the deal was still live after the SHORT bot was stopped).
- Reads are capped at 100 rows each and run once per start/save, never in the
  trading loop.

## Blast Radius

- Core `start()` and the parent `start()` gain one awaited, try/catch-wrapped
  call on user start/save of spot DCA/combo bots. On failure it logs a warning
  and returns; start continues unchanged.
- `reloadBot` sets one boolean; no other behaviour of the reload changes.
- New `botmessages` rows of a new per-pair subType. No schema change. The admin
  bot-error subType table treats an unknown subType as show-to-user
  (`boterrorsubtypes` is true by default), which is the intent.
- Grid, futures, hedge and terminal bots: untouched (gated on bot type and
  `futures`).
- No order, amount, status or deal field is written.
