# 015 — plan

Spec: [`specs/015.bot-message-symbol-moves-a-coalesced-row.md`](../specs/015.bot-message-symbol-moves-a-coalesced-row.md)

## Solution

`core/src/bot/main.ts`, `processError`, the `bucket !== null` branch only.

`onEvery` (the `$set` payload) carries `symbol`. For a PER-CONTRACT subType that
is inert — `symbol` is also in the upsert filter, so the `$set` can only rewrite
it to the value it already holds. For every other subType the filter has no
`symbol`, so the `$set` moves the row inside the UNIQUE
`botMessageCoalesceKey`, which is the collision in spec §1.2.2.

Change: split one payload in two at the point of use.

- `$setOnInsert` gains `symbol` when `!perSymbol` — the row is labelled once,
  when it is created, and never moved again.
- `$set` drops `symbol` when `!perSymbol` — both in the upsert and in the E11000
  fallback fold, which re-uses the same payload and today fails for the same
  reason the upsert did.
- The per-contract branch and the `bucket === null` (`always`-mode
  `createData`) branch are byte-identical to today: both still write `symbol`,
  the first from the filter, the second from the full merged document.

This is the spec §3 fix (pin, don't refresh). No new helper: it is a destructure
of an object literal that already exists three lines above.

Deliberately NOT done, per spec §3:
- widening the coalesce identity by `symbol` for all subTypes — the row-per-pair
  flood `DEFAULT_PER_SYMBOL_SUBTYPES` exists to prevent, and a contradiction of
  spec 007 §1.1.3;
- dropping `symbol` from the write entirely — spec §2.3 shows the row is the only
  record of the failing contract;
- taking `symbol` out of `botMessageCoalesceKey` — that would close the residual
  double-insert too, but it is a `syncIndexes()` drop-and-rebuild of a unique
  index on a 108k-row prod collection to fix a race that has produced exactly one
  duplicate group in the index's lifetime, and the rebuild would fail on that very
  group.

## JIT tier

Tier 0. The causal path is four lines of an object literal inside a method that
already reads as one linear write; there is no decision/I-O seam here worth
cutting, and `processError` is on every bot's hot error path. Extracting it would
be scope creep, not modernization.

## Blast Radius

1. **Other call sites.** `processError` is overridden in main-app
   (`src/bot/index.ts`) and reached via `handleErrors`; neither reads or writes
   the `$set`/`$setOnInsert` payloads, which are local to this method. No other
   writer of `botmessages` builds a coalesce key —
   `grep -rn 'botMessageCoalesceKey\|messagesDb.updateData' src core/src`.
2. **`core/` submodule.** Yes — `core/src/bot/main.ts` is `main-app-sh`, shared
   with the self-hosted build. Parent pointer bump needed at ship time. The change
   is confined to one method's own local write payload; it adds no export, no type
   and no signature change, so nothing downstream can see it except through the
   rows themselves.
3. **Documented contracts (root `CLAUDE.md` Danger List).** Item 12, shared Mongo
   `gainium` collections: `botmessages` is read directly by admin-app
   (`getBotErrors` → admin Bot Errors page) and by the dashboards. **No schema
   change, no index change, no new field, no field removed** — `symbol` is still
   written on every row, just once instead of on every occurrence. Item 4
   (socket.io `bot message`) is untouched: the emitted payload still carries the
   occurrence's own `symbol` from the local variable, not from the row.
4. **Other tests on this path.** `core/src/bot/perContractBotMessage.spec.ts`
   (spec 007) is the one that pins this exact write. It asserts on upsert KEYS,
   which this change does not touch, and includes `§1.1.3 an account-wide
   condition keeps one row per bot however many pairs hit it` — the closest
   existing guard on the bot-level branch. Must stay green, together with the full
   `core` suite.
