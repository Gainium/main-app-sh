# 032 — plan: an add-funds fill moves a deal past its next indicator DCA signal

Spec: [`specs/032.add-funds-skips-an-indicator-dca-level.md`](../specs/032.add-funds-skips-an-indicator-dca-level.md)

## 1. Solution

One expression in `dcaHelper.addDCAOrderByIndicator`:

```ts
.filter((d) => d.deal.levels.complete === index + 1)
```

becomes

```ts
.filter((d) => nextLadderLevel(d.deal) === index + 1)
```

`nextLadderLevel` already exists (`src/bot/dca/ladderLevels.ts`, spec `031`),
already carries the `consumesLadderLevel` override §4.4 needs, and is already
used by `executeNextDcaLevel`. Nothing new is introduced and no new test double
is required.

The `orders.find((o) => o.levelNumber === index + 1)` line below it is
deliberately untouched (§4.2).

### 1.1 Extraction tier

**Tier 0** on the decision itself — it was extracted in `031`; this is the third
call site adopting it. The surrounding method still mixes signal bookkeeping,
sizing and venue I/O, and is deliberately left that way: none of that is on this
defect's causal path, and pulling it apart would be a modernization sprung on a
one-line selection fix (runbook radius rule).

## 3. Blast Radius

**1. Other call sites.** `addDCAOrderByIndicator` is `private` with a single
caller, `checkIndicatorStatus` (`dcaHelper.ts:4418`), which is where `index` is
derived. `nextLadderLevel` gains a third caller and does not change.

Every reader of `levels.complete` was checked. Most are not asking this
question at all — `getDealDCAByMarketToCheck` already subtracts the additions
itself, `isDealForDCALevelCheck` compares `complete < all` (a bound, not a
position), and the alert and stats writers read it as a count of entries, which
is what it is.

**Two are in the same family and are NOT fixed here.** Neither is reached by
this change, both are unreproduced, and each needs its own spec:

- `getDealDCALevelToCheck` (`dcaHelper.ts:17392`) arms the DCA level check on
  `currentOrders` filtered by `dcaLevel > levels.complete`, i.e. it reads the
  counter as "the last ladder level filled". An addition inflates it, so the
  check would arm one level deeper per addition. It runs only for deals with
  `action: useOppositeBalance`, and its baseline off-by-one against `dcaLevel`
  needs establishing before anything is changed — `levels.complete` is 1 with
  only the base order filled, and the filter is strict `>`.
- `updateUsage`'s `levels.complete > 0 && levels.complete === levels.all`
  (`dcaHelper.ts:9516`) reads the pair as "the ladder is fully consumed" and
  caps the deal's reported maximum usage when it is. On the indicator path
  `levels.all` does not grow per addition (spec §1.3) while `complete` does, so
  additions can make that equality true before the ladder is spent, and
  understate `usage.max`.

Both are consequences of the same counter, and both are filed rather than
folded in: this spec's claim is reproduced and theirs are not, and a selection
fix should not carry two unverified behaviour changes with it.

**2. Is it under `core/`?** Yes — `main-app-sh`, shared, public, deployed
platform-wide. Submodule pointer bumped deliberately in the private parent; the
core commit message carries no issue ids, forum links or user detail.

**3. Documented cross-service contracts.** None. No API/GraphQL shape, no
socket.io event, no queue, no Mongo field. `levels` keeps its shape and its
values — this changes only which deals a signal selects.

**4. Other tests that must stay green.** `npm test` in full. No existing suite
drives `addDCAOrderByIndicator`; `ladderLevels.spec.ts` pins `nextLadderLevel`
itself and must not move.
