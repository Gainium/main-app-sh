# Plan 029 — the deal balance ledger counts orders that never executed

Spec: [`specs/029.deal-ledger-counts-orders-that-never-executed.md`](../specs/029.deal-ledger-counts-orders-that-never-executed.md).

## 1. Solution

The spec's Assumption puts the whole error in `updateDealBalances`'s reading of
the deal's order rows, so that is where the change goes — not in `closeDeal`'s
arithmetic, which is correct given a correct ledger.

One decision the spec left open: **how a row proves it executed nothing.**

- *Never reached a venue.* `orderId === '-1'` on a CANCELED row. §2.4 shows the
  split is total across production (14,721 vs 392), so this is a fact about the
  row, not a heuristic. Guarded on CANCELED specifically rather than "not
  FILLED" so a still-working row whose venue id has not been written back yet is
  untouched — those are excluded from the ledger by status anyway.
- *Reports zero.* Read `executedQty` as a number and use it when it parses,
  zero included. The `origQty` fallback keeps its original case — a field that
  cannot be read at all — and stays off the base order, whose partial fills
  `baseOrderQty.ts` documents must never be guessed at.

Rejected alternatives:

- *Reconcile `currentBalances` at close time instead.* Treats the symptom, and
  the reconciliation it would use is the same miscount, so it repairs a wrong
  ledger into the same wrong ledger.
- *Trust `deal.size` or the venue position as the oracle.* Both are derived
  from the same rows and were equally inflated on the affected deals
  (`size 31.22` against 20.466 of counted entry fills).
- *Cap the residual base at close using `tpOrder.acBefore/acAfter`.* The quote
  leg is wrong by −450 as well, so capping the base alone books −443 instead of
  +95. Only a correct ledger gives a correct figure.
- *Stop writing `executedQty === origQty` on unplaced safety rows.* Correct in
  the long run, but 14,721 such rows already exist and are read on every bot
  load; the read side is what decides the money today.

## 2. Build order

1. `src/bot/dca/executedFill.ts` — pure `executedFillQty(order)`; no DB, queue
   or HTTP import. Same shape as the existing `baseOrderQty.ts` /
   `partialTp.ts` decision modules.
2. `src/bot/dca/executedFill.spec.ts` — unit, pinned to the real row shapes.
3. `src/bot/dca/phantomFillLedger.harness.spec.ts` — drives the real
   `updateDealBalances` and the real `closeDeal` over the deal's recorded rows.
4. `dcaHelper.updateDealBalances` — filter and both reduces call
   `executedFillQty`.
5. `dcaHelper.closeDeal`, the spec `024` rebuild — same reading for `replay`
   (spec §4.5).

## 3. Blast radius

1. **Other call sites.** `executedFillQty` is new; nothing else calls it.
   `updateDealBalances` is called from `dcaHelper` (5 sites), `comboHelper`
   (3 sites, including bot start and `calculateDealBalances`) — every one of
   them wants the corrected reading, which is the point. The spec `024` rebuild
   inside `closeDeal` is the only other replay of these rows and is updated with
   it.
2. **`core/` submodule.** Yes — this file is shared and deployed platform-wide
   (cloud + self-hosted, DCA and combo bot workers). The pointer bump is
   deliberate.
3. **Documented contracts.** None touched: no GraphQL shape, no socket event,
   no queue name, no `BaseReturn`, no Mongo schema field. `currentBalances` is
   an existing field whose *value* becomes correct; its type and readers are
   unchanged.
4. **Deliberately NOT touched.** `dealOrders` at `closeDeal` L2428 keeps its own
   filter, so the fee loop that also walks it (`feeBaseFull`/`feeQuoteFull`,
   `feeByAsset`, spec `014`) computes exactly what it computed before. Widening
   there would change fee accounting on every closing deal, which this bug does
   not require.
5. **Other tests on this path.** `lostLedgerClose.harness.spec.ts` (spec `024`)
   replays the same rows and must stay green — it does. `baseOrderQty.spec.ts`,
   `tpCoverageReconcile.spec.ts`, `partialTp.spec.ts` and
   `nanOrderRefusal.spec.ts` read `executedQty` through their own helpers and
   are untouched.

## 5. Left open

The four already-closed deals, the bot aggregate `profit` and the user's profit
history are persisted values that no code recomputes; they keep their inflated
figures until a migration restacks them. Spec §5.
