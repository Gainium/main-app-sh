# Plan 026 — re-size cancel status, and the double-counted close in `grossEntryVolume`

Spec: [`specs/026.resize-cancel-promoted-and-gross-entry-double-counts-closes.md`](../specs/026.resize-cancel-promoted-and-gross-entry-double-counts-closes.md).
Issue #717.

## Build order

1. `core/src/bot/main.ts` — normalise the row's status for a re-size cancel
   (spec §4.1). Independent of step 2; ship-safe on its own.
2. `core/src/bot/dca/baseOrderQty.ts` — `grossEntryVolume(dealSize, reduceFundsBase)`
   (spec §4.2), and correct the module doc comment that asserts `deal.size` is
   net of closes.
3. `core/src/bot/dcaHelper.ts` — the one call site, line 14170. `reduceFundsBase`
   is already computed at 14133; `add` and `pendingReduceFunds.base` stop being
   passed.

## Contract decisions the spec left open

- **`grossEntryVolume`'s signature.** The spec fixes the value, not the shape.
  Decision: change the parameters rather than keep `(dealSize, add, pendingRF)`
  and subtract inside. `add` is a bundle of three quantities with three
  different answers (take-profit closes: do not add back; executed
  reduce-funds: add back; pending reduce-funds: do not), and the only
  parameter that can be used correctly is the one that is actually needed.
  Sole non-test caller is `dcaHelper.ts:14170`.
- **How §4.1 forces the status.** Decision: normalise `order.status` right after
  the copy loop, not by excluding `status` from the copy. Excluding it would
  change the DEFAULT path too — that path is the one every close/teardown
  caller depends on, and it is the venue's status it reads.
- **The `executedQty >= origQty` escape.** Decision: keep it, so a cancel that
  genuinely raced a complete fill is still recorded FILLED and the
  `result.status === 'FILLED'` compensation at `dcaHelper.ts:13844` still fires
  for the case it was written for.

## JIT legacy tier

**Tier 0 for `main.ts`.** The change is four lines inside
`cancelOrderOnExchange`, which is already the single place that decides what a
cancel response means. Extracting the decision would mean threading the venue
response shape through a new module for one boolean; the runbook's radius rule
says the touched radius is the guard itself. Its behaviour is pinned by
`resizeCancelPromotion.spec.ts` driving the real method off the prototype.

**Already Tier 2 for `baseOrderQty.ts`** — it is a pure module with no
imports, extracted for exactly this reason by spec `017`. Nothing to extract;
the fix is arithmetic inside it.

## Blast Radius

1. **Other call sites.** `grossEntryVolume`: one non-test caller
   (`dcaHelper.ts:14170`) plus `baseOrderQty.spec.ts` — grepped, none other.
   `cancelOrderOnExchange`: 19 call sites, of which exactly **two** pass
   `promotePartialToFilled: false` (`dcaHelper.ts:10244`, `dcaHelper.ts:13838`).
   Every other call site keeps the default `true` and is not reached by the new
   branch at all.
2. **`core/` submodule.** Both files are under `core/` (`main-app-sh`) — shared,
   public, deployed platform-wide. `main.ts`'s `cancelOrderOnExchange` is the
   bot engine's only cancel path and runs on cloud and self-hosted alike. The
   parent pointer is bumped by the ship path, not here.
3. **Documented cross-service contracts** (`main-app/CLAUDE.md`): none touched.
   No GraphQL shape, no `/api/v2` shape, no socket.io event name, no archive
   queue, no Mongo schema field. `order.status` values written are the same
   enum strings the row already carries; this changes *which* of them a re-size
   cancel gets, not the set.
4. **Other tests on this path.**
   - `src/bot/dca/baseOrderQty.spec.ts` — three `grossEntryVolume` cases, one of
     which (`186.79, -51.5 -> 238.29`) asserts the behaviour spec §1.2 shows is
     wrong. Rewritten under §2.2's evidence, and recorded here as a **spec
     disagreement resolved in the spec**, not a test edited to go green.
   - `src/bot/dca/tpSizingFromPosition.harness.spec.ts` (spec 017) — every case
     passes `grossEntry: dealSize`, i.e. a deal that has closed nothing, so all
     of them are unaffected by §4.2 and must stay green. This is the #702
     regression guard.
   - `src/bot/cancelNoExchangeOrderId.spec.ts` (spec 011) — the other
     `cancelOrderOnExchange` suite; all of its cases go down the `notok` branch
     and never reach the copy loop.
   - `src/bot/dca/tpCoverageReconcile*.spec.ts`, `partialTp.spec.ts`,
     `tpCloseOutcome.spec.ts`, `dealOutcome.spec.ts` — the surrounding
     take-profit decisions. Must stay green.
   - Full `npm test` in `core/`, plus `tsc` in `core/` AND in the parent
     (`exchange-connector`'s lesson: a shared-module signature change can break
     a build that does not import the file directly).

## Verify plan against spec (gate 4)

- §1.1 → build step 1 → 6 tests. The Solution fixes the cause §3.1 names (the
  copy loop overwriting the field the guard reads), not the symptom (the deal
  being closed), which `dealOutcome`'s `dealLeftOpenSize` already catches
  downstream.
- §1.2 → build steps 2+3 → 7 tests. The Solution fixes the cause §3.2 names
  (the closed quantity added back to a `deal.size` that never had it removed),
  not the `position` branch that exposed it — that branch is correct for the
  short-order-map case it was written for, and §017's suite pins it.
- §2.2 / §2.3 are evidence, discharged by the two `grossEntryVolume` unit cases
  and the harness's reduce-funds case.
- §5 out-of-scope items appear in no build step.
