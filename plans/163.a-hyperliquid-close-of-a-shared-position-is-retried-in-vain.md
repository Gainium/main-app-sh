# 163 — plan: stop retrying a Hyperliquid close that only part of a shared position

Spec: [163](../specs/163.a-hyperliquid-close-of-a-shared-position-is-retried-in-vain.md).

## Solution

Root cause per spec §3: `closeDealById` retries every notional refusal as if
the price had slipped. Before it decides to retry, a notional refusal on a
venue that accepts a sub-minimum close only for the whole position asks the
venue for its position once. If the venue answers with a position on this
side larger than the close, the retry is skipped and the existing terminal
branch runs, reporting a specific message instead of the venue's text.

- **Decision — pure, JIT tier 2:** `isPartialCloseOfSharedPosition` in
  `src/bot/dca/sharedPositionClose.ts`, built on `findVenuePosition`
  (spec 005) so the two position readings cannot drift. Fail-safe like
  `reconcileDealAgainstVenue`: anything but a venue answer showing a larger
  position leaves today's behaviour.
- **Orchestration — one private method** on the helper,
  `sharedPositionCloseRefusal`, which gates on the venue list before making
  any call, probes `futures_getPositions` once, and returns the message to
  report, or nothing.
- **Call site:** the string-refusal block of `closeDealById`. The retry
  condition gains `&& !shared`; the terminal branch passes the specific
  message to `handleOrderErrors` only. Every other consumer — the
  trailing-close classifier, the restore, `positionAlreadyClosed` — keeps
  reading the venue's own `result` (spec §1.3).

Contract decisions the spec left open:

- **The quantity compared** is `tpOrder.qty`: on futures the adaptive-close
  and fee-sizing fallbacks are both gated `!this.futures`, so it is what was
  sent.
- **The message** does not contain the venue's text, so the bot-error rule
  keyed on `must have minimum value of $10` cannot override it; a separate
  rule maps it to its own subtype (admin data, outside this repo).
- **Probe only after a refusal**, never before sending: a close that is the
  whole position must keep going out exactly as today (spec §1.3).

## Build order

1. `main-app-sh` (this repo): module + call site + specs, release patch.
2. `main-app` parent: bump the `core/` pointer, release patch.
3. Admin data: bot-error rule for the new message (substring of its fixed
   wording) → its own subtype, user-visible, stops the bot as today.

## Blast Radius

1. **Call sites.** `closeDealById` only (DCA and combo through the shared
   helper). The probe runs only for `hyperliquidLinear`, only after a
   notional refusal, at most once per attempt; with the retry skipped, a
   shared-position close makes one venue order and one position read where
   it made six orders before. Other venues: no new calls.
2. **Under `core/`** — public `main-app-sh`, every DCA/combo/hedge worker.
3. **Contracts.** No API/socket/queue/schema change. User-visible: the error
   text for this case. The bot-error classification reads the new text.
4. **Tests:** `dca/positionFlatDirectionRefusal.harness.spec.ts` (075),
   `dca/refusedCloseRestore.harness.spec.ts`,
   `dca/refusedCloseDeadlock.harness.spec.ts`,
   `dca/trailingTpCloseRetry.harness.spec.ts`, `dca/trailingCloseRetry.spec.ts`,
   and the full suite.
