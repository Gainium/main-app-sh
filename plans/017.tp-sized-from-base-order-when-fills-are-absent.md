# 017 — Plan

Spec: `specs/017.tp-sized-from-base-order-when-fills-are-absent.md` (issue #702).

## Solution

Two edits, both in `core/`, both narrow.

### A. `src/bot/dca/baseOrderQty.ts` — cross-check the base-order row (§3)

`resolveBaseOrderQty` already computes `fromDeal = grossEntry - filledQty`, the
volume the counted fills do not explain. Today that number is only consulted when
the base-order row is absent. Compute it first and consult it on both branches:
if the deal holds more than `filledQty + boFromOrder` accounts for, the remainder
is an entry fill the order map has lost, and `fromDeal` is the base order's real
contribution.

Direction is one-way on purpose: the resolved quantity can only be RAISED to the
position, never lowered below the row. Lowering it is a different decision with a
different failure mode (an over-stated position sends a take-profit the venue
rejects, which leaves the deal with none at all — the AIOZ failure the `deal`
branch was written for), and §2.3 shows the two measures agree on 99.6% of the
fleet, so there is nothing to lower.

Both sides are compared through `floor` — round-DOWN to the pair's base precision
— so a sub-step float residue in `deal.size` (`452.20000000000005`,
`989458.9999999998`) cannot look like a missing order.

New `BaseOrderQtySource` value `'position'`, so the log line at the call site can
say what actually happened. Reusing `'deal'` would have made the existing message
(`"has no base order on record"`) a lie for the new case, which is the shape of
error that costs an operator an hour.

### B. `src/bot/dca/tpCoverageReconcile.ts` — `rearm` on an undersized resting TP (§4.1)

`rearm: staleTps.length > 0 || live.length === 0 || state === 'under'`.

`under` means the deal needs a bigger take-profit. `placeOrders` looks the resting
take-profit up by `['NEW','PARTIALLY_FILLED']` and, when it can sell less than the
replacement, cancels it with `promotePartialToFilled: false` and sends the
replacement in the SAME pass (`dcaHelper.ts:13234-13308`) — that is the path this
re-arm feeds. `over` is unchanged.

### Not doing

- **The `placeOrders` resize branch** the brief suggested rewriting to "place in
  the same pass instead of cancelling and waiting": it already does. There is no
  `continue` between the cancel at `:13287` and `sendGridToExchange` at `:13308`;
  only a `return` on the venue answering `FILLED`. The
  `"Wait until cancel the order …"` wording is stale text, not behaviour, and
  changing the hottest money path to fix a log string is not worth the risk.
- **F193, COIN-M units** — spec §4.2. Real, separate, and untouched by either
  edit.

## Blast Radius

1. **Other callers of `resolveBaseOrderQty`** — one:
   `dcaHelper.getTPOrder:13522`. Grepped; `grossEntryVolume` has the same single
   caller plus its own spec.
2. **`core/` submodule** — YES. Both files are shared code, embedded in every
   `main-app-sh` consumer and deployed platform-wide. The parent pointer has to be
   bumped deliberately.
3. **Cross-service contracts** — none touched. No GraphQL shape, no socket event,
   no queue name, no Mongo schema field. `BaseOrderQtySource` is internal to
   `core/src/bot/dca` and reaches production only as text inside a log line.
4. **Behaviour at risk** — the take-profit QUANTITY on every DCA/Combo deal.
   Mitigated by direction (raise only), by the precision floor, and by §2.3:
   on 8,704 of 8,740 live deals `deal.size` and the entry rows agree, so the new
   branch is inert. The 9 deals where `size > rows` are multi-take-profit deals
   already outside the single-TP path.
5. **Tests that must stay green** — `baseOrderQty.spec.ts` (the AIOZ regression
   set), `tpCoverageReconcile.spec.ts`, `tpCoverageReconcile.harness.spec.ts`,
   `tpCoverageRepairScope.spec.ts`, `partialTp`, `tpFees`, `multiTpCompletion`,
   and the parent repo's `tests/processing/tpBurstInvariant.ts`.
