# 250 — Plan: an unknown-order lookup never moves an order row backwards

Spec: `specs/250.unknown-order-lookup-never-moves-a-row-backwards.md`.

## Solution

1. New pure predicate `venueAnswerRegressesRow(local, venue)` in
   `src/bot/venueAnswerRegression.ts` (JIT tier 2). It takes plain
   `{status, executedQty}` shapes and imports nothing.
2. In `MainBot._runUnknownOrderLadder` (`src/bot/main.ts`), right before the
   existing `find.status !== request.data.status` overwrite: convert the
   venue's fill size the same way the spec `235` guard above it does, and
   if the predicate says the answer regresses the row, log it and return
   the row (FILLED) or `null` (anything else) without writing.
3. Nothing changes on the combo close path. A returned FILLED row already
   flows through `cancelAllOrder` → `handleUnknownOrder` →
   `processFilledOrder`, which dedups through `processedFilled`. The row
   stays FILLED in the order map, which is what `updateDealBalances` reads.

The existing `orderSnapshotMerge.statusRank` is not reused: it ranks
CANCELED equal to FILLED, so it would block a written-off row from being
revived by a live venue answer (spec §1.2).

## Blast radius

- Callers of `_handleUnknownOrder`: every bot type, through the cancel paths
  in `cancelOrderOnExchange`, the combo/DCA reconcile paths and the
  `sendOrderToExchange` write-off guard. The guard only stops writes that
  would move a row backwards. FILLED → FILLED was already a no-op
  ("already processed").
- `core/` file: shared by every main-app deployment (cloud and
  self-hosted). No contract shape changes: no GraphQL, socket, queue or
  schema change.
- Tests that must stay green: `unknownOrderKeepsMergedRemainder`,
  `unknownOrderVenueFillSize`, `unknownOrderByIdVenueDbFallback`,
  `cancelNoExchangeOrderId`, `orderNotFound`, and the full core suite.
