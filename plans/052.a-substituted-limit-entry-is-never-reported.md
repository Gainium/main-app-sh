# 052 — Plan

Spec: [`specs/052.a-substituted-limit-entry-is-never-reported.md`](../specs/052.a-substituted-limit-entry-is-never-reported.md).

Additive only. Spec §4.4 lists what must not move: the refusal predicate, the
`forceLimit` re-place, the termination guard, the existing `handleLog` line.
The red run confirms that boundary — `still re-places the base order as a LIMIT`
passes before any engine change, so the only absent behaviour is the report.

## §1 Build order

1. `bot/utils.ts` — `limitOnlyEntryReplaced` subType constant, beside
   `closeNotActioned` / `trailingCloseFailed` and their "deliberately NOT in
   `errorDict`" note, which is the reason it lives in that file.
2. `bot/limitOnlyEntry.ts` — `limitOnlyEntryReplacedMessage`, beside the
   predicate that decides the substitution it describes.
3. `bot/conditionLatch.ts` — `limitOnlyEntryFallback` latch reason.
4. `bot/errorRulesCache.ts` — add the subType to
   `DEFAULT_PER_SYMBOL_SUBTYPES` (spec §4.3).
5. `bot/dcaHelper.ts` — `reportLimitOnlyEntryReplaced`, placed immediately after
   `reportTrailingCloseFailed`, whose shape it copies; the latch-gated call in
   the fallback branch; the latch `clear` on the venue-accepted path.

Steps 1–3 landed before the red run so the tests could fail on the missing
report rather than on a missing import (gate 2).

## §2 Contract decisions the spec left open

- **`event` string on the `botevents` row: `Bot warning`.** Before `0c2cdcd`
  this refusal reached `handleErrors`, which writes ``Bot ${setError ? 'error'
  : 'warning'}``. The report is a warning (§4.1, the entry succeeded), so `Bot
  warning` is the faithful analogue of the row the regression removed.
- **No `shouldProceed()` guard**, unlike `reportTrailingCloseFailed`. That guard
  exists because the trailing sweep runs on a timer and may outlive ownership.
  Here `placeBaseOrder` has already decided to act on this bot and has already
  sent an order; a gate that could silently drop the report would re-create the
  defect in miniature.
- **Latch instance: the existing `standingConditionLatch` on `MainBot`**, not a
  new one — so the 24 h `STANDING_CONDITION_REARM_MS` re-arm applies, and a book
  that stays limit-only for days still reminds the user daily.

## §3 JIT legacy tier

**Tier 0 for the branch itself** — the decision logic it needs
(`shouldFallBackToLimitEntry`) was already extracted pure by `3f3fa20`, and the
message is extracted pure here alongside it. The engine change is a call, not a
rewrite. A higher tier would mean restructuring `placeBaseOrder`, which is 400
lines of unrelated causal path and is exactly the drive-by the runbook forbids.

## §4 Blast Radius

1. **Other call sites.** `shouldFallBackToLimitEntry` has one caller
   (`dcaHelper.ts`). The three new exports are new names — no existing call site
   resolves to them. `comboHelper.ts:5057` has the parallel slippage ladder but
   no limit-only branch, so it is untouched.
2. **`core/` submodule.** Yes — every file here is under `core/`
   (`main-app-sh`), so this is shared/public and deploys platform-wide. The
   parent pointer is bumped deliberately at ship time. The public-changelog and
   public-commit-message policy applies: no issue numbers, no user ids, no
   affected-account counts in anything that lands in `core/`.
3. **Cross-service contracts.** None of the Danger List entries is touched. No
   GraphQL field, no REST shape, no socket event NAME. The report reuses the
   existing `bot message` emit, whose payload already carries `subType` as an
   additive field — dashboards that do not know this subType render it as any
   other bot message, which is the intended behaviour.
   One shared-collection note: `botmessages` gains rows with a new `subType`
   value. Admin Bot Errors groups by subType and will show it as a new group
   with no configured behaviour row; that is the documented fail-safe path
   (`getSubTypeBehavior` → null → shown, raw message), and an admin can tune it
   from `boterrorsubtypes` later with no deploy.
4. **`DEFAULT_PER_SYMBOL_SUBTYPES`** is read by `isPerSymbolSubType`, which
   feeds both `buildCooldownKey` and the `botMessageCoalesceKey` filter. Adding
   a member only changes behaviour for occurrences carrying THAT subType, so no
   existing subType's rows move inside the unique index — the failure mode spec
   015 documents. Nothing else reads the set.
5. **Other tests on this path.** `limitOnlyEntry.spec.ts` (the predicate) and
   `conditionLatch.spec.ts` must stay green, plus the full `npm test` suite.

## §6 Verification

Gate 6 is `npm test` in `core/` plus `npx tsc --noEmit` in **both** `core/` and
the parent — a widening in `core/` alone can break the parent build, which
compiles its own copy of these sources.

The spec's §1.2 claim is about a database row, so it is settled against a
database: `limitOnlyEntryReport.harness.ts` drives the real
`MainBot.prototype.processError` over the real `botMessageDb` against local
Mongo, before and after, and reads the row back out.
