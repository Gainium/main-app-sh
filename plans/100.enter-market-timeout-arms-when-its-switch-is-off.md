# Plan 100 — "Enter Market Timeout" arms when its switch is off

## Solution

Derive all LIMIT-order timeouts in one pure function,
`src/bot/dca/limitTimeouts.ts` `resolveLimitTimeouts(settings)`, and assign
them in `setClassProperties()` — the one method both `start()`s (core's and the
main-app parent's override) call before anything reads the values. Delete the
switch-gated override block from both `start()`s.

Three outputs:

- `enterMarketTimeout` — base-order entry timer; `0` unless the switch is on
  with usable seconds (§4.1/§4.2). The existing `enterMarketTimeout === 0`
  branch in `checkBaseOrder` then re-arms the reposition timer indefinitely and
  the enter-market timer is never armed; `notUseLimitReposition` keeps leaving
  the order untouched. No timer code changes.
- `orderLimitRepositionTimeout` — `0` when the user's timeout is shorter than
  10 s, else `10000`; recomputed on every call (§4.4).
- `limitFallbackTimeout` (new field) — the pre-fix value (user value, or
  `35000`), read by the close-by-limit branch of `checkTPOrder` and by the
  spec-057 top-up window instead of `enterMarketTimeout` (§4.3), so those two
  paths behave exactly as before.

JIT tier: **2** — the derivation is pure and naturally separable; the timer
code is Tier 0 (not changed).

## Decisions the spec left open

- **Close-by-limit keeps its fallback.** The switch sits in the base-order
  section of both dashboards (V1 `BaseOrder.tsx`, V2 strategy settings), so it
  does not govern closes. That branch's `>` gate (vs `<` in the base path)
  plus a forced-market timer on the *reposition* interval means close-by-limit
  goes to market after 10 s today. That is left exactly as is — not mirrored,
  not changed. Changing it would alter every manual limit close and is not this
  bug.
- **Top-up window keeps 45 s** for a switch-off bot via `limitFallbackTimeout`
  rather than a separate constant, so a switch-on bot's widened window
  (spec 057 design) also stays as is.
- **Grid bot** (`helper.ts` `closeBotByTp`) is out of scope: it never reads
  these settings and keeps the `main.ts` `35000` field default.

## Blast Radius

1. Call sites: `enterMarketTimeout` is read in `checkBaseOrder` (behaviour
   change, intended), `checkTPOrder` close-by-limit and `topUpSettledBaseEntry`
   (switched to `limitFallbackTimeout`, value unchanged), grid `helper.ts`
   (separate class, untouched). `setClassProperties` is also called after a
   deal settings update — the derivation is idempotent.
2. `core/` file — shared with every main-app deployment (cloud and
   self-hosted); parent pointer bump needed. The parent's `src/bot/dcaHelper.ts`
   `start()` override is edited too (block deleted).
3. No GraphQL, socket, queue or DB shape touched. Settings fields are read
   only.
4. Tests on this path: `partialBaseEntry.harness`, `baseEntryTopUp.harness`,
   `settleCancelNoFillReport.harness` (fixture now also sets
   `limitFallbackTimeout`, the field the window reads), `limitOnlyEntryReport`.
