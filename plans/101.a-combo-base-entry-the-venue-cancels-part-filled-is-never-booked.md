# 101 — plan

Spec: `specs/101.a-combo-base-entry-the-venue-cancels-part-filled-is-never-booked.md`.

## Build order

1. `src/bot/comboHelper.ts` — import `shouldSettlePartialBaseEntry` and
   `pickRestoreBaseEntry` from `./dca/partialBaseEntry`.
2. `processCanceledOrder` `dealStart` branch: same predicate and inputs as
   `dcaHelper.processCanceledOrder`; settle via `settlePartialBaseEntry`, else
   `checkUnfilledBaseEntryCancel` (unchanged path for an unfilled cancel).
3. `restoreWork` start-deal block: read every `dealStart` row of the deal (no
   status filter, full documents), choose with `pickRestoreBaseEntry`; if the
   chosen row is terminal and the order map does not hold it, `setOrder` it
   (without the Redis write) before `checkBaseOrder`.

JIT tier: 0. The decision is already a pure, tested module (`dca/partialBaseEntry`,
spec 048); this change only wires it into the Combo call sites.

## Contract decisions left open by the spec

- Restore reads full documents (no projection) so the row can be put back into
  the map on a cold load. One row per deal in the normal case; a handful when
  entries were re-placed. Cost is negligible and restore-only.

## Blast Radius

1. Call sites: `comboHelper.processCanceledOrder` is the order queue's
   `onCanceled` for Combo (and Hedge Combo, which builds on the Combo mixin).
   `restoreWork` runs once per bot start. No other caller.
2. File is under `core/` (main-app-sh) — shared by every main-app worker; the
   parent's submodule pointer must be bumped at ship.
3. No GraphQL/REST/socket/queue shape changes. Writes: the existing
   `promoteEndedBaseEntry` promotes the `dealStart` order row to `FILLED` and the
   deal opens through the existing `startDeal`. That is an order execution being
   booked — money-adjacent; flagged amber.
4. Tests that must stay green: `comboGridCancelLedger.spec.ts` (f4416a9's unfilled
   base cancel), `dca/venueCanceledBaseEntry.harness.spec.ts`,
   `dca/partialBaseEntry.harness.spec.ts`.
