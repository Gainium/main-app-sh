# 132 — Plan: the Deal Returns series stops at the newest 500 closed deals

Spec: [specs/132](../specs/132.deal-returns-series-capped-at-500-deals.md)

## Solution

1. Tier 1 extraction (JIT runbook): move the `getBotProfitChartData`
   aggregation pipeline out of the resolver, unchanged, into
   `dealReturnsPipeline(userId, botId)` in `src/utils/dealReturn.ts`, next to
   `dealReturnPercentage`, the per-deal math the same series uses. It builds
   a stage array and does no I/O, so a test can check it with no database.
   Not Tier 2/3: the resolver still owns the DB call, and nothing else on the
   path needs pulling apart.
2. Drop the `{ $limit: 500 }` stage. Keep the `$match`, `$project` and
   `$sort` stages exactly as they are.

No safety ceiling: the largest bots hold tens of thousands of deals, and
the series is ~2 MB of `{ value, time }` at that size. Any ceiling low enough
to matter would bring back the empty-chart symptom on those bots, and the
dashboard would then need a "showing latest N" label, which would mean a
GraphQL response field and a paired frontend change.

## Blast Radius

1. Call sites: `getBotProfitChartData` is the only user of the pipeline.
   GraphQL consumers: V2 `useBotProfitChartData` (DrawerPerformanceChart's
   Deal Returns panel) and V1 `botStats.tsx`. Both plot whatever array they
   get, and neither assumes 500 or fewer points.
2. `core/` (main-app-sh): this is shared code, but only main-app's GraphQL
   server uses the resolver.
3. Contracts: the GraphQL response shape `[{ value, time }]` stays the same.
   Only the number of elements changes.
4. Tests: the new `src/utils/dealReturn.spec.ts`. No other spec covers the
   resolver.
