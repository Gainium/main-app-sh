# 072 — Plan

Spec: [`specs/072.a-delisted-pair-strips-a-single-pair-bots-only-pair.md`](../specs/072.a-delisted-pair-strips-a-single-pair-bots-only-pair.md)

## §1 Build order

1. **`src/bot/dcaHelper.ts` `checkSettingsPairs()`** — give the prune a floor.
   Register `pairsNotFound` unconditionally (the caller's stop branch reads it),
   then prune only when something would be left. Spec §2.1.
2. **`src/bot/index.ts` `changeDCABot()` / `changeComboBot()`** — key the
   single-pair refusal on "the bot HAS a pair", not on `useMulti` alone, and
   route the empty-pair case through the same length validation and `symbol`
   rebuild the multi branch already uses. Spec §2.2.
3. Version bump + CHANGELOG (repo ceremony).

## §2 Contract decisions the spec left open

- **Where the floor lives.** Inside `checkSettingsPairs`, not in the two
  `start()` callers. The callers already agree on "all pairs missing ⇒ stop the
  bot"; duplicating a floor in both (core's `start()` and main-app's override,
  which is the one the bot service actually runs) would be two places to drift.
  `checkSettingsPairs` is the only writer of the emptied `settings.pair`.
- **`pairsNotFound` is populated whether or not anything was pruned.** It is
  today only populated inside the prune branch. Both `start()` implementations
  decide "stop the bot" off `pairsNotFound.size`, so a floor that skipped the
  prune without registering the set would leave the bot *running* with a dead
  pair — strictly worse than the bug. This is the one line that must not be
  missed.
- **`calculateUsage()` stays tied to an actual prune.** It re-derives the bot's
  cost from the pair count; nothing changed, so nothing to re-derive.
- **The repair accepts exactly one pair.** A `useMulti:false` bot takes one
  pair; the empty-pair unlock must not become a back door to a multi-pair
  single bot. Anything other than length 1 keeps the existing refusal
  (`Cannot change pair for non-multi pairs bot` for >1, `Need to specify at
  least one pair` for 0).
- **Combo gets the identical change.** `changeComboBot` carries a
  character-identical refusal and combo bots share `dcaHelper`'s prune —
  production has 15 emptied combo bots. Fixing only DCA would leave the
  dashboard unlock (out of repo, spec §1.6) silently broken for combo, since
  its payload mapper treats DCA and combo the same.
- **No `useMulti` bot behaviour changes.** Every multi branch keeps its
  condition; the new predicate only *widens* which bots reach it.

## §3 Blast Radius

1. **Other callers of `checkSettingsPairs()`** — two, both `start()`:
   `core/src/bot/dcaHelper.ts:20091` and the main-app override at
   `main-app/src/bot/dcaHelper.ts:842` (the live one; the parent class extends
   core's helper and re-implements `start()`). Both branch on
   `pairsNotFound.size` and `settings.pair.length > 1 && useMulti`. Walked both
   for each spec row:
   - single-pair, pair retained → `useMulti` false → `Bot will stop` (unchanged
     outcome, no data loss);
   - multi with all pairs missing, pairs retained → `size < pair.length` is
     `N < N` → false → `Bot will stop` (unchanged outcome);
   - multi with some missing → prune still happens, so both callers see exactly
     what they see today.
   No caller edit needed, and neither `start()` reads a "was anything pruned"
   signal.
2. **`core/` submodule.** Both files are in `main-app-sh` — shared with the
   self-hosted edition and every service embedding this `core/`. `dcaHelper` is
   the DCA/combo/hedge engine; `index.ts` `Bot` is the API-side bot service.
   No exported signature, type, or GraphQL/REST/socket shape changes: the diff
   is entirely inside two method bodies.
3. **Cross-service contracts (`main-app/CLAUDE.md`).** None touched. No
   GraphQL SDL change, no `/api/v2` shape change, no socket event, no queue, no
   Mongo schema change. `changeDCABot`'s *refusal set* narrows, which is a
   behaviour change visible to the dashboards and to `/api/v2` bot updates —
   strictly permissive (a call that used to be refused may now succeed); no
   previously-accepted call becomes refused.
4. **Other tests on these paths.** `npm test` (mocha, `src/**/*.spec.ts`) is
   the whole suite and must stay green — in particular the specs that drive
   `dcaHelper` off its prototype (`openNewDealRefusal`, `qtyStepGuard`,
   `notEnoughBalanceReasons`, `limitOnlyEntryReport`, …).

## §4 JIT extraction tier

**Tier 0.** `checkSettingsPairs` is already a small, single-purpose method, and
the `changeDCABot` guards are three adjacent `if`s. There is no decision logic
tangled with I/O to lift out — the prune's only I/O is the `updateData` it is
supposed to make, and the guards' only I/O is the read that already happened.
Extracting either would add a module and a test boundary without removing a
smell on the path being touched. A higher tier here would be scope creep on a
`core/` file with platform-wide blast radius.

## §6 Gate 4 — plan vs spec

Walked §1 and §2 of the spec section by section. Every numbered behaviour row
has a test above. The two changes are the two defects the spec's §1.4
Assumption names, in the order it names them — the prune's missing floor and
the refusal's wrong key — not a symptom fix downstream of either. §1.5's
non-goals are all respected: no migration, multi-pair pruning untouched, the
single-pair product rule untouched for configured bots, grid untouched. No
decision above was closed by the spec.
