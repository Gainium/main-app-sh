## Contract decisions the spec left open

- **Mutex, not `$inc`.** The spec allowed either. `$inc` was rejected: every
  other writer of `bot.profit` (`createTransaction`, `profitAfterPositionClosed`,
  both close paths) persists an ABSOLUTE value built from `this.data`, so a
  single `$inc` site would race those `$set`s rather than replace them, and
  converting all of them is a far wider change than the defect needs. The mutex
  keeps one writer model and matches how the engine already serialises per-bot
  work.
- **No `limit` on the key.** `IdMutex`'s `limit` argument makes the wait queue
  a `getFixedArray`, which EVICTS a waiter whose promise then never settles.
  `createTransaction` is awaited by nothing, but its own tail (`limitOrders`)
  reads `mutex.get(this.botId)` and an evicted promise would leak a lock; an
  unbounded queue is correct here, and the queue is bounded in practice by the
  fills one bot can take.
- **Why the test's stubs resolve on the microtask queue.** A `setTimeout`
  stub HIDES this race: Node drains microtasks after each timer callback, so
  the first call runs to completion before the second's timer fires. Verified
  both ways — with a `setTimeout` stub the unfixed code passed; with microtask
  stubs it reproduces the two-rows-one-base shape from §2.
- **No new utility.** Nothing is added: `IdMute`/`IdMutex`
  (`core/src/utils/mutex.ts`) is the repo's existing per-id serialiser and is
  already on this method — only its key changes. The memory assignment copies
  the line `profitAfterPositionClosed()` already has.

## Blast radius

1. **Other call sites.** `createTransaction` is called from exactly one place
   (`processFilledOrder`, un-awaited). Nothing else takes the
   `${botId}transaction` key — grepped `transaction${` and `}transaction` across
   `core/src` and `src`.
2. **Throughput.** Fills on ONE bot now book one at a time. They already did
   whenever two deliveries shared a `clientOrderId`, and `processFilledOrder`
   above it is already serialised per bot; different bots are unaffected, and
   the ledger write is a single insert plus a single update.
3. **`core/` submodule.** All of it is in `core/` (`main-app-sh`), shared and
   public. It is bot-engine code; no other service imports `bot/helper.ts`.
4. **Cross-service contracts** (main-app `CLAUDE.md`): none. No GraphQL, REST,
   socket.io, RabbitMQ or Mongo *schema* change. `transactions` keeps its
   shape; `cummulativeProfit*` and `bot.profit` only get the values they were
   supposed to have. The `bot transaction update` / `bot settings update`
   socket events keep their names and payloads.
5. **Tests that must stay green.** `gridCloseProfitLedger.spec.ts` (spec 045)
   drives both close paths and the ledger; the full `core` suite is the gate.
