## Decisions the spec left open

- **Teardown predicate.** The fix reuses spec `178`'s `cancelRetryWanted`
  instead of a new "closing deals" marker. `processDealClose` already calls
  `deleteDeal` before `cancelAllOrder`, so during the sweep that predicate is
  true for exactly the closing deal's orders, and false for every open deal.
- **No new positional parameter.** The parent repo overrides
  `cancelOrderOnExchange` and forwards its arguments by position.
- **JIT tier.** Tier 1: the refusal predicates are named module functions.
  The rest stays in place, because the method is I/O orchestration.

## Blast Radius

- `cancelOrderOnExchange` has about 30 callers. The new branch runs only when
  `cancelIsTeardown` is true, which means the bot is stopping (`blockPriceCheck`)
  or the order's deal is not in memory. A running deal's cancels take the old
  path (§1.1.6).
- `removeOrdersByDeal` has one caller, `processDealClose`. After
  `cancelAllOrder(…, true)`, the only live orders left are those whose cancel
  the venue did not confirm. A restart already reloads such rows from the DB
  as open orders, so keeping them in memory matches what a restart does.
- This is under `core/` (main-app-sh, public). No GraphQL, socket, queue or
  schema shape changes.
- Existing suites on this path: `teardownCancelRateLimit.spec.ts` (§4.5
  amended), `closedDealCancelLockoutRetry.spec.ts` (spec 178),
  `lateEntryFillAfterClose.spec.ts` (spec 112), and the full core suite.
