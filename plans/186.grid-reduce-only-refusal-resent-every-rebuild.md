# 186 — plan: back off a grid level refused as un-reducible

## Build order

1. `src/bot/positionAlreadyClosed.ts` — the position-already-closed reason list
   and `isPositionAlreadyClosedReason`, moved verbatim from `dcaHelper.ts`
   (spec §3.2). `dcaHelper`'s protected method delegates to it, so the DCA /
   combo callers are unchanged.
2. `src/bot/gridReduceOnlyGuard.ts` — `GridReduceOnlyGuard`, a `RetryBackoff`
   (namespace `gro`, 60 s → 15 min, ×2) keyed on bot, symbol, side, price.
   Same shape and windows as `RiskTierGuard`: the condition is routinely
   transient (a fill on the opening side grows the position again), so a level
   placed late is a real cost and the ceiling stays short.
3. `MainBot.gridReduceOnlyLevel(order)` + a pre-send gate in
   `sendOrderToExchange`, beside the risk-tier gate, with its own
   `gridReduceOnlyShortCircuit` flag threaded through the same four places the
   risk-tier flag is (ambiguity probe, row delete-vs-retire, error report).
   Record on a real matching refusal; clear on acceptance.

## Contract decisions the spec left open

- Gate scope: `futures && reduceOnly && typeOrder === regular && needToSendOrder`.
  `regular` is the grid level type only; grid stop/TP (`stop`) and every DCA /
  combo type are out (spec §1.3).
- Downstream on a suppressed attempt: silent, like the risk-tier gate — the
  write-ahead row is deleted and no error is reported (spec §4.2). The real
  refusal that opened / re-opens the window is reported as today.
- JIT tier: Tier 1 — the predicate moves into its own named, tested module; the
  gate stays in the legacy method next to its siblings. Tier 2/3 would mean
  extracting the whole pre-send gate chain, which is not on this bug's path.
- Not done: resyncing the grid's position from the venue. The grid's own book
  is not wrong in a way this refusal proves (spec §2.2 — the bot kept trading),
  and changing grid position accounting would alter normal placement, which
  the brief rules out.

## Blast radius

1. Call sites: `isPositionAlreadyClosedReason` — `dcaHelper.ts` (2), via the
   inherited method in `comboHelper.ts` (1); behaviour identical (same list,
   same normalisation). `sendOrderToExchange` serves every bot type; the gate
   matches only `regular` reduce-only futures orders.
2. Under `core/` (main-app-sh): shared, deployed platform-wide; the parent's
   submodule pointer needs a bump.
3. No GraphQL / REST / socket / queue / collection shape changes. New Redis key
   namespace `gro:cd:*`, TTL-bounded, read and written by this module only.
4. Other tests on this path: `riskTierRefusal.spec.ts`,
   `strandedLocalRefusal.spec.ts`, `comboFlatDealGridRefusal.spec.ts`,
   `dca/positionFlatDirectionRefusal.harness.spec.ts`,
   `dca/restingTpPositionGone.harness.spec.ts`, full `npm test`.
