# 157 — plan

Spec: `specs/157.limit-only-book-refuses-the-close-remainder-sweep.md`.

## Solution

1. `sellRemainder` gains one optional trailing argument, `sweep`:
   - `'send'` — run the method's own guards and quantity derivation, send the
     MARKET sweep with `returnError`, report a refusal exactly as the
     non-`returnError` send used to (`handleOrderErrors`, setError/sendError
     off — a `D-SR` order never set a bot error), and return
     `{ result }`. No booking, no `sellRemainder` flag. Returns nothing when a
     guard stopped it before a send.
   - `{ result }` — the sweep was already sent; book that answer instead of
     sending again.
   - absent — unchanged.
2. `closeDeal`'s take-profit branch, before it commits anything: when the
   remainder the close would leave (same arithmetic as today, applied to the
   ledger before the close leg) clears the venue minimums, call
   `sellRemainder(…, 'send')`. If the answer is a limit-only refusal
   (`isLimitOnlyReason`), do not close: record the take-profit fill in
   `tpHistory`, clear `pendingClose`, and call the new
   `closeRemainderByLimit(botId, dealId, qty)` (not awaited) with the quantity
   the refused sweep carried. Otherwise continue exactly as today and pass the
   answer to the existing post-close `sellRemainder` call as `{ result }` (it
   is booked even if the post-close remainder re-read disagreed).
3. `closeRemainderByLimit` — `@IdMute` on `closeDealById`'s key
   `${botId}${dealId}`, so it queues behind a close request still in flight.
   Cancels the deal's resting `dealTP` orders with
   `promotePartialToFilled: false` (fills → `tpHistory`, netted from the
   quantity; a cancel that comes back `FILLED` is handed to
   `handleUnknownOrder` and nothing is placed), then rests one LIMIT `dealTP`
   at the latest price. A refusal is reported (`handleOrderErrors`) and goes to
   `restoreOrReportRefusedClose`.

Contract decisions left open by the spec: the LIMIT re-close is sized from the
sweep, NOT by re-entering `closeDealById(closeByLimit)`. That path sizes with
`getTPOrder`, and a remainder exists precisely because that sizing and the
ledger disagreed — in the §2 deal it would rest the same short take-profit
again, and once the sizing reads "nothing to close" `closeDealById` takes its
"Close without TP order" branch, which closes the deal with no order and books
none of the take-profit's proceeds. Cost of the choice: no close-by-limit
reposition timer; the order rests at the price it was placed at until it fills
or the user closes again.

JIT tier: Tier 0 (no extraction). The change is a guarded early return in
`closeDeal` plus a send/book seam in `sellRemainder`; extracting either 300-line
method is out of proportion to a fix on a money path.

## Blast radius

1. Call sites of `sellRemainder`: `closeDeal` (changed), `updateDeal`
   late-fill path, `placeBaseOrder`-side closed-deal path, main-app
   `comboHelper.ts:236` — all positional, none pass the new argument, so
   unchanged.
2. `closeDeal` take-profit branch: reached from every take-profit fill
   (DCA, combo, terminal). The new branch only runs when the sweep is refused
   with a limit-only reason; profit-in-base deals never sweep (`sellRemainder`
   returns early) and are untouched; terminal simple deals likewise.
3. `core/` file — shared, public (`main-app-sh`); parent pointer bump
   required. No GraphQL/socket/queue/collection shape change.
4. Other tests on this path: `lateEntryFillAfterClose.spec.ts`,
   `evidenceFreeFilledPromotion.spec.ts`, `remainderDoubleCount.spec.ts`,
   `reduceOnlyRemainder.spec.ts`, full `npm test`.
