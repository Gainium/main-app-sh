# 023 — Plan

Spec: `core/specs/023.nan-take-profit-quantity-is-write-ahead-persisted.md`.

## Solution

One guard in `core/src/bot/dcaHelper.ts` `getTPOrder`, placed immediately
before the `const tpOrder: Grid = { … }` literal — i.e. after the combo branch
has had its say and after `tpPrice` is final, but before anything is built,
sent or persisted:

```ts
if (!Number.isFinite(qty) || !Number.isFinite(tpPrice) || tpPrice <= 0) { … return [] }
```

reported through `this.handleErrors(...)`, mirroring `addDealFunds`'
`Order qty is not a number` refusal (`dcaHelper.ts`) and
`createInitialDealOrders`' `Latest price is 0` bail.

This fixes the root cause the spec's §3 Assumption names — a non-finite
quantity leaving `getTPOrder` — rather than the symptom (the `CastError` on the
deal save, which is downstream of the persisted `"NaN"` string).

### Why here and not earlier

Guarding only `_qty` (`filledQty + boQty`) would catch §3.4 but not the combo
branch, which discards `qty` and recomputes it from the deal's balances
(spec §4.3) — and the same incident produced NaN balances. One check after both
producers covers both engines. Guarding only `boPrice` at the nominal division
would leave every other arithmetic path in a 300-line method unguarded.

### Why not also `sendOrderToExchange`

Spec §5. It is the widest-blast-radius path in the engine and the evidence
names a single producer. Recommended as a follow-up, not bundled here.

### Tier (JIT legacy extraction)

**Tier 0.** The causal path is a 300-line method that mixes sizing with
`getExchangeInfo`/`getUserFee`/`getDeal` I/O, but the change is a four-line
refusal at an existing seam; the sizing decision it protects
(`resolveBaseOrderQty`) was already extracted pure in `dca/baseOrderQty.ts` by
spec 017. Extracting more of `getTPOrder` here would be scope creep on a
production incident fix.

## Blast Radius

1. **Other call sites.** Seven callers of `getTPOrder`
   (`dcaHelper.ts` placeBaseOrder / two asset-requirement estimators /
   tp-coverage repair / the initial-order builder / `remainingCloseQty` /
   the SL path). All already tolerate an empty or absent result — enumerated in
   spec §4.2. The new `return []` is the same value the combo branch already
   returns twice.
2. **`core/` submodule.** Yes — `core/src/bot/dcaHelper.ts` is shared
   (`main-app-sh`) and deployed platform-wide. The change is additive and
   unreachable on any input that is finite today, so consuming services see no
   behaviour change on healthy deals.
3. **Documented cross-service contracts.** None touched. No GraphQL/REST shape,
   no socket.io event, no queue name/payload, no Mongo schema field. The
   `orders` documents this prevents are malformed rows nothing wants.
4. **Existing tests on this path.** `dca/tpSizingFromPosition.harness.spec.ts`,
   `dca/baseOrderQty.spec.ts`, `dca/tpCoverageReconcile*.spec.ts`,
   `dca/partialTp.spec.ts`, `dca/tpFees.spec.ts` all exercise `getTPOrder` or
   its inputs and must stay green.
