# Plan 018 — learn the quantity precision a venue refuses

Implements `specs/018.venue-refused-quantity-precision-never-learned.md`.

## 1. Build order

1. **`core/src/bot/qtyStepGuard.ts`** (new). Two layers in one file, mirroring
   `quantRulesGuard.ts`:
   - **Pure decision functions**, no I/O, no framework import:
     `isQtyDecimalsRefusal(reason)`, `deriveAcceptedDecimals(qty)`,
     `decimalsToStep(d)`. These carry every rule in spec §4.1/§4.2 and are
     independently testable (Part 3 of the dev-flow skill).
   - **`QtyStepGuard`** — a static class holding the account-scoped learned
     precision. In-process `Map` is authoritative for reads; Redis is the
     persistence layer.
2. **`core/src/bot/main.ts` — `getExchangeInfo`** applies a learned step to the
   row it returns (spec §4.5, §4.6, §4.8).
3. **`core/src/bot/main.ts` — `sendOrderToExchange`** grows the quantity twin of
   the existing tickSize branch (spec §4.4).
4. Version + changelog per `main-app/CLAUDE.md`.

## 2. Contract decisions the spec left open

- **Key shape.** `qstep:<exchangeUUID>:<symbol>` → the accepted decimal count as
  a decimal string. Flat namespaced key, TTL 90 days, exactly the
  `quantRulesGuard` convention. A new key prefix; no existing key space touched.
- **Storing decimals, not the step.** The refusal teaches a *decimal count*;
  storing that and deriving the step keeps the value exact (`10**-d`) and
  removes any float-parse round trip from the hot path.
- **Reads never await Redis.** `getExchangeInfo` is called on essentially every
  tick, and `RedisClient.getInstance()` retries a dead Redis forever
  (`db/redis.ts` `getClient`), so awaiting it on that path could wedge the
  engine. The read is therefore `peek()` — a synchronous `Map` lookup — with a
  **fire-and-forget** hydrate scheduled behind `RedisClient.isReady` on the
  first miss for a key. A persisted step is then live from the second call after
  a worker restart, and an account that never learned anything costs one `Map`
  miss and nothing else (spec §4.6).
- **Writes are best-effort.** `record()` updates the `Map` first and persists
  after, so the retry in §4.4 works identically whether or not Redis answers
  (spec §4.7).
- **Rounding direction is DOWN, unconditionally** (spec §4.4). `math.round(n, d,
  true)` — the helper already in `core/src/utils/math.ts`; no new rounding code.
- **No retry counter.** `count` is passed through unchanged, as the tickSize
  branch does, so the coin-M contract conversion (`count === 0`) and the
  write-ahead persist keep their existing semantics. Termination is proved by
  §4.2 strictly decreasing the decimal count on each pass.

## 4. Blast Radius

1. **Other call sites.** `getExchangeInfo` on `MainBot` is the single read path
   for pair filters in the bot engine (`baseAssetPrecision`, and every
   `baseAsset.step` remainder in `dcaHelper`, `gridMonitor`, `comboHelper`,
   `helper`). That breadth is the point of §4.5 — but it also means the change
   must be a no-op when nothing is learned, which spec §4.6 pins and the tests
   assert by **object identity** (`expect(info).to.equal(sharedRow)`).
2. **`core/` submodule.** Both edited files are under `core/` = `main-app-sh`,
   shared with every consuming service and deployed platform-wide. The parent
   pointer must be bumped. The new file is additive; the two edits are additive
   branches.
3. **Owned contracts (root CLAUDE.md Danger List).** None touched. No GraphQL
   shape, no REST shape, no socket event, no RabbitMQ queue, no shared Mongo
   collection — the learned value lives in a NEW Redis key and nowhere else.
   Notably **the `pairs` collection is not written**, which is what keeps the
   change off Danger List #12 and honours the operator's "do not make the
   instrument-filter loader host-keyed".
4. **Danger List #1 `BaseReturn<T>`** is read (`request.status`/`request.reason`)
   and not changed.
5. **Other tests on this path.** `strandedLocalRefusal.spec.ts`,
   `cancelNoExchangeOrderId.spec.ts`, `krakenOrderId.spec.ts`,
   `orderNotFound.spec.ts`, `reduceOnlyRemainder.spec.ts`,
   `perContractBotMessage.spec.ts` all drive `sendOrderToExchange` or its
   neighbours and must stay green.

## 5. JIT legacy tier

**Tier 1** on `sendOrderToExchange` (runbook): the rules are extracted into a
named, tested module (`qtyStepGuard.ts`) even though the call site remains the
same 700-line refusal ladder. Not Tier 2/3 — `sendOrderToExchange` is on the
live order path for every bot type; restructuring it is not something to spring
on a bug fix, and the radius rule says the extraction covers only the branch
being added.
