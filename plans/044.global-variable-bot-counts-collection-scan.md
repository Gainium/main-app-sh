# 044 — Plan

Spec: `specs/044.global-variable-bot-counts-collection-scan.md`

## Solution

Add three lines to `registerIndexes()` in `core/src/db/schema.ts`, next to the
existing per-collection index blocks:

```ts
botSchema.index({ 'vars.list': 1 })
comboBotSchema.index({ 'vars.list': 1 })
dcaBotSchema.index({ 'vars.list': 1 })
```

with one comment block (on the `dcaBot` line, the collection the cost is on)
carrying the measurements and the "not compound with `isDeleted`" reasoning,
and one-line cross-references on the other two — matching how
`parentBotId_1` is already documented at `:3254-3266`.

This fixes the cause the spec's §3 names. No call-site change: the filter is
already the right filter, it simply has nothing to run against.

### Contract decisions the spec left open

- **Single-field, not compound.** Spec §4.2. `isDeleted: {$ne: true}` is an
  anti-predicate — a `$ne` cannot bound an index scan — so adding it buys
  nothing and costs an index entry move on every soft delete.
- **Not sparse / not partial.** Only ~18% of `dcabots` carry a variable, so a
  sparse index would be smaller. It is not worth the divergence: the existing
  comparably-selective index on this collection (`parentBotId_1`, present on
  ~1% of bots) is a plain index and measures 1.4MB against a 0.01GB total
  index footprint. A plain index also stays usable if this filter is ever
  combined with a sort, which a sparse one is not.
- **All three collections, even `bots` (0 rows with variables today).**
  `getBotsByGlobalVar` counts all three unconditionally, so all three take the
  scan. An index over a field no document carries is ~0 bytes.

## Blast Radius

1. **Other call sites.** `registerIndexes()` is called once per process from
   `core/src/db/model.ts:187` and `src/db/model.ts:455`. Adding an index
   declaration cannot change any query's result, only its plan.
2. **`core/` submodule.** Yes — `core/src/db/schema.ts` lives in
   `main-app-sh`, shared with the self-hosted edition. Adding an index is
   additive and safe there: a self-hosted instance builds it at boot on a much
   smaller collection.
3. **Contracts this repo owns.** Root Danger List #12, "Shared Mongo `gainium`
   collections": legacy `main-dash` and `admin-app` read these collections
   directly. This change adds no field, removes no field and changes no
   document — it only adds an access path, so those readers are unaffected.
4. **Index-build cost on deploy.** `registerIndexes()` feeds Mongoose
   `autoIndex`/`syncIndexes` at boot. Building `{vars.list: 1}` on production
   `dcabots` means ~112k keys over 51,755 documents (§2.4: 69,740 variable
   entries plus one null key per variable-free document) — seconds, and
   Mongo 8 builds indexes without blocking readers. The other two collections
   are 3,760 and 2,895 documents.
5. **Write path.** `vars.list` changes only when a user attaches or detaches a
   variable on a bot — not on any per-tick or per-fill write. This is the
   opposite of the mutable-field case (`status`) the `orders` comment at
   `:3306` warns about.
6. **Other tests on this path.** None exercise `registerIndexes()`; the new
   spec is the first. `npm test` in `core/` must stay green.
