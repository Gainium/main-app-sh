# Plan 166 — A base remainder whose cancel only the stream confirms is never re-placed

## Build order

1. `dcaHelper.findEndedBaseRemainderOrder(dealId, addFundsId)` — the entry's
   order if it is recorded `CANCELED`/`EXPIRED`: the order map first, then the
   stored row (`ordersDb.readData` on `botId`/`dealId`/`addFundsId`). The row's
   `addFundsId` and status are checked in code as well as in the filter.
2. `dcaHelper.bookEndedBaseRemainderOrder(row)` — books a dated fill it states
   through `promoteEndedBaseEntry` + `handleUnknownOrder`, exactly as
   `settleBaseEntryRemainderOrder` does for a terminal cancel answer; returns
   the executed quantity.
3. `checkBaseEntryRemainder`:
   - no resting order → look for an ended one (§4.2); found → book it, drop the
     entry, place the rest; not found → re-arm (unchanged §4.3.5).
   - cancel answer `null` → look for an ended one (§4.1); found → continue as a
     settled cancel; not found → warn + re-arm (unchanged §4.3.4).

## Contract decisions

None. No schema, GraphQL, socket or queue shape changes. The stored-row read
uses fields `saveOrderToDb` already writes (`addFundsId`, `dealId`, `botId`).

## JIT tier

Tier 0 for the surrounding legacy: the change is two small methods next to the
existing remainder methods, reusing `settledBaseEntryFill` and
`promoteEndedBaseEntry`. No extraction is needed to make the path testable;
the existing harness drives the real methods.

## Blast Radius

1. Call sites: `checkBaseEntryRemainder` is called only by its own timer
   (`armBaseRemainderTick`). `buyBaseEntryRemainder` keeps its current
   behaviour (it re-arms and asks the user to retry on a null cancel).
2. `core/` is shared (`main-app-sh`): affects every DCA bot with a resting
   base remainder (LIMIT entry, market entry off). Pointer bump in main-app.
3. Owned contracts: none touched.
4. Other tests: the whole `baseEntryRemainder.harness.spec.ts` (§4.3.4 and
   §4.3.5 must stay green), plus the core suite.
