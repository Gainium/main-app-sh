# 111 — plan: a part-filled LIMIT base entry opens the deal and rests its remainder

## Build order

1. `src/bot/dca/baseEntryRemainder.ts` (pure, Tier 2):
   - `baseEntryRemainderQty` (§4.1);
   - `remainderKeepsResting` (§4.3.2), which delegates to spec `103`'s
     `repositionKeepsRestingBaseEntry` so the two cannot drift.
2. `types.ts`: `AddFundsSettings` gains optional `baseRemainder` and
   `baseTotal` (§4.7). `Deal.pendingAddFunds` is typed off it, so it follows.
3. `src/bot/dcaHelper.ts`:
   - `baseEntryMayEnterAtMarket(settings)`: the expression
     `topUpSettledBaseEntry` already used inline, now shared by both callers.
     Tier 1 extraction, same file.
   - `restBaseEntryRemainder(orderBo)`, called at the end of `startDeal`'s
     open branch, after `placeOrders` (§3.2, §4.1).
   - `placeBaseEntryRemainder(dealId, symbol, qty, total)`: rounds, checks
     the venue minimum, calls `addDealFunds` with a LIMIT and arms the tick
     (§4.1).
   - `baseRemainderTimers`, `armBaseRemainderTick`, and the
     `checkBaseEntryRemainder` tick (§4.3). Its mutex is
     `baseRemainder${botId}${dealId}`, which is not `addFunds…`, since it calls
     `addDealFunds`.
   - `settleBaseEntryRemainderOrder(order)`: cancel, then book the fill with
     `settledBaseEntryFill` + `promoteEndedBaseEntry` (spec `059`). Returns
     the executed quantity, or `null` when the cancel got no terminal answer.
     Used by the tick and by the buy (§4.3.3, §4.3.4, §4.6).
   - `dropBaseRemainderEntry(deal, id)`.
   - `buyBaseEntryRemainder` (§4.6), on the same mutex as the tick.
   - `resumeBaseEntryRemainder(d)`, called from `restoreWork` after
     `resumeTrailingCloseRetry(d)`, which both the service-restart and normal
     branches reach, and from `resendPendingFunds` (§4.4).
   - Bot stop clears `baseRemainderTimers`, next to
     `canceledBaseEntryTimers` (§4.5).
4. Contract (§4.7):
   - `src/graphql/schema.ts`: the two fields, the input and the mutation.
   - `src/graphql/resolvers.ts`: the resolver, a copy of the auth shape of
     `cancelPendingAddFundsDealOrder`.
   - `src/bot/index.ts`: `Bot.buyDealBaseRemainder`, a copy of the worker
     dispatch of `cancelPendingAddFundsDealOrder`.
   - `src/db/schema.ts`: the `funds` sub-schema fields.
5. CHANGELOG + version (minor, a feature).

## Contract decisions the spec left open

- The mutation reuses `cancelTerminalDealOrderResponse` as its return type,
  so no new response type is needed.
- The buy's MARKET add carries no `baseRemainder`. If the venue answers it
  non-FILLED, it becomes an ordinary pending add-funds entry, and the tick
  does not reposition it into a LIMIT.

## Blast radius

1. Call sites:
   - `startDeal` is overridden in the parent (`src/bot/dcaHelper.ts`). The
     override calls `super.startDeal` first, so the hook runs.
   - `resendPendingFunds` has two callers: restore and the settings update.
     The arm is idempotent (it clears first).
   - `addDealFunds` is unchanged. The new fields ride through `...settings`
     into the pending entry and through the spec `110` re-send.
   - `topUpSettledBaseEntry` now reads the extracted predicate, with the same
     expression.
2. Everything is under `core/` (`main-app-sh`, public, platform-wide).
   Self-hosted picks it up with the next image. The parent pointer bump is
   part of shipping.
3. Contracts:
   - GraphQL (Danger List #3): additive only, two nullable fields and one new
     mutation. Old dashboards never select them.
   - Shared Mongo `deals`: two optional sub-fields on `pendingAddFunds[]`.
     Legacy main-dash and admin-app read the array, and extra keys are
     ignored.
   - No socket, queue or REST change.
4. Tests that must stay green:
   - `baseEntryReposition.harness.spec.ts` (spec 103);
   - `partialBaseEntry*.spec.ts`;
   - `settleCancelNoFillReport.harness.spec.ts`;
   - `pendingFundsResend.harness.spec.ts` (spec 110);
   - `baseEntryTopUp.harness.spec.ts`;
   - the whole `npm test` suite, plus `tsc` in core and the parent.

## JIT tier

Tier 2 for the two decisions, in the new pure module. Tier 1 for the
market-entry predicate: it is shared in place and not moved out of the class,
because its inputs are instance state (`enterMarketTimeout`). The I/O methods
stay on the mixin, next to `settlePartialBaseEntry`, whose shape they follow.
Nothing else in `dcaHelper` is restructured.
