# 238 — plan

Spec: `specs/238.a-close-misses-entry-fills-still-queued-for-booking.md`.

## Build order

1. `src/bot/closeCountsQueuedEntryFills.spec.ts` — red first (§1.1.1, §1.1.2,
   §1.1.4 fail before the change; §1.1.3 pins today's behaviour).
2. `dcaHelper.ts`: `queuedEntryFills(dealId)` reads the deal's FILLED/CANCELED
   `dealRegular` rows that are in `ordersInBetweenUpdates`, not in
   `dealUpdateOrders`, not add-funds, executed > 0, and sums their ledger delta
   the same way `updateDeal` does. Empty on a combo.
3. `closeDeal`: `preRemainder` adds that delta (§4.1); once the close is
   committed and the ledger is usable, re-read, book, and mark them
   (§4.2, §4.3).

## Decisions the spec left open

- **Where to measure.** The brief proposed rebuilding the remainder from all
  filled orders. Not taken: the ledger is right except for the queued fills,
  and replacing it would change the sweep for every deal (fees, add funds,
  partial take-profits each have their own handling in it). Counting only the
  queued fills is the narrowest change that makes take-profit and close agree.
- **JIT tier 0/1.** One private method next to `closeDeal`, no extraction:
  the rest of `closeDeal` is not on the causal path.

## Blast Radius

1. Call sites: `closeDeal` take-profit branch only. `queuedEntryFills` is new.
   The parent `src/bot/dcaHelper.ts` does not override `closeDeal`;
   `comboHelper` does not override it either and is excluded (`this.combo`).
2. **`core/` (main-app-sh)** — shared, public, deployed to every DCA bot
   worker. Order placement path: a remainder sweep is now sent at close for
   queued fills a smaller take-profit did not cover (once, combined), instead
   of per fill afterwards; the total is unchanged (§1.1.3 test).
3. No GraphQL/socket/queue/schema shape change. `currentBalances`/`profit`
   persisted values change for affected deals (now correct).
4. Other suites on this path: `lateEntryFillAfterClose` (spec 112),
   `tpHistoryLedgerRebuild` (212), `limitOnlyCloseRemainder` (157),
