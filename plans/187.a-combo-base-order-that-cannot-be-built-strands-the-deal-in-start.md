# 187 — plan: Combo base order that cannot be built strands the deal in `start`

Spec: [`specs/187…`](../specs/187.a-combo-base-order-that-cannot-be-built-strands-the-deal-in-start.md).

## Solution

In Combo `placeBaseOrder` (`src/bot/comboHelper.ts`), right after
`getBaseOrder`, call spec 039's `shouldDiscardUnbuiltBaseEntry` with the same
inputs DCA passes. When it answers true, log, retire through the inherited
`retireUnfundedDeal` (cancel, `reopen: false`), and return. That is the same
helper Combo's `fundShortSpotEntry` refusal already uses on a `start` deal.

JIT tier 0. The decision is already a pure, tested module (spec 039), so it is
reused, not re-extracted. The Combo method stays as it is apart from the new
early return.

## Blast Radius

1. Call sites: Combo `placeBaseOrder` is reached from `openNewDeal`, the
   slippage retry, the close→reopen path and `restoreWork`'s `start` replay.
   Only the last two can carry `oldDealId`. All of them reach the guard only
   when `getBaseOrder` returned nothing. Hedge Combo inherits the Combo mixin
   and gets the same behaviour.
2. `core/`: yes. The file is in `main-app-sh`, so the parent pointer must be
   bumped.
3. Contracts: none. No GraphQL, socket, queue or schema change. The deal is
   cancelled through the existing close path, which already emits its usual
   deal update.
4. Other tests: `dca/unbuiltBaseEntry.harness.spec.ts` (decision unchanged) and
   the full core mocha suite.
