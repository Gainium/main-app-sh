# 126 — Plan: REST bot update and clone can replace a bot's indicators

Spec: [`specs/126.rest-bot-update-replaces-indicators.md`](../specs/126.rest-bot-update-replaces-indicators.md)

## Build order

1. `validators/logic.ts` — lift the indicator rules out of
   `validateCreateDCABotInputLogic` into `requiredIndicatorErrors` (the
   condition → indicator rules) and `indicatorConsistencyErrors` (those plus
   max-20, duplicate ids, group references both ways, unused indicators).
   Creation calls the latter; behaviour on create is unchanged.
2. `validators/indicatorUpdate.ts` (new) — `applyIndicatorSettingsUpdate(current,
   update, vars)`: array check → strip per-item `_id` → per-type defaults
   (`addIndicatorsDefaults`, as create) → item schema (`indicatorCoreConfig`,
   `indicatorGroupConfig`, as create) → consistency on `{...current, ...update}`
   → prune `vars`. With no indicator keys it only runs
   `requiredIndicatorErrors` when `startCondition`/`dcaCondition` is in the
   update; otherwise it returns its input untouched.
3. `bot/utils.ts` `checkDCABotSettings` — allowlist `indicators`,
   `indicatorGroups`; allow `startCondition: TechnicalIndicators` and
   `dcaCondition: indicators` at bot level only. `checkDCADealSettings` gains a
   `dcaConditions` parameter whose default keeps deal updates as they were.
4. Wire into the six handlers that run `checkDCABotSettings`: v2
   `PUT /bots/:type/:id`, v2 `POST /bots/:type/:id/clone` (non-grid), v1
   `updateDCABot`, `updateComboBot`, `cloneDCABot`, `cloneComboBot`. Each uses
   the returned `settings` and `vars` in place of the raw body and the stored
   vars.
5. `validators/bots/config.ts` — add `lwCondition` to `indicatorCoreConfig`
   (stored by the dashboard and added by the `lw` per-type defaults, but
   missing from the schema, so it failed as "unexpected field" on create too).
6. OpenAPI `UpdateDCABotInput` / `UpdateComboBotInput` (clone bodies inherit
   them), `SCHEMAS.md`.

## Decisions the spec left open

- Error shape: `{status: NOTOK, reason: 'Validation error', errors}` — the shape
  bot creation already returns, on both v1 and v2.
- `_id` on items is dropped silently (not an error) — §2.4.
- Combo: `dcaCondition` stays DCA-only (it is in `onlyDcaSettingsKeys`).
- Conditions re-checked without indicator keys: only `startCondition` and
  `dcaCondition`, the two indicator-driven conditions the update allowlist can
  set. Only the "needs its indicator" rules run then, so a legacy bot with
  unrelated stored inconsistencies is not newly rejected for an unrelated save.

## Blast radius

1. Call sites: `checkDCABotSettings` — exactly the six handlers above
   (grep). `checkDCADealSettings` — deal updates use the new parameter's
   default, unchanged. `validateCreateDCABotInputLogic` — create DCA/Combo via
   the extracted functions, same rules in the same order apart from the
   max-pairs error now preceding the max-indicators one.
2. All files are under `core/` (`main-app-sh`, public, embedded in the cloud
   and self-hosted main-app). Pointer bump in main-app after push.
3. Contract: public REST `/api/v2/*` (Danger List #2). The change is additive —
   bodies that were accepted are accepted unchanged, except an update that
   sets `startCondition`/`dcaCondition` to an indicator-driven value without
   the indicator, which previously could not be set at all. GraphQL untouched.
   Consumers to tell: gainium-mcp `update_bot` can now pass indicators.
4. Other tests on the path: `pairRoundTrip.spec.ts`,
   `openapiEnumExamples.spec.ts`, `openapiInlineUnionEnums.spec.ts` — whole
   suite green.

JIT tier: Tier 1 — the indicator rules move into named, tested functions; the
handlers keep their existing shape.
