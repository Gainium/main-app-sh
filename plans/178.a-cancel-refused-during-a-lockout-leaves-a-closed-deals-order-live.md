# 178 — plan

Spec: `specs/178.a-cancel-refused-during-a-lockout-leaves-a-closed-deals-order-live.md`.

## Solution

- `src/bot/main.ts` `cancelOrderOnExchange`: in the refusal branch, after the
  not-found and cancel-pending routes and before the unchanged `handleErrors`
  report, a refusal matching `isRateLimitReason` or `isVenueLockout` (reused
  from `authGuard.ts`, not re-worded) calls `queueCancelRetry`.
- `queueCancelRetry` / `runCancelRetry` (new, private, `MainBot`): one pending
  re-send per client order id, delay `max(stated hold + 1s, back-off step)`
  jittered, four steps. On fire: re-read the row via the existing
  `findOwnOrder`, require `NEW`/`PARTIALLY_FILLED` and `cancelRetryWanted`,
  then call `cancelOrderOnExchange` with the original arguments.
- `cancelRetryWanted` is a protected hook: `false` in `MainBot`, overridden
  in the DCA helper (inherited by Combo) as "the order's deal is no longer
  open" (`getDeal`).
- Timers via an overridable `scheduleCancelRetry` (unref'd `setTimeout`),
  jitter via `cancelRetryJitter`, so the spec drives both deterministically.

JIT tier: 0 for the surrounding method — the new logic is small, self-named
methods beside the spec `134` helpers; nothing existing is restructured.

## Blast Radius

1. Callers: every `cancelOrderOnExchange` caller (DCA/Combo close, TP
   re-size, trailing, checkOrders, GraphQL user cancel via the bot). None sees
   a different return value or a delay — the re-send is never awaited. A
   re-send only goes out for an order whose deal has closed, which no caller
   still wants resting.
2. `core/` submodule — shared, bump the parent pointer.
3. No contract touched (no GraphQL, socket, queue or schema change).
4. Spec `134` teardown ladder unchanged; its suite stays green.
