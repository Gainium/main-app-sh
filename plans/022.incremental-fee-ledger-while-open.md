# 022 — accrue the observed-fee ledger on every fill, not just at close

Plan for [`specs/022.incremental-fee-ledger-while-open.md`](../specs/022.incremental-fee-ledger-while-open.md).

## Solution

### 1. Extract `computeObservedFeeLedger`

New method near `getCommDeal` in `dcaHelper.ts`:

```ts
async computeObservedFeeLedger(deal: ExcludeDoc<Deal>): Promise<{
  feeByAsset: FeeLedgerEntry[]
  feePaid: { base: number; quote: number }
} | null> {
  if (!deal._id || !deal.flags?.includes(DCADealFlags.feeByAsset)) {
    return null
  }
  const dealOrders = this.getOrdersByStatusAndDealId({
    dealId: `${deal._id}`,
    status: ['FILLED', 'CANCELED'],
  }).filter(
    (o) =>
      +o.executedQty > 0 &&
      ![TypeOrderEnum.br, TypeOrderEnum.rebalance].includes(o.typeOrder),
  )
  let feeByAsset: FeeLedgerEntry[] = []
  let feeBaseFull = 0
  let feeQuoteFull = 0
  let cachedPrices: { pair: string; price: number; exchange: string }[] | undefined
  const resolveLegUsdRate = async (
    asset: string,
    order: (typeof dealOrders)[number],
    legAmount: number,
    singleLeg: boolean,
  ): Promise<number> => {
    if (singleLeg && order.feePaidUsd !== undefined) {
      const usd = +order.feePaidUsd
      return legAmount > 0 ? usd / legAmount : 0
    }
    const { baseAsset, quoteAsset } = deal.symbol ?? {}
    if (asset === baseAsset) return this.getUsdRate(deal.symbol.symbol, 'base')
    if (asset === quoteAsset) return this.getUsdRate(deal.symbol.symbol, 'quote')
    if (!cachedPrices) {
      const pricesResult = await this.exchange?.getAllPrices(true)
      cachedPrices =
        pricesResult?.status === StatusEnum.ok
          ? pricesResult.data.map((p) => ({ ...p, exchange: 'all' }))
          : []
    }
    return utils.findUSDRate(asset, cachedPrices ?? [], this.data?.exchange) || 0
  }
  for (const o of dealOrders) {
    const observed = observedFeeSplit(o, deal.symbol?.baseAsset, deal.symbol?.quoteAsset)
    const legs = observedFeeLegs(o, deal.symbol?.baseAsset, deal.symbol?.quoteAsset)
    for (const leg of legs) {
      const rate = await resolveLegUsdRate(leg.asset, o, leg.amount, legs.length === 1)
      feeByAsset = accrueFeeLedger(feeByAsset, leg.asset, leg.amount, rate)
    }
    if (observed) {
      feeBaseFull += observed.base
      feeQuoteFull += observed.quote
    }
  }
  return { feeByAsset, feePaid: { base: feeBaseFull, quote: feeQuoteFull } }
}
```

Same shape as `closeDeal`'s existing loop with the estimate-fallback
and `offPairFeeUsd` branches removed (spec's Design section: those stay
close-only) and `tpOrder.symbol` generalized to `deal.symbol.symbol`
(every order in the deal shares one symbol — no order object needed to
resolve it).

### 2. Call it from `startDeal`

After `findDeal.deal.settings.avgPrice = avgs.avg || initialPrice`
(`:6699`) and before the existing `saveDeal` call (`:6710`), add a
second, independent save:

```ts
const ledger = await this.computeObservedFeeLedger(findDeal.deal)
if (ledger) {
  findDeal.deal.feeByAsset = ledger.feeByAsset
  findDeal.deal.feePaid = ledger.feePaid
  this.saveDeal(findDeal, {
    feeByAsset: findDeal.deal.feeByAsset,
    feePaid: findDeal.deal.feePaid,
  })
}
```

A second `saveDeal` call rather than folding into the existing one:
the existing call's field list is unrelated bookkeeping
(balances/prices/levels/status) and this keeps the new behavior a
clean, independent addition rather than one more thing to track inside
an already-large object literal.

### 3. Call it from `updateDeal`

else if (dealTP) {...} else {...regular...}` split — structurally
common to all three, so one call covers a safety/DCA order fill, a
plain or reduce-funds TP fill, and an add-funds fill alike:

```ts
const ledger = await this.computeObservedFeeLedger(findDeal.deal)

```

Same reasoning as `startDeal`: independent save, not folded into any
of the three branches' own field lists.

### 4. Make `closeDeal` idempotent against an earlier incremental update

One line, immediately before `for (const o of dealOrders)` (`:2343`):

```ts
findDeal.deal.feeByAsset = []
```

Without this, `closeDeal`'s `accrueFeeLedger` calls seed from whatever
`findDeal.deal.feeByAsset` currently holds — which, after this spec,
could already be the correct pre-close total from the last incremental
update — and would add the same legs a second time. `feePaid`
(`feeBaseFull`/`feeQuoteFull`) needs no equivalent fix: they are
already local variables initialized to `0` inside `closeDeal`, never
seeded from the deal's stored value.

## Why this JIT tier (1, not 0 or 2)

Tier 1: pull the observed-only computation into its own named method,
even though it stays coupled to `this` (DB-backed order lookups,
`this.getUsdRate`, `this.exchange`) — matching this repo's own
guidance for `closeDeal`/`getCommDeal`-adjacent work (spec 020/021's
"too heavy to make pure, extract only if there's a real duplication
reason to"). Here there IS a real reason: three call sites
(`startDeal`, `updateDeal`, and implicitly the pattern `closeDeal`
already has) need the identical computation, so a shared method is the
right size — not a pure module function (needs `this`), not a full
ports-and-adapters rewrite (nothing here is decision-logic-vs-I/O that
benefits from that boundary; it is I/O-shaped end to end, same as its
neighbors).

## Blast radius

1. **Other call sites.** `startDeal` has one call site
   (`processFilledOrder`, spec 020/021's own traces already confirm
   this file's dispatch shape); `updateDeal` has several
   (`processFilledOrder`'s `dealRegular`/`roa`/multi-tp-partial/reduce
   branches, all converging on the same function) — the one insertion
   point covers all of them by construction, not by enumerating each
   caller. `closeDeal`'s only change is the one-line seed fix; its
   own call sites (`processFilledOrder`'s full-close branch) are
   unaffected in shape.
2. **`core/` submodule.** `main-app-sh` — parent pointer bump at ship
   time.
3. **Contracts this repo owns.** `feeByAsset`/`feePaid` are existing
   `Deal` schema fields (spec 014/020) — no shape change, just an
   earlier and more frequent write. Any consumer already reading these
   fields (combo's own display, dashboards) sees more current data
   sooner, never a different final value once the deal closes (spec
   020's fix plus this plan's idempotency fix keep the close-time
   result identical to before).
4. **Other tests.** No existing test reaches `startDeal`/`updateDeal`/
   `closeDeal` (same constraint noted in spec 020/021 — this repo has
   no harness light enough to instantiate `MainBot`). `orderFee.spec.ts`
   and `feeLedger`'s own coverage (`observedFeeSplit`/`observedFeeLegs`/
   `accrueFeeLedger`) is unaffected — reused, not changed.

## Test approach

Same constraint as spec 020/021, compounded: this spec touches THREE
methods on the same heavy class. Gate 2/6 is a live reproduction —
run a deal through base order → a safety order fill (or a multi-TP
partial) → close, on a `PAPER_FEE_ASSET_SYMBOLS`-configured symbol, and
confirm `feeByAsset`/`feePaid` are populated and correct **after the
base order alone** (before any close), stay correct through the
intermediate fill, and land on the SAME final numbers at close that
spec 020/021 already validated (the idempotency check this plan exists
to guarantee).

Flagging again, now for the third spec in a row: a `tests/processing/`
integration harness reaching `processFilledOrder`/`startDeal`/
`updateDeal`/`closeDeal` would let gate 2 pin all of this with a red/
green test instead of a live rerun each time. Recommended as its own
task — three specs deep into needing it is a real signal, not a
one-off.
