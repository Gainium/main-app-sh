# 043 — plan

Spec: [`specs/043.a-dust-close-is-refused-forever-and-says-nothing.md`](../specs/043.a-dust-close-is-refused-forever-and-says-nothing.md)

## Build order

One file, `src/bot/dcaHelper.ts`, plus one new instance field on the mixin.

1. **`closeBelowMinimumStreak: Map<string, number>`** on `DCABotHelper`
   alongside the other per-bot Maps. Consecutive refusals per `dealId`. Not
   Redis-backed and deliberately so, for the reason `ConditionLatch` documents:
   it gates whether a REPORT is written, a bot lives in one worker at a time,
   and a restart re-reporting once is correct.
2. **Rewrite the `035` §4.3 block** in `getTPOrder`:
   - `heldQty` from `trackedPosition(...)`, floored onto the base grid;
   - `qtyForFloor` unchanged;
   - long and `qtyForFloor > heldQty` → bounded price raise (§4.2) when
     `!sl`, else refuse; otherwise `tpOrder.qty = qtyForFloor` as today.
   - one `refuse()` closure holding §4.3/§4.4's reporting decision, so the
     three refusal exits cannot drift apart.
3. **Clear the streak** immediately after the block, on every path that got
   past it.

## Contract decisions the spec left open

- **Where "what the deal holds" comes from.** `trackedPosition` from
  `dca/tpCoverageReconcile`, already imported into `dcaHelper` and already used
  at the tp-coverage reconcile site. Its own docstring names `getTPOrder`'s
  sizing terms as what it must agree with, and `trackedPosition(size, …)` is
  algebraically `|dealSize| + add` — the exact term `getTPOrder` already
  subtracts. Verified against production: the HYPE-USDC deals report
  `size: 0.13` and `currentBalances.base: 0.13`, and `trackedPosition` returns
  0.13 where the close was sized 0.12. No new helper.
- **The bound on the raise.** `MAX_CLOSE_PRICE_DEVIATION`, the constant §4.4
  already uses, applied in the opposite direction and only to a price WE
  compute. Expressed inline (two lines) rather than as a second helper:
  `closeGivesValueAway` is one-sided by design and documented as such, and a
  near-copy of it pointing the other way would read as a duplicate of the rule
  it is not.
- **N.** 5. The refusal recurs roughly once a minute per deal, so five is a few
  minutes of a genuinely standing condition and cannot be reached by one bad
  cycle — which matters because `dealSize` can be transiently under-read while
  a restarted worker is still loading deals (spec `017`'s `resolveBaseOrderQty`
  fallbacks exist for exactly that), and a spurious user error is worse than a
  late one.
- **`setError`.** False. `processError` turns `setError` into
  `setRangeOrError(BotStatusEnum.error)`, which stops the bot. One dust deal
  must not stop a bot still trading its other pairs.

## Blast radius

1. **Other call sites.** The changed block is inside `getTPOrder` and nothing
   else reads its locals. `getTPOrder` itself has eight call sites
   (`prepareTpOrder`, `createCurrentDealOrders`, the two `createDealBalances`
   estimates, the tp-coverage re-arm, `reduceFunds`, `checkTPLevel`); all of
   them already handle an empty return, which is what this block does today on
   every long. The change only ever turns an empty return into an order, plus
   the reporting change — no caller sees a new shape.
2. **`core/` submodule.** Yes — `dcaHelper.ts` is `main-app-sh`, shared with
   every consuming service and the self-hosted edition. Parent pointer bump
   required. This is the widest-blast-radius file in the platform, which is why
   §4.5 pins the untouched path and why the `035` harness must stay green.
3. **Owned contracts.** None touched. No GraphQL, REST, socket.io, RabbitMQ or
   Mongo schema change. `botmessages` rows keep the same message stem
   (`Close order is below the exchange minimum. Deal … qty … at price … is
   under …`), so any admin `boterrorsubtypes` rule keyed on the text still
   classifies it the same way; only the reporting FLAGS and the quantity shown
   change.
4. **Other tests on this path.** `dca/tpPriceRefusal.harness.spec.ts` (035),
   `dca/tpNanRefusal.harness.spec.ts` (023), `dca/nanLadderRefusal.harness.spec.ts`
   (025), `dca/tpLadderPriceRefusal.harness.spec.ts` (037),
   `dca/tpSizingFromPosition.harness.spec.ts` (017),
   `dca/tpSizingAfterPartialTp.harness.spec.ts`, `dca/tpCoverageReconcile.spec.ts`.
   All must stay green. **`035`'s §4.3 case changes expectation** — it is the
   case this spec amends, and it was already written to accept either outcome;
   its `tps.length` branch now asserts the bounded raise instead of a
   near-market price. Amended in place, with the amendment named.

## JIT legacy extraction tier

and the one piece of it that is genuinely a reusable judgement — "what does
this deal hold" — is ALREADY extracted, as `trackedPosition`. Wiring the
existing pure module in at this call site is the extraction; lifting more of
`getTPOrder` out is scope the bug does not pay for.
