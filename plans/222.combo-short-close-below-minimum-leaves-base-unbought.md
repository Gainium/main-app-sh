# Plan 222 — carry a skipped combo SHORT buy-back to the next close

Spec: `specs/222.combo-short-close-below-minimum-leaves-base-unbought.md`.

## Build order

1. Pure rules, `src/bot/dca/comboShortCloseCarry.ts`: read/set a per-symbol
   carry, accrue after a skip, repay after a fill. No I/O (JIT Tier 2: a new
   module, because the carry is new logic and needs no legacy extraction).
2. Storage: `shortCloseCarry: [{ symbol, base }]` on the combo bot schema
   (`src/db/schema.ts`) and on `DCABotSchema` in `types.ts` (optional; the
   helper's `this.data` is typed through it).
3. `dcaHelper.ts`:
   - `getTPOrder` gets a trailing optional `shortCloseCarry`. Only
     `prepareTpOrder` passes it. In the combo branch, for SHORT spot with quote
     profit, it adds `min(carry, what the deal's quote can pay for beyond its
     own buy-back)` before the venue-minimum checks. A skip records the deal's
     own shortfall in `shortCloseBelowMinimum`. A built order records the
     carried base it contains in `shortCloseCarryInOrder`.
   - `closeDealById` clears both entries before `prepareTpOrder`. In the
     `No tp order. Close without order` branch it calls
     `carrySkippedShortClose`, which adds the recorded shortfall to the carry
     and persists it.
   - `closeDeal` (filled close order) calls `settleShortCloseCarry` after the
     fill is booked. It repays the carry by the carried base in that order,
     scaled by `executedQty / origQty`.
4. Version bump and changelog, in core and in the parent.

## Decisions the spec left open

- **Where the carry lives:** a new persisted bot field, not a value derived
  from closed deals (spec §2.3). It starts at 0, so deploying it sends no order
  by itself. It is stored data: the ship gate stops on it.
- **Repay measured against the order, not the books.** For SHORT the combo
  close subtracts an entry-fee estimate (`comboEntryBaseFee` over the deal's
  SELL fills) from its own part, by design. A books-based repayment would leave
  that estimate in the carry for good.
- **Carry limited by the deal's quote.** This mirrors the existing SHORT spot
  cap in `prepareTpOrder`. Without the limit, that cap could cut a
  carry-inflated order back under the minimum, and the venue would refuse it.
- **Restart window:** `shortCloseCarryInOrder` is in memory. A close order
  that fills after a bot restart does not repay, so the next close buys the
  carry again. That over-buy is bounded by one minimum order and leaves the
  bot holding base, not short of it. Persisting it per order would mean
  another stored field for a millisecond-wide market-order window.

## Blast Radius

1. Call sites: `getTPOrder` has 11 callers. Only `prepareTpOrder` passes the
   new argument, so the other 10 size exactly as before (harness §1.5 case).
   `prepareTpOrder` is used by `closeDealById` and by the spec 015 fee-sizing
   resend. Both are close paths, and both clear or overwrite the in-memory
   maps.
2. Under `core/` (main-app-sh): shared with self-hosted, and the parent's
   submodule pointer moves. No other service imports `dcaHelper`.
3. Contracts: a new OPTIONAL field on the shared `combobots` Mongo
   collection. It is not in GraphQL, REST or socket payloads. Legacy main-dash
   and admin-app read `combobots` directly, and an unknown extra field is
   inert for them.
4. Other tests on this path: `comboFeeDust`, `tpDustClose`,
   `closeAfterSweptTpFill`, the refused-close harnesses, and the full core
   suite.
