# 174 — plan

## Solution

1. **`dcaHelper.restoreWork`, the "never started" replay (§1.1.1–§1.1.5).**
   This step runs on a service restart only. It comes after the funded-entry
   and stale-trigger checks and before the call to `placeBaseOrder`. For each
   `dealStart` order of the deal that the order map holds (`NEW` /
   `PARTIALLY_FILLED`) with the `'-1'` placeholder, it asks the venue through
   `getOrderForReconcile`. Only when the answer is `isDefinitiveOrderNotFound`
   does it call `MainBot.retireUnsentOrder` (spec 172). That method re-checks
   `'-1'`, applies the `unsentOrderMinAgeMs` floor, and requires that Mongo has
   no row for the client order id before it drops the order from the map. Then
   `placeBaseOrder` runs unchanged. Its `currentBase` refusal still guards every
   order that was not dropped.

JIT tier: Tier 0. This is a guard inside the existing legacy branch, and it
reuses the existing lookup, classification and retirement helpers. Nothing is
new except the call site.

## Blast Radius

- Call sites: only the DCA `restoreWork` start-deal branch, and only in the
  case that already decided to re-place the entry. Combo has its own restore
  path and is untouched (spec §4.3).
- `core/` (main-app-sh): public and shared. The submodule pointer needs a bump
  in main-app.
- No GraphQL, socket, queue or schema change. There is one venue lookup per
  `'-1'` entry per restart. The Mongo read is by `clientOrderId`, which is
  indexed.
- Order-moving: when the venue definitively does not know the old client order
  id and Mongo has no row for it, `placeBaseOrder` places a new entry. A
  lookup that is ambiguous or positive, or an order with a row or a real id,
  keeps the refusal, so no second entry is placed.
- Tests that must stay green: `restartMidDealStart.spec.ts` (spec 172),
  `coldRestartDealSnapshot.spec.ts` (spec 151), and the rest of `npm test`.
