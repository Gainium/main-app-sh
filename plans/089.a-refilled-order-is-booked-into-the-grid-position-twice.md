# 089 — Plan

Spec: `specs/089.a-refilled-order-is-booked-into-the-grid-position-twice.md`.

Give the position fold the per-fill idempotency `createTransaction` already has,
and seed it from the rebuild so the teardown at the start of every bot run
cannot double-book.

## §1 Build order

All four edits are in `core/src/bot/helper.ts`, the grid helper mixin.

1. **The record.** A `private positionBooked: Set<string> = new Set()` beside
   `feeProcessed` (`:160`) — the same shape this class already uses to make
   `processFeeOrder` idempotent per `clientOrderId`.
2. **The guard.** In `calculatePosition` (`:2157`), after the
   `!this.data || !this.futures` return (spec §4.1 — a spot grid folds nothing
   and must not populate the record), return early on a `clientOrderId` already
   in the record, and add it otherwise. The early return is logged at debug so
   the refusal is greppable next to the `Position after …` line it replaces.
3. **The seed.** A `protected seedBookedPosition(orders)` next to
   `resetPosition`, and a call to it in `loadOrders` (`:310`) with the SAME
   filtered slice `calculatePositionForOrders` is handed — the two must not
   drift, so the slice is lifted into one local and used for both.
4. **The lifetime.** Clear the record in `clearClassProperties` (`:2478`),
   where `this.orders` is already emptied. Not cleared on `resetPosition`
   (spec §4.3).

## §2 Contract decisions the spec left open

- **The record is a `Set<string>` of `clientOrderId`, in memory.** The durable
  alternative — reusing `createTransaction`'s ledger read
  (`transactionDb.countData({ index })`) — is unusable here: `processFilledOrder`
  calls `createTransaction` WITHOUT awaiting it and then awaits
  `calculatePosition`, and `createTransaction` is serialised per bot behind
  `@IdMute(…'transaction')` with several awaits before its insert. On the
  observed timeline the re-delivery arrives ~170 ms after the fill, well inside
  the window where the row may not be written yet — the guard would be racy in
  precisely the case it exists for.
- **No cap and no TTL.** Both would be a threshold that silently stops covering
  a slow re-delivery. The record is bounded by the same thing `this.orders` is:
  it holds ids for orders whose whole `Order` document that map already retains,
  so it cannot grow to a new order of magnitude (spec §4.3).
- **`seedBookedPosition` is `protected`, not `private`.** `comboHelper` embeds
  this mixin and may need the same seeding if it grows a rebuild; `private`
  would also put it out of reach of the spec test.

## §3 Blast Radius

1. **Other call sites of the changed functions.** `calculatePosition` has three
   callers, all in this file: `processFilledSwap` (`:701`, a swap order, once,
   behind `swapLock`), `processFilledOrder` (`:2106`) and the balance-diff
   reconcile (`:3349`). None folds the same `clientOrderId` twice by design, so
   none is broken by the guard. Verified that no partial-fill path reaches it:
   every `processFilledOrder` caller (`:1197`, `:1308`, `:1397`, `:1599`,
   `:1861`) is gated on `status === 'FILLED'` or iterates a `filledOrders`
   list — `PARTIALLY_FILLED` orders are routed to `partiallyFilledOrders`
   instead. An order is therefore folded once, when it reaches FILLED, and the
   guard cannot swallow a legitimate delta.
   `calculatePositionForOrders` keeps its only caller (`:310`) and is unchanged.
2. **`core/` submodule.** Yes — this is `main-app-sh`, shared and deployed
   platform-wide. The change is confined to the grid helper mixin
   (`BotHelper` for `BotType.grid`); `dcaHelper` and `comboHelper` have their
   own position folds and are not touched. No exported type, signature or
   default changes, so nothing downstream recompiles differently.
3. **Documented contracts (root `CLAUDE.md` Danger List).** None touched. No
   `BaseReturn<T>`, no `/api/v2` shape, no GraphQL field, no socket.io event
   name, no Redis channel, no `ARCHIVE_QUEUES` payload. `position` and
   `positionHistory` keep their shapes — the change is to the VALUE written,
   which is the defect. `_handleUnknownOrder`'s return contract is deliberately
   left alone (spec §4.4), which is what keeps `dcaHelper`/`comboHelper` and the
   `sendOrderToExchange` write-off guard out of the radius.
4. **Other tests on this path.** `gridPositionValue.spec.ts` (spec 064, reads
   `data.position` for `tpSl`), `gridCloseProfitLedger.spec.ts`,
   `remainderDoubleCount.spec.ts` (borrows the same
   `calculateAbstractPosition`), `cancelNoExchangeOrderId.spec.ts` (the
   unknown-order ladder). Full `npm test` in `core/` must stay green, plus
   `tsc` in BOTH `core/` and the parent — the parent `src/` is a coupled copy
   that compiles against these types.

## §5 JIT legacy tier

**Tier 0.** The causal path is a four-line fold in an existing method; the fix
is a guard on it. `calculatePosition` already mixes the decision with
`updateData`/`emit`, but extracting it buys nothing here — the defect is the
absence of a key, not the coupling — and pulling a method out of a 5.3k-line
mixin that every grid bot runs is scope the bug does not justify.
