# Plan 202 — the close-after-X auto-stop deadlocks on the deal-close lock

## Solution

Fix the root cause the spec's §3 names, the way spec `055` fixed
`placeOrders`: a caller that already holds the lock runs the body without
taking it again.

1. `processDealClose` keeps its `@IdMute` and delegates to a new protected
   `processDealCloseHoldingLock` holding the old body. Subclasses extend the
   body, so both entries run them (main-app's close webhook moves there).
2. `checkClosedDeals` (only caller: `processDealClose`) stops through
   `stopFromDealClose`, which calls `stop(leave, false, false, true)`.
3. `stop(…, holdingCloseLock)` passes the flag to the start-deal cancels;
   `closeDealById(…, holdingCloseLock)` then calls
   `processDealCloseHoldingLock`. The flag is NOT forwarded to the
   loading-queue replay, which runs later outside the lock. Combo's
   `closeDealById` override forwards it.
4. Recursion guard: inside the nested cancel `checkClosedDeals` fires again.
   While a stop is running (`stopsInFlight > 0`) and start deals remain,
   `stopFromDealClose` starts no second stop. The running one is already
   cancelling them. With no start deal left, it is the old inline
   `stop(leave)`.
5. `stop` counts itself in `stopsInFlight` (`finally` decrement).
   `openNewDeal` refuses while it is > 0, which covers every start path.
   `openDealBySignal` refuses as well and reports it through
   `reportIgnoredWebhookSignal`.

JIT tier 0: the touched methods stay where they are. The change is a
lock-ownership split, the smallest one that removes the deadlock.

Rejected: deferring the stop until the lock is released (fire-and-forget).
The reload sweep that triggered it in production keeps running and would
replay base orders for deals the deferred stop is about to cancel. Also
rejected: AsyncLocalStorage reentrancy, which also leaks into un-awaited calls
spawned inside the lock (`updateBotDeals` → `checkOpenedDeals`) and would let
them run beside the holder.

## Blast Radius

1. Call sites: `processDealClose` callers are unchanged (still locked).
   `stop` has one new optional trailing parameter, and every existing caller
   passes ≤ 3 args. main-app's `DCABotHelper.stop` override forwards it.
   `closeDealById` has a new optional trailing parameter; combo's override
   forwards it, and no other caller passes 13 args.
2. `core/` — shared. Bump the parent pointer.
3. No GraphQL / socket / queue / collection shape changes.
4. Existing specs that drive these paths:
   `closeCancelRefused`, `closeSweepResume`, `closeAfterSweptTpFill`,
   `userRefusalFeedback.harness`, `lateEntryFillAfterClose`.
   `dca/trailingTpCloseRetry.harness` pins the close body's
   `clearTrailingRetryTimer` by source text. Its marker moves to
   `processDealCloseHoldingLock`, where the body now lives, and the wiring it
   pins is unchanged.
