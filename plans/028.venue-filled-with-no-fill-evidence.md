# Plan 028 — A venue answer of FILLED carrying no fill evidence closes a deal on nothing

Spec: [`specs/028.venue-filled-with-no-fill-evidence.md`](../specs/028.venue-filled-with-no-fill-evidence.md).

## 1. Solution

Two guards on the causal path the spec's Assumption (§3) names, plus the pure
predicate they share.

1. **`src/bot/fillEvidence.ts` (new, pure).** `statesQuantity(value)` — did the
   payload state this number at all, `0` included. `isFillEvidenceFree(o)` — did
   it state no fill at all (§4.1). No DB, queue, HTTP or framework import; the
   Part-3 boundary check is trivially satisfied.

2. **`MainBot.mergeCommonOrderWithOrder` (`src/bot/main.ts`).** The single funnel
   every reconcile path — `dcaHelper.checkOrders`, `comboHelper`, `helper.ts`,
   `sendOrderToExchange`'s price recovery — runs a venue answer through.
   - §4.3: `executedQty` / `cummulativeQuoteQty` the payload does not state
     fall back to the local values instead of being erased.
   - §4.4: the `quote / base` derivation is `Number.isFinite`-guarded, so
     `NaN / NaN` falls back to the local price rather than collapsing to `0`.
     The derivation keeps reading the PAYLOAD's own figures (not the §4.3
     fallbacks) so a venue that reports a quantity but no executed value is
     priced exactly as before.
   - §4.2: a `FILLED` with no fill evidence at all, against a local order that
     is not already `FILLED`, keeps the local `status` and `updateTime` and
     raises a WARN naming the order and the payload.

3. **`dcaHelper.closeDeal` (`src/bot/dcaHelper.ts`).** §4.5: a resolved close
   quantity that is not a finite number greater than zero refuses the close —
   error naming the take-profit, `pendingClose` cleared, `endMethod` called, the
   deal untouched.

### Decisions the spec left open

- **Keep the local status, do not `quarantine`.** `quarantine` means "stop
  polling this order" (see `MainBot`'s own comment on the push half of the
  invariant). The order under this guard is exactly the one that must keep
  being polled, because the next answer is what resolves it.
- **Guard `mergeCommonOrderWithOrder`, not each caller.** Nine call sites across
  four files reach it; a per-caller guard would be nine copies and would miss
  the grid and combo engines, which took the same 16-row promotion.
- **Not `dealTP`-only,** although the brief named `dealTP`. The same window
  promoted 8 `dealRegular`, 3 `dealGrid` and 1 `regular` row the same way and
  poisoned eight further deals' `currentBalances`/`assets`. Restricting the
  guard to take-profits would leave that half in place for no reduction in risk.
- **`closeDeal` refuses on `qty <= 0`, not only on non-finite `qty`.** They are
  the same statement — this take-profit sold nothing — and a zero would divide
  to `NaN` on the very next line anyway.

### JIT extraction tier (Part 4)

**Tier 1** for the new predicate: `isFillEvidenceFree` / `statesQuantity` are
pulled into their own named, tested module rather than inlined in the 8k-line
`main.ts`. Not Tier 2+ — the two guards themselves stay inside the existing
methods, because extracting the merge or `closeDeal` is a rewrite of the deepest
part of the engine, sprung on a bug fix. Not Tier 0 — the predicate has two call
sites already and is the whole safety argument, so it needs its own test.

## 2. Blast Radius

1. **Other call sites of `mergeCommonOrderWithOrder`** (grepped): `main.ts:8118`
   (`sendOrderToExchange` price recovery — uses `merged.price` only, and only
   when `executedQty > 0`, so the new branch cannot fire on a real fill there),
   `dcaHelper.ts` ×3, `helper.ts` ×7, and the combo/hedge engines through the
   same helper. All of them get the guard, which is the point. **No call site
   changes.**
   Call sites of `closeDeal`: 8 in `dcaHelper.ts` (`closeDealById`,
   `processFilledOrder`, signal close, stop, …). Only the `tpOrder` arm is
   touched; the liquidation and no-TP arms are untouched.
2. **`core/` submodule** — yes. `main.ts`, `dcaHelper.ts` and the new module are
   all under `main-app-sh`, shared with the self-hosted edition and deployed
   platform-wide. The parent pointer needs bumping deliberately at ship time.
3. **Documented contracts** (root Danger List / this repo's `CLAUDE.md`
   § Cross-service contracts): **none touched.** No GraphQL/REST/OAuth shape, no
   socket.io event name, no RabbitMQ queue or payload, no Mongo schema field, no
   `BaseReturn<T>`. The change is entirely inside the bot engine's own
   interpretation of an exchange payload; the persisted `orders` document keeps
   every field it had, with values that are strictly more conservative.
4. **Other tests on this path that must stay green:**
   `src/bot/orderNotFound.spec.ts`, `src/bot/reconcileAttemptReporting.spec.ts`,
   `src/bot/resizeCancelPromotion.spec.ts`, `src/bot/strandedLocalRefusal.spec.ts`,
   `src/bot/nanOrderRefusal.spec.ts`, `src/bot/cancelNoExchangeOrderId.spec.ts`,
   `src/bot/dca/tpCoverageReconcile*.spec.ts`, `src/bot/dca/lostLedgerClose.harness.spec.ts`,
   `src/bot/dca/multiTpCompletion*`, `src/bot/dca/placeOrders*`. Whole suite run,
   both `tsc --noEmit` projects (core and parent) run.

### The risk that is NOT reduced

A venue answer that is wrong but *does* state a fill still promotes. This guard
is deliberately the narrowest one that covers the observed failure; it is not a
plausibility check on venue data.

## 4. Build order

1. `fillEvidence.ts` + its unit spec.
2. The merge guard; run the harness spec (red → green on §4.2/§4.3/§4.4).
3. The `closeDeal` guard; run the harness spec (red → green on §4.5).
4. `tsc --noEmit` in `core/` **and** in the parent `main-app/` — the parent
   compiles `core/` sources, so a core-only typecheck is not enough.
5. Full `npm test` in `core/`.
6. Version bump + `CHANGELOG.md` entry in `core/` (public repo — mechanism only,
   no ids, no counts).
