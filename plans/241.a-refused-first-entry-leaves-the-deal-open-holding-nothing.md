# 241 — plan

## Change

1. `src/bot/dca/strandedStartClose.ts`
   - `isRetirableStrandedStart` takes an optional `graceMs`, defaulting to
     `STRANDED_START_GRACE_MS` (§4.1).
   - New pure `shouldRetireRefusedEntry` (§4.2). It reuses
     `isAmbiguousOrderFailure` / `isPlacementReadBackMiss` from
     `utils/exchange`, the same classifiers `sendOrderToExchange` uses to decide
     whether to ask the venue before writing an order off.
2. `src/bot/dcaHelper.ts`
   - `retireStrandedStartDeal` passes an optional `graceMs` through. The sweep
     caller does not pass one, so it keeps the 24 h grace.
   - New `retireRefusedStartDeal(botId, dealId)`, under `closeDealById`'s
     per-deal `IdMute` key. It calls `retireStrandedStartDeal(…, auto, 0)`, and
     only when that filtered write lands does it do the bookkeeping that
     `processDealClose` would do for a deal that never held anything:
     `clearDealTimer`, `removeDealFromStopLossMethods`, `pendingClose`,
     `removeOrdersByDeal`, `deleteDeal`, `resetAssets`,
     `updateBotDeals(false)`, `updateUsage(reset)` and
     `checkDealsAllowedMethods` (§4.3). It deliberately skips
     `restoreFromRangeOrError`, reopen, profit, cost facts and stats (§4.7).
   - `placeBaseOrder`, final refusal `else`, after `handleOrderErrors` and the
     terminal `stop()`: if `shouldRetireRefusedEntry`, then
     `await retireRefusedStartDeal`.

JIT tier 2 for the decision (pure, tested with no mocks). The orchestration
stays in the legacy method as a single guarded call. No wider extraction:
`placeBaseOrder` is on the path, but only its last branch is touched.

## Decisions the spec left open

- Message: reuse `strandedStartCancelMessage` (written by
  `retireStrandedStartDeal`). It already says the deal never opened, nothing
  is on the exchange and it was cancelled. No new wording.
- `closeTrigger`: `auto`, the sweep's default.
- Funding-hold deals (spec 044 beta) are excluded rather than settled here.
  Their reservation bookkeeping is out of scope, and the sweep still covers
  them.

## Blast radius

- Call sites: `retireStrandedStartDeal` has one existing caller
  (`closeDealById` map-miss path), which passes no grace, so it is unchanged.
  `isRetirableStrandedStart` has the same single runtime caller.
- Subclasses: `comboHelper` overrides `placeBaseOrder` wholesale, so combo is
  untouched. Production has no combo deals of this shape (spec §2). The hedge bot
  (`hedgeHelper`) is a `MetaBot` over child bots. A DCA leg runs this
  `placeBaseOrder` and inherits the change, a combo leg does not, and a
  hedge-funding deal with a `fundingHold` is excluded. The
  main-app parent does not override `placeBaseOrder`.
- `core/` (public `main-app-sh`): the pointer is bumped by `psh` at push.
- Contracts: none. No schema, GraphQL, socket or queue change. The deal write
  sets the same four fields the sweep already sets.
- Re-entry: the bot stays in whatever status `handleOrderErrors` put it in. Its
  next entry comes from its normal start triggers, and repeat venue refusals
  are already throttled by the per-`symbol@side` not-enough-balance backoff,
  `ComplianceGuard` and `AuthFailureGuard`. This is the same behaviour as after
  spec 039's unbuilt-entry cancel and the funding-refused retire.
- Tests that must stay green: `dca/unactionedClose.harness.spec.ts` (spec 046),
  `limitOnlyEntryReport.spec.ts`, `quantRulesRetry.spec.ts`,
  `strandedLocalRefusal.spec.ts`, `newDealBalanceRetry.spec.ts`,
  `userRefusalFeedback.harness.spec.ts` and the rest of the placement family.

## Invariant

main-app `specs/invariants/deals.invariants.json` gets
`deals.refused-entry-still-start` (observe). `deals.start-stuck-nothing-resting`
excludes `startBlocked` deals on purpose, so nothing watched this shape.
