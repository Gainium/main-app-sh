# 149 — plan

## Build order
1. `src/bot/settingsReloadLeverage.spec.ts`: a second `describe` drives the real
   `MainBot.loadData` through a service-restart load
   (`serviceRestart && !secondRestart`, not a reload) followed by a keep-orders
   reload. Red before the change: 40 + 40 venue calls for 40 unchanged pairs.
   The spec 148 §4.2 case stays, renamed to §1.1.3. An instance that never
   loaded at all still applies every pair.
2. `src/bot/main.ts` `loadData` futures loop: hoist `requiredSide`, `leverage`,
   `margin`, `leverageSide` and `appliedKey` above `if (skipFutures)`. None of
   them read the positions response, so this only reorders the code. On the skip
   path, set `appliedFuturesSettings[symbol] = appliedKey` before `continue`. The
   apply block reuses the same constants, so the key cannot drift between the two
   paths.
3. Core version bump plus CHANGELOG, then the parent version and CHANGELOG, and
   the pointer bump at ship.

## Contract decisions left open by the spec
- Seeding happens only after the per-symbol hedge-leg checks, at the same place
  the skip path already `continue`d. A leg that refuses to start returns before
  it.
- Values come from the persisted settings and the live hedge read, the same
  inputs the apply block uses.

## JIT tier
Tier 0: a reorder plus one write inside the legacy loop. Extraction is out of
radius.

## Blast radius
1. `appliedFuturesSettings` is read only by the spec 148 skip in the same loop.
   Only a keep-orders reload (`this.reload`) consults it.
2. `core/` file, shared by every bot type. Grid never sets `this.reload`, so
   seeding has no effect there.
3. No GraphQL, socket, queue or DB shape is touched. No venue call is added. The
   values sent are unchanged.
4. Must stay green: the spec 148 cases, `hedgeMode.harness.spec.ts`, the full
   core mocha suite.
