# Plan 024 — reconcile a lost balance ledger before `closeDeal` books profit

Spec: `specs/024.deal-close-books-a-full-volume-loss-from-a-lost-ledger.md`
(issue #716).

## 1. Solution

Two changes, both in `core/src/bot/dcaHelper.ts`, addressing the two halves of
the causal chain the spec's Assumption names.

### 1.1 `closeDeal` — reconcile before booking (spec §3.1/§3.2, §4.1-§4.3)

The take-profit branch already loads `dealOrders` — filled/partially-filled
orders for this deal, minus `br`/`rebalance` — but only *after* it has mutated
`currentBalances` at L2384. **Hoist that existing computation above the
mutation and reuse it**; no new query, no new filter, no new helper.

Then, immediately before L2384:

- Decide the ledger is **lost** when either side is non-finite
  (`NaN`/`null`/absent — `Number.isFinite` is false for all three) *or* both
  sides are exactly `0`.
- Only act if `initialBalances` is itself finite (it is the baseline the
  rebuild starts from) and there is at least one filled order other than the
  take-profit legs this close accounts for. Otherwise leave everything alone —
  §4.2.
- Rebuild as `initialBalances` + each such order, using the **same formula the
  live fill path uses** (`processFilledOrder`, L7356-7365), and the ROA branch's
  formula (L7424-7439) for add-funds fills, detected with that method's own
  `clientOrderId.indexOf('ROA') !== -1` test — §4.3.
- Exclude `tpOrder.clientOrderId` and the `filledTp` ids, because L2384 applies
  those separately as `qty`/`price`.
- Report through `handleErrors` (non-notifying, like the spec-023 refusal) so
  the repair is never silent.

`getTPOrder`'s spec-023 refusal is the precedent for the shape: a guard that
fires only on a provably broken input, placed immediately before the code that
would otherwise consume it.

### 1.2 `loadOrders` — do not seed a non-finite ledger from Redis (spec §3.3/§4.4)

`loadOrders` L1328 already refuses the whole restored set when any deal's
`avgPrice` is not a number (`checkAvg`) and falls back to the DB. Extend that
existing predicate to the balance ledger. This is where the `null` entered
memory, and the DB copy is the last mongoose-**validated** state — the
CastErrors in spec §2.3 are the proof that Mongo never accepted the NaN.

## 2. Contract decisions the spec left open

- **Repair vs. refuse.** The deal has already closed on the venue; refusing to
  book would strand it open forever. Repair, and report.
- **Tolerance-based detection was rejected.** Comparing the live ledger against
  the rebuild on *every* close and repairing on drift would fire on legitimate
  divergence (partial fills, funds added/reduced mid-deal) and put a rewrite in
  the money path of every DCA close. The predicate stays narrow: non-finite, or
  exactly `{0, 0}`.
- **No new utility.** `getOrdersByStatusAndDealId` + the existing `dealOrders`
  filter already produce the order set; the ledger formulas are lifted from the
  two live call sites rather than generalised into a new shared helper, so
  there is one arithmetic definition per behaviour, not a third.

## 3. Blast Radius

1. **Other call sites.** `closeDeal`'s take-profit branch is the only code
   changed; the liquidation branch (L2710+) and `sellRemainder`/`processFilledOrder`
   are untouched. `dealOrders` is moved earlier within the same block and is
   not read before its new position. `loadOrders`' `checkAvg` has one call site.
2. **`core/` submodule.** Yes — `main-app-sh`, shared with every consuming
   service and deployed platform-wide. The parent pointer must be bumped
   deliberately. Behaviour is additive and gated on a state that cannot occur
   on a healthy deal, so consumers see no shape change.
3. **Cross-service contracts.** None touched. No GraphQL/REST shape, no
   socket.io event name, no queue name or payload, no Mongo schema field is
   added, removed or retyped. `deal.currentBalances` / `deal.profit` keep their
   existing types; only their *values* change, and only for a deal whose values
   are already wrong.
4. **Other tests on this path.** `src/bot/dca/tpNanRefusal.harness.spec.ts`
   (spec 023, same deal), `src/bot/feeLedger.spec.ts` and the rest of
   `src/**/*.spec.ts` must stay green.

## 4. JIT legacy tier

**Tier 0.** `closeDeal` is a 400-line I/O-mixed method, but the causal path is
a single arithmetic guard inserted ahead of one assignment. Extracting the
ledger arithmetic into a pure module would mean moving the L2384 close delta
and the L7356/L7424 fill formulas with it — a rewrite of the money path of
every DCA close, on a bug whose fix is 30 lines. Radius rule: not "already
being touched." Recommend it as its own modernization task.

## 6. What this plan does not verify

- §4.4's guard is verified by reading, not by a test: `loadOrders` reaches for
  Redis and Mongo in its first ten lines and there is no existing harness for
  it in this repo. It is a two-term extension of a predicate one line above it.
- Spec §5.1 — repairing the seven corrupted production deals and backing the
  −$3,576.35 out of the bot aggregates and profit history — is a production
  database write and is out of scope for the fix session.
