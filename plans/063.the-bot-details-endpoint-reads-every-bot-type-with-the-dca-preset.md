# 063 — Plan

Spec: [`specs/063.the-bot-details-endpoint-reads-every-bot-type-with-the-dca-preset.md`](../specs/063.the-bot-details-endpoint-reads-every-bot-type-with-the-dca-preset.md)

## Build order

1. **`src/server/v2/fieldConfig.ts`** — add `BOT_TYPE_ENDPOINT` plus
   `endpointForBotType(botType)`. `fieldConfig.ts` has no imports and is where
   `ENDPOINT_FIELD_CONFIG` and `EndpointType` already live, so the mapping
   from a path segment to a preset key belongs there and stays dependency-free
   (spec §4.1).
2. **`src/server/v2/api.ts`, details handler** — replace the hedge-only
   ternary with `endpointForBotType(botType)` for every type, and write
   `req.fieldSelection` back (spec §4.2). `req.endpointType` is left alone:
   nothing outside `middleware.ts` reads it.
3. **`src/server/v2/api.ts`, hedge list registration (`:1127`)** — use the same
   helper instead of the duplicate ternary. Same values, no behaviour change;
   it exists so the mapping has one home and cannot drift.
4. **`src/server/v2/fieldConfig.ts`** — add `settings.slPerc`, and only that,
   to `GRID_BOT_EXTENDED_FIELDS` (spec §4.3). Measured against the pristine
   presets, it is the one path a grid caller gets today that the grid preset
   did not name, so without this the fix would remove a field. Its sibling
   thresholds are a preset-content gap (spec §4.4), tracked separately.
5. **`src/server/v2/botDetailsFieldPreset.spec.ts`** — the regression guard.
6. **`src/server/v2/openapi-v2.yaml`** — name `settings.slPerc` in the grid
   `extended` preset description, since that preset is also the grid list
   endpoint's. The details endpoint's own docs already promised the fixed
   behaviour ("Supports the same field selection presets as
   `GET /api/v2/bots/grid`", `:6274`) and need no change.

## Contract decisions the spec left open

- **`endpointForBotType` is total.** An unrecognised segment falls back to
  `bots.dca`, i.e. exactly today's behaviour. The details handler rejects
  anything outside `ALL_BOT_TYPES` with a 400 before reaching it, so the
  fallback is unreachable there; it exists so the helper never widens a
  response by accident on a future caller.
- **Where the re-resolution happens.** In the handler, after the bot-type
  guard — not by teaching `fieldSelectionMiddlewares` to take a resolver.
  That middleware factory is used by nine other routes whose endpoint really
  is fixed; changing its signature would touch all of them for one route's
  benefit. The handler already re-resolves for hedge, so this is the idiom
  the file established, not a new one.
- **`meta.fields`.** Writing `req.fieldSelection` back is part of the fix, not
  cosmetic: without it the response would carry the grid definition while
  advertising the DCA preset, and the hedge branch has shipped that mismatch
  since the hedge re-resolution was added.

## JIT extraction tier

**Tier 1** (runbook): the duplicated botType→preset ternary is pulled into one
named, tested module-level function next to the config it indexes. Not Tier 2
— it already is a pure function of its argument, there is no I/O to separate.
Not Tier 0 — the mapping is exactly what the bug is about, so leaving it
inline as a third copy is what caused this.

## Blast radius

1. **Other call sites.** `endpointForBotType` is new — the only callers are
   the two ternaries it replaces. `req.fieldSelection` is read by
   `validateFieldsMiddleware` (no-op here: the route passes no
   `allowedFields`) and by `responseMetadataMiddleware` at `res.send` time,
   which is the intended effect. No other route registers
   `/api/v2/bots/:botType/details`.
2. **`core/` submodule.** Yes — this is `main-app-sh`, shared and deployed
   platform-wide. The parent pointer is bumped at ship time.
3. **Cross-service contract (root Danger List #2).** `/api/v2/*` is the
   public `api.gainium.io` contract consumed by gainium-mcp,
   n8n-nodes-gainium, the chrome extension and the dashboards. The change is a
   **strict widening** of the grid, combo and hedge responses: every field
   returned today is still returned (the dca preset's paths that resolve on a
   grid document — `_id`, `uuid`, `settings.name`, `settings.pair`, `status`,
   `exchange`, `exchangeUUID`, `paperContext`, `profit.*`, `cost`,
   `workingTimeNumber`, `profitToday`, `statusReason`, `created`, `updated` —
   are all named by the grid preset too, verified in the spec test), plus the
   fields that type's own preset names. Nothing is removed and nothing is
   renamed, so no consumer can lose a field it reads today. `fields=full` and
   custom field lists are untouched. DCA responses are byte-identical.
4. **Other tests on this path.** `src/server/v2/gridFieldProjection.spec.ts`
   (specs 061 / 062 — the presets themselves) must stay green; this change
   does not touch the presets.
