# 241 — A paper order cut off by a restart is never retired (plan)

Spec: `specs/241.a-paper-order-cut-off-by-a-restart-is-never-retired.md`.

## Solution

`isDefinitiveOrderNotFound(res, exchange?)` takes an optional exchange. When it
is a paper exchange (`isPaper`) and the reason is exactly `Unknown order`, the
answer is definitive. Everything else is unchanged (§1.3).

The restart/start callers that act on a definitive not-found pass
`this.data?.exchange`:

- `dcaHelper.checkOrders`: the TP/SL loop and the regular/grid loop
  (`noteOrderNotFound`, which retires a `'-1'` order past the spec 177 floor).
- `dcaHelper` / `comboHelper` start: the `retireUnsentOrder` sweeps for `'-1'`
  orders with no saved row.
- `helper.checkOrders` (grid bot): `noteOrderNotFound`.

Deliberately NOT passed:

- `_runUnknownOrderLadder` and the fee-sizing fallback lookup run seconds after
  a placement whose answer may still be in flight. Making paper's answer
  definitive there would write off, or resend, an order paper may be creating.
  Their paper behaviour stays as it is.
- `reconcileRetryDecision` (pure, no bot context). A paper `Unknown order`
  still takes the 3-attempt ladder there before the caller judges it, which
  costs a few paper lookups but changes nothing else.
- `resolveNeverPlacedOrder` is Kraken-only.

JIT extraction tier: 0. The change sits in an already-pure helper.

## Blast Radius

1. Call sites: every `isDefinitiveOrderNotFound(` in `src/bot` (listed above).
   The parent `main-app` repo has none.
2. `core/` (`main-app-sh`): a shared export. The new parameter is optional, so
   existing callers compile and behave as before.
3. No GraphQL, socket, queue or schema shape changes.
4. Tests that must stay green: `orderNotFound.spec.ts`,
   `neverPlacedKrakenOrder.spec.ts`, `restartMidOrder.spec.ts`,
   `restartMidDealStart.spec.ts`, and the full core suite.
