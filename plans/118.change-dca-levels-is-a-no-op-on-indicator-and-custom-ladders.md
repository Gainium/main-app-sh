# 118 — plan

## Solution

1. `types.ts` `DCADealsSettings` + `db/schema.ts` `dcaDealSchema.settings`: add
   the optional deal-only `dcaLevelsCap: number` (same shape of precedent as
   `dcaIndicatorLevels`, which also exists only on the deal).
2. `dcaHelper.dcaLadderSize`: for `indicators` / `custom`, return
   `min(count, dcaLevelsCap)` when a finite, non-negative cap is set.
   Percentage / dynamic keep returning `ordersCount`.
3. `dcaHelper.createInitialDealOrders`: its inline copy of the ladder-size
   branch is replaced by `this.dcaLadderSize(settings)` (reuse; identical for
   every uncapped deal — a NaN `ordersCount` became 0, and the loop ran zero
   times on either).
4. `dcaHelper.createCurrentDealOrders`: the custom branch of
   `dcaOrdersCount` uses `dcaLadderSize` too.
5. `dcaHelper.updateDealSettings`: when the patch is the action's shape (keys
   ⊆ `{ordersCount, useDca}`, `ordersCount` present, `useDca !== false`) and
   the deal's aggregated `dcaCondition` is `indicators` / `custom`, add
   `dcaLevelsCap: ordersCount` to the patch before it is merged.
6. `dcaHelper.resetDealSettings`: pass `dcaLevelsCap: undefined`. The reset
   merges the bot's settings over the deal's, and the bot has no cap, so
   without this a reset deal would keep the action's limit (spec §1.1 reset).

JIT tier 0: guards at the decision points, no extraction.

## Blast radius

1. Callers of `dcaLadderSize`: `executeNextDcaLevel`, `updateUsage` spent
   check, parent `sendSafetyOrderFilledAlert`. All want the capped ladder.
2. Callers of `createInitialDealOrders` (open, fills, edits, add funds,
   indicator signal, execute-next): only a deal carrying `dcaLevelsCap`
   changes. `levels.all` everywhere is derived from its output.
3. Nothing reads the bot's or deal's existing `ordersCount` as a cap, so no
   existing indicator / custom deal changes on deploy (spec §4.2).
4. Mongo: one optional field on `dcadeals.settings`. No migration. Legacy
   main-dash / admin-app readers ignore unknown settings keys.
5. GraphQL / REST / socket: untouched — the action's existing patch shape is
   what triggers it, so no frontend change and no deploy ordering.
6. `core/` submodule (`main-app-sh`): pointer bump in main-app. The parent
   `src/bot/dcaHelper.ts` overrides none of the touched methods.
7. Combo: `comboDealSchema` does not get the field; combo ladders are
   minigrid-managed and untouched.
