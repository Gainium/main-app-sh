# 064 — Plan

Spec: `specs/064.grid-position-unrealized-value-is-scaled-by-the-price-ratio.md`.

## Build order

1. **§4.1 — the expression.** Replace `const val = current.qty * perc * price`
   with `const val = current.qty * diff` at all four sites, and drop the now
   unused `perc` (`noUnusedLocals` is on). `diff` is already the signed price
   delta in the position's favour, so this is the whole correction; no new
   helper is introduced and none is needed — `profitAfterPositionClosed()`
   already books the realized close this way (spec §2.4), and the two now
   agree.
   - `src/bot/helper.ts` `tpSl()` — the TP/SL trigger.
   - `src/bot/gridMonitor.ts` `updateDealStats()` and `addNewBot()`.
   - `src/bot/botMonitor.ts` — the grid `liveStats` writer.
2. **§4.2 — the grid removal path.**
   - `types.ts`: `BotParentRemoveStatsEventDtoDcaCombo` gains a `botType`
     discriminator, a `…Grid` variant carrying the final `PriceMessage` and the
     bot snapshot is added, and `BotParentRemoveStatsEventDto` unions the two.
   - `src/bot/gridMonitor.ts`: `removeBotStats(data, bot)` — measure at the
     stopping price through the existing `updateDealStats`, flush through the
     existing `completeStats`, then drop the entry. It takes the same
     per-bot `@IdMute` key as `addBotStats`, so it queues behind an in-flight
     sample instead of racing it.
   - `src/bot/worker/statsService.ts`: `removeStats` becomes async and routes
     on `botType`.
   - `src/bot/helper.ts` `afterBotStop()`: build the snapshot and call it.
     `afterBotStop()` runs at the TOP of `stop()`, before the close order is
     placed — so the position is still open and the measurement is the
     unrealized loss the bot is stopping on, which is the point.
3. **§4.3 — `DealMonitor.removeDealStats(id, combo)`** flushes through the
   existing `completeStats` before deleting; `dcaHelper.processDealClose`
   awaits it and passes its `combo` flag.
4. **§4.4** — clamp the interval in `GridMonitor.completeStats` the way
   `DealMonitor.completeStats` already does.

## Contract decisions the spec left open

- **Where the final grid measurement comes from.** `afterBotStop()` has no
  `PriceMessage`; it reads `getLastStreamData(pair)` — the price the engine
  last saw, which is the price the TP/SL decision was made on. The *time* is
  `Date.now()`, not the stream time, because it is the end of the tracked
  interval; §4.4 clamps the case where the stream is ahead of the local clock.
- **Snapshot duplication.** The grid stats snapshot literal exists twice — in
  `core` `priceUpdateCallback` and again in main-app's override of it. The
  flush needs a third. Instead of a third copy, the literal is extracted once
  as `protected gridStatsSnapshot()` on the core mixin and the two existing
  call sites are pointed at it (JIT tier 1: a named, single-purpose method, on
  the path being touched, no new abstraction).
- **The removal takes the same `@IdMute` key as the sample.** Wanted: a sample
  must not interleave between the final measurement and the flush. `IdMutex`'s
  `limit` argument makes the wait queue a `getFixedArray`, which EVICTS a
  waiter (whose promise then never settles) once the queue is full — so an
  awaited call under that mutex is only safe where the queue cannot reach the
  limit. Here the callers of `<botId>stats` are one sample per 60 s per bot
  plus at most two stops, so 10 outstanding calls on one bot is not reachable
  without a multi-minute DB stall. `DealStats.removeStats` also swallows and
  logs, so a *failed* flush can never break `stop()`.
- **…but the wait on it is bounded anyway (§4.2).** A swallowed rejection does
  not help against a promise that never settles, which is exactly what queue
  eviction produces, and `afterBotStop()` is awaited at the top of `stop()`
  before the closing order. `flushBotStats` therefore races the flush against
  `FLUSH_STATS_TIMEOUT_MS` (5 s) and warns instead of waiting. 5 s is far above
  any healthy `completeStats` write and far below anything a user would notice
  in a close. Written as a local `Promise.race` with a cleared timer, matching
  the idiom already in `core/src/utils/leverageBracketCache.ts` and
  `core/src/utils/user.ts` — there is no exported timeout helper in this repo
  to reuse, only local ones.
- **No new utility.** Checked `core/src/utils`, `core/src/bot` and the
  dashboard core for an existing unrealized-PnL helper; there is none, and the
  fix does not need one — it removes a factor from an expression that already
  computes what it needs.

## Blast radius

1. **Other call sites of the expression.** Grepped `* perc *` across
   `core/src`, `src` and the dashboard: six, of which four are in this repo and
   all four are changed. The remaining two are the dashboard's client-side
   recompute of the same numbers (`main-dash-sh core/src/types/gridBot.ts`) —
   a different repository, tracked separately (spec §4.5). Until it ships, an
   OPEN futures grid bot's Drawdown/PnL is recomputed client-side with the old
   factor; for a CLOSED bot — the reported case — the dashboard returns
   `bot.stats` untouched, so the stored value this fix repairs is what is
   shown.
2. **`core/` submodule.** All of this is in `core/` (`main-app-sh`), shared and
   public. It is bot-engine code: `gridMonitor`, `dealMonitor`, `botMonitor`
   and the grid mixin are consumed only by main-app's bot workers. No other
   service imports them.
3. **Cross-service contracts** (main-app `CLAUDE.md`): none touched. The
   `BotParent*StatsEventDto` types are in-process only — nothing posts them
   over a worker port or a queue; the only producers and consumers are the bot
   helpers and `DealStats`, in the same process. No GraphQL, REST, socket.io,
   RabbitMQ or Mongo *schema* change: `stats.drawdownPercent` /
   `runUpPercent` / `timeIn*` keep their shape and meaning, and only get the
   values they were supposed to have.
   The one behavioural contract that DOES change: a `valueChanged` TP/SL now
   triggers where the setting says, which for an open long means **earlier**
   than the unfixed build and for an open short **later**. That is the defect
   being fixed, and it moves both in the direction of the user's setting.
4. **Tests that must stay green.** `gridCloseProfitLedger.spec.ts` (spec 045)
   covers `profitAfterPositionClosed` on the same mixin; `tpBurstInvariant`,
   `limitOnlyEntry` and the rest of the `core` suite must be unaffected. Full
   `npm test` in `core/` is the gate.
