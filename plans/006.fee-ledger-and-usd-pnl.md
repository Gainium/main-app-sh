# 006 — Plan: per-asset fee ledger and USD-only third-asset PnL

Spec: `specs/006.fee-ledger-and-usd-pnl.md`.

## Solution

### New pure module: `src/bot/feeLedger.ts`

Two functions, next to `orderFee.ts` (same directory, same "no DB/queue/
exchange client" purity bar as `orderFee.ts`/`tpFees.ts`/
`positionReconcile.ts`):

```ts
export type FeeLedgerEntry = { asset: string; total: number; totalUsd: number }

// Every fee leg this order reports, on-pair or not, each as its own
// {asset, amount} — the raw legs observedFeeSplit either books (on-pair,
// summed) or discards whole (any off-pair leg present). Conceptually more
// primitive than observedFeeSplit: observedFeeSplit sums these when every
// leg is on-pair, else returns null.
export function observedFeeLegs(
  order: Partial<Order>,
  baseAsset?: string,
  quoteAsset?: string,
): { asset: string; amount: number }[]

// Merge one {asset, amount, usdRate} contribution into a running per-asset
// ledger — the profitByAssets find/filter/push shape (dcaHelper.ts:2356-2384),
// generalized into a pure, independently-testable function.
export function accrueFeeLedger(
  ledger: FeeLedgerEntry[] | undefined,
  asset: string,
  amount: number,
  usdRate: number,
): FeeLedgerEntry[]
```

**Deliberately not in this module:** resolving `comBase`/`comQuote` — that
stays exactly where it is (`observedFeeSplit` + `observedFeeOnSide` in
`orderFee.ts`, called directly by `createTransaction`/`closeDeal`). This
module adds the ledger dimension only; it does not touch or duplicate the
existing base/quote booking logic. USD conversion (multiplying an amount
by a rate) is also not in this module — `usdRate` is a plain number the
caller already looked up (§2.3 of the spec: looked up once, at the point
the caller processes the fee), keeping this module free of any async I/O,
same as its neighbors.

### Call-site integration (per spec §2.2/§2.4/§3, gated on the new flags)

- **`dcaHelper.ts:closeDeal`** (`:2266-2389`): where the loop already calls
  `observedFeeSplit` per order (`:2266-2270`), also call `observedFeeLegs`.
  When `DCADealFlags.feeByAsset` is on the deal: for every leg, look up
  `usdRate` (§1.4 of the spec — `getUsdRate` for base/quote-side legs,
  `findUSDRate` for anything else) and `accrueFeeLedger` it into
  `findDeal.deal.feeByAsset`; when a leg is off-pair (i.e. this order's
  `observedFeeSplit` returned `null` but `observedFeeLegs` is non-empty),
  skip the existing estimate fallback (`:2276-2284`) for that order's fee
  entirely — contribute `0` to `feeBaseFull`/`feeQuoteFull` instead.
  On-pair legs are unaffected: `feeBaseFull`/`feeQuoteFull`/`commission`
  keep computing exactly as they do today.
- **`comboHelper.ts:createTransaction`** (`:918-932`) and
  **`helper.ts:createTransaction`** (`:3220-3222`, grid — §2.4 also adds
  the `observedFeeSplit`/`observedFeeOnSide` call here for the first time):
  same shape, per fill rather than once at close, gated on
  `BotFlags.feeByAsset`/`DCADealFlags.feeByAsset` respectively. `profit.totalUsd`
  gets the off-pair contribution's `totalUsd` subtracted at the same point
  `profit.total`/`profit.totalUsd` are otherwise updated for that
  transaction; `profit.total` (native-currency) does not.
- **`comboMinigrid` vs. `deal` (spec §4 Q2 — resolved: mirrored).**
  `feeByAsset` is written to both, the same way `feePaid`/`fullFee`
  already are (`comboHelper.ts:2490-2509`, via `updateMinigridFee`) — one
  extra field alongside the two it already keeps in sync, not a new
  mirroring mechanism.
- **Ledger contents (spec §4 Q3 — resolved: raw split, not the
  `observedFeeOnSide`-converted amount).** `feeByAsset` records what
  `observedFeeLegs` reports per asset — both legs, if a venue's breakdown
  named two — independent of which single side `comBase`/`comQuote`
  ultimately booked to. The ledger's job is "what did we actually pay,
  per asset," not "what did PnL subtract."
- **`usdRate` preference order (spec §2.3).** At each call site, before
  falling back to `getUsdRate`/`findUSDRate`: if the order carries
  `feePaidUsd` (venue-supplied — Kraken today, per `websocket-connector-sh`
  spec `003`), use `+order.feePaidUsd` directly for that order's
  contribution instead of computing a rate. This is a one-line branch at
  each call site, not a new function in `feeLedger.ts` — it's "which
  number to hand `accrueFeeLedger` as the pre-multiplied USD amount," not
  a decision `feeLedger.ts` needs to make itself.
- **Grid's own `feePaid` (spec §2.5).** `helper.ts:createTransaction`
  writes `comBase`/`comQuote` into a running `this.data.feePaid.{base,quote}`
  on every transaction — new field, new write, same shape as
  `dcaDealSchema`/`comboDealSchema`'s `feePaid`, same
  update-every-transaction cadence `comboHelper.ts:2490-2509`
  (`updateMinigridFee`) already uses for `minigrid.feePaid`. Gated on
  `BotFlags.feeByAsset` (§3) same as everything else in this plan — no
  separate flag for this one field.

### New flags/fields

- `types.ts:1226-1231` `DCADealFlags` gains `feeByAsset`. Set at deal
  creation next to `newMultiTp` (`dcaHelper.ts:1744`).
- `types.ts:2319-2325` `BotFlags` gains `feeByAsset`. Set at grid bot
  creation next to where `kucoinNewFee` is (`src/bot/index.ts:3856`).
- `types.ts:2021-2056` `BotSchema` gains `flags?: string[]` (new — grid has
  none today), `feeByAsset?: FeeLedgerEntry[]`, and `feePaid?: {base:
  number; quote: number}` (§2.5 — new, grid has no equivalent today).
- **Mongoose, not just the TS interface** — the actual persistence layer.
  `src/db/schema.ts` `botSchema` (`:609-688`, grid's mongoose document —
  confirmed to spread `...botCommon` at `:610` and have no `flags` key of
  its own, unlike `dcaBotSchema`/`comboBotSchema` which each declare their
  own at `:1899`/`:1844`) gains, inside that same literal: `flags:
  [String]`, `feeByAsset: [{asset: String, total: Number, totalUsd:
  Number}]`, `feePaid: {base: Number, quote: Number}`. A TS interface
  change with no matching mongoose field persists nothing — this is the
  piece that actually makes the data durable.
- `dcaDealSchema`/`comboDealSchema`/`comboMinigrid`
  (`src/db/schema.ts:1967,2148,2782`) gain `feeByAsset: [{asset: String,
  total: Number, totalUsd: Number}]`, mirroring the existing
  `profitByAssets` sub-schema (`src/db/schema.ts:419-425` — the literal
  array-of-subdoc definition; confirmed exact line range) verbatim — or,
  simpler and equally valid since it's the identical shape, reference the
  same `profitByAssets` schema constant directly rather than duplicating
  the three-field literal a fourth time.
- **GraphQL** (`src/graphql/schema.ts`) — new `FeeByAsset` type mirroring
  `ProfitByAssets` (`:4401-4405`); `feeByAsset: [FeeByAsset]` added to
  `dcaDeal`/`comboDeal` (`:4249,4266`) and `minigrids` (`:3665-3690`);
  `fullBot` (`:2848-2895`, currently has none of these) gains `flags:
  [String]`, `feePaid: FeePaid` (existing type, `:3662-3665`),
  `feeByAsset: [FeeByAsset]`. No resolver code — confirmed passthrough via
  the default resolver, same as `profitByAssets` today.
- **REST `/api/v2/*`** — `src/server/v2/fieldConfig.ts`: `feeByAsset`
  added to `DCA_DEAL_EXTENDED_FIELDS`/`COMBO_DEAL_EXTENDED_FIELDS`
  (`:217-230`); `GRID_BOT_EXTENDED_FIELDS` (`:164-178`, currently has none
  of `flags`/`feePaid`/`feeByAsset`) gains all three. Mirror into
  `src/server/v2/openapi-v2.yaml`'s `DCADealExtended`
  (`:2268`)/`ComboDealExtended`/`GridBotExtended` (`:2715-2762`) — and
  correct `DCADealExtended.feePaid`'s existing `type: number` (`:2302-2305`,
  pre-existing inaccuracy against the real `{base, quote}` shape) to an

  (`src/server/v2/fieldUtils.ts:103`) builds straight off the

## Contract decisions the spec left open

- **§4 Q1 (capture-time precision):** accepted as "close enough" —
  whatever price `getUsdRate`/`findUSDRate` returns when the caller runs,
  same precision bar `fundingProcessor.ts` already accepts for the
  structurally identical problem. No new price-fetch mechanism.
- **§4 Q2 (mirrored vs. single source):** mirrored — see above.
- **§4 Q3 (raw split vs. on-side-converted):** raw split — see above.

## JIT extraction tier

**Tier 2** for `feeLedger.ts` — pure, no I/O, sits next to `orderFee.ts`'s
existing Tier-2 functions, same reasoning: the decision ("what per-asset
legs did this order's fee touch," "fold one contribution into a running
per-asset total") has no I/O in it once the amounts and rate are handed
in.

**Tier 0 at the call sites** for this pass: `closeDeal`/`createTransaction`
(both `comboHelper.ts` and `helper.ts`) stay exactly as legacy as they are
today — the new logic is a few more lines calling into `feeLedger.ts`
(and, for grid, the already-proven `orderFee.ts` calls combo has used
since `eb18ef6`), not a rewrite. Not Tier 1: nothing new and
infra-coupled is being pulled out of these functions; the smell being
added (a few more lines in an already-large function) is not materially
worse than what's already there, and a bigger extraction here is exactly
the "drive-by rewrite on a live trading engine" this skill warns against.

## Blast radius

1. **Other call sites.**
   - `observedFeeSplit`/`hasObservedFee`/`observedFeeOnSide` (existing,
     unmodified) are called from `dcaHelper.ts:2156-2160,2266-2270`,
     `comboHelper.ts:918-926`, `main.ts:5082,5109` — none of those call
     sites change; `helper.ts` (grid) gains new calls to the same
     functions but that's new usage, not a changed contract.
   - `deal.feePaid`/`deal.commission`/`this.data.profit.total` are read
     by `dealMonitor.ts:228-254`, `botMonitor.ts:424-448` (live PnL
     preview for open deals) and the socket.io `bot deal update`/
     `bot transaction update` events (unchanged names, per
     `app/CLAUDE.md` §Cross-service-contracts) that both dashboards
     consume — `feeByAsset` is a pure addition to the payload these
     already carry; no existing field there changes shape. Dashboard
     consumption is explicitly out of scope for this initiative (per
     the top-level request) but this is the point at which the new field
     starts silently reaching them — noted, not acted on.
2. **`core/` submodule.** This is `main-app-sh`; the whole repo is the
   `core/` submodule content (`app/CLAUDE.md` §Cross-service contracts).
   Every schema/type change here is platform-wide once the pointer in
   `app` is bumped.
3. **Cross-service contracts.** GraphQL (`src/graphql/schema.ts`) and REST
   `/api/v2/*` (`fieldConfig.ts`/`openapi-v2.yaml`/`definitions/types.ts`)
   are updated in this same pass (see "New flags/fields" above) —
   revised from the original plan's "flag for a follow-up," since a field
   that exists on the schema and stays unexposed on these surfaces is
   exactly the kind of thing that gets forgotten and has to be
   rediscovered later. Both are additive (new optional fields, new type),
   confirmed via `app/CLAUDE.md` §Cross-service-contracts as this repo's
   own owned contracts — no consumer (either dashboard, `gainium-mcp`,
   `n8n-nodes-gainium`, the OAuth-scoped public API) reads a field that
   doesn't exist yet, so nothing existing breaks. Dashboard *display* of
   the new fields is still out of scope (per the top-level request) —
   only the fields being queryable is in scope here.
4. **Restarting bot workers.** All consuming code
   (`dcaHelper`/`comboHelper`/`helper`/`main.ts`) is worker-path — inert
   until bot workers restart, same staged-rollout shape as the Aug 2026
   fix and `websocket-connector-sh` spec `003`. Depends on spec `003`
   being deployed first for any non-Binance venue's off-pair fee to ever
   be observed in the first place; Binance's off-pair (BNB) case already
   works today via the existing WS path.
