# 035 — Plan

Spec: `specs/035.deal-close-price-is-laundered-from-zero-into-a-giveaway.md`
(issue #731).

## §1 Build order

All three changes are in `core/src/bot/dcaHelper.ts`, inside `getTPOrder`.
They are independent, and deliberately ordered cheapest-blast-radius first.

1. **§4.1 — refuse a zero/non-finite close price, before the nudge.** Insert
   the guard immediately after `tpPrice` is computed and *above* the
   `tpPrice === avgPrice` nudge. This is the root cause: spec `023` already
   wrote the correct predicate (`!Number.isFinite(tpPrice) || tpPrice <= 0`),
   it just sits ~100 lines below the code that destroys the evidence. The fix
   is to run that same predicate where it can still see `0`.
   Re-assert it once more after the second `math.round(tpPrice,
   ed.priceAssetPrecision)`, which can itself round a small price to 0 on a
   coarser precision.
2. **§4.3 — the notional-floor clamp moves quantity, never price.** Collapse
   the long/short fork so both sides compute `ceil(quoteAsset.minAmount /
   tpOrder.price)`. Refuse when that quantity is non-finite or `<= 0` (the
   spec `025` §4.4 mirror), and refuse for a long when it exceeds the position
   — a long close SELLs, so it cannot be raised past what the deal holds.
3. **§4.4 — a one-sided market-relative bound** on the finished
   `tpOrder.price`, using `_price` (the market price every call site already
   passes) and a new module constant `MAX_CLOSE_PRICE_DEVIATION = 10`.

## §2 Contract decisions the spec left open

- **Which market reference?** `_price`, `getTPOrder`'s second parameter, not a
  fresh `getLatestPrice` call. Verified at all seven call sites: each passes
  `deal.lastPrice`, `price`, or a `getLatestPrice` result. Using the value
  already in hand adds no I/O and no new failure mode, and when it is `0` —
  precisely the outage that causes this bug — the bound is skipped rather than
  guessing, because §4.1 has already refused by then.
- **How far is "orders of magnitude"?** `10`. A stop loss is a few percent from
  entry; even a total-loss exit is nowhere near 10x. The production row was off
  by 128x.
- **One-sided or symmetric?** One-sided. A close priced away from the market in
  the *harmless* direction merely rests unfilled, and asking for that is
  legitimate (a fixed TP far above market). Only the value-losing direction is
  refused: a SELL far below market, a BUY far above it. A symmetric bound would
  break `useFixedTPPrices` users for no safety gain.
- **Refuse or clamp on §4.3's long branch?** Refuse. The spec's §1.1.2 says
  price carries intent and quantity is the free variable — but for a long the
  free variable is bounded by the position, and the `Math.min(tpOrder.qty,
  qtyNew)` immediately above already treats "a long may not exceed its
  position" as an invariant. Raising quantity there would break that invariant
  to satisfy a floor. So: say the position cannot be closed at this size on
  this venue, rather than invent a price.

## §3 JIT legacy tier

**Tier 0** — no extraction. The causal path is three guards inside an existing
21k-line method; every one of them is a refusal that reads values already in
scope. Extracting a `closePriceIsSane()` module would mean threading
`isLong`/`_price`/precision through a new seam for three comparisons, which is
more surface than it removes. The existing sibling refusals (spec `023` at
`:14618`, spec `025` at the `big.js` catch) are inline in this same method for
the same reason — matching them keeps the four readable together. Reassess if a
fourth lands.

## §4 Blast radius

1. **Other call sites.** Seven `getTPOrder` callers in `dcaHelper.ts`. All
   already handle an empty return: spec `023` §4.2 exists specifically to pin
   that `[]` (not `undefined`) comes back so callers' `?.length` guards fire.
   This change adds three more `return []` paths to a contract that already has
   two.
2. **`core/` submodule.** Yes — `dcaHelper.ts` is shared code, deployed
   platform-wide, and prices **every** DCA/combo take-profit and stop-loss.
   Widest blast radius in the platform. This is why every change here is a pure
   refusal or a widening: it can only turn an order that is already wrong into
   no order. §4.5 is the test that enforces it.
3. **Cross-service contracts.** None touched. No GraphQL shape, no socket event
   name, no queue payload, no shared collection field. `Grid` is unchanged.
4. **Other tests on this path.** `tpNanRefusal.harness.spec.ts` (023),
   `nanLadderRefusal.harness.spec.ts` (025), `tpSizingFromPosition.harness.spec.ts`
   (017), `tpSizingAfterPartialTp.harness.spec.ts`, `tpCoverageReconcile`,
   `multiTpCompletion`, `partialTp`, `tpFees`, `placeOrders` TP-guard. All must
   stay green.

**Known behaviour change, deliberate.** A *long spot* deal whose entire close
notional sits under the venue's minimum previously got an order resting at an
invented price that could never fill; it now gets no order and a logged (not
user-facing) refusal. Neither closes the deal. The refusal is the honest
outcome, and the previous behaviour was itself a silent defect — the user saw a
take-profit that was never going to execute. This is the amber part of the
change; §4.1 alone would fix #731.
