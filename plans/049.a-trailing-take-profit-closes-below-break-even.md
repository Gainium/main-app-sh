# 049 — Plan: a trailing take profit closes below break even

Spec: `specs/049.a-trailing-take-profit-closes-below-break-even.md`

## 1. Solution

Fix the root cause named in spec §3 at the single decision point, plus the
corollary at the rejection site.

### 1.1 The break-even floor (spec §5.1–§5.4) — `checkDealsStopLoss`

In the trailing arm of `checkDealsStopLoss`, after the arm has been identified
and before `triggerStopLoss` runs, refuse the close when the deal is at or
below break even, and disarm instead.

Placement is forced: the floor must be tested against `last`, the live tick.
`getDealStopLossPrice` returns a *level*, and for a long the close fires on
`last <= level`, so clamping the level there would make the close fire *more*
eagerly, not less. `checkDealsStopLoss` is the only place holding both the
armed level and the live price.

Scoped with `d.deal.trailingMode === TrailingModeEnum.ttp` — the deal's own
record of *which* trail armed. That keeps a trailing stop loss (`tsl`) and the
plain stop-loss branches untouched (spec §5.3), and is stricter than gating on
settings alone, since a bot may enable both trails.

Break even reuses the engine's existing fee idiom rather than a new helper —
the same shape as `checkMinTp`:

```ts
const diff = this.isLong ? last - avg : avg - last
const net  = diff / avg - (fee?.taker ?? 0.001) * 2
```

`avg` uses `dealRefPrice(settings.avgPrice, d.deal.avgPrice)`, the existing
helper for choosing the usable average, so a safety-order fill that moved the
average is picked up automatically (spec §2.4 / brief item 3).

### 1.2 Disarm on terminal rejection (spec §5.5) — `closeDealById`

In the `else` branch that calls `handleOrderErrors` with the CANCELED MARKET
row, disarm the trailing state.

This is the *terminal* branch: the `isNotionalReason` slippage retry and the
`isPositionAlreadyClosedReason` branch both return before it, so the immediate
in-profit retry path is unaffected. Where the trail is still legitimately in
profit, `checkTrailing` re-arms from the current price on the next tick, so
the exit is re-armed rather than lost.

### 1.3 Shared disarm

Both sites need the same three-field reset plus a persist. There is no
existing helper (the only other disarm, in the settings-change path, is
inline and does not reset `bestPrice`), so add one small private method,
`disarmTrailing(d, reason)`. `bestPrice = 0` is required, not cosmetic: left
at the old high, `checkTrailing` would not recompute the level until price
exceeded that high again (spec §2.4 shows the recompute is gated on
`old.price !== d.deal.bestPrice`).

## 4. Blast Radius

1. **Other call sites.** `checkDealsStopLoss` is called from the price-update
   path and from `checkAllowedMethods`; it is the only consumer of
   `dealsForStopLoss`. The new guard is inside its trailing arm only. The
   plain-SL and dynamic-AR branches are untouched, as are `getDealStopLossPrice`,
   `setDealForStopLoss` and `triggerStopLoss`.
2. **`core/` submodule.** Yes — `src/bot/dcaHelper.ts` is in `main-app-sh`,
   shared with every consuming service and the self-hosted platform. Widest
   blast radius in the repo (root CLAUDE.md Danger List §11). The change is
   behavioural inside one method, and adds **no exported type, no schema
   field, no new persisted field** — `trailingMode`, `trailingLevel` and
   `bestPrice` already exist and are already written by `triggerTrailing`.
3. **Documented contracts.** None touched. No GraphQL schema change, no
   socket event, no queue payload, no `BaseReturn` shape. `closeTrigger`
   labelling from `259b486` is preserved exactly — the floor refuses *before*
   `triggerStopLoss`, so no close changes its recorded trigger.
4. **Other tests on this path.** `src/bot/dca/trailingTpCloseTrigger.harness.spec.ts`
   (spec 042) drives the same method and must stay green. It needs a
   `getUserFee` stub added: the method now consults the user's fee, and that
   method is defined on the real bot base class, not on the harness's
   `FakeBase`. Its assertions are unchanged.

## 5. Risk

The change can only ever **prevent** a close that would have booked a loss on
a take-profit trail. It cannot cause a close that would not otherwise have
happened. The reachable downside is a deal staying open where it previously
closed at a loss — which is the intended behaviour per spec §1.1, and the deal
remains subject to every other close path (stop loss if enabled, manual close,
the trail re-arming above the take-profit price).

## 6. Not addressed

Spec §6.1 (`closeBySl` in-memory, so a rejected close is not retried until a
restart) and §6.2 (no user-visible message on a rejected close). Both are
separate concerns with wider retry/notification implications.
