# Plan 057 — A base entry cut short is never topped back up

Spec: `specs/057.a-base-entry-cut-short-is-never-topped-back-up.md`.

## Build order

1. **`src/bot/dca/partialBaseEntry.ts`** — add `shouldTopUpSettledBaseEntry`,
   the §4.1/§4.2 decision, next to the settle decision it follows. Pure; no new
   module, because it reads the same row and the same spec pair.
2. **`src/bot/remainderFill.ts`** (new) — `isVenueCanceledRemainderFill`, the
   §4.5 venue shape. New file rather than an addition to
   `reduceOnlyRemainder.ts`, whose name scopes it to reduce-only closes; it
   imports that file's `RemainderOrder` type rather than restating it.
3. **`src/bot/main.ts`**
   - `fillPartiallyFilledOrder(order, settledBaseEntry = false)` — the
     `coinbase` return becomes conditional on the caller not opting out (§4.4).
     Default `false`, so every existing caller is byte-for-byte unchanged.
   - `buyRemainder`'s success gate uses `isVenueCanceledRemainderFill` (§4.5).
4. **`src/bot/dcaHelper.ts`** — `settlePartialBaseEntry` offers the settled row
   to the remainder machinery before booking it, and reports cut-short only if
   it is still short (§4.3/§4.6).

## Contract decisions the spec left open

- **Where the freshness clock comes from.** `Date.now()` read in
  `settlePartialBaseEntry`, window from the bot's own
  `orderLimitRepositionTimeout + enterMarketTimeout` instance fields. Both are
  already set from `settings.limitTimeout` in `setClassProperties`, so a bot
  that widened its entry window widens this with it and no constant is
  invented. `now` and the window are arguments to the pure predicate so the
  test does not depend on wall-clock.
- **The opt-out is a parameter, not a new method.** `fillPartiallyFilledOrder`
  owns `allowToProcessBr`, the per-order `IdMute` and the
  `partiallyFilledFilledSet` de-duplication; a second entry point into
  `buyRemainder` would have to restate all three.
- **Order of operations.** Top up, then `handleUnknownOrder`. Booking first
  would open the deal twice or force a re-size; `buyRemainder` already merges
  into the same row at the blended average, which is exactly what `startDeal`
  reads.

## Blast Radius

1. **Other call sites.**
   - `fillPartiallyFilledOrder`: two existing callers (`main.ts` order-queue
     consumer, `main.ts` synchronous placement response). Both keep the default
     `settledBaseEntry = false`, so both are unchanged, `coinbase` guard
     included.
   - `buyRemainder`: one caller (`fillPartiallyFilledOrder`) plus its own
     recursion. Only the success gate changes, and only by adding a venue whose
     orders could not reach the function at all before this change.
   - `settlePartialBaseEntry`: three callers (`checkBaseOrder` `id` branch,
     `checkBaseOrder` `dealId` branch, `processCanceledOrder`). All three keep
     their existing behaviour; the top-up is decided inside, on age.
2. **`core/` submodule.** Yes — every file here is in `main-app-sh`, shared by
   cloud and self-hosted. The parent's pointer is bumped at ship time.
3. **Cross-service contracts.** None touched: no GraphQL shape, no socket event
   name, no queue payload, no Mongo field. The rows written are the same
   `orders` rows, with quantities the engine already writes.
   The change DOES place real orders on real venues — Danger List by effect
   rather than by contract, and the reason this is not a green-tier fix.
4. **Other tests that must stay green.**
   - `src/bot/dca/venueCanceledBaseEntry.harness.spec.ts` (specs 038/048) —
     drives the same settle; its fixture rows are dated 2026-09-10, far outside
     any entry window, so §4.2 declines the top-up and its assertions hold.
   - `src/bot/reduceOnlyRemainder.spec.ts` — `buyRemainder`'s reduce-only gate,
     untouched.
   - `src/bot/resizeCancelPromotion.spec.ts`, `src/bot/fillEvidence.spec.ts` —
     `cancelOrderOnExchange` promotion, untouched.
   - The full `npm test` suite in `core`, plus `tsc` in `core` AND in the
     parent (the parent keeps a coupled copy of the build).

## JIT legacy tier

**Tier 1** on the touched path: the two new decisions come out of the method
bodies into named, tested modules (`shouldTopUpSettledBaseEntry`,
`isVenueCanceledRemainderFill`), matching the shape this repo already uses for
`shouldSettlePartialBaseEntry` and `canRecoverReduceOnlyRemainder`. Not Tier 2+:
`settlePartialBaseEntry` and `buyRemainder` stay where they are and keep their
I/O — extracting the order-placement chain is a modernization task, not
something to spring on a money path in a bug fix.
