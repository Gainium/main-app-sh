# Plan 090 — A stale `NEW` acknowledgement rewinds a part-filled order

Spec: `specs/090.a-stale-acknowledgement-rewinds-a-part-filled-order.md`.

## Build order

1. `src/bot/staleExecutionReport.ts` — the pure predicate
   `executionReportRewindsOrder(held, report)`. New file, no imports beyond
   its own types. JIT tier: **Tier 2** (fully pure). The decision is a
   comparison of two plain shapes and needs nothing from the bot, so nothing
   lower is justified; Tier 3 (a port) would be inventing an interface for a
   two-field comparison.
2. `src/bot/staleExecutionReport.spec.ts` — the decision, against the
   production timestamps.
3. `src/bot/staleAcknowledgement.harness.spec.ts` — the real
   `convertExecutionReportToOrder` replaying the production report sequence.
   This is the test that fails for the reason §3 names: without the call site
   the row reads `NEW` and `shouldSettlePartialBaseEntry` answers `false`.
4. `src/bot/main.ts` — capture `held` before the merge, ask the predicate after
   it, return `null` on a rewind. Import added next to `fillEvidence`, which is
   the same kind of rule.
5. `CHANGELOG.md` + `package.json` patch bump.

No other service is touched, and no build order across services applies.

## Contract decisions the spec left open

- **Where the `held` snapshot is taken.** §4.2 requires the comparison to be
  post-conversion; it does not say how to keep the pre-merge values, since
  `order` is mutated in place from line 5695 on. Decided: a two-field snapshot
  (`status`, `updateTime`) taken immediately after `find` resolves, the same
  shape and for the same reason as `settlePartialBaseEntry`'s `observed`
  (spec `059`).
- **What a rewind returns.** Decided: `null`, the converter's existing "nothing
  to process" answer, already used twice in the same method
  (`main.ts:5663`, `:5683`). `processOrderQueue` handles it by moving on.
- **Log level.** §4.4 fixes this at `handleLog`; the plan adds no choice.
- **Whether `process` gates it.** Decided: yes, mirroring the already-filled
  guard directly above. The un-gated caller (`getOrder`'s Redis-cache branch)
  converts a stored report in isolation to answer a lookup, and has no row it
  could rewind.

## Blast Radius

1. **Other call sites.** `executionReportRewindsOrder` is new — one caller.
   `convertExecutionReportToOrder` has two callers: `processOrderQueue`
   (`process: true`, the one being changed) and `getOrder`'s Redis-cache branch
   (`process` undefined, unaffected by construction).
2. **`core/` submodule.** Yes — both files are under `core/`, i.e.
   `main-app-sh`, shared and deployed platform-wide. Every bot type running on
   top of `MainBot` (DCA, combo, grid, hedge) gets the guard. That is intended:
   the rewind is a property of the stream consumer, not of any bot type.
   The parent's submodule pointer is bumped at ship time.
3. **Contracts this repo's `CLAUDE.md` documents as owned/emitted.** None. No
   GraphQL/REST shape, no socket.io event name, no queue name or payload, no
   Mongo schema field. `Order` is unchanged — the guard reads two of its
   existing fields and adds none.
4. **What a dropped report no longer reaches**, which is the real radius:
   - `updateOrderOnDb` — the write that put `NEW`/`0` over a fill. Intended.
   - `emit('bot update')` — a dashboard row that would have flickered back to
     unfilled no longer does.
   - `setOrder` — the map keeps the newer row.
   - `onNew`: DCA's `processNewOrder` is a no-op; combo's override cancels the
     order when its minigrid has already closed, which for a row that has since
     filled or ended is a request the venue would refuse. Spec §4.3.
   - `fillPartiallyFilledOrder` — reached only with a `NEW` report carrying no
     fill, so nothing it owns (the remainder machinery, spec `088`'s post-mutex
     re-read) can be engaged by the shape being dropped.
5. **Other tests on this path that must stay green.** The whole `core` suite —
   `convertExecutionReportToOrder` is under every stream-driven harness. The
   ones that exercise it or the rows it writes:
   `settleCancelNoFillReport.harness.spec.ts`,
   `settledBaseEntryCancelReplay.harness.spec.ts`,
   `venueCanceledBaseEntry.harness.spec.ts`,
   `partialBaseEntry.harness.spec.ts`, `baseEntryTopUp.harness.spec.ts`,
   `remainderDoubleCount.spec.ts`, `resizeCancelPromotion.spec.ts`,
   `orderFee.spec.ts`, `fillEvidence.spec.ts`.

## Gate 4 — plan against spec

Walked. Every numbered section has a row above. The one plan decision the spec
did not leave open is the log level (§4.4 fixes it) and the plan does not
re-decide it. The Solution fixes the cause §3 names — the converter's lack of
report ordering — rather than the symptom, which would have been teaching
`shouldSettlePartialBaseEntry` to accept a `NEW` row carrying a stale zero.
That reading was rejected: it would make every other consumer of the map
(`getAvgPrice`, the `levels.complete` fold, `findBaseOrderByDeal`) go on
reading a rewound row.
