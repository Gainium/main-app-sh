# 008 — Plan

Spec: [`../specs/008.per-cycle-warn-on-a-standing-condition.md`](../specs/008.per-cycle-warn-on-a-standing-condition.md)

## Solution

A small pure latch, `core/src/bot/conditionLatch.ts`, that answers one question:
*is this the first time this condition has held since it last cleared?*

```
shouldReport(key, now) → true on the first call, false while the key stays set,
                         true again after `reArmAfterMs` of continuous holding
clear(key)             → the condition ended; the next occurrence reports again
```

`MainBot` owns one instance per bot (`standingConditionLatch`). The two refusal
call sites gate **only** their `handleErrors` call on it, and the matching
success branch calls `clear()`.

### Why a latch at the call site, not a gate inside `handleErrors`

Spec §3. `handleErrors` sees a string and a method name; it cannot distinguish
"the same standing condition, evaluated again" from "this failed again, which is
news". The call site can: it has the symbol, and it has the success branch that
defines when the condition ended. A gate inside `handleErrors` would also have
to be keyed on message text, which §1.2.4 rules out.

### Why `reArmAfterMs` and not a pure transition latch

Spec §1.1.3. `Cannot start deal` is configured `logMode: coalesce`,
`logWindowSec: 86400` — the platform's own answer to "how often should the user
hear about this again" is daily. A pure transition latch would silently downgrade
that to one notification for the lifetime of the condition, which is a
user-facing regression smuggled in with a log fix. `reArmAfterMs` defaults to
24 h at the two call sites, so the volume falls from ~1,165/bot/day to ~1 while
the reminder cadence the user already gets is unchanged.

### Why in-memory, not Redis

Unlike `RetryBackoff` (which must be shared across workers because it gates
whether an *order* is sent to a venue), this gates only whether a *report* is
written. A bot lives in exactly one worker at a time, so an in-process map is
already per-(bot, symbol). Worker restart re-arms the latch and re-reports once
— which is correct, not a leak: a restarted worker has no record that the user
was told. Prod restarts these workers a handful of times a day, so the residual
volume is bounded at (bots × restarts), not (bots × cycles).

## Contract decisions the spec left open

- **Latch key shape** — `` `${reason}|${symbol}` ``. `reason` is a stable
  internal constant, never the formatted message (spec §1.2.4). The bot
  dimension is implicit: the latch is per bot instance.
- **Terminal DCA is exempt** (spec §4.1). `settings.type === terminal` bypasses
  the latch entirely, so the branch that calls `this.stop()` always reports.
  This also matches `processError`'s existing reasoning that a terminal has no
  stable bot to key a window on — every occurrence there is a first occurrence.
- **Re-arm point** — `checkBalance.status === true` for that symbol, i.e. the
  same evaluation that would have opened the deal. Not "a deal opened": the
  cooldown checks below it can still decline to open, and the balance condition
  has genuinely cleared regardless.
- **`not in pairs` gets no latch** — it has no user-facing surface at all and
  the loop handles it immediately (spec §2.4). `handleDebug` is the whole fix.

## Blast Radius

1. **Other call sites of the changed functions** — none. `conditionLatch.ts` is
   new. `standingConditionLatch` is a new field, referenced only by the four
   lines that this change adds. `handleErrors` / `processError` are **not**
   modified, so every other reporter keeps today's behaviour exactly.
   `handleDebug` at `dcaHelper.ts:1554` replaces a `handleWarn` whose return
   value is unused (statement position, both return `void`).
2. **`core/` submodule — yes.** Danger List #11. These files ship inside every
   `*-sh` consumer of `main-app-sh`. The change adds a private field and one new
   leaf module; it exports no new type into a cross-service shape and changes no
   existing signature, so consumers recompile unchanged. Parent pointer bump
   required.
3. **Documented owned contracts** — none touched. No GraphQL, no `/api/v2`, no
   socket.io event name, no RabbitMQ queue, no `BaseReturn<T>`. The only shared
   Mongo collection affected is `botevents`, and only in *how many* documents are
   written — no field, index or shape changes, so the legacy `main-dash` and
   `admin-app` readers are unaffected (they read fewer rows, which is the point).
4. **Other tests exercising this path** — `core/src/bot/perContractBotMessage.spec.ts`
   drives the real `processError` off the prototype; unchanged, must stay green.
   `dealRefPrice`, `orderFee`, `orderNotFound`, `quantRulesRetry`,
   `reduceOnlyRemainder`, `userStreamLiveness` specs share the runner and must
   stay green. Full `core/npm test` is the gate.
