# Plan 081 — A status change is logged as a manual buy

Spec: [`specs/081.a-status-change-is-logged-as-a-manual-buy.md`](../specs/081.a-status-change-is-logged-as-a-manual-buy.md)

## 1. Solution

Fix the spec's §3 Assumption directly: the tail of `changeStatus` infers
origin from an input field being set. Replace that inference with the one
condition the branches above actually encode — a **grid** bot moving to
**open** is the only request that forwards the buy mode to a worker.

JIT extraction **Tier 2** (pure): the decision plus the two row payloads move
out of the 14k-line orchestrator into `src/bot/buyDialogEvent.ts`, which
imports nothing but the shared enums. Tier 1 (extract-but-coupled) was
rejected because nothing here needs a DB or a worker handle — it is a
predicate over two enum values — and Tier 3 (a port) would be inventing an
interface for a function with no I/O. The radius is the two adjacent writes
that are already being touched; the rest of `changeStatus` is Tier 0.

The `buyCount` write moves with the `buyType` write (spec §4.1.2). They are
the same defect, and guarding only the reported one would leave a bare
"Buy count: N" row on a stop — a worse symptom, since it reads as a manual
buy with no mode.

Nothing about what the callers send changes (spec §4.2.1): a caller-side fix
in one dashboard leaves the other, and any future API client, able to write
the row. The legacy dashboard's grid `sendSetStatus` proves the input reaches
a stop from more than one place.

### 1.1 Contract decisions the spec left open

- **Predicate shape.** `isManualBuyStatusChange(type, status)` — two enum
  arguments, no object, so a call site cannot pass the wrong field silently.
- **Payload ownership.** `buyDialogEventsFor(...)` returns the rows rather
  than exposing only the predicate. This is what makes §5.5 structural: one
  producer for both rows, so they cannot drift apart again. The call site
  becomes a `for … of` over its result.
- **Event name.** Exported as `BUY_DIALOG_EVENT` beside the producer. The
  existing repo-wide event constants live in `types.ts` (`BOT_STATUS_EVENT`
  = `'Status'`), but moving this literal there is a change in a file every
  service reads for no benefit at this radius; the string value is unchanged
  either way.
- **No new helper for anything else.** Checked first: there is no existing
  buy-dialog/event-origin helper anywhere in `src/` — the literal
  `'Buy dialog'` appeared at exactly the two sites being fixed and nowhere
  else in the repo.

## 3. Blast Radius

1. **Other call sites.** `grep -rn "Buy dialog" src/` returns only the two
   lines being replaced. `buyType`/`buyCount` also reach `changeBot`
   (`src/bot/index.ts:~4377`), which forwards them to the grid worker's
   `reloadBot` and writes **no** `Buy dialog` event — unchanged and
   untouched. `src/bot/helper.ts` `setStatus` is the consumer that adopts the
   mode; also untouched.
2. **`core/` submodule.** Yes — this is `main-app-sh`, shared/public and
   deployed platform-wide. The parent `main-app` pointer is bumped
   deliberately at ship time. The change is confined to a code path that only
   the main-app orchestrator runs, so the self-hosted consumers inherit the
   same log correction and nothing else.
3. **Cross-service contracts** (root `CLAUDE.md` Danger List). None crossed:
   - No GraphQL schema change — `changeStatus`'s input and return are
     untouched, so both dashboards are unaffected.
   - No socket.io event name touched (`bot update`, `bot stats update`, …).
   - No worker `postMessage` argument changed — verified at runtime, the grid
     worker receives byte-identical `args` before and after (§4 below).
   - Shared Mongo `botevents` (Danger List #12): the schema, the collection
     and the `event: 'Buy dialog'` literal are unchanged; only the number of
     rows written changes. The current dashboard's event taxonomy keys on the
     literal (`core/src/lib/botEventTaxonomy.ts` `case 'buy dialog'`) and
     keeps working — its own comment flags exactly this missing guard as the
     backend bug being fixed here. Admin-app reads the collection generically.
   - `botevents` is a log, not state: nothing reads a `Buy dialog` row to
     make a decision, so writing fewer of them cannot change bot behaviour.
4. **Other tests on this path.** No existing spec references `changeStatus`
   or `'Buy dialog'` (`grep -rln` over `src/**/*.spec.ts` — none). The full
   mocha suite is the regression net.

## 4. Verification beyond the unit spec

Drive the real `Bot.prototype.changeStatus` for a grid stop and a grid start
with a recording `botEventDb` and a fake worker — proving the guard sits on
the log write and not on the worker call:

| request | worker `args` | `Buy dialog` rows |
|---|---|---|
| grid → `closed`, **before** | `["closed", true, null, null, null, null]` | **2** (`Buy count: 3`, `Buy type: all`) |
| grid → `closed`, **after** | `["closed", true, null, null, null, null]` | **0** |
| grid → `open`, before & after | `["open", null, "all", "3", null]` | 2 (unchanged) |

The worker arguments are identical on both rows of the table — the only
behavioural difference is the log.
