# 198 — Plan: read the aggregate's bots' orders per chunk

## Solution

- `runAggregate` first calls `prefetchBots(deals)`: the distinct bots needing
  historical facts (deals with no recorded `feesEstimated`) and off-pair fees
  (deals on a `FEE_TOKEN_VENUES` venue). The deal loop is unchanged; it finds
  every bot in the caches.
- `loadHistoricalFacts(ids)` / `loadBotUnbooked(ids)`: for ids not cached,
  `IN_CHUNK` (500) bots per read, chunks one after another (no read burst),
  each bot's cache entry set at once to its chunk's promise. The single-bot
  `historicalFacts` / `botUnbooked` go through the same path with one id.
- Per chunk: one MARKET-order read (`botId: {$in}`), the bots' settings
  through the existing `botContexts` batcher, one `$group` by `botId` over the
  "fee not reported" filter (replaces the per-bot `limit: 1` probe), one
  fee-bearing-order read. Off-pair fees are still valued per bot, bot after
  bot (§1.3: the candle-day cap stays per bot).
- Failure semantics kept: a failed read gives the same fallback the per-bot
  read gave (`feesEstimated: true` / `complete: false`), cached the same way.

JIT tier 0: the arithmetic (`dealSlippage`, `sumUnbookedFees`) is already
pure; only the loading changes.

## Blast Radius

1. Callers: `botUnbooked` / `historicalFacts` are private, used only by
   `runAggregate`; `runAggregate` backs `tradingCostsSummary` and the bot
   field `tradingCosts`. No GraphQL shape change.
2. `core/` file (shared): main-app only consumer of this handler.
3. Queries: all on `orders.botId_1`; the `$group` probe examines every
   matching order of the chunk's bots instead of stopping at the first per
   bot — bounded by the same index range the MARKET read already walks.
4. Tests: `tradingCosts.handler.spec.ts` (read-shape assertions updated to
   `$in` + the grouped probe), `feeAssetPrices.spec.ts`.
