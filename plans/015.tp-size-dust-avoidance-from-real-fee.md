# 015 — Plan: skip the TP quantity gross-up when a deal's fee was all third-asset

Spec: `specs/015.tp-size-dust-avoidance-from-real-fee.md`.

## Solution

One new pure function in the existing `src/bot/dca/tpFees.ts` (not a new
file — it already owns exactly this "what does the quantity leg's fee
input evaluate to" decision for the futures case, `worstFee`/
`tpPriceDisplacement`; this is the same kind of decision, same module):

```ts
export function quantityFeeIsThirdAssetOnly(
  feeByAsset: { asset: string; total: number }[] | undefined,
  commission: number,
  feePaid: { base: number; quote: number } | undefined,
): boolean
```

True only when at least one third-asset fee has been observed (`feeByAsset`
non-empty) **and** nothing on-pair has (`commission` and both
`feePaid.base`/`feePaid.quote` are `0`) — resolving spec §5 Q1: a deal
with no fills yet has neither, so it reads `false`, not vacuously `true`.

### Call sites (both gated: new-flagged deal, per `014` §3, AND this predicate)

- `dcaHelper.ts:getBaseOrder` (`:7622-7627`): `feeFactor` becomes `1`
  (today's futures/short/simple value) when
  `quantityFeeIsThirdAssetOnly(deal.feeByAsset, deal.commission,
  deal.feePaid)` is true, in addition to the existing conditions — one
  more arm in the same ternary, not a new branch shape.
- `dcaHelper.ts:getTPOrder` (`:13232`): `maxFee` computed as `this.futures
  || quantityFeeIsThirdAssetOnly(...) ? 0 : worstFee(fee)` — same
  treatment as the existing futures zeroing at `:13096-13101`, and same
  file-header rule (§ note in `tpFees.ts`): **the price leg
  (`priceFee`/`tpPriceDisplacement`) is never touched by this** — a
  third-asset fee still doesn't cover the round trip's price-side cost by
  itself, so `priceFee` keeps reading the account's real fee exactly as
  it does for futures today.

### Correction made during gate 5 — `maxFee` itself is NOT zeroed

The plan as originally written said `maxFee` should be computed as
`this.futures || quantityFeeIsThirdAssetOnly(...) ? 0 : worstFee(fee)` —
mirroring `feeFactor`'s shape. Checked directly against `getTPOrder`: `maxFee`
(`const maxFee = worstFee(fee)`) is read at **three** sites, not one — the
plain-DCA quantity computation this spec targets, and two more sites
**inside the `if (this.combo) { ... }` branch** (a combo-specific qty
recompute that unconditionally overwrites whatever `qty` the plain-DCA
computation produced). Spec §4 explicitly excludes combo's TP path from this
spec. Zeroing the `maxFee` constant itself would have reached those two
combo-only sites too, for any combo deal `quantityFeeIsThirdAssetOnly`
evaluates true for (combo gets `feeByAsset` too, per `014` §2.4) — silently
widening this spec's blast radius into the exact territory §4 rules out and
§1's "one mechanism and only balance as a pair" warning is about.

Fixed by zeroing the multiplier only at the plain-DCA usage site's own
ternary (`this.futures || quantityFeeIsThirdAssetOnly ? 1 : long ? 1 - maxFee
: 1/(1-maxFee)`), leaving `const maxFee = worstFee(fee)` itself untouched.
Safe precisely because the combo branch overwrites `qty` unconditionally,
so this site's value never survives into a combo deal's actual TP anyway.

**Update, §4 correction below:** the "combo excluded" framing above was
this pass's starting point, not its ending one — once combo was brought
into scope, its OWN `filled.reduce(...) * maxFee` read (one of the "two
more sites," §4 correction below) was deliberately made to respect
`tpQuantityFeeIsThirdAssetOnly` too, the same way the plain-DCA site does.
The other combo-only site (further down, gated `this.botType !==
BotType.combo`) is never reached by a combo deal at all, so it stays
genuinely untouched.

### Resolving spec §5 Q2 — recomputed live, not a stored flag

Both call sites already read `deal.commission`/`deal.feePaid`/
`deal.feeByAsset` off the in-memory deal document they're already
operating on — no DB round trip, no new write, no staleness window to
manage. A stored "all-third-asset-so-far" flag would need an extra write
at the one place an on-pair fee first lands (undoing it) for no
performance benefit over a three-field boolean check. Recompute live.

### §7 solution: the two-stage placement and its sticky flag

**Correction against the spec's assumption:** §7.2 was written assuming
`isErrorNotEnoughBalance`/`isNotionalReason` are freestanding pure
functions, on the strength of the research pass's phrasing. Checked
directly against the code: both are **private class methods**
(`main.ts:2774-2781`, `dcaHelper.ts:5450-5457`), each a thin
case-insensitive substring loop over an array — `notEnoughErrors`
(`main.ts:283`, already `export const`) and `notionalReasons`
(`dcaHelper.ts:243`, currently module-private, **not** exported). This
changes where `isFeeSizingRejection` can live:

```ts
// dcaHelper.ts, next to isNotionalReason et al. — a THIRD private method,
// not a freestanding export, matching its siblings' actual shape.
private isFeeSizingRejection(reason: string): boolean {
  return this.isErrorNotEnoughBalance(reason) || this.isNotionalReason(reason)
}
```

Not placed in `tpFees.ts`: doing so would need `notEnoughErrors`/
`notionalReasons` (or the two private methods' logic) importable from a
pure module, and `notEnoughErrors` lives in `main.ts`, which imports
`mongoose`/`RedisClient`/`Rabbit` at module scope (`main.ts:131,134,147`)
— importing anything from `main.ts`, even an inert string array, drags
those side-effecting imports transitively into whatever imports it.
`tpFees.spec.ts` currently imports nothing but `tpFees.ts` itself; adding
a `main.ts` import to that chain would compromise exactly the "no
DB/queue/exchange client" purity bar `014`'s plan and this file's own
JIT-tier section both hold `tpFees.ts` to. **Consequence: §7.2's
classifier is Tier 0 like its siblings, not independently unit-testable
without instantiating the bot class** — spec §10's claim that this piece
is "testable now, not blocked on `016`" was wrong; corrected in the
traceability table below. `export`ing `notionalReasons` alongside
`notEnoughErrors` is still worth doing regardless (consistency, and
`main.ts`/`dcaHelper.ts` already cross-import each other's classifiers
freely) — it just doesn't unlock a pure-module test on its own.

**New sticky field**, sibling to `Deal['startBlocked']`
(`types.ts:1399-1425`), not a reuse of it (that field is hard-scoped to
the opening order by its own comment):

```ts
type FeeSizingFallback = {
  status: 'pending' | 'confirmed'  // added on review — see §7.3
  since: number
  confirmedAt?: number
  reason: string        // the classified rejection reason, verbatim
  triggeredByOrderId: string  // the real-fee attempt that got rejected
}
```
— `feeSizingFallback?: FeeSizingFallback` added to `DCADealsSchema`/
`ComboDealsSchema` (deal-level, alongside `startBlocked`) **and** to the
grid `BotSchema` (bot-level, per §7.3 — grid has no deal to hang it on).
Both are DB-persisted (`updateData`, same as `startBlocked`), so restart-
safe by construction, matching `startBlocked`'s own guarantee.

**Wiring, per §7.4 and §7.3's pending/confirmed split:**
- Before building a TP at the §2 zeroed size, check
  `deal.feeSizingFallback` (or `bot.feeSizingFallback` for grid) first —
  if `status === 'confirmed'`, skip `quantityFeeIsThirdAssetOnly` entirely
  and use today's §1 sizing. A `pending`-only record does not gate this
  check — `quantityFeeIsThirdAssetOnly` still runs and a real-fee attempt
  can still be tried again. This is the "read many times" half of §7.3.
- **Chain A** (`placeOrders`/`sendGridToExchange`, no `returnError`
  today): this plan adds a `returnError: true` call specifically for a
  §2-zeroed TP (only when `quantityFeeIsThirdAssetOnly` is true and no
  `confirmed` fallback flag is set yet — every other Chain A placement is
  unchanged), so the rejection reason is available to classify. On
  `isFeeSizingRejection`:
  1. write `feeSizingFallback` via `updateData` with `status: 'pending'`;
  2. rebuild the same TP with §1 sizing, resend with a `...ef`-suffixed
     `clientOrderId` (§8 item 3 — see below for the ambiguous-outcome
     check);
  3. on that resend's own success, a second `updateData` flips `status`
     to `'confirmed'` (sets `confirmedAt`) and raises a bot-event/error
     the orchestrator captures (mirrors how `markDealStartBlocked`
     already posts a bot event for its own condition,
     `dcaHelper.ts:777-861`) — this is the one signal an operator actually
     sees; on the resend failing instead, **no second write** — the
     record stays `pending`, unconfirmed, and this placement falls
     through to Chain A's existing (unchanged) generic handling.
- **Chain B** (`closeDealById`/`prepareTpOrder`, already `returnError:
  true`): the `isFeeSizingRejection` check is a new branch checked
  **before** the existing adaptive-close/notional-retry branches
  (`dcaHelper.ts:5903-5987`) — same reasoning as spec §7.4: those
  existing branches would just recompute the same too-small size again
  without this check running first. Same pending→confirmed write
  sequence as Chain A.
- **Futures — no new guard needed.** `quantityFeeIsThirdAssetOnly` is
  already never called for a futures deal (§1/§2's existing
  `this.futures` branch zeroes the gross-up unconditionally, before this
  predicate would ever be consulted) — so step 1 of §7.1 never fires on
  futures, `feeSizingFallback` is never written, and none of the above
  wiring needs its own separate futures check. Spec §7.3a restates this
  explicitly; noted here so the plan doesn't read as silent on it.
- **§8 item 3 (ambiguous outcome).** Resolved: check order status via
  `getOrder`/the existing cache-or-REST lookup (`main.ts:getOrder`,
  `:4452`) for the real-fee attempt's `clientOrderId` before sending the
  estimated-fee resend, not fire blind. A confirmed-not-live real-fee
  order is the only condition that proceeds to the resend; anything else
  (found live, lookup itself fails) aborts the fallback for this tick and
  lets the next `placeOrders`/`checkTPLevel` pass re-evaluate from
  scratch — safer to skip a cycle than to risk a double order.
- **§8 item 4 (grid reset/expiry) — resolved: no reset in this pass.** A
  grid bot's `feeSizingFallback`, once set, is permanent for that bot,
  same as DCA/combo's deal-scoped one. Building a re-arm mechanism (retry
  after N days, after M clean fills) is speculative without evidence
  a stale flag is actually costing meaningful accuracy in practice —
  ship without one, add it as a follow-up if the flag turns out to fire
  on transient causes often enough to matter. Noted as a known
  limitation, not silently decided.
- **§8 item 2 (fee-observation race) — resolved: not a new problem.**
  `quantityFeeIsThirdAssetOnly` flipping across consecutive TP builds
  before fee data settles is bounded by the same TP-replacement machinery
  that already handles a changed TP size for any other reason (a filled
  safety order changes the deal's TP size on every fill regardless of
  this spec) — not a new class of churn, just a new occasional cause of
  one. No new debouncing added.

## §2/§3 correction — persisted fields were the wrong input (found writing tests)

The original "Resolving spec §5 Q2" section above said `getBaseOrder`/
`getTPOrder` could read `deal.feeByAsset`/`commission`/`feePaid` directly
off the in-memory deal document, live, with "no staleness window to
manage." That assumed all three fields are kept current on every fill. They
are not: `feeByAsset` (spec 014 §2.2) is written only inside `closeDeal`'s
TP-fill branch — which runs strictly AFTER the TP being sized here has
already been built and sent. For a deal's first take-profit (and for a
non-multi-TP deal, its only one), `closeDeal` has never run, so
`feeByAsset` is unconditionally empty and `quantityFeeIsThirdAssetOnly`
unconditionally reads false — the zeroing this spec exists for could never
fire for the common case, only for a second-or-later TP on a multi-TP deal.

Fixed by not trusting the persisted fields at all: `getBaseOrder`/
`getTPOrder`/both Chain A and Chain B's `isZeroedFeeSizeTp` now call a new
`currentDealFeeIsThirdAssetOnly` (dcaHelper.ts), which re-scans every
currently-filled order via `getOrdersByStatusAndDealId` (the same
in-memory index `getCommDeal` already re-scans on every call — no new DB
cost) and answers the question from the orders directly, via a new pure
`ordersFeeIsThirdAssetOnly` (tpFees.ts). `quantityFeeIsThirdAssetOnly`
itself is unchanged and still correct — the bug was in what its callers
fed it, not in the predicate. Still gated on the new-deal flag (014 §3),
checked inside the new method.

## §7 implementation notes (gate 5)

- **Grid needed no wiring in this pass, only the reserved schema field.**
  §4 excludes grid's TP path from §2/§3 the same as combo's — grid's
  `helper.ts` never calls `quantityFeeIsThirdAssetOnly`, so a grid TP can
  never be "zeroed" and §7's fallback can never have anything to fall back
  from. `BotSchema.feeSizingFallback` exists (spec 014-style forward-
  compatible field) but is never written by this pass — matches §7.3's
  mention of a bot-level flag being a future landing spot, not a claim that
  this pass wires it.
- **The estimated-fee resend does not thread `closeDealById`'s explicit
  `price` parameter through.** Chain B's normal flow honors an explicit
  `price` override (used by `closeByLimit`); `runFeeSizingFallback`'s
  resend goes through `prepareTpOrder`'s own fresh `getLatestPrice` instead.
  Acceptable for now — the fallback's whole point is fixing SIZE, not
  matching an explicit price — but noted as a known simplification, not an
  oversight, in case `closeByLimit` + the fee-sizing fallback ever interact
  in a way that matters.
- **§7.3's "raises an error the orchestrator captures"** is implemented as
  `this.handleErrors(..., setError: false, sendError: true, setEvent: true)`
  on confirm — visible to the user/admin as a notification, but does not
  flip the bot into an error state (the deal is fine; only its fee-sizing
  assumption for THIS one case was wrong, and every future TP now
  correctly uses the account-rate size).
- **`tests/processing/feeSizingTwoStage.ts` now covers §2/§3 and the core of
  §7** (added after this note was first written): a base order filled with
  a third-asset fee produces a same-size TP (no gross-up); an on-pair fee
  keeps the existing gross-up (proves the zeroing is gated, not
  unconditional); real-fee TP rejected → estimated-fee resend succeeds →
  sticky flag confirmed, with the operator-facing error raised; real-fee TP
  rejected → resend also fails → flag stays `pending`, never confirmed, no
  error raised. Drives the REAL `getTPOrder`/`closeDealById` against a real
  in-memory-Mongo deal (`Object.create`-ing the dcaHelper prototype, per
  `openNewDealRefusal.harness.ts`'s precedent — only the exchange/Redis
  surface is stubbed). **Still not covered**: §7.2's rejection classifier
  firing on an UNRELATED reason (spec §10 scenario 3) and §8 item 3's
  ambiguous-outcome status check actually short-circuiting the fallback
  (scenario 4, `getOrderForReconcile`/`isDefinitiveOrderNotFound` returning
  "found live" or "lookup failed" rather than "confirmed not found") — both
  worth adding before this ships with full confidence, but the core
  mechanism this spec exists for is no longer test-free.

## §4 correction — combo brought into scope (post-review)

Spec §4 originally excluded combo's TP path as "untraced." Traced on
review: `getTPOrder`'s `if (this.combo) {...}` branch sizes its TP off a
balance-based formula (`qty = <balance math> - filled.reduce((acc, v) =>
acc + v.executedQty * maxFee, 0)`), not the plain path's multiplier — but
that subtraction was still the flat account-rate ESTIMATE, unconditionally,
the exact same gap §2/§3 fixed for the plain path. Since
`tpQuantityFeeIsThirdAssetOnly` (computed once, above both branches) is
deal/order-level and not DCA-specific, combo's subtraction now reads it
too — zero when the deal's fees so far were all third-asset, the flat
estimate otherwise, identical to the plain path's reasoning.

This also resolves what §4's `feeBalance` worry was actually about:
`feeBalance` (a KuCoin-fee-discount running balance, written in
`comboHelper.ts` at fill time, keyed by the transaction not the TP order's
`clientOrderId`) is untouched by this change — it's additive, upstream of
the `qty -= f` line this spec edits, and unrelated to which of the two
`...rf`/`...ef` attempts ultimately fills. Confirmed by tracing every
`feeBalance` write site, not assumed from DCA parity.

`isZeroedFeeSizeTp` in both Chain A and Chain B no longer excludes combo —
same predicate, same `runFeeSizingFallback`, same sticky flag, reusing the
`...ac`-suffix precedent's own reasoning for why two `clientOrderId`s for
one logical attempt is already a safe, proven shape in this codebase.
`tests/processing/feeSizingTwoStage.ts`'s `combo` describe block covers
both the zeroing (no subtraction) and the two-stage fallback (rejected →
resend at the full estimate → sticky flag confirmed) for a combo deal.

## §9 Q1 correction — grid reset ties to stop-BY-TP, not any stop

The original "no reset in this pass" answer still stands (grid's own TP
path isn't wired to any of this yet — `helper.ts` never calls
`quantityFeeIsThirdAssetOnly`/`currentDealFeeIsThirdAssetOnly` at all, so
`BotSchema.feeSizingFallback` is a reserved field, never written). But the
right reset condition, for whenever grid support lands: reset specifically
when the bot stops **because its TP closed** — not on every `stop()` call
(a pause, a manual stop, an error stop all leave the position/balances
in place, so a fee-sizing lesson learned mid-run is still valid after
those). A TP close is the one case where everything afterward starts
against a genuinely fresh balance, the same reasoning DCA/combo's
deal-scoped flag relies on implicitly (a new deal already starts with no
flag at all). Locate grid's TP-close-specific path (as opposed to its
generic `stop()`) before wiring this, not assumed to be the same call.

## JIT extraction tier

**Tier 2** for `quantityFeeIsThirdAssetOnly` (`tpFees.ts`) — pure, no I/O,
added next to `worstFee`/`tpPriceDisplacement`, independently unit-tested.

**Tier 0** for `isFeeSizingRejection` (`dcaHelper.ts`) — a private method,
same as the two siblings it composes (`isErrorNotEnoughBalance`,
`isNotionalReason`), for the reason given above: pulling it out to a pure
module would mean pulling `main.ts`'s side-effecting imports along with
it. This is a case where the JIT ladder's "lowest tier that removes the
smell" genuinely is Tier 0 — the smell (a private-method classifier with
no isolated test) isn't being made worse by adding a third one shaped
exactly like the two it already sits next to, and extracting a purer
version would cost a real architectural change (untangling
`notEnoughErrors`/`notionalReasons` from `main.ts`/`dcaHelper.ts`'s
mutual imports) that this spec did not set out to do.

**Tier 0 for the retry orchestration itself** (§7's wiring inside
`placeOrders`/`sendGridToExchange`/`closeDealById`/`prepareTpOrder`) —
same reasoning as `014`'s plan: a few more lines and one more DB write
(`updateData` for `feeSizingFallback`) in already-large, already-legacy,
I/O-coupled functions, not a rewrite. Not Tier 1: nothing here is being
pulled into a newly-named module — the orchestration (try, classify,
check status, retry, persist) is inseparable from the exchange/DB calls
it coordinates, which is exactly what Tier 0 is for on a live trading
engine mid-bug-fix rather than mid-modernization.

## Blast radius

1. **Other call sites.** `getBaseOrder` is DCA-only; `getTPOrder` is shared
   with combo (§4's original "untraced" exclusion lifted — see the §4
   correction above, combo's own balance-based branch now reads the same
   `tpQuantityFeeIsThirdAssetOnly`). Both are additive and read `false`
   for a deal with no `feeByAsset`/without the new-deal flag, i.e. for
   every deal until `014` ships and populates it — no behaviour change
   for an existing deal either way. `worstFee`/`tpPriceDisplacement`'s
   existing callers (`getTPOrder`, `prepareTpOrder`'s SL path per
   `tpFees.ts`'s own header) are unaffected — this adds a new export,
   doesn't change either existing one.
2. **`core/` submodule.** Same as `014` — this repo is the `core/` content;
   platform-wide once the pointer in `app` is bumped.
3. **Cross-service contracts.** None — no schema, GraphQL, socket, or
   queue shape changes. Purely an internal quantity-math input.
4. **Restarting bot workers.** Same staged-rollout shape as `014`/`003`:
   inert until `014` ships (nothing produces `feeByAsset` before then,
   so the predicate is always `false`) and bot workers restart.
5. **The §1 warning, restated as a blast-radius item.** This plan
   deliberately does not touch `feeFactor`'s `1 + fee.taker` branch or
   `maxFee`'s `worstFee(fee)` branch for any deal that has (or ever had)
   an on-pair fee — those stay exactly as `:7601-7621`/`:13242-13250`
   describe, untouched, so bug #396's fix and the Kraken `fciq`/`fcib`
   reasoning are not at risk from this change.
6. **§7's new call sites.** `isErrorNotEnoughBalance` (`main.ts:2774-2781`)
   and `isNotionalReason` (`dcaHelper.ts:5450-5457`) gain one new caller
   each (`isFeeSizingRejection`) — both are pure predicates already
   called from several places; a new caller doesn't change their
   behaviour for existing callers. Chain A (`placeOrders`) gains a
   `returnError: true` call it doesn't make today, but **only** on the
   specific, new, flag-gated path (§2-zeroed TP, no `feeSizingFallback`
   yet) — every other Chain A placement keeps calling
   `sendGridToExchange` exactly as it does today, `returnError` still
   falsy.
7. **Cross-service contracts, revised.** `feeSizingFallback` is a new
   field on the deal/bot schema — same additive, no-existing-consumer-
   breaks reasoning as `014`'s equivalent fields. Whether it's exposed on
   GraphQL/REST is not decided here (unlike `014`'s fields, this one is
   diagnostic/internal, not obviously dashboard-relevant) — flag as an
   open question for whoever next touches this spec rather than silently
   including or excluding it.
8. **Restarting bot workers, revised.** Also depends on spec `016`
   existing for §7's own tests to run before this ships with confidence
   — §2's mechanism has unit coverage today; §7 does not, until `016`
   lands (§10).
