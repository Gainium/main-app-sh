# 008 — Plan: port the integration-test harness from `app`

Spec: `specs/008.test-processing-harness.md`.

## Solution

1. `npm i -D mongodb-memory-server sinon` (versions: match whatever `app`'s
   `package.json` pins, so behavior is proven-identical rather than a
   fresh version pickup).
2. Edit `src/db/data.ts`: add the `NODE_ENV === 'testing'` branch verbatim
   from `app/src/db/data.ts`'s shape, adapted to have no `coreConnect`
   layer to call through to (this file already builds the connection
   string directly) — `MONGO_DB_URI` env override still takes priority
   over spinning up a fresh server, same as `app`, so a developer/CI job
   that wants a real Mongo in test mode still can.
3. New directory `tests/processing/`, new npm script `processing:test`
   (`tsc --project tsconfig.json && env NODE_NO_WARNINGS=1
   NODE_ENV=testing mocha --timeout 30000 --exit -r ts-node/register
   'tests/processing/**.ts'`), mirroring `app`'s script verbatim except
   for the path (`app-sh` has no `dotenv/config` requirement to carry
   over unless `src/config` needs it — check at implementation, don't
   assume).
4. One smoke test, `tests/processing/smoke.ts`: create a user via the real
   DAO (`userDb.createData`), stub `ExchangeChooser.chooseExchangeFactory`
   with the §2-item-3 shape, drive one real production path (the
   simplest available — e.g. a balance check or a single grid-bot
   creation resolver call) and assert the write landed in the in-memory
   Mongo. This is the harness's own proof of life — not a fee-feature
   test, just confirmation the three pieces in §2 actually work together
   in this repo before `007` builds on them.

### Why there's no red-test gate 2 for this spec

Gate 2 asks for a test that fails, before implementation, for the reason
the spec states. There is no decision function here to pin — this spec
adds *tooling* (a DB stub, a stub pattern, a directory + script), not
business logic. The closest equivalent is: before step 2-3, `tests/
processing/smoke.ts` cannot exist/run at all (no directory, no script, no
in-memory Mongo) — that absence is this spec's "red." Gate 6 is "the
smoke test passes," which is also, for this spec, the whole of gate 5's
proof.

## Contract decisions the spec left open

- **§3 Q1 (`exchangeChooser.ts` interface parity):** resolved at
  implementation time by reading `app-sh/src/exchange/exchangeChooser.ts`
  directly and matching the stub to its real shape — not assumed
  identical to `app`'s copy going in.
- **§3 Q2 (one `MongoMemoryServer` per process):** adopt `app`'s choice
  (one per process, wipe collections between tests) — no reason found to
  diverge.
- **§3 Q3 (`tsconfig.json` include path):** add `tests/processing` to
  whatever `include`/`files` the existing config uses, mirroring however
  `app`'s `tsconfig.json` includes its own `tests/` — checked, not
  assumed, at implementation.

## JIT extraction tier

Not applicable — this spec adds no business-decision code. The one
production file touched, `src/db/data.ts`, gains a conditional branch, not
a decision worth extracting into a pure module (it's "which connection
string," gated on an env var already read everywhere else in this file
the same way).

## Blast radius

1. **Other call sites of `src/db/data.ts`.** This is the single Mongo
   connection factory for the entire process — every DAO in
   `src/db/dbInit.ts` depends on it indirectly. The new branch only
   activates when `NODE_ENV === 'testing'` (or `MONGO_DB_URI` is
   explicitly set) — confirmed this repo's production `NODE_ENV` is never
   `'testing'` (that value is test-runner-only, set by the new
   `processing:test` script and by the existing `package.json:8` `test`
   script). Production connection behaviour is unchanged.
2. **`core/` submodule.** This repo is the `core/` content; `app`'s own
   `src/db/data.ts` wrapper is UNCHANGED by this spec (it delegates to
   `coreConnect.connection()`, i.e. this file, and already has its own,
   separate test-mode branch layered on top — the two don't conflict,
   `app`'s branch fires first and this repo's new branch becomes a no-op
   dead code path from `app`'s perspective, since `app` already returns
   before delegating deeper in test mode). Confirm this at gate 5 rather
   than assume — if `app`'s wrapper always short-circuits before calling
   this file's `getMongooseConnect` in test mode, this repo's own branch
   only ever fires when `app-sh` is tested standalone (the actual goal),
   never double-fires when `app`'s suite runs.
3. **Cross-service contracts.** None — devDependency and test-only code,
   no schema/API/queue shape change.
4. **CI.** A new script must be wired into whatever CI runs `npm test`
   today if `processing:test` is meant to run automatically, not just
   locally — check `.github/workflows/` at gate 5; not assumed here.
