# 075 — plan

Spec: `specs/075.a-close-refusal-naming-the-position-direction-is-not-read-as-flat.md`

## 1. Solution

Add the missing OKX wording to `positionAlreadyClosedReasons`
(`core/src/bot/dcaHelper.ts`), keeping the entry already there — the two are
different messages from the same venue, not two spellings of one, so neither
can replace the other.

The entry is stored as the **substring** `'positions in this direction for this
contract'` rather than the full sentence. Everything the venue puts around that
clause is decoration it has changed before ("Order failed because…", the
trailing "to reduce or close."), while the clause itself is the condition. The
entry is matched through `normalizeReason`, exactly like every other entry, so
punctuation and casing are already out of the comparison.

That is the whole code change: one array entry plus the comment that says which
venue and why. No new helper — `isPositionAlreadyClosedReason` and
`normalizeReason` already exist and already do the matching; the defect is a
gap in the data they read (spec §3.1), and the right fix for a gap in a lookup
table is to fill the table.

## 3. Contract decisions the spec left open

- **Where in the list.** Beside the existing OKX entry, under the same
  `// OKX` comment, so the next person reading the list sees at once that this
  venue has two wordings. The list has no ordering semantics — it is a
  `some`-style scan — so position is documentation only.
- **How much of the sentence to store.** The clause, not the sentence (§1).
- **Nothing is exported.** `notionalReasons` and `notEnoughErrors` are exported
  so their lists can be unit-tested without a bot; this list stays private
  because the harness drives the real `closeDealById`, which is the stronger
  test and the one the spec actually requires (§4.3).

## 4. Blast Radius

1. **Other call sites.** `positionAlreadyClosedReasons` has exactly one reader,
   `isPositionAlreadyClosedReason` (`dcaHelper.ts`), which in turn has exactly
   one caller: the string-refusal ladder inside `closeDealById`. Verified by
   grep across both `core/src` and the parent repo's `src`. Nothing else in the
   platform reads either.
2. **`core/` submodule.** Yes — this file is in `core/`, shared by the cloud
   and self-hosted builds. The change is additive to a private const, so it
   adds no type, no export and no signature: nothing downstream can fail to
   compile. The parent repo does **not** override `closeDealById` (checked:
   the parent's `src/bot/dcaHelper.ts` only mentions it in a comment), so the
   core implementation is the one the bot workers run.
3. **Documented cross-service contracts.** None touched. No GraphQL field, no
   REST shape, no socket event, no queue payload, no Mongo schema field, no
   `BaseReturn` shape. The only observable change is which branch one method
   takes on one venue string.
4. **Behavioural radius — what else can now reach the branch.** Any DCA or
   Combo deal whose close is refused with this wording. That is the intended
   population and, per spec §4.1, the venue has scoped the answer to the
   `positionSide` the deal itself sent, so the branch cannot act on another
   leg's state. Grid never reaches this code (spec §4.4).
5. **Other tests on this path that must stay green.**
   `src/bot/dca/refusedCloseDeadlock.harness.spec.ts`,
   `src/bot/dca/refusedCloseRestore.harness.spec.ts`,
   `src/bot/dca/lostLedgerClose.harness.spec.ts`,
   `src/bot/dca/tpCloseOutcome.spec.ts`,
   `src/bot/dca/positionReconcile.spec.ts`,
   `src/bot/closeDealNotOpen.spec.ts`, `src/bot/strandedLocalRefusal.spec.ts`,
   `src/bot/notEnoughBalanceReasons.spec.ts`, plus the full suite.

## 5. JIT legacy tier

**Tier 0.** The causal path is a module-level `const` array and a six-line
predicate that already has one responsibility and no I/O. There is no
decision/I-O tangle on the path to cut, and `closeDealById` itself is only
*read* here, not modified — extracting any part of it would be scope creep
against a method the runbook's radius rule keeps out of a one-entry data fix.
