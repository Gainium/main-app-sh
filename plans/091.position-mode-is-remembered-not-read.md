# Plan 091 — A futures bot remembers the account's position mode instead of reading it

Spec: `specs/091.position-mode-is-remembered-not-read.md`.

## Build order

1. `src/bot/hedgeModeGuard.ts` — new module. Three things, all of them
   decisions the engine was making inline or not at all:
   - `isPositionSideRefusal(reason)` — the venue-refusal predicate (§4.5);
   - `hedgeLegForSettings(settings)` — the leg, or `null` (§4.6);
   - `readHedgeMode(uuid, fetch, maxAgeMs)` — the per-connection coalesced read
     (§4.2).
   JIT tier: **Tier 2** for the first two (pure, no imports beyond types);
   **Tier 1** for `readHedgeMode`, which owns process state (the cache) and is
   handed its I/O as a callback rather than reaching for an exchange client.
   Tier 3 would mean inventing a port for a single boolean read.
2. `src/bot/hedgeModeGuard.spec.ts` — the three decisions, including the
   both-directions refusal wording and the NEUTRAL-grid refusal to guess.
3. `src/bot/hedgeMode.harness.spec.ts` — the real `MainBot.readAccountHedge`
   and the real `MainBot.sendOrderToExchange` over a fake OKX that enforces
   hedge mode. This is the test that fails for the reason §3 names.
4. `src/bot/main.ts` — the `loadData` call site (§4.1), `readAccountHedge` /
   `persistHedgeMode` (§4.1/§4.3), and the refusal branch in
   `sendOrderToExchange` (§4.5/§4.6).
5. `CHANGELOG.md` + `package.json` patch bump.

No other service is touched, and no build order across services applies.

## Contract decisions the spec left open

- **Where the coalescing lives.** §4.2 requires one read per connection but does
  not say where. Decided: a module-level map in `hedgeModeGuard`, shape copied
  from `utils/leverageBracketCache` (fresh-TTL + in-flight coalescing, errors
  never cached). Not Redis: `QtyStepGuard`'s note applies — this is read from a
  bot load and from an order path, and `RedisClient.getInstance()` retries a
  dead Redis forever. The bound is the same one `leverageBracketCache` relies
  on (one entry per connection this process loaded a bot for), so no eviction
  policy.
- **The three freshness windows.** 60 s for a SERVICE-RESTART load (covers the
  burst; a mode changed at the venue is picked up by the next load within a
  minute). 0 for a user-initiated start — `setHedge` cannot reach a worker's
  cache, so that path keeps the uncached read it has today, and concurrent
  starts still share one in-flight call. 5 s for the refusal path (the re-read
  must be a real re-read, but a burst of refused orders on one connection must
  not become a burst of venue calls).
- **What an unanswered read returns.** Decided: `null` from `readHedgeMode`, and
  `readAccountHedge` then returns the stored copy with `status: ok`. It never
  reports `notok`: `loadData` treats a `notok` hedge read as "leave `this.hedge`
  alone", which for a restart would silently keep `false` — the failure being
  fixed. Returning the stored copy is both explicit and exactly today's
  behaviour.
- **The write-back's Mongo shape.** Decided:
  `{_id, exchanges: {$elemMatch: {uuid, hedge: {$ne: live}}}}` +
  `{$set: {'exchanges.$.hedge': live}}`. The `$ne` makes an already-correct copy
  a no-op rather than a write, and the positional `$` bounds the write to one
  array element and one field (§4.3/§4.4).
- **Whether the refusal path may re-send.** §4.5 says once; §4.6 says not when
  the leg is unknown. Decided: gate on `this.futures`, on the live mode actually
  DIFFERING from the held one, and on the corrected `positionSide` differing
  from the order's. All three must hold, which is also what makes it
  self-limiting without a counter.
- **`count` on the re-send.** Passed through unchanged, exactly as the tick-size
  and quantity-decimals branches do, so the coin-M contract conversion and the
  `count === 0` write-ahead keep their meaning.

## Blast Radius

1. **Other call sites.** `hedgeModeGuard` is new — its only callers are the two
   added in `main.ts`. `readAccountHedge` has two callers, both added here.
   `this.hedge` is READ at ~20 order-building sites; none of them change, they
   just receive a value that is now right. The `hedge` local in `loadData` keeps
   its `BaseReturn<boolean> | null` shape, so the `hedge.status`,
   `hedge?.data` and `!hedge?.data` readers below it are untouched.
2. **`core/` submodule.** Yes — both files are under `core/`, i.e.
   `main-app-sh`, shared and deployed platform-wide. Every bot type on every
   futures venue runs this code. The behaviour change is confined to
   `allPositions` venues (binance / okx / bitget / kucoin-full / paper) and
   only on a service-restart load; every other venue already read live.
3. **Cross-service contracts.** None of the shapes in the root Danger List move.
   No GraphQL, REST, socket.io, Redis-channel or RabbitMQ change. One Mongo
   collection is written (`users.exchanges[].hedge`) — a field main-app already
   owns and already writes from the `setHedge` mutation, with the same value
   domain. No schema change.
4. **Exchange load.** The one measurable cost. Net effect on a mass restart:
   ≈320 `getHedge` calls (one per futures connection per worker process) where
   today there are 0 and before 198d586 there were ≈1,400.
5. **Other tests on this path.** `nanOrderRefusal`, `zeroSizeOrderRefusal`,
   `qtyStepGuard`, `strandedLocalRefusal` and `tpBurstInvariant` all drive
   `sendOrderToExchange`; the new branch is gated on `this.futures` AND a
   position-side refusal wording, so none of them reach it. `redisSnapshotGuard`
   drives `loadData`'s Redis arm only and stops before the futures block.
