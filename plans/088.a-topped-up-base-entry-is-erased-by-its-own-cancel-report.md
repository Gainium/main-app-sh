# Plan 088 — A topped-up base entry is erased by its own cancel report

Spec: `specs/088.a-topped-up-base-entry-is-erased-by-its-own-cancel-report.md`

## Build order

One step, one file.

1. `src/bot/main.ts`, `fillPartiallyFilledOrder`: move the
   `partiallyFilledFilledSet` block ABOVE the `coinbase` early return, and say
   in the comment why the order matters (spec `088` §3/§4.1).

Nothing else changes. `getAvgPrice`, the `levels.complete` recompute,
`topUpSettledBaseEntry`, `resolveBaseOrderQty`, `getTPOrder`, `buyRemainder`
and `processOrderQueue` are all untouched.

## Contract decisions the spec left open

- **Which of the two rules moves.** The spec names the ordering as the defect
  but not which line to move. The `coinbase` return is the one with a recorded
  scope ("do not send a remainder order on this venue", spec `057` §4.4/§5); the
  set branch has none beyond "you are the second caller through the mutex".
  Moving the set branch UP therefore preserves the documented rule exactly and
  narrows nothing: the set branch places no order, so lifting it above a guard
  whose subject is order placement cannot let an order out.
- **No new predicate.** `partiallyFilledFilledSet.has()` and `getOrderFromMap`
  already exist and are already what this branch reads. Nothing is added.

## Blast radius

1. **Other call sites.** `fillPartiallyFilledOrder` has three callers:
   `processOrderQueue` (the stream replay — the one this fixes), the synchronous
   placement-response path in `main.ts`, and `topUpSettledBaseEntry` (which
   passes `settledBaseEntry: true` and never saw the `coinbase` return anyway).
   The behaviour of all three changes only for a `clientOrderId` that is in
   `partiallyFilledFilledSet` — i.e. one `buyRemainder` has already merged.
   `buyRemainder` has exactly one entry point (this method), so on `coinbase`
   the set can only ever hold settled base entries.
2. **`core/` submodule.** Yes — `src/bot/main.ts` is `main-app-sh`, shared with
   every consuming service. The method is bot-engine-internal: it is not
   exported, not part of any REST/GraphQL shape, not a socket event, not a queue
   payload, and not a stored field. Blast radius is "every service that runs the
   DCA/combo/grid engines", which is the bot workers.
3. **Cross-service contracts** (root `CLAUDE.md` Danger List). None touched. No
   `BaseReturn<T>`, no `/api/v2`, no GraphQL schema, no socket.io event name, no
   Redis channel, no `ARCHIVE_QUEUES`, no shared Mongo field. The `orders` row
   this makes the queue write is the row spec `058` already persists — the write
   becomes an idempotent rewrite of values already on disk.
4. **The callback that fires.** `processOrderQueue` dispatches on the returned
   row's status, so a Coinbase settled entry now reaches `onFilled` where it
   reached `onCanceled`. Both are no-ops for it, and this is the shape every
   non-Coinbase venue has already run in production since 2026-09-18:
   - `processFilledOrder` de-duplicates on `processedFilled`, and the settle's
     `handleUnknownOrder` → `processFilledOrder` has already registered this
     `clientOrderId` for this deal;
   - `processCanceledOrder`'s `dealStart` branch is gated on
     `shouldSettlePartialBaseEntry`, which returns false once the deal has left
     `start`.
5. **Take-profit sizing.** `findBaseOrderByDeal` now returns the merged row
   instead of the book fill, so `resolveBaseOrderQty` reports `source: 'order'`
   where it reported `'position'`. The QUANTITY is unchanged wherever
   `deal.size` is current, because that branch is one-way — it only raises the
   contribution above the row and never lowers it (spec `026`). On the
   production deal both of the calls that logged the rescue resolve to the same
   quantity after the change; the `holds more than its order rows account for`
   warning simply stops being raised, which is what it is for.
6. **Tests that must stay green.** `baseEntryTopUp.harness.spec.ts` (spec `057`,
   including `§4.4 the guard still holds for every other caller` — that order is
   not in the set, so the guard still returns before anything is sent),
   `partialBaseEntry.harness.spec.ts` (`038`/`048`/`059`), `baseOrderQty.spec.ts`
   (`026`), and the full `npm test` suite in `core/`.

## Legacy tier (Part 4)

**Tier 0.** The causal path is two adjacent guard clauses in a method that is
already small and already has a named, tested pure decision layer around it
(`partialBaseEntry.ts`, `remainderFill.ts`). There is no decision logic mixed
with I/O to extract here — the fix is the order of two returns. Extracting the
method's guard ladder into a predicate module would be a rewrite of code that is
not what is wrong, on the widest-blast-radius file in the platform.
