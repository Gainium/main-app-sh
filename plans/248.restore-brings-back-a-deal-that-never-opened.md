# Plan 248 — Restore brings back a deal that never opened

Spec: `specs/248.restore-brings-back-a-deal-that-never-opened.md`.

## Build order

1. `src/bot/dca/restoreDealGuard.ts` — pure `dealHoldsPosition` +
   `RESTORE_NEVER_OPENED_REASON` (§4.1). Reuses `executedFillQty` (spec 029);
   no new fill arithmetic.
2. `Bot.restoreDeal` (`src/bot/index.ts`) reads the deal's order rows (same
   projection `retireStrandedStartDeal` uses) and refuses before any write
   (§4.2). Placed after the `useBots` hop, so it runs on the process that owns
   the DB read whichever process received the mutation.
3. No resolver change: the `restoreDeal` resolver delegates to
   `Bot.restoreDeal` and returns its `{status, reason}` verbatim; V2 shows
   `reason` on a non-OK answer (`useDealActions.ts`).

## Contract decisions

- The refusal is a `notok` `BaseReturn` with a reason string: the same shape
  the mutation already returns for "Only canceled deals can be restored". No
  GraphQL schema change.
- The V2 Restore button is NOT pre-disabled. The only state on a V2 deal row is
  `levels.complete`, and a canceled deal whose base partly filled also reads
  `complete: 0` (`sellRemainder`'s own test), so a client-side gate would block
  real positions. The server refusal is the gate.

## Blast radius

- Restore only. One extra indexed read (`orders.dealId`) per restore request.
- Refuses only a deal with no filled order row (or, with no rows, an empty
  ledger). Production read: of every restore ever made, only the defect deal
  is refused; the others (terminal imports, `FILLED` `'-1'` rows) still pass.
- No data, schema, socket or cross-service contract touched.
