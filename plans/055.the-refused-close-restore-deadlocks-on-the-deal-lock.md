# 055 — plan

Spec: `specs/055.the-refused-close-restore-deadlocks-on-the-deal-lock.md`.

## 1. Solution

The spec's Assumption names one cause: a call chain holding
`` `${botId}${dealId}` `` awaits a method guarded by the same key on the same
non-reentrant `IdMutex`. The fix removes exactly that, and nothing else.

Split `placeOrders` into the guard and the body:

- `placeOrders` keeps its `@IdMute(mutex, … => `${botId}${dealId}`)` and now
  does nothing but delegate. Every existing caller is untouched (§4.2).
- `placeOrdersHoldingDealLock` is the former body, `protected`, undecorated,
  documented as callable **only** by a caller that already holds the key.
- `restoreCloseAfterRefusal` — whose sole caller is `closeDealById`, which
  holds that key — calls the undecorated one.

Rejected alternatives:

- **Make `IdMutex` reentrant.** Correct in the abstract, but `IdMutex` is the
  serialisation primitive under every bot type, the exchange layer and the
  stream layer. Platform-wide blast radius for a one-call-site defect.
- **Give `mutex` a `lockTimeout`.** Turns the deadlock into a silent
  force-release of a lock someone else may be holding, across ~46 keys. It
  masks this bug rather than removing it.
- **Fire the restore after `closeDealById` returns.** Loses the `resting()`
  result that decides whether §4.2's "uncovered" report fires, and reorders
  the restore relative to the refusal reporting the spec `053` comment
  explicitly placed it after.
- **Re-implement the placement inside `restoreCloseAfterRefusal`.** Duplicates
  `placeOrders`. `getTPOrder` + `placeOrders` is the pair that sizes every
  other close in the engine; a second copy is a defect, not a fix.

## 2. Build order

1. `core/src/bot/dcaHelper.ts` — split `placeOrders` (guard + body).
2. `core/src/bot/dcaHelper.ts` — point `restoreCloseAfterRefusal` at the body.
3. `core/src/bot/dca/refusedCloseRestore.harness.spec.ts` — the spec `053`
   harness stubs the restore's seam, so its override moves with the seam.
4. `core/src/bot/dca/refusedCloseDeadlock.harness.spec.ts` — new.
5. Version + changelog in `core` and in the parent.

No parent-repo source change: the defect is entirely inside `core/`.

## 3. Blast Radius

1. **Other call sites.** `placeOrders` has 17 call sites across `dcaHelper.ts`
   and `comboHelper.ts` and one definition; no override anywhere. All of them
   keep calling the decorated wrapper, whose signature, name, return type and
   lock key are unchanged. Only `restoreCloseAfterRefusal` moves.
2. **`core/` submodule.** Yes — this is `main-app-sh`, shared code deployed
   platform-wide (cloud + self-hosted). The parent's pointer must be bumped
   deliberately. The changed method is internal to the DCA/combo engine: it is
   not an exported type, a GraphQL shape, a socket event, a queue payload or a
   Mongo field, so it crosses none of the Danger List contracts.
3. **Contracts in `CLAUDE.md`.** None touched. `placeOrdersHoldingDealLock` is
   `protected`, so it is not part of any external surface.
4. **Other tests on this path.** The whole spec `053` suite
   (`refusedCloseRestore.harness.spec.ts`, 12 tests) exercises the same
   `closeDealById` refusal branch and must stay green — it is the regression
   guard for the issue this fix must not undo. Full core suite: 962 tests.

**Restart risk.** Shipping restarts the bot engines. A bot whose deal lock is
currently deadlocked is *freed* by that restart, which is the same relief a
reload gives today — so the restart is part of the remedy, not a risk to it.

## 4. Traceability

| Spec section | Test |
|---|---|
| §4.1 restore completes inside the deal lock | `refusedCloseDeadlock.harness.spec.ts` → "closeDealById returns after the restore", "really enters the placeOrders body…", "releases the deal lock…" |
| §4.2 other callers unchanged | `refusedCloseRestore.harness.spec.ts` (12 tests, unchanged assertions) + full core suite |
| §4.3 a stop reaching a refused close completes | `refusedCloseDeadlock.harness.spec.ts` → "stop() returns and writes the bot closed" |

## 5. Gate 4 — plan vs spec

Every spec section appears above. The plan decides only what the spec left
open (which of the four candidate mechanisms to use for the fix). It fixes the
cause the Assumption names — the self-deadlock — not the symptom (the bot not
stopping), and it does not weaken spec `053`: the restore still runs, with the
same sizing, the same guards and the same ordering, which §4 of that spec's
own harness re-verifies.
