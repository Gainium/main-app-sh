# 207 — plan

## Solution

In `_runUnknownOrderLadder`'s status-change branch (`src/bot/main.ts`), derive
`executedQty` from the venue's answer (`request.data`) through the existing
`convertOrderExecutedQty`, and take the venue's `cummulativeQuoteQty` through
the existing `convertOrderQuoteQty`. Both are the conversions the
`getOrder` reconcile wrapper already applies to the same venue shape, so no new
helper. Kept local:

- `price` — Binance's `GET /api/v3/order` answers `0` for a market order;
- the whole old reading when the venue states no fill size (§4.2), because the
  FILLED → `origQty` fallback inside `convertOrderExecutedQty` would otherwise
  run on venue units for contract-sized venues;
- `cummulativeQuoteQty` on KuCoin futures, whose venue value the reconcile
  wrapper rebuilds rather than trusts.

JIT tier 0: one assignment in place; the ladder is legacy but the defect is a
single wrong argument.

## Blast radius

- Call sites: every caller of `_handleUnknownOrder` — the cancel paths
  ("unknown order", "cancel in progress", refused teardown cancel) and the two
  reconcile callers. All bot types (DCA, Combo, Grid) go through it. Behaviour
  changes only when the venue reports a different status AND a positive fill
  size; the recorded size then matches the venue instead of the last stream
  event. A genuinely partial fill is still recorded as partial (§4.4), so the
  spec `157` remainder sweep is unchanged for it.
- `core/` submodule: yes, the parent pointer has to be bumped.
- Contracts: none. Same `orders` fields and statuses, no schema, GraphQL or
  socket change.
- Tests that must stay green: `neverPlacedCoinbaseOrder`,
  `cancelDuringPlacement`, `limitOnlyCloseRemainder`, `closeAfterSweptTpFill`,
  the full `npm test`.
