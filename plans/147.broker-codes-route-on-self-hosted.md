# 147 — plan: the self-hosted API serves the broker-codes feed

## Build order
1. `src/server/brokerCodes.ts`: `brokerCodesHandler(req, res)`. It reads
   `brokerCodesDb` with the projection `{ exchange, code, zone }` and no `_id`,
   and applies the `v=2` zone filter. Kept out of `index.ts` so it can be
   tested without booting the server.
2. `src/server/index.ts`: `app.get('/broker-codes', apiLimiter, brokerCodesHandler)`
   next to the other public GETs (`/tickers`, `/candles`), before the `/` GraphQL
   mount.
3. Test: `src/server/brokerCodes.spec.ts`.

## Decisions left open by the spec
- Rate limiter: the existing `apiLimiter` (50/min per client IP). The dashboard
  calls the route once per wallet setup. The hosted API's licence limiter does
  not exist on this server.
- Response shape: the same as the hosted API's route, so the dashboard and any
  instance that reads one or the other see one shape.

## JIT extraction tier
None. This is a new handler, not legacy code being pulled apart.

## Blast Radius
1. Call sites: the only reader is the dashboard's Hyperliquid setup
   (`completeHyperliquidSetup`). This server previously answered the path with
   a GraphQL 400, so no client could depend on it.
2. `core/` is shared: the private parent repository builds against this
   submodule, but its server entry is its own `src/server/index.ts`, which
   registers its own `/broker-codes`. It does not import this file, so the
   route is not registered twice.
3. Contracts: the new public GET route matches the hosted API's existing shape.
   No GraphQL, socket, queue or collection-schema change. The route is read-only.
4. Other tests: none exercise `server/index.ts` routes. The server suite
   (`clientIp.spec.ts`) must stay green.
