# Plan 201 — A venue cancel-all leaves a grid bot trading nothing

## Build order

1. `src/bot/gridVenueCancelReplace.spec.ts` (red: no `onCanceled` on the grid bot).
2. `src/bot/helper.ts`:
   - `processCanceledOrder(order, updateTime, expired)` registered as
     `cbFunctions.onCanceled`; filters (§4.1) and queues the order in
     `venueCanceledLevels` (in memory, keyed by client order id).
   - `scheduleCanceledLevels(botId)`: `@RunWithDelay` per bot, 2 s (§4.2).
   - `placeCanceledLevels(botId)`: `@IdMute(mutex, botId)` (the key
     `limitOrders` holds), drains the queue and places each still-wanted level
     through `placeRegularOrder(mapOrderToGrid(o))`, as `checkOrders` does.
3. CHANGELOG + patch bump (1.116.1).

## Decisions the spec left open

- **Rested vs refused** reuses spec 179's `combo/gridCancelRested.ts`
  (`wasRestingWhenCanceled`, 60 s) instead of a grid copy: the same venue
  behaviour and the same timestamps.
- **The level is matched against the ladder by side, price, quantity** using
  `origPrice` (the grid price written at placement, `mapGridToOrder`). The
  cancel report's `price` is the venue's, which is the same value for an
  unfilled LIMIT, but `origPrice` is the one that cannot drift.
- **Placement is sequential**, as `checkOrders` places its cancelled orders on
  a restart. The batched venue path of `limitOrders` (spec 082) is not reused:
  it is woven into `limitOrders`' own loop and progress reporting.
- **The pass is not awaited by the order queue.** `onCanceled` only queues and
  schedules, so the user stream is not held while 78 orders are placed.

## JIT extraction tier

Tier 0 for `helper.ts`: the new methods are small orchestration over existing
engine calls, and the one decision with real logic (rested vs refused) is
already a pure module (spec 179). No legacy code on the path is rewritten.

## Blast Radius

1. Call sites: `cbFunctions` is consumed by `processOrderQueue` only
   (`main.ts`); it already calls `onCanceled` for DCA and combo bots. Combo
   and DCA have their own `processCanceledOrder`; `helper.ts`'s
   `createBotHelper` is the grid mixin and is not a base of either, so their
   callbacks are unchanged. Hedge/combo specs that stub `cbFunctions` are
   unaffected.
2. `core/` submodule (`main-app-sh`): shared code, deployed to every bot
   worker. Parent pointer bump needed.
3. No GraphQL, socket, queue or DB shape change. New log lines only.
4. Other grid specs (`grid*.spec.ts`) build the helper with stubs and must
   stay green; run them.
