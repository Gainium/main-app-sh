# 005 — Plan: reconcile an open deal against the venue's position list

Spec: `specs/005.zombie-deal-venue-position-reconciliation.md`.

## Solution

Fix the root cause the spec's §3 Assumption names — the missing path — by
adding one, at the only place that already knows "this deal wanted to close and
could not": the `!closeInFlight` tail of `checkTPLevel`.

When a take-profit close leaves nothing in flight on a **futures** deal, ask
the venue for its positions. Three outcomes:

| venue answer | action |
|---|---|
| call failed / not `ok` | do nothing — fall through to the existing behaviour |
| a matching non-zero position exists | clear the probe cooldown, fall through |
| no matching position, first reading | log, wait for the next window |
| no matching position, second reading | log, raise a deal warning, `closeDeal(botId, dealId)` |

`closeDeal(_botId, dealId)` with no `tpOrder` and no `liquidationPrice` is the
existing "Close without TP order" primitive (`dcaHelper.ts:2516`) — the same one
`closeDealById` already uses for this exact condition at `dcaHelper.ts:6006`.
It books `status: closed`, settles the P&L the filled targets already realised,
and runs `processDealClose`. Reusing it is why this change adds no accounting.

### Why not key on the refusal text

Spec §2.3: the loop running in production today never reaches the venue, so it
never gets a refusal. A guard hung off `terminalRejection` would leave exactly
the deals this issue is about untouched. Driving it from "nothing in flight"
covers both shapes.

### Rate limiting

A positions round trip must not ride the price tick. Gate it on a dedicated
`RetryBackoff` (`namespace: 'dpp'`, 5 min → 1 h). Reused deliberately: it is
Redis-backed, so the window survives a PM2 worker restart and is shared across
the per-bot-type workers, which an in-process map is not.

`record()` is called for the *probe*, not for a venue rejection. That is a
departure from the "only real rejections extend the window" note in
`retryBackoff.ts`, and is safe here for the opposite reason that note gives:
the window is not gating an order, and a successful probe that finds the
position calls `clear()`, so it does self-heal.

Worst case cost: one `futures_getPositions(symbol)` per deal per 5 min, and
only for deals sitting at a take-profit level they cannot close.

### Two agreeing readings before closing

`record()` already returns the consecutive `attempt` count, so requiring
`attempt >= 2` costs one condition and removes the only plausible false
positive: a venue answering `{status: ok, data: []}` during an outage. The
asymmetry is the whole argument — a deal whose position is genuinely gone has
been gone for months and loses nothing by waiting one more window, whereas
closing a deal whose position is still open abandons it with no take profit and
no stop loss. Finding the position calls `clear()`, which resets the count, so
this cannot accumulate across unrelated windows.

## Contract decisions the spec left open

- **Side matching.** Mirror `BotInstance.loadData` (`main.ts:3678-3690`)
  verbatim, including its `BOTH` → sign mapping and its "only apply the side
  test under `hedge`" rule. A second, differently-worded matcher is how the two
  answers drift.
- **Spot deals are excluded.** Guarded on `this.futures`; spot has no positions
  to reconcile against and `futures_getPositions` is meaningless there.
- **Fail-safe direction.** An unavailable venue answer must never close a deal.
  Booking a deal closed while the position is in fact still open would abandon
  a live position — strictly worse than the bug. Encoded as a distinct
  `kind: 'unavailable'` in the pure module rather than an empty array, so
  "call failed" cannot be confused with "no positions".
- **No new `DCACloseTriggerEnum` member.** The precedent at `dcaHelper.ts:6006`
  closes without one; the reason is carried by the log line and the deal event.

## JIT extraction tier

**Tier 2** (runbook) for the new logic: the decision is pure and goes in its own
tested module, `core/src/bot/dca/positionReconcile.ts`, next to its five
siblings (`tpCloseOutcome`, `dealOutcome`, `partialTp`, `tpFees`,
`baseOrderQty`). Not Tier 3 — no ports/adapters on a legacy bug touch. Not
Tier 1 — the judgement genuinely has no I/O in it.

`main.ts:3678` and `main.ts:3783` inline the same position lookup and are **not**
refactored onto the new helper: they are outside the causal path (bot start, not
deal close) and rewriting them is scope creep on a live trading engine. Noted,
not done.

## Blast radius

1. **Other call sites.** `checkTPLevel` is called from `priceUpdateCallback`
   (`dcaHelper.ts:17984`) and `checkDealsForTPLevelCheck`. The insert is inside
   the `!closeInFlight` branch, after `closeByTp` is already released, and
   `continue`s only on the close path — every existing ending is preserved.
2. **`core/` submodule.** Yes — this is `main-app-sh`, shared and deployed
   platform-wide. The new file is additive; the `dcaHelper.ts` edit is confined
   to the DCA take-profit path.
3. **Cross-service contracts (root Danger List).** None touched. No GraphQL, no
   REST, no socket event names, no RabbitMQ queue, no shared Mongo schema field
   is added or changed. `futures_getPositions` is *consumed*, not altered.
   `botEventDb.createData` is used with the shape the sibling call 30 lines
   above already uses.
4. **Restarting bot workers.** Shipping this restarts live trading engines. The
   change is inert until a deal reaches a take-profit level it cannot close.
