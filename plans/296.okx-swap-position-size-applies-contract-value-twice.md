# Plan 296 — OKX USDT-swap open positions apply the contract value twice

## Build order
1. core `src/graphql/handlers/orders.handler.ts`: export `okxContractValue`
   and `okxLinearCloseContracts`; in `getAllOpenPositions` skip the
   step-denominator division when the contract value is not 1 (it was already
   applied as `× baseAsset.multiplier`).
2. core `src/graphql/resolvers.ts` and main-app `src/graphql/resolvers.ts`
   (which overrides core's `closePositionOnExchange`): convert with
   `okxLinearCloseContracts`.
3. Parent picks up the core pointer at push time (`psh`).

## Decisions
- The close conversion uses the engine's `getOKXDenominator` rule, not a new
  one. Checked against every live OKX linear instrument (global SWAP + EU
  X-Perp, all contract values are powers of ten): read = pos × ctVal and close
  = pos exactly.
- §1.3: pairs with contract value 1 keep the old arithmetic bit-for-bit, so the
  helper falls back to the step-denominator conversion for them.
- Tier: none of the JIT extraction tiers beyond pulling the duplicated
  conversion into one exported pure function the two resolvers share.

## Blast Radius
1. Call sites: `getAllOpenPositions` (positions query, both resolvers'
   `closePositionOnExchange`, the import-position resolvers) — only the
   `okxLinear` branch changes. The step-denominator expression is otherwise
   only in the bot engine (`getOKXDenominator`), untouched.
2. core/ submodule: yes — shared with self-hosted.
3. Contracts: GraphQL response shape unchanged; only the `quantity` value for
   `okxLinear` pairs with contract value ≠ 1.
4. Other tests: `orders.handler.failedVenue.spec.ts`,
   `orders.handler.deadline.spec.ts` stay green.
