# 189 — Plan: a grid take-profit close sells again while the bot is stopping

Spec: `specs/189.a-grid-take-profit-close-sells-again-while-it-stops.md`.

## Solution

Latch the close in `BotHelper.closeBotByTp` (`src/bot/helper.ts`), right after
the exchange-info check:

- return when `this.stopFilled` — the closing order has filled (any path);
- return when no `oldTpSl` was passed and `this.blockLimit` is set — a fresh
  trigger arriving after a close (or a stop) already started.

And make every path that books the closing fill set `stopFilled`: the
placement reply's FILLED branch in `closeBotByTp`, and `processFilledStop`
(which `processSellAtStop`'s reply reaches without passing through
`processFilledOrder`). `processSellAtStop` already guards on `stopFilled`, so
both close entry points now share one latch.

Re-entries with `oldTpSl` (the LIMIT reposition and enter-market timers) still
run while the close order is resting, so the single normal close is unchanged
(§1.3). `blockLimit` and `stopFilled` are both reset by
`clearClassProperties` on start, so a restarted bot triggers again.

This fixes the cause the Assumption names: a queued trigger having no latch.
It deliberately does NOT carry `currentBalances` into memory after the close:
both the stream delivery and the placement reply compute the same absolute
`$set` from the unchanged in-memory value, which makes the duplicate write
idempotent today. Carrying it into memory would make the second of the two
subtract the sale twice. With the latch, no code path re-reads those balances
for a sale after the close. `sellBaseAmount()` already caps the quantity at
`currentBalances.base` (+ fee balance) — the brief's cap holds once the
latch stops the re-entry.

JIT tier: **0**. One guard on a live trading path; extraction would widen the
diff for no gain.

## Blast radius

1. Call sites: `closeBotByTp` ← `priceUpdateCallback` (fresh trigger) and its
   own `limitTimer` / `enterMarketTimer` (with `oldTpSl`). `stopFilled` is read
   only by `processSellAtStop` and now `closeBotByTp`; `blockLimit` by
   `placeOrders`' grid generation and now `closeBotByTp`.
2. `core/` submodule — grid bot workers on cloud and self-hosted. DCA/Combo do
   not use this method.
3. No GraphQL / REST / socket / queue / collection shape changes.
4. Tests on this method that must stay green: `gridStopAndSellFlatPosition`,
   `gridCloseProfitLedger`, plus the full core suite.

## Amendment — spec §6

The Solution above assumed `clearClassProperties` reset the latch "on start".
It reset it on every call, and `stop()` ends in `clearClassProperties(true)`.
And the cloud application overrides `closeBotByTp` / `priceUpdateCallback`
wholesale, so the latch above never ran in production.

- `clearClassProperties`: reset `stopFilled` / `blockLimit` inside the
  `if (start)` branch only. Both are read only by the grid helper
  (`processSellAtStop`, `placeOrders`' queue, `closeBotByTp`); a stopped bot
  keeping `blockLimit` set refuses queued grid placements, which is what a
  stopped bot should do. Every start path (`start()`, `reloadBot()` →
  `start(true)`) passes `start = true`.
- `closeBotByTp`: also return when `this.data.status` is `closed`.
- `priceUpdateCallback`: return before any check when `stopFilled` or the bot
  is `closed`.
- `stopFilled` becomes `protected` so the cloud override can read it.
- The cloud override (`main-app/src/bot/helper.ts`) gets the same latch, the
  same `closed` guard, sets `stopFilled` on its placement reply's FILLED
  branch, and the same `priceUpdateCallback` guard.

Unchanged: the closing order's size and type, and the `oldTpSl` re-entries of
a resting close (the `blockLimit` arm only refuses fresh triggers).
