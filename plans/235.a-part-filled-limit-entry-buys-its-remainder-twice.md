# 235 — plan: one owner for a part-filled base entry's remainder

Spec: `specs/235.a-part-filled-limit-entry-buys-its-remainder-twice.md`.

## Build order

1. Red tests: `src/bot/dca/limitEntryNoMarketTopUp.harness.spec.ts`, the real
   `dcaHelper` mixin over the real `MainBot`, venue stubbed.
2. `MainBot.remainderMayGoToMarket(order)` (default `true`), asked by
   `buyRemainder` once it has decided an order is short, before it marks the
   order in `partiallyFilledFilledSet`.
3. `dcaHelper` overrides it: a non-combo `dealStart` asks
   `baseEntryMayEnterAtMarket(getAggregatedSettings(deal))`, the same question
   the settle path (`topUpSettledBaseEntry`) and spec `111` already ask.
4. `restBaseEntryRemainder` returns early when `partiallyFilledFilledSet` holds
   the entry: a remainder `buyRemainder` already sent is never rested again.

## Decisions the spec left open

- A hook on the base class, not a `botType` check inside `buyRemainder`, so that
  `MainBot` does not learn DCA entry settings. This is the same shape as
  `allowToProcessBr`.
- The gate covers every caller (user stream, placement answer,
  `completeFilledBaseEntry`, the settle) because it sits in `buyRemainder`.

## Blast radius

`core/` (main-app-sh), so every main-app consumer. Behaviour changes only for a
non-combo DCA/hedge base entry on a bot whose LIMIT entry has the Enter Market
Timeout off. There the remainder is now only rested (spec `111`). Two knock-on
effects: such a bot's `remainderFullAmount` raise-to-minimum no longer fires for
the base entry, and a contract-sized account's stream-`FILLED`-short entry gets
spec 111's "reported as filled" notice instead of a market buy. No schema,
GraphQL, socket or Redis contract is touched.
