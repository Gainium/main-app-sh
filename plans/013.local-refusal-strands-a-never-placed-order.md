## §2 Contract decisions the spec left open

- **Delete, not mark CANCELED.** Both clear the symptom. Marking `CANCELED`
  restores the exact pre-`3f7ae42` behaviour but reinstates the row bloat that
  commit was trying to kill (§1.3). Deleting satisfies both goals at once and is
  what the triage brief asked for.
- **`deleteManyData`, not `deleteData`.** `clientOrderId` is uniquely indexed so
  the filter can only ever match one row, and `deleteData` reports a no-match as
  `'Server error'` — which is the NORMAL outcome here whenever the row has
  legitimately moved on (§4.4). Using it would emit a bot error on the healthy
  path.
- **Filter shape.** `{ clientOrderId, status: 'NEW', orderId: noExchangeOrderId }`
  rather than `{ clientOrderId }` alone. This is what makes §4.4 structural
  rather than an argument about ordering.
- **Migration bounds.** Floored at the `3f7ae42` rollout instant
  (2026-08-06T07:37Z) so the pre-existing phantom population is left to spec 011,
  and ceilinged at `now - 24h` so a placement genuinely in flight — which wears
  this same shape for a few seconds — can never be caught.

## §3 Blast Radius

1. **Other call sites.** `deleteOrderFromDb` is new; it has exactly one caller.
   The `else` branch is reachable only when one of the three short-circuit flags
   is set, all three of which are local `let`s scoped inside
   `sendOrderToExchange` — no other method can enter this branch.
   `updateOrderOnDb`'s own behaviour is untouched, and `grep` confirms no other
   site deletes order rows, so nothing else changes shape.
2. **`core/` submodule.** YES — `core/src/bot/main.ts` is `main-app-sh`, shared
   code deployed platform-wide (cloud + self-hosted). The submodule pointer must
   be bumped deliberately. The change is additive (one new method, one `else`),
   touches no exported type, so consuming services rebuild unchanged.
3. **Documented contracts** (root `CLAUDE.md` Danger List): **item 12, shared
   Mongo `gainium` collections.** This changes the *population* of the `orders`
   collection, not its schema — no field is added, removed or retyped, so the
   direct readers (legacy `main-dash`, `admin-app`) keep parsing it identically.
   What changes for them is that rows describing orders which never existed stop
   appearing, which is the point. GraphQL, socket.io and the archive queues are
   untouched.
4. **Other tests on this path.** `cancelNoExchangeOrderId.spec.ts` (spec 011)
   exercises the sibling cancel path and must stay green; the full core suite is
   the backstop.

## §5 JIT legacy tier

**Tier 0.** `sendOrderToExchange` is deep legacy — a ~900-line method mixing
decision logic with venue, Redis and Mongo I/O — and it is squarely on the causal
path, so a Tier 1 extraction is arguable. It is declined deliberately: the defect
is one missing statement, the surrounding block is under active repair by three
separate recent commits (`3f7ae42`, `cd279ef`, spec 011), and an extraction here
would collide with that work while enlarging the diff on the single hottest
order-placement path in the platform. The new `deleteOrderFromDb` is itself the
small structural improvement — the DAO verb that was missing is now named and
tested rather than inlined.
