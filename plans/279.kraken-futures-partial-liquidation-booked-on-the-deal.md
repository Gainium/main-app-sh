# 279 — plan: book a Kraken Futures partial liquidation on the deals

Spec: [`specs/279…`](../specs/279.kraken-futures-partial-liquidation-booked-on-the-deal.md).

## Build order

1. Pure rules `src/bot/dca/partialLiquidation.ts`: chunk grouping from fills, booked-chunk ids from
   rows, the deterministic row id, `planPartialLiquidation` (cap, newest first, whole-deal close).
2. `main.ts`: `onLiquidation(order, time, venueQty)`. The chunk's executed quantity is passed and
   the persisted row is unchanged.
3. `dcaHelper.ts`: record chunks during the settle. On settle exhaustion on Kraken USD-M one-way,
   call `bookPartialLiquidation`: read fills, skip booked chunks, plan, write rows, then
   `processFilledOrder`, then the message. Other venues keep the old message.
4. `dcaHelper.ts`: `sweepPartialLiquidations`, armed and stopped by overriding
   `startConsumerHeartbeat` / `stopConsumerHeartbeat`. Every DCA and Combo start path arms that
   heartbeat, the app's own `start()` override included.
5. main-app: pack `specs/279.invariants.json`, migration v60 + test.

## Decisions the spec left open

- The booking path is the reduce-funds fill (spec 047 / DCA `updateDeal` reduce branch), not a new
  ledger type: every reader already counts it. That includes `typeOrder: dealTP` with
  `reduceFundsId`, so no new enum value reaches GraphQL, the dashboards or `loadOrders`.
- The cap is `books − held` (spec §3.2), evaluated on the venue position read the settle already
  makes.
- The idempotency key is the chunk's venue order id, stored in the row's `orderId`.
- The sweep period is 30 min, with the first run 90 s after a start.
- JIT tier: **Tier 2** for the rules (pure module, its own spec). The engine glue stays in the helper
  (Tier 0 for the surrounding legacy methods, which are not restructured).

## Blast Radius

1. **Call sites.** `processLiquidationOrder` is bound as `onLiquidation` for DCA and Combo
   (`dcaHelper.ts`) and Grid (`helper.ts`, its own method). The added optional args do not change
   Grid. `startConsumerHeartbeat` / `stopConsumerHeartbeat` are overridden on the DCA helper only:
   `super` runs first and the sweep is gated to Kraken USD-M one-way, so every other bot keeps an
   identical heartbeat.
2. **`core/`.** All engine files are in `core/` (main-app-sh, public). It is used only by main-app's
   bot workers, and no other service runs the bot engine. The core commit message must stay free of
   issue numbers and user data.
3. **Owned contracts.** No GraphQL, REST, socket, queue or schema change. New `orders` rows use
   existing fields. A `LIQ-` reduce row appears in a deal's orders like a reduce-funds order. The
   dashboards already render those.
4. **Tests that must stay green.** `hedgeLiquidationPair.spec.ts` (liquidation routing),
   `gridFuturesCloseFeeProfit.spec.ts`, `dca/venueCloseEvidence.spec.ts` (spec 277),
   `combo/comboDealFunds*.spec.ts` (spec 047). The full core suite also has to pass.
5. **The stream (websocket-connector-sh).** Already flags `partialLiquidation` (shipped
   2026-11-25). Not changed here. Partial versus full is decided by the venue's position, which is
   stronger evidence than `fill_type`.
