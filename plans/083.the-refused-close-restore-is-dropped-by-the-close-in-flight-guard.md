# 083 — Plan

Spec: [`083`](../specs/083.the-refused-close-restore-is-dropped-by-the-close-in-flight-guard.md).

## 1. Build order

One file, `core/src/bot/dcaHelper.ts`, two edits:

1. **`placeOrdersHoldingDealLock`** gains a fifth, optional parameter
   `opts?: { afterTerminalCloseRefusal?: boolean }`. When it is set, the two
   close-in-flight guards (`closeBySl` at :15067, `closeBySl || closeByTp` at
   :15071) are skipped. Nothing else in the method changes — not
   `allowToPlaceOrders`, not the exchange-info resolution, not the TP re-size
   lookup, not the `isDealForTPLevelCheck` skip.
2. **`restoreCloseAfterRefusal`** passes `{ afterTerminalCloseRefusal: true }`
   on its existing call at :1142.

No new helper. The spec's §4.1 is a *scope* change to an existing guard, so the
right shape is an opt-out on the method that owns it — the same idiom
`cancelOrderOnExchange`'s `promotePartialToFilled: false` opt-out (bug #694)
already uses in this file. Grepped for an existing "this caller is a recovery"
predicate to reuse: there is none; `isTrailingCloseInFlight` answers a different
question (does the DEAL have a persisted retry) and is already consulted
elsewhere.

### Contract decisions the spec left open

- **Opt-out, not flag-clearing.** Settled in spec §4.2 against evidence, not
  left to the plan.
- **Where the opt-out lives.** A fifth parameter on
  `placeOrdersHoldingDealLock` rather than a field on the `orders` bag: the bag
  is shared with `placeOrders`, whose callers must never be able to set this.
  `placeOrdersHoldingDealLock` is `protected` and has exactly two callers, so
  the parameter's reach is closed by the type system.
- **Both guards, not just the first.** `restoreCloseAfterRefusal` cannot know
  which flag its deal carries; §1.3 shows both limbs reach it. The `closeByTp`
  limb is then correctly refused further down by `isDealForTPLevelCheck`
  (§5.2), which the test pins.

## 2. JIT legacy tier

**Tier 0.** The causal path is two guards and one call argument inside a
5,000-line class whose decision logic and I/O are interleaved throughout.
Extracting a pure "may this caller place into this deal?" predicate would mean
moving `allowToPlaceOrders`, `closeBySl`, `closeByTp` and the exchange-info
resolution out together, which is a radius far wider than the line being
touched — the runbook's scope-creep case. Not Tier 1: there is no smell *on the
path being touched* that a named module removes; the guards are already a
two-line, side-effect-free test, and the defect is that one caller was in their
scope and should not be.

## 3. Blast Radius

1. **Other call sites.** `placeOrdersHoldingDealLock` has two:
   `placeOrders` (:14996) and `restoreCloseAfterRefusal` (:1142). Only the
   second passes the opt-out; the first does not and its signature is unchanged,
   so every caller beneath `placeOrders` — the ladder rebuild, the reconnect
   coverage correction, `restoreWork`, comboHelper's callers — is byte-identical.
   The parameter is optional, so nothing else needs touching.
2. **`core/` submodule.** Yes — `main-app-sh`, shared with every consuming
   service and deployed platform-wide. The parent pointer is bumped
   deliberately. `dcaHelper` runs in the DCA/combo bot workers
   (`Gainium-DCA-bot`), which restart separately from `Gainium-main-app`.
3. **Documented cross-service contracts.** None touched. No GraphQL shape, no
   `/api/v2` shape, no socket.io event, no Redis channel, no RabbitMQ queue, no
   Mongo schema field. The only externally visible change is which orders reach
   the venue and the disappearance of a misleading log line.
4. **Other tests on this path.** `tests/processing/tpBurstInvariant.ts` (drives
   the real `placeOrders`/`placeOrdersHoldingDealLock`),
   `tpRePlacePartialFill.ts`, `tpResizeCancelNeverPromotes.ts`,
   `tpUnderfilledSweepsSafetyOrders.ts`, `orderProcessing.ts`,
   `marketEntryNotional376.ts`, `kucoinPriceProtection.ts`,
   `percentFundsBasis.ts`. All must stay green.
5. **Behavioural blast radius in production.** Deals that previously got a
   dropped restore now get a real order sent to the venue — ~1,288 events over
   seven days, 275 deals, 125 bots (spec §2.2). Where the shortfall is real the
   venue refuses it and `handleOrderErrors` reports as it already does for the
   ~1.06M restores that were never dropped; spec `074`'s `uncoveredCloseBackoff`
   bounds the repeat at 5 min → 1 h per deal, so this cannot become a send loop.
   Where the shortfall has cleared, the deal ends up covered — which is the
   entire point of spec `053`.
