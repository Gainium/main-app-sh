# Plan 065 — Paginated v2 listings drop rows on a non-unique sort key

Spec: [`specs/065.paginated-v2-listings-drop-rows-on-a-non-unique-sort-key.md`](../specs/065.paginated-v2-listings-drop-rows-on-a-non-unique-sort-key.md)

## Build order

1. **Append `_id` to all nine paginated v2 sorts** (`src/server/v2/api.ts`).
   `{ asset: 1 }` → `{ asset: 1, _id: 1 }` for balances;
   `{ created: -1 }` → `{ created: -1, _id: -1 }` and
   `{ createTime: -1 }` → `{ createTime: -1, _id: -1 }` for the other eight.
   This is the whole correctness fix — spec §3.

2. **Declare `{ userId: 1, asset: 1, _id: 1 }` on `balancesSchema`**
   (`src/db/schema.ts`). Performance only; it does not change what is
   returned. Kept as a separate step so it can be dropped without touching
   step 1.

3. **Regression test** (`tests/processing/v2PaginationTiebreaker.ts`), driving
   the real handler against in-memory Mongo.

## Contract decisions the spec left open

- **Tiebreaker direction follows the primary key.** `_id: -1` under
  `created: -1` / `createTime: -1`, `_id: 1` under `asset: 1`. Every collection
  involved uses the default ObjectId `_id`, whose high bits are a creation
  timestamp, so descending `_id` inside a `created` tie reads newest-first —
  consistent with the primary key rather than fighting it. (`paperPositions` is
  the only schema with a custom `String _id`; it is not one of these nine.)

- **`_id`, not another field.** It is the only key guaranteed unique and
  present on every one of these collections, and it is already indexed, so it
  adds no storage. A compound tiebreaker on, say, `uuid` would be unique for
  bots but not for balances.

- **No change to `readData`.** `src/db/crud.ts` forwards `options` verbatim;
  making it inject a tiebreaker centrally would silently alter every caller in
  the codebase, including non-paginated single-document reads. The sort belongs
  to the call site that also owns the `skip`/`limit`.

- **Page size and `meta` untouched.** Spec §4 rules both out.

## Blast radius

`src/server/v2/api.ts` is the **public `api.gainium.io` contract** — root
`CLAUDE.md` Danger List item 2. Consumers: both dashboards, `gainium-mcp`,
`n8n-nodes-gainium`, `chrome-extension`.

- **Response shape: unchanged.** Same fields, same `meta` keys, same page size.
  Nothing added, nothing removed, no type changed. A consumer cannot observe
  the difference except by the rows it receives.
- **Ordering: changes only within a tie group**, where it was previously
  undefined and unreproducible between two calls. No consumer can have depended
  on it. Ordering *between* distinct key values is untouched.
- **`src/db/schema.ts` is a shared Mongo schema** — Danger List item 12. The
  change is additive (one index declaration); no field is added, removed or
  retyped, so the legacy dashboard and admin-app, which read these collections
  directly, are unaffected. `models.balance.syncIndexes()` runs at boot
  (`src/db/model.ts`), so the index is built on the deployed collection
  automatically. It is additive and droppable.
- **`core/` is a submodule** shared with every consuming service — but both
  files are main-app-only surfaces (the v2 HTTP API and the Mongo schema), so
  nothing else in the family links to them.
