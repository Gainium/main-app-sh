# 076 — Plan: any string is accepted as an account time zone

Spec: [076](../specs/076.any-string-is-accepted-as-an-account-time-zone.md).

## 1. Solution

Fix the cause the spec's Assumption names — the absence of a resolve test on
the two write paths — not the values already stored.

1. `core/src/utils/index.ts` — add `isValidTimezone(timeZone)`, a `try/catch`
   around `Intl.DateTimeFormat(undefined, { timeZone })`. It lands beside
   `getTimezoneOffset` / `getWeek`, the consumers that degrade to UTC on an
   unresolvable zone (spec §2.2), and it is the same test `createOrUpdateUser`
   has always applied inline (spec §1.1).
2. `core/src/graphql/resolvers.ts` — in `setTimezone` and in `userSettings`,
   before any write: a non-empty `timezone` that fails `isValidTimezone`
   returns `{ status: notok, reason: 'Invalid timezone' }`. Empty/absent is
   untouched, and in `userSettings` the refusal covers the whole call, so a
   settings save never lands half-applied.

**Tier (legacy-extraction ladder): Tier 1.** The predicate becomes a named,
tested helper, but it stays in the shared `utils` bag next to the functions it
guards rather than moving to a new pure module — the call sites are two guard
clauses inside a 7k-line resolver file, and cutting a deeper seam there is not
on this bug's causal path.

**Not done here:** repairing the values already stored (a data change), and
rewiring `createOrUpdateUser`'s inline copy of the test — the signup path
coerces to `UTC` rather than refusing, which is right for a browser-detected
value, and it is not on this bug's path.

## 2. Blast radius

1. **Other call sites.** `setTimezone` and `userSettings` are the only
   resolvers that write `users.timezone` after signup; the signup/magic-link
   paths write through `createOrUpdateUser`, which already guards. Nothing
   else in `core/` or in the parent repo sets the field. The parent's
   `src/graphql/resolvers.ts` spreads `...coreResolvers.Mutation` and does
   **not** override either mutation, so these bodies are what cloud runs.
2. **`core/` submodule.** Both files are shared code (Danger List #11): the
   change ships to self-hosted as well as cloud. It is additive — one new
   exported helper, two guard clauses — and changes no exported shape.
3. **Contracts.** The GraphQL schema is untouched: `setTimezoneResponse` and
   `userSettingsResponse` already carry `{ status, reason }`, so the refusal
   uses the existing envelope. What narrows is which inputs are *accepted*, so
   the clients were checked:
   - V2 (`main-dash-redesign`, `core/src/pages/Settings.tsx` +
     `useUserSettings.ts`) sends only values from its picker and surfaces
     `reason` as a toast on a non-OK status — the refusal is visible, not
     silent.
   - V1 (`main-dash`, `pages/settings.tsx`) sends only list values.
   - A direct GraphQL caller sending an unresolvable zone is exactly the case
     this change is meant to refuse.
   Aliases the dashboards legitimately send and store — `Asia/Calcutta`,
   `UTC`, `Europe/Kiev`, `Etc/GMT±N` — must keep saving, which is why the
   check is a resolve test and not `Intl.supportedValuesOf` (spec §2.3).
4. **Other tests on this path.** `tests/coreAuthResolvers.ts` and
   `tests/user.ts` drive the same resolver factory and must stay green.
