# 034 — plan: enough additions report an untouched ladder as fully spent

Spec: [`specs/034.additions-can-report-a-ladder-as-spent.md`](../specs/034.additions-can-report-a-ladder-as-spent.md)

## 1. Solution

Add `remainingLadderLevels(deal, ladderSize)` to
`src/bot/dca/ladderLevels.ts` — `ladderSize - (nextLadderLevel(deal) - 1)`,
built on the function spec `031` already provides — and replace the counter
comparison in `updateUsage`:

```ts
const settings = await this.getAggregatedSettings(findDeal.deal)
const ladderSize = settings.useDca ? this.dcaLadderSize(settings) : 0
if (
  findDeal.deal.levels.complete > 0 &&
  remainingLadderLevels(findDeal.deal, ladderSize) <= 0
) { …cap… }
```

`settings.useDca` is consulted because `dcaLadderSize` does not: it reports
`ordersCount` whether or not DCA is switched on, and §4.3 needs a
DCA-off deal to cap the moment its base order fills, which is what
`levels.all === 1` achieves today.

### 1.1 Equivalence on the case that must not move (§4.4)

With no additions, `nextLadderLevel(deal) - 1` is `levels.complete - 1`, and
`levels.all` is `ladderSize + 1` — set that way by `openNewDeal` and rebuilt
that way by `updateDeal`. So `complete === all` ⟺ `complete - 1 === ladderSize`
⟺ `remaining === 0`. Identical, on every `dcaCondition`, except where §4.6
applies.

### 1.2 Scope: DCA only

`comboHelper` **overrides** `updateUsage` in full and never calls `super`, so
this change cannot reach a combo deal. That is what makes using
`dcaLadderSize` safe here — it has no combo semantics to get wrong.

### 1.3 Extraction tier

**Tier 2**, same module and idiom as `031`/`033`: an arithmetic decision
inlined in a 200-line method that also reads balances, rates and leverage,
coming out pure.

## 3. Blast Radius

**1. Other call sites.** One: `dcaHelper.updateUsage`. `remainingLadderLevels`
is new. `nextLadderLevel` gains a caller and does not change.

**2. Is it under `core/`?** Yes — `main-app-sh`, public, deployed
platform-wide. Pointer bumped deliberately; no issue ids or user detail in the
commit message.

**3. Documented cross-service contracts.** None directly, but note what
`usage` feeds: it is aggregated into bot-level usage (`dcaHelper.ts:9824`) and
read by the backtest reporter (`main-app/src/backtest/process/main.ts`), and it
is a persisted deal field both dashboards render. The SHAPE does not change;
values change only for deals that have taken add funds, which is the defect.
No trading decision was found reading `usage.max` — it is a reporting quantity.

**4. Other tests that must stay green.** `npm test` in full. Nothing currently
drives `updateUsage`; `ladderLevels.spec.ts` must keep all its existing cases.

**5. What this deliberately does not do.** `getDealDCALevelToCheck` — surveyed,
found unreachable, left alone with the reasoning recorded in spec §5 so the
next survey does not re-raise it.
