# 159 — plan

Spec: `specs/159.canceled-reduce-funds-stays-pending.md`.

## Solution

All in `src/bot/dcaHelper.ts`.

1. `processCanceledOrder`: a `dealTP` with `reduceFundsId` goes first to the
   new `settleCanceledReduceFunds`; when that handles it, the ordinary
   take-profit handling (partial into `tpHistory`, spec 095 restore) is skipped.
2. `settleCanceledReduceFunds(order)`:
   - deal not open → not handled (falls through, as before);
   - entry still pending AND `isOwnCancel` → not handled (§1.4, spec 110 re-send);
   - executed > 0 with a usable `updateTime` → `updateDeal(order)`. Its
     existing dealTP/`isReduce` branch is the FILLED path: drops the entry,
     `bookReduceFundsFill` with the executed qty, books the P&L of the
     executed part, removes the order from `tpHistory`, re-builds and re-places
     the close. Executed qty and price are read from the order, so a CANCELED
     order with fills is booked exactly as a fill of that size.
   - nothing executed and entry pending → `dropCanceledReduceFunds`: under the
     deal's `update` mutex, filter the entry, re-build current orders and
     `placeOrders` the diff (the same steps the FILLED reduce branch takes).
3. `updatePartiallyFilledTP`: skip a reduce order that `updateDeal` has
   already processed (`dealUpdateOrders`), so a late PARTIALLY_FILLED event
   cannot re-add the partial to `tpHistory` (§3.5).
4. `cancelTerminalDealOrder`: filter `pendingReduceFunds` by
   `order.reduceFundsId` (was `addFundsId`).

JIT tier 0: the decision is three branches inside the existing orchestrator,
reusing `updateDeal` and `bookReduceFundsFill`; nothing new to extract.

## Decisions the spec left open

- A venue-cancelled reduce is not re-sent. The user's request is gone from the
  exchange; re-placing it would be a trade the venue refused. The executed
  part stands as a reduce.
- `updateDeal`'s dedupe (`dealUpdateOrders`, keyed by clientOrderId) makes
  booking idempotent if a FILLED promotion of the same order also arrives.

## Blast Radius

- Call sites: `processCanceledOrder` is the `onCanceled` callback of DCA bots
  (combo overrides its own). `updateDeal` already handled reduce orders;
  `cancelTerminalDealOrder` is the user's per-order cancel.
- `core/` (main-app-sh): shared, deployed to the bot workers. Parent pointer
  bump needed at ship.
- No GraphQL/REST shape, socket event, queue or schema change. Deal fields
  written (`pendingReduceFunds`, `reduceFunds`, `size`, `tpHistory`, profit)
  are the ones the FILLED reduce path already writes.
- Tests that must stay green: `pendingFundsResend.harness.spec.ts` (spec 110),
  `reduceFundsFill.spec.ts`, `tpSizingAfterPartialTp.harness.spec.ts`,
  `canceledTpRestore.harness.spec.ts`, the rest of `src/bot/**`.
