# 040 — plan

## 1. Build order

1. `src/bot/dca/liquidationDealLink.ts` — the pure rule: which deals a
   liquidation ended (§4.4) and what has to be written for each (§4.2).
2. `src/bot/dca/liquidationDealLink.spec.ts` — pure tests, plus the mixin
   harness driving the real `processLiquidationOrder` (repo idiom, copied from
   `unactionedClose.harness.spec.ts`).
3. `src/bot/dcaHelper.ts` — capture the open deals before the close, and call
   the new `linkLiquidationOrderToDeals` after it.
4. Version bump + changelog in `core` and in the parent, per the repo's
   ceremony.

## 2. Contract decisions the spec left open

- **The write is a `dealId` stamp on the existing row, not a new order.**
  `MainBot` has already persisted the liquidation by the time DCA sees it
  (`processOrderQueue` awaits `saveOrderToDb` before calling `onLiquidation`),
  so the row is there to be claimed. `clientOrderId` is uniquely indexed, so
  the filter is that alone.
- **Reuse over new helpers.** The copy path calls the existing
  `MainBot.saveOrderToDb`, which already stamps `paperContext` and `leverage`;
  the claim path calls `ordersDb.updateData(filter, update, false, true)`, the
  same shape `updateOrderOnDb` uses. No new persistence helper.
- **JIT tier: 1 → 2.** The rule is extracted fully pure (no DB client, no
  framework import) into `dca/`, alongside the existing `dealOutcome.ts`,
  `executedFill.ts`, `ladderLevels.ts`. The I/O stays in the helper method.
  Tier 3 is not warranted for a bug touch.

## 3. Blast radius

1. **Other call sites.** `processLiquidationOrder` is defined once, in
   `dcaHelper`, and wired as the `onLiquidation` callback in `helper.ts:198`.
   Combo inherits the same helper; grid has its own path and is untouched. The
   new method is called from exactly one place.
2. **`core/` submodule.** Yes — `main-app-sh`, shared platform-wide. The change
   is additive (one new module, one new method, three lines inside an existing
   one); no exported type or signature changes, so nothing that embeds `core/`
   has to change with it. The parent pointer is bumped deliberately.
3. **Contracts this repo owns.** None touched. No GraphQL shape, no socket
   event, no REST route, no queue payload. The only shared surface is the
   `orders` Mongo collection — and only a field that the schema already
   defines and the collection already carries on every other order type.
   Consumers that read `orders` directly (legacy `main-dash`, `admin-app`) see
   a liquidation row that now names its deal; none of them filter liquidation
   rows OUT by the absence of a `dealId`.
4. **Who now sees the row, and who still does not.** Checked each reader:
   - `Bot.getDealOrders` (`{ dealId, botId, status: 'FILLED', typeOrder != br }`)
     — the intended change; the row is returned and the V2 chart draws a close
     marker from it. `mapOrderName` already renders `liquidation` as
     *Liquidation order*, so no dashboard change is needed.
   - `MainBot.loadOrders` and `dcaHelper`'s order load — both filter
     `typeOrder: { $nin: [liquidation, br] }`; the row still never reaches the
     in-memory order map, with or without a `dealId`.
   - `mergeDeals` (`dcaHelper`) — filters `typeOrder` to
     `dealStart|dealRegular|dealTP`. Unaffected.
   - `sellRemainder`'s fee sum (`dcaHelper`) — filters
     `side: BUY` for a long (SELL for a short); a liquidation is always the
     opposite side. Unaffected.
   - `closeDeal`'s `dealOrders` — reads the in-memory map and filters
     `executedQty > 0`. Doubly unaffected, and §4.3 keeps the quantities `'0'`
     so it stays that way.
5. **Tests that must stay green.** The whole `core` spec suite (708 cases),
   `unactionedClose.harness.spec.ts` in particular — it drives the same
   `dcaHelper` mixin.
