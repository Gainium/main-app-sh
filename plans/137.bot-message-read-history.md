# 137 — plan: read bot messages stay in a searchable history

## Build order

1. `main-app-sh` (this repo): schema fields + indexes, handler
   (`getBotMessage` view, `markBotMessageRead`), GraphQL contract.
2. Parent `main-app`: bump the `core` pointer. Deploy **before** the dashboard
   — the dashboard selects `isRead`/`readAt` and sends `view`, which an older
   API rejects (400 on the whole feed).
3. `main-dash-sh` + `main-dash-redesign`: query builders, `useNotifications`
   uses `markBotMessageRead` and a bot view, panel gets Unread / All / Read.

## Decisions the spec left open

- §4.1 Mark-all is **not** context-scoped — parity with today's dismiss-all.
- §4.2 New index `{userId, showUser, paperContext, isDeleted, isRead,
  created:-1}` (`botMessageFeedByRead`). Every view constrains `isRead` as a
  point-set (`$in`), so the index bounds it exactly and `created` still comes
  from the index via SORT_MERGE. The existing 5-field feed index becomes
  redundant for the feed; it is left in place (dropping an index is a separate
  prod operation).
- §2.6 TTL is a plain `{readAt: 1}` index with `expireAfterSeconds` 90d
  (`botMessageReadHistoryTtl`). A TTL index only expires documents whose field
  is a date, so unread rows (no `readAt`) are never touched. No backfill: no
  existing row has `readAt`, so the index reaps nothing on build.
- Legacy `unreadOnly: false` keeps matching deleted rows too (§2.3), and now
  also read rows (`isRead` any).

## Blast radius

1. Callers of `getBotMessage`: only the `getMessageBot` resolver. Callers of
   the feed with no input / `unreadOnly: true`: both dashboards' bell; their
   result now excludes read rows — which only exist once a client calls
   `markBotMessageRead`, so legacy V1 is unaffected until then, and after it
   correctly treats read rows as not unread.
2. `core/` is the shared `main-app-sh` submodule — ships to cloud and
   self-hosted. The new indexes are built by `syncIndexes()` on boot.
3. Contract: GraphQL schema (Danger List #3) — additive only (new optional
   input field, new output fields, new mutation). Shared Mongo collection
   `botMessages` (#12): admin-app reads it fleet-wide by `time`; new fields are
   additive.
4. Coalescing: `processError` upserts on `botMessageCoalesceKey`; read rows
   have no `bucket`, so they are outside it (§2.5) — same mechanism the
   dismiss already relies on. `perContractBotMessage.spec.ts` and
   `botMessageSymbolMove.spec.ts` stay green.

JIT tier: Tier 1 — the filter construction is pulled into a named exported
function (`botMessageFeedFilter`) so the view rules are tested without a DB.
