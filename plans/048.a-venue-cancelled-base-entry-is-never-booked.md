# 048 — Plan

Spec: `specs/048.a-venue-cancelled-base-entry-is-never-booked.md`.

## Contract decisions the spec left open

- **`executedQty` is used verbatim, never re-converted.**
  `convertExecutionReportToOrder` already applies the coin-margined /
  contract-sized conversion to every stream report, and `loadOrders` restores
  the row as persisted. `cancelOrderOnExchange` calls `convertOrderExecutedQty`
  because ITS quantity came raw from the venue's cancel response; the promotion
  added here starts from an already-converted row, so calling it again would
  double-count the position.
- **`hasPendingCheck` at the new call site reads `dealTimersMap.has(dealId)`** —
  the same reading spec `038` uses in `checkBaseOrder`'s reposition branch, and
  for the same reason. It is what distinguishes a cancel the engine issued from
  one the venue issued.
- **The user-visible report is a `Deal` botEvent, not a bot message.** A new
  error subType is created enabled-by-default and would raise the bot's error
  state for a condition the engine has just handled correctly; the deal's own
  event history is where `Order created` / `Deal cancelled` already go, which is
  exactly where the report said nothing appeared.
- **The restore query drops its `status` filter rather than widening it.** A
  Mongo predicate on `executedQty` has to cope with it being a STRING —
  `'0.00000000' > '0'` is true lexicographically, which is why `loadOrders` uses
  `$expr`/`$convert` for the same question. A `start` deal has a handful of
  `dealStart` rows, so reading them and deciding in code is cheaper to get right
  and is directly testable.

## Build order

1. `src/bot/dca/partialBaseEntry.ts` — `terminalEntryHoldsAFill` (private),
   `shouldSettlePartialBaseEntry` gains `executedQty` / `updateTime`,
   `pickRestoreBaseEntry` added.
2. `src/bot/dcaHelper.ts`
   - `processCanceledOrder` — route a `dealStart` row through the decision.
   - `settlePartialBaseEntry` — terminal rows take `promoteEndedBaseEntry`
     instead of `cancelOrderOnExchange`; a successful settle calls
     `reportBaseEntryCutShort`.
   - `checkBaseOrder` — both existing call sites pass the two new inputs, so the
     restore path (which routes through the `id` branch) can settle a terminal
     row.
   - `restoreWork` — array read without the `status` filter, choice by
     `pickRestoreBaseEntry`.
3. Tests, then the version bump + changelog in both repos.

## JIT extraction tier

**Tier 1 for the new decision, Tier 0 for everything else.** The decision this
change turns on is already extracted and pure (`partialBaseEntry.ts`, spec 038),
so the new inputs go there and nowhere else. `settlePartialBaseEntry` gains one
branch and two small named methods rather than inline blocks, which is as far as
the radius rule reaches — `processCanceledOrder` and `restoreWork` are legacy
I/O-mixed methods that are NOT rewritten, only edited where the causal path runs
through them.

## Blast Radius

1. **Other callers of the changed functions.**
   - `shouldSettlePartialBaseEntry` — 3 call sites, all in `dcaHelper` (2
     pre-existing in `checkBaseOrder`, 1 new). The two new inputs are optional
     and absent means "no fill", so any caller that does not pass them keeps the
     spec 038 behaviour exactly.
   - `settlePartialBaseEntry` — 3 call sites, all in `dcaHelper`. The new branch
     is keyed on `order.status` being terminal, which spec 038's two callers can
     now also reach (that is the point).
   - `processCanceledOrder` — `comboHelper` **overrides it and never calls the
     DCA implementation**, so combo/hedge-combo bots are untouched. `gridHelper`
     has no such callback.
   - `restoreWork` — `comboHelper` has its own; the DCA one is edited in place.
   - `promoteEndedBaseEntry` / `reportBaseEntryCutShort` — new, one caller each.
2. **`core/` submodule.** Yes — every file here is shared and deployed
   platform-wide (cloud and self-hosted). The parent's pointer needs bumping.
3. **Documented contracts.** None crossed. No GraphQL field, REST shape, socket
   event name, Redis channel or RabbitMQ payload is touched. The `orders`
   collection is written with an existing field set — a row that would have
   stayed `CANCELED` is now written `FILLED` with the same `executedQty`, which
   is the shape `cancelOrderOnExchange` has always produced for the same
   situation and which the legacy dashboard and admin-app already read.
4. **Other tests on this path that must stay green.**
   `dca/partialBaseEntry.harness.spec.ts` (spec 038 — extended here with the
   `botEventDb` stub the new report needs), `resizeCancelPromotion.spec.ts`,
   `strandedLocalRefusal.spec.ts`, `placeOrders*.spec.ts`, and the full suite.
