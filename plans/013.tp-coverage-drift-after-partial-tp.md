# Plan 013 — take-profit coverage drift after a partial take-profit

Spec: `specs/013.tp-coverage-drift-after-partial-tp.md` (issue #696).

## 1. Build order

1. **`src/bot/dca/tpCoverageReconcile.ts`** — pure decision module. No DB, no
   exchange client, no framework import. Sits beside `positionReconcile.ts`,
   which it is modelled on, and borrows that module's central discipline: the
   probe distinguishes *the venue said nothing is there* from *the venue said
   nothing at all*, and only the first is an answer (§1.7).
2. **`src/bot/dcaHelper.ts`** — call it from the reconcile pass and log the
   verdict (§4.1). Correction behind the operator flag (§4.2).

## 2. Contract decisions the spec left open

- **Where tracked position comes from.** Not a new formula: mirror the terms
  `getTPOrder` already uses to size a replacement — `|deal.size|`, minus
  `tpHistory` entries whose order is not itself a filled close, minus filled
  close orders' `executedQty`, minus `reduceFunds` and pending reduce funds.
  §2.3 is the check that this is the engine's own arithmetic and not a
  reconstruction of it: the `NEW` take-profit the engine placed on the CTSIUSDT
  deal is 533, and `trackedPosition` for that deal is 533.
- **What "actionable" means (§1.5).** The engine's existing placeability test,
  used verbatim at `dcaHelper.ts:6583`, `:5563`, `:5946` — `qty >=
  baseAsset.minAmount && qty * price >= quoteAsset.minAmount`. A drift that
  fails it could not be turned into an order, so it is not drift worth acting
  on. This is what clears the KUBUSDT dust deal in §2.1 without a magic epsilon.
- **Which orders are cancellable.** Only `PARTIALLY_FILLED` ones. In both
  over-covered deals (§2.3, §2.4) the `NEW` order is the correctly-sized
  replacement and the partial is the residue, so cancelling the partial alone
  both removes the duplicate and restores coverage. Cancelling a `NEW`
  take-profit is a different decision with a different risk and is not in scope.
- **Where the sweep runs.** `checkOrdersAfterReconnect` — already driven both by
  user-stream reconnect and by the periodic reconcile sweep
  (`reconcileViaSweep`), and it already asks the venue about every open order
  and merges the answer (`getOrderForReconcile` → `mergeCommonOrderWithOrder`).
  Those merged orders are venue truth, which is exactly what §1.7 requires, at
  no extra API cost. Adding a separate timer would duplicate that machinery and
  its rate-limit budget.
- **The operator gate.** `BOT_TP_COVERAGE_REPAIR`, read through the same
  `process.env` constant pattern as `BOT_ORDER_QUARANTINE_STRIKES` and
  `BOT_RECONCILE_LOOKUP_ATTEMPTS` (`main.ts:357-394`). Unset = detect and log
  only. This is the "operator approval" the brief requires; deploying the change
  cannot by itself cancel or place an order.

## 3. Blast Radius

1. **Other call sites.** `tpCoverageReconcile.ts` is a new file with one caller.
   The wiring adds a new method and one call at the end of the DCA
   `checkOrdersAfterReconnect`; it changes no existing statement in that loop.
   `restingTpQty` duplicates no helper — the `origQty − executedQty` expression
   exists inline in `placeOrders` (`dcaHelper.ts:12996`, added by #694) and this
   is the same measure; the call site is left alone rather than refactored,
   since that line is nine days old and is the #694 fix itself.
2. **`core/` submodule.** Yes — this repo *is* `main-app-sh`, deployed platform
   wide. The parent `main-app` pointer must be bumped. Nothing here is imported
   by `exchange-connector`/`websocket-connector`/`paper-trading`, which do not
   consume `src/bot/dca/*`.
3. **Documented contracts.** None touched. No GraphQL field, no socket event
   name, no queue name or payload, no `BaseReturn<T>`, no shared Mongo schema
   change — the detection path only reads. The correction path, when armed,
   calls `cancelOrderOnExchange` and `placeOrders`, both unchanged.
4. **Danger: the FILLED promotion.** `cancelOrderOnExchange` promotes a
   cancelled order carrying fills to `FILLED`, which reaches
   `processFilledOrder` → `closeDeal`. Every order this plan cancels is by
   definition `PARTIALLY_FILLED`, so every one of them would trip it. The
   correction must pass `promotePartialToFilled: false` — the opt-out added by
   #694 (`007.tp-resize-cancel-must-never-promote`), and for the identical
   reason: this cancel is a re-size, not a close. Getting this wrong closes the
   deal on the fraction that sold and strands the rest, i.e. reproduces the bug
   being fixed, on more deals.
5. **Tests that must stay green.** The whole `npm test` suite (330 passing at
   `62429c2`); in particular `dca/partialTp.spec.ts`, `dca/tpCloseOutcome.spec.ts`,
   `dca/multiTpCompletion.spec.ts` and `dca/positionReconcile.spec.ts`, which
   cover neighbouring take-profit accounting.

## 4. JIT extraction tier

**Tier 2** (fully pure) for the new decision module — the judgement is
arithmetic over plain numbers and needs no I/O, which is why it can be tested
against the three production deals directly. The `dcaHelper` caller stays Tier 0:
it is the existing orchestration, it is not on the causal path of the defect
(the defect is the *absence* of a check), and rewriting any part of that
6,000-line reconcile loop to accommodate an additive check would be scope creep.
