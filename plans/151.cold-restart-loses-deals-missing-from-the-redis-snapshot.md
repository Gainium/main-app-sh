# 151 — plan

## Build order
1. `src/bot/dcaHelper.ts` `loadOrders`: when the cold-restart branch restored
   deals from the Redis snapshot (`loadFromDb === false`), read Mongo for this
   bot's `start` / `open` / `error` deals whose `_id` is not among the restored
   ones. Any it finds go into `deals`, the same array the Mongo load fills. A
   failed read is logged and the snapshot is kept (§1.1.4).
2. `keys` (the deal ids `_loadOrders` loads orders for) becomes the restored
   ids plus those deals, so their orders reach the order map (§1.1.2).
3. The block that seeds DB-loaded deals and rebuilds open ones runs when
   `loadFromDb` OR when the added read found deals. It already processes only
   `deals`, so restored deals are not touched (§1.1.3).

`restoreWork` is unchanged. A loaded `start` deal with a FILLED base order
already takes its filled-base branch (`startDeal`). That path is covered by
spec 101 / 125.

JIT tier 0. The change reuses the existing Mongo-load path for the missing
deals and extracts nothing.

## Blast Radius
- `loadOrders` is the DCA load path. Combo's `loadOrders` calls `super` first,
  so Combo bots get the same fix. Hedge DCA/Combo use the same mixins.
- One extra `dealsDb` read per bot on a cold restart from a non-empty snapshot.
  It filters on `botId` + `status`, the same shape the Mongo load already sends
  on every reload. It returns nothing in the common case.
- The `serviceRestart` path in `main.ts` `loadData` (specs 148/149) is not
  touched.
- Files are under `core/` (main-app-sh), so the parent pointer needs a bump.
- No GraphQL, socket or DB shape change.
- Must stay green: `coldRestartOrderSnapshot.spec.ts`,
  `comboPartialBaseEntry.spec.ts`, `restartDeal.spec.ts`, and the full core
  suite.
