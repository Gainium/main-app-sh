# 161 — plan: a cancelled safety order is re-sent under the id the venue already spent

Spec: `specs/161.cancelled-safety-order-resent-under-its-spent-id.md`.

## Solution

1. **Pure decision (Tier 2)** — `src/bot/clientOrderIdReissue.ts`:
   `isSpentStatus`, `resolveLevelClientOrderId` (keep / adopt / mint, following
   the spent-id → replacement chain) and `siblingClientOrderIds` (the
   last-character swap spec 145 already used, now as an ordered candidate list).
   No I/O; the caller passes a status lookup.
2. **State** — `MainBot.reissuedClientOrderIds: Map<spent id, replacement id>`.
   Written by both re-send paths below, read by the placement loop. Per bot,
   in memory only: it bounds a second send inside one process lifetime, which
   is the window the evidence shows (seconds to ~100 minutes). A restart
   rebuilds the ladder with fresh ids (`restoredFromRedis` → `getOrderId`).
3. **Placement** — `dcaHelper.placeOrdersHoldingDealLock`: before the batch
   phase and the loop, `reissueSpentLevelId` runs over every `dealRegular`
   level (not stop-listed): `adopt` writes the live replacement id onto the
   level, so the loop's existing "Order duplicate" / batch-eligibility checks
   skip it; `mint` gives the level `getOrderId('D-RO' | 'CMB-RO')` (the same
   prefix choice the ladder restore uses) and records spent → fresh for both
   the level's id and the chain's end. The level object is mutated in place, so
   the deal's ladder carries the live id from then on.
4. **Duplicate branch** — `main.sendOrderToExchange`: after the venue confirms
   it holds the refused id only as cancelled (spec 136 path unchanged), walk the
   sibling candidates; a sibling this bot holds (memory, else its DB row) live
   or FILLED is returned without a send; a spent sibling is skipped; the first
   free one is sent. Spent → sibling is recorded.

JIT tier: Tier 2 for the decision (it is naturally pure), Tier 0 for the rest
of `placeOrdersHoldingDealLock` / `sendOrderToExchange` — only the id choice is
on the causal path.

## Blast Radius

1. Call sites: `placeOrdersHoldingDealLock` is shared by DCA, combo (inherits
   the DCA helper) and hedge. Only `dealRegular` levels are touched; combo
   minigrid `dealGrid` levels and TPs (which get a fresh id on every rebuild)
   are not. The duplicate branch serves every bot type and order type; its
   behaviour changes only when the sibling it would have sent already exists
   for this bot (previously: sent and, on Bybit, refused; elsewhere possibly
   placed twice).
2. `core/` submodule: yes — shared by every main-app deployment (cloud and
   self-hosted). No exported type, GraphQL, socket, queue or collection shape
   changes. The parent's `sendOrderToExchange` override only delegates.
3. Contracts: none. Order rows keep the same shape; only which client order id
   a re-placed level carries changes.
4. Tests that must stay green: `duplicateClientOrderId.spec.ts` (specs
   136/145), every `src/bot/dca/*.harness.spec.ts` that drives placement, the
   full `npm test` suite.

Behaviour on venues that DO allow reusing a cancelled id (Binance spot): the
level is still placed exactly as before, under a fresh id instead of the old
one. Risk accepted: an order written off locally as CANCELED while still live
on the venue would no longer be caught by the venue's duplicate refusal. Every
write-off path asks the venue first (specs 136, 154, 155), so the CANCELED in
the map is the venue's own answer.
