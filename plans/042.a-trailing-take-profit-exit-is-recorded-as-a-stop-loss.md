# Plan 042 — A trailing take-profit exit is recorded as a stop loss

Spec: [`specs/042.a-trailing-take-profit-exit-is-recorded-as-a-stop-loss.md`](../specs/042.a-trailing-take-profit-exit-is-recorded-as-a-stop-loss.md)

## 1. Solution

One edit, in `src/bot/dcaHelper.ts` → `checkDealsStopLoss`, to the `trailing`
flag the method hands `triggerStopLoss`. It fixes the root cause the spec's
Assumption names, both halves of it:

1. **`!multiTp` → `!useMultiTp`.** `multiTp` is the multi-take-profit target
   *array*; the toggle is `useMultiTp`. This is not a new concept — it is the
   flag the sibling stop-loss arm four lines above already uses (`!useMultiSl`)
   and the one `getTrailingSettings` uses in `skipTp`. `useMultiTp` replaces
   `multiTp` in the destructure (`multiTp` has no other use in the method).
2. **Require the level that was hit to be the trailing level** —
   `!!d.deal.trailingMode && !!d.deal.trailingLevel`, gating the whole `||`.
   This is the same guard `getDealStopLossPrice` applies before it returns
   `deal.trailingLevel`, and `isDealForStopLoss` before it registers the deal.
   Without it, step 1 alone would label a genuine stop-loss close on a
   trailing-take-profit bot as `trailing` (spec §2.4) — re-opening the defect
   commit `9092ca79` fixed. **Both issues are satisfied:** trailing closes are
   `trailing` again (pre-`9092ca79` behaviour), and real stop-loss closes stay
   `sl` (`9092ca79`'s behaviour).

The `!moveSL` term in the stop-loss arm is left exactly as it is: removing it
would relabel move-stop-loss closes, which is neither asked for nor measured.

### Contract decisions the spec left open

- **Which flag names "multi take profit is on"** → `useMultiTp`. Chosen because
  §2.1 measured `useMultiTp: false` on 755/755 of the affected deals, and
  because `getTrailingSettings`/`isDealForStopLoss` already treat it as
  canonical. No new helper: `useMultiTp` already exists on the settings shape.
- **How "this close was at the trailing level" is expressed** → by mirroring
  `getDealStopLossPrice`'s own guard on `deal.trailingMode` /
  `deal.trailingLevel`, rather than comparing `priceToClose` to
  `deal.trailingLevel` (float equality on a value that moves between ticks).

### JIT legacy tier

**Tier 0 — no extraction.** The predicate now exists in three places
(`isDealForStopLoss`, `getDealStopLossPrice`, `checkDealsStopLoss`) and drift
between them is what caused this bug, so a shared predicate is tempting. It is
declined here: the three copies are *deliberately* not identical
(`checkDealsStopLoss` carries `!moveSL` and `!useMultiTp`; the other two carry
neither), so a single shared predicate would either change which price is
monitored — the one thing spec §4.5 forbids — or degenerate into a helper taking
two boolean opt-outs, which is not clearer than the inline condition. A
comment at the site records why the array test was wrong, which is what would
have prevented the drift. Not a lower tier: nothing smaller removes the defect.

## 3. Blast radius

1. **Other call sites of the changed code.** The `trailing` flag is local to
   `checkDealsStopLoss`; it is read exactly once, in the `triggerStopLoss(…)`
   call at the end of the same loop body. `grep -n 'multiTp'` over
   `dcaHelper.ts` confirms line 18953 was `multiTp`'s only use inside this
   method. `triggerStopLoss` has one other caller — none; only this site
   (`grep -n 'triggerStopLoss'` → definition + this call). `comboHelper`'s
   `triggerStopLossCombo` is a separate method and is untouched.
2. **Branch selection in the `if / else if` chain** — the one effect that is not
   just the label, and the only reason this change is not purely cosmetic.
   Gating branch 1 changes which branch a close can reach, in both directions:
   - **Branch 1 → no branch.** A close that used to match the *trailing stop
     loss* arm without an armed level now falls through. Branch 2 cannot catch
     it (it needs `!trailingSl || useMultiSl`, and that arm already required
     `trailingSl && !useMultiSl`), and branch 3 needs `dynamicAr`. So no branch
     runs, exactly as for the reported cohort today — the label becomes `sl`,
     which is correct, because an unarmed deal is registered for its real
     stop-loss level. Branch 1's body is `handleLog` + `trailing = true` and has
     no side effects, so nothing else changes.
   - **Branch 2 → branch 1.** Reviving the trailing-take-profit arm means an
     armed trailing close on a bot with `useSl: true` now takes branch 1 and
     *skips* branch 2. Branch 2's only material side effect is the multi
     stop-loss accounting (`closeBySl` / `notCheckSl` / `closeByMulti`, i.e.
     `slSource`) under `useMultiSl && multiSl.length && dealCloseConditionSL ===
     tp`; everything else in it is logging. Skipping it is *semantically right*
     — `getDealStopLossPrice` returned `deal.trailingLevel` for such a deal, so
     the level hit was the trailing level and not one of the stop-loss targets —
     but it is still a behaviour change, so it was measured rather than argued:
     prod has **one** bot with `useSl + useMultiSl + trailingTp + tp/tp +
     !useMultiTp` and a non-empty `multiSl`, it has **0** open deals with an
     armed trailing level and **0** such closes in the 5 days to 2026-09-12, and
     its `multiSl` holds a single target, so even for it `inUseSl.length > 1` is
     false and only `closeByMulti` would differ. Nothing else in the chain reads
     `multiTp`, so no other selection moves.
3. **`core/` submodule.** Yes — this file is in `core/` (`main-app-sh`),
   shared/public and deployed platform-wide. The parent repo's
   `src/bot/dcaHelper.ts` is a 1,145-line subclass that does not reference
   `multiTp` or the trailing flag, so it needs no change; the parent's submodule
   pointer is bumped at ship time.
4. **Documented contracts.** `DCACloseTriggerEnum` is **not** changed — no new
   member, no rename, no schema change. `trailing` is already in the enum, in
   both Mongo schemas (`closeTrigger: { type: String, enum: DCACloseTriggerEnum }`),
   in the GraphQL schema and in the dashboards' copy of the types, and 166k
   existing deals already carry it, so every consumer already renders it. What
   changes is *which* existing value is written. Danger List: item 12 (shared
   Mongo collections) is touched only in value, not shape; item 3 (GraphQL
   schema) and item 11 (`core/` types) are untouched.
5. **Other tests on this path.** `src/bot/dca/unactionedClose.harness.spec.ts`
   exercises `closeDealById` with every `DCACloseTriggerEnum` member including
   `trailing`; `lostLedgerClose`, `tpCloseOutcome`, `partialTp` and
   `liquidationDealLink` touch `closeDeal`/close accounting. All must stay
   green — the full suite is the gate-6 criterion.

### Not covered by this change

- The 7,333 rows already stamped `sl`. Spec §5: code cannot correct them.
- The separate 2026-08-28 collapse in `trailing` labels for trailing-**stop-loss**
  bots (spec §5) — different cohort, different mechanism, still open.

## 5. Gate 4 — plan vs spec

Walked §1–§5. Every numbered requirement appears above. The Solution fixes the
mechanism §3 names (a dead array test, plus a missing "was it the trailing
level" check) and not a symptom — it does not touch `closeDeal`'s
`tpOrder.sl ? sl : tp` fallback, which §3 shows is not implicated because it
never overwrites a set `closeTrigger`. The two decisions recorded in §1 are both
ones the spec left open (which flag; how to express "at the trailing level").
No spec section was renegotiated to make the plan easier.
