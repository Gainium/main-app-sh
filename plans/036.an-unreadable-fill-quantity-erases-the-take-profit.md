# 036 — Plan

Spec: `specs/036.an-unreadable-fill-quantity-erases-the-take-profit.md`.

## §1 Build order

One change, two call sites, both in `core/src/bot/dcaHelper.ts` inside
`getTPOrder`. They are the two sums spec §1.2 names and nothing else:

1. **§4.3 — the close-side sum** (`filledCloseOrders.reduce`, inside `add`).
2. **§4.1/§4.2 — the entry-fill sum** (`const filledQty = …`).

Both become the idiom the same subsystem already uses:
`(parseFloat(\`${v.executedQty}\`) || 0)`.

## §2 Contract decisions the spec left open

### §2.1 Which existing helper

Three candidates already exist; the spec did not pick one.

- **`dca/tpCoverageReconcile.ts` — `trackedPosition` / `restingTpQty`.**
  Chosen. They read `executedQty` as
  `(parseFloat(\`${o.executedQty}\`) || 0)` and their own doc comment says they
  are *"the terms `getTPOrder` already uses to size a replacement … not a second
  opinion about them"*. The two are supposed to be the same measurement, and
  `soldViaFilled` there is line-for-line the `filledCloseOrders` sum here. The
  drift is that one of the pair is sanitised and the other is not, so applying
  the existing idiom is what makes them agree again — not a new utility.
- **`dca/executedFill.ts` — `executedFillQty`.** Rejected, deliberately. It is
  purpose-built for the *ledger* and carries two extra rules this call site must
  not take: a CANCELED row with `orderId '-1'` answers 0, and an unreadable
  `executedQty` falls back to **`origQty`** — the quantity the order was
  *planned* for. Substituting a plan for a fill is exactly the AIOZ failure
  `baseOrderQty.ts` was written for: it over-states the position, the venue
  rejects the close, and the deal ends with no take-profit — the same outcome
  this spec is fixing. `|| 0` under-states instead, and §2.2 is why that is
  safe here and is not safe there.
- **A new shared sanitiser.** Rejected: it would duplicate the idiom above for
  two call sites, and a new export in `core/` is platform-wide surface.

### §2.2 Why 0, and not a guess

`resolveBaseOrderQty` (spec `017`) derives the base order's contribution as
`floor(max(0, grossEntry - filledQty))` and takes it over the base order's own
row whenever it is larger. So a fill sum that under-counts is picked back up
from `deal.size` — the deal's persisted books, which agree with the summed
entry rows within 0.5% on 8,704 of 8,740 live deals. The §4.2 test pins exactly
this: with the poisoned row the quantity is still `230.7`, unchanged.

There is no equivalent recovery on the close side (§4.3), so a filled close
whose `executedQty` is unreadable will be under-counted and the replacement
take-profit over-stated by what it sold. That is strictly better than today —
NaN means *no take-profit at all*, guaranteed — and it matches
`trackedPosition`. Reading the sold quantity back out of `tpHistory` would be
the stronger repair; it is a different change, with its own double-count risk
(the two records of one close), and is left out.

## §3 Blast radius

1. **Other call sites.** `+…executedQty` appears in ~15 other places in
   `dcaHelper.ts`. Only these two feed the take-profit quantity; the rest are
   out of scope (spec §5) and untouched. The nearest neighbour,
   `+o.executedQty > 0` at `dcaHelper.ts:14337`, needs nothing: `NaN > 0` is
   `false`, so a bad row is already excluded there rather than propagated.
2. **`core/` submodule.** Yes — `dcaHelper.ts` is shared/public and deployed
   platform-wide (cloud + self-hosted). Danger List item 11. The parent pointer
   must be bumped.
3. **Documented contracts.** None. No exported signature, GraphQL field, socket
   event, queue payload or Mongo shape changes; the edit is inside one method
   body. Order rows are read, never written.
4. **Behavioural reach.** The expression is identical for every row whose
   `executedQty` is a readable number — `+'233.6'` and
   `parseFloat('233.6') || 0` are the same value — so every healthy deal on the
   platform is byte-identical. It differs only where today's value is `NaN`,
   which is the defect. One edge worth naming: a row reading exactly `'0'`
   gives `parseFloat('0') || 0` → `0`, unchanged.
5. **Other tests on this path.** `tpNanRefusal.harness.spec.ts` (spec 023),
   `tpSizingFromPosition.harness.spec.ts` (017),
   `tpSizingAfterPartialTp.harness.spec.ts`, `baseOrderQty.spec.ts`,
   `tpCoverageReconcile*.spec.ts`, `partialTp.spec.ts` — all must stay green,
   and `023`'s guard in particular must keep firing for the price-driven NaN it
   was written for.

## §4 Legacy tier

Tier 0 — the smell on the causal path is the coercion itself, and the
established fix is one already-present expression. `getTPOrder` is a 600-line
method mixing sizing with I/O, but extracting it is not on this path and would
be scope creep of exactly the kind the runbook's radius rule forbids.
