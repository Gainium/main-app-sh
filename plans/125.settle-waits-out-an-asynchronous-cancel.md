## Build order

1. `dca/partialBaseEntry.ts`: `baseEntryCancelSettleAttempts` (6),
   `baseEntryCancelSettleDelayMs` (500), `isSettledBaseEntryAnswer(status)`.
2. `dcaHelper.ts`:
   - `settlePartialBaseEntry` becomes a single-flight wrapper (per client order
     id, `settlingBaseEntries`) around the unchanged body, now
     `settlePartialBaseEntryNow` (§4.3).
   - after the cancel, a non-terminal answer goes to `awaitBaseEntryCancel`,
     which re-reads via `getOrderForReconcile` + `mergeCommonOrderWithOrder`;
     `FILLED` is written through `promoteEndedBaseEntry` (§4.1).
   - a settle ending in the warn with the order still live records it in
     `unsettledBaseEntries`; `processCanceledOrder` treats such an order as
     having no pending check (§4.2).
   - `restoreWork` loads a terminal-with-fill base row into memory before
     `checkBaseOrder` when it is missing (§4.4).

## JIT extraction tier

Tier 0/1: the decision constants and predicate live in the existing pure module
`dca/partialBaseEntry.ts`; the I/O stays in the helper next to the code it
extends. No wider extraction — the settle chain was already split this way by
specs 038/048/059.

## Blast Radius

1. Call sites of `settlePartialBaseEntry`: `checkBaseOrder` (×2),
   `processCanceledOrder` (DCA), `comboHelper.processCanceledOrder`. All get the
   single-flight guard and the re-read; Combo inherits both. No signature
   change.
2. All files are under `core/` (main-app-sh) — shared with self-hosted; pointer
   bump in main-app.
3. No GraphQL/REST/socket/queue/collection shape change. Orders writes are the
   same forced FILLED promotion spec 059 already does.
4. Tests that must stay green: `settleCancelNoFillReport`,
   `venueCanceledBaseEntry`, `partialBaseEntry`, `baseEntryTopUp`,
   `baseEntryRemainder`, `baseEntryReposition`, `comboPartialBaseEntry`, full
   core suite.

Latency: only a cancel that came back non-terminal waits — at most
6 × (500 ms + one lookup) inside `checkBaseOrder`'s per-symbol mutex.
