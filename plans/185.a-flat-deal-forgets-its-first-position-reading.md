# Plan 185 — keep the position-gone readings in their own long-lived count

## Build order

1. Tests (red) in `src/bot/comboFlatDealGridRefusal.spec.ts`. The fake Redis
   now keeps the TTL that `RetryBackoff` sets, and `elapse(ms)` drops every key
   that would have expired by then.
2. `src/bot/dcaHelper.ts`: a new `RetryBackoff` `positionGoneReadings`
   (namespace `dpg`, `memoryMs` one day). `reconcileDealPosition` records it
   only for an answered flat verdict and gates the close on its `attempt`. It
   clears it with the throttle wherever the throttle is cleared.
3. Version 1.109.2 and a CHANGELOG entry.

## Decisions the spec left open

- **A second key rather than `memoryMs` on `dpp`.** Giving the throttle a day of
  memory would fix §1.2.1 alone. But it would also stretch §1.2.2's
  unanswered-probe-as-reading flaw from a 10-min window to a day, and it would
  leave the throttle escalated at 1 h for a day after a venue blip. A separate
  count fixes both and leaves the throttle exactly as spec 005 set it.
- **One day of memory**, the same as `tpg` (spec 143), for the same reason:
  the passes come hours apart.
- **JIT tier 0.** The change stays inside `reconcileDealPosition`, which is
  already the extracted decision point. The verdict functions it calls are
  pure and untouched.

## Blast Radius

- Callers of `reconcileDealPosition`: `checkTPLevel` (spec 005), the spec-047
  §4.4 notional-floor path in `getTPOrder`, and the combo grid refusal (spec
  175). All three get the same rule. In `checkTPLevel`, probes are already 5
  min apart, so settling still takes two windows. The only difference there is
  that an unanswered probe no longer counts.
- `core/` is the shared `main-app-sh` submodule, so the parent pointer must be
  bumped. No GraphQL, socket, queue or Mongo shape changes. The only new
  state is the Redis key `dpg:cd:<botId>:<dealId>`, with a TTL.
- Other tests on this path: `src/bot/dca/tpDustClose.harness.spec.ts` and the
  full core mocha suite.
