# 237 — plan

## Solution

1. `reconcileRetryDecision` (`main.ts`): `stop` when `isKeyPermissionRefusal(reason)`,
   checked before the rate-limit branch. Every `getOrderForReconcile` caller
   therefore spends one lookup on a key refusal instead of three; it already
   handles an unanswered result, so only the count changes.
2. Both `checkOrdersAfterReconnect` loops: on an unanswered lookup whose reason
   is a key refusal, add the remaining orders to `unresolved` (DCA: also mark
   their deals unresolved for TP coverage, which skips them) and `break`.
   No write path is reached for those orders.

JIT tier 0: the loops stay inline; the reused classifier is the existing
`isKeyPermissionRefusal` (authGuard, spec 232). No new helper.

## Blast Radius

- `reconcileRetryDecision` is used only by `reconcileLookup`, which serves
  `getOrderForReconcile` (restart probes, reconnect pass, combo/DCA checks).
  A key refusal never carries data, so callers see the same result one round
  trip earlier. Quarantine/write-off need a definitive not-found and are not
  affected.
- `core/` is shared (main-app-sh). No exported signature, GraphQL, socket or
  DB shape changes.
- Lockout answers are not covered: the exchange-balancer's Kraken auth breaker
  holds a locked-out key off.
- Other tests on the path: `reconcileRateLimit.spec.ts`,
  `reconnectCanceledBaseEntry.harness.spec.ts`,
  `dca/reconnectSweepStaleSnapshot.harness.spec.ts`.
