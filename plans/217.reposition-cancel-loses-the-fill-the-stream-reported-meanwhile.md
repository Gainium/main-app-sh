# Plan 217: the reposition cancel keeps the stream's fill report

Spec: `specs/217.reposition-cancel-loses-the-fill-the-stream-reported-meanwhile.md`.

## Solution

JIT tier 0/1. This is a narrow change inside the existing reposition arm. No
extraction, because the decision is one predicate that the existing pure
`terminalEntryHoldsAFill` already answers.

1. `dcaHelper`: new instance map `repositionCancelReports` (client order id →
   the fullest terminal report seen, or `undefined`).
2. `checkBaseOrder` reposition arm: register the id before
   `cancelOrderOnExchange`. Read and drop it in a `finally` around the cancel and
   `bookCanceledBaseEntry`, so the spec 125 wait is covered too and no record
   outlives the arm. If the answer did not book and a report exists while the
   deal is still `start`, call `settlePartialBaseEntry(report)` and return.
   Otherwise the existing `placeBaseOrder` path runs unchanged.
3. `noteRepositionCancelReport(order)`: records a terminal fill-bearing
   `dealStart` report only for an id the arm registered. It is called first
   in the DCA `processCanceledOrder` and in the Combo override.

Decision left open by the spec: settle through `settlePartialBaseEntry`
rather than by feeding the report into `bookCanceledBaseEntry` as `observed`.
`settledBaseEntryFill` ignores `observed` when the answer is non-terminal or
missing, and `settlePartialBaseEntry` already handles an ended row (promote,
force-write, top-up, book) and its own re-entry guard.

`cancelOrderOnExchange`'s copy loop in `main.ts` is NOT changed. It serves
every cancel (take profits, safety orders, grids), and a "keep the higher
`executedQty`" rule there would compare a raw venue answer against a converted
map row on contract-sized accounts. It would also undo the Hyperliquid
spec-041 correction for shrunk reduce-only orders.

## Blast Radius

1. Call sites: `checkBaseOrder`'s reposition arm is the only consumer. The two
   `processCanceledOrder` implementations (DCA and Combo) gain one recording
   call that is a no-op unless the arm is mid-cancel. The `enterMarketPrice`
   arm and `settlePartialBaseEntryNow` are untouched.
2. `core/` submodule: yes (`main-app-sh`). Bump the parent pointer.
3. Contracts: none. There is no GraphQL, socket, queue or schema change.
   Orders are written through the existing `promoteEndedBaseEntry`.
4. Tests that must stay green: specs 133, 111, 101, 059/125, 177 and 210
   harnesses, and all of `src/bot/**/*.spec.ts`.
