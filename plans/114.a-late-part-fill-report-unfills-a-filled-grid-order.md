# Plan 114 — A late part-fill report un-fills a filled order

Spec: `specs/114.a-late-part-fill-report-unfills-a-filled-grid-order.md`

## Build order

1. `lateFillReportUnfills.harness.spec.ts` — replay FILLED → PARTIALLY_FILLED
   (same timestamp) through the real `convertExecutionReportToOrder`, order map
   indexes and `isOrderExistInDeal`; red on the unfixed tree (status reads
   `PARTIALLY_FILLED`, the counter level reads as occupied).
2. `executionReportUnfillsOrder` in `staleExecutionReport.ts` (pure), with unit
   tests in `staleExecutionReport.spec.ts`.
3. Ask it in `convertExecutionReportToOrder` beside spec `090`'s check, gated on
   `process`, returning `null`, logged with `handleLog`.

## Contract decisions the spec left open

- A new predicate rather than widening `executionReportRewindsOrder`: `090`'s
  rule and its log line (`older than`) are pinned by their own tests and
  describe a different shape (older timestamp); this one has no time component.
- The pre-existing venue-scoped "already filled" guard is left as is. It is now
  a subset of the new rule for `NEW`/`PARTIALLY_FILLED`, and it also drops
  `CANCELED`-over-`FILLED` for those venues, which this spec keeps out of scope.

## Blast Radius

- `core/` is shared by every bot type (DCA, combo, grid, hedge) on cloud and
  self-hosted. The only behaviour change: a `NEW`/`PARTIALLY_FILLED` report for
  an order held `FILLED` no longer replaces the in-memory row or reaches
  `onNew`/`onPartiallyFilled`. Mongo never accepted that write
  (`updateOrderOnDb` filter), so persisted state is unchanged.
- An in-memory `FILLED` without venue evidence is already refused (spec `028`),
  so no path relies on a later part-fill to "correct" a premature FILLED.
- No GraphQL, REST, socket, Redis or DB schema contract is touched.
