# 221 — plan

Spec: `specs/221.refused-safety-order-resent-under-its-written-off-id.md`.

## Solution (root cause §3.1)

- `MainBot` remembers the client ids its venue-refusal write-off retires
  (`noteWrittenOffClientOrderId` / `isWrittenOffClientOrderId`, an in-memory
  `Set` capped at 2048, oldest dropped first). Recorded only in the
  `!servedLocally` branch, where the row is written CANCELED. A local-guard
  refusal deletes its row and keeps its id (§1.2).
- `dcaHelper.reissueSpentLevelId` asks for an id's status from the order map,
  falling back to `CANCELED` for an id the bot wrote off. The existing pure
  `resolveLevelClientOrderId` then mints a fresh id exactly as for a CANCELED
  row it still holds (spec 161). No change to the pure module.

JIT tier: 0. The decision already lives in a pure module (spec 161); the
change only widens what the call site tells it.

## Blast radius

1. Call sites: `reissueSpentLevelId` is the only consumer, called from
   `placeOrdersHoldingDealLock` for DCA and combo (`dealRegular` levels only).
   The write-off branch is shared by every bot type; Grid only records, it
   never reads.
2. `core/` (main-app-sh): shared, but no type, schema, GraphQL, socket or queue
   shape changes. Parent pointer bump + parent version.
3. No DB writes added; the row a written-off id holds is unchanged.
4. Stays green: `clientOrderIdReissue.spec.ts`,
   `dca/spentLevelIdPlacement.harness.spec.ts`, `duplicateClientOrderId.spec.ts`,
   `restartDealBalanceCooldown.spec.ts`, `restartDeal.spec.ts`, full core suite.
