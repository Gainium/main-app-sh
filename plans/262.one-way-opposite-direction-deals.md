# 262 — plan

## Build order

1. `dca/opposingNetPosition.ts`: pure side derivation, verdict and messages (§4.0).
2. `MainBot.findOpposingDealHolder`: optional `strategy` filter, `private` →
   `protected` (§4.1.1). With no argument the query is byte-identical, so bot
   start is unaffected.
3. `dcaHelper.netPositionHeldAgainst`: one venue read, fail-open (§4.1.2, §4.2).
4. `dcaHelper.refuseNewDealAgainstOpposingPosition`, wired into both new-deal
   gate chains (DCA `openNewDealBody`, combo `openNewDeal`) (§4.1).
5. `closeDealById`: verdict computed before the branch chain. The
   close-without-order branch also requires "not held against" (§4.2).
6. `conditionLatch.newDealAgainstOpposingPosition` key (§4.1.4).

## Blast Radius

- `core/` is shared (`main-app-sh`). The change runs in the DCA and combo bot
  workers only. No GraphQL, REST, socket, Redis or Mongo schema change.
- Venue load: one `futures_getPositions(symbol)` per new-deal attempt on a
  one-way futures DCA/combo bot, and only when no opposite deal was found in
  the DB. Plus one per refused-as-flat close on one-way futures. An ASAP bot
  that keeps being refused re-reads at most once per 60 s.
- DB load: two `dcadeals`/`combodeals` reads per new-deal attempt on one-way
  futures. They use the `userId` + `status: 'open'` partial index (`limit 5`).
- Trading behaviour: deals that would trade against the account's own net
  position are no longer opened. Flat-position closes are unchanged.
