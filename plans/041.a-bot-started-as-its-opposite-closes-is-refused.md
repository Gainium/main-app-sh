# 041 — plan

## 1. Build order

1. `src/bot/opposingPositionSettle.spec.ts` — pure tests, written first (red:
   the module does not exist).
2. `src/bot/opposingPositionSettle.ts` — the pure rule: what counts as flat
   (§4.2) and the bounded re-read (§4.1, §4.3, §4.4, §4.7). Pure but for the
   injected `fetch`/`sleep`, the same shape as `reconcileLookup` in `main.ts`.
3. `src/bot/main.ts` `loadData` "check positions" — on a side mismatch, when
   §4.5 allows, call `awaitPositionFlat` with a re-read of the same scope as the
   original (§4.6); on a flat read, log, replace `positionsRequest`, continue;
   otherwise refuse exactly as today.
4. Version bump + changelog in `core` and in the parent, per the repo's
   ceremony; bump the parent's submodule pointer.

## 2. Contract decisions the spec left open

- **Where the wait sits.** Inside the existing `if (side !== requiredSide)`
  branch, before `handleErrors`. The margin and leverage checks above it are
  untouched (spec §5).
- **The fresh read replaces `positionsRequest`.** The later `zeroPosition`
  lookup (leverage/margin changes) then sees the flat account, which is what a
  start on a flat account sees today.
- **Re-read scope.** `allPositions ? futures_getPositions() :
  futures_getPositions(symbol)` — the same two call shapes the method already
  uses.
- **Restart gate.** `!skipFuturesError && !this.serviceRestart`.
- **JIT tier: 2.** The decision (flat? keep waiting?) has no I/O of its own, so
  it is a plain module with the fetch and sleep injected. Tier 1 would leave the
  loop inline in a 450-line method with no way to test it; Tier 3 (a positions
  port) is not warranted for a bug touch.

## 3. Blast radius

1. **Other call sites.** The side check exists once, in `MainBot.loadData`,
   reached from `BotHelper.start` (grid) and `DCAHelper.start` (DCA and combo,
   which passes `skipFuturesError = deals.active > 0`). The new module is
   called from exactly one place. `server/v2/helpers.ts`
   `findConflictingFuturesPosition` makes the same side comparison at bot
   *creation* over the public API; that is a pre-flight answer to a request,
   not a start racing a close, and is left as is.
2. **`core/` submodule.** Yes — `main-app-sh`, shared platform-wide (cloud and
   self-hosted). The change is additive: one new module, one branch inside an
   existing one; no exported type or signature changes. Parent pointer bumped
   deliberately.
3. **Contracts this repo owns.** None touched: no GraphQL/REST shape, socket
   event, queue payload or collection field. The refusal message is unchanged
   (`bot/utils.ts` classifies it by prefix, and `findConflictingFuturesPosition`
   deliberately mirrors its wording).
4. **Behaviour change, stated.** Only on a path that refuses today, and only
   when the refusal would stop the bot: the refusal arrives up to 10 s later,
   after at most 5 extra position reads through the balancer. Bots that are
   refused for a genuinely opposing position are still refused.
5. **Tests that must stay green.** The whole `core` spec suite. No existing
   spec drives `loadData`.

## 5. Gate 2 note

The red run fails on the missing module, not on an engine decision: `loadData`
has no harness (it opens exchange, DB, Redis and user-stream connections
before reaching the check), and building one is larger than this fix. The
behaviour the spec's Assumption names — a single read, no second look — is
what the absent `awaitPositionFlat` encodes, and the §4.1 case replays the
reported sequence (opposite position on the first re-read, flat on the next).
