## Contract decisions the spec left open

- **Which helper writes the row.** `updateOrderOnDb` — the same one the
  user-stream path uses on the same object after the same call. No new helper:
  the JIT runbook's tier 0 (this is not the smell being fixed) and the reuse
  rule both point at it.
- **`setOrder` is not called.** `fillPartiallyFilledOrder` already does
  `this.orders.set(clientOrderId, order)` on the row it returns, so the
  in-memory map is correct before this code runs; the gap is the DB only.
- **The write is awaited.** `settlePartialBaseEntry` opens the deal on the next
  line; an unawaited write could land after `startDeal` has read the row back.
- **Growth test, not an unconditional write.** `+booked.executedQty > before`
  keeps §4.3 true and makes the change a no-op on every path where the
  remainder was declined.

## Blast Radius

1. **Other call sites.** `topUpSettledBaseEntry` has exactly one caller,
   `settlePartialBaseEntry` (`dcaHelper.ts`), itself reached only from the two
   `shouldSettlePartialBaseEntry` branches of `checkBaseOrder` and the
   reduce-only branch at the bottom of `dcaHelper`. `updateOrderOnDb` is
   unchanged.
2. **`core/` submodule.** Yes — this file is `main-app-sh`, shared and deployed
   platform-wide. The change is additive and confined to one method; it writes
   an existing collection with an existing helper and introduces no new field,
   type or shape.
3. **Contracts this repo owns.** None touched. No GraphQL/REST shape, no
   socket.io event, no queue name. The `orders` collection is a shared Mongo
   collection (root Danger List #12), but this writes the SAME fields the
   user-stream path already writes for the same situation — legacy main-dash
   and admin-app read rows, and a row whose `executedQty` now matches what the
   venue actually executed is the shape they already expect.
4. **Behaviour visible to a deal.** `cost`, `size`, `avgPrice`, `usage`,
   `currentBalances`, `profit` and the fee ledger of a deal whose base entry
   was topped up stop reverting to the pre-remainder fraction. That IS the fix.
   No other deal is reached: without a `br` merge the guard is false.
5. **Other tests on this path.** `src/bot/dca/baseEntryTopUp.harness.spec.ts`
   (spec 057, whole file), `src/bot/dca/partialBaseEntry.spec.ts`,
   `src/bot/reduceOnlyRemainder.spec.ts`, `src/bot/remainderFill*.spec.ts` —
   all must stay green.
