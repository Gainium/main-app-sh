# 033 — plan: on OKX, one safety order in sixty is booked as an addition

Spec: [`specs/033.okx-safety-orders-are-routed-as-add-funds.md`](../specs/033.okx-safety-orders-are-routed-as-add-funds.md)

## 1. Solution

`updateDeal`'s

```ts
const roa =
  order.clientOrderId.indexOf('-ROA-') !== -1 ||
  order.clientOrderId.indexOf('ROA') !== -1
```

becomes

```ts
const roa = isAddFundsOrder(order)
```

with `isAddFundsOrder(order) = !!order.addFundsId` added to
`src/bot/dca/ladderLevels.ts` beside `isLadderOrder`, which already answers the
complementary question from the same field.

Trivial as an expression, and the point is not the expression. The named
function carries §2.2 — why the id cannot be consulted on OKX — to the next
person who sees a one-line predicate and reaches for the client order id again,
and `ladderLevels.spec.ts` pins it against the real generator.

### 1.1 Why not keep the id test as a fallback

Considered and rejected. A fallback only helps if `addFundsId` can be missing on
a real addition; spec §2.3 traces every route and it cannot. Keeping it would
therefore preserve the 1.64% false positive to guard a case that does not
occur — the fallback IS the defect.

### 1.2 Extraction tier

**Tier 2**: a decision inlined in a 400-line method that also writes the deal,
saves it, and places orders, coming out fully pure. Same module and same idiom
as `031`.

## 2. Build order

1. `isAddFundsOrder` in `src/bot/dca/ladderLevels.ts`.
2. `ladderLevels.spec.ts` — §4.1/§4.2/§4.3, including a measured-rate case that
   drives the REAL `utils.id` and asserts the old test's rate and the new
   test's zero.
3. Apply §1 at the call site.
4. `npm test`.
5. Version bump + `CHANGELOG.md` in both repos, admin What's New draft.

## 3. Blast Radius

**1. Other call sites.** One: `dcaHelper.updateDeal`. `comboHelper` has no
equivalent test — combo returns early from `addDealFunds`, so a combo deal has
no add-funds orders at all. The `-ROA-`/`ROA` strings appear nowhere else in
`core/src/bot`.

**2. Is it under `core/`?** Yes — `main-app-sh`, public, shared, deployed
platform-wide. Submodule pointer bumped deliberately; the commit message
carries no issue ids, forum links or user detail.

**3. Documented cross-service contracts.** None. No API/GraphQL shape, no
socket.io event, no queue, no schema change — `addFundsId` is an existing
persisted field being read where a string was read before.

**4. Other tests that must stay green.** `npm test` in full. No existing suite
asserts the id-based routing. `ladderLevels.spec.ts` (15 cases) and the two
add-funds harnesses must not move: they exercise the counts downstream of this
branch and are already keyed on `addFundsId`, so a correct routing fix cannot
disturb them — if one moves, the fix is wrong.

**5. Direction of risk.** This trades a false positive for a possible false
negative, which spec §4.3 calls out as the worse failure. §2.3's table is the
evidence that it cannot happen; the tests pin the positive direction
(`addFundsId` present ⇒ routed as an addition) as explicitly as the negative.
