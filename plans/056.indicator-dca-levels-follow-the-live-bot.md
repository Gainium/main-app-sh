# 056 — plan

Spec: `specs/056.indicator-dca-levels-follow-the-live-bot.md`.

## 1. Solution

The spec's Assumption names one cause: the per-deal snapshot omits the
indicator ladder's per-level sizes and distances. The fix adds exactly those
to the snapshot and reads them first.

- `types.ts` — `DCAIndicatorLevel { orderSize?, minPercFromLast? }`;
  `DCADealsSettings.dcaIndicatorLevels?: DCAIndicatorLevel[]`.
- `DCAUtils.getInitalDealSettings` — records one entry per `startDca`
  indicator, in ladder order (§4.1).
- `db/schema.ts` — `dcaIndicatorLevels` on the DCA and combo deal schemas
  (§4.2). Without it mongoose drops the field on write.
- `dcaHelper.dcaIndicatorLevel(settings, index)` — the deal's frozen entry,
  else the live `startDca` indicator at that index (§1.1.3, §1.1.4). Used by
  both `createInitialDealOrders` reads (§4.3) and by `addDCAOrderByIndicator`'s
  distance gate, which now reads the aggregated settings it already had in
  scope instead of `this.data.settings` (§4.4).
- `graphql/schema.ts` — `dcaIndicatorLevels: [dcaIndicatorLevelType]` on
  `dcaDealSettings` and `comboDealSettings` (§4.5). Additive.

Decisions the spec left open:

- **Match levels by position, not by indicator `uuid`.** A level IS a
  position in the `startDca` list — `addDCAOrderByIndicator` and
  `nextLadderLevel` both number levels that way — so "safety order #2 costs X"
  is the property to freeze. Matching by uuid would unfreeze a level whenever
  the user replaced its indicator, which is exactly the edit §1.1.2 says must
  not move sizes.
- **A frozen entry wins even when its `orderSize` is empty.** An empty size
  already means "use the deal's `orderSize`", which is itself frozen; falling
  back to the live indicator there would re-open the bug.
- **No backfill of deals already running.** A backfill would have to guess the
  indicator sizes a deal opened with; the bot's current values are exactly the
  wrong guess. Old deals keep today's behaviour until they close (§1.1.3).

JIT tier: **Tier 0/1.** The two reads were inline filters on the live list;
they now go through one named method. Nothing else on the path is pulled
apart.

## 2. Build order

1. `core` — types, snapshot, schemas, `dcaIndicatorLevel`, the three reads,
   GraphQL. Version + changelog.
2. Parent `main-app` — `tests/dcaIndicatorLevelsFrozen.ts`, pointer bump,
   version + changelog.
3. Dashboard (`main-dash-sh`) — the deal-details projection reads the frozen
   levels when present. Separate repo, separate change.

## 3. Blast Radius

1. **Other call sites.** Indicator `orderSize` / `minPercFromLast` are read in
   exactly the three places changed (grep `minPercFromLast`, `startDca` in
   `src/bot`). `comboHelper` overrides `createInitialDealOrders` and never
   reads indicator sizes; it inherits `addDCAOrderByIndicator` and so gets
   §4.4. Hedge DCA runs `dcaHelper`.
2. **`core/` submodule.** Yes — shared, deployed on cloud and self-hosted.
   The pointer is bumped deliberately in the parent.
3. **Contracts in `CLAUDE.md`.** Two, both additive: a new field on the shared
   deal collections (legacy readers ignore unknown fields) and a new field on
   two GraphQL output types (no existing selection changes).
4. **Other tests on this path.** The parent's full mocha suite, notably
   `botSettingsKeepOrders.ts` (settings saves leave running deals alone) and
   `graphqlSchema.ts`.
