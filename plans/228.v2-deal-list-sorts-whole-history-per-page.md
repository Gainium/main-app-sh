# 228 — plan

## Solution

Declare, in `src/db/schema.ts`:

- `dcaDealSchema.index({ userId: 1, status: 1, createTime: -1, _id: -1 })`
- `dcaDealSchema.index({ userId: 1, createTime: -1, _id: -1 })`
- the same two on `comboDealSchema`.

Each index matches the listing's sort key exactly after its equality prefix, so
the planner walks it in order and stops after `skip + limit`. Nothing in
`api.ts` changes: same filter, same sort, same tiebreaker (spec 065).

JIT tier: 0 — index declarations only, no logic touched.

## Contract decisions

- Keep `userId_1_status_1_createTime_-1` and `userId_1` declared (spec §4).
- No partial filter: the no-status listing must see every status.

## Blast Radius

1. Call sites: every reader of `dcadeals`/`combodeals` gets two more candidate
   plans. Equality on `userId` (+ `status`) is a prefix of indexes that already
   exist, so the planner's choice for other shapes can only gain an option. The
   open-deal partial index keeps serving the open-tab GraphQL read.
2. `core/` is shared (main-app-sh): the indexes are created by `syncIndexes()`
   at main-app boot on cloud and on self-hosted. Building them is a one-off
   background build per collection. Each new index is about the size of the
   existing `userId_1`.
3. Write cost: `userId`, `createTime` and `_id` never change after insert;
   `status` changes once (open → closed). Per-tick deal updates touch none of
   these keys, so they don't move the btree entries. Inserts write two more
   index entries.
4. No GraphQL, REST shape, socket or queue contract changes.
5. Tests: `tests/processing/v2PaginationTiebreaker.ts` must stay green.
