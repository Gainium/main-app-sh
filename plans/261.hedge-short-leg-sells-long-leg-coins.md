# 261 — plan

## Build order

1. `baseFunding.ts`: pure `hedgeShortSellFits` (§3.1).
2. `fundingReservation.ts`: `heldByHedgeLongLegs` (§3.2), reusing `restingLocked` for the
   take profits already on the book; 5 s cache, bypassed at the order site.
3. `main.ts`: a `refuseSpendingHeldFunds(order)` hook (default `null`) consulted in
   `_sendOrderToExchange` right after the not-enough-balance cooldown. A refusal sets its own
   `heldFundsShortCircuit`: it is a refusal on the merits, so the not-enough-balance accounting
   (refused-size memory, backoff window once tripped, the "Not enough balance" message) runs as
   for a venue refusal and a repeated attempt backs off; only the row clean-up (write-ahead row
   deleted, no CANCELED write-off) and the Kucoin/Coinbase/Bybit balance retries know it never
   left this process (§3.3).
4. `dcaHelper.ts`: `hedgeShortLegReserveApplies`, the hook override, a
   `spendableForNotEnoughBalance` override for the report, and the `checkBalance` subtraction
   (§3.3, §3.4).

JIT tier: 1. The decision is a pure function; the reads stay in the existing reservation
service; no legacy method is reshaped.

## Contract decisions left open by the spec

- Refusal reason: `Insufficient balance: …` so `matchesNotEnoughBalance` classifies it with the
  venue's own wording; the user sees the existing "Not enough balance" message.
- Scope gate: `!futures && !combo && !isLong && parentBotId` and the user is NOT in the base-funding
  beta (`baseFundingAllowed()`); at the order site the deal is also neither stamped nor carrying an
  action. Combo hedge legs are not in scope.
- Unreadable reads: order site → send (the venue decides, as before); new-deal gate → unknown.

## Blast radius

1. Call sites: `refuseSpendingHeldFunds` is new and only consulted in
   `_sendOrderToExchange`; every non-DCA bot gets `null`, every DCA bot outside the scope gate
   returns before any read. `spendableForNotEnoughBalance` callers (the cooldown block and
   `handleOrderErrors`) see a different figure only for the short leg's base.
2. `core/` submodule: yes — shared engine code; the parent pointer is bumped by `psh`.
3. Contracts: none — no schema, GraphQL, socket or queue change; reads only (`dcadeals` through
   the `{ userId, status }` index, `orders` by `dealId`).
4. Other tests on this path: the `sendOrderToExchange` harness specs and the funding specs
   (`baseFunding.spec.ts`, funding reservation specs) — full core suite.
