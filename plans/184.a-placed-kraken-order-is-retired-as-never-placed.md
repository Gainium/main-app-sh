# Plan 184 — keep an accepted order under its own id; ask before writing off a `'-1'` order

Spec: `specs/184.a-placed-kraken-order-is-retired-as-never-placed.md`.

## Build order

1. `src/bot/main.ts` `sendOrderToExchange`: pin an accepted answer's
   `clientOrderId` to the one sent, and warn on a differing echo (§4.1).
2. `resolveNeverPlacedOrder`: add Kraken spot (exact client-id `getOrder`) and
   KuCoin full futures (open orders, the Coinbase branch) (§4.2).
3. `getOrder`: on `venueOrderId() === null`, wait for an in-flight placement,
   resolve, then either fail with the lookup's reason, continue with the
   adopted id, or answer `orderAbsentOnVenue` (§4.3).
4. `noteOrderNotFound`: never retire on `orderNeverReachedExchange` (§4.4).
5. Version + changelog: core patch, main-app patch + core pointer.

## Contract decisions the spec left open

- Kraken spot only (`ExchangeEnum.kraken`). Kraken futures is addressed by
  client id already, so `venueOrderId` never returns null for it.
- The "venue does not hold it" answer gets its own wording
  (`orderAbsentOnVenue`). It still matches `isDefinitiveOrderNotFound`, so
  the spec 177 retirement after the venue answered is unchanged (§1.1.6).
- The connector's txid echo is not changed here. That fallback is in
  exchange-connector-sh and is filed separately, and §4.1 neutralises any echo.

## JIT extraction tier

Tier 0. The changes sit inside existing branch points, and the new behaviour is
driven through the real methods off the prototype.

## Blast Radius

- Call sites:
  - `getOrder` is called by every reconcile and restart probe, so the new
    branch is reached only for a `'-1'` order on Coinbase, Kraken spot or
    KuCoin full futures. Each such lookup costs one venue read (Kraken: open
    plus up to two closed reads), where it used to cost none. It stops once
    the order is adopted or retired.
  - `resolveNeverPlacedOrder` is also reached from `cancelOrderOnExchange` and
    `_handleUnknownOrder`, so Kraken / KuCoin-FF cancels of a `'-1'` order now
    find a live order and cancel it by its real id (spec 154 behaviour, now on
    these venues too).
- `core/` (main-app-sh): shared, needs a pointer bump in main-app.
- Contracts: none. No GraphQL, socket, queue or schema shape changes. The
  `orders` row gains its real `orderId` and `clientOrderId` instead of being
  split.
- Other tests: `neverPlacedCoinbaseOrder`, `cancelDuringPlacement`,
  `cancelNoExchangeOrderId`, `orderNotFound`, `duplicateClientOrderId`, and the
  rest of `src/**/*.spec.ts`.
