# 067 — Plan

## Solution

Make **the exchange-native symbol the primary key for pair resolution**, with
the documented `BASE_QUOTE` split as the fallback. This is the root cause spec
067 §3 names: the rule is currently "split on `_`, except for X-Perp", and the
exception is the rule.

Two gates have to change, in the order a request meets them.

### 1. The format gate — `validators/bots/schema.ts`

`validateCommonSchema` rejects `!p.includes('_')`. Drop that clause: keep
rejecting non-strings and blank strings, and let the DB-backed resolution
below decide whether the symbol exists. Schema validation short-circuits
before the logic validator, so this clause is what makes a concatenated symbol
unreachable; it is also a *format* assertion standing in for an *existence*
check the next stage already performs, against the authoritative `pairs`
collection and with a better message.

### 2. The resolution gate — one shared rule, applied at its three call sites

New pure function in `bot/utils.ts`, beside the `isXperpPair` special case it
generalises:

```
findPairBySymbol(pairs, input)   // native `pair` exact match, else BASE_QUOTE split
```

Pure by Part 3 — it takes rows and a string, touches no client. Applied at:

- `validators/bots/logic.ts` — DCA/combo `foundPairs` and the
  "following pairs are invalid" message (both currently open-code the split).
- `validators/bots/logic.ts` — grid. This site builds a Mongo *filter* rather
  than holding rows, so it keeps two indexed lookups in the same precedence:
  `{exchange, pair}` first, `{exchange, baseAsset.name, quoteAsset.name}` only
  if that misses. Same rule, expressed against the index.
- `bot/index.ts` — `Bot.checkPairs`, which the clone endpoint calls.
- `server/v2/api.ts` — `submitBacktestRequest`, the fourth copy of the same
  rule, on the same public surface: a body read off a bot is refused there for
  the same reason.

`isXperpPair` stays exported and keeps its other callers (`convertPairs`,
`utils.ts:1500`) — those are Tier 0, off this causal path.

### 3. The clone pair — `server/v2/api.ts` + `server/v2/helpers.ts`

`api.ts:3671-3675` rebuilds a grid clone's pair as
`` `${symbol.baseAsset}_${symbol.quoteAsset}` ``. `Bot.createBot` resolves by
native `pair`, so that value finds no row and the clone is stored with an empty
`baseAsset`/`quoteAsset` (spec §1.3). Delete the grid branch: every bot type
reuses `sourceBot.settings.pair`, which is already native and already exact.
Extract the remaining ternary as `clonedBotPair` in `server/v2/helpers.ts`
(Tier 1 — a named, tested unit beside `addAditionalFields` and
`applyGridFuturesConstraints`, the other helpers this create path uses), so the
choice is assertable without standing up the route.

## Contract decisions the spec left open

- **Format gate wording.** No new error string: an unknown symbol now produces
  the existing DB-backed message (`The pair X is invalid for exchange Y` /
  `The following pairs are invalid for exchange Y: ...`) instead of
  `Field pair contains invalid entries: X`. A caller that was getting a 400
  still gets a 400 on the same field; only the text is more accurate.
- **Precedence direction.** Native-first, not split-first. Measured in spec
  §2.3: no production `pairs` row has `pair === base + '_' + quote`, so the
  exact match cannot capture a `BASE_QUOTE` input, and native-first is the only
  order that cannot silently select a different contract.
- **Trimming.** `findPairBySymbol` trims the input before both attempts,
  matching the existing grid site's `base.trim()`.

## Blast Radius

1. **Other call sites of the changed code.**
   - `validateCommonSchema` is shared by DCA, combo, grid and terminal-deal
     creation — intended: spec §2.2 counts DCA and combo as ~96% of the
     affected bots. Terminal deals take a pair the same way and gain the same
     acceptance.
   - `Bot.checkPairs` has two callers: the v2 clone endpoint (`api.ts:3653`)
     and `changeDCABotPairs` (`bot/index.ts:3193`). Both only gain the ability
     to resolve a native symbol; a `BASE_QUOTE` argument behaves identically.
   - `convertPairs` / `utils.ts:checkPairs` are untouched (Tier 0). Note
     `convertPairs` already passes a separator-free pair through unchanged.
2. **`core/` submodule.** Yes — every file here is under `core/`
   (`main-app-sh`), so this ships to every consuming service and to
   self-hosted. The changed surface is the v2 REST validators and
   `Bot.checkPairs`; no type shape changes.
3. **Documented contracts (root `CLAUDE.md` Danger List).**
   - **#2 public REST `/api/v2/*`** — touched, and deliberately: this is the
     endpoint contract being repaired. The change is **additive on the wire** —
     an input accepted today is accepted tomorrow and resolves to the same
     instrument (`pairRoundTrip.spec.ts` §2.3 pins both directions). Nothing
     is removed. `gainium-mcp`, `n8n-nodes-gainium` and `chrome-extension` send
     `BASE_QUOTE` and are unaffected.
   - **#3 GraphQL schema**, **#4 socket.io events**, **#12 shared Mongo
     collections** — untouched. No stored shape changes; `settings.pair`
     keeps being written as the native symbol, which is what it already was.
   - **#1 `BaseReturn<T>`** — untouched.
4. **Other tests on this path.** `botDetailsFieldPreset.spec.ts` and
   `gridFieldProjection.spec.ts` cover the same read presets (specs 061-063,
   066) and must stay green — this change does not touch the read side at all,
   which is the point of §2.3. Full `npm test` is the gate.
