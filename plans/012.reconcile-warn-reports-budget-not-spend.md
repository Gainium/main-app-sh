# Plan 012 — Reconcile warn reports the attempt budget as the attempt count

Implements `specs/012.reconcile-warn-reports-budget-not-spend.md`.

## Solution

Root cause per §3: `reconcileLookup` never tells anyone how many attempts it
spent, so the call sites interpolate the budget constant. Fix by making the
spend reportable and reporting it — not by rewording the claim away.

Three edits, all in `core/src/bot/`:

1. **`main.ts` — `reconcileLookup` reports its spend.** Add an optional
   `onAttempts?: (spent: number) => void` to `opts`. Count `fetch()` calls
   in a local, invoke the callback once immediately before `return last`.
   Nothing else in the function moves: same stop conditions, same jittered
   backoff, same `T | undefined` return (§4 — the return type is a
   Danger-List-#11 shared export and must not change).

2. **`main.ts` — `getOrderForReconcile` threads it.** Add `onAttempts` to
   its `opts`. Both branches report (§5.3): the no-exchange early return
   calls it with `1` (it spends exactly one `getOrder`, no ladder); the
   normal branch passes it straight into `reconcileLookup`.

3. **`main.ts` — one pure `reconcileUnresolvedWarn(ids, attemptsSpent,
   budget?)`**, used by both loops. Today the message is a 4-line template
   literal duplicated verbatim in `helper.ts:1209` and `dcaHelper.ts:9443`
   — including the `slice(0, 10)` / `…` truncation — and that duplication
   is why the same wrong number is printed in two places. One function, one
   wording, testable (§5.4). `budget` defaults to `reconcileLookupAttempts`
   so the call sites no longer import the constant at all.

4. **`helper.ts` / `dcaHelper.ts` — sum the spend for unresolved orders
   only.** A `let unresolvedLookupAttempts = 0` beside the existing
   `unresolved: string[]`, a per-order `attemptsForOrder` captured via the
   new callback, added to the sum on the `unresolved.push(...)` branch. The
   warn becomes `this.handleWarn(reconcileUnresolvedWarn(unresolved,
   unresolvedLookupAttempts))`.

Counting only the unresolved orders matters: summing every order in the pass
would make "39 order(s) after 172 attempts" and reintroduce exactly the
ambiguity being removed.

### Rejected alternative

Reword both sites to "after up to 3 attempts" (the report's own second
suggestion). It stops the false claim in two lines but leaves the question
that caused the misreading — *did the ladder actually run?* — permanently
unanswerable from the log, and leaves the duplication in place.

### JIT extraction tier

**Tier 2** for the message formatter (pure function, no I/O, its own test) —
it is directly on the causal path (it *is* the defect) and duplicated. Tier
0 for everything around it: `checkOrdersAfterReconnect` in both files is a
large I/O-mixed method, and nothing beyond the four lines named above is on
the path. No ports, no adapters, no restructuring of the loops.

## Blast Radius

1. **Other call sites of `reconcileLookup`** — `main.ts:1127`
   (`getOrderForReconcile`) and `src/bot/orderNotFound.spec.ts`. `onAttempts`
   is an optional field on an existing options object, so both compile and
   behave identically unchanged.
2. **Other call sites of `getOrderForReconcile`** — 4 in this repo
   (`helper.ts:1175`, `helper.ts:1452`, `dcaHelper.ts:9396`,
   `dcaHelper.ts:9534`, `dcaHelper.ts:9697`). Only the two reconnect-loop
   ones (`helper.ts:1175`, `dcaHelper.ts:9396`) pass the new option; the
   restart probes are untouched.
3. **`core/` submodule** — yes, this is `main-app-sh`, shared
   platform-wide (Danger List #11). Mitigated by making every change
   additive: no exported signature narrows, no return type changes, one new
   export. The parent `main-app/src/` references none of these symbols
   (grepped: zero hits).
4. **Contracts owned/emitted by this repo** — none touched. No GraphQL
   shape, no socket.io event name, no REST route, no queue payload, no Mongo
   field. `BaseReturn<T>` is passed through untouched.
5. **The log string itself** — it is operator-facing text, not a contract.
   Grepped `/root/agent-workspace/scripts` and `/root/git/claus-dashboard`
   for consumers of "could not read … order(s)": zero. Nothing parses it.
6. **Other tests on this path** — `src/bot/orderNotFound.spec.ts`
   (`reconcileLookup` stop conditions and call counts) must stay green; it
   is the guard that edit 1 changed nothing behavioural.
