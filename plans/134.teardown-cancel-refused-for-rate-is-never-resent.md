# 134 — plan

## Build order

1. `src/bot/teardownCancelRateLimit.spec.ts` — drives the real
   `cancelOrderOnExchange` off the prototype against a scripted transport
   (same harness as `cancelNoExchangeOrderId.spec.ts`). Red before the change:
   one request, no re-send.
2. `src/bot/main.ts`:
   - module helper `isRateLimitReason` (`too many visits`, `rate limit`,
     `too many requests`, case-insensitive);
   - `teardownCancelRetryDelays()` and `sleepBeforeCancelRetry()` — protected
     seams, so the test runs without real sleeps;
   - in `cancelOrderOnExchange`, after the first answer and before the existing
     routing: when `blockPriceCheck` is set and the answer was not primed from
     the batch, re-send while the answer is a rate-limit refusal.

## Decisions the spec left open

- The re-send sits before the routing, so every outcome reuses it unchanged
  (field copy, promotion, emit, `setOrder`/`deleteOrder`, DB write, the
  unknown-order ladder). No new write path.
- A primed (batched) answer is never re-sent; it is already a venue
  confirmation.

## Blast radius

- `core/` (`main-app-sh`) — shared by cloud and self-hosted. The change only
  runs inside `stop()` on a rate-limit refusal; a running bot's cancel path is
  byte-for-byte the same.
- A stop under rate limiting can take up to ~1.5 min longer per refused order.
  Nothing waits on it with a timeout: the delete route does not await the
  worker, and the bot mutexes have no lock timeout.
- No contract, schema or event name changes.
