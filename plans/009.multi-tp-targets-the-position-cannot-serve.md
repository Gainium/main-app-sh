# 009 — Plan

Spec: `specs/009.multi-tp-targets-the-position-cannot-serve.md` (issue #658).

## Solution

The spec's Assumption names the completion test's `total` as the root cause: it
counts configured targets, not servable ones. The quantity that settles it is
already computed by the arming code, so the fix reuses it rather than deriving
a second answer.

1. **`src/bot/dca/multiTpCompletion.ts`** (new, pure) — `shouldRearmTpTargets`
   replaces the bare `total > filled`. Re-arm iff there are unfilled configured
   targets **and** the deal still has a quantity to close. `null`/`NaN` mean
   "not determined" and re-arm, exactly as `positionReconcile`'s `unavailable`
   does — an absent answer must never book a deal closed.
2. **`dcaHelper.remainingCloseQty`** (new, private) — one call to the existing
   `getTPOrder(..., aggregate = true)`, which returns the un-split take-profit,
   i.e. the whole remaining position. `undefined` (no exchange info / no fee)
   maps to `null`. The just-filled order is subtracted only when the order map
   has not already booked it, so the answer does not depend on whether the fill
   arrived through `getOrders` (which `setOrder`s before `onFilled`,
   `main.ts:5659-5672`) or straight from `checkTPLevel`
   (`dcaHelper.ts:17938`).
3. **`dcaHelper.processFilledOrder`** — the one condition swapped.

### Why not the splitter

Guarding `getTPOrder`'s `qty < minAmount → qty = minAmount` floor against an
exhausted `restQty` looks like the smaller fix and is the wrong one: a deal
with no take-profit order is dropped by `getDealTPLevelToCheck`
(`dcaHelper.ts:15990-16010`), so `checkTPLevel` never runs for it — and 005's
reconciliation probe only fires from `checkTPLevel`. The deal would stop
emitting rejected orders and start sitting open silently, with the backstop
disarmed. Spec §4 records this.

### JIT tier

Tier 2 (runbook): the decision comes out pure, in the `src/bot/dca/` shape the
sibling decisions already use (`positionReconcile`, `tpCloseOutcome`,
`partialTp`). The quantity stays where it is — `getTPOrder` is called, not
extracted; extracting 120 lines of splitter that mutates `price` and `qty`
together is scope the bug does not justify.

## Blast Radius

1. **Other call sites.** `shouldRearmTpTargets` and `remainingCloseQty` are new
   and each has exactly one caller. `getTPOrder`'s `aggregate` mode is used
   today by `updateAssets` (`dcaHelper.ts:8433`, `:8469`) and is read-only —
   this adds a caller, it does not change the function.
2. **`core/` submodule.** Yes — `main-app-sh`, shared with every consuming
   service. The touched code is DCA-engine-only (`dcaHelper`), so the ripple is
   to whoever runs the DCA engine, i.e. main-app. No type in the public surface
   changes; `multiTpCompletion.ts` is a new file with no re-export.
3. **Cross-service contracts (`../CLAUDE.md` § Cross-service contracts).** None
   touched. No GraphQL/REST shape, no socket.io event, no archive queue, no
   Mongo field added or changed — `dcadeals` is read, never re-shaped. The
   deal closes through the existing `closeDeal(botId, dealId, order)` call that
   the last configured target already used, so `bot deal update` payloads and
   the deal-closed alert are unchanged.
4. **Behaviour change, stated exactly.** A multi-TP/multi-SL deal whose books
   say zero base is left now closes on that fill instead of re-arming. Every
   other outcome is byte-identical: a positive remainder re-arms as before, an
   undetermined remainder re-arms as before, and a deal with all configured
   targets filled closes as before.
5. **Other tests on this path.** `src/bot/dca/partialTp.spec.ts`,
   `tpCloseOutcome.spec.ts`, `positionReconcile.spec.ts`, `dealOutcome.spec.ts`
   and `baseOrderQty.spec.ts` all exercise deal-close decisions and must stay
   green (they do — 300 passing).
