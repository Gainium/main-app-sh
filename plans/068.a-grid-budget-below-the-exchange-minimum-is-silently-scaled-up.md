# 068 — Plan

Spec: [`specs/068.a-grid-budget-below-the-exchange-minimum-is-silently-scaled-up.md`](../specs/068.a-grid-budget-below-the-exchange-minimum-is-silently-scaled-up.md)

## §1 Solution

Three pieces, smallest first.

### §1.1 New pure module — `src/bot/gridBudgetGuard.ts` (Tier 2)

Plain functions, no infra imports (only `../utils/math` for step rounding):

- `GRID_BUDGET_TOLERANCE = 0.1`
- `gridLevelMinimum({ unit, minNotional, minQty, step, lowestPrice, highestPrice })`
  → spec §4.3.
- `gridBudgetVerdict({ budget, wanted, minimum, tolerance? })`
  → `{ refuse: false } | { refuse: true, minimumBudget: number | null }` — spec
  §4.1, §4.2.
- `gridBudgetRefusalMessage({ budget, minimumBudget, asset, levels, pair })`
  → spec §4.5.
- `type GridSizingReport = { unit: 'base' | 'quote'; wanted: number; minimum: number }`

Shape mirrors the existing colocated guards (`qtyStepGuard.ts`,
`quantRulesGuard.ts`, `limitOnlyEntry.ts`): a narrowly named file next to the
engine with its own `.spec.ts`. Unlike those it needs no Redis, so it is fully
pure.

### §1.2 The sizing routine reports (Tier 0 on the math)

`MainBot` gains `public lastGridSizing: GridSizingReport | null = null`.
`generateGridsOnPrice` sets it once per call, immediately after the
budget-derived amount is computed and **before** the floor that overwrites it:

| branch | `unit` | `wanted` |
|---|---|---|
| quote / base | `base` | `baseAmount` (pre-floor) |
| quote / quote, base / quote | `quote` | `quoteAmount` (pre-floor, after the NaN fallback) |
| base / base | `base` | unrounded `budget / (…)` behind `tempSellQty` |
| coin-margined (non-Bitget) | `base` | `budget / levels` |

`minimum` comes from `gridLevelMinimum` with the lowest / highest level price of
`initialGrids`. The legacy pre-2022 `else` branch reports `null` (fail-open).

**Why the sizing math is not extracted (not Tier 1/2):** the routine is shared
with six combo call sites and has no equality tests. An extraction whose
correctness cannot be pinned is a rewrite of the money path under cover of a bug
fix. Recording two numbers is additive and cannot change a quantity (spec §1.5,
§4.8). Extraction of the sizing math is a Tier 3 task in its own right — named
here, not folded in.

### §1.3 The start path refuses

`helper.ts` (grid helper mixin) gains
`async refuseStartBelowMinimumBudget(): Promise<boolean>`:

1. no `data` / no `initialGrid` / latest price `0` → `false` (fail-open);
2. `generateCurrentGrids(price, side, all = true, noslice = false,
   returnGrid = true)` — the return-grid overload does not touch `this.grids`;
3. `lastGridSizing` null → `false`; else `gridBudgetVerdict`;
4. on refuse: `handleErrors(message, 'start')`, `serviceRestart = false`,
   `finishLoad = true`, `await this.stop()`, return `true` — the same sequence
   as the existing "cannot run in hedge mode" refusal.

`start()`:

- captures `const serviceRestartAtEntry = this.serviceRestart` before the
  "Last balance change not set, perform full restart" downgrade, so a legacy bot
  that is downgraded during a service restart is still never refused (§4.7);
- after the max-orders check and **before** `if (checkStartCondition) await
  this.swapAssets()`:
  `if (!this.restart && !this.restartProcess && !serviceRestartAtEntry && (await this.refuseStartBelowMinimumBudget())) { endMethod; return }`.
  `restartProcess` is what marks a settings-edit reload: `reloadBot` clears
  `restart` when the user asks for a new start order, so `restart` alone would
  let that variant through to the guard (spec §4.7.1).

**The private cloud parent overrides `start()`.** Its grid helper
(`src/bot/helper.ts` in the parent) extends this mixin and replaces `start()`
wholesale with a twin that adds restart statistics and bot-cost bookkeeping, and
calls `swapAssets()` itself. Wiring the guard only into this repository's
`start()` would protect self-hosted installs and **leave the cloud edition
unguarded**. The parent therefore gets the same one-line guard at the same seam
in its own `start()`, with its own early-return bookkeeping, under its own
spec/plan number and its own test. `refuseStartBelowMinimumBudget()` lives here
precisely so that both `start()` twins call one implementation.

The guard runs whether or not the start price is reached, so a bot waiting in
`range` status is refused at start, not later when the price trigger calls
`swapAssets()`. That later call site therefore needs no guard of its own.

### §1.4 Decisions the spec left open

- **Q1 tolerance** — 10 %, as proposed. One constant.
- **Q2 settings-edit restart** — not guarded (`this.restart` and
  `this.restartProcess` excluded).
  Known-not-addressed; see Blast Radius.
- **Error classification** — none added. The message stays `Uncategorized`
  (spec §4.5); a test pins that no `errorDict` key claims it.

## §3 Blast Radius

1. **Call sites.** `generateGridsOnPrice`: one grid call site
   (`helper.ts generateCurrentGrids`) and six in `comboHelper.ts`. All seven now
   also write `lastGridSizing`; only the new grid method reads it. `start()` of
   the grid helper mixin is used as-is by `src/bot/worker/botService.ts` here
   (self-hosted). The private parent's grid helper extends the mixin but
   **overrides `start()`**, so it inherits the new method and not the wiring —
   see §1.3; the parent change is part of this fix, not a follow-up. `swapAssets()` has three callers; none
   is modified.
2. **`core/` submodule.** Every file touched is in this repository, which is
   embedded as `core/` by the cloud app and shipped to self-hosted installs.
   Both editions get the refusal. Commit here, then bump the pointer in the
   parent deliberately; the parent's commit carries the private evidence.
3. **Owned contracts.** None change. No GraphQL/REST/socket/DB shape is
   touched. The refusal travels as an ordinary bot error message over the
   existing `bot sends message` wire event.
4. **Behaviour change users will see.** A grid bot that today starts with an
   inflated grid will, on its next *user-initiated* start, stop with the new
   message instead. Running bots are untouched by deploys (§4.7). This is the
   intended change, and it is the reason the message states the budget needed.
5. **Known-not-addressed.**
   - Settings-edit restart (`restart = true`) re-sizes through the same floor
     and is not guarded (spec §5 Q2).
   - Combo minigrids floor the same way (spec §1.5).
   - The v2 create endpoint and the dashboard form accept such a budget (spec
     §5 Q3); the dashboard's "Min budget" hint rounds to nearest where §4.3
     rounds up.
   - The balance check in `swapAssets` still divides by leverage; with the
     guard in place it can no longer be reached by an inflated start order.
6. **Other tests on this path that must stay green:** `gridCloseProfitLedger`,
   `nanOrderRefusal`, `qtyStepGuard`, `strandedLocalRefusal`,
   `evidenceFreeFilledPromotion`, `redisSnapshotGuard` — all build on the same
   mixin or on `MainBot`.

## §5 After it ships

The effect is observable: the engine log gains a countable line
(`is below the minimum … Bot will stop`). Capture a baseline at deploy time and
check at +24 h / +72 h that (a) refusals occur only on user-initiated starts,
(b) no bot was stopped during the deploy's own service restart, (c) no new
start order exceeds its bot's budget by more than the tolerance.
