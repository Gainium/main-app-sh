# 127 — Plan: a grid "stop and sell" stops the bot even when the position is already flat

Spec: `specs/127.grid-stop-and-sell-stops-on-a-flat-futures-position.md`.

## Solution

In `BotHelper.closeBotByTp` (`src/bot/helper.ts`), move `this.stop(true)` out
of `if (payload.grid && payload.additional) { … }` to just after it, and give
the futures branch an explicit "position already closed" log so the stop has a
witness in the bot log. The pending-close path keeps its early `return`
inside the block, so it still does not stop (§4.3); a `FILLED` close still
books and then stops (§4.2, §4.4); a flat futures position now stops (§4.1).

This fixes the root cause the spec's Assumption names — the stop being gated
on having built a close order — not the dashboard symptom.

JIT tier: **0**. The method mixes decision and I/O, but the defect is one
misplaced call; extracting the branch would widen a diff on the live
take-profit path for no gain.

## Blast radius

1. Call sites: `closeBotByTp` is called from `priceUpdateCallback` (grid
   TP/SL on price) and from its own reposition / market-timeout timers.
   The timers only run after a pending close order was placed (§4.3 path),
   where behaviour is unchanged. `stop()` is idempotent enough for a second
   call (it clears timers, cancels nothing left, ends the open shift) and the
   new path calls it exactly once.
2. `core/` submodule — shared by main-app on cloud and the self-hosted
   edition. Grid bot workers only; DCA/Combo do not use this method.
3. No GraphQL / REST / socket / queue / collection shape changes.
4. Other tests on this method: `gridCloseProfitLedger.spec.ts` (§4.4 drives
   `closeBotByTp` spot FILLED path), `gridPositionDoubleBook.spec.ts`,
   `gridTransactionProfitRace.spec.ts` — must stay green.
