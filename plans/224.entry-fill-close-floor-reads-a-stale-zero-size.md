# Plan 224 — entry-fill close floor reads a stale zero size

Spec: `specs/224.entry-fill-close-floor-reads-a-stale-zero-size.md`.

## Solution

In `getTPOrder`'s below-minimum branch (`dcaHelper.ts`, spec `035` §4.3 /
`043`), keep the size-derived holding (`trackedPosition`) as the primary
measure. When it reads ≤ 0, fall back to the holding the deal's own executed
entry rows show: base order `executedQty` plus counted safety fills, plus `add`
(closes and reduce-funds, already negated), minus `entryBaseFee` (the base fee
the rows report, already computed above for spot longs), floored to the base
step. Use the fallback only when it is positive.

This fixes the cause the spec's §3 names: the measure read before it was
written. Reordering the base-fill handler so `updateUsage` runs first was
rejected. `updateUsage` needs the balances and average that the handler books
only after the orders are built, and moving that sequence would touch every
fill path.

JIT tier 0: the change is a one-expression addition inside the existing branch
and reuses values the method already computes (`bo`, `filledQty`, `add`,
`entryBaseFee`). No new helper.

## Blast radius

1. Call sites: `getTPOrder` is called from the fill handlers, re-arm paths,
   `checkBalance` and tp-coverage. The new value is read only inside the
   below-minimum branch, and only when the size-derived holding is ≤ 0. Every
   other state computes the same `heldQty` as before (§4.4).
2. The file is under `core/` (main-app-sh), so it is shared by every bot
   worker. The parent pointer needs bumping.
3. No GraphQL, socket, queue or schema change. No persisted field changes.
4. Tests that must stay green: `tpDustClose` (043/047, the EDU zero-holding
   and settle-window cases), `tpPriceRefusal` (035), `tpSizingFromPosition`
   (017), `dcaCloseEntryFee` (098), plus the full core suite.
