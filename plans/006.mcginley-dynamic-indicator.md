# 006. McGinley Dynamic indicator — app-sh plan

Implements [specs/006.mcginley-dynamic-indicator.md](../specs/006.mcginley-dynamic-indicator.md).
Depends on `indicators` repo's `002.mcginley-dynamic-indicator` (spec §
reference: `IndicatorConfig` member `{ type: IndicatorEnum.mg; interval:
number }`) being published as a `@gainium/indicators` version — for this
demonstration PR set, both are developed together on paired branches; the
real dependency bump (`package.json` + `yarn install`) happens once
`indicators` is actually tagged/published, which is outside this repo.

## Build order

1. `types.ts`:
   - `IndicatorEnum.mg = 'MG'`.
   - `IndicatorHistory` union member `{ type: IndicatorEnum.mg; value: number }`.
   - `IndicatorConfig` union member `{ type: IndicatorEnum.mg; interval: number }`.
   - No `SettingsIndicators` field (spec §2).
2. `src/graphql/schema.ts`: add `MG` to the hand-written `IndicatorsEnum`
   SDL block (the one place that doesn't auto-derive from the TS enum —
   spec §3).
3. `src/bot/dcaHelper.ts`: one new signal-interpretation branch, mirroring
   `ATR`/`ADR` exactly (both raw-number results consumed through the
   generic `indicatorValue`/`indicatorCondition` threshold path):
   ```ts
   if (
     lastData.type === IndicatorEnum.mg &&
     prevData?.type === IndicatorEnum.mg
   ) {
     last = lastData.value
     prev = prevData.value
   }
   ```
   Placed alongside the existing `ATR`/`ADR` blocks. No change to the
   config-building ternary (spec §4).
4. `src/server/v2/botDefaults.ts`: new `[IndicatorEnum.mg]` entry —
   `{ ...base, indicatorLength: 14, indicatorValue: '0' }`, matching
   `ATR`'s entry shape (spec §2).
5. Regenerate (do not hand-edit, per spec §3):
   - `npm run generate:definitions` → `src/server/v2/definitions/generated.ts`.
     First run warned `no INDICATOR_META entry for "MG" — using defaults` —
     not foreseen in the original build order. `INDICATOR_META` in
     `src/utils/generate-definitions.ts` is a hand-maintained metadata table
     (name/description/example) the generator reads per indicator; added an
     `MG` entry mirroring `ATR`'s shape (same "generic threshold, no
     bespoke fields" pattern), then re-ran — warning gone.
   - `npm run generate:schemas` → `src/server/v2/openapi-v2.yaml`.
   - `npm run generate:ai-docs` → `AI_API_GUIDE.md` + `SCHEMAS.md`.
6. `CHANGELOG.md` + version bump (this repo's own release ceremony).

## Contract decisions the spec left open (§3)

- **GraphQL enum-only change** — confirmed by reading `schema.ts`: no
  bespoke input/output fields needed, only the `IndicatorsEnum` member.
- **Generated docs, not hand-written** — confirmed by reading each
  generator script's `writeFileSync` target; running them is part of gate
  5/6, not a manual doc-writing step.
- **No `src/indicators/test.ts` harness in this repo** — use this repo's
  actual idiom (mocha/chai, `src/**/*.spec.ts`) for gate 2/6 instead.

## JIT legacy extraction tier (`dcaHelper.ts`)

**Tier 0 — not extracted, left as-is.** `checkIndicatorConditions` is a
single, ~10,000-line-spanning method mixing decision logic for ~35
indicator types with class state (`this.data`, `this.indicators`,
`this.handleDebug`). The new branch for McGinley is 4 lines, structurally
identical to the existing `ATR`/`ADR` branches sitting right next to it,
and this method currently has **zero** test coverage for *any* of its ~35
existing branches (confirmed: grepped every `*.spec.ts` in the repo for
`checkIndicatorConditions`/`dcaHelper`, no hits). Extracting only the new
branch into a pure, tested function while its 30+ siblings stay inline
would be inconsistent with the surrounding code and disproportionate to a
4-line addition that introduces no new decision logic (the actual
crossing/threshold math it feeds into is pre-existing, shared, and
untouched). Not a drive-by rewrite candidate — flagging that this method
overall is a Tier-1/2 candidate for whoever eventually does a deliberate
pass over it, but that pass is out of scope here.

## Blast Radius

1. **Other call sites** — grepped `IndicatorEnum.lw`/`lwThreshold` (the
   closest recent-addition precedent) across the repo to enumerate every
   file a new indicator touches: `types.ts`, `src/db/schema.ts`,
   `src/graphql/schema.ts`, `src/server/v2/{validators/bots/config.ts,
   botDefaults.ts, openapi-v2.yaml, definitions/generated.ts}`,
   `src/bot/dcaHelper.ts`. Checked each explicitly in §2/§3 of the spec —
   most need **no change** because McGinley has no bespoke fields (LW's
   footprint is large *because* LW has 4 bespoke fields; McGinley has
   zero).
2. **`core/` submodule** — N/A here; **this repo is itself `app`'s `core/`
   submodule** (`app-sh` = `main-app-sh`). Everything in this PR is
   therefore the shared/deployed-platform-wide layer by definition — the
   outer `app` repo's own change is just a submodule-pointer bump (out of
   scope for this 3-repo demonstration, matching `indicators`' plan
   already flagging `app`/outer as out of scope).
3. **Contract surface this repo's `CLAUDE.md` documents as owned** — the
   GraphQL schema and the public v2 REST API are both explicitly
   cross-service contracts (dashboards consume GraphQL; `gainium-mcp`/
   `n8n-nodes-gainium`/`chrome-extension`/the in-app AI agent consume v2).
   Both are touched here (steps 2 and 5) — additive only (`MG` is a new
   enum member, not a change to any existing member), so no existing
   consumer's behaviour changes.
4. **`@gainium/backtester`** — same gap already named in `indicators`'
   plan: a bot using `MG` will not backtest correctly until a separate
   backtester PR lands (out of scope here, flagged not silently skipped).
5. **Other tests exercising this path** — none currently exercise
   `dcaHelper.ts` (see JIT tier note above); the new `botDefaults.spec.ts`
   is additive, doesn't change any existing indicator's defaults.
