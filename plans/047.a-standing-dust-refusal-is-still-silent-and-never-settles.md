# Plan 047 — A standing dust refusal is still silent, and a fully-exited deal never settles

Spec: [`specs/047`](../specs/047.a-standing-dust-refusal-is-still-silent-and-never-settles.md).

## Build order

1. **`src/bot/dca/positionReconcile.ts`** — add the spot verdict as a pure
   function beside `reconcileDealAgainstVenue`, and let
   `dealPositionGoneMessage` take the clause naming what the deal was doing when
   the probe ran (it currently hard-codes "reached its take profit", which is
   only true of the `checkTPLevel` caller).
2. **`src/bot/dcaHelper.ts` `reconcileDealPosition`** — branch on `futures`
   instead of returning at the first line. Probe cooldown, two-agreeing-probes,
   `clear()` and `closeDeal` stay where they are and are shared by both venues.
3. **`src/bot/dcaHelper.ts` `getTPOrder`** — `refuseBelowMinimum` becomes async:
   clamp the printed quantity, ask (2) when the deal's holding is at or below
   zero, and otherwise report on the first occurrence.
4. **Delete** `CLOSE_BELOW_MINIMUM_REPORT_AFTER` and the
   `closeBelowMinimumStreak` map — nothing else reads them.

## Contract decisions the spec left open

- **Which balance read.** `getBalancesFromExchange()` rather than
  `this.exchange.getBalance()` directly: it already carries the hard-auth
  short-circuit that stops a dead API key bursting through, which is exactly the
  shape a stuck months-old deal has.
- **What "minimum order quantity" is.** `getExchangeInfo(symbol).baseAsset.minAmount`
  — the same field `getTPOrder` sizes the base grid from.
- **Where the probe is asked from.** Inside `refuseBelowMinimum`, not on the
  price tick: the refusal is reached once per worker start on the deal-load
  path, and `positionProbeBackoff` bounds it to one venue round trip per deal
  per 5 min regardless.

## Blast Radius

1. **Other callers of `reconcileDealPosition`** — one, `checkTPLevel`'s
   `!closeInFlight` branch (spec `005`). It previously returned `false`
   immediately for every spot bot; it will now probe and can settle a spot deal.
   That is the same defect class `005` fixed and is intended, but it is the
   widest edge of this change.
   `grep -n "reconcileDealPosition" src/` → 2 hits, both in `dcaHelper.ts`.
2. **Other callers of `dealPositionGoneMessage`** — one, `reconcileDealPosition`.
   The new parameter is optional and defaults to today's wording, so the `005`
   text is unchanged.
3. **`core/` submodule** — yes. Every consuming service embeds this file, so the
   parent pointer has to move with it. No exported type changes shape; the two
   new exports are additive.
4. **Cross-service contracts** — none touched. No GraphQL, REST, socket.io,
   Redis channel, RabbitMQ queue or Mongo schema field changes. `botmessages`
   rows keep their shape; only the `showUser` flag on one message's rows changes
   from always-false to first-occurrence-true, which is what the spec asks for.
5. **Notification volume** — the thing to watch. Measured over the 44 h since
   `043` shipped: 13 distinct deals, 25 occurrences fleet-wide. Raising each on
   its first occurrence, then deferring to `errorRaiseBackoff` (5 min → 1 h per
   bot and subtype), bounds this at roughly one notification per affected deal's
   bot per window.
6. **Tests that must stay green** — `tpDustClose.harness.spec.ts` (043),
   `tpPriceRefusal.harness.spec.ts` (035), `positionReconcile.spec.ts` (005),
   `tpCoverageReconcile*`, `multiTpCompletion*`, and the rest of
   `src/**/*.spec.ts`.

## JIT legacy extraction tier

Tier 1 for the `getTPOrder` touch — the refusal exit is already a named closure
and stays one; nothing is worth lifting out of a 21k-line method for a
three-line change. Tier 2 for the new spot verdict: it is a pure function with
its own tests, matching `reconcileDealAgainstVenue` next to it. No tier 3 — the
port this would want (`PositionSource`) is a modernization task, not something to
spring on a bug fix.
