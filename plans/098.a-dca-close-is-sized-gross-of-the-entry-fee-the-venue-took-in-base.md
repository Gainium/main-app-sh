# Plan 098 — DCA close net of the observed base entry fee

## Build order

1. `src/bot/dcaHelper.ts` `getTPOrder`, non-combo sizing — compute
   `entryBaseFee = comboEntryBaseFee([bo, ...filledOrders], maxFee, base, quote)`
   for long spot outside the spec-015 gate; when it exceeds `_qty × maxFee`,
   size `_qty − entryBaseFee` instead of `_qty × (1 − maxFee)`.
2. Same method, `tpOrder.qty` rounding — the `zeroFee && !combo` nearest-rounding
   exemption does not apply once an observed fee was netted (floor instead).
3. Version 1.60.17 + CHANGELOG (public: mechanism only).

## Decisions left open by the spec

- **Reuse `comboEntryBaseFee` (spec 097), no new helper.** It already is
  "per row, max(estimate, observed base)". The extra `max` with `_qty × maxFee`
  covers a base-order quantity recovered from the position (`resolveBaseOrderQty`
  source `position`/`nominal`) that no row accounts for.
- **Keep the original expression when observed ≤ estimate** rather than always
  subtracting, so configured-rate accounts stay byte-identical (no float drift
  between `_qty × (1 − f)` and `_qty − _qty × f` at a step boundary).
- **Rounding.** Without step 2 the BNB case nets to 0.014985 and rounds back to
  0.015 on a 0.001 grid — the fix would not fix the reported case.
- **JIT extraction tier:** tier 0/1 — reuse an extracted pure function; the
  surrounding method is not restructured.

## Blast Radius

1. Call sites: `getTPOrder` feeds TP placement, SL, `prepareTpOrder` (market /
   limit close), the refused-close restore and tp-coverage reconciliation — all
   inherit the (only ever smaller) long spot size. `comboEntryBaseFee` gains a
   second caller; its behaviour is unchanged.
2. `core/` submodule (`main-app-sh`), shared with every DCA bot worker. main-app
   parent does not override `getTPOrder`. Pointer bump is the ship pipeline's job.
3. No contract touched: no GraphQL / REST / socket / queue / schema change.
4. Tests on this path: all `dca/*.harness.spec.ts`, `tpFees.spec.ts` — full
   core suite.
