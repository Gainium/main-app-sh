## Order of work

1. The two new modules with their tests — pure, no engine wiring, so they can
   be run in isolation first.
2. `main.ts`: the holder lookup, then swap the refusal string and the settle
   window for the new helpers. The lookup goes in a `try/catch` returning
   `null`; `loadData`'s caller awaits it outside its own try/catch, so a throw
   here would escape the bot entirely (the 2026-08-06 straggler shape).
3. `index.ts`: gate the settle on `closesPosition` so `leave` and non-closing
   actions are untouched, and count deals rather than reading the venue.
4. `npm test`, `npm run lint`, version bump + changelog.

## Risks and how they are bounded

- **A longer wait on the start path.** Only for a stopped holder or no holder,
  and only when the refusal would otherwise stop the bot
  (`!skipFuturesError && !serviceRestart`, unchanged from spec 041). A running
  holder — the case observed refusing five times in three minutes — still gets
  10 s.
- **Extra venue calls.** The park re-reads at 3 s, not 2 s, so ~61 s costs 22
  reads rather than 31.
- **Extra DB reads on the refusal path.** Two `readData`s, capped at 5 rows,
  only when a start is about to be refused.
- **A webhook that now blocks for up to 15 s.** Only after an action that is
  meant to flatten, and only for that bot's own deals. `/trade_signal` already
  awaits each item; this makes the await mean what callers assume it means.
- **Wording.** The first sentence is asserted verbatim in the tests because
  the v2 API and the bot-error rules both depend on it.

## Not in this change

- `findConflictingFuturesPosition` keeps the short wording (no bot to name on
  a synchronous API call).
- A deal whose recorded size is below the venue position — separate defect.
