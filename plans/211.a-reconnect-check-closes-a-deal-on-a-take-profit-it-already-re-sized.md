# Plan 211 — a reconnect check closes a deal on a take-profit it already re-sized

Spec: `specs/211.a-reconnect-check-closes-a-deal-on-a-take-profit-it-already-re-sized.md`.

## Solution
Tier 0 on the touched legacy code, two guards in `src/bot/dcaHelper.ts`:
- `checkOrdersAfterReconnect`: after the venue lookup, read the order from the
  map (`getOrderFromMap`); unless it is still in `orderStatuses`, skip it
  (debug line, no merge, no DB write, not counted for coverage — a terminal
  order rests nothing).
- `closeDeal`: a sweep refusal matched by `isErrorNotEnoughBalance` while a
  `NEW`/`PARTIALLY_FILLED` `dealTP` of the deal other than the closing order
  rests joins the limit-only branch; `closeRemainderByLimit` already cancels
  that take-profit as a re-size before it places the LIMIT.
`getOrder`'s CANCELED-with-fills → FILLED promotion is not touched: other
callers (`_handleUnknownOrder`, the restart check) rely on it.

## Blast Radius
1. Callers: `checkOrdersAfterReconnect` runs for DCA and Combo bots (combo
   inherits it) on reconnect, user start and the reconcile sweep. Grid has its
   own and is unchanged. `closeDeal`'s guard only adds a keep-open case to the
   branch spec `157` added.
2. Under `core/` (main-app-sh): pointer bump needed in main-app.
3. Contracts: none — no schema, GraphQL, socket or queue change.
4. Tests: `limitOnlyCloseRemainder.spec.ts` (spec 157 §1.5 stays green: a
   balance refusal with nothing resting still closes), the full core suite.
