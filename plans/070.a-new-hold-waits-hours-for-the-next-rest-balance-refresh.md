# Plan 070 — a new hold waits hours for the next REST balance refresh

Spec: `specs/070.a-new-hold-waits-hours-for-the-next-rest-balance-refresh.md`.

## Solution
`src/utils/holdRefresh.ts` holds the scheduling rule as a testable factory:
`createHoldRefresh()` returns `schedule(provider, uuid, eventType, run)` /
`cancel(uuid)`. It arms one timer per connection on the FIRST `executionReport`
of a window and ignores the rest, so the refresh runs after the burst rather
than inside it. `holdFromRestOnly` is the one-entry set that gates it —
Kraken spot today.

`connectUserBalance`'s Redis subscription parses the message once and offers the
event to the scheduler before pushing it to `balanceMsg`; the work it schedules
is `refreshBalanceForHold`, which re-reads the user (the event can arrive long
after the document was loaded) and calls the existing `updateUserBalance` for
that one connection. `disconnectUserBalance` cancels a pending refresh.

## Blast Radius
1. Only `ExchangeEnum.kraken` is in `holdFromRestOnly`. Every other venue takes
   one Set lookup per order event and nothing else — no new connector calls.
2. Connector load: bounded at one `getBalance` per Kraken spot connection per
   5 s, and only while that account is trading. The three existing polling
   timers (coinbase 10 min, hyperliquid 10 min, bitget 2 min) are unconditional
   by comparison.
3. `updateUserBalance` is the same call `connectUserBalance` already makes, so
   the write path, the `balance` publish and the spec 069 reconciliation are
   unchanged — only the timing moves.
4. API process only (`connectUserBalance` runs there). Bot workers read the
   collection and are untouched, so no worker restart is needed for this.
5. A refresh failure is logged and dropped; the next order event schedules
   another. No retry loop, no backoff to tune.
6. Interaction with spec 069: this shortens the window in which the stored hold
   is stale, which is exactly the window `streamedFree` subtracts through. It
   cannot make `free` wrong in a new way — a refresh writes both halves from one
   connector answer.
