# 131 — plan

## Build order

1. `src/bot/zeroFee.ts`: `zeroFeeApplies(connection, paperContext)` — the
   eligibility rule now inline in `loadData`, moved verbatim (Tier 2 extraction:
   pure, no I/O).
2. `loadData` uses it (behaviour unchanged).
3. `updateExchangeCredentials` re-derives `this.zeroFee` with it from the
   connection it already re-reads, logging only when the value changes.
4. `setZeroFee` publishes `updateuserStore` `{userId, uuid}` after a successful
   write — the same message and shape `updateExchange` sends.

## Contract decisions

- Reuse the existing `updateuserStore` → `botUpdateUserExchange<thread>`
  channel rather than a new one. Its existing consumer re-instantiates the
  exchange client with unchanged keys (`update=true`, no stream reconnect),
  which is what a key edit already does; no new message, no new subscriber.

## Blast radius

1. Call sites: `zeroFee` is assigned only in `loadData`; `updateExchangeCredentials`
   is called only from the `botUpdateUserExchange` subscription. Every bot type
   (DCA, combo, grid, hedge children) inherits both from `MainBot`.
2. All touched files are under `core/` (main-app-sh) — shared with self-hosted.
   Pointer bump in main-app follows.
3. No GraphQL shape, no socket event, no schema change. `updateuserStore` is an
   existing internal Redis channel, payload unchanged.
4. Other tests on this path: `hedgeMode.harness.spec.ts` (drives `loadData`),
   the `dca/*` harnesses that set `zeroFee` directly. Full `npm test` stays green.
