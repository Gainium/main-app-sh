# Plan 002 — user-stream channel lost on concurrent subscribe

Spec: `specs/002.user-stream-channel-lost-on-concurrent-subscribe.md`.

## Solution (fixes the Assumption, not the symptom)

1. `src/db/redis.ts` `RedisWrapper` — Tier 1 extraction of the pub/sub
   bookkeeping (stays coupled to the node-redis client, but is now
   independently testable through an injected `_instance`):
   - a per-channel `IdMutex` around `subscribe`, `unsubscribe`,
     `resubscribe` (§4.2);
   - `unsubscribe(ch, cb)` returns before touching the client when `cb` is
     not in `subscribeMap` (§4.1); the no-listener form keeps its meaning
     (used by `utils/user.ts` on the `app` instance);
   - new `resubscribe(ch)` (§4.3).
2. `src/bot/main.ts` + main-app `src/bot/main.ts` override
   `setExchangeCredentials`: drop the pre-subscribe `unsubscribe` (§4.4).
3. `src/bot/main.ts`: `userStreamInfoCb` records `lastUserStreamInfoAt`,
   acks via `HSET gainium:userStreamAck:<uuid>` (§4.5), handles `PING`;
   new `resubscribeUserStream()`; silence check piggybacks on the existing
   30 s consumer heartbeat (§4.6). Prober liveness is read from the
   fill-failsafe heartbeat key — a cross-repo contract, documented in the
   Blast Radius below.
4. `src/bot/sharedStream.ts`: `addListener` awaits the client and gains
   `resubscribe(uuid)` (§4.8, used by 3).
5. `src/bot/dcaHelper.ts` `stop()`: call `closeUserStream()` once the last
   deal closed and the bot is closed (§4.7).
6. `src/bot/index.ts` (bot host): internal-API method
   `resubscribeUserStream(exchangeUUID)` that fans out to every hosted bot
   on that account — the self-heal handle the fill-failsafe calls when a
   sweep goes unacknowledged.

Build order: 1 → tests green → 2, 4, 5 → 3, 6 → main-app pointer bump.

## Blast Radius

1. Call sites of `RedisWrapper.unsubscribe` with a listener: bot `main.ts`
   (`closeUserStream`, `sendBotClosed`), `dcaHelper.ts`/`helper.ts` pair
   unsubscribes, `indicators/service.ts`, `sharedStream.ts`. All pass a
   listener they registered, so §4.1 changes nothing for them. The
   no-listener form: `utils/user.ts:740-741` on the `app` instance —
   unchanged.
2. Everything here is under `core/` = `main-app-sh`, consumed by main-app,
   the self-hosted image, and every bot worker. The main-app submodule
   pointer must be bumped deliberately; bot workers only pick it up on a
   restart (Rule 6 ceremony).
3. Contracts (documented in main-app `CLAUDE.md` Danger List and the root
   `CLAUDE.md`):
   - Redis channel `userStreamInfo<uuid>` gains a `PING <ms>` message; every
     existing consumer only substring-matches its own messages, so this is
     additive.
   - New Redis hash `gainium:userStreamAck:<uuid>` (field botId → ms):
     writer core bots, reader main-app fill-failsafe.
   - Reads `gainium:failsafe:heartbeat` (writer main-app fill-failsafe):
     new optional field `pingMs`. Absent/stale ⇒ the bot treats silence as
     "no prober", never as deafness.
   - Bot-host internal API method `resubscribeUserStream(exchangeUUID)` on
     the existing rabbit RPC queues, caller main-app fill-failsafe.
4. Other tests on the path: `core` `npm test` (all specs); main-app
   `tests/fillFailsafe.ts`, `tests/reconcileLookupRetry.ts`,
   `tests/streamOrderSnapshotStaleness.ts` (invariants gate).

## Contract decisions the spec left open

- Silence threshold default 6 min = 3 × the prober's default 2 min period;
  env `USER_STREAM_SILENCE_MS`.
- The ack hash has a TTL of 1 h refreshed on every write, so it never grows
  past the live population.
- Repair escalation: warn on the 1st and 2nd silent repair; visible
  non-stopping bot error on the 2nd; keep repairing every window.
