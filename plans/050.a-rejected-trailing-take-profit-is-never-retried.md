# 050 — Plan: a rejected trailing take profit is never retried

Spec: `specs/050.a-rejected-trailing-take-profit-is-never-retried.md`

## 1. Solution

Fix the root cause named in spec §3 at the single terminal-refusal branch, by
giving that branch (a) a classification of the refusal and (b) one persisted,
restart-durable per-deal retry record. Nothing else on the close path changes.

### 1.1 New pure module — `src/bot/dca/trailingCloseRetry.ts`

Every decision, none of the I/O. Contents:

- `TRAILING_TP_RETRY_DELAYS_MS = [30_000, 37_500, 45_000, 52_500, 60_000]` and
  `TRAILING_TP_MAX_RETRIES` (spec §4.3, §6.4).
- `isRetryableTrailingCloseRejection(reason)` — the §4.1 **denylist**: order-
  and account-scoped refusals plus §4.2's ambiguous-outcome ones are refused,
  everything else is retried. The module owns its own wording lists rather
  than importing `notEnoughErrors` / `notionalReasons`, because both live in
  modules that import this one's consumer (`main.ts`, `dcaHelper.ts`) and the
  import would be circular. The cross-list invariant is pinned from the test
  instead, which can import both (`trailingCloseRetry.spec.ts` asserts every
  `notEnoughErrors` entry classifies non-retryable). `authGuard`'s
  `AUTH_FAILURE_SIGNATURES` / `VENUE_LOCKOUT_SIGNATURES` are imported
  directly — `authGuard` has no cycle with this module — so a dead credential
  and a lockout cannot drift apart from their owner.
- `isTrailingRetryPending(state, now)` — §6.11. A `retrying` record suppresses
  the live close paths only while it is genuinely pending: until its deadline,
  plus `TRAILING_RETRY_STALE_MS` (5 min) of grace for the attempt itself. Past
  that the record is ignored, so a worker that died in the gap — or a
  re-entered close that returned down a path never reaching the refusal site —
  cannot leave a deal unmanaged. This is the self-releasing property spec 049
  §6.1 said `closeBySl` lacked.
- `nextTrailingRetryDelay(attempts)` and
  `trailingRetryStateAfterRefusal(prev, reason, now)` — the state machine.
  `attempts` counts failed attempts including the initial one, so the sixth
  refusal is what pauses.
- `trailingTpArmingPermitted(state, last, armingLine, isLong)` — the §5.2
  crossing rule, returning `{ permitted, rearmReady }`.
- `closeIsAboveBreakEven({ last, avg, taker, isLong })` — spec 049's floor,
  extracted from the inline arithmetic in `checkDealsStopLoss` because the
  retry path (spec §4.4) is now a second caller of the same rule. Tier 2 of
  the JIT runbook: pure, no engine types. The two callers must not be allowed
  to disagree about what "profitable" means.
- `trailingCloseFailedMessage(dealId, symbol, reason, attempts)` — the user
  wording, pure for the reason `dealOutcome.ts` gives: the whole point of
  §6.6 is a sentence, and sentences get tidied back into being wrong.

### 1.2 New deal field — `trailingClose`

`types.ts`: `TrailingCloseRetry`, a sibling to `DealStartBlock` /
`FeeSizingFallback` (a plain descriptive value object on the deal, written by
the engine, never changing deal status):

```ts
type TrailingCloseRetry = {
  status: 'retrying' | 'paused'
  attempts: number          // failed attempts, the initial one included
  since: number             // ms epoch of the first refusal in this run
  lastAttempt: number
  nextAttempt?: number      // `retrying` only — the restart-durable deadline
  reason: string            // the venue's own text, verbatim
  rearmReady?: boolean      // `paused` only — the §5.2 crossing, earned
}
```

`src/db/schema.ts`: a `trailingClose` block with `_id: false`, added to **both**
the DCA and the combo deal schema, exactly as `startBlocked` is. On the combo
schema it is defensive only — combo has no trail (§6.13), so nothing writes
the field there; it is declared so that a mongoose `strict` drop can never
become the way we find out otherwise.

Why on the deal and not in Redis (where `RetryBackoff` lives): this is per-deal
state that must be read back by the same worker that owns the deal, must be
visible to the user through the deal API (§6.12), and must be consistent with
`trailingLevel` / `trailingMode`, which are already deal fields. `RetryBackoff`
is a per-account/per-constraint *suppression* window with no owner to attach
to; this is a scheduled action on one deal.

### 1.3 Engine wiring — `src/bot/dcaHelper.ts`

| Method | Role |
|---|---|
| `trailingRetryTimers: Map<string, NodeJS.Timeout>` | the in-memory timers |
| `isTrailingCloseInFlight(d)` | `isTrailingRetryPending(trailingClose, now)` — not a bare status test (§6.11) |
| `handleTrailingCloseRefusal(d, reason, closeTrigger)` | the decision at the refusal site; returns whether it took ownership |
| `scheduleTrailingRetry(dealId, delay)` | one timer per deal, replacing any previous |
| `retryTrailingClose(dealId)` | the §4.4 preconditions, then re-enter `closeDealById` |
| `resumeTrailingCloseRetry(d)` | restart durability, from `nextAttempt` |
| `pauseTrailingAfterFailedClose(d, state)` | §6.6: disarm, pause, release, report |
| `clearTrailingRetry(d)` | drop the record, release `closeBySl` |
| `reportTrailingCloseFailed(d, state)` | the event + bot message |
| `clearTrailingRetryTimers()` | §6.10, called from `clearClassProperties` |

Call sites changed:

1. **The refusal branch** (the `else` that writes the CANCELED MARKET row).
   `handleTrailingCloseRefusal` runs first; 049's `disarmTrailing` stays as the
   `false` branch of it. This is the only place the feature is entered.
2. **`checkDealsStopLoss`** — `isTrailingCloseInFlight(d)` joins the existing
   top-of-loop `continue` guard (§6.3). It has to be there and not only on
   `closeBySl`, which is in-memory and gone after a restart (spec §2.3).
3. **`checkTrailing`** — the same guard, plus the `ttp` arming branch gated on
   `trailingTpArmingPermitted`; arming clears the record (§5.3), and an earned
   `rearmReady` is persisted (§6.8).
4. **`restoreWork`** — `resumeTrailingCloseRetry(d)` next to the existing
   `setCloseByTimer(d.deal)`, which is the engine's own idiom for re-arming a
   persisted deadline per active deal (spec §2.4). DCA only: combo overrides
   `restoreWork` wholesale, but it also has no trail — its
   `checkDealsForStopLossMethods` override never calls
   `checkDealsForTrailing`, so `dealsForTrailing` is always empty and no
   refused trailing close can exist there (§6.13).
5. **`clearClassProperties`** — `clearTrailingRetryTimers()` (§6.10).
6. **`checkDealsStopLoss`'s break-even floor** — now calls
   `closeIsAboveBreakEven` instead of computing `net` inline.
7. **`processDealClose`** — `clearTrailingRetryTimer(dealId)`: the deal is
   finished, so a timer still pointed at it has nothing to retry.
   Deliberately NOT in `removeDealFromStopLossMethods`, which the
   settings-change path also calls for a deal that is open and mid-retry —
   clearing there would drop a legitimate retry with nothing to re-arm it
   until the next restart.

**One `saveDeal` per `checkTrailing` iteration, and it goes last.** `saveDeal`
replaces both the wrapper and the deal in the map with copies, so a save made
part-way through that loop keeps the copy while the level computed afterwards
is written to the object the loop is still holding — which would arm a trail at
`trailingLevel: 0`, a trail that then neither closes (`trailingLevelArmed`
needs a non-zero level) nor recomputes (the recompute is gated on `bestPrice`
beating the stored extreme). So both of the loop's new writes — the earned
crossing and the cleared record — are collected into a `retryPatch` local and
persisted after `triggerTrailing`, onto whatever is in the map by then. The
harness models this copy-on-write in its `saveDeal` stub for the same reason,
and asserts the re-armed trail carries a level.

`retryTrailingClose` re-enters `closeDealById` with exactly the arguments
`triggerStopLoss` uses for a trailing close (`closeByMarket`, `sl = true`,
`closeTrigger = trailing`, `count = 0`), so spec 042's `closeTrigger` labelling
and the slippage ladder both behave as they do on the first attempt.

### 1.4 New subType — `src/bot/utils.ts`

`export const trailingCloseFailed = 'Trailing take profit not executed'`,
raised by passing it to `processError` directly and deliberately **not** added
to `errorDict` — the same reasoning the neighbouring `closeNotActioned`
carries: `errorDict` matches on message text and would then claim unrelated
messages.

## 4. Blast Radius

1. **Other call sites of what changes.** `closeDealById`'s refusal branch has
   one entry point and is reached from every close type; the new code is gated
   on `closeTrigger === trailing && trailingMode === ttp` (or an existing
   record), so a manual/TP/SL/API close is untouched. `checkDealsStopLoss` and
   `checkTrailing` are called from the price-update path and
   `checkAllowedMethods`; both changes are additional `continue` conditions
   plus one gate inside the `ttp` arming branch — the `tsl`, plain-SL,
   move-SL, multi-SL and dynamic-AR arms are not touched.
   `clearClassProperties` is called from every start/stop/reload path; the
   addition is one more timer sweep in the shape of the four already there.
   `restoreWork` has a combo override (`comboHelper.restoreWork`) — checked:
   it does not call through, and it does not need to, because combo has no
   trail (§1.3.4). Combo's inherited `checkDealsStopLoss` / `checkTrailing`
   are reached with an always-empty `dealsForTrailing`, so the new guards are
   no-ops there.
2. **`core/` submodule.** Yes — `src/bot/dcaHelper.ts`, `types.ts`,
   `src/db/schema.ts` and `src/server/v2/*` are all in `main-app-sh`, shared
   with every consuming service and with the self-hosted platform. Widest
   blast radius in the repo. The deal-document change is **additive and
   optional** (`trailingClose?`), so an older reader ignores it and a deal
   without it behaves exactly as today.
3. **Documented contracts.**
   - v2 REST: one new optional deal field, on the `standard` preset — additive,
     documented (§1.5). No endpoint, no request shape, no status code changes.
   - GraphQL: unchanged on purpose. A deal read through GraphQL simply does
     not carry the field.
   - Socket: `bot deal update` carries the whole deal document, so consumers
     see the new field appear. Additive; no consumer reads unknown keys.
   - No queue payload, no event name, no `BaseReturn` shape changes.
   - `closeTrigger` labelling (spec 042) is preserved: a retry re-enters with
     `DCACloseTriggerEnum.trailing`, so a retried close is recorded exactly as
     the first attempt would have been.
4. **Other tests on this path that must stay green.**
   `src/bot/dca/trailingTpBreakEvenFloor.harness.spec.ts` (spec 049 — drives
   the same `checkDealsStopLoss`, and its §5.5 source pin asserts the refusal
   branch still contains `disarmTrailing`, which this plan keeps),
   `src/bot/dca/trailingTpCloseTrigger.harness.spec.ts` (spec 042),
   `src/bot/notEnoughBalanceReasons.spec.ts` (the list this feature's denylist
   is pinned against), plus the whole `npm test` suite since `dcaHelper.ts`,
   `types.ts` and `db/schema.ts` are imported almost everywhere.
5. **API v2 presets.** Adding a field to `DCA_DEAL_STANDARD_FIELDS` widens the
   default deal response for every v2 consumer. Additive only; the repo has no
   test asserting the exact key set of a preset (checked), so this is reviewed
   by hand and documented rather than pinned.

## 5. Risk

- **A retry on a refusal whose outcome was actually "accepted".** The spec's
  §4.2 exclusion keeps the ambiguous transport failures out, and §4.4's
  preconditions (deal still `open`, still above break even) are re-checked
  before every retry, so a first attempt that did reach the venue leaves
  nothing for the retry to do. The residual case — a 5xx returned after the
  matching engine accepted the order, with the fill not yet visible to the
  engine — is the one the user explicitly asked to retry; it is bounded by
  `reduceOnly` on futures and by the position-already-closed branch, which
  books the deal closed without an order.
- **A profitable exit still missed.** Six attempts over ~4 minutes cannot
  outlast a 30-minute Kraken lockout. That is deliberate (spec §4.3): past a
  few minutes the price the decision was made on is gone, so the honest
  outcome is the §6.6 message, not an unbounded loop. The trail then re-arms
  on the next genuine crossing.
- **A paused trail that never re-arms.** If price never returns over the
  arming line, the deal stays open — which is the same outcome spec 049
  already chose over closing below break even, and every other exit (stop
  loss, manual close, the resting take-profit order) is untouched (§6.9).
- **Memory.** One `Map` entry and one `setTimeout` per retrying deal, for at
  most a minute each, cleared on every stop path (§6.10) and pinned by a test.

## 6. Not addressed

Spec §7.1 (ambiguous-outcome refusals need a reconcile before a retry),
§7.2 (per-account suppression when many deals share a locked-out account) and
§7.3 (combo, which has no trail today). All three are separate decisions.
