# 045 — Plan

Spec: `specs/045.grid-position-close-pnl-never-reaches-the-profit-ledger.md`.

## Solution

Two call sites, both in `src/bot/helper.ts`, both reusing the existing
`MainBot.saveProfitToDb()` writer. No new helper: `saveProfitToDb()` already
owns the hour bucketing, the `botType`/`terminal`/`paperContext` key and the
`$inc` upsert; a second way to write that ledger would be the defect, not the
fix.

1. **§4.1 futures** — in `profitAfterPositionClosed()`, after `bot.profit` is
   updated, `this.saveProfitToDb(profitUsd, result.updateTime || +new Date())`.
   Placed *inside* the method (not at its two call sites) so the existing
   `position.qty === 0` early return is the dedup (§4.3), and so both callers
   are covered by one line.
2. **§4.2 spot** — in `processFilledStop()`'s `!this.futures` branch, inside the
   existing `if (res.status === StatusEnum.ok)` block,
   `this.saveProfitToDb(profitUsd, res.data.updateTime)`. Exactly the shape
   `createTransaction()` uses at `helper.ts:3658-3660`; the unique `index` on
   `transactions` makes the insert the dedup (§4.3).

3. **§4.4 the other emitter** — `closeBotByTp()`'s spot ledger write keeps its
   value and moves inside its own existing `if (res.status === StatusEnum.ok)`
   block. Not cosmetic: with step 2 in place and this write ungated, a fill that
   `processFilledStop()` already booked is booked again here. Applied in core
   AND in `main-app/src/bot/helper.ts`, which overrides the whole method and is
   the copy production runs.

`closeBotByTp()`'s dead `res.data?.updateTime ?? +new Date()` fallback goes with
the move — inside the ok branch `res.data` is always present, and this is the
shape `createTransaction()` and step 2 use.

### Tier (JIT legacy extraction)

**Tier 0.** The causal path is a missing call to an existing, already-tested
writer, inside two methods that are otherwise correct. Extracting
`profitAfterPositionClosed`'s arithmetic into a pure module would be a rewrite
of code the fix does not depend on — scope creep on a ledger-accuracy fix that
has to ship to live trading engines.

## Blast radius

1. **Other call sites.** `saveProfitToDb` has 3 existing callers in
   `src/bot/helper.ts` / `dcaHelper.ts` family; none are modified.
   `profitAfterPositionClosed()` has two callers (`processFilledStop()` futures
   branch `helper.ts:2863`, `closeBotByTp()` futures branch `helper.ts:4491`) —
   both intentionally inherit the new write, and `main-app`'s subclass override
   of `closeBotByTp` (`src/bot/helper.ts:573`) calls the same core method, so
   the running prod path is covered without editing the parent repo.
   `processFilledStop()` has two callers (`processFilledOrder()` `helper.ts:1947`,
   `processSellAtStop()` `helper.ts:2720`).
2. **`core/` submodule.** Yes — `main-app-sh`, shared with self-hosted. The
   change adds no exported symbol, no type change and no signature change; it is
   a behavioural fix confined to two method bodies.
3. **Cross-service contracts (root `CLAUDE.md` Danger List).** None touched. No
   GraphQL schema change (#3), no socket event change (#4), no `BaseReturn`
   (#1), no queue payload (#6). Item #12 (shared Mongo collections) is adjacent
   but unchanged in *shape*: `userProfitByHour` gains rows/values it should
   always have had; its documents keep the same fields, and the only readers
   (`resolvers.getProfitByUser`, the ClickHouse snapshot mirror) already sum
   `profitUsd`.
4. **Known consequence, deliberate.** Statistics for *future* grid closes will
   include the close leg. Historical rows are **not** back-filled — past grid
   closes stay missing from the ledger, so an old day's figure does not change.
   A back-fill (replay `bot.profit` − Σ transactions per closed grid bot into the
   ledger hour of the close) is a separate, data-writing task and is not part of
   this fix.
5. **Other tests on this path.** `src/bot/evidenceFreeFilledPromotion.spec.ts`
   and the `dca/*.harness.spec.ts` family stub `saveProfitToDb()`; the full
   mocha suite must stay green.
