# 031 — plan: an add-funds order consumes a configured DCA level

Spec: [`specs/031.add-funds-consumes-a-configured-dca-level.md`](../specs/031.add-funds-consumes-a-configured-dca-level.md)

## 1. Solution

Two counts in `dcaHelper.ts` answer "where is this deal in its configured
ladder", and both read a value that an add-funds fill also moves. Each gets the
discriminator the rest of the engine already uses for the same question.

### 1.1 `createCurrentDealOrders` — how many levels are left (§4.1)

`filledRegular` currently admits any `dealRegular` row. Filter it through a
named predicate instead:

```ts
.filter((o) => isLadderOrder(o))
```

with `isLadderOrder(order) = order.typeOrder === dealRegular && !order.addFundsId`.

Not the `D-ROA` client-order-id prefix — spec §3 records why (`getOrderId`
strips dashes on OKX, so an ordinary `D-RO-A…` id reads as `…DROA…`).

### 1.2 `executeNextDcaLevel` — which level is next (§5)

`const level = deal.deal.levels.complete` becomes
`const level = nextLadderLevel(deal.deal)`, i.e.
`levels.complete - (funds?.length ?? 0)` — the subtraction
`getDealDCAByMarketToCheck` already performs on the same pair of fields.
`deal.funds` is append-only (`updateDeal`'s add-funds branch is its only
writer; `reduceDealFunds` books a `dealTP` and never touches it), so the two
terms stay in step for the life of the deal.

§5.3 needs no separate change: `opts.expectedLevel` is compared against this
same `level`.

### 1.3 Extraction tier

**Tier 2** (runbook) for both: each is a one-line boolean/arithmetic decision
currently inlined in a method that also does exchange I/O, and each comes out
fully pure — no DB, Redis, queue or exchange import — into
`src/bot/dca/ladderLevels.ts`, testable with no mocking. Alongside
`baseOrderQty.ts`, `executedFill.ts`, `dealOutcome.ts`, the module's existing
neighbours.

Not Tier 1: nothing here needs infra, so leaving it coupled would be a worse
result for no saving. Not Tier 3: no new port, no adapter, no injection — the
callers keep calling a plain function, and inventing an interface for a
predicate would be ceremony the spec never asked for.

Deliberately NOT extracted: the surrounding `left = dcaOrdersCount - …` /
`sort().slice()` selection. It is on the causal path but is not where the
defect lives, and pulling the ladder selection out of a 23k-line file is a
modernization task, not a bug touch (runbook radius rule).

## 2. Build order

1. `src/bot/dca/ladderLevels.ts` — `isLadderOrder`, `nextLadderLevel`.
2. `src/bot/dca/ladderLevels.spec.ts` — the pure decisions (§4.1, §4.3, §5.1).
3. `src/bot/dca/addFundsLadderSlot.harness.spec.ts` — the real
   `createCurrentDealOrders` and the real `executeNextDcaLevel` over the
   reproduction's order rows (§4.2, §4.3, §5.2).
4. Apply §1.1 and §1.2.
5. `npm test`; then re-run the §2 reproduction against the patched stack.
6. Version bump + `CHANGELOG.md` entry in both repos, admin What's New draft.

## 3. Blast Radius

**1. Other call sites of what is changing.**
`createCurrentDealOrders` has 14 call sites in `dcaHelper.ts` and one in
`comboHelper.ts`'s minigrid path. The change is to the count *inside* it, so
every caller sees it — that is the fix. Combo is unaffected in practice:
`addDealFunds` and `executeNextDcaLevel` both return early on `this.combo`, so
a combo deal has no add-funds `dealRegular` rows and `isLadderOrder` admits
exactly what the old filter admitted.

`executeNextDcaLevel` has one caller (the bot-service internal API) and is
itself new in core 1.58.0.

**2. Is it under `core/`?** Yes — `main-app-sh`, shared, public, deployed
platform-wide (cloud + self-hosted). The submodule pointer in the private
parent gets bumped deliberately after the core commit, and the core commit
message carries no issue ids, forum links or user detail (root `CLAUDE.md` §8).

**3. Documented cross-service contracts.** None touched. No GraphQL/REST shape,
no socket.io event name or payload, no Rabbit queue, no Mongo field added,
removed or retyped. `assets.required` / `usage` / `levels` keep their shapes —
`assets.required` changes VALUE for a deal that has taken add funds, which is
the reported defect being corrected, and both dashboards render whatever
number arrives.

**4. Other tests on this path that must stay green.** `npm test` in core, in
full. `nanLadderRefusal.harness.spec.ts` drives the ladder builder;
`tpCoverageReconcile*`, `tpSizing*`, `resizeCancelPromotion` and
`phantomFillLedger` all run over `dealRegular` order fixtures. None of those
fixtures carries an `addFundsId`, so §1.1 must leave every one of them
unchanged — that is itself the regression check for "a safety order still
counts".
