# 242 — Order execution modes: plan (phase 1)

## Build order

1. `src/bot/dca/orderExecution.ts` — pure module (Tier 2): `resolveExecution`,
   `stageForClose`, `closeTimerPlan`, `clampChasePrice`. No I/O, no engine
   imports beyond enums/types from `core/types.ts`.
2. `dcaHelper.ts` `closeDealById`, LIMIT close branch: replace the two timer
   blocks (the reposition timer and the forced-market timer that overwrote it)
   with one decision from `closeTimerPlan`, fed by the stage's resolved
   execution. The per-deal close context (stage execution, trigger price,
   first-placement time) is kept in a `Map` keyed by deal id, created on the
   first LIMIT attempt and cleared where `startTimeoutTime` is cleared today.
3. Same branch, price: when the stage execution is `chase` with
   `maxChasePerc > 0`, clamp the close price with `clampChasePrice` against the
   stored trigger price.
4. `triggerStopLoss`: resolve `sl`; `chase` → `closeByLimit`, anything else →
   `closeByMarket` (today's behaviour). `split` stays market until phase 3
   (logged once per deal).
5. `checkTPOrder` re-calls `closeDealById` without `closeTrigger`; the stored
   per-deal context carries the stage across re-placements, so the re-call
   needs no new parameter.

## Contract decisions left open by the spec

- Stage for a close with no trigger (re-placement, legacy callers): the stored
  per-deal context; with none, `close` (manual) legacy derivation.
- The trigger price for the chase cap is the first limit price the close used
  (what `closeDealById` priced at the first attempt), not a separately fetched
  quote.

## Blast radius

- **Call sites:** `closeDealById` is called from TP/SL triggers, webhooks,
  indicators, timers, bot stop, manual close, the combo helper (override) and
  `checkTPOrder`. Only the `closeByLimit` branch changes; `closeByMarket` and
  `leave` paths are untouched. `triggerStopLoss` has one caller
  (price watch, `dcaHelper.ts` ~28391).
- **core/ submodule:** every file here is in `core/` (`main-app-sh`, public,
  shipped to self-hosted). Pointer bump via `psh`.
- **Contracts:** no GraphQL/REST/socket/queue change in phase 1 (the settings
  fields were added in the previous step). Mongo: no new collection or field.
- **Tests that must stay green:** `limitTimeouts.harness.spec.ts`,
  `repositionCancel*.harness.spec.ts`, `settleCancelNoFillReport`, every
  `*Close*`/`tp*` harness spec under `src/bot/dca`, plus the full `npm test`.
- **Behaviour change for existing bots:** a bot-driven LIMIT close now goes to
  market after its timeout (default 35 s) instead of after ~10 s. That is the
  documented behaviour; it is the fix.

## JIT extraction tier

Tier 2 for the decision logic (pure module, unit tested). The timer arming in
`closeDealById` stays in place (Tier 0 around it) — only the decision is
extracted; no drive-by refactor of the 30k-line helper.

## Phase 2

- `resolveLimitTimeouts` reads `entryExecution`: chase → reposition =
  `repriceSec`, market timer = `timeoutSec`; limit → no reposition, market timer
  = `timeoutSec`. The close fallback (`limitFallbackTimeout`) stays on the
  legacy switch.
- `getBaseOrder`: order type from `entryOrderType`; a chasing base order is
  capped against its first placement price (`entryTriggerPrice`, per deal,
  cleared in `closeDeal`).
- `updatePartiallyFilledTP` → `armRestingTpTimeout` (once per deal) →
  `expireRestingTp`: cancel the part-filled take profit, then close the rest at
  market (same sequence as `checkTPOrder`). Timer cleared in `closeDeal`.
- Blast radius: `getBaseOrder` has 8 callers (all base-order paths, including
  imports and terminal deals); only the order type for a STORED execution and
  the cap change. `updatePartiallyFilledTP` gains a timer only when the bot has
  a stored `limit` take profit with a timeout.

## Phase 3a — split closes

- Pure: `planSplitSizes`, `splitFloorBreached` (`orderExecution.spec.ts`).
- Engine (`dcaHelper.ts`): `maybeStartSplitClose` hooked into `closeDealById`
  before it blocks placement and cancels; `startSplitClose` /
  `placeSplitSlice` / `onSplitSliceFilled` (hooked into the reduce-fill branch
  of fill processing) / `repriceSplitSlice` / `advanceSplitOnTimer` /
  `finishSplitClose`. Slices use `reduceDealFunds` (which records its order id
  in `lastReduceOrderId`); the last slice is `closeDealById` under
  `splitFinalizing`, with a seeded chase context for a chasing last slice.
- State cleared in `closeDeal` and `clearClassProperties`.
- Verified on the local paper stack: 4 market slices 5 s apart, booked as one
  stop-loss close; a bot stop mid-split closes the rest at once.
- Blast radius: `closeDealById` gains an early return only when the stage
  resolves to `split`; `reduceDealFunds` records an id; the reduce-fill branch
  notifies the runner (no-op without a split).

## Base order split (§6.5)

- Pure: `entrySplitEligible`, `entryOrderType` for split, `resolveLimitTimeouts`
  treats a chasing split as chase for slice 1.
- Engine: `applyEntrySplit` right after `getBaseOrder` in `placeBaseOrder`
  (shrinks `origQty` to slice 1; plan per deal in `entrySplits`);
  `onEntryBaseFilled` from `startDeal` (every base-fill path goes through it —
  hooking the fill dispatcher missed synchronous fills); `placeEntrySlice` /
  `sendEntrySlice` via `addDealFunds` (records `lastAddOrderId`);
  `onEntrySliceFilled` from the dealRegular fill dispatch (`addFundsId`);
  `repriceEntrySlice`, `advanceEntryOnTimer`. Cleared in `closeDeal` and
  `clearClassProperties`.
- Verified on paper: 4 market slices 5 s apart; deal holds 4 × slice.
