# 030 — Plan: a manual deal close reports success without acting

Spec: [`specs/030.manual-close-reports-success-without-acting.md`](../specs/030.manual-close-reports-success-without-acting.md)

## 1. Contract decisions the spec left open

- **Where the decision lives.** In `src/bot/dca/dealOutcome.ts`, the existing pure
  module for "how a deal ended, in the words the user reads". It already holds
  `dealCloseEventDescription` / `leftOpenPositionMessage` and has no DB, queue or
  exchange import, so the verdict is testable with nothing mocked. New exports:
  `verdictForMissingDealOnClose(status, closeTrigger)` and
  `unactionedCloseMessage(dealId, symbol)`.
- **How "the caller was answered ok" is detected.** By `closeTrigger`, not by a
  new parameter. `DCACloseTriggerEnum.manual` is produced in exactly four places,
  all of them the `closeTrigger ?? manual` dispatch default in
  `BotInstance.closeDCADeal` / `closeComboDeal`; `api` is produced only by the
  public REST close route, which goes through the same dispatch. No internal
  engine call site produces either. Adding a trailing `dispatched` parameter to
  `closeDealById` was rejected: TypeScript silently accepts an override that
  declares fewer parameters, so a tail argument is exactly the kind of thing that
  goes missing on one relay and not the other (the `handleErrors` /
  `processError` symbol argument did precisely that).
- **Subtype.** A new `closeNotActioned = 'Close request not actioned'` in
  `src/bot/utils.ts`, alongside `positionLeftOpen`, so the admin error rules can
  tune it separately. No `errorDict` entry: the message is raised by calling
  `processError` directly with the subtype, never by string-matching in
  `handleErrors`.
- **Raise shape.** Mirrors `announceLeftOpenPosition`, the nearest precedent for
  "not a failure of the bot, but it must reach the user": a `botEvents` row plus
  `processError(botId, subType, terminal, setError=false, sendError=true,
  message, time, message, force=true, symbol)`.

## 2. Build order

1. `src/bot/dca/dealOutcome.ts` — add the pure verdict + message. (Green: the
   `§4.1` block of the spec test.)
2. `src/bot/utils.ts` — add the `closeNotActioned` subtype constant.
3. `src/bot/dcaHelper.ts` — add `reportUnactionedClose(dealId, closeTrigger)` next
   to `announceLeftOpenPosition`, and call it from the `!findDeal` branch of
   `closeDealById` before the existing `handleWarn` return.
4. `src/bot/index.ts` — delete the dispatch-time `botEventDb.createData`. There
   are **four** of them, not two: `closeDCADeal` and `closeComboDeal` each have a
   `findLocal` branch (the bot is already running — `postMessage` straight to its
   worker) and a `createNewBot` branch (the bot is booted first, then the close is
   posted to it). Both branches write the same premature event and both return
   `ok`, so both have the defect; the `createNewBot` one is if anything weaker
   evidence of a close, since the bot had not even started when it was written.

## 3. Blast radius

1. **Other call sites of `closeDealById`.** 15 in-repo (`comboHelper` ×3,
   `dcaHelper` ×12) plus the two `postMessage` dispatches. The signature is
   unchanged and the new code sits inside a branch that previously did nothing
   but log, so every caller whose deal IS in the map is byte-for-byte unaffected.
   `comboHelper` inherits this method — the combo bot gets the same fix, which is
   intended (`closeComboDeal` has the identical defect).
2. **`core/` submodule.** All four files are under `core/` (`main-app-sh`), which
   is shared with every consuming service and deployed platform-wide — Danger
   List #11. The parent pointer needs bumping. Mitigation: nothing here changes a
   type, a signature or an exported shape that another service consumes; the two
   new exports are additive.
3. **Cross-service contracts (`main-app/CLAUDE.md`).** None touched. No GraphQL
   shape, no REST shape, no socket.io event name, no RabbitMQ queue. `closeDCADeal`
   keeps returning the same `{status: ok, data: 'Deal scheduled to be closed'}` —
   dashboards are unaffected. `botMessages` / `botEvents` gain rows of shapes that
   already exist; the admin Bot Errors page groups by `subType` and will show a
   new one, which is the point.
4. **Behaviour removed.** The dispatch-time `Close DCA deal` / `Close Combo deal`
   bot event, at all four dispatch sites. Grepped for consumers first: the
   strings `Close DCA deal` / `Close Combo deal` / `closed manually` appear
   nowhere in either dashboard (V2 `main-dash-redesign` or V1 `main-dash`) nor
   anywhere else in `main-app`, so no UI filters or labels on them — the rows
   simply stop being written. A confirmed close still writes its own event from
   `processDealClose`, and the `leave` path still writes one from
   `announceLeftOpenPosition` when volume is left behind. The one case that loses
   an event is `leave` on a deal holding nothing — nothing happened, and nothing
   is reported.
5. **Notification volume.** Measured against 37 days of production warnings: 576
   lines, 45 distinct bot+deal pairs, of which one internal hourly retry accounts
   for 518. Gating on `manual`/`api` excludes that pair entirely (it has no
   `main-app` log line at all). The remaining candidates are one line per user
   click.
6. **Other tests on this path.** `src/bot/dca/dealOutcome.spec.ts` (pins the
   wording of the sibling messages) must stay green, as must the rest of
   `npm test`.

## 5. JIT legacy extraction tier

**Tier 2** for the decision, Tier 0 for everything around it. The verdict is
lifted into the existing pure `dealOutcome.ts` module (no DB/queue/exchange
import) and tested with nothing mocked. The DB read and the two raises stay in
`dcaHelper` — they are I/O and belong to the orchestration unit. Nothing else on
`closeDealById`'s 400-line body is on this change's causal path, so it is not
touched.
