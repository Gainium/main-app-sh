# Plan 011 — Cancelling an order that never reached the venue

Spec: `specs/011.cancel-an-order-that-never-reached-the-venue.md`. Issue #671.

## Solution

One guard in `MainBot#cancelOrderOnExchange` (`core/src/bot/main.ts`), taking
the branch condition that already exists in that method and naming it, so the
`'-1'` check and the request builder cannot drift apart:

```ts
const byExchangeId =
  this.data?.exchange === ExchangeEnum.coinbase ||
  this.data?.exchange === ExchangeEnum.kraken ||
  this.kucoinFullFutures
const request =
  byExchangeId && order.orderId === noExchangeOrderId
    ? this.exchange.returnBad()(new Error(orderNeverReachedExchange))
    : await this.exchange.cancelOrder({
        symbol: order.symbol,
        newClientOrderId: byExchangeId ? `${order.orderId}` : order.clientOrderId,
      })
```

Deliberately shaped as a *substitute response* rather than an early `return`:
everything below — the `unknownOrderMessages` scan, the
`Send cancel request … Order not found` log line, the `_handleUnknownOrder`
hand-off — then runs unchanged, and any future change to that routing applies to
this case for free. It is the identical shape `_runUnknownOrderLadder` uses at
`:4753`, which is spec §4.6's reuse requirement.

Tier (JIT legacy runbook): **Tier 0** on the surrounding method. The causal path
is one expression; the smell is a missing check, not mixed decision/IO. The
extraction that would remove the duplication properly — a single "how is this
order addressed at the venue" port shared by `venueOrderId()`, the ladder and
this method — is a real improvement and explicitly **not** taken here, because
`venueOrderId()`'s map-miss fall-through is not the behaviour this call site
wants (spec §5.2) and reconciling the two is a bigger change than the bug.

## Blast Radius

1. **Other call sites.** `cancelOrderOnExchange` has 30+ callers
   (`src/bot/dcaHelper.ts`, `src/bot/helper.ts`, `src/bot/main.ts`,
   `src/bot/combo/*`) plus `cancelGridOnExchange`. None passes the venue id
   itself — every one hands over an `Order` and reads the returned order — so
   the change is invisible to all of them **except** in the one case where the
   returned value differs: previously a transient failure on the wasted call
   returned `undefined` and left the row `NEW`; now that case cannot arise and
   callers get the retired order (or `null`), which is the same value they get
   today whenever the venue answers "not found". `graphql/handlers/orders.handler.ts`
   exports an unrelated same-named function and is not touched.
2. **`core/` submodule.** Yes — this is `main-app-sh`, Danger List #11, shared
   with the self-hosted edition. The parent pointer is bumped deliberately. The
   edit is confined to one method of the bot engine; it changes no exported
   type, no signature and no shared shape.
3. **Cross-service contracts owned by main-app** (GraphQL, `/api/v2`, socket.io
   event names, `ARCHIVE_QUEUES`, shared Mongo schemas): none touched. No new
   entry in `unknownOrderMessages`, so the connector↔main-app error-wording
   coupling is unchanged — `orderNeverReachedExchange` is already matched by the
   existing `'Order not found'` entry and is already produced by two other paths
   in this same file.
4. **Other tests on this path that must stay green.**
   `src/bot/orderNotFound.spec.ts` (it asserts
   `isDefinitiveOrderNotFound('Order not found: no exchange order id') === true`,
   which is what makes the substituted response terminal rather than a retry
   loop), `src/bot/krakenOrderId.spec.ts`, `src/bot/quantRulesRetry.spec.ts`, and
   the rest of `npm test`.
