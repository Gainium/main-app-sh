# Plan 208 — the placement answer opens the deal before the top-up merges

Spec: `specs/208.placement-answer-opens-the-deal-before-the-top-up-merges.md`.

## Solution

`dcaHelper.placeBaseOrder`'s `FILLED` answer branch opens the deal on
`completeFilledBaseEntry(result)` instead of on `result`. The new method is
the stream consumer's two steps, nothing more:

1. answer filled in full (`executedQty >= origQty`, or unreadable) → return it
   untouched (§4.4);
2. otherwise `fillPartiallyFilledOrder(answer)`, which owns the per-order
   mutex, `partiallyFilledFilledSet`, `allowToProcessBr`, the Coinbase skip
   and `buyRemainder`; then `updateOrderOnDb(row, true)` when it grew, as
   `processOrderQueue` and `topUpSettledBaseEntry` do.

Stream first: the call queues on the mutex the stream's top-up holds, then
the post-mutex re-read returns the merged map row (§4.1). Answer first: the
call runs `buyRemainder` itself; the stream's later report hits the re-read
and sends nothing (§4.2, §4.3).

Not `topUpSettledBaseEntry`: its `shouldTopUpSettledBaseEntry` gate (market
entry allowed, entry window) would add a condition the stream path does not
have, which changes whether a top-up is sent (spec §1.3).

JIT tier 0 — one branch and one small method beside its sibling
`topUpSettledBaseEntry`; no extraction, the decision already lives in
`buyRemainder`.

## Blast Radius

1. Call sites: the branch is in DCA `placeBaseOrder` only. `comboHelper`
   has its own copy of the branch (`await this.startDeal(result)`) and is not
   changed here; the brief scopes the DCA engine. `fillPartiallyFilledOrder`
   gains a third caller with the stream's own arguments
   (`settledBaseEntry = false`).
2. `core/` (main-app-sh): shared and public; the parent's pointer is bumped.
   The parent `src/bot/dcaHelper.ts` does not override `placeBaseOrder`.
3. No GraphQL, socket, queue or schema shape changes. The `orders` row is
   written with the same merged quantities the stream path already writes.
4. Mutexes: the answer now waits on `${botId}${clientOrderId}fillPartially
   FilledOrder` while holding `placeBaseOrder`'s lock. The stream's top-up
   (`sendGridToExchange` → `sendOrderToExchange`) takes no `placeBaseOrder`
   lock, so no cycle; the queue already blocks on this mutex during a top-up
   today.
5. Other tests on the path: `placementAnswerAfterStreamFill`,
   `placementFillFeeOnce`, `unfillableTopUp`, `cancelledLimitNoTopUp`,
   `limitOnlyEntryReport`, the rest of `src/bot/*.spec.ts`.
