# 287 — plan

## Build order

1. `helper.refreshTpSlEntry()`: drop the value-changed TP/SL gate; keep only
   `settings && futures && usesUnpairedEntry` (§4.1, §4.5).
2. `helper.updateLiveStats()`: after `lastStatsCheck`, if
   `tpSlEntryPrice(position) === null` (no entry for this position), await the
   refresh it started before computing stats (§4.2, §1.1.3). The cached-entry
   branch of `tpSlEntryPrice()` makes a second sample free.
3. Spec `124` §4.6: note that spec `287` reverses it.

## Decisions the spec left open

- The restart refresh lives in `updateLiveStats`, not in core `start()`: the
  parent `main-app/src/bot/helper.ts` overrides `start()` entirely, so a hook
  there would never run on the grid workers. `updateLiveStats` is armed by
  core's `clearClassProperties`, which the parent start calls.
- No new port or module: the existing `tpSlEntryPrice()` / `refreshTpSlEntry()`
  pair already owns the read and the cache.

## JIT extraction tier

Tier 0. The decision (`gridPositionEntry`, `readUnpairedEntry`) is already
extracted (specs 099/124); only the gate and a call site change.

## Blast Radius

1. Call sites: `refreshTpSlEntry` is called from the fill path
   (`processFilledOrder` → booked.then) and from `tpSlEntryPrice()`;
   `tpSlEntryPrice` from the TP/SL tick and now `updateLiveStats`. Grepped;
   no caller in the parent `src/`.
2. File is under `core/` (main-app-sh, public, platform-wide). Self-hosted
   grids get the same behaviour.
3. Contracts: none changed. `closeEntry` already exists on the bot document,
   GraphQL type and `bot settings update` event (spec 124 §4.7); the V2
   dashboard already consumes it via `gridPositionEntry`.
4. Cost: one ledger read per fill for every neutral futures grid (was: only
   value-changed ones), plus at most one per position from the stats sample.
5. Tests that must stay green: `gridCloseEntry*.spec.ts` (specs 099/117/124),
   the grid TP/SL specs, the full core suite.
