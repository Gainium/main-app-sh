# Plan 235 — an unknown-order lookup drops a merged market top-up

Spec: `specs/235.unknown-order-lookup-drops-a-merged-remainder.md`.

## Solution

In `src/bot/main.ts` `_runUnknownOrderLadder`, `request.status === ok`
branch, before the status comparison: if the row is in
`partiallyFilledFilledSet`, is FILLED, and its `executedQty` is greater than
the venue's converted `executedQty` (0 if the venue states none), log and
return the row. Same shape as spec `088`'s guard in
`fillPartiallyFilledOrder`. JIT tier 0: in-place guard, no extraction.

## Blast Radius

1. Callers of `_handleUnknownOrder`: cancel/unknown-order handling, the
   settle, the placement write-off guard. Only rows already merged by
   `buyRemainder` are affected, and for them the result changes from a
   CANCELED/short write + map removal to "FILLED, unchanged".
2. Rows the set does not hold: unchanged (spec 207 tests stay green).
3. `partiallyFilledFilledSet` holds random client order ids, which are never
   reused, so a stale entry cannot pin an unrelated order.
4. No shared type, GraphQL, socket or Mongo schema change.
