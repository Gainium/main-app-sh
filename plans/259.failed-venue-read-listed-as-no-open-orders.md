# 259 — plan

## Solution

- Per-account result becomes `VenueRead<T> = {rows} | {failed}`; helpers
  `venueNotOk` / `venueThrew` / `lateVenue` build the failed case and log the
  warning (§3.5). `collectVenueReads` merges rows, builds `reason`, and
  reports `allFailed` (§3.1–§3.4).
- Both handlers return `OpenListReturn<T>` = `BaseReturn<T>` plus an OK
  answer that carries a `reason` string. `ReturnGood.reason` is typed
  null-only platform-wide; widening that shared type is out of scope, so the
  widening is local to these two handlers (and the parent repo's thin
  wrapper's annotation).
- JIT tier 1: the merge is pulled into a named function in the same file; no
  further extraction.

## Blast Radius

1. Callers: core + parent `resolvers.ts` GraphQL queries (pass the answer
   through), the import-order / close-position mutations (`.data ?? []` —
   a failed single-account read already yielded "Position not found"; it
   still does). The parent `src/graphql/handlers/orders.handler.ts` wrapper
   (type annotation only).
2. `core/` submodule: yes — shared code; parent pointer bumps via `psh`.
3. GraphQL contract (Danger List #3): shape unchanged; a failed read now
   answers NOTOK / sets `reason`. V2 `useExchangeOrders` /
   `useExchangePositions` read `data ?? []` regardless of status, so partial
   rows still render; `flattenPosition` already treats non-OK as unknown;
   claus `readVenueOrder` already treats non-OK as "venue read failed".
4. Tests: `orders.handler.deadline.spec.ts` (spec 214) stays green.
