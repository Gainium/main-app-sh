# Plan 264 — bot funding charged only for settlements the deal took

## Build order

1. Core `src/bot/dcaHelper.ts` `processDealFunding`: ask the deal commit for the
   updated document (`returnDoc`); `notok` → return; miss → read the deal's
   stored `funding`, adopt it on the live deal, save, return; hit → bot `$inc`
   (also `returnDoc`), live deal from the committed document,
   `setDeal(live)` (saves the snapshot), bot mirror from the stored bot.
2. Parent: bump core; one-off `scripts/repairBotFundingTotals.ts` (dry run by
   default, CAS writes, rollback file); observe invariant in
   `specs/invariants/deals.invariants.json`.
3. Order in prod: deploy the bot workers first, then run the repair, else the
   next restart re-inflates repaired totals.

JIT extraction tier: none. The change stays inside one method and keeps its
shape; the decision is two branches on the existing write result.

## Blast Radius

1. Callers: `onFundingNotify` (settlement notify, startup catch-up) and the
   close-time settle. Combo inherits the method; grid uses its own
   `processGridFunding` (bot-level CAS already gates the `$inc`), unchanged.
2. `core/` file: shared by every main-app deployment (cloud + self-hosted).
3. Contracts: no schema, GraphQL or socket change. `bot settings update` still
   carries `{ funding }`, now the stored value.
4. Other tests on this path: `src/bot/dca/trailingTpRebase.harness.spec.ts`
   ("funding settlement does not undo a save made while it was computing"):
   its fake deal collection now returns the updated document the way
   `findOneAndUpdate` does.
