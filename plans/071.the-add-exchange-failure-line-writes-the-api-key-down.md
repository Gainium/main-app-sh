# Plan 071 — the add-exchange failure line writes the API key down

Spec: `specs/071.the-add-exchange-failure-line-writes-the-api-key-down.md`.

## Solution
`src/utils/keyFingerprint.ts` is a copy of `exchange-connector-sh`'s helper,
byte-identical on purpose (§4.5) — a shared package between the two services
would be a new cross-service dependency for eleven lines of djb2. Both copies of
the `addExchange` failure line swap `key: "${key}"` for `key#${keyFingerprint(key)}`.

## Blast Radius
1. One log line in each of two files. No behaviour, no response, no schema: the
   reason returned to the user was never built from this string.
2. The fingerprint is lossy by construction. Two different keys can collide
   (32 bits); that is acceptable for "tell these attempts apart" and is why the
   spec asks for stability and difference, not uniqueness.
3. Anything downstream that parsed `key: "..."` out of main-app logs would
   break — nothing does; the field has no reader (log-snapshot keeps only
   timestamped signature lines).
4. The existing 682 lines are untouched. New lines stop immediately on deploy of
   the API process; no worker restart is involved.
