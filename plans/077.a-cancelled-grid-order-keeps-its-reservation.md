# Plan 077 — A cancelled grid order keeps its reservation

Implements spec
[`077.a-cancelled-grid-order-keeps-its-reservation`](../specs/077.a-cancelled-grid-order-keeps-its-reservation.md).

## 1. Solution

One method: `comboHelper.ts` `processCanceledOrder`. It is rewritten in place —
no new module, no new helper. Everything it needs already exists on the class:
`getOrdersByStatusAndDealId` (the live-order index), `getMinigrid` /
`setMinigrid` / `saveMinigrid`, `calculateMinigridBalances` (the same fold the
fill path uses at `updateMinigrid`), `updateAssets`.

Order of the method, matching the spec's sections:

1. return unless `typeOrder === dealGrid` (§4.5) — replaces the `!expired` and
   `positionChanged` gates (§4.1);
2. return if the live-order index still holds a `dealGrid` order for the same
   minigrid / side / price / qty — the late-cancel race (§4.2);
3. drop the matching entries from `minigrid.currentOrders` and
   `deal.currentOrders`, matched on `type`, `minigridId`, price, qty, side
   (§4.3);
4. if the minigrid ladder changed, recompute `currentBalances`, `assets`,
   `grids` from it and `saveMinigrid` them (§4.4);
5. `await updateAssets(dealId)` — the line that rewrites `deal.assets.used`
   (§4.4).

### Contract decisions the spec left open

- **Prune all matching entries, not the first.** The pre-existing branch used
  `.filter()`; keeping it means a duplicated level (which the ladder generator
  does not produce) still cannot survive as a phantom. It is safe here
  *because* step 2 already established nothing rests at that level.
- **`saveMinigrid` rather than only `setMinigrid`.** `grids` is a persisted
  field read by the dashboard; leaving it in memory only would keep the level
  counts wrong for anyone reading the deal.
- **No `updateUsage` call.** `usage` is the deal's own ladder (regular orders),
  which this change does not touch.

## 3. Blast Radius

1. **Other call sites.** `processCanceledOrder` is reached from exactly one
   place — `main.ts` `processOrderQueue`'s `onCanceled` callback, wired in
   `dcaHelper.ts:716`. The combo override has no other caller and no
   `super` call today, so widening it cannot change any DCA path. Grepped:
   `processCanceledOrder` appears in `comboHelper.ts` (this override),
   `dcaHelper.ts` (base + wiring) and `dca/venueCanceledBaseEntry.harness.spec.ts`
   (the base's own tests, untouched).
2. **`core/` submodule.** Yes — this is `main-app-sh`, root Danger List #11.
   The method is combo-bot-internal: it is not exported, not part of the
   GraphQL schema, not a socket event, not a REST shape, not a queue payload.
   The shared surface it touches is the `comboMinigrid` document's `grids` /
   `currentBalances` / `assets` fields and `comboDeals.assets`, and it writes
   them to the values the fill path already writes — it corrects them rather
   than changing their meaning. Consumers (both dashboards) read them as-is.
3. **Owned/emitted shapes.** `saveMinigrid` emits `bot minigrid update` and
   `saveDeal` emits `bot deal update` — both already emitted from this path's
   neighbours; no new event, no changed payload shape.
4. **Other tests on this path.** `dca/venueCanceledBaseEntry.harness.spec.ts`
   exercises the *base* `processCanceledOrder` (dealStart / dealTP) and must
   stay green; nothing else touches the combo override.

### Risk the plan accepts

Hedge-combo bots inherit this override. Their minigrid ledger is the same
structure and the same `updateAssets` fold, so the correction applies equally;
there is no hedge-specific branch in either method to break.
