# Plan 182 — resume a close sweep a restart interrupted

Spec: `specs/182.a-restart-during-a-deal-close-sweep-leaves-its-orders-live.md`.

## Build order

   "which recorded sweeps does this start resume" decision (§4.3).
2. `src/bot/main.ts`: `RedisKeys` gains `closeSweeps`.
3. `src/bot/dcaHelper.ts`:
   - state `closeSweeps` (dealId → start ms) and `closeSweepsInFlight`;
   - `loadCloseSweeps` (§4.2), called at the top of `loadOrders`;
   - `processDealClose`: `noteCloseSweep` before the first cancel, `finishCloseSweep`
     after `afterDealClose` (§4.1), only when `cancel`;
   - `resumeCloseSweeps` + the no-op hook `afterCloseSweepResumed` (§4.3), called
     from `restoreWork` before its order checks;
   - the placement loop's spec `160` check also stops on `closeBySl` / `closeByTp`
     unless `afterTerminalCloseRefusal` (§4.4).
4. `src/bot/comboHelper.ts`: the spec `173` database write moves into
   `closeDealMinigridsInDb` (Tier 1 extraction, same filter and gate), used by
   `afterDealClose` and by the `afterCloseSweepResumed` override, which also drops
   the deal's minigrids from memory. Combo `restoreWork` calls
   `resumeCloseSweeps` after `resumeComboFundsChanges`.
5. Version + changelog: core patch bump, main-app patch bump + core pointer.

## Contract decisions the spec left open

- The record is a new field in the bot's existing Redis hash. It is written with
  `setToRedis` and awaited, not through `@RunWithDelay`: the debounce starves under
  exactly the churn that makes a sweep long (§1.2.2).
- An entry is cleared only when no order of the deal is still open in memory. A
  refused cancel (spec `180`) keeps it for the next start, and the resume then
  reads Mongo's state of that order.
- 7-day expiry, so an entry that can never be resolved (deleted account) does not
  stay forever.
- The resume runs on every start mode, not only a cold restart. A user start after
  a crash is the same situation, and the read is one indexed `dealId` query per
  recorded deal.

## JIT extraction tier

Tier 2 for the decision (`closeSweeps.ts`, no I/O). Tier 1 for the minigrid sweep
(`closeDealMinigridsInDb`, moved out of `afterDealClose` unchanged). The rest of
`processDealClose` / `restoreWork` is Tier 0: only call sites are added.

## Blast Radius

1. Call sites: `processDealClose` serves every DCA/Combo close and cancel path. It
   gains a Redis write before the sweep and after it. `loadOrders` and both
   `restoreWork`s gain one Redis read and, only when a record exists, one `orders`
   read by `dealId` (indexed) per recorded deal. The placement break applies
   to every caller of `placeOrders` while a close flag is set. The method already
   refuses those callers on entry.
2. All edits are under `core/` (main-app-sh): shared code. The pointer bump in main-app is
   deliberate, and other consumers pick it up on their own bump.
3. Contracts: no GraphQL / REST / socket / queue / Mongo schema change. The Redis
   per-bot hash gains a field that only this code reads.
4. Tests that must stay green: `closeCancelRefused.spec.ts` (spec 180 sweep),
   `comboCloseDuringReload.spec.ts` (spec 173), `coldRestartOrderSnapshot.spec.ts`,
   `coldRestartDealSnapshot.spec.ts`, the whole core suite.
