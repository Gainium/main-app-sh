# 215 — plan

## Solution

The fix is in `limitOrders` → `placeOne` (`src/bot/helper.ts`). Both the
batched and the sequential paths run through `placeOne`.

1. Add a guard at the top of `placeOne`: `isGridClosing()`, which is
   `stopFilled || blockLimit || data.status === closed`. When it holds,
   `placeOne` returns before it sends anything (§4.1).
2. After `placeRegularOrder` resolves `NEW`/`PARTIALLY_FILLED` on a closing
   bot, call `cancelPlacedAfterClose`. It skips an order that the bot's own
   cancel already claimed (`isOwnCancel`, noted by `primeCancelBatch` /
   `cancelOrderOnExchange` for the stop's snapshot). Otherwise it calls
   `cancelOrderOnExchange(order, false)`. A FILLED answer goes to
   `handleUnknownOrder`, the same as `cancelAllOrder` does (§4.2).

JIT tier 0. The touched code is the placement body, and the change is two
guards plus two small methods. No extraction is needed.

## Blast Radius

- Call sites: `placeOne` is local to `limitOrders`. `isGridClosing` and
  `cancelPlacedAfterClose` are new and have no other callers.
  `placeCanceledLevels` already refuses on `blockLimit` (spec 201 §4.2), and
  this follows it.
- `core/` (main-app-sh) is shared and public. The change sits in the grid
  helper mixin, which only grid bots load. Combo minigrids use
  `comboHelper` and are not touched.
- No GraphQL, socket, queue or schema change.
- An open grid with no close in progress never has `stopFilled`, `blockLimit`
  or a closed status. Each of these is set only by the stop/close paths and is
  reset by a fresh start (`clearClassProperties(_, true)`). Normal placement
  is therefore unchanged (§4.3).
- Suites that must stay green: `src/bot/grid*.spec.ts`, which includes spec
  189 `gridTpCloseSingleShot` and spec 201 `gridVenueCancelReplace`.
