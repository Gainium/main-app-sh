# 020 — a closed deal's off-pair fee ledger never reaches Mongo

Plan for [`specs/020.close-deal-drops-feebyasset-on-save.md`](../specs/020.close-deal-drops-feebyasset-on-save.md).

## Solution

Add `feeByAsset: findDeal.deal.feeByAsset` to the `saveDeal` call at
`dcaHelper.ts:2512-2525`, matching the key `comboHelper.ts:2609-2618`
already uses for the same field:

```ts
this.saveDeal(findDeal, {
  commission: findDeal.deal.commission,
  profit: findDeal.deal.profit,
  updateTime: findDeal.deal.updateTime,
  status: findDeal.deal.status,
  lastPrice: findDeal.deal.lastPrice,
  currentBalances: findDeal.deal.currentBalances,
  size: findDeal.deal.size,
  tpHistory: filledTp,
  feePaid: findDeal.deal.feePaid,
  feeByAsset: findDeal.deal.feeByAsset,
  feeBalance: findDeal.deal.feeBalance,
  ac: findDeal.deal.ac,
  closeTrigger: findDeal.deal.closeTrigger,
})
```

This is the root cause the spec's Assumption names — a one-key
addition to an existing `$set` object literal. Nothing about the
computation, the gating, or `accrueFeeLedger` changes.

## Why no extraction

JIT tier **0**. A missing key in an object literal that is already a
plain, inline `$set` payload — there is no decision logic here to pull
apart, and the sibling combo path already shows the correct shape
in-line, which is what this mirrors.

## Blast radius

1. **Other call sites.** `accrueFeeLedger` has exactly one call site in
   `dcaHelper.ts` (`:2359`, inside this same branch) — grepped and
   confirmed (§4 of the spec: the other `saveDeal(findDeal, {...})`
   calls in this file don't compute `feeByAsset` at all, so they have
   nothing to drop and are unaffected by this change). `comboHelper.ts`
   already includes the field in its own, separate `saveDeal` call —
   untouched.
2. **`core/` submodule.** `main-app-sh` — parent pointer bump at ship
   time.
3. **Contracts this repo owns.** `feeByAsset` is an existing, declared
   `Deal` schema field (`db/schema.ts`, `types.ts:1052` etc.) already
   read by `dca/tpFees.ts`'s live (in-memory) predicate and by the
   combo close path — this only fixes ONE write path to actually
   persist a value that was already being computed and already had a
   home. No shape change, no new field, no consumer to update.
4. **Other tests.** No existing test exercises `closeDeal`'s `saveDeal`
   call's field list directly (confirmed: no test file references
   `saveDeal` with this call's field set). Gate 2 adds the first one.

## Test approach

`closeDeal` lives on the same `MainBot`-derived class as `main.ts`'s
`convertExecutionReportToOrder` (spec 019) — too heavy to instantiate
for a one-key regression (DB singletons, `ExchangeChooser`,
`SharedStream`, per that spec's own JIT reasoning). Unlike spec 019,
there is no natural pure-function extraction here either: the bug is
not in a decision computation, it's a literal object missing a key at
a call site deep inside a ~350-line branch with heavy `this` state.

Extracting the whole branch would be a real rewrite, not a JIT touch —
disproportionate to a one-key fix and explicitly against this skill's
"never a drive-by rewrite" rule. Given no lighter test harness for
`closeDeal` exists in this repo today (confirmed: no
`dcaHelper.*.spec.ts` or `tests/processing/` coverage reaches this
method), gate 2 is satisfied by the LIVE reproduction already on file
in spec 020 §2 — a real paper deal, run end to end, whose `Order`
documents and resulting (broken) deal document are the red evidence.
Gate 6 is the same reproduction re-run after the fix, confirming
`feeByAsset` is no longer empty.

This is flagged, not silently decided: a proper regression test for
`closeDeal` would need the `tests/processing/` integration harness
(in-memory Mongo, `ExchangeChooser` stub — mentioned in this repo's
own recent history, ` feat(test): port app's integration-test harness`)
extended to drive a full base-order → TP-fill → close cycle. That is
larger than this bug fix and is recommended as its own follow-up, not
done here.
