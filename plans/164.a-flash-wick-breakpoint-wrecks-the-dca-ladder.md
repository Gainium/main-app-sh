# 164 — plan: a flash-wick breakpoint wrecks the DCA ladder

## Build order

1. `src/bot/dca/gridBreakpoints.ts` (new, pure):
   - `percentageLadderEnd`: the deepest unrounded level of a percentage
     ladder, the same running sum `createInitialDealOrders` steps through.
   - `isDisplacementInLadder`: whether a displaced price is a positive finite
     number and not beyond that end.
   - `isLevelFilled`: whether a ladder level already has a FILLED ladder
     order at its own price (not PARTIALLY_FILLED, which is still resting;
     not add-funds).
2. `dcaHelper.createInitialDealOrders`: compute the end for a percentage,
   non-ATR/ADR ladder and apply only the breakpoints that pass
   `isDisplacementInLadder` (§1.3, §1.4).
3. `dcaHelper.createCurrentDealOrders`, checked rebuild (`noCheck = false`):
   drop already-FILLED levels from the current orders before the first level
   is examined (§1.1). At the `latestPrice` breakpoint branch, skip and log
   when the market is beyond the ladder's deepest current level (§1.2).
   Dropping (not only refusing the breakpoint) is required: refusing alone
   re-sends the filled level at its own price, above the market, and it fills
   at once. The old code re-sent it at the market price instead.
4. Release: core 1.99.3 + CHANGELOG, parent 2.148.2 + CHANGELOG.

## Decisions left open by the spec

- Bound for §1.2 is the deepest level of the ladder actually in hand
  (`initialOrders`), so it works for every ladder type. Bound for §1.3 is the
  closed form, because the build is what produces that ladder.
- The fill-path breakpoint (`updateDeal`, a real fill price) is not refused at
  creation. §1.3 makes the build ignore it when it lies beyond the ladder.
- No DB migration. Stored breakpoints beyond the ladder become inert on the
  next rebuild (settings edit, fill or reload). Stopping the bot and rewriting
  `gridBreakpoints` is not needed.

## JIT extraction tier

Tier "extract the decision": three pure predicates move out, and the two
methods keep their I/O and control flow. Neither method is restructured,
because each is several hundred lines of mixed logic and only the
breakpoint lines are on this path.

## Blast Radius

1. Call sites: `aggregateBreakpoint` has two callers (`updateDeal` fill path,
   `createCurrentDealOrders`). Only the second gains a refusal. The breakpoint
   lookup in `createInitialDealOrders` is the only reader of
   `gridBreakpoints`. `comboHelper` initialises the field but never reads it.
2. `core/`: shared engine code, used by every DCA/combo/hedge worker that
   extends `dcaHelper`. Behaviour changes only for a breakpoint beyond the
   ladder, a non-positive one, or one for an already-filled level.
3. Contracts: none. No GraphQL, socket, queue or schema change; the stored
   `gridBreakpoints` shape is unchanged.
4. Other tests on this path: `dca/ladderRounding.harness.spec.ts`,
   `dca/nanLadderRefusal.harness.spec.ts`, `combo/ladderRounding.harness.spec.ts`,
   `dca/spentLadderReplace.harness.spec.ts`.
