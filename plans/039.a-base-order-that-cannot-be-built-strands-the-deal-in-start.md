# Plan 039 — A base order that cannot be built strands the deal in `start`

Spec: [`specs/039…`](../specs/039.a-base-order-that-cannot-be-built-strands-the-deal-in-start.md)

## Solution

One guard in `placeBaseOrder`, immediately after `getBaseOrder` returns.

`getBaseOrder` answering falsy means the deal has no entry order and no way to
get one on this attempt. If that deal is in `start` and the engine holds no order
row for it at all, retire it through the existing
`closeDealById(botId, dealId, CloseDCATypeEnum.cancel, reopen = false)` — the
same call `restoreWork` already makes one branch above for a stale non-ASAP
deal — and return.

This is the root cause the spec's §3 names: the deal row is a write-ahead record
that is never retired when the thing it was written for cannot be produced. It is
the same shape as spec `013` (an order row written before the guard that refuses
it) and the fix has the same form — retire the write-ahead record on the refusal
path.

### Why not somewhere else

- **`createDeal` later, after the order is built.** `getBaseOrder` takes the
  `dealId` and writes `balanceStart` onto the deal, and six call sites depend on
  the current ordering. Re-ordering the two is a rewrite of the deal-open path,
  not a fix for this defect.
- **`checkBalance` should refuse instead of bypassing.** Out of scope per spec
  §3: it would report a *balance* shortfall for an *auth* failure, and it would
  not cover the other ways `getBaseOrder` returns empty.
- **A reaper for `start` deals.** Bigger blast radius, and unnecessary: §4.2 gets
  the existing rows healed by the restore path the next time each bot starts.

### JIT extraction tier

**Tier 2** for the decision, Tier 0 for everything around it. The predicate moves
to `src/bot/dca/unbuiltBaseEntry.ts` as a pure function with no imports beyond
the shared enum — matching `partialBaseEntry.ts`, the spec-`038` sibling that
answers the same question about the other stranded shape. The 22k-line
`dcaHelper` mixin around it is untouched: a drive-by extraction there is exactly
the scope creep the runbook forbids.

No new utility duplicates an existing one — `partialBaseEntry.ts` keys on
`PARTIALLY_FILLED`, which is by definition not this shape (this deal has no
order at all), and there is no existing "is this deal inert" helper.

## Build order

1. `src/bot/dca/unbuiltBaseEntry.ts` — pure `shouldDiscardUnbuiltBaseEntry`.
2. `src/bot/dca/unbuiltBaseEntry.harness.spec.ts` — decision tests + the real
   `placeBaseOrder` driven over the mixin. Red before step 3.
3. `src/bot/dcaHelper.ts` — the guard, wired at the `getBaseOrder` return.

## Blast Radius

1. **Other call sites of the changed function.** `placeBaseOrder` has 9 call
   sites in `dcaHelper.ts` and 3 in `comboHelper.ts` (which inherits it). The
   guard fires on the falsy-`baseOrder` path only, which today is a silent
   early return in *every* one of them — so no caller loses behaviour it has.
   For the three callers that pass an `oldDealId` after cancelling a base order
   (`checkBaseOrder`'s two branches, the slippage retry), the cancelled row is
   still in `this.orders`, so `orderCount > 0` and the guard does not fire.
2. **`core/` submodule.** Yes — this file is in the shared submodule, so the
   change reaches every service embedding `main-app-sh`, cloud and self-hosted.
   The parent pointer needs bumping. The behaviour is confined to the DCA/combo
   bot engine; nothing outside it calls `placeBaseOrder`.
3. **Contracts this repo owns.** None touched. No GraphQL field, no socket event
   name, no REST shape, no queue payload, no Mongo schema change. The one
   externally visible effect is that a deal which would have sat at `start`
   forever now reaches `canceled` — a status the dashboard, the API and the
   deal list already handle, and the same one the restore loop already writes
   for stale non-ASAP deals.
4. **Re-entrancy.** `closeDealById` mutexes on `${botId}${dealId}`,
   `placeBaseOrder` on `${botId}placeBaseOrder${symbol}` — different keys, no
   self-deadlock. `reopen = false` is load-bearing: `processDealClose`'s reopen
   branch calls `openNewDeal`, which would re-enter `placeBaseOrder` for the
   same symbol.
5. **Other tests on this path.** `partialBaseEntry.harness.spec.ts`,
   `limitOnlyEntry.spec.ts`, `qtyStepGuard.spec.ts`, `nanOrderRefusal.spec.ts`
   and `strandedLocalRefusal.spec.ts` all exercise base-order placement and must
   stay green.
