# 155 — plan

## Solution

JIT tier 1: three named helpers on `MainBot`. No extraction of the legacy
methods they are wired into.

- `trackPlacement(clientOrderId, send)` runs the venue call of a placement and
  keeps `placementsInFlight[clientOrderId]` while it is outstanding. The entry
  resolves to the venue's order id, or null on refusal / failure, and removes
  itself. It covers only the venue call, never the post-processing, so a waiter
  cannot deadlock on a lock that processing takes (§4.1).
- `awaitPlacementInFlight(order)` waits on that entry when `order` is still
  `'-1'`. On an id it calls the existing `adoptExchangeOrderId` (spec 154), so
  memory and DB get the real id (§4.2/§4.3).
- `cancelOrphanedPlacement(order, venueOrder)` handles a placement reply for an
  order already retired as CANCELED while it was `'-1'`. If the venue has it
  open, it cancels by the real id, calling `exchange.cancelOrder` directly, not
  `cancelOrderOnExchange`, so no fill processing runs against a closed deal.
  Any fills are logged with `handleError` (§4.4).

Wiring:

1. `sendOrderToExchange`: the `openOrder` / batcher call goes through
   `trackPlacement`. Pre-send short-circuits still set `request` before it and
   never register.
2. `cancelOrderOnExchange`: `awaitPlacementInFlight(order)` before spec 154's
   `resolveNeverPlacedOrder`.
3. `_runUnknownOrderLadder`, `byId` block: the same, before
   `resolveNeverPlacedOrder(local)`.
4. `sendOrderToExchange` success branch: when `ord` is CANCELED and `'-1'` and
   the venue returned a real id, call `cancelOrphanedPlacement` before
   `setOrder`. The status merge is unchanged.
5. The ladder takes a `lookups` count. The `'-1'` fast path passes the real
   number, and the write-off line prints it (§4.5).

## Blast radius

- The code is under `core/` (`main-app-sh`, public). DCA/Combo/Grid bot
  workers all extend `MainBot`. The submodule pointer must be bumped.
- No GraphQL, socket, queue or schema change. The only write is `orderId` on
  an `orders` row, which already happens (spec 154).
- Venues: the wait only happens when a cancel or ladder meets a `'-1'` order
  whose placement is in flight. On the venues that cancel by client id, a
  `'-1'` order is not short-circuited, so the wait only gives the cancel a
  real id earlier. The late-reply cancel is venue-independent, but it fires
  only on an order retired while `'-1'`.
- Added latency: a racing cancel waits at most one placement round trip
  (prod: 160–440 ms).
- Log wording: the `Order not found after 5 attempts 2000 ms` line becomes
  `Order not found after N lookup(s)`. Only claus-dashboard's monitor prompt
  prose names the old wording. No parser matches it.
- Tests that must stay green: `cancelNoExchangeOrderId`,
  `neverPlacedCoinbaseOrder`, `cancelBatch`, `cancelPendingKraken`,
  `unknownOrder*`, and every `Object.create(MainBot.prototype)` harness. The map
  is created lazily for those, since field initialisers do not run.
