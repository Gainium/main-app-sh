# 064 — A grid futures position's unrealized value is scaled by `lastPrice / entry`, and the stats of the final window are never flushed

## §1 Definition

A futures grid bot reports its result in two places, and both are derived from
the same quantity — the unrealized value of the open position:

- **the trigger**: `tpSl()` (`core/src/bot/helper.ts`) compares
  `(unrealized + realized) / (initialValue / leverage)` against the bot's
  `valueChanged` take-profit / stop-loss settings;
- **the statistics**: `GridMonitor` (`core/src/bot/gridMonitor.ts`) tracks the
  extreme of that same ratio into `stats.drawdownPercent` /
  `stats.runUpPercent`, and `BotMonitor` (`core/src/bot/botMonitor.ts`) writes
  it into `liveStats.valueChange*`.

### §1.1 Expected

- **§1.1.1** The unrealized value of a position of `qty` base units entered at
  `entry` and marked at `lastPrice` is `qty * (lastPrice − entry)` for a long
  and `qty * (entry − lastPrice)` for a short — exactly the quantity
  `profitAfterPositionClosed()` books as the realized result when that same
  position is closed at `lastPrice`.
- **§1.1.2** A `valueChanged` stop-loss set to −4 % triggers when the bot's
  total result first reaches −4 % of its initial value.
- **§1.1.3** `stats.drawdownPercent` is never smaller than the loss the bot
  actually realized: the deepest point of a losing run includes the moment the
  stop-loss fired.
- **§1.1.4** The same holds on the profitable side, symmetrically:
  `stats.runUpPercent` includes the moment a `valueChanged` **take-profit**
  fired. A bot's final window is a run-up when it stops on its take-profit and
  a drawdown when it stops on its stop-loss; both are measured by the same
  `updateDealStats`, both are lost by the same missing removal path, and both
  must be verified. A bot the engine stopped on a logged
  `Position unPnL 4.8%, in settings 3%, TP trigger` stored a `runUpPercent` of
  2.6 %: the window that fired the stop was never written.

### §1.2 Actual

- **§1.2.1** Every site computes `perc = (lastPrice − entry) / entry` first and
  then `val = qty * perc * lastPrice`, which is
  `qty * (lastPrice − entry) * (lastPrice / entry)` — the true value scaled by
  `lastPrice / entry`. For a long in loss that factor is below 1, so the open
  loss is **understated**; for a short in loss it is above 1, so the open loss
  is **overstated**. The bias is zero only at the entry price and grows with the
  move.
- **§1.2.2** The stop-loss therefore fires late on a long (and early on a
  short), by the same factor: on the reported bot a −4 % stop-loss was still
  reading −3.53 % when the position was really −4.00 % down, and only fired at
  a true −4.6 %, closing at −4.80 %.
- **§1.2.3** `GridMonitor` has **no removal path**: `DealStats.removeStats`
  (`core/src/bot/worker/statsService.ts`) only forwards to
  `DealMonitor.removeDealStats`, and nothing ever drops or flushes a grid bot's
  entry. A grid bot samples its stats at most once every 60 s
  (`lastCheckPerSymbol` in `priceUpdateCallback`), and `completeStats` only
  writes to the bot document on the *next* sample after a window closes — so
  the window that ends with the bot stopping is never sampled and never
  written. The deepest drawdown of a stop-loss close is discarded.
- **§1.2.4** `DealMonitor.removeDealStats` has the same shape: it does
  `this.stats.delete(id)` with no flush, so any DCA/combo deal measurement
  taken since the last window close is dropped when the deal closes.

## §2 Evidence

### §2.1 The reported bot, read back from the API

A paper `binanceUsdm` grid on `SYNUSDT`, `leverage: 1`, `isolated`,
`slCondition: 'valueChanged'`, `slPerc: -0.04`:

```
initialBalances { base: 560, quote: 149.8798 }   initialPrice 0.24342333
initialValue = 560 * 0.24342333 + 149.8798      = 286.19686
stats.drawdownPercent = 0.03449297941195287     = 3.449 %
stats.timeCountStart  = 1789912876593           = 14:01:16.593Z
profit.total          = -30.222178808570057     = -10.56 % of initialValue
```

The stop-loss was set to −4 %. The stored maximum drawdown (3.449 %) is
**smaller than the loss the bot realized** — against the true realized result
(−13.73, −4.796 % of the same `initialValue`) and against the stored
`profit.total` alike. Drawdown and result share the denominator, so there is no
"different bases" explanation: the drawdown is simply wrong.

### §2.2 The engine's own sample is bigger than the stored maximum

At 14:02:05.255Z — 48.7 s after the last flush at `timeCountStart`, and 0.1 s
before the close — the engine logged `Position unPnL -4.16%` from
`tpSl()`. That sample is 4.16 % against a stored maximum of 3.449 %: it was
never persisted, because the next `GridMonitor` sample was not due until
14:02:16 and the bot was gone by then (§1.2.3).

### §2.3 …and that sample is itself understated

`-4.16 %` is `(qty * perc * lastPrice + realized) / initialValue`. Undoing the
`lastPrice / entry` factor on the position leg (0.890 on this bot) gives
−4.796 %, which is exactly the bot's true realized result. So the three numbers
line up as:

| | value |
|---|---|
| true maximum drawdown | **4.796 %** |
| what `tpSl()` computed at that moment (§1.2.1) | 4.163 % |
| what the bot document stores (§1.2.3) | 3.449 % |

### §2.4 The realized side of the same file disagrees with the unrealized side

`profitAfterPositionClosed()` books the close of that very position as
`+result.price * qty - price * qty` — `qty * (close − entry)`, with no
`lastPrice / entry` factor. The unrealized estimate and the realized booking of
the same position therefore disagree by that factor at every price but the
entry.

### §2.5 The sites that carry the expression

`core/src/bot/helper.ts` (`tpSl`), `core/src/bot/gridMonitor.ts`
(`updateDealStats` and `addNewBot`), `core/src/bot/botMonitor.ts`
(grid `liveStats`) — and, outside this repo, the dashboard's client-side
recompute of the same two values in `main-dash-sh`
(`core/src/types/gridBot.ts`, both `calculateCurrentStats` and the live-stats
builder).

## §3 Assumption

Two independent defects compound on the same number:

1. **The formula.** `qty * perc * lastPrice` re-multiplies a ratio that was
   just divided by `entry`, so every unrealized grid position value carries a
   spurious `lastPrice / entry` factor. The correct expression is the signed
   price delta the code already computes: `qty * diff`.
2. **The missing flush.** `GridMonitor` entries are never removed and never
   flushed on stop, so the stats of the last (≤ 60 s) window — the window that
   contains the stop-loss — are lost. Because that window is also never
   *sampled* (§2.2), a flush alone is not enough: the flush has to take one
   final measurement at the price the bot is stopping on.

A fix to (1) alone leaves the stored drawdown short by the missing window; a
fix to (2) alone leaves both the trigger and the drawdown short by
`lastPrice / entry`.

## §4 Scope

- §4.1 `qty * diff` at every site in this repo (§2.5).
- §4.2 `GridMonitor.removeBotStats` — measure at the stopping price, flush,
  then drop — reached from `DealStats.removeStats` and called by the grid
  helper's `afterBotStop()`. **The wait is bounded.** This is the only awaited
  work between the start of `stop()` and the closing order, and the monitor's
  `IdMute` wait queue is a `getFixedArray` whose evicted waiters never settle
  (`core/src/utils/mutex.ts`; this mutex is constructed with no `lockTimeout`,
  so nothing force-releases it either). An unbounded await would turn a stalled
  stats write into a position held open through its own stop-loss — the very
  failure this spec is about. Losing the statistic is the strictly better
  failure: it is what the unfixed build did on every stop.
- §4.3 `DealMonitor.removeDealStats` — flush before dropping (§1.2.4). No final
  measurement: the DCA/combo close path does not carry the deal snapshot,
  usd rate and fee that `addDealStats` needs, so this recovers the measurements
  already taken and not yet written, and no more.
- §4.4 `completeStats` must not `$inc` a negative interval when the flush time
  precedes `timeCountStart` (`DealMonitor.completeStats` already clamps this;
  `GridMonitor.completeStats` does not, and the flush introduces a
  locally-clocked time).
- §4.5 Out of scope, tracked separately: the dashboard's client-side recompute
  in `main-dash-sh` (§2.5) — a different repository and a different deploy.
