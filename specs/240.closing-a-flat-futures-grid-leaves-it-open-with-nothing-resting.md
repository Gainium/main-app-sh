# 240 — Closing a flat futures grid leaves it open with nothing resting

Bug spec.

## §1 Definition

### §1.1 Expected

When a user closes a futures grid with "close at market" or "close at limit"
(`CloseGRIDTypeEnum.closeByMarket` / `closeByLimit`), the bot cancels its grid,
closes whatever position is left with a reduce-only order, and stops. If there
is no position, there is nothing to close and the bot still stops.

### §1.2 Actual

`stop(…, close)` hands off to `processSellAtStop`, which cancels every grid
order and then, for a futures bot, sends a reduce-only close for
`position.qty` whatever that is. With a flat position that is a zero-size order.
`sendOrderToExchange` refuses it ("Order qty must be greater than zero", spec
084 §4.3) and answers nothing. `processSellAtStop` only clears the progress bar
on an empty answer. Nothing stops the bot and nothing retries, so it stays
`open` with every grid order cancelled. Its `levels.active` counters still
describe the grid it cancelled. The dashboard shows it running, and it never
trades again.

The spot branch already handles the equivalent case: nothing worth selling
leads to `stop(true)`. The futures branch had no counterpart.

### §1.3 The same hole in the take-profit / stop-loss close

Core's `closeBotByTp` got this fixed in spec 127, but main-app overrides
`closeBotByTp` wholesale, and its copy kept the pre-127 shape: no close order
for a flat futures position, and `stop(true)` reachable only after a close
order was built.

## §2 Evidence

Production, Bybit USDⓈ-M, neutral futures grid, 2026-11-12 (identifiers
withheld, because this file is public):

- `18:18` the grid starts and places 4 limit orders; none fills (`position.qty`
  stays 0).
- `18:23:23–25Z` all 4 grid orders `CANCELED` (the user's close).
- `18:23:25.954Z` WARN `Order qty must be greater than zero. Order GRID-TP-…
  qty 0, price 0.13929, side SELL Method sendOrderToExchange()`.
- No stop. The bot document stays `status: open`, `levels.active` 2/2,
  `position.qty: 0`, with zero `NEW`/`PARTIALLY_FILLED` orders, until the user
  closes it again at `22:08`. The invariant sentinel
  (`grid.open-bot-nothing-resting`) flagged it.

## §3 Assumption (hypothesis)

`processSellAtStop` has no flat-position branch for futures, and treats an empty
placement answer as final. Checking for a flat position after the grid is
cancelled (fills that land during the cancel have been booked by then), and
then stopping, makes the flat case end like the spot branch does. An empty
answer for a real position should be retried the way a `CANCELED` close already
is.

## §4 Required behaviour

### §4.1 A flat futures position places no order and stops

`processSellAtStop` (market and limit) on a futures grid with
`position.qty <= 0` cancels the grid, sends no order and calls `stop(true)` once.

### §4.2 Unchanged: an open futures position is closed reduce-only

A futures grid with an open position still sends one reduce-only close for the
whole position (MARKET or LIMIT as requested). A FILLED answer goes to
`processFilledStop`. A resting answer arms the reposition timer.

### §4.3 A refused close is retried, not abandoned

When the venue answers nothing for a real position, the method arms the same
reposition timer a `CANCELED` close already arms, and does not stop. Stopping
there would orphan a live position on the venue.

### §4.4 main-app's `closeBotByTp` override stops a flat futures grid

Core spec 127 §4.1–§4.4, applied to the override in main-app
`src/bot/helper.ts` that production runs.

### §4.5 Unchanged: spot

A spot grid sells `sellBaseAmount()` as before.

## §5 Out of scope

- A futures position that is non-zero but below the venue minimum. Its close
  goes out unchanged and is retried under §4.3. `baseAsset.minAmount` is not in
  position units on every contract-sized venue, so stopping on it could orphan
  a real position.
- Rows already left in this state. Each one is a single user close away from
  `closed`, and the sentinel lists them.
