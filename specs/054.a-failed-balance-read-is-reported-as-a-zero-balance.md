# 054 — A failed balance read is reported to the user as a zero balance

Bug spec (Part 0 template: Definition / Evidence / Assumption).

## §1 Definition

### §1.1 Expected

When the engine cannot READ an account's balances — the venue call failed, the
connector returned an error, the request timed out — it does not know what the
account holds. "Unknown" is not "zero".

1. `openNewDeal` must not tell the user their account cannot fund a base order
   on the strength of a read that never returned. That statement is a claim
   about the user's money and it is false.
2. The deal is not opened this cycle. The pair re-arms and the next cycle
   re-reads, exactly as it does when the latest price is unavailable
   (`latestPrice === 0`) or the base order cannot be sized (`!base`).
3. The unreadable read is already reported on its own, by `checkAssets()` →
   `handleErrors(..., 'checkAssets()', 'getBalance')`. It does not need a
   second, contradictory message.

### §1.2 Actual

`checkAssets()` returns the same value for both outcomes: a `Map`. On the
failure paths that `Map` is EMPTY, and `checkBalance()` reads it with
`balance?.get(asset)?.free ?? 0`, so a failed read is scored as an available
balance of exactly 0. `requiredAmount / leverage > 0` is true for every bot
that has ever been configured, so `checkBalance` returns `status: false` and
`openNewDeal` reports:

> Not enough balance to start new deal required: `<n>` `<asset>`, available: 0
> `<asset>`, price: `<p>` `<asset>`

to a user whose account is fully funded.

### §1.3 Also wrong at the same call site

That refusal is the only `handleErrors` call in `openNewDeal` that does not
pass `symbol`. `handleErrors`' 8th argument exists precisely so the
notification names the pair the occurrence failed on instead of the bot's first
configured pair; without it a multi-pair bot's alert names no pair at all.

## §2 Evidence

### §2.1 The reporter's own bot (production, 2026-09-18)

Three consecutive alert events on one DCA bot, read back over the dashboard
GraphQL API:

```
01:50:41.706  error    Could not find user's accounts information
01:50:46.987  error    Could not find user's accounts information
01:50:46.989  warning  Not enough balance to start new deal required:
                       100.09692 USDC, available: 0 USDC, price: 0.471 USDC
```

The two errors are `checkAssets()` → `getBalance` failures. The 5.281 s between
them is `openNewDeal`'s own `await sleep(5000)` retry: first `checkBalance`
fails, second `checkBalance` fails, and 2 ms later the refusal is written. The
same account's later events that day show a quote balance in the thousands, and
five deals opened normally on the same bot within twenty minutes. The account
was funded the whole time.

The three events also show §1.3: every other alert on that bot carries its pair,
these three carry none.

### §2.2 The population

Balance reads fail across the fleet for reasons that say nothing about how much
money an account holds:

| reason (sampled from the engine log, `Step getBalance`) | count |
| ------------------------------------------------------- | ----- |
| `connect ETIMEDOUT <venue>:443`                         | 87    |
| `read ECONNRESET`                                       | 36    |
| `Exchange connector \| Internal Server Error`           | 26    |
| `balances.data is not iterable`                         | 23    |
| `EGeneral:Temporary lockout`                            | 48    |

324 distinct DCA bots hit a failed balance read in the sampled window (the
sample was capped, so that is a floor). Each one is a bot that can be told it
has no money while it does.

### §2.3 The path, in code

`core/src/bot/main.ts` `checkAssets()`:

- the `getBalance` failure branch reports and then `return asset` — `asset` is
  the `Map` built so far, empty whenever `direct = true`;
- the `AuthFailureGuard` cooldown short-circuit does the same;
- when there is no `this.exchange` at all, nothing is read and the empty `Map`
  falls through to the success return.

`core/src/bot/dcaHelper.ts` `checkBalance()` and `core/src/bot/comboHelper.ts`
`checkBalance()` then do `balance?.get(...)?.free ?? 0`. Both call
`checkAssets(true, true)` — `direct = true` — so the DB fallback that could have
supplied figures is skipped by construction and the map is always empty on
failure.

## §3 Assumption

The root cause is that `checkAssets()`'s return type cannot express "I did not
read anything." An empty `Map` is a legitimate success value — it is what an
account that holds none of the pair's assets looks like — so every caller that
treats a missing entry as `0` is correct for a successful read and wrong for a
failed one, and no caller can tell which it got.

The fix is therefore at the producer: a failed read must return a value no
successful read can return. `undefined` is already in `checkAssets()`'s declared
return type and is already what every caller handles (`balance?.get(...)`), so
it is the available signal and no consumer changes shape.

`checkBalance()` then gains a third outcome. Today it answers a yes/no question
("can this fund the order?") and both of its answers assert something about the
account. "I could not read the account" is neither, and must be carried out to
`openNewDeal` rather than collapsed into one of them.

## §4 Required behaviour

### §4.1 `checkAssets()` signals a failed read

A read failure returns `undefined` rather than an empty `Map` when it has
nothing to serve. Failure means: the venue/connector call returned `notok`, the
auth cooldown served a cached rejection instead of calling, or there was no
exchange client to call.

If the DB fallback already produced figures (`direct = false` and at least one
asset resolved), those are still returned — partial data is data, and this must
not regress the callers that rely on it.

A SUCCESSFUL read that finds none of the pair's assets keeps returning an empty
`Map`. That is the value that makes `undefined` unambiguous.

### §4.2 `checkBalance()` carries "unknown" out

`dcaHelper.checkBalance()` and `comboHelper.checkBalance()` return
`{ status: false, unknown: true }` when `checkAssets()` reports a failed read,
logged at debug in the same shape as the existing `latestPrice === 0` and
`!base` bypasses. They must not compute `required`/`available` from a map they
do not have.

### §4.3 `openNewDeal` neither opens nor accuses

On `unknown`, `openNewDeal` logs at debug, calls `resetPending`, invokes
`cbIfNotOpened` and returns. No `handleErrors`, no bot message, no `botevents`
row, no deal.

The standing-condition latch (spec 008) is left EXACTLY as it was found —
neither reported against nor cleared. A failed read is not evidence that a
standing shortfall ended, so clearing it would make a genuine, unchanged
shortfall re-report on every recovery; and reporting against it would consume
the one report the user gets for a condition that was never observed.

### §4.4 A genuine shortfall is unchanged

A successful read that really is short keeps returning
`{ status: false, required, available, price }`, keeps going through the spec
008 latch, and keeps stopping a terminal deal. §4.3 is reached only via the new
`unknown` flag.

### §4.5 The refusal names its pair

The `openNewDeal` shortfall `handleErrors` call passes `symbol` as its 8th
argument.

### §4.6 Out of scope — must not move

- `placeBaseOrder` and the #789 limit-only-entry fallback and its latch. This
  change only decides whether `placeBaseOrder` is reached.
- The `notEnoughBalance` refusal on an individual ORDER
  (`helper.ts` `checkBalances`) — that one reads a balance the venue itself
  returned with the rejection, and is not affected.
- `checkAssets()`'s success path, its DB fallback, and the `AuthFailureGuard`
  cooldown policy.

## §5 Open questions

None. The signal (`undefined`), the carrier (`unknown`) and the latch policy
(§4.3) are decided above because each is a behaviour question, not a build
question.
