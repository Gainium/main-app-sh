# 217 — A reposition cancel loses the fill the user stream reported while it was in flight

Bug spec. Extends `133` (a reposition cancel that races a partial fill), `059`
(a cancel answer that states no fill) and `125` (wait out an asynchronous
cancel).

## §1 Definition

### §1.1 Expected

When the reposition tick of a LIMIT base order cancels it, and the venue's own
end-of-order report (`CANCELED` with an executed quantity) reaches the bot
while that cancel is still in flight, the deal opens on the quantity that
report states. No second base order is placed on top of it.

An entry that filled nothing is still cancelled and re-placed at the new price,
exactly as before (§4.3).

### §1.2 Actual

The reposition arm reads the row (`NEW`, nothing executed), cancels it, and
decides only from the cancel ANSWER and that pre-cancel snapshot. Neither one
holds the fill:

- the snapshot was taken before the fill was reported;
- the stream report replaces the row in the order map with a new object, and
  `cancelOrderOnExchange` then writes the answer onto the OLD object and puts
  it back into the map, so the stream's copy is gone;
- the answer may state nothing executed, still list the order live, or fail.

The deal stays in `start` and `placeBaseOrder` buys the whole entry again. The
account then holds both entries, the deal books only the second one, and its
take profit leaves the first unsold.

The stream callback (`processCanceledOrder`) does not settle the report
either, because the deal still holds reposition timers: by design that
machinery owns the order (specs `038`/`125`).

## §2 Evidence

Production, Hyperliquid spot, LIMIT entry, repositioning on (identifiers
withheld, this file is public):

- `07:47:52` entry placed, 37.16 at the limit; the user stream reports it
  `open` with no fills.
- `07:47:55` the venue fills 37.11 of it. Hyperliquid sends no fill event for
  the resting order.
- `07:48:02.661` reposition tick: "… not filled. Create new one".
- `07:48:03.552` stream: "Processing msg … CANCELED … base: 37.11". The orders
  collection keeps this row (`CANCELED`, `executedQty 37.11`).
- `07:48:08.327` "Send base order": a second entry is placed, fills, and the
  deal opens on it alone. The deal's size is 37.15 against 74.26 executed.

## §3 Assumption (hypothesis)

The reposition arm has no way to see a report that arrived during its own
cancel. Recording the venue's terminal report for an entry while a reposition
is cancelling it, and settling on that report when the cancel answer could not
book a fill, fixes §1.2. Any of the three answers (no fill, still live after
the spec `125` wait, or a failed cancel) ends the same way.

## §4 Required behaviour

- §4.1 While the reposition arm is cancelling an entry, a terminal `dealStart`
  report for it that states an executed quantity is recorded, on the DCA and
  the Combo cancel callbacks. The record is dropped when the arm finishes.
- §4.2 After the cancel, if the answer did not book the entry and a recorded
  report states a fill, the entry is settled through `settlePartialBaseEntry`
  on that report, and no base order is placed. This holds whether the answer
  stated no fill, still listed the order live, or the cancel failed.
- §4.3 With no such report, nothing changes. An unfilled entry is cancelled and
  re-placed as before, and no extra venue call is made.
- §4.4 A deal that already left `start` is not settled again.

## §5 Not covered

A stream report that arrives only AFTER the arm has re-placed the entry is not
recorded, because the arm has already finished. The deal timers are re-armed
by then and the callback defers to them, as before.

## Invariants

Covered by the existing main-app pack invariant
`deals.cancelled-part-fill-base-left-out` (`specs/invariants/deals.invariants.json`
in main-app), which detected this case.
