# 032 — an add-funds fill moves a deal past its next indicator DCA signal

On a DCA bot whose safety orders fire on indicator signals rather than on price
deviation, adding funds to an open deal makes the deal's next signal stop
matching it. The level that was due never fires, and the next signal to arrive
fills a deeper level instead — early, at that level's size.

This is the sibling `031` named as out of scope (§7 there): the ladder-count fix
does not reach this path, so the defect is neither caused nor cured by it, and
was left for its own reproduction. This is that.

## 1. Definition

Each `startDca` indicator on the bot IS one ladder level: the first fires safety
order 1, the second safety order 2, and so on. `checkIndicatorStatus` resolves
the fired indicator to its position in that list and hands it over as `index`:

```ts
const index = (settings.indicators ?? [])
  .filter((ind) => ind.indicatorAction === IndicatorAction.startDca)
  .findIndex((si) => si.uuid === i.uuid)
this.addDCAOrderByIndicator(this.botId, index, i.symbol, lastData.time)
```

`addDCAOrderByIndicator` then decides which open deals that signal applies to:

```ts
const deals = this.getDealsByStatusAndSymbol({
  status: DCADealStatusEnum.open,
  symbol,
}).filter((d) => d.deal.levels.complete === index + 1)
```

and, for each, fills the ladder order that indicator names:

```ts
const dcaOrder = orders.find((o) => o.levelNumber === index + 1)
```

### 1.1 Expected

Signal *k* applies to a deal that has consumed exactly *k* ladder levels. The
base order counts as 1, so `levels.complete` is that number — **on a deal that
has never taken add funds**. An addition is an entry outside the ladder: it
must leave the deal on the same level, waiting for the same signal.

### 1.2 Actual

`updateDeal`'s add-funds branch increments `levels.complete` on every add-funds
fill, the same counter this filter reads. A deal with *k* consumed levels and
*n* additions carries `levels.complete = 1 + k + n`, so it matches signal
*k + n*:

- the signal the deal was actually due, *k*, now matches **no deal at all** —
  that level never fires again for the life of the deal;
- the next signal to arrive, *k + n*, matches it and fills `levelNumber
  k + n + 1` — a level the deal had not reached, at that level's size.

With one addition on an untouched ladder that is: signal 1 stops firing, and
the first signal the deal does answer buys level 2.

### 1.3 Nothing in the deal hints at it

On the percentage ladder an addition at least shows up as `levels.all` growing
by one (spec `031` §1.3). Here it does not: `updateDeal` recomputes `levels.all`
from the ladder rows when `currentOrders` holds no `dealRegular` — which is
always true for `dcaCondition: indicators`, whose safety orders never rest on a
venue — so it stays at "startDca count + 1". The deal reads `2/4` where it read
`1/4`, exactly as if a safety order had filled.

## 2. Evidence

Reproduced on the paper stack (paper Binance spot, SOL/USDT, deal
`6aa25708bddc789145b3e76e`). The bot: `dcaCondition: indicators`, three
`startDca` indicators — so three ladder levels — no SL, `tpPerc: 50` so nothing
closes.

| step | `levels` | `funds` | `assets.required.quote` |
|---|---|---|---|
| deal opened | 1/4 | 0 | 0 |
| add 10 USDT | **2/4** | 1 | 0 |

`required.quote` is 0 throughout because an indicator ladder rests nothing on
the venue — which is also why spec `031`'s change cannot reach this path, and
why the count has to be read off the deal instead.

The deal's complete order history at that point:

```
D-BO-fDllGjO…   dealStart    FILLED  0.198 @ 101.58
D-TP-acs5Yyl…   dealTP       CANCELED
D-ROA-8V0Wnw…  dealRegular  FILLED  0.098 @ 101.53   addFundsId ac5fd9fc-…
D-TP-UyPUD2u…   dealTP       NEW
```

**No safety order has been consumed** — the only `dealRegular` row is the
addition — and yet `levels.complete` is 2. Signal 1 (`index` 0) tests
`levels.complete === 1` and no longer matches this deal; signal 2 (`index` 1)
tests `levels.complete === 2` and does.

## 3. Assumption (root cause, stated as hypothesis)

The same one spec `031` §5 names for `executeNextDcaLevel`: `levels.complete` is
not the deal's ladder position once an add-funds order has filled, and this is
the last call site still reading it as though it were. `031` shipped
`nextLadderLevel(deal) = levels.complete - (additions that took no level)` for
exactly this quantity; the fix is to select on it.

Confidence is higher here than for a fresh hypothesis: the correction is already
in the tree, already used by two other call sites, and `getDealDCAByMarketToCheck`
performed the same subtraction long before either.

## 4. Required behaviour

### 4.1
A deal is selected for `startDca` signal `index` when it has consumed exactly
`index` ladder levels, however many add-funds orders it has also filled.

### 4.2
The order the signal fills is unchanged: `levelNumber === index + 1`, the level
that indicator names. This spec moves *which deals a signal applies to*, not
which level it buys.

### 4.3
A deal that has never taken add funds is selected exactly as before — the
correction is a no-op on `funds: []`.

### 4.4
An addition flagged `consumesLadderLevel` (spec `031` §6) is left in the count,
so the planned "replace the next available DCA level" opt-in advances the
indicator ladder by one on purpose, in step with the percentage ladder.

### 4.5
No migration. The selection is evaluated per signal from the deal's current
counters, so a deal whose signal stopped matching starts matching again as soon
as the fix is running.

## 5. Explicitly out of scope

**`levels.all` does not grow per addition on this path (§1.3).** Correcting it
would change what "N of M" means on every indicator-condition deal, including
deals that never touch add funds, and nothing has been reported about it. It is
a display question, filed separately rather than folded into a selection fix.
