# 035 — A deal-close price of zero is laundered into a tradeable giveaway price

Issue #731. Bug spec (Definition / Evidence / Assumption).

Third in the family that starts at spec `023` (#714) and `025` (#715). Those
two stopped a non-finite **quantity** from reaching the venue. This one is
about the **price** leg, which has the opposite failure shape: nothing here is
NaN, so every finiteness guard those specs added is satisfied. A price of `0`
is instead quietly *repaired* twice — once into one tick, then into a price
that clears the venue's notional floor — and the resulting order is perfectly
well-formed, tradeable, and roughly two orders of magnitude below the market.

## §1 Definition

### §1.1 Expected

- **§1.1.1** When the price inputs a close is derived from are unusable —
  `avgPrice` (and the optional explicit `price`) zero or non-finite —
  `getTPOrder` returns `[]` and reports it, exactly as it already does for an
  unusable quantity (spec `023` §4.1). A close that cannot be priced is not
  placed at a guessed price.
- **§1.1.2** The `quoteAsset.minAmount` clamp brings an order up to the venue's
  notional floor by adjusting **quantity**, never by rewriting **price**. Price
  carries the trader's intent; quantity is the free variable. If the floor
  cannot be met without moving price, the close is refused rather than
  re-priced.
- **§1.1.3** No close order is submitted at a price orders of magnitude away
  from the live market. A close whose price fails a market-relative sanity
  bound is refused with a named error.

### §1.2 Actual

On 2026-09-08, after a price-lookup failure (`Cannot get prices Cannot read
properties of undefined (reading 'map')`), two deal-close SELL orders were
built from a zero price:

- `13:18:28.078Z` — a `dealTP` SELL at **price 0.000001** with **origQty NaN**.
  Rejected by the venue ("No order response"). This is spec `023`'s quantity
  defect; the *price* of exactly one tick is this spec's defect, visible in the
  same row.
- `13:59:36.725Z` — `D-TP-m2hygo2sAbY4CBFiarHyCGPBgZ1aVx`, SWFTC-USDC SELL
  **51029 @ 0.00002 LIMIT**, while the market was **0.002561**. The quantity
  was finite and correct, so nothing refused it. It was accepted and **filled
  at 0.002561** — 128× its own limit price — only because the book happened to
  be deep enough to walk. The order document keeps both numbers:
  `origPrice: '0.00002'`, `price: '0.002561'`.

### §1.3 Why this is not spec 023/025 again

`023` and `025` refuse non-finite values. `0.00002` is finite, positive, on
tick, above the base-asset floor and above the notional floor — it passes every
guard in the file. The harm is not malformedness; it is that the number is
*wrong by 128×*, and nothing in `getTPOrder` compares a close price to the
market it is closing into.

## §2 Evidence

### §2.1 The production row

`origPrice: '0.00002'` / `price: '0.002561'` / `origQty: 51029` on
`D-TP-m2hygo2sAbY4CBFiarHyCGPBgZ1aVx`. Triage confirmed the venue parameters
from production `pairs`: `priceAssetPrecision 6`, `quoteAsset.minAmount 1`.

### §2.2 The arithmetic reproduces the row exactly

`1 / 51029 = 1.9597e-5`, rounded **up** at 6 dp = `0.00002`. That is the
`quoteAsset.minAmount / tpOrder.qty` expression at `dcaHelper.ts:14795-14801`,
digit for digit. The input it was handed, `0.000001`, is
`1e-priceAssetPrecision` — the one-tick fingerprint spec `023` §2.3 already
named as meaning "`avgPrice` was 0".

### §2.3 The three steps, in the order they run

1. **`dcaHelper.ts:14498-14504`** — `tpPrice = round(price ?? avgPrice * (1 +
   tpPerc) * displacement, priceAssetPrecision)`. With `avgPrice` 0 and no
   explicit `price`, every factor multiplies zero: `tpPrice = 0`.
2. **`dcaHelper.ts:14505-14512`** — the "nudge by one tick" fallback exists to
   break a tie when the computed close equals the entry. `0 === 0` satisfies
   it, so it fires on a *degenerate* input it was never meant to see and
   returns `0 + 1e-6 = 0.000001`. **This is the laundering step:** a value that
   means "unknown" becomes a value that means "one tick".
3. **`dcaHelper.ts:14618-14628`** — spec `023`'s guard, `!Number.isFinite(
   tpPrice) || tpPrice <= 0`, is *correct* and would have refused step 1's
   `0`. It runs 106 lines too late: by the time it reads `tpPrice`, step 2 has
   already made it `0.000001`, which is `> 0`. **The guard that exists for
   this exact value never sees it.**
4. **`dcaHelper.ts:14789-14801`** — `tpOrder.price * tpOrder.qty` is
   `0.000001 * 51029 = 0.051`, below `quoteAsset.minAmount` of 1. On a long,
   the clamp raises **price** to `ceil(minAmount / qty)` = `0.00002`. The short
   branch of the very same `if` raises **quantity** instead; only the long
   branch touches price.

### §2.4 Impact shape

Silent. The order is accepted, so there is no error surface — the user sees a
close that filled. It cost nothing here because the book absorbed 51029 SWFTC
without moving 128×, which is luck, not a mechanism. On a thin book the same
order sweeps the depth and the position is sold for whatever is resting.

## §3 Assumption (hypothesis, not fact)

The root cause is **step 2 running before step 3**: an equality-tie nudge
placed ahead of the validity guard, so `0` — the one value the guard exists to
reject — is converted into a passing value before the guard is reached. The
`minAmount` price-rewrite at step 4 is a second, independent defect that
amplifies `0.000001` into a *tradeable* price; on its own (with a healthy
`avgPrice`) it is a smaller error, but it is still the wrong free variable to
move, and it is what turned a venue-rejected order into a filled one.

Corollary: because both defects produce a finite, positive, on-tick price,
**no finiteness guard anywhere downstream can catch either**. The only check
that can is a comparison against the live market — which `getTPOrder` does not
make today.

## §4 Required behaviour

- **§4.1** `getTPOrder` refuses (returns `[]`, reports "not a number") when the
  price it must derive the close from is 0 or non-finite, **before** the
  one-tick nudge can rewrite it.
- **§4.2** The one-tick nudge still fires for its intended case: a legitimate
  computed close that lands exactly on a legitimate `avgPrice`.
- **§4.3** The `quoteAsset.minAmount` clamp raises **quantity** on both sides,
  never price. If the resulting quantity is not finite and positive, the close
  is refused (mirroring spec `025` §4.4's `Number.isFinite(tpOrder.qty)`).
- **§4.4** A close price that is orders of magnitude from the live market is
  refused with a named error, whatever produced it.
- **§4.5** A deal with real prices is untouched — same quantity, same price, to
  the unit.

## §5 Blast radius

`getTPOrder` is `core/`: shared by every service embedding `main-app-sh`, and
it prices **every** DCA/combo take-profit and stop-loss on the platform. The
change must be a pure refusal-and-widening: it may only turn orders that are
already wrong into no-orders. §4.5 is the test that enforces that.
