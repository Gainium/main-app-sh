# 295 — DCA take profit is not replaced while the old one's cancel is unconfirmed

Bug spec (gainium-dev-flow, bug flavour). Builds on 242 (`closeReplacements`:
a replacement take profit placed by `checkTPOrder`).

## Definition

`checkTPOrder` re-positions a DCA deal's take profit: it cancels the resting
take profit and places a new one with `closeDealById`. It treated every cancel
result that was not `FILLED` as "the old take profit is gone". That includes:

- `undefined`, which `cancelOrderOnExchange` returns when the venue refused the
  cancel and the refusal was only reported (a generic venue error such as OKX
  `Systems are busy`, a rate limit, a lockout). Open-deal orders are not queued
  for a cancel retry, so nothing else follows up;
- `null`, which the unknown-order lookup returns when it could not settle the
  order.

In both cases the old take profit may still be resting on the venue. Placing
the replacement then leaves the deal with two closing orders for the same
position, which can close it twice.

### Required behaviour

1. **§1.1** When the cancel of the old take profit returns no order (`undefined`
   or `null`), no replacement is placed and the deal is not marked in
   `closeReplacements`. A re-check of the same take profit is armed on the
   deal's `limitTimer`.
2. **§1.2** The re-check backs off: 5 s, 15 s, 30 s, then every 60 s while the
   venue keeps refusing. Attempts are counted per take-profit client order id
   and the count is cleared when the take profit is resolved or a fresh
   (non-re-check) call starts.
3. **§1.3** The re-check reads the order from the bot's map and, when the
   stream has already removed it, from the orders collection
   (`findOwnOrder`). If the row is already `CANCELED`/`EXPIRED` the replacement
   is placed without a second cancel. If it is `FILLED` it is handed to
   `handleUnknownOrder` and nothing is placed. Otherwise the cancel is sent
   again and the rules of §1.1/§1.4 apply.
4. **§1.4** A cancel the venue answered is unchanged: a returned order that is
   not `FILLED` (including a `NEW` read-back after an accepted asynchronous
   cancel) is replaced at once exactly as before; `FILLED` still goes to
   `handleUnknownOrder`.

### Not changing

- Take-profit placement when the cancel succeeds (almost every time).
- `cancelOrderOnExchange`, the unknown-order ladder, the cancel retry queue.
- Grid orders, safety orders, stop loss.

## Evidence

- An OKX perpetual DCA deal: the take-profit re-position found the old take
  profit unfilled and sent its cancel. OKX answered `Systems are busy` and the
  cancel was only reported. About 0.6 s later a replacement take profit was
  placed for the same deal while the first one was still resting. Both rows
  later ended `CANCELED`, so no double close happened this time, but nothing
  in the engine prevented it.
- Code: `checkTPOrder` gated only on `cancelOrder?.status === 'FILLED'`, a check
  that has been there since the first public release.

## Assumption

A returned order means the venue answered the cancel. OKX and several other
connectors read the order back after an accepted cancel, so a successful
cancel can report `NEW`. Holding on anything but `CANCELED` would delay the
normal path, so only an unanswered cancel is held.

## Tests

`src/bot/tpReplaceAfterRefusedCancel.spec.ts` drives the real `checkTPOrder`
through each section above.
