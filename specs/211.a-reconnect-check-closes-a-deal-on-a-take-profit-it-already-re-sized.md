# 211 — A reconnect check closes a deal on a take-profit it already re-sized

Bug spec (Definition / Evidence / Assumption). Tests:
`src/bot/dca/reconnectSweepStaleSnapshot.harness.spec.ts` (§1.1, §1.2),
`src/bot/limitOnlyCloseRemainder.spec.ts` (§1.3).

## §1 Definition

A DCA deal's take-profit that part-filled and was then cancelled by the bot as
a re-size (its fills kept as a partial take profit, a new take-profit placed
for the rest) is not a close.

**Expected.**

- §1.1 The reconnect check (`checkOrdersAfterReconnect`, also run as the
  periodic reconcile sweep) does not act on a venue answer for an order the bot
  no longer holds as open: not one that ended locally (`CANCELED`, `FILLED`)
  after the check read its list, and not one that has left the order map. It
  does not hand it to the fill handler and does not write the answer over the
  row.
- §1.2 Unchanged: an order still held as `NEW`/`PARTIALLY_FILLED` whose fill
  the user stream missed is caught exactly as before.
- §1.3 When a close's remainder sweep is refused for balance while another
  take-profit of the same deal is still resting, the deal is not closed: it
  takes the spec `157` §1.1–§1.3 path (fill kept in `tpHistory`, the resting
  take-profit cancelled as a re-size, the rest offered as one LIMIT close).
  Spec `157` §1.5 is otherwise unchanged: any other refusal, including a
  balance refusal with nothing of the deal resting, closes the deal as before.

**Actual.** The check read its list once and paced one venue lookup per order
for over a minute. A take-profit it had read as `PARTIALLY_FILLED` was
cancelled as a re-size meanwhile. `getOrder` answers any `CANCELED` order with
fills as `FILLED`, so the check handed that take-profit to
`processFilledOrder`, which closed the deal on it. The close measured a
remainder, sent a MARKET sweep while the deal's full-size take-profit still
rested and held every coin, and the sweep was refused for balance. That refusal
is not a limit-only one, so the deal was written closed with the whole position
left in the account and nothing tracking it.

## §2 Evidence (prod, read-only)

- §2.1 Coinbase spot DCA deal, bot log: `00:30:02.066 Check order after user
  stream reconnect`; `00:30:14.910 base order remainder … Re-placing it`;
  `00:30:15.956 Processing msg … D-TP-… CANCELED … base: 3929.2` (venue:
  `cancel_reason: User requested cancel`); `00:31:09.705` a new take-profit for
  14546.8 rests; `00:31:20.280 TP order FILLED` with no take-profit filling at
  that moment, in the same millisecond as `Order D-ROA-… was already processed`
  (the base remainder cancelled at 00:30:14 with a part fill); `00:31:20.285
  tp-coverage drift` — logged only by `checkOrdersAfterReconnect`;
  `00:31:21.633 Not enough balance Order id: D-SR-… balance total - 14546.8,
  free - 0, required - 3406.5`; `00:31:21.955` the resting take-profit
  cancelled.
- §2.2 Order rows: buys filled 25687.1, sells filled 11140.3, so the account
  held 14546.8. The deal row: `status: closed`, `size: 11140.3` (= the
  re-sized take-profit's 3929.2 plus the partial take profits before it),
  `D-SR-…` `CANCELED, executedQty 0`.

## §3 Assumption (root cause — hypothesis)

`checkOrdersAfterReconnect` decides from the order object it read at the start
of the pass, not from what the bot holds when the venue answers. Re-reading the
map after the lookup and skipping an order no longer held open removes the
false close; a test whose lookup cancels the take-profit locally and answers
`FILLED` must see `processFilledOrder` called today and not after.

Separately, `closeDeal` treats only a limit-only refusal as recoverable, so a
refusal caused by the deal's own resting take-profit books the close.

Not in scope: the remainder above was measured as 3406.5 against a real
14546.8, because `updateDealBalances` books cancelled part-filled take-profits
into `currentBalances` while `closeDeal` subtracts `tpHistory` from it again.
That double count is a separate defect with its own fix.

## Invariants

None added: the wrong state (a closed deal whose orders still hold a position)
is already the subject of the close-reconciliation checks in main-app.
