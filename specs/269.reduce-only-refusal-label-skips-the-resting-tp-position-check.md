# 269 — A Binance reduce-only TP refusal skips the spec 143 position check

Bug spec. Amends `143` §4.1; every other part of `143` stands, including §1.3
(the deal is never closed by this path).

## §1 Definition

- §1.1 **Expected.** A futures deal's resting take-profit refused by Binance
  USD-M with `ReduceOnly Order Failed. Please check your existing position and
  open orders.` goes through spec `143`: the venue position is read; if the venue
  holds none for the deal, the take-profit is held back on the `143` backoff and
  the user is warned once on the deal.
- §1.2 **Actual.** The position is never read. The same take-profit is sent and
  refused on every pass (each worker start), indefinitely, and the user is told
  nothing.
- §1.3 **Unchanged.** Spec `143` §1.3 and §4.2–§4.6: a position the venue still
  holds, or a venue that does not answer, changes nothing; no deal is closed and
  nothing is booked on this path; the leverage refusal is not probed.

## §2 Evidence

- §2.1 Production bot log: a hedge-mode Binance USD-M account, a SHORT bot whose
  deals' take-profits are refused with the message above at every worker start
  (latest burst 2026-11-25 01:56Z). Not one `TP refused (…)` line from
  `checkRefusedRestingTpPosition` for that bot, while the same line appears for
  paper and Kraken accounts.
- §2.2 Production `boterrorrules` (admin API, 2026-11-25): builtin substring rules
  `reduce-only` (priority 79) and `reduceonly` (priority 80) map to
  `Futures position restriction`. They take precedence over `errorDict`
  (`getErrorSubType`), so the dict's `ReduceOnly Order` → `Futures position` never
  applies in production.
- §2.3 The position reconciler records the account's venue positions as 0 for the
  deals' symbol and side (`positions(hedge)`).

## §3 Assumption

- §3.1 (confirmed by the harness) `sendFuturesRestingTp` gates the position check
  on `getErrorSubType(reason) === 'Futures position'`. The `143` harness used the
  static dict (no rules cache loaded), so it never saw the production label.

## §4 Required behaviour

- §4.1 The `143` position check runs for a futures `dealTP` refusal labelled
  either `Futures position` or `Futures position restriction`, except the
  leverage case.
- §4.2 Everything downstream of the check is `143` unchanged.
