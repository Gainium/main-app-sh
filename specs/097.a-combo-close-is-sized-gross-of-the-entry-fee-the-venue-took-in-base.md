# 097 — A combo close is sized gross of the entry fee the venue took in base

## §1 Definition

### §1.1 Expected

A spot combo deal's take-profit (and every other close built by `getTPOrder`'s
combo branch — the market close, the refused-close restore) sells no more base
than the deal actually holds. Its size is the deal's own balance ledger
(`currentBalances.base`), net of the base the venue took as fees on the deal's
entry fills.

### §1.2 Actual

The only fee correction in the combo branch is an ESTIMATE:
`Σ executedQty × maxFee` over the deal's filled entry-side orders, where
`maxFee` is the account's configured rate. When that rate is 0 — the exchange
account carries the user-set `zeroFee` flag, and `getUserFee` short-circuits to
`{maker: 0, taker: 0}` — the correction is 0 even when the venue in fact
charged the entry fee in the BASE asset and says so on the order's own fill
rows. The close is then sized above what the deal holds, the venue refuses it
for balance, and the refused-close restore re-arms the same oversized quantity
(it calls the same `getTPOrder`), leaving the deal open with no close on the
book.

## §2 Evidence

1. Code: `getTPOrder`, `this.combo` branch —
   `f = tpQuantityFeeIsThirdAssetOnly ? 0 : filled.reduce(acc + executedQty × maxFee)`;
   `maxFee = worstFee(await getUserFee())`; `getUserFee` returns zeroes when
   `this.zeroFee`.
2. Production (spot combo deal, binance, 2026-09-21): base order BUY filled with
   its commission reported in the base asset (0.1% of the fill). The close went
   out at exactly `currentBalances.base` (entry − grid sells), was refused
   "insufficient balance" with the venue's free balance short by that
   commission, and the restore re-armed the identical quantity and was refused
   again. The account's exchange entry carries `zeroFee: true`.
3. The observed fee is already on the rows: `observedFeeSplit` (orderFee.ts)
   over the deal's real base-order row returns `{ base: <commission>, quote: 0 }`,
   and `ordersFeeIsThirdAssetOnly` is `false` — the third-asset gate is not
   what zeroed the correction.

## §3 Assumption (hypothesis)

The only missing input is the fee the venue reported. Taking, per filled
entry-side row, the LARGER of the estimate and the base leg that row actually
reports closes the gap without changing any other case:

- a zeroFee account whose venue charged in base: the observed leg replaces a
  0 estimate — the defect;
- a normally-configured account: the observed leg ≈ the estimate — unchanged
  (the estimate is kept whenever it is larger, e.g. rows with no fee data,
  quote-denominated fees, a short's SELL entries);
- the all-third-asset gate (spec 015) still zeroes `f` exactly as before.

The correction can therefore only ever LOWER a combo close, never raise it,
so it cannot sell profit the deal has not earned.

## §4 Behaviour

- §4.1 Per filled entry-side row, the base fee subtracted is
  `max(executedQty × maxFee, observedFeeSplit(row).base)`; a row with no
  observable split contributes the estimate alone.
- §4.2 The spec-015 third-asset gate still yields `f = 0`.
- §4.3 Sizing stays sourced from the deal's balance ledger; the filled-order
  sizing of the non-combo path is not used for combo.
- §4.4 Out of scope: the non-combo DCA path has the same zeroFee blind spot
  (`_qty × (1 − maxFee)`); it is a separate change with its own blast radius.
