# 259 — a failed exchange read is listed as "no open orders"

Bug spec (SKILL.md Part 0). Scope: `src/graphql/handlers/orders.handler.ts`
(`getAllOpenOrders`, `getAllOpenPositions`). Builds on spec 214 (per-exchange
deadline), whose behaviour for healthy venues is kept.

## §1 Definition

### §1.1 Expected

- §1.1.1 When an account's open orders / positions cannot be read (the
  connector answers NOTOK, the call throws, or it misses the list deadline),
  the answer says so. An account that could not be read never looks like an
  account with nothing open.
- §1.1.2 The rows of every account that did answer are still returned.

### §1.2 Actual

- §1.2.1 Each account's read is collapsed to `[]` on NOTOK, on a throw and on
  a late answer, and the handler answers `{status: OK, reason: null}`. A
  single-account request for an account whose read failed is
  indistinguishable from one whose venue holds nothing. Only the late path
  logs anything; NOTOK and throws are silent.

## §2 Evidence

- Code: `.then` returns `[]` when `status !== OK`; `.catch(() => [])`;
  `lateVenue` returns `[]`; the merge is `(await Promise.all(queries)).flat()`
  and the answer is hard-coded `reason: null`.
- Reproduced in `orders.handler.failedVenue.spec.ts` with fake venues: before
  the change a single NOTOK / throwing / late account answered
  `{status: OK, data: []}` and a mixed request answered `reason: null`.
- Consumers that decide "is this order still resting?" from this list read
  that `[]` as "the order is gone".

## §3 Requirements

- §3.1 A request where every account failed (incl. a single-account request
  whose account failed) answers `NOTOK`, `data: null`, with `reason` naming
  each account (provider + uuid) and its cause: the connector's reason, the
  thrown message, or the deadline.
- §3.2 A request where some accounts failed answers `OK` with the rows of the
  accounts that answered, and `reason` naming the failed accounts only.
- §3.3 = §3.1 for several accounts that all failed.
- §3.4 When every account answered, `reason` stays `null` (unchanged).
- §3.5 Every failed account is logged as a warning with provider and uuid
  (NOTOK, throw and late alike).
- §3.6 GraphQL shape is unchanged (`status`, `reason`, `data`); this is a
  behaviour change only. Spec 214 §4 holds unchanged.

## §4 Assumption (root cause, hypothesis)

The per-account promise has a single result type (an array), so a failure
can only be expressed as an empty array and the merge cannot tell the two
apart. Giving each account's result a tagged shape (rows | failed cause)
lets the merge report failures without changing what healthy accounts
contribute.

## Invariants

None — a read-path reporting defect; it writes no state.
