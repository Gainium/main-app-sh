# 045 — A grid bot's position-close P&L never reaches the user profit ledger

Issue #764 — "GRID bot loses not reflect on stat dashboard".

## §1 Definition

A grid bot books profit in two different places over its life:

- **§1.1 Per grid round-trip.** Each matched buy/sell pair is booked by
  `createTransaction()` — a row in `transactions` plus an `$inc` into the
  `userProfitByHour` ledger via `saveProfitToDb()`.
- **§1.2 At close.** When the bot stops with an open position/inventory, the
  closing fill carries the remaining, un-round-tripped P&L. On futures this is
  `profitAfterPositionClosed()`; on spot it is the transaction built inside
  `processFilledStop()` / `closeBotByTp()`.

**Expected.** Both kinds of P&L reach the user profit ledger
(`userProfitByHour`), because that collection is the *only* source the account
statistics read (`resolvers.getProfitByUser`, every timeframe). The bot's own
`profit.totalUsd` and the account statistics must therefore agree.

**Actual.** Only §1.1 reaches the ledger. The closing leg of §1.2 updates
`bot.profit` (and, on spot, writes a `transactions` row) but performs no ledger
write on two of the three close paths, so the account statistics are permanently
short by the close P&L of every grid bot that ever closed with inventory.

Because a grid bot accumulates its round-trip profit *while running* and realises
the adverse move only *at the close*, the omission is systematically
loss-shaped: the statistics keep the profitable half and drop the losing half.
That is exactly what the reporter describes — "when a grid bot ends with a loss,
it doesn't deduct that amount from the stats. Only profits are added."

## §2 Evidence

Reporter `64c33715e3ee8daa34f19dbb`, paper grid bot `6aa76a7cf3f81f03b9d03735`
("ARK Natural", ARK-USDT, `paperBinanceUsdm`, `settings.futures: true`), read
2026-09-14 through the dashboard GraphQL as the reporter:

| Quantity | Query | Value |
|---|---|---|
| §2.1 bot's own realised P&L | `getBot.data.profit.totalUsd` | **−10.985231** |
| §2.2 sum of its ledger-backed transactions | `getBotTransactions` (6 rows) | **+1.407399** |
| §2.3 §2.1 − §2.2 = P&L that reached no transaction and no ledger row | | **−12.392630** |

§2.3 is the position close the triage log line names (exit at 06:26:48Z,
−$12.39). It exists in `bot.profit` and nowhere else.

**§2.4 The account statistics confirm the ledger is short.** `getProfitByUser`
(`timeframe: 0`, UTC, paper) reports **+8.894248** for 2026-09-14 — a positive
day, while this one bot alone lost $10.99. Had §2.3 been booked the day would
read −3.498.

**§2.5 The gap is the close leg, not a per-transaction drift.** Same two reads
over the reporter's other paper grid bots:

| Bot | State | `profit.totalUsd` | Σ transactions | Gap |
|---|---|---|---|---|
| `6aa41b6f3df613e16497a0d1` DOGS | open (never closed) | 6.174356 | 6.173705 | +0.0007 |
| `6aa36d6c2d3a9f803ca83c54` MARSCOIN | closed | 8.826872 | 8.479978 | +0.347 |
| `6aa76a7cf3f81f03b9d03735` ARK | closed | −10.985231 | 1.407399 | **−12.393** |

An open bot agrees with its ledger; every closed bot is off by its close leg,
in whichever direction the close went.

**§2.6 The code path.** `resolvers.getProfitByUser` aggregates
`userProfitByHourDb` in all four timeframe branches; nothing else feeds the
statistics. `saveProfitToDb()` (`src/bot/main.ts:1318`) is the only writer. In
`src/bot/helper.ts` it is called from exactly two places — `createTransaction()`
(§1.1) and the **spot** branch of `closeBotByTp()`. It is called from neither
`profitAfterPositionClosed()` nor the spot branch of `processFilledStop()`.

## §3 Assumption (root-cause hypothesis)

The two close paths in §2.6 omit the `saveProfitToDb()` call that the third
close path (`closeBotByTp()`'s spot branch) makes. Adding it on both paths, with
the same dedup guarantee the existing writers already rely on, closes the gap.

## §4 Required behaviour

- **§4.1 Futures close books to the ledger.** `profitAfterPositionClosed()`
  writes the same `profitUsd` it adds to `bot.profit` into `userProfitByHour`,
  bucketed on the closing fill's `updateTime`. This covers both of its callers
  (`processFilledStop()`'s futures branch and `closeBotByTp()`'s futures
  branch).
- **§4.2 Spot stop fill books to the ledger.** `processFilledStop()`'s spot
  branch writes its `profitUsd` into `userProfitByHour`.
- **§4.3 A single fill is booked once.**
  - Futures: `profitAfterPositionClosed()` already returns early on
    `position.qty === 0`, and every caller calls `resetPosition()` immediately
    after it; a second delivery of the same fill therefore books nothing. The
    ledger write must sit *inside* that guard.
  - Spot: the `transactions` row carries `index: order.clientOrderId` under a
    **unique** index (`db/schema.ts:856`), so the second write of the same fill
    is refused. The ledger write must be gated on that insert having succeeded —
    the idiom `createTransaction()` already uses.
- **§4.4 `closeBotByTp()`'s spot ledger write survives §4.2 unchanged in
  value and gains the same gate.** It is the *other* `Stop order filled`
  emitter: it places the closing order itself and handles a synchronously
  FILLED answer, while the user stream delivers the same `clientOrderId` to
  `processFilledStop()` — the two await-points in between make the interleaving
  reachable. Its write is currently ungated, so once §4.2 exists a fill booked
  by `processFilledStop()` could be booked a second time here. Gating it on the
  same insert (`res.status === StatusEnum.ok`) keeps the write on every path
  that actually records a transaction and books each fill exactly once. This
  applies to core **and** to the `main-app` subclass that overrides the whole
  method, which is the copy that runs in production.
- **§4.5 Nothing else changes.** No change to `bot.profit`, to the emitted
  socket payloads, to the `transactions` shape, or to the statistics resolvers.

## §5 Out of scope

`processLiquidationOrder()` (`src/bot/helper.ts:1799`) carries an inlined copy of
the §4.1 calculation and has the same missing ledger write. It is a distinct
close path, not the one reported, and is left for a follow-up.
