# 131 — The Ignore Fees toggle never reaches running bots

All bot types · `core/src/bot/main.ts` (`loadData`, `updateExchangeCredentials`)
· `core/src/graphql/resolvers.ts` (`setZeroFee`)

## 1. Definition

### 1.1 Expected

Turning **Ignore Exchange Fees** on or off for a connection changes how the
bots already running on that connection size their closing orders from the
next order they build, without a bot restart. The help article states that the
switch affects new trades, not running ones.

### 1.2 Actual

A running bot keeps whatever the switch said when the bot was loaded. The
toggle only takes effect after that bot is restarted (or its worker process
is). A bot running when the switch is turned on keeps reserving the fee and
selling slightly less than the deal holds, leaving base-asset dust on every
deal it opens afterwards, indefinitely.

## 2. Evidence

Production, a DCA bot on a Coinbase connection now stored with
`zeroFee: true`:

- The worker loaded the bot once, at its process start: `Load data start` →
  `Load data end` with **no** `Zero fee exchange` line between them (other bots
  on zero-fee connections log that line during the same load burst). The same
  worker PID has run the bot ever since; there is no later `Load data start`.
- The switch was turned on hours after that load. Deals opened afterwards still
  closed short of the bought quantity (1469.4 bought, 1467.9 sold), i.e. the
  fee was still reserved.

Code path:

- `MainBot.zeroFee` is assigned in exactly one place, `loadData`, from
  `user.exchanges[uuid].zeroFee` (minus paper / OKX / Bybit). `getUserFee`
  answers `{0, 0}` from that field and `getTPOrder` rounds down to the full
  holding on it.
- `setZeroFee` writes `users.exchanges` and nothing else. The bot workers keep
  the user document in an in-memory `userStore` that is refreshed only by an
  `updateuserStore` publish, which `setZeroFee` never sends — so even a re-read
  of the user at deal time would see the old value.
- The publish/refresh channel already exists and is used by `updateExchange`:
  `updateuserStore` → `BotSharedData.updateUserStore` refreshes the cache and
  publishes `botUpdateUserExchange<thread>` → every bot on that connection runs
  `updateExchangeCredentials`, which re-reads the connection but ignores
  `zeroFee`.

## 3. Assumption (root cause hypothesis)

Two gaps, both needed for the switch to reach a running bot:

1. `setZeroFee` does not publish `updateuserStore`, so no running bot is told.
2. `updateExchangeCredentials`, the bots' handler for that notice, does not
   re-derive `zeroFee`.

A test that delivers the notice to a bot loaded with the switch off and then
flips the stored flag must see `zeroFee` stay `false` today (red), and a test
of `setZeroFee` must see no publish today (red).

## 4. Scope

### 4.1 Eligibility unchanged

The same rule decides `zeroFee` on load and on refresh: the connection's flag,
not a paper-context bot, provider not OKX / Bybit (any market). One function
holds it.

### 4.2 Both directions

Turning the switch off on a running bot clears `zeroFee` as well.

### 4.3 Other connections

A notice for a different connection changes nothing.

## 5. Known limit — open deals

`zeroFee` is a bot-level field. A deal that is already open keeps its resting
closing order, but a closing order it re-places after the switch (for example
after a further DCA fill) is sized with the new setting — the same thing a bot
restart already does today. Freezing the setting per deal would need a stored
per-deal field and is out of scope.
