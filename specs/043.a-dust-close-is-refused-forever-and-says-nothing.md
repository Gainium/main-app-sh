# 043 — A close under the venue's notional floor is refused forever, and says nothing

Issue #755. Amends spec `035` §4.3 (#731).

## §1 Definition

`getTPOrder` builds the order that closes a DCA deal. When the close it has
sized would sit under the venue's minimum notional (`quoteAsset.minAmount`),
spec `035` §4.3 made it refuse and return `[]`.

### §1.1 Expected

A deal whose position CAN be closed within the venue's rules gets a close
order:

- if the quantity the deal actually **holds** clears the notional floor, the
  close is sized to it;
- if it does not, but there is a price at or under an order of magnitude from
  the market at which the held quantity clears the floor, the close rests
  there — that price is not invented, it is the lowest one at which this venue
  will accept this close at all;
- only when neither holds is the close refused, and a refusal that keeps
  holding is **reported to the user**, because nothing the bot does will clear
  it.

### §1.2 Actual

Every long close under the floor is refused, unconditionally and silently, and
the deal is left with no close order at all. The refusal repeats for as long as
the deal is open — about once a minute — writing a hidden bot-message row each
time and telling the user nothing.

## §2 Evidence

### §2.1 The refusal is unconditional on the long side

Entering the `035` §4.3 block *is* the statement `tpOrder.price *
tpOrder.qty < quoteAsset.minAmount`, i.e. `minAmount / tpOrder.price >
tpOrder.qty`. The block then computes

```
qtyForFloor = ceil_precision(minAmount / tpOrder.price)
```

and refuses when `isLong && qtyForFloor > tpOrder.qty`. `tpOrder.qty` is already
on the `precision` grid, so `qtyForFloor >= minAmount / tpOrder.price >
tpOrder.qty` always. **The long branch of this guard can only ever refuse.**
Before `035` the same branch always PLACED the order, by raising the price to
`ceil(minAmount / qty)`.

### §2.2 What production shows

Bot-error records over a 48 h window, hidden lane (`showUser: false`),
non-paper:

| symbol | occurrences | close sized | held (`deal.size`) | held × price | floor |
|---|---|---|---|---|---|
| HYPE-USDC (hyperliquid) | 31 | 0.12 | 0.13 | 10.59 | 10 |
| HYPE-USDC (hyperliquid) | 13 | 0.12 | 0.13 | 10.66 | 10 |
| HYPE-USDC (hyperliquid) | 3 | 0.12 | 0.13 | 10.68 | 10 |
| GRAMUSDT (binance) | 3 | 2.42 | 2.42 | 3.89 | 5 |
| QNTUSDT (binance) | 3 | 0.06 | 0.06 | 4.15 | 5 |
| AMPUSDT (binance) | 3 | 553 | 553 | 0.49 | 5 |

Three shapes, and the guard treats all three the same:

- **The deal holds enough.** On the HYPE-USDC deals the close was sized 0.12
  while the deal holds 0.13 — a whole `0.01` step lost to fee-netting followed
  by flooring onto a coarse base grid. 0.13 at the same price is 10.59 USDC,
  over the 10 USDC floor. The position is closeable; the guard says it is not,
  because it compares the floor against the *close size* and calls that
  variable `positionQty`.
- **The deal does not hold enough, but a price exists.** GRAMUSDT needs
  2.0661 against a 1.608 market (1.28×) and QNTUSDT needs 83.33 against 69.16
  (1.20×). Both are ordinary resting take-profits.
- **Genuine dust.** AMPUSDT holds 0.49 USDC of value against a 5 USDC floor;
  it would need 10.2× the market. This one cannot be closed, and is exactly the
  one the user has to be told about.

### §2.3 The silence

The refusal calls `handleErrors(..., setError=false, sendError=false,
setEvent=false)`. `processError` still writes a `botmessages` row, so the admin
Bot Errors page counts it, but `showUser` is false and no notification, bot
event or error state is produced. Per the same window, ~98 % of the occurrences
carry no deal id at all: they come from `checkBalance`'s hypothetical pre-open
ladder (`createCurrentDealOrders` with `dealId: ''`), which describes a deal
that does not exist and can never be a user's problem.

### §2.4 Onset

`git blame src/bot/dcaHelper.ts` over the block returns `308094e9`
(2026-09-10), the `035`/#731 fix. The production records begin the same day and
there are none in the preceding six days.

## §3 Assumption

The root cause is that `035` §4.3 chose the wrong quantity to measure the floor
against — the fee-netted, grid-floored **close size**, named `positionQty` —
and, having chosen it, made "cannot reach the floor" unreachable for a long, so
the branch is dead on arrival. The silence is a second, independent defect: the
refusal was given the reporting flags of a routine condition because the
hypothetical `dealId: ''` ladder dominates its volume, and a real deal that can
never close inherited that treatment.

## §4 Requirements

### §4.1 Measure the floor against what the deal HOLDS

Compare `qtyForFloor` against the deal's tracked position — `|deal.size|` less
`tpHistory`, less filled close orders, less executed and pending reduce-funds —
which is what `dca/tpCoverageReconcile.trackedPosition` already computes and
what `getTPOrder`'s own `add` term already subtracts. Size the close to
`qtyForFloor` when it fits inside that, so the close sold is the *smallest*
quantity that clears the floor and never more than the deal owns.

### §4.2 Restore a bounded price raise, take-profit path only

When the held quantity cannot clear the floor at the computed price, raise the
price to `ceil(minAmount / heldQty)` — the lowest price at which the venue will
accept this close — and size the close to the held quantity. Bounded by
`MAX_CLOSE_PRICE_DEVIATION` above the live market, the mirror of §4.4's rule
and the same constant: past an order of magnitude the order is clutter, not a
trade, and the user should be told instead. Fails open when the market price is
unknown, exactly as `closeGivesValueAway` does.

Take-profit builds only (`sl === false`). A long stop-loss raised above the
market is a take-profit wearing a stop-loss's name; those keep refusing.

This **amends `035` §4.3**, which required the floor to be met by quantity and
never by price. `035`'s reasoning holds for the case it was written from — a
price that was already garbage, laundered into a tradeable one — and both
guards that catch that case stay exactly as they are: §4.1's zero/non-finite
`tpPrice` refusal runs before the nudge, and §4.4's giveaway bound runs after
this block. A raise can only move a long close AWAY from the giveaway
direction, so it cannot reach §4.4.

### §4.3 Report a standing refusal to the user

Count consecutive refusals per `dealId`. On the Nth, report through
`handleErrors` with `sendError`/`setEvent` so the user gets the message, the
bot event and the notification. Clear the count as soon as a close of
acceptable notional is built for that deal.

`setError` stays false: a single unclosable dust position must not put an
otherwise healthy multi-deal bot into an error state.

### §4.4 The hypothetical ladder never reports

A refusal with no `dealId` describes a deal that does not exist. It is a debug
line and nothing else — no `handleErrors`, no bot-message row, no counting
towards §4.3.

### §4.5 Nothing else moves

A deal whose close already clears the notional floor — the overwhelming
majority — must come back byte-identical.
