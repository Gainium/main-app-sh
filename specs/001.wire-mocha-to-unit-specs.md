# 001 — Wire real mocha to the scattered hand-rolled unit specs

## §1. Behaviour today

10 `*.spec.ts` files live next to the modules they cover (`src/bot/`,
`src/exchange/`, `src/bot/dca/`, `src/bot/combo/`), each a regression test
pinning a specific production incident. This repo has no test runner
(§1.1) — every file is a standalone script with its own hand-rolled
`expect`/`check` helper that does the comparison itself, `console.log`s
PASS/FAIL, and calls `process.exit(1)` on any failure. Each file's header
comment says to run it directly via `npx ts-node --files --project
tsconfig.json <path>` (§1.2). Nothing runs these in CI, or even runs them
all together — a developer has to know the 10 file paths and invoke each
one individually.

## §2. Desired behaviour

`npm test` runs all 10 spec files through a single real test runner
(mocha, matching the `describe`/`it` + chai `expect` convention already
used in this org's `app` repo — its `tests/*.ts` import `{ describe, it }
from 'mocha'` and `{ expect } from 'chai'`) and exits non-zero if any
assertion fails (§2.1). CI runs `npm test` on every PR (§2.2). Each
hand-rolled assertion becomes its own `it()`, not one monolithic
per-file pass/fail, so a failure names the specific regression case that
broke (§2.3). The specs stay where they are, next to the modules they
cover — that placement is intentional per their own header comments
("kept byte-identical... alongside the module it covers") and moving them
to a `tests/` directory is out of scope (§2.4).

## §3. Open questions / assumptions

- §3.1 New devDependencies: `mocha`, `chai`, `@types/mocha`, `@types/chai`
  are not present in this repo today (only `ts-node` is). This is a public
  repo (`Gainium/main-app-sh`). Per this task's explicit brief (user
  instruction: "wire real mocha to them"), adding these as devDependencies
  is in scope and pre-authorized, not an open question — noted here only
  because the dev-flow skill otherwise asks that a new test framework be
  flagged rather than added silently.
- §3.2 Assertion semantics: converting `JSON.stringify(actual) ===
  JSON.stringify(want)` comparisons to chai's `.to.deep.equal()` is not
  byte-identical in one edge case (an object key explicitly set to
  `undefined` compares equal to an absent key under JSON.stringify, but
  not under chai's deep-equal). Resolved in the plan by verifying every
  converted assertion against a captured baseline (§4) rather than by
  reasoning about it in the abstract.
