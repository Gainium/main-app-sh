# 139 — Single position per pair

Feature spec. A DCA bot setting under which the bot holds **at most one open
deal per pair**. A start signal for a pair that already has an open deal no
longer opens a second deal: it adds an **entry** to the open one. Deals that
arrive from elsewhere (a terminal deal moved in, deals already open when the
setting is turned on) are **adopted** into the open deal.

Builds on spec 138 (merged deals are one position). Spec 138's statistics
rules for merged-away deals are reused here unchanged, apart from §6.2.

## §1 Terms

- §1.1 **Position.** The single open deal a single-position bot holds on a
  pair. It is an ordinary deal document. Nothing in the data model separates a
  "position" from a "deal".
- §1.2 **Entry.** One buy (long) or sell (short) that grows the position: the
  base order that opened it, or a later start signal routed into it (§3).
  Entries are not deals, and they are not safety orders.
- §1.3 **Adoption.** Folding another open deal into the position (§4). The
  position survives with its id, its creation time and its history. The
  adopted deal is merged-away in the spec 138 sense.

## §2 Settings

- §2.1 `singlePosition?: boolean` on DCA bot settings (`types.ts`
  `DCABotSettings`, the db schema, GraphQL, and the v2 config validator and
  OpenAPI). Missing means `false`. Additive: older clients and self-hosted
  instances ignore it.
- §2.2 `maxPositionEntries?: number`. The most entries a position can hold,
  counting the base order. Missing or 0 means no limit. Funds stay bounded by
  entry size × entries per pair × `maxNumberOfOpenDeals` pairs.
- §2.3 While `singlePosition` is on:
  - §2.3.1 **Safety orders are off.** New positions are created with
    `useDca: false`, and the dashboard disables the DCA section with a note
    that entries replace safety orders. The bot's DCA settings are kept, not
    erased, so turning the setting off brings them back.
  - §2.3.2 `maxDealsPerPair` is ignored, because it is 1 by definition. The
    dashboard hides it. `maxNumberOfOpenDeals` still caps how many pairs hold
    a position (multi-pair bots).
  - §2.3.3 Bot controller "close after X deals opened" is refused by
    validation. A position never re-opens per signal, so the count would only
    grow with closes. "Close after X closed / won / lost" stays available.
- §2.4 **Where it is offered.** DCA bots only. Combo bots are excluded, since
  spec 138 refuses to merge combo deals. Hedge DCA is excluded for v1: one
  position per side is follow-up work. Grid bots and terminal deals don't have
  the setting.
- §2.5 Turning the setting on or off is a sizing change for the purpose of
  `resetStatsAfter`. The "since last change" statistics start fresh, because
  deal counts, win rate and durations mean something different on either side
  of the switch. Lifetime statistics (`botWindowStats`) are unaffected.

## §3 Entries — start signals on a pair with an open position

- §3.1 **The invariant: a single-position bot never has two open deals on one
  pair.** This applies to every path that can open a deal:
  - the start condition (ASAP, indicators, webhook, timer);
  - the bot's "+ New deal" button (`openNewDealMan`);
  - API and webhook `startDeal`;
  - Max/MCP tools;
  - start after a restart.

  It is enforced in the engine at `openNewDeal`. A check only in the UI or the
  API does not meet this spec.
- §3.2 When `openNewDeal` resolves a pair that has an open deal of this bot,
  it routes to an entry instead of creating a deal. The entry passes the
  ordinary gates in their current order. Each gate is adapted as follows:
  - §3.2.1 `maxNumberOfOpenDeals`: not consulted, because the pair already
    holds a slot.
  - §3.2.2 `maxPositionEntries`: refuse once the position holds that many
    entries. Report the refusal through the `reportMaxDealsReached` latch with
    a new scope `entries`, so the user sees "position full", once, the same way
    as "max deals reached".
  - §3.2.3 Static price filter (`checkInRange`): unchanged.
  - §3.2.4 Dynamic price filter (`checkInDynamicRange`): the reference price
    for a position is the **last entry's fill price**, never the position's
    average. The average moves toward the market after every entry, so
    measuring against it would bunch entries closer and closer together.
    `lastPricesPerSymbol` is updated with that price when an entry fills
    (§3.4).
  - §3.2.5 Cooldown after deal start: measured from the last entry's fill.
    Cooldown after deal stop: unchanged, since it is measured from the
    position's close.
  - §3.2.6 Balance check and `allowRaiseToExchangeMin`: as for a base order.
  - §3.2.7 `checkNewDealApproval`: runs for entries too, with a context that
    marks the request as an entry, so approval hooks can tell the two apart.
- §3.3 **Entry order.** Placed through the add-funds machinery
  (`addDealFunds` → `pendingAddFunds` → the `roa` fill branch of
  `updateDeal`). The order is sized and typed like the bot's base order:
  order size and size type, market or limit, "Use available". It carries a new
  `positionEntry: true` flag on the add-funds settings and the order, so it can
  be counted and told apart from a user's manual add-funds.
- §3.4 **On an entry fill**, the existing `roa` branch updates funds, average
  price, balances and levels, rebuilds the take-profit orders and re-runs the
  SL checks. In addition:
  - §3.4.1 `deal.positionEntries` (new field, 1 at creation) is incremented.
  - §3.4.2 The pair's `lastPricesPerSymbol` entry and the deal-start time
    behind cooldown after deal start are set from this fill (§3.2.4–5).
  - §3.4.3 A trailing take-profit resets its best price. Same rule as a safety
    order fill: the target moved.
  - §3.4.4 Multi-TP re-splits over the new size. Verify that the `roa` branch
    already does this, and add it if not.
- §3.5 **One entry in flight per position.** While an entry order is unfilled,
  further start signals for that pair are skipped, not queued. They are logged
  at debug level and are not reported to the user. Start signals for one pair
  are serialised, so two near-simultaneous signals can't both pass the
  "already has an open deal" check and open two deals.
- §3.6 SL and TP are measured from the position's average, as for any deal.
  Close-by-timer counts from the position's creation (unchanged). An option to
  count from the last entry is out of scope.

## §4 Adoption — folding an open deal into the position

- §4.1 `adoptDeals(targetDealId, sourceDealIds)` is a new engine operation
  next to `mergeDeals`. Unlike a merge, it keeps the target deal. The target
  must be open, all deals must have the same symbol and strategy, and the
  operation is refused for combo bots (spec 138 §2.4) and hedge bots (§2.4).
- §4.2 Steps, run in the target bot's worker under the same mutex as
  `mergeDeals`:
  - §4.2.1 Mark each source `{ child: true, parentId: target }` **before**
    cancelling it (spec 138 §2.1.4).
  - §4.2.2 Cancel each source through the ordinary close path
    (`CloseDCATypeEnum.cancel`, `reopen = false`). This cancels its open
    orders on the exchange. Any profit it has booked is credited to its own
    bot's total.
  - §4.2.3 Re-point the source's filled `dealStart` / `dealRegular` / `dealTP`
    orders to the target, as `mergeDeals` does. A source's base and safety
    fills become entries of the target. They keep their `typeOrder`, but the
    order also gets `positionEntry: true` so the counts and TP sizing include
    it.
  - §4.2.4 Recompute the target's funds, average price, initial and current
    balances, usage (including `maxUsd`) and `tpHistory` from all of its filled
    orders. `deal.positionEntries` = the target's entries + 1 per adopted
    deal. Each adopted deal counts as one entry, whatever its own ladder
    filled.
  - §4.2.5 Cancel the target's own unfilled safety orders, then rebuild its
    TP / SL (`createCurrentDealOrders`, `checkDealSlMethods`). Do not reload
    the whole bot; spec 138 history shows reload-per-merge causing duplicate
    starts.
  - §4.2.6 Emit the realtime updates for the target, the sources and the
    re-pointed orders (spec 138 §2.3 payload rule).
- §4.3 The target keeps `_id`, `createTime`, its own statistics and its
  funding cursor. It is **not** flagged `parent: true`: it is a real opened
  deal and must keep counting in "deals opened" (spec 138 §2.2.1 excludes
  `parent: true`). Adopted ids are recorded in a new `adoptedIds: string[]` on
  the target.
- §4.4 The position's `maxPositionEntries` doesn't apply to adoption. A
  position may go past its limit through adoption, and it then takes no
  further entries until it closes.

## §5 When adoption happens

### §5.1 Turning the setting on

- §5.1.1 On save (`changeDCABot`) with `singlePosition` going from off to on,
  for every pair of the bot:
  - **More than one open deal:** the **oldest** open deal is the target, and
    the others are adopted into it (§4).
  - **Exactly one open deal:** it becomes the position. Its unfilled safety
    orders are cancelled and its TP is rebuilt. `positionEntries` = 1.
  - **No open deal:** nothing happens.
- §5.1.2 **The server refuses the change** while any pair has more than one
  open deal, unless the request carries `adoptOpenDeals: true`. Answer `NOTOK`
  and list the affected pairs. This applies to GraphQL and v2 alike, so API
  clients cannot merge positions without asking for it. Cancelling ladders on
  single-deal pairs needs no flag, because §2.3.1 already says the bot has no
  safety orders.
- §5.1.3 **Dashboard confirmation.** When the save would adopt or cancel
  ladders, show a dialog before sending it:
  - one row per affected pair: "BTCUSDT — 3 deals → 1 position", with size
    before → after, new average price, and TP price old → new;
  - "Open safety orders and take-profit orders of these deals are cancelled
    and replaced. This cannot be undone.";
  - **Confirm** sends `adoptOpenDeals: true`. **Cancel** leaves the setting
    off.
- §5.1.4 Adoption needs the bot's worker, because it cancels orders on the
  exchange. If the bot is not running and has open deals on any pair, refuse
  the change: "Start the bot to switch it to single position".

### §5.2 Moving a deal into a single-position bot

- §5.2.1 "Move to bot" (terminal → bot, `useMoveDealToBot`) and a
  cross-bot merge (spec 138 §2.4.3) whose target bot has `singlePosition` on
  **and** an open deal on that pair adopt the incoming deal into that open
  deal (§4), instead of calling `mergeDeals`.
- §5.2.2 If the target bot has no open deal on the pair, the current path is
  unchanged: the moved deal becomes the position. Its `positionEntries` = 1.
  Its unfilled safety orders are cancelled (§2.3.1).
- §5.2.3 **Picker.** `MoveDealToBotDialog` labels such bots with "Merges into
  your open BTCUSDT position". **Confirmation** uses the same before/after
  rows as §5.1.3, for the one pair. The orphan terminal bot is deleted as
  today.
- §5.2.4 GraphQL: a new `adoptDeals` mutation (or `mergeDeals` gaining a
  `targetDealId`). The engine refuses a plain `mergeDeals` that would leave a
  single-position bot with two open deals on a pair (§3.1).

### §5.3 Turning the setting off

- §5.3.1 Nothing is split. The position stays one deal, with no safety orders,
  until it closes. New deals follow the restored settings. The dashboard says
  so in the toggle's help text.

## §6 Statistics

- §6.1 A position is one deal in every per-deal statistic: one deal, one win
  or loss, one duration from creation to close. Entries are not counted as
  deals. Expect fewer, larger and longer deals, and a higher win rate, than
  the same strategy without the setting. That's why §2.5 resets "since last
  change".
- §6.2 **Peak capital.** A position's capital is its `usage.maxUsd`, which
  grows with entries. Like a DCA deal's safety orders, the sweep attributes the
  final maximum to the deal's whole interval. This is a known overstatement,
  shared with ordinary DCA, and per-fill attribution is out of scope. An
  adopted deal holds capital until the target's creation (spec 138 §2.1.3). The
  target is always older (§5.1.1), or the source moved in after it, so the
  clamp leaves the source zero capital and the target's grown `maxUsd` covers
  it. **Required check:** the sweep must clamp by the deal named in `parentId`
  whether or not that deal is flagged `parent: true`. Verify this and fix it
  if not.
- §6.3 An adopted deal follows spec 138 §2.1 unchanged. It is excluded from
  per-deal statistics, and any money it booked still counts.
- §6.4 Return on peak capital and profit factor (from gross P&L) stay
  comparable across the switch and are the figures to read. No new statistic
  is added in v1.

## §7 Validation — start conditions that cannot space entries

- §7.1 `singlePosition` with start condition **ASAP** requires **at least one
  of**:
  - `useDynamicPriceFilter`, with a deviation;
  - cooldown after deal start (`cooldownAfterDealStart` with an interval).

  Without either, every check would add an entry and fill the position at
  almost one price within seconds.
- §7.2 Enforced server-side in `createDCABot` / `changeDCABot` and in the v2
  bot validators (`server/v2/validators/bots/config.ts`), with the reason:
  "Single position with ASAP needs a dynamic price filter or a cooldown after
  deal start".
- §7.3 Dashboard (`DealStartSettings`): an inline error on the toggle with
  one-click **Enable dynamic price filter** and **Add cooldown** actions. The
  toggle stays enabled. Greying it out would hide the reason.
- §7.4 Indicator, webhook and timer start conditions have no requirement. An
  indicator condition that stays true re-enters every candle, so the dashboard
  suggests a cooldown in the toggle's help text without requiring it.

## §8 Backtesting

- §8.1 The backtester (`@gainium/backtester`, server-side and in both
  dashboards) does not simulate single position in v1. A backtest of a bot
  with `singlePosition` on is refused with "Backtesting is not available for
  single-position bots yet". It is not run as if the setting were off, because
  those results would mislead.

## §9 Out of scope

- Hedge DCA (one position per side). Combo bots.
- Safety orders on a position (a ladder re-anchored to the average after each
  entry).
- A maximum position size in money (`maxPositionEntries` bounds it for fixed
  entry sizes).
- Close-by-timer counted from the last entry.
- Per-fill capital attribution in the peak-capital sweep.
- Splitting a position back into deals.
- Backtester support.

## §10 Verification

- §10.1 Engine harness (as `mergedDeals.harness.spec.ts`):
  - §3.1: every start path on a pair with an open position produces an entry,
    never a second deal, including two concurrent signals;
  - §3.2: each gate as described;
  - §3.4: entry fill updates and dynamic-filter reference;
  - §3.5: an in-flight entry skips the next signal;
  - §4: adoption keeps the target's id and history, cancels the sources'
    orders, marks them before cancelling, and recomputes balances, TP and
    `positionEntries`;
  - §5.1.2 and §5.1.4: refusals;
  - §7: validation on both GraphQL and v2.
- §10.2 Statistics: a bot with one position (3 entries) plus one adopted deal
  reads as one deal in `pairStats` and `botWindowStats`, with peak capital =
  the position's `maxUsd`.
- §10.3 Local stack, paper DCA bot, in the browser:
  - ASAP + dynamic filter adds entries at the configured spacing;
  - TP moves after each entry;
  - turning the setting on with 3 open deals on a pair shows the
    confirmation, and confirming leaves one position;
  - moving a terminal deal into the bot adopts it;
  - the ASAP-without-spacing error is shown and its one-click fixes work.
