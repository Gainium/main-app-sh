# 136 — "Client order ID already exists" written off while the order is live

Bug spec (Definition / Evidence / Assumption).

## §1 Definition

In `sendOrderToExchange`, the duplicate branch (`count == 0`, reason matches the
"already exists" family) does this whenever the order is not yet in the map with
a real exchange id, which it never is when the stream lags behind the
placement answer: it calls `deleteOrder` (which also unregisters the id from
the stream router), persists the order as CANCELED, and re-sends it under a
regenerated `…2` id. The venue still holds the original order, live. Its fills
reach no bot, and the copy competes with it for balance.

## §2 Evidence

OKX spot DCA bots, production logs. The bot logs `Order …S is duplicate`, then
sends `…2`. The user stream later reports **both** `…S` and `…2` as `live` on
OKX, and the deal's take-profit is then refused for "not enough balance"
because the orphaned orders lock the funds.

## §3 Assumption

"Already exists" means the venue has an order under this id. That is true for
every phrasing matched except "Client order id is not valid", which is a
format refusal.

## §4 Behaviour after the fix

§4.1 Venue has the order → keep tracking it (via `_handleUnknownOrder(id,
symbol, justPlaced=true)`), no write-off, no `…2` copy.
§4.2 Venue definitively has no such order → unchanged: CANCELED + `…2`.
§4.3 "Client order id is not valid" → unchanged: no lookup, regenerate at
once.
§4.4 Price, size and number of orders a deal places: unchanged. Only the
handling after an "already exists" answer changes.
