# 026 — A re-size cancel is written FILLED, and the replacement it triggers is over-sized by the quantity already closed

Issue #717 (the +6h check on #696). Two coupled defects on the same deal,
B3-USDC `6a90e161a76e7fe63ea3118f`, bot `6a8b89e98e06bef801add796`.

Both are read off production, not inferred.

---

## §1 — Definition

### §1.1 `cancelOrderOnExchange` ignores its own `promotePartialToFilled: false`

**Expected.** `promotePartialToFilled: false` is the caller declaring *intent*:
this cancel is a deliberate RE-SIZE of a still-live order, never a close
(`main.ts:8268-8280`, spec `007.tp-resize-cancel-must-never-promote`, and the
two call sites `dcaHelper.ts:10244` / `dcaHelper.ts:13838`). A partially filled
order cancelled under that flag must be persisted **`CANCELED`**, whatever the
venue's cancel response happens to say.

**Actual.** The response's `status` is copied onto the row *before* the flag is
consulted, so a venue that answers `FILLED` bypasses the opt-out entirely. The
row is written `FILLED` and the flag never runs.

### §1.2 `grossEntryVolume` adds the already-closed quantity back to `deal.size`

**Expected.** `resolveBaseOrderQty` derives the base order's contribution as
`grossEntry - filledQty`. `grossEntry` must therefore be the deal's **gross
entry volume** — the sum of every entry fill, base order included.

**Actual.** `grossEntryVolume` returns `|deal.size| - add - pendingReduceFundsBase`,
and `add` carries the quantity already sold by partial take-profits. `deal.size`
is **already gross** of those closes (§2.2), so they are added a second time.
The base-order contribution comes out over-stated by exactly the closed
quantity, and the take-profit built from it over-states the position by
`closed × (1 - fee)`.

`deal.size` *is* net of executed `reduceFunds` (§2.3), so that part of the
add-back is correct and must stay.

## §3 — Assumption (root-cause hypothesis)

1. `main.ts:8373-8384` copies `request.data.status` onto `order` for every key
   the response happens to carry. The `promotePartialToFilled` guard at
   `main.ts:8385` is written `order.status === 'CANCELED'`, so it reads the
   *venue's* status, not the status the cancel implies. A `FILLED` response
   walks straight past the opt-out.
2. `baseOrderQty.ts:58-64` subtracts `add` (negative closed volume) from
   `|deal.size|`. Since `deal.size` never had the closes taken out (§2.2), that
   is a double count of exactly the closed quantity.

---

## §4 — Solution

### §4.1

Immediately after the field-copy loop, before the existing
`+order.executedQty !== 0 && order.status === 'CANCELED'` guard: when
`promotePartialToFilled === false` and the venue reports fewer units executed
than the row's own `origQty`, force `order.status = 'CANCELED'`.

`origQty` is safe to compare against — the copy loop deliberately excludes it,
so it is still the local row's number. An order the venue reports as genuinely
complete (`executedQty >= origQty`) is a real fill and is left alone.

### §4.2

`grossEntryVolume(dealSize, reduceFundsBase)` returns
`Math.abs(dealSize) + reduceFundsBase`. The `add` / `pendingReduceFundsBase`
parameters go away: `add` bundles take-profit closes (must not be added back),
executed reduce-funds (must be) and pending reduce-funds (must not), and the
only honest way to use it is to stop using it.

`reduceFundsBase` is already in scope at the one call site
(`dcaHelper.ts:14133`). Pending reduce-funds are QUEUED, still in the position,
and `deal.size` already includes them — nothing to add back.

## §5 — Out of scope

- Why `deal.size` / `currentBalances` are not decremented by a partial
  take-profit at all. §2.2 shows this is uniform fleet behaviour and both
  `trackedPosition` and `getTPOrder`'s `add` term are written for it. Changing
  it is a much wider change than this defect.
- The `if (result && result.status === 'FILLED')` compensation at
  `dcaHelper.ts:13844`. With §4.1 it becomes unreachable for a partially-filled
  re-size cancel, but it still correctly catches a cancel that raced a genuine
  complete fill. Left alone.
- The 21 already-drifted deals. This fix stops new ones; repairing the existing
  ones is the #696 armed-repair path, which is a separate, operator-armed run.
