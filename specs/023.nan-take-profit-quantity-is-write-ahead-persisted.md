# 023 — A NaN take-profit quantity is built, sent and write-ahead persisted

Issue #714. Bug spec (Definition / Evidence / Assumption).

## §1 Definition

### §1.1 Expected

`getTPOrder` returns take-profit orders whose quantity is a finite, positive
number. When the deal state it is handed cannot produce one — because the
prices it sizes from are absent — it returns nothing and says so, exactly as
its sibling `createInitialDealOrders` already does when the latest price is 0
(`dcaHelper.ts` "Latest price is 0", `return []`) and as `addDealFunds` already
does for its own quantity (`isNaN(+origQty) || !isFinite(+origQty)` →
`Order qty is not a number`, refuse).

### §1.2 Actual

`getTPOrder` returns a `Grid` with `qty: NaN`. The order is then built, write-
ahead persisted by `sendOrderToExchange` and sent to the venue, which rejects
it. The persisted row keeps `origQty: "NaN"` and `cummulativeQuoteQty: "NaN"`
as **strings** — mongoose's `String` fields accept them — and every later deal
aggregate that casts those strings to `Number` produces `NaN`, so the deal
document can no longer be saved at all.

### §2.2 Scale

16 such rows exist in production `orders`, across 10 deals, 6 bots and 2 users
— **every one of them `exchange: 'coinbase'`, `typeOrder: 'dealTP'`,
`orderId: '-1'`** (the write-ahead record; the venue never accepted one). The
resulting `CastError` deal-save refusals ran to 654 log lines over ~2 h on
2026-09-08.

### §2.3 `MathHelper.round` turns Infinity into NaN

`core/src/utils/math.ts` `round()` stringifies its input, so
`Number('Infinity' + 'e0')` is `NaN`:

```
round(Infinity, 6)      = NaN
round(Infinity, 6, true)= NaN
```

This is the step that converts a division by zero into a NaN nobody can see.

### §2.4 Reproduced against the real code

`core/src/bot/dca/tpNanRefusal.harness.spec.ts` drives the real `getTPOrder`
over the SWFTC-USDC fixture with the deal's price inputs at 0 and its order map
empty, and returns `qty: NaN, price: 0.000001` — the prod row to the digit,
including the `[big.js] Invalid number` it swallows.

## §3 Assumption (root-cause hypothesis)

1. The deal's price inputs reaching `getTPOrder` are 0 (`avgPrice` 0,
   `boPrice` 0) and its order map holds no rows for the deal, so
   `resolveBaseOrderQty` reports `source: 'nominal'`.
2. The nominal re-derivation divides by that price:
   `baseOrderSize / boPrice` (or `baseOrderSize / (usdRate * boPrice)`), giving
   **Infinity**; `Math.max(Infinity, minAmount)` is Infinity.
3. `boQty = this.math.round(Infinity, precision, …)` → **NaN** (§2.3).
4. `_qty = filledQty + boQty` → NaN → `qty` → `tpOrder.qty` → NaN.
5. `tpPrice = round(0 * (1 + tpPerc) * displacement, precision)` is 0, which
   equals `avgPrice`, so the existing "nudge by one tick" fallback sets the
   price to exactly `1e-priceAssetPrecision` — the `0.000001` in §2.1.
6. **Every guard below is a no-op on NaN**, because every comparison with NaN
   is false: `tpOrder.qty < baseAsset.minAmount`,
   `tpOrder.price * tpOrder.qty < quoteAsset.minAmount`, and the combo branch's
   own two `return []` bails. The one thing that does notice —
   `new Big(tpOrder.qty).mod(step)` throwing `[big.js] Invalid number` — is
   caught, logged and **execution continues**.

Coinbase is where it fires because that is where the price inputs went to 0;
nothing in the arithmetic is venue-specific. The identical failure was already
diagnosed and guarded one function away, in `createInitialDealOrders`, whose
comment names it exactly: *"baseQty becomes Infinity (baseOrderSize / 0),
new Big() throws 'Invalid number' and we still return a bogus TP order with an
Infinity qty."* `getTPOrder` never got that guard.

## §4 Required behaviour

### §4.1 Refuse, before the order is built

Before the `tpOrder` `Grid` literal is constructed, a non-finite quantity or a
non-finite/non-positive price must abort the build: report through
`handleErrors` and return `[]`.

### §4.2 `[]` is an established return, not a new contract

`getTPOrder`'s combo branch already returns `[]` for "this deal cannot be
closed right now", and every caller handles it: `placeBaseOrder` guards
`if (tpOrder)`, the tp-coverage repair logs *"has nothing to re-arm with"* and
`continue`s, `remainingCloseQty` already returns `null` on a non-finite qty.

### §4.3 The refusal covers combo as well as DCA

The combo branch recomputes `qty` from `currentBalances`/`initialBalances`,
which the same incident showed going NaN. Placing the guard after that branch
and before the literal covers both engines with one check.

### §4.4 No effect on a healthy deal

A deal with real prices must produce byte-identical orders to today.

## §5 Out of scope

- **The 16 poisoned rows already in production.** Cleaning them is a prod
  database write and is not part of this change.
- Why the coinbase price inputs were 0 in the first place. This spec makes the
  consequence loud and harmless; the price-feed question is separate.
- `sendOrderToExchange`'s write-ahead save (`core/src/bot/main.ts`). Adding a
  second, engine-wide refusal there would catch any other order builder that
  develops the same defect, but it is the widest-blast-radius path in the bot
  and the evidence names `getTPOrder` as the only producer.
