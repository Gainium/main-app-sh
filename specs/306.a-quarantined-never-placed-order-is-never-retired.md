# 306 — A quarantined never-placed order is never retired

A safety order whose placement got no exchange id back keeps the `'-1'`
placeholder, `status: NEW`, and the deal counts it as resting. Spec 109 retires
such an order once the venue definitively says it does not exist. That retire
lives inside `noteOrderNotFound`, and it never reached orders the quarantine
had marked first:

- The restart probe skips every quarantined order (`isOrderQuarantined`)
  before asking the venue, so `noteOrderNotFound` is never called for it.
- The user-stream reconnect pass does ask, and Binance answers `Order does not
  exist.`, but the pass files every lookup without data as "could not read"
  and never calls `noteOrderNotFound`.

Quarantine shipped before spec 109, so every `-1` order it marked in between
is held for good: the reconnect pass reports it unresolved on every pass, the
restart probe says "Skipped 1 quarantined order(s) — not polled. Restart the
bot to re-check them.", and a restart skips it again. The deal believes it has
a safety order on the book that the venue never had. Nothing raises an error.

## §1 Definition

### §1.1 Expected

- **§1.1.1** The restart probe never skips a `'-1'` order for being
  quarantined. A quarantined order that has an exchange id is still skipped.
- **§1.1.2** The restart probe's definitive not-found for such an order
  retires it (spec 109), and the existing restart handling places it again
  (spec 177 §1.2).
- **§1.1.3** In the DCA / Combo reconnect pass, a definitive not-found for a
  `'-1'` safety order (`dealRegular`) past the never-placed age floor
  (spec 177 §1.2) retires it (`CANCELED` row, out of the order map), logs the
  retire, and does not count it as unresolved.
- **§1.1.4** After the pass, each retired safety order of an open deal whose
  book is not being rebuilt is placed again at its level through
  `placeOrders`. An order outside the venue's price band is held there and
  the user told (spec 283).
- **§1.1.5** The grid reconnect pass retires such an order the same way. As on
  the grid restart check, placing it again is left to the next restart's grid
  diff.
- **§1.1.6** The bot's own "no exchange order id" answer never retires
  anything (spec 184 §4.4).
- **§1.1.7** An order with an exchange id is never retired by any of this.
- **§1.1.8** A `'-1'` take-profit is not retired by the DCA reconnect pass;
  the restart check retires it and places its replacement (spec 177 §1.2.1).

### §1.2 Actual

§1.1.1–§1.1.5 did not hold: a `'-1'` order quarantined before spec 109 stayed
`NEW` in memory and in the database indefinitely.

## §2 Evidence

- A `'-1'` Binance spot safety order quarantined about seven weeks before
  spec 109 shipped was still `NEW` months later. The reconnect pass logged
  "Reconcile could not read 1 order(s) after 1 lookup attempt(s)" for it on
  every pass. "after 1 lookup attempt" is the retry ladder stopping on a
  definitive answer.
- The retire's log line ("never reached the exchange and the exchange
  confirms it does not exist (Order does not exist.)") does appear for other
  orders, so Binance's answer is definitive and the retire works where it is
  reached. It never appeared for this order.

## §3 Assumption

A `'-1'` order is one the venue never acknowledged. Asking about it once per
restart and once per reconnect pass costs at most one lookup each, and a
definitive answer removes it for good. The quarantine guards against
repeatedly asking about orders that DO have an exchange id. It has no job for
a `'-1'` order that spec 109 can settle.

## §4 Tests

`src/bot/quarantinedNeverPlacedOrder.harness.spec.ts`:

- §4.1 `isOrderQuarantined` — `'-1'` not skipped, exchange id skipped (§1.1.1).
- §4.2 `noteOrderNotFound` retires a quarantined `'-1'` order (§1.1.2).
- §4.3 DCA and Combo reconnect pass: retired, logged, placed again, not
  unresolved (§1.1.3, §1.1.4).
- §4.4 the bot's own answer retires nothing (§1.1.6).
- §4.5 an exchange id is left alone (§1.1.7).
- §4.6 a `'-1'` take-profit is left to the restart check (§1.1.8).
- §4.7 a deal that is not open, or whose book is being rebuilt, gets nothing
  placed (§1.1.4).
- §4.8 grid reconnect pass: retired; own answer and exchange id untouched
  (§1.1.5–§1.1.7).

## Invariants

- `never-placed-order-quarantined-resting` (main-app pack, observe): no open
  order holds `orderId: '-1'` with `quarantine.since` set. After this fix such
  an order is asked about on every restart and reconnect, so one that persists
  means the retire is still not reached.
