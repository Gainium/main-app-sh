# 115 — A deal-settings edit re-places a spent safety order

Bug spec. The behaviour already exists and is wrong.

## §1 Definition

### §1.1 Expected

Once every configured safety order of a DCA deal has filled, rebuilding the
deal's orders (a deal-settings edit, e.g. changing the take profit) keeps no
safety order. Only the exit orders are placed.

### §1.2 Actual

`createCurrentDealOrders` counts the ladder levels still to place as
`left = ordersCount - <filled ladder orders>`. It then picks one of two
selections per direction:

- `left && !isNaN(left)`: the nearest `left` levels, on the far side of the
  price;
- otherwise, the "no count" selection: EVERY level on the far side of the
  price.

`left === 0` is falsy, so a spent ladder takes the second branch. When the
rebuilt ladder puts a level beyond the deal's `lastPrice`, that level is kept
and `updateDealSettings` hands it to `placeOrders`. It already filled. The
venue refuses it for balance (the bot goes to error), or, when the balance is
there, the deal takes on position the user never configured.

The rebuilt level does not have to be the filled one's exact price. The ladder
is recomputed from the deal's settings, so a one-tick drift from the fill is
enough to put it beyond `lastPrice`, which the last fill had set.

## §2 Evidence

- Prod log, DCA bot worker, 2026-09-27 (SHORT spot deal, `ordersCount: 6`,
  all six safety sells FILLED, the last at 0.4925):
  `00:31:14.852 Generate initial deal orders`, then
  `00:31:14.853 Generate current deal orders @ 0.4925`. That is the path
  `updateDealSettings` takes, and it ran in the same second as the
  `updateDCADealSettings` API call (`tpPerc: 25, trailingTp: true`).
  `00:31:15.113 Not enough balance … side: sell, price - 0.4926, order type:
  DCA … required - 209.72 TIA` is the size of level 6, re-sent one tick from
  its fill. The bot re-sent it again on restart at 00:34:20.
- Harness `src/bot/dca/spentLadderReplace.harness.spec.ts`, before the fix:
  with all six levels FILLED, `createCurrentDealOrders` returns the rebuilt
  level 6, and `updateDealSettings` places it, on both SHORT and LONG.

## §3 Assumption (root cause)

The selection treats `left === 0` ("no level remains") the same as "the count
could not be computed" (NaN). The fix is to give `left === 0` its own meaning:
no safety order.

## §4 Scope

- §4.1 Changed: a deal whose configured ladder (`ordersCount`, or the custom
  step count) is non-zero and fully filled keeps no safety order.
- §4.2 Not changed: which safety orders are selected while at least one level
  is unfilled (`left > 0`), a NaN count, or a bot with no configured ladder
  (`ordersCount` 0).
- §4.3 Not addressed: `left < 0` (more ladder fills than the ladder now
  configures, e.g. `ordersCount` lowered mid-deal). It still takes the
  counted branch with a negative slice.
