# 126 — REST bot update and clone can replace a bot's indicators

Feature spec, landing in existing code (the REST update/clone handlers).

## §1 Behaviour today

A DCA or Combo bot's indicators (`indicators`, `indicatorGroups`) can be set
when the bot is created through the public REST API, but no REST call can
change them afterwards:

- `PUT /api/v2/bots/{dca|combo}/{botId}` and `POST /api/v2/bots/{type}/{botId}/clone`
- the legacy `POST /api/updateDCABot`, `POST /api/updateComboBot`,
  `PUT /api/cloneDCABot`, `PUT /api/cloneComboBot`

all reject a body carrying either key with `400 Unknown settings`, because
the bot-settings allowlist does not list them. The OpenAPI
`UpdateDCABotInput` does not document them either. The dashboard can edit
indicators (through GraphQL, which has no allowlist) and the engine already
reloads a running bot's indicator set when its settings change.

## §2 Behaviour wanted

### §2.1 Accepted

Every endpoint in §1 accepts `indicators` and `indicatorGroups` for DCA and
Combo bots.

### §2.2 Full-array replacement

Each array is replaced wholesale by what the request sends; there is no merge
by `uuid`. Sending `indicators: []` removes every indicator. A caller keeps an
existing indicator by sending it back, `uuid` included. An array that is not
sent stays as stored.

### §2.3 Same item rules as creation

Each indicator and group is checked against the same field schema bot
creation uses, after the same per-type defaults are filled in — so a minimal
indicator that creation accepts is accepted here. A non-array value is
rejected.

### §2.4 Round trip

An indicator read back from the API and sent again unchanged is accepted. In
particular a stored per-item `_id` is ignored, not rejected.

### §2.5 Consistency judged on the resulting bot

The cross-field rules creation applies (a `ti` start needs a `startDeal`
indicator; group references resolve both ways; no duplicate ids; at most 20
indicators; indicators present must be used by some condition) are applied to
the settings the bot will run with — the stored settings with the update laid
over them — because the condition and the indicator it needs can sit on
either side of the update. A request that would leave the bot inconsistent is
rejected with `400`, reason `Validation error`, and an `errors` list of
`[field, message]` pairs, the same shape creation uses.

### §2.6 Variable links

A bot variable linked into an indicator (`indicators.{uuid}.{key}`) whose
`uuid` the update removes is unlinked; links into a kept `uuid`, and links to
anything else, stay.

### §2.7 Nothing else changes

A request that sends neither key, and does not change `startCondition` or
`dcaCondition`, behaves exactly as before.

### §2.8 Safety-order indicators

Safety-order indicators (`indicatorAction: startDca`, `section: dca`, with
their per-indicator `minPercFromLast`) are items of the same array and follow
§2.2–§2.6. In addition, a **bot** update may now set
`dcaCondition: "indicators"` (DCA) and `startCondition: "TechnicalIndicators"`
(DCA and Combo) — both previously rejected as `Wrong settings` — so a bot can be
moved onto indicator-driven safety orders or an indicator deal start. A
**deal** update still may not set `dcaCondition: "indicators"`.

Whenever an update changes `startCondition` or `dcaCondition`, even without
indicator keys, the resulting bot must have an indicator for every
indicator-driven condition it uses (§2.5's "needs its indicator" rules only;
the other consistency rules are not re-judged on stored data the request did
not touch).
