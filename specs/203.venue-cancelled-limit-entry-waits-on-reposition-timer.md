# 203 — a venue-cancelled limit entry waits on a reposition timer that never acts

Bug spec. Follows `263de26` (the cancelled-entry check) and specs `038`, `048`
and `125` (the base-entry settle paths).

## 1. Definition

### 1.1 Expected

When the exchange cancels a deal's LIMIT base order before any of it traded,
and the bot did not ask for that cancel, the deal is cancelled about
`canceledBaseEntryDelayMs` later and the bot is free to open a new one. That
is what already happens to an entry whose deal holds no timers.

### 1.2 Actual

On a bot that repositions its limit entry, or has an enter-market timeout,
the deal holds `dealTimersMap` state, and the deal stays in `start` with
nothing on the venue. Nothing is logged and nothing is sent to the user. The
hourly old-start-deals cron cancels it 24 h later.

## 2. Evidence

Production, a single-deal Coinbase DCA bot, DCA worker log, 2026-10-24 UTC:

```
23:09:37.269 Deal created with id <deal>
23:09:37.804 Processing msg <pair> D-BO-…, NEW, 0.0069
23:09:38.053 Processing msg <pair> D-BO-…, CANCELED, 0.0069, base: 0
   …nothing for this deal for 24 h…
2026-10-25 23:15:01.987 [cron-jobs] Closing old start deals | closing DCA deal <deal>
```

- The venue cancelled the entry 0.25 s after it was placed. There is no
  `not filled. Create new one` line, which the bot logs before each of its
  own cancels, so the bot did not cancel it.
- The `was canceled on the exchange … not by the bot` line is missing for
  this deal. It appears thousands of times for other bots.
- The sentinel invariant `deals.start-stuck-nothing-resting` raised the deal.

Code path (core `src/bot`):

1. The order queue (`main.ts`, cancel branch) deletes a CANCELED row with no
   fill from the order map, then calls `processCanceledOrder`.
2. `checkUnfilledBaseEntryCancel` passes
   `hasPendingCheck: dealTimersMap.has(dealId)`, which is true, so
   `isUnattributedUnfilledBaseEntryCancel` declines.
3. The reposition tick `checkBaseOrder(id)` reads the order map, finds
   nothing, and returns without a log line or a re-arm. The enter-market
   timer is armed only when that timeout is on.

The harness (`dca/venueCanceledBaseEntry.harness.spec.ts`, spec 203 block)
reproduces steps 2 and 3. Before the fix, cases §4.1 and §4.4 fail: the
timers stay and no deal check is armed.

## 3. Assumption

The timer deferral is redundant for the case it was written for.
`cancelOrderOnExchange` calls `noteOwnCancel` before every cancel the engine
sends, and every engine cancel goes through it: a reposition, a re-size, a
close, and the bulk cancel through `primeCancelBatch`. So `ownCancel` already
separates the engine's cancels from the venue's. With timers held, the
deferral only routes a venue cancel to a tick that cannot act on it.

## 4. Required behaviour

- §4.1 An unattributed, unfilled CANCELED entry on a `start` deal with no
  other live `dealStart` row stops the deal's reposition and enter-market
  timers, drops its `dealTimersMap` entry, and arms the cancelled-entry
  check. This holds whether or not the deal has timers.
- §4.2 A cancel the bot recorded (`isOwnCancel`) does exactly what it does
  today. Its timers stay and no check is armed. That covers the bot's own
  reposition cancel-and-re-place.
- §4.3 If another `dealStart` row of the deal is still resting, nothing
  changes.
- §4.4 A reposition tick for an entry that is no longer in the order map, on
  a `start` deal whose timers this process holds, with no live `dealStart`
  row and no own-cancel record, does what §4.1 does instead of returning
  silently. This is the safety net for a cancel report that was processed
  before the timers were armed.
- §4.5 The restore path, which holds no timers, is unchanged.
- §4.6 Part-filled entry settlement (`shouldSettlePartialBaseEntry`, specs
  038/048/125) is unchanged.
- The 15 s re-check (`cancelDealOfCanceledBaseEntry`) is unchanged. If the
  deal holds timers again or has a live entry by then, a new entry was placed
  and the deal is left alone.

## Invariants

There is no new invariant. `deals.start-stuck-nothing-resting` in main-app's
`specs/invariants/deals.invariants.json` already catches this state. That
invariant is how the case was found.
