# 134 — A teardown cancel refused for rate is never re-sent, and the row stays NEW

Bug spec. Related: `011` (cancel an order that never reached the venue),
`082` (batched teardown cancels).

## §1 Definition

### §1.1 Expected

When a DCA or Combo bot is stopped or deleted, every resting order it cancels
ends up recorded as the venue holds it — `CANCELED` (or `FILLED`), not `NEW`.

### §1.2 Actual

`stop()` walks the bot's resting orders through `cancelOrderOnExchange`. When
the venue refuses a cancel for rate (Bybit: `Too many visits. Exceeded the API
Rate Limit.`, returned after the connector's own short retry ladder is
exhausted), the refusal is reported through `handleErrors` and nothing else
happens: the row stays `NEW` in memory and in the database. `stop()` then
closes the user stream. The venue's own `Cancelled` event for the order, which
arrives later, reaches no listener, so nothing ever corrects the row. On a
deleted bot no later start, sweep or reconcile revisits it.

## §2 Evidence

Production, Bybit spot Combo bots deleted in batches on one API key
(identifiers withheld — this file is public):

- `12:24:31Z` "Close by cancel"; the deal's grid orders are cancelled one by
  one.
- `12:24:43Z` cancel of a grid order refused: `Too many visits. Exceeded the
  API Rate Limit. Method limitOrders() Step Send cancel request CMB-GR-…`.
- `12:24:58Z` minigrids closed; the stop completes and the stream is released.
- `12:25:32Z` the user-stream connector receives the venue's `Cancelled`
  event for that order. The bot worker logs nothing for it.
- Today the row is still `NEW`. Every `NEW` grid row left on the deleted bots
  of that account matches a logged rate-limit refusal of its teardown cancel.

## §3 Assumption (root cause)

The teardown is the one caller of `cancelOrderOnExchange` with no second
chance to learn an order's outcome. A rate-limit refusal is transient: the
same request succeeds later. Re-sending it after a back-off, while the bot is
stopping, gets an answer that the existing routing already turns into the
right row — `CANCELED` on success, or the unknown-order ladder when the venue
says the order no longer exists.

## §4 Required behaviour

- §4.1 While the bot is stopping, a cancel refused for rate is re-sent after a
  back-off; a successful answer is recorded as for any cancel.
- §4.2 An answer of "order does not exist" on a re-send goes to the
  unknown-order ladder (existing routing), which records the venue's state.
- §4.3 The re-sends are bounded (three, ~5s / 15s / 45s, jittered so the bots
  of one mass deletion do not return in the same second). When all are
  refused, the refusal is reported exactly as before.
- §4.4 A running bot is untouched: one request, reported as before.
- §4.5 Any refusal that is not a rate limit is not re-sent.

"Stopping" is `blockPriceCheck`, which `DCABotHelper.stop()` sets before it
cancels anything and `clearClassProperties` resets.

## §5 Out of scope

- Rows already left `NEW` by past teardowns (a data repair, tracked
  separately).
- Pacing a mass teardown across bots on one key.
