# 030 — A manual deal close reports success without acting

Bug spec (existing behaviour is wrong).

## §1 Definition

### §1.1 Expected

When a user (dashboard) or an API client asks to close/cancel a deal, exactly one
of two things must be true afterwards:

- the engine actioned the request and the deal reaches a terminal status
  (`closed` / `canceled`); or
- the user is told the request did not take effect.

### §1.2 Actual

`BotInstance.closeDCADeal` / `closeComboDeal` (`src/bot/index.ts`) dispatch the
close to the owning bot worker with `worker.postMessage(...)` — fire and forget —
and immediately return `{status: ok, data: 'Deal scheduled to be closed'}`.

Inside the worker, `DCABotHelper#closeDealById` (`src/bot/dcaHelper.ts`) resolves
the deal from the in-memory map (`this.getDeal(dealId)`). When the map has no
entry it logs `[WARN] Deal <id> not found when close` and returns. The WARN is a
log line only (`MainBot#handleWarn` → `_handleLog('warn', …)`); it reaches no bot
event, no notification and no deal field.

So a close request against a deal that is live in the database but absent from
the worker's map is answered `ok`, is never actioned, and leaves no user-visible
trace at all.

### §1.3 Second, independent defect on the same path

`closeDCADeal` also writes a bot event *on dispatch*:

```
event: 'Close DCA deal', description: `DCA deal closed manually, id: ${dealId}`
```

It is written before the worker has done anything, so it is written just as
reliably when the close is silently dropped. It is the record the user reads to
confirm the close happened — and in the failure case it is false.

## §2 Evidence

Prod, user-initiated cancel, 2026-09-08 (bot `6a9456d3…`):

```
main-app-out  22:11:58.196Z [DEBUG] Api call closeDCADeal ["…","6a9456d3…","6a9ca65c…","cancel",true,false,null]
DCA-bot-error 22:11:58.204Z [WARN]  Bot (dca) 6a9456d3… | Deal 6a9ca65c… not found when close
main-app-out  22:17:39.631Z [DEBUG] Api call closeDCADeal ["…","6a9456d3…","6a9c6d36…","cancel",true,false,null]
DCA-bot-error 22:17:39.636Z [WARN]  Bot (dca) 6a9456d3… | Deal 6a9c6d36… not found when close
```

A few ms after the API accepted each request the engine dropped it.

**What the user was shown.** `botEvents` for the two deals holds *four* rows,
one per click, each written at the dispatch instant and each answered ~1 ms
later by the WARN above:

```
2026-09-08T22:11:58.203Z  Close DCA deal | DCA deal closed manually, id: 6a9ca65ce93810e4ab166d77
2026-09-08T22:17:39.636Z  Close DCA deal | DCA deal closed manually, id: 6a9c6d36e93810e4ab1125bd
2026-09-09T15:57:08.772Z  Close DCA deal | DCA deal closed manually, id: 6a9c6d36e93810e4ab1125bd
2026-09-09T15:57:36.804Z  Close DCA deal | DCA deal closed manually, id: 6a9ca65ce93810e4ab166d77
```

No close event follows any of them. **The repeat a day later is the proof the
signal is missing**: the user came back and clicked cancel on both deals again,
which nobody does if they were told the first attempt failed. The record they
had to read from said, four times, that the deal was closed manually.

Both deals stayed `status: open` from 2026-09-08 until an out-of-band manual
correction to the production database on 2026-09-10 (part of a separate
data-repair task) set them to `canceled`; their `updated` timestamps still read
`13:22:31Z` / `13:36:51Z` on 08 Sep, i.e. **the product never wrote to them
after the close attempts.** Nothing in the engine ever actioned these closes.

Population of the WARN across the retained prod log window (579 lines, 45
distinct bot+deal pairs): one pathological pair repeats hourly (521 lines, deal
`6a86d694…`, `status: start` since 2026-08-20). Searching all 155 retained
`main-app` log files for that deal id returns **0 matching lines** — it is an
**internal engine** retry, not a request anybody was answered `ok` for, and the
`manual`/`api` gate in §4.1 excludes it. The reporter's two are the dispatch
case and appear once per user click.

## §3 Assumption (root-cause hypothesis)

The map miss itself has its own cause and is **out of scope here** (tracked
separately as spec 028 / the deal-state divergence work). What this spec fixes is
the *reporting* contract on top of it:

1. `closeDealById`'s `!findDeal` branch cannot distinguish "already terminal, this
   request is a duplicate — nothing to do" from "the database still says this deal
   is live, so the request was lost". It treats both as a debug-grade WARN.
2. `closeDCADeal` writes the confirmation event on dispatch rather than on the
   confirmed action.

A read-only status lookup in the `!findDeal` branch separates the two cases.
It must stay read-only: re-entering close from there would re-close the 46 of 47
deals in the measured population that are already terminal (the constraint the
prior triage established, and the reason this spec does not add a Mongo
fallback).

## §4 Required behaviour

### §4.1 The verdict

Given a close request whose deal is missing from the worker's map, and the deal's
status as the database reports it *at that moment*:

| DB status | close trigger | verdict |
|---|---|---|
| absent / unreadable | any | `silent` — nothing can be claimed |
| `closed`, `canceled` | any | `silent` — duplicate request, today's WARN is the whole story |
| `open`, `start`, `error` | `manual`, `api` | `report` — a caller was answered `ok` and nothing happened |
| `open`, `start`, `error` | anything else | `silent` — internal engine retry, no caller was answered |

The live set is the complement of `{closed, canceled}` — deliberately the same
predicate `closeDCADeal` itself uses to admit the request
(`status: {$nin: [closed, canceled]}`), so the two cannot drift apart.

`manual` and `api` are exactly the triggers the dispatch path produces:
`closeTrigger ?? DCACloseTriggerEnum.manual` in `closeDCADeal`/`closeComboDeal`,
and `DCACloseTriggerEnum.api` from the public REST close route. No internal
engine call site produces either (`tp`, `sl`, `timer`, `bot`, `base`, `auto`,
`webhook`, `liquidation`, `combined`, `indicator`, `trailing`).

### §4.2 The report

A `report` verdict raises, on the deal:

- a `botEvents` row (`event: 'Deal'`, `type: warning`, carrying `deal` and
  `symbol`), and
- a user notification via `processError` with `setError = false`
  (a failed close must not flip the bot into `error` — the bot is fine; the
  request was lost) and `sendError = true`, `force = true` (a user who cancels
  two deals in a row has to be told about both, so the re-raise backoff must not
  swallow the second).

Subtype `Close request not actioned`, its own row so the admin error rules can
tune it without touching real errors.

### §4.3 The premature confirmation

The `DCA deal closed manually` / `Combo deal closed manually` bot event written on
dispatch is removed. A confirmed close already writes its own deal event from
`processDealClose` (`dealCloseEventDescription` — "Deal closed…" / "Deal
cancelled…"), and the `leave` path already writes one from
`announceLeftOpenPosition` when volume is left behind. The only case that loses an
event is `leave` on a deal holding nothing, where there is nothing to report.

## §5 Non-goals

- §5.1 Fixing why the map entry is missing (spec 028 / #719).
- §5.2 Making the close request synchronous, or acknowledging it back through
  `postMessage`. That changes the API contract shape and is a much larger change;
  the reporting gap is what the user was hurt by.
- §5.3 Any write to the deal from the `!findDeal` branch.
