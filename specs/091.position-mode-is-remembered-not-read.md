# 091 — A futures bot remembers the account's position mode instead of reading it

Bug spec. The behaviour already exists and is wrong.

## §1 Definition

### §1.1 Expected

A futures account is in one of two position modes. In **one-way** mode the venue
keeps a single net position per contract and every order must name `BOTH`
(`net`, on OKX). In **hedge** mode the long and the short leg exist
independently and every order must name the leg it acts on (`LONG` / `SHORT`).

The mode belongs to the account and the user may change it at the exchange at
any time, without telling us. Whatever the engine puts in `positionSide` must
therefore follow the mode the VENUE is enforcing now — not the mode we recorded
when the connection was added.

### §1.2 Actual — a restart adopts a cached mode

`user.exchanges[].hedge` is a cache. It is written when the connection is added
and when the user flips the mode through Gainium's own `setHedge` mutation.
Nothing writes it when the user flips the mode at the exchange.

`MainBot.loadData` substituted that cache for the live read whenever the load
was a service restart:

```ts
const skipFutures = this.serviceRestart && !this.secondRestart
…
let hedge = allPositions
  ? skipFutures
    ? { data: !!keys.hedge, status: StatusEnum.ok }   // ← the cached copy
    : await this.exchange.getHedge()
  : null
…
if (hedge.status === StatusEnum.ok) { this.hedge = hedge.data }
```

`this.hedge` is what every order builder in the engine reads
(`this.hedge ? (this.isLong ? LONG : SHORT) : BOTH`, ~20 call sites across
`dcaHelper`, `comboHelper`, `helper` and `main`), so one wrong value at load
makes every order of that bot name the wrong mode, and the venue refuses all of
them:

| Venue | Code | Message |
|---|---|---|
| OKX | 51000 | `Parameter posSide error` |
| Binance USD-M / COIN-M | -4061 | `Order's position side does not match user's setting.` |

Both directions of the disagreement produce the same refusal — OKX answers
`Parameter posSide error` both for `net` sent to a hedge account and for
`long`/`short` sent to a one-way account.

`allPositions` (binance / okx / bitget / kucoin-full / paper) is the only family
affected. Every other futures venue falls through to `getHedge(symbol)` further
down the same block, which has always been a live read on every load.

### §1.3 The user-visible failure

The bot places nothing. It cancels and re-places its ladder on each tick, every
replacement is refused, and an open position is left with no resting orders
around it. Nothing recovers it: the next service restart reads the same cached
copy and fails identically.

## §2 Evidence

Production, `okxLinear`, `SOL-USD_UM_XPERP`, combo LONG:

1. **The cache is a month old.** The connection stored `hedge: false` with
   `lastUpdated 2026-08-22T02:19:16.645Z`. The account was switched to hedge
   mode at the exchange around 2026-09-20.
2. **The restart read cost nothing, which is the signature.** The bot log holds

   ```
   [3395522] 2026-09-23T00:54:59.190Z | Bot (combo) … | Get hedge
   [3395522] 2026-09-23T00:54:59.190Z | Bot (combo) … | Got hedge: false
   ```

   The two lines bracket the read and are in the SAME millisecond: no exchange
   round trip happened. That is only reachable through the `skipFutures` arm.
3. **36 seconds later the venue refuses.**

   ```
   [3395522] 2026-09-23T00:55:35.530Z | … Reason Parameter posSide error
                Method limitOrders() Step Send new order request …, side BUY
   ```

   Repeated at 2026-09-22T23:08, 2026-09-23T00:55 and 04:56 — three separate
   worker PIDs, i.e. three separate service restarts, each re-reading the same
   cached `false`.
4. **Not one account.** The same refusal appears for a second, unrelated
   `okxLinear` connection on 2026-08-18/19, that one with `hedge: true` stored —
   the mirror-image disagreement.

## §3 Assumption

The root cause is the substitution in §1.2 and nothing downstream of it. The
`positionSide` expression at every order builder is correct GIVEN `this.hedge`;
`this.hedge` is wrong because `loadData` was handed a cached boolean instead of
the venue's answer.

A test written from this assumption must fail because the venue's mode is never
asked for — not because an order builder computed the wrong side from a correct
mode.

Corollary, and the reason a load-time fix alone is not the whole answer: the
mode can also change while the bot is already running, when no load happens at
all. The only evidence the engine gets in that window is the refusal itself.

## §4 Required behaviour

### §4.1 The mode is read from the venue on every futures load

`loadData` asks the venue, for every futures connection, service restart or
not. The stored copy is used only when the venue does not answer — which is
strictly what the substitution did anyway, so nothing gets worse when the
exchange is down.

### §4.2 …but once per connection, not once per bot

The substitution was introduced deliberately (`main-app-sh` 198d586,
2025-08-05, "Read hedge status from db while in service restart") to take one
exchange call per futures bot off a mass restart. That concern is legitimate —
there are of the order of 1,400 live futures bots on the affected venues — and
the fix must not simply revert it.

Position mode is a property of the CONNECTION, so one read answers every bot on
it. Coalescing the read per `exchangeUUID` with a short freshness window makes a
mass restart cost roughly one call per account (≈320) rather than one per bot,
i.e. strictly fewer calls than the code 198d586 replaced.

The freshness window applies to the SERVICE RESTART only. A user-initiated start
keeps the uncached read it has today: `setHedge` runs in the API process and
cannot invalidate a bot worker's in-process cache, so a user who changes the mode
through Gainium and immediately starts a bot must not be served a window-old
answer. Concurrent starts still share one in-flight call.

### §4.3 A venue-read mode is written back

When the venue disagrees with `user.exchanges[].hedge`, the stored copy is
corrected. It is the fallback in §4.1 and it is read by other consumers, so
leaving it wrong guarantees the next unanswered read is wrong too.

The write is scoped to the one array element and to the `hedge` field. It does
NOT touch `status` or `lastUpdated`: those record the user telling us something,
and this is us catching up with the exchange.

### §4.4 The position mode on the user's exchange account is never changed

Nothing on this path calls `setHedge`. The mutation's active-bot guard is
untouched and still refuses a mode change while bots are running; this fix does
not depend on that guard, it only reads.

### §4.5 A position-side refusal re-reads the mode and re-sends once

On `Parameter posSide error` / `-4061`, `sendOrderToExchange` re-reads the mode
(accepting an answer at most a few seconds old, so a burst of refused orders is
not a burst of venue calls), stores it per §4.3, and re-sends the order under
the corrected mode.

Self-limiting with no counter, exactly like the existing tick-size branch: the
resubmission carries the mode just read, so a second refusal finds the live mode
equal to the one already held and falls through to normal error handling.

### §4.6 The recovery refuses to guess a leg

Correcting hedge→one-way is unambiguous: `BOTH`. Correcting one-way→hedge needs
the leg, and the recovery takes it from the bot's own direction — the same
expression the order builders use. When the settings name no single leg (a
NEUTRAL grid), the recovery does NOT re-send. On a hedge account a wrong leg
does not fail; it opens a position on the other side.

### §4.7 One-way accounts are unchanged

An account whose venue-reported mode equals its stored mode — every one-way
account that nobody has touched — takes exactly the path it takes today: the
same `this.hedge`, the same `positionSide`, no write-back, no retry.
