# 125 — A part-filled base-entry settle waits out an asynchronous cancel

Bug spec. Extends `038` (settle a part-filled entry), `048` (terminal rows) and
`059` (a cancel answer that states no fill).

## §1 Definition

### §1.1 Expected

When `settlePartialBaseEntry` cancels the remainder of a part-filled base
order, the deal opens on the quantity that executed — whatever moment the
venue chooses to report the cancel as done.

### §1.2 Actual

On Coinbase the cancel is asynchronous. The connector's `cancelOrder` sends
the cancel and immediately reads the order back; at that instant the venue
still lists it `OPEN`, which the connector maps to `PARTIALLY_FILLED`.
`settlePartialBaseEntry` treats every non-terminal answer as "not settled",
warns `could not be settled (PARTIALLY_FILLED). Deal stays in start until the
bot restarts`, and returns. The deal stays in `start` with zero balances, no
take profit and no safety orders, while the account holds the executed
quantity.

### §1.3 Actual, second half

The venue's own `CANCELED` user-stream event for the same order arrives a few
hundred milliseconds later, carrying the fill. `processCanceledOrder` declines
to settle it because the deal still holds LIMIT-entry timers
(`hasPendingCheck: dealTimersMap.has(dealId)`) — the rule that leaves an
engine-owned cancel to the engine. But the engine's settle has just given up,
so nothing acts on it until the next bot start.

## §2 Evidence

Production, Coinbase spot, LIMIT entry, 2026-10-02 (identifiers withheld —
this file is public):

- `13:36:18.250Z` stream: base order `PARTIALLY_FILLED`, 12055.9 of 14913.5.
- `13:36:28.170Z` reposition tick: "stopped at 12055.9 of 14913.5 … Cancelling
  the remainder and opening the deal on what filled".
- `13:36:28.501Z` / `.750Z` stream: `CANCELED`, base 12055.9 (twice).
- `13:36:28.610Z` WARN: "could not be settled (PARTIALLY_FILLED)".
- Orders collection: the row is `CANCELED`, `executedQty: 12055.9`, dated.
  Deal: `status: start`, `currentBalances {base: 0, quote: 0}`.

Connector: `exchange-connector-sh` `coinbase/index.ts cancelOrder` reads
`getOrder` right after `cancelOrder` succeeds; `convertOrder` maps
`OPEN`/`PENDING` with `completion_percentage > 0` to `PARTIALLY_FILLED`.

## §3 Assumption (hypothesis)

The settle gives up on the first, non-terminal cancel answer. Re-reading the
order a few times after a cancel the venue ACCEPTED returns the terminal state
(`getOrder` already promotes `CANCELED`-with-fills to `FILLED` and converts
the quantity), which the existing `bookSettledBaseEntry` chain books.

## §4 Required behaviour

### §4.1 Wait out the cancel

When the cancel answer is a row whose status is not terminal (`NEW` /
`PARTIALLY_FILLED`), the settle re-reads the order through
`getOrderForReconcile`, at most `baseEntryCancelSettleAttempts` times,
`baseEntryCancelSettleDelayMs` apart, and stops at the first terminal answer
(`FILLED`, `CANCELED`, `EXPIRED`).

- `FILLED` → the row is persisted (forced, as `promoteEndedBaseEntry` does)
  and booked through `bookSettledBaseEntry`.
- `CANCELED` / `EXPIRED` → the existing spec `059` path
  (`settledBaseEntryFill` against what was observed before the cancel).
- Still not terminal after the last attempt → the existing warn, unchanged.

A cancel that got no answer at all (`undefined`) is not re-read: there is no
evidence the venue accepted it (spec `059` §1.1 unchanged).

### §4.2 A failed settle hands the order back to the stream

When a settle ends in the warn, the order is recorded as unsettled. A later
`CANCELED`/`EXPIRED`-with-fills event for it on a `start` deal settles the
deal even though the deal still holds timers.

### §4.3 No double booking

- A settle already running for an order makes a second call for the same
  order a no-op.
- Once a deal is booked it leaves `start`, so `shouldSettlePartialBaseEntry`
  refuses every later event for it (unchanged).

### §4.4 Restore path (workaround check — refuted, fixed)

`restoreWork` picks a `start` deal's `CANCELED`-with-fill base row from Mongo
(`pickRestoreBaseEntry`, spec `048`) and hands its id to `checkBaseOrder`,
which reads the in-memory order book. A bot start loads that book from Mongo
with `status: { $nin: ['CANCELED', 'EXPIRED'] }`, so the row is not there and
`checkBaseOrder` does nothing: a restart does NOT settle such a deal unless a
Redis order snapshot happens to still hold the row. The spec `048` harness
pre-seeds the row in memory, which hid this.

Required: when the picked row is terminal with a dated fill and is not in
memory, `restoreWork` reads the full row and puts it in the order book
(without a Redis write) before `checkBaseOrder`, which then settles it through
the existing terminal-row path (no venue call).
