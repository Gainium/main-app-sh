# 171 — The funding-reservation read scans every deal on every new-deal check

Bug spec (gainium-dev-flow Part 0). Main-app spec 044 §5 / §8 owns the
reservation itself; this spec changes only how it is read.

## 1. Definition

§1.1 Expected. A spot DCA / combo bot's new-deal balance check
(`checkBalance`) subtracts what the account's bot-funded deals hold
(`FundingReservation.reservedQuote` / `reservedBase`) and returns in well
under a second. Once the funds a closed deal freed are on the account, the
next deal opens on the first check that sees them, or on the spec 152
re-check 10 s later.

§1.2 Actual. The reservation read filters the deals collections on
`exchangeUUID`, `symbol.<asset>`, `status` and an `$or` over the funding
fields. None of those fields leads an index on `dcadeals` or `combodeals`,
so every read is a full collection scan. Each balance check therefore
blocks for minutes, and every spot bot runs it, whether or not its user
ever funded a deal. One refused check plus its 5 s retry takes about
4 minutes instead of about 5 seconds. The 10 s re-check then pays the same
cost again before the deal opens.

## 2. Evidence

§2.1 Prod mongod slow log, 2026-10-18 14:55–15:34Z (read-only index
snapshot). The top four slow shapes are this read:
`COLLSCAN gainium.dcadeals {$or,exchangeUUID,status:{$in},symbol.baseAsset}`
ran 6,036 times at p50 105 s and p95 137 s. The `symbol.quoteAsset` shape
and the two `combodeals` shapes follow it. Together they are about 97% of
all slow-op time in that window. `dcadeals` holds about 2.8M documents.

§2.2 Prod bot log, a short LDOUSDT bot, 2026-10-18:
- 14:36:25.8: TP filled.
- 14:36:27.9: `Open new deal` and `Check assets start`.
- 14:36:28.3: orders generated, then nothing for about 114 s, which is the
  reservation read plus the 5 s sleep.
- 14:38:22.6: `Check assets start` (the retry).
- 14:40:05.6: the warning is logged, about 103 s later.
- 14:40:15.6: the spec 152 re-check.
- 14:41:39.8: `Create new deal`, about 84 s later.

The same roughly 2-minute gap between the two `Check assets start` lines
shows on unrelated bots in the same worker. For example, on two BTC bots:
14:31:54 → 14:34:15 and 14:37:10 → 14:39:15. So the stall is not
specific to the pair, the deal or the user.

§2.3 Onset: the read shipped with the base-funding feature (core 1.103.0,
`0001164`, 2026-10-18) and has run on every spot balance check since.

## 3. Assumption (hypothesis, confirmed by §2.1)

§3.1 The stall comes from the reservation query not being index-backed.
An account (`exchangeUUID`) belongs to exactly one user: `linkedTo` only
links legs within one user's own `exchanges`. So adding the owner's
`userId` to the filter returns the same deals. The read can then use the
existing `userId_1_status_1_createTime_-1` index on `dcadeals` and
`userId_1` on `combodeals`.

## 4. Required behaviour

- §4.1 The reservation read filters on the account owner's `userId`, in
  addition to every condition it has today.
- §4.2 The result is unchanged: the same deals, reserved figures and cache.
- §4.3 Without a `userId`, the read does not query; it answers 0, as it
  already does without an `exchangeUUID`. Every caller has the owner at
  hand: the bot's `userId`, or the session user in the preview handler.
- §4.4 Not changing: the balance requirement, cooldowns, the reservation
  arithmetic, the spec 152 re-check schedule, and indexes (no DDL).
