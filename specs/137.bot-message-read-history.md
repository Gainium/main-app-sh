# 137 — Read bot messages stay in a searchable history

Feature spec (new behaviour on top of the existing notifications feed).

## §1 Behaviour today

- §1.1 "Mark as read" on a bot message (single or all) soft-deletes it
  (`isDeleted: true`, `$unset bucket`). The row leaves the feed and the
  partial TTL `botMessageTombstoneTtl` reaps it 30 days after `created`.
- §1.2 There is therefore no way for a user to look back at an error they
  acknowledged. Read and deleted are the same state.

## §2 Behaviour wanted

- §2.1 **Read is not delete.** Acknowledging a message marks it read
  (`isRead: true`, `readAt: <now>`). It is not soft-deleted and is not
  covered by the tombstone TTL.
- §2.2 **Views.** The feed answers three views over the user's visible,
  non-deleted messages in the current paper/live context:
  - `unread` — not yet read (rows written before this feature count as
    unread: an absent `isRead` is unread).
  - `read` — read only.
  - `all` — both.
  Search and pagination apply to every view; `total` is the count of the
  view requested.
- §2.3 **Unread count.** The unread badge counts exactly the `unread` view.
  Clients that send no view keep their behaviour: `unreadOnly: true` (and no
  input at all) is the `unread` view; `unreadOnly: false` keeps its existing
  meaning (every visible row, deleted ones included) for older dashboards.
- §2.4 **Mark read.** One message by id, or — with no id — every unread
  message of the user. Marking an already-read message is a no-op and does
  not move its `readAt`. A deleted message cannot be marked read.
- §2.5 **Recurrence re-alerts.** Marking read takes the row out of the
  coalescing key (`$unset bucket`), exactly like the dismiss did, so the next
  occurrence of the same condition creates a new unread message instead of
  incrementing the read one.
- §2.6 **Retention.** A read message is kept for 90 days after it was read,
  then removed by a TTL on `readAt`. Unread messages have no age limit
  (unchanged). Deleted messages keep the 30-day tombstone TTL (unchanged).
- §2.7 **Explicit delete stays.** `deleteBotMessage` keeps its current
  semantics (soft-delete). Existing soft-deleted rows are not converted into
  read history — they may have been hidden for other reasons.

## §3 Contract

- §3.1 `getMessageBotInput.view: String` — `unread | read | all`. When
  present it wins over `unreadOnly`. Unknown values are rejected with
  `status: NOTOK`.
- §3.2 `messageData.isRead: Boolean`, `messageData.readAt: Float` (epoch ms).
- §3.3 `markBotMessageRead(input: markBotMessageReadInput!)` with
  `markBotMessageReadInput { id: String }`; response `{ status reason }`.

## §4 Open questions (decided in the plan)

- §4.1 Whether "mark all" is scoped to the current paper/live context.
  Today's dismiss-all is not; keep parity.
- §4.2 Index shape that keeps the `unread` feed index-bounded now that read
  rows remain `isDeleted: false`.
