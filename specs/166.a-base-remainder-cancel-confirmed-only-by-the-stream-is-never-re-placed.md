# 166 — A base remainder whose cancel only the stream confirms is never re-placed

Bug spec (Definition / Evidence / Assumption). Extends spec `111` §4.3.

## §1 Definition

- **§1.1 Expected.** When the reposition tick of a resting base-order
  remainder (spec `111` §4.3) moves it to a new price, the old order ends and
  the unfilled rest is placed again, so the deal still reaches the base size
  the user configured. This holds however the venue reports the end of the
  old order: in the cancel answer, or only on the user stream.
- **§1.2 Actual.** If the cancel answer does not say the order ended, the tick
  logs "could not be cancelled. Leaving it" and re-arms (§4.3.4). The user
  stream then (or already) reports the order `CANCELED`, which no one acts
  on: a cancelled add-funds order books nothing and drops nothing. Every later
  tick finds no `NEW`/`PARTIALLY_FILLED` order for the entry and re-arms
  without doing anything (§4.3.5), on every restore too. The deal keeps
  running on the part of the base order that filled first, with a pending
  entry and no order on the venue.

## §2 Evidence

- Coinbase LIMIT entry, "Enter Market Timeout" off: the base order filled
  about a quarter, the deal opened on that, and the rest rested as a `D-ROA-…`
  LIMIT (spec `111` §4.1). 50 s later the price moved, the tick logged
  "…rests at P1, price is now P2. Re-placing it". 321 ms later the user stream
  reported the order `CANCELED` with nothing filled. 121 ms after that the tick
  warned "…could not be cancelled. Leaving it". Nothing else was logged for
  the order or the deal; the deal kept its pending entry with no order on the
  venue.
- The Coinbase connector's cancel answers with a `getOrder` read made right
  after the cancel request succeeds. That read can still show the order
  `OPEN`, which maps to `NEW`, so `cancelOrderOnExchange` returns a `NEW` row.
  `settleBaseEntryRemainderOrder` returns `null` for any non-terminal answer.
- `cancelOrderOnExchange` then removes the unfilled row from the order map
  (`removeFromLocal`, nothing executed). `updateOrderOnDb` refuses to rewrite a
  `CANCELED` row, so the stored row keeps the stream's `CANCELED`.

## §3 Assumption (root cause)

- **§3.1** The tick only ever learns that its remainder order ended from the
  cancel answer. An order that ended any other way (the stream, a reload, the
  venue) is invisible to it: §4.3.4 and §4.3.5 both re-arm, and neither looks
  at the order's recorded end.

## §4 Required behaviour

- **§4.1** When the cancel gets no terminal answer, the tick reads the
  remainder order's recorded state (the order map, then the stored row, keyed
  by the entry's `addFundsId`). If it is `CANCELED` or `EXPIRED`, the cancel is
  treated as settled: any fill it states is booked through the add-funds fill
  path (as in §4.3.3), the entry is removed, and the unfilled rest is placed
  again at the new price. Otherwise §4.3.4 is unchanged.
- **§4.2** When the tick finds no resting order for the entry but a recorded
  `CANCELED`/`EXPIRED` order carries the entry's id, it does the same: book
  what it filled, remove the entry, place the rest at the current price.
  When there is no such order (not on the book yet), §4.3.5 is unchanged.
  - **§4.2.1** Only an end at least `max(60 s, reposition timeout)` old, and
    dated (`updateTime > 0`), counts here. A deal close and a settings rebuild
    cancel the remainder while the deal is still `open`, and they own what
    follows (the close, or the spec `110` re-send); the tick must not place a
    remainder in that window. §4.1 needs no such wait: there the tick cancelled
    the order itself, as in §4.3.3.
- **§4.3** Restore needs nothing new: spec `111` §4.4 already arms the tick on
  every restore, so a deal left with such an entry is completed by §4.2 on the
  first tick after the fix is running.
- **§4.4 Unchanged.** A `FILLED` order is the fill path's (it removes the
  entry). A `NEW`/`PARTIALLY_FILLED` order is §4.3.2/§4.3.3's. No MARKET order
  is sent (§4.2 of spec `111`).

## §5 Open questions

- A fill stated on a stream-only `CANCELED` remainder is trusted only when it
  can be dated (`settledBaseEntryFill`), the same rule as §4.3.3.
