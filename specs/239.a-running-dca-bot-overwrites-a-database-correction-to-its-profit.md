# 239 — A running DCA bot overwrites a database correction to its profit (bug spec)

Code: `src/bot/profitCorrection.ts` (pure), `DCABotHelper.applyProfitCorrection`
in `src/bot/dcaHelper.ts`, field `profitCorrections` on the DCA bot schema.
Tests: `src/bot/profitCorrection.spec.ts`.

## §1 Definition

- §1.1 Expected: when a closed deal's profit is corrected after the fact, the
  bot's realized-profit total (`profit.total`, `totalUsd`, `pureBase`,
  `pureQuote`) can be corrected by the same amount and keeps it.
- §1.2 Actual: there is no way to do that for a running bot. The DCA worker
  holds `data.profit` in memory, adds each booking to it and `$set`s the whole
  object (`updateData({ profit })` in closeDeal and the late-fill paths). On a
  service restart `loadData()` restores `data` from the bot's Redis `botData`
  snapshot, not from the database. A database write to a running bot's profit
  is therefore overwritten at its next booking, including after a restart.

## §2 Change

- §2.1 `applyProfitCorrection(delta, reason, correctionId)` on the DCA helper
  adds `delta` (`total, totalUsd, pureBase, pureQuote`) to the worker's own
  `data.profit`, then persists it the way a booking does (`updateData`), emits
  `bot settings update`, and logs before → after.
- §2.2 It writes the Redis `botData` snapshot immediately (awaited), not only
  through the delayed `saveBotDataToRedis`, so a restart right after the call
  restores the corrected profit. The snapshot passes the restore path
  (`poisonedSnapshotProfitField`, `convertDCABot`).
- §2.3 The id is appended to `profitCorrections` (persisted with the profit
  and in the snapshot). A call with an id already there returns `duplicate`
  and changes nothing.
- §2.4 Refused, with nothing changed: a non-finite delta field, an empty or
  over-long id, a non-DCA (combo/hedge) bot, a bot whose data is not loaded
  yet (`loadData()` would replace it afterwards). It never throws, because a
  throw inside a worker method leaves the caller's RPC without a reply. A
  failed persist after the in-memory add is reported as
  `applied, persist failed: …`; the next booking persists it.
- §2.5 Reached by bot id through the existing `callBotFunctionFromMeta`
  internal-API method of the DCA bot host, which posts to the worker that
  holds the bot and returns its answer (or null when no worker holds it).

## §3 Assumption

- §3.1 Adding the delta and `$set`ting in the same tick as the bookings keeps
  it consistent with them: both mutate the one in-memory object, and the next
  `$set` carries every change.

## Invariants

None: this is a capability, not a detector. The state it corrects has its own
detector in the deal pack.
