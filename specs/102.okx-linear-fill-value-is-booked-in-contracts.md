# 102 — An OKX USDT-margined fill's value is booked in contracts

Bug spec. The behaviour already exists and is wrong.

## §1 Definition

### §1.1 Expected

An `okxLinear` order row carries `cummulativeQuoteQty` in the same unit as
every other venue's: the quote value of the base quantity that executed, so
`cummulativeQuoteQty ≈ executedQty × price`.

### §1.2 Actual

OKX sizes swap orders in contracts, each worth `ctVal` base units. Both the
connector's `getOrder` answer and the user stream's execution report state the
filled value as `avgPx × accFillSz`, where `accFillSz` is a count of
**contracts**. The engine converts `executedQty` from contracts to base
(`convertOrderExecutedQty` / the stream's inline equivalent) but stores the
quote untouched. The stored value is therefore off by `1 / ctVal`: 1000× on a
`ctVal = 0.001` symbol (gold), 10× at `0.1`, and 100× **too small** at
`ctVal = 100`. Symbols with `ctVal = 1` happen to be right.

Three writers, one defect:

1. `getOrder` — the venue answer (and the reconcile prefetch).
2. `convertExecutionReportToOrder` — the user-stream report (and the Redis
   order cache, which is parsed through the same method).
3. `sendOrderToExchange` — the placement response saved as the order row.

### §1.3 Unchanged

- `executedQty`, `price` and `status` on every path.
- KuCoin futures (also sized in contracts) keeps its own branches.
- OKX spot, OKX inverse (COIN-M) and paper venues are not sized through this
  path and are untouched.
- The placement path's price derivation (`cummulativeQuoteQty / executedQty`),
  which runs on the raw payload while both quantities are still in contracts.
- Existing rows are not rewritten.

## §2 Evidence

- Prod row, XAU-USDT `okxLinear` MARKET `dealStart`: `executedQty 0.508`,
  `price 4837.9`, `cummulativeQuoteQty 2457653.2` = 508 contracts × 4837.9.
- The latest 3,000 filled `okxLinear` rows, grouped by symbol: the ratio
  `cummulativeQuoteQty / (executedQty × price)` is constant per symbol and
  equals `1 / ctVal` (1000, 100, 10, 1, 0.01, 0.001 …).
- Prod logs, one row per writer, each at the same millisecond as the DB write:
  - stream — `Processing msg HYPE-USDT …, FILLED, 95.255, base: 0.2, quote: 190.51`
    (0.2 × 95.255 = 19.05; HYPE `ctVal = 0.1`);
  - placement — a MARKET `dealStart` whose only log line is `Save order …`,
    stored at 10×.

## §3 Assumption

The quote is never rescaled where the base is. Dividing the stated quote by the
same `getOKXDenominator(symbol)` that `executedQty` is divided by makes the two
agree, on every `ctVal` (above and below 1), at each of the three writers.

## §4 Change

§4.1 `convertOrderQuoteQty(symbol, quote)` divides a stated quote by
`getOKXDenominator(symbol)` for an `okxLinear` bot sized in contracts, and
returns it unchanged otherwise (another venue, an absent or non-numeric value).

§4.2 `getOrder` applies it beside `convertOrderExecutedQty`.

§4.3 `convertExecutionReportToOrder` applies it to the execution report's
`totalQuoteTradeQuantity`.

§4.4 `sendOrderToExchange` applies it to the placement payload's own quote
when converting the saved row's `executedQty`. A quote the payload did not
state (the row's own held value, already in base) is not rescaled.

## §5 Out of scope

Backfilling existing rows (an irreversible data transform; separate operator
ask). The connector and stream producers keep emitting contract values:
changing them would change the `BaseReturn` / stream payload for every
consumer.
