# 207 — an order lookup that answers FILLED keeps the stale fill size

Bug spec. Touches the unknown-order ladder (`MainBot._runUnknownOrderLadder`)
and, through it, the take-profit close (`dcaHelper.closeDeal`, spec `157`'s
remainder sweep).

## 1. Definition

### 1.1 Expected

When the bot asks the venue what happened to an order (a cancel answered
"unknown order") and the venue says the order is in a different status, the
order the bot records and acts on carries the venue's filled quantity and
filled value. A take-profit the venue reports fully FILLED closes its deal with
the whole position sold, so `closeDeal` sends no remainder sweep.

### 1.2 Actual

The ladder copied the venue's `status` and `updateTime` onto the local row but
re-derived `executedQty` from the local row itself. A row whose last user
stream event was a partial fill kept that partial size under the new status
`FILLED`. `closeDeal` then measured the remainder from that size and swept the
"unsold" coins at market — coins the take-profit had already sold, so the
sweep sells whatever else the account holds of that asset, or is refused for
balance and the deal is booked closed still counting them.

### 1.3 Not changing

A take-profit that genuinely filled only part of the position (the venue's own
`executedQty` is partial) still has its remainder swept at market.

## 2. Evidence

Production, a Binance spot LONG DCA deal (EUL/USDT):

- A MARKET take-profit for 17.86 was placed. Its `orders` row ends as
  `status: FILLED`, `executedQty: 0.10000000`, `cummulativeQuoteQty: 0.1263`.
- Five minutes later a close cancelled it: `Send cancel request … Order not
  found` → `Real order … status: FILLED` → `Save order … with status FILLED`
  → `TP order FILLED`. The status changed in that write, so the row was not
  FILLED before it — the ladder's status-change branch wrote the stale 0.1.
- 0.7 s later the remainder sweep `…-SR-…` was refused: `required - 17.75 EUL`
  (17.86 − 0.1, rounded to step) while the account held 16.84 EUL. A FILLED
  Binance order has `executedQty == origQty`, so the take-profit had sold all
  17.86 and the 16.84 belonged to something else.
- The deal was booked closed with `currentBalances.base` 17.76; the sentinel
  invariant `forum.closed-spot-long-deal-holds-base` raised it.

## 3. Assumption (hypothesis)

`_runUnknownOrderLadder` sets `find.executedQty =
convertOrderExecutedQty(find)` — the local row — instead of converting the
venue's `request.data`. Converting the venue's answer (and taking its
`cummulativeQuoteQty`) makes the returned order report the full fill, and
`closeDeal`'s `preRemainder` becomes ≈0, so no sweep is sent.

## 4. Requirements

- §4.1 Status-change branch: when the venue states a positive `executedQty`,
  the recorded `executedQty` is the venue's (through
  `convertOrderExecutedQty`) and `cummulativeQuoteQty` is the venue's (through
  `convertOrderQuoteQty`) when positive. The local `price` is kept (Binance
  answers `0` for a market order's price).
- §4.2 A venue answer with no usable fill size (0 / missing) keeps the old
  reading of the local row, including its FILLED → `origQty` fallback.
- §4.3 Fed the order §4.1 returns, `closeDeal` sends no remainder sweep and
  the deal's base ledger ends ≈0.
- §4.4 (§1.3) A venue answer with a genuinely partial `executedQty` is
  recorded as that partial size, and `closeDeal` still sweeps the rest.

## Invariants

Covered by the existing `forum.closed-spot-long-deal-holds-base` invariant
(main-app `specs/invariants/forum.invariants.json`), which raised this defect.
No new invariant.
