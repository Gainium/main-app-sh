# 215 — A grid that closes while placing its ladder leaves orders behind

Bug spec (Definition / Evidence / Assumption).

## §1 Definition

§1.1 Expected: once a grid bot starts closing (a stop or a take-profit closes
it, or the user stops it), the ladder placement still running places no
further level. Nothing the bot placed is left resting on the exchange after
the bot is closed.

§1.2 Actual: the placement loop in `limitOrders` keeps going after the close
starts. Every level it places after the close took its cancel snapshot stays
resting on the exchange, and stays `NEW` in `orders`, on a bot whose status is
`closed`. Nothing tracks those orders. A fill opens a position no bot manages.

## §2 Evidence

A Hyperliquid perp grid (long, 2x) started and swapped into its base at
15:24:36. Its first ladder sell was still being placed when the stop-loss
triggered at 15:24:37 (`slAction: stopAndSell`). The trace in prod's grid-bot
log:

- 15:24:37.318 `SL trigger`. `closeBotByTp` sets `blockLimit` and runs
  `cancelAllOrder(true)`. The cancel waits on the in-flight first sell, which
  is then cancelled (spec 155 works here).
- 15:24:39–15:24:40 the loop places the second and third sells anyway.
- 15:24:41.180 `Stop order filled. Processing stop...` (`stopFilled = true`).
  `stop()` takes its snapshot and cancels the sells that exist at that moment
  (CANCELED 15:24:42, :43, :44).
- 15:24:43–15:24:45 the loop places two more sells. They come after the
  snapshot, so nothing cancels them.
- 15:24:45.840 `stop()` finishes: status `closed`, user stream closed.
- 15:24:47–15:24:59 the loop places 9 more sells on the closed bot.

In total 11 sells (736.69…802.8) are left `NEW` on a `closed` bot.

Code path: `limitOrders` → `placeOne` (core `src/bot/helper.ts`). Nothing in
`placeOne`, the batched block or the sequential loop reads `blockLimit`,
`stopFilled` or `data.status`. `limitOrders` reads `blockLimit` only once,
before the diff is computed.

## §3 Assumption (hypothesis)

The startup placement loop does not check the close latch before each
placement. `stopFilled` (spec 189) and `blockLimit` (the close in progress,
which `placeCanceledLevels` already honours, spec 201 §4.2) are both set
before the stop path takes its cancel snapshot. Checking them before each
placement therefore closes the window for every placement that has not yet
started.

A placement that is already in flight when the close starts is covered only
if the snapshot finds its write-ahead row (spec 155/192). If the placement
resolves after the snapshot was taken, the snapshot does not hold it and
nothing cancels it.

## §4 Required behaviour

§4.1 `placeOne` sends nothing when the bot is closing: `stopFilled`, or
`blockLimit`, or `data.status === closed`. This applies to the sequential path
and to the batched path, which share `placeOne`.

§4.2 Suppose a placement resolves `NEW`/`PARTIALLY_FILLED` while the bot is
closing, and no cancel of the bot's own has claimed that order
(`isOwnCancel`). Then the order is cancelled on the exchange right there. When
a cancel has already claimed it (the stop's snapshot holds the order), it is
left to that cancel, so the order is not cancelled twice.

§4.3 Unchanged: an open grid with no close in progress places and replaces
orders exactly as before.

## Invariants

- `grid.closed-bot-order-resting` (main-app `specs/invariants/deals.invariants.json`,
  observe): a closed live grid bot has a LIMIT order resting (`NEW` /
  `PARTIALLY_FILLED`) that is older than 30 minutes.
