# 017 — A take-profit sized from the base order when the entry fills are absent

Issue #702. Follow-up to #694 (`007`), #696 (`013`) and #700 (`014`), which
between them stopped the drift being *created* by a partially-filled take-profit
and made the detector accurate. This spec is the other producer of the same
exposure: a re-armed take-profit that covers only the base order.

## 1. Definition

### 1.1 Expected

A DCA deal that closes on a single take-profit rests one order that can sell the
whole position the deal holds. The position a deal holds is what the deal itself
records — `deal.size`, less what `tpHistory` and the filled close orders say has
already been sold, less base withdrawn by reduce funds. That is the measure
`trackedPosition` (`src/bot/dca/tpCoverageReconcile.ts`) already uses to judge
coverage, and `getTPOrder` must size the close in the same terms, so a deal
cannot be judged uncovered by the very number the engine was supposed to arm.

### 1.2 Actual

`getTPOrder` sizes the close as `_qty = filledQty + boQty`
(`src/bot/dcaHelper.ts:13577`) — a sum over rows found in the bot's **in-memory
order map**:

- `filledQty` — the `FILLED` (and partially-executed `CANCELED`) `dealRegular`
  rows for the deal;
- `boQty` — the `dealStart` row, via `findBaseOrderByDeal` →
  `resolveBaseOrderQty`.

The order map is a cache. It is rebuilt on every worker restart, from a Redis
snapshot whose staleness is documented at `main.ts:4017-4042`, or from a DB query
that has repeatedly been found to exclude rows it needed
(`main.ts:4055`, `dcaHelper.ts:1391-1429`). When an entry row is missing from it,
the sum silently under-states the position and **nothing compares the result
against the deal's own books**.

`resolveBaseOrderQty` (`src/bot/dca/baseOrderQty.ts`, shipped 2026-08-26 for
#423/AIOZ) does make that comparison — but only on the branch where the
`dealStart` row itself is missing. When the base-order row is present it
short-circuits on `boFromOrder > 0` and returns it unchecked, so a deal whose
**safety-order** rows are the ones missing gets a take-profit sized at exactly
the base order.

### 1.3 Blast

`origQty` of the re-armed order equals the base order, so the shortfall equals
the whole of the safety-order volume — on a deal that has filled its ladder that
is most of the position. The order rests at `NEW` and never resizes: coverage is
only ever re-established as a side effect of `placeOrders`, which runs on a fill.

## 2. Evidence

### 2.1 The named deal, read from prod Mongo 2026-09-08

`6a301c7ca999bdafb2ad8055` — AIXBTUSDT, bot `69a7887e6f6867bb88bd08c9`,
`status: open`, `size: 510`, `tpHistory: []`, `reduceFunds: []`.

| clientOrderId | typeOrder | status | origQty | executedQty |
|---|---|---|---|---|
| `D-BO-WjgCbz9iZqRPjWN3oNH5oIz7SzQxro` | dealStart | FILLED | 250 | 250 |
| `D-RO-Y36FpoOukhMuum4yLnE3aJIjnM7xuM` | dealRegular | FILLED | 260 | 260 |
| `D-TP-P9XE23yyimUSdnIbs4uWpiYqmR8fZx` | dealTP | **EXPIRED** | **510** | 0 |
| `D-TP-3w5x48B7xtLpQUQMNepJpT1GKajf7j` | dealTP | **NEW** | **250** | 0 |

The first take-profit is the whole position. The replacement is the base order,
to the unit. The detector has reported it on every pass since:

```
2026-09-07T00:30:08Z | Bot (dca) 69a7887e6f6867bb88bd08c9 | tp-coverage drift |
  deal 6a301c7ca999bdafb2ad8055 (AIXBTUSDT) under: 260 of 510 has no
  take-profit covering it (1 live take-profit(s) resting 250)
2026-09-08T00:30:06Z | …identical…
```

`693b8695e6e7cc790c7388ef` (AAVEUSDT) is the same shape at ladder depth: base
order `0.027`, ten safety fills, `size: 0.728`, one `NEW` take-profit at
`origQty 0.027` — 96% of the position with nothing covering it.

### 2.2 The population, measured on prod 2026-09-08

Open DCA deals with no partial take profit and no add/reduce funds, holding at
least one resting `dealTP`, where the resting quantity is short by more than 2%
of the position **and the shortfall equals the filled safety orders to within
2%** — i.e. the take-profit is the base order and nothing else:

**61 deals across 8 users**, average 92% of the position uncovered.
(80 further deals are short for other reasons and are out of scope here.)

### 2.3 `deal.size` is the authority, fleet-wide

Same query without the drift filter — 8,740 open DCA deals holding a resting
take-profit:

| `deal.size` vs `sum(dealStart+dealRegular executedQty)` | deals |
|---|---|
| agrees within 0.5% | **8,704** (99.6%) |
| size > order rows | 9 |
| size < order rows | 27 |

So on a bot whose order map is complete the two measures are the same number,
and sizing from the position changes nothing. It only ever fires where the map
is short — which is the defect.

### 2.4 Executable

`src/bot/dca/tpSizingFromPosition.harness.spec.ts` drives the real
`getTPOrder` over the rows in §2.1. With both rows in the map it returns **510**
(= `D-TP-P9XE23…`); with the safety-order row absent it returns **250**
(= `D-TP-3w5x48…`). Production reproduced to the unit, with no stack.

## 3. Assumption

The root cause is that `getTPOrder` derives the position from order rows only,
and `resolveBaseOrderQty` applies its cross-check against the deal's own books
on one branch (`boFromOrder === 0`) and not the other. If the base order's row
is present but the deal holds more base than the counted rows explain, the
unexplained remainder belongs to entry fills the map has lost, and the deal's
own position is the correct size for the close — exactly as it already is when
the base-order row is the missing one.

## 4. Related, and deliberately not in scope

### 4.1 The repair pass cannot act on this population

`reconcileTpCoverage`'s `rearm` is `staleTps.length > 0 || live.length === 0`.
Every deal in §2.2 rests exactly one `NEW` take-profit, so `staleTps` is empty
and `live.length` is 1: `rearm` is `false` and an armed `BOT_TP_COVERAGE_REPAIR`
would log the drift and do nothing. A deal reported `under` needs a *bigger*
take-profit, and `placeOrders` already cancels an undersized resting order and
sends the replacement in the same pass (`dcaHelper.ts:13248-13308`), so
re-arming an `under` deal lands in the path built for it. `over` keeps the
conservative rule — placing on top of over-coverage is how the duplicate
take-profit was made.

### 4.2 COIN-M inverse futures are measured in the wrong units (F193)

Not fixed here. `6a8e19f4ec3af3dac20bc06b` (BTCUSD_260925) has `size 1.00088`
BTC and a resting take-profit the DB records as `origQty 0.9392`, but the
detector reads the **venue-confirmed** order and reports
`take-profits offer 780` — the venue quotes COIN-M in $100 contracts. The
verdict is a false `over`, and by the same mismatch a genuinely uncovered COIN-M
position could read `covered`. It is a defect in the detector's unit handling,
not in sizing, and §4.1's change does not touch it: a false `over` yields
`staleTps: []` and therefore `rearm: false` before and after. Left open.
