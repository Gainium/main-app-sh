# 018 — A venue that refuses our quantity precision is never learned from

Bug #664. Companion to `007.tp-resize-cancel-must-never-promote` only in shape:
this is the QUANTITY twin of the tickSize/PRICE_FILTER re-quantize branch that
already lives in `sendOrderToExchange` (`core/src/bot/main.ts`).

## 1. Definition

### 1.1 Expected

When a venue refuses an order because the **quantity** carries more decimals
than that account's venue accepts, the bot must (a) resubmit the order once at a
precision the venue can accept, and (b) remember the accepted precision for that
**connection + symbol**, so the next order on the same bot is sized correctly
without a refusal.

### 1.2 Actual

The refusal is terminal. `sendOrderToExchange` has a re-quantize-and-retry branch
for the **price** side of exactly this problem (`tick size` / `price_filter`,
`main.ts` ~:7517) but none for the quantity side, so
`Order quantity has too many decimals.` falls through to generic error handling:
the local order row is written off `CANCELED`, the deal makes no progress, and
the next order is computed from the *same* stale precision and refused again.

The bot re-attempts on its own cadence forever. Measured in prod (read-only,
`~/.pm2/logs` archives): one bot logged the refusal on 2026-08-28, 08-30, 09-01,
09-04 — a 7.1-day standing condition — and one admin bot-error row carries
`count: 32` over 616,765,177 ms.

### 1.3 Scope of "correct precision"

`baseAsset.step` for a pair is loaded from the venue's **public instrument
list** and stored once per `exchange@pair` in the `pairs` collection
(`getAllExchangeInfo`, `exchange-connector` `core/src/exchange/exchanges/*`).
It is deliberately **not** per-account, and §5.2 says it must stay that way.
The learned value in §4 is an *account-scoped override that only ever coarsens*
the shared value; it never edits the shared record.

## 2. Evidence

### 2.1 The refusals (prod logs, read-only)

`logs -n 40 Gainium-DCA-bot decimals`, 40 matching lines, e.g.

```
2026-09-01T19:00:02.696Z | Worker 11 | Bot (dca) 6a91bbd64889ca2352428bad | Error |
  Reason Order quantity has too many decimals. Method limitOrders()
  Step Send new order request D-TP-BwH7v8mBxFYCby1UveLSm0MgEMxQFX, qty 0.2473, price 104.52, side SELL
```

Every rejected quantity in the sample carries exactly **4 decimals**:
`0.0118 0.2004 0.2473 0.2483 0.1985 0.0089 0.1941 0.0668 0.0487 0.0289`.

### 2.2 Whose orders they are

`getUserByBotId` on every bot id in the sample returns the same user,
`6a58ffba11e25b72ba1d3993`. Prod `dcabots` (read-only) shows **six** bots, all
`exchange: 'bybit'`, all `settings.pair: ['SOLUSDT']`, across **four different
`exchangeUUID`s** — the user re-created the API connection repeatedly. All six
are now `closed`.

Of those four connections only one survives on the user doc; it is
`provider: 'bybit'`, **`bybitHost: 'eu'`**.

### 2.3 Why 4 decimals is refused (the venue, queried live)

`GET /v5/market/instruments-info?category=spot`, paginated, both hosts:

| | `api.bybit.com` | `api.bybit.eu` |
|---|---|---|
| spot symbols | 538 | 133 |
| `SOLUSDT` `basePrecision` | `0.0001` | **not listed at all** |
| `SOLUSDC` `basePrecision` | `0.0001` | `0.001` |

34 symbols present on both hosts publish a **different** `basePrecision`, EU
always the coarser one (`LTCUSDC` `0.00001` → `0.001`, `XRPUSDC` `0.01` → `0.1`,
…). 58 symbols exist on EU and not on `.com`.

So the `pairs` row for `bybit@SOLUSDT` says step `0.0001`, every quantity we
compute is a legal 4dp multiple of it, and the EU host this account's orders are
actually signed against (`bybitHostMap[eu] = https://api.bybit.eu`,
`exchange-connector` `core/src/exchange/types.ts:555`) refuses all of them.

### 2.4 What the existing EU merge does and does not do

`getAllExchangeInfo` (connector, `bybit/index.ts:1115`) **already** re-reads the
EU list and merges the stricter of the two into the shared row — but only
`if (get)`, i.e. only for symbols present in **both** lists. `SOLUSDT` is absent
from EU entirely, so nothing merges and the `.com` step stands. This is why the
"make the instrument-filter loader host-keyed" idea would not have fixed this
bot either: there is no EU `SOLUSDT` row to key to.

## 3. Assumption (hypothesis)

The root cause is that **the venue's own refusal is the only source of truth we
have for this account's quantity precision, and we throw it away.** The refusal
message names the failing quantity; a quantity with `d` decimals that the venue
refuses proves the venue accepts at most `d-1`. Nothing in `sendOrderToExchange`
reads that, so no order is ever resubmitted and no future order is sized
differently.

Gate-2 test must fail *because* the refusal produces exactly one venue call and
leaves the order written off — not because of a missing stub or a thrown error.

## 4. Required behaviour

### 4.1 Recognising the refusal

A refusal whose reason contains `quantity has too many decimals`
(case-insensitive) — and only the **quantity** variant; the platform already has
a separate `Order price has too many decimals.` classification in
`core/src/bot/utils.ts` — is a quantity-precision refusal.

### 4.2 Deriving the accepted precision

From the quantity we actually sent: `accepted = countDecimals(qty) - 1`, floored
at 0. A quantity with no decimals yields `-1` ⇒ nothing can be learned and the
refusal falls through unchanged.

### 4.3 Learning is monotone and account-scoped

The learned precision is stored per `(exchangeUUID, symbol)` and may only ever
**decrease**. A later refusal at a coarser precision lowers it again; a value can
never be raised by this path.

### 4.4 Retry exactly as far as the arithmetic allows

The order is re-quantized DOWN to the learned precision and resubmitted. Rounding
down, never up: a SELL must not exceed the position and a BUY must not exceed the
budget. The resubmission happens only when the re-quantized quantity differs from
what was sent and is still `> 0`. Because §4.2 strictly decreases the decimal
count on every refusal and stops at 0, the retry chain is finite without a
counter — the same self-limiting argument the tick-size branch already relies on.

### 4.5 Future orders size correctly from the start

Once learned, every subsequent sizing decision for that connection + symbol uses
the coarser step. It is applied where the bot reads the pair's filters, so all of
`baseAssetPrecision()` and the `baseAsset.step` remainder arithmetic in
`dcaHelper` / `gridMonitor` / `comboHelper` pick it up from one place.

### 4.6 Inert by default

An account that has never been refused has no learned entry, and every read path
must behave byte-for-byte as it does today: the shared `pairs` row is returned
unchanged and no extra I/O is on the hot path.

### 4.7 Fail-open

Any error reaching the learned-step store is logged and treated as "nothing
learned". A Redis blip must never wedge order placement or change sizing.

### 4.8 Never mutate the shared pair record

The object returned by the shared exchange-info store is handed to every bot in
the worker. Applying a learned step must produce a copy; mutating in place would
coarsen the step for every other user on that pair.

## 5. Open questions / deliberate non-goals

- **5.1** Cross-worker propagation is not instant. A step learned in worker A
  reaches worker B when B restarts or when B is itself refused once. Accepted:
  §4.4 makes that a single refusal, which is the same self-heal the brief asks
  for.
- **5.2** Making the instrument-filter loader host-keyed is explicitly **out of
  scope** (operator instruction): it would change sizing for every `.com` bot,
  and §2.4 shows it would not have fixed this account anyway.
- **5.3** `quoteAsset.minAmount` being defaulted to `1` for USDT/USDC quotes
  (finding F189) is a *different* defect on the same bot and is not touched here.
- **5.4** The EU host not listing `SOLUSDT` at all — i.e. the user trading a pair
  their region's venue does not publish — is a product question (should we refuse
  to create the bot?), not this fix.
