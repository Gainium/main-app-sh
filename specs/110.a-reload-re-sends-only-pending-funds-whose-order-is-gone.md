# 110 — A reload re-sends only the pending add/reduce funds whose order is gone

## §1 Definition

### §1.1 Expected

- **§1.1.1** After a keep-orders reload (settings save, deal restore) a
  `pendingAddFunds` entry whose order (matched on `addFundsId`) is still
  resting is not sent again, and stays in the pending list.
- **§1.1.2** An entry whose order was cancelled, or that has no order, is sent
  again, as before. That covers the user-start reload and a deal settings
  update, which both cancel the deal's orders first.
- **§1.1.3** The same holds for `pendingReduceFunds` (matched on
  `reduceFundsId`).
- **§1.1.4** An entry whose order has already FILLED is not sent again either.
  The fill path removes the entry, and sending it again would add the same
  amount twice.
- **§1.1.5** Unchanged: a settings save leaves every resting order in place
  (`tests/botSettingsKeepOrders.ts` in the app).

### §1.2 Actual (before)

- Every pending entry was re-sent on every non-cold reload. Since a settings
  save stopped cancelling the deal's orders, each re-send placed a twin next to
  an order still resting, and both could fill.

## §2 Evidence

- On a live deal, one keep-orders reload at 07:51Z re-placed five limit
  additions (0.1274, 0.1249, 0.1308, 0.1323, 0.1192) whose orders were all still
  resting. The deal's `funds` now hold each of the first four twice, and two NEW
  0.1192 orders rest against one pending entry.
- `restoreWork` (keep-orders branch) and `updateDealSettings` cleared the pending
  lists and re-sent every entry with no look at the order map.

## §3 Assumption

The re-send was written when every such reload cancelled the book first. The
keep-orders reload removed that cancel but not the re-send. Keying the re-send
on whether an order with the entry's id still stands fixes both callers: the
cancelling ones find the order CANCELED and re-send it, and the keep-orders one
finds it NEW and leaves it alone.
