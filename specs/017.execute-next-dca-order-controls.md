# 017 — Execute next DCA: order type, size, and what happens to the levels below

Follow-up to the feature shipped in 1.58.0 (community request
`/t/execute-next-dca-manually/5072`). Feedback on the shipped version asked for
three things, and answering them changes behaviour rather than only display.

Feature spec: §2–§4 define behaviour that does not exist yet. §5 is a gap in
behaviour that does exist and reads closer to a bug — its Evidence is given.

## §1 What exists today (1.58.0)

`executeNextDcaLevel` fills the deal's next safety order **at market**, sized
**exactly as the ladder sized it**, and consumes that ladder slot. Two
properties follow from that, and both are load-bearing:

- **§1.1** The order is the ladder's own grid entry, so the deal's books stay
  consistent with the ladder by construction.
- **§1.2** `expectedLevel` pins the level the dialog quoted, so a confirmation
  can never execute a different level than the one it priced.

Neither property survives §3 and §4 unchanged. Preserving what they were
protecting is the hard part of this spec, not the features themselves.

## §2 Order type — market, or a limit that chases

### §2.1 Expected

The user chooses **market** (today's behaviour, the default) or **limit**.

A limit order is placed at the current price and, if it does not fill, is
cancelled and re-placed at the new current price on a fixed interval until it
fills — the same "chase" the limit **base order** already performs. The bot's
existing settings govern it, and are not re-invented here:

| existing setting | role |
|---|---|
| `orderLimitRepositionTimeout` (10 s) | interval between re-placements |
| `notUseLimitReposition` | user has turned chasing off — place once, leave it |
| `enterMarketTimeout` + `useLimitTimeout` | after this long, give up and take market |
| `slippageRetry` | hard cap on re-placement attempts |

### §2.2 Why reuse rather than invent

`checkBaseOrder` (`core/src/bot/dcaHelper.ts:7373`) is the existing shape:
look the order up; if it is not `FILLED`/`PARTIALLY_FILLED`, cancel it, and if
the cancel comes back `FILLED` hand it to `handleUnknownOrder` and stop;
otherwise re-place, which re-arms the timer. A second mechanism with its own
timers, its own retry cap and its own cancel/fill race would be a second thing
to get wrong on a live venue.

### §2.3 The level is consumed on FILL, never on placement

A resting limit that never fills must leave `levels.complete` untouched. The
level is consumed by `processFilledOrder` → `updateDeal`, exactly as today.

**Consequence that must be stated in the UI, not just here:** between placing
the manual limit and it filling, the deal has **no safety order at that
level** — the ladder's own resting order was cancelled to make room. If the
user cancels the chase, or it exhausts `slippageRetry` without filling, the
ladder's order must be restored.

**It will not restore itself.** This was checked, not assumed. The ladder is
re-placed on exactly three events, none of them periodic:

| trigger | where |
|---|---|
| a fill | `updateDeal` — cancels the resting `dealRegular` set and re-places `findDiff(currentOrders, previousOrders)` |
| worker restart / partially-filled pass | `checkOrders`, but only inside its `if (this.serviceRestart \|\| partiallyFilled)` gate (lines 9715–10078) — the "order wasn't found in orders, but must be in grid" re-place at :10032 lives inside that gate |
| a settings save | the `placeOrders` at :10553, guarded against the TP burst |

So an abandoned chase leaves the deal with **no safety order at that level
until one of those happens**, which can be a long time — and the ladder being
there when price drops is the entire point of it. §2.4's cancel path and the
`slippageRetry` exhaustion path must therefore re-place the ladder order
**explicitly**. This is a requirement of this spec, not a property inherited
from the engine.

### §2.4 Cancelling a chase in flight

The user must be able to stop a chase that is running. A chase in flight is
visible as a resting `dealRegular` order; cancelling it must also clear the
repositioning timer, or the next tick re-places an order the user just killed.

## §3 Editable volume

### §3.1 Expected

The user may change the size of the level being executed, in the deal's own
size unit. The dialog shows the ladder's size as the default and recalculates
cost, projected average and slippage live from the edited value.

### §3.2 Bounds

- Not below the venue minimum (`baseAsset.minAmount`, `quoteAsset.minAmount`) —
  the engine already raises undersized manual orders and must keep doing so.
- Not above the deal's remaining available budget. A manual level that spends
  the whole remaining allocation leaves the levels below it unfundable; the
  dialog must show that, and §4 decides whether those levels then shrink.

### §3.3 Effect on §1.2

An edited size means the order is no longer the ladder's grid entry, so
`expectedLevel` alone no longer pins what will happen. The request must carry
the **size it quoted** as well, and the engine must refuse if the deal moved on.

## §4 What happens to the levels below — user's choice

### §4.1 Today's behaviour, precisely

The ladder is a pure function of `deal.initialPrice` and the bot's settings.
Level *i*'s price compounds from level *i−1*'s **ladder** price
(`orders[orders.length-1].price` in `createInitialDealOrders`), never from a
fill; its size is `orderSize × volumeScale^(i−1)`, plus `deal.sizes.dca[i−1]`
(the compounding reinvestment, unrelated to this feature). So executing a level
early — or at a different size — changes **nothing** below it today.

### §4.2 Expected

The dialog offers two modes, and states plainly which one is active:

- **`keep`** (default, today's behaviour): levels below keep their configured
  prices and sizes. The edit applies to this level only.
- **`rebase`**: the levels below are re-derived from the level just executed —
  size *i* becomes `executedSize × volumeScale^(i−N)`, and price deviation
  compounds from the executed level's **fill** price rather than its ladder
  price.

### §4.3 `rebase` needs per-deal persistence

`createInitialDealOrders` regenerates the whole ladder on every call, so a
rebase cannot be a one-off mutation of `currentOrders` — it would be recomputed
away on the next fill. It requires a value persisted on the deal that the
generator reads.

**`deal.sizes.dca[]` must not be reused for this.** It is the compounding
reinvestment split (`calculateCompoundReduce`), it is *additive*, and it is
recomputed from realised profit — overloading it would corrupt compounding for
any deal that also has it. `rebase` needs its own field.

### §4.4 A rebase is not undoable

Once the levels below are re-derived, the original ladder is not recoverable
from the deal (its inputs, `initialPrice` and settings, still exist — but the
deal has been told to ignore them). The UI must say so before confirming.

## §5 Amount, cost and projected average are missing on some deals

### §5.1 Definition

**Expected:** the confirmation always shows the size it is about to send, what
it will cost, and where the average moves to.

**Actual:** those three rows are absent on `dcaByMarket` deals and on
`dcaCondition: 'indicators'` deals.

### §5.2 Evidence

Reported from the field on the shipped version, and reproduced by reading the
path: the dialog derives size from a **resting** `dealRegular` order fetched by
`useDealOrders`. `placeOrders` never sends `dealRegular` orders to the venue
when `dcaByMarket` is set or the deal's action is `useOppositeBalance`
(`core/src/bot/dcaHelper.ts:13186`), and `createCurrentDealOrders` strips
`dealRegular` entries entirely for `indicators`. On those deals there is no
resting order, so size is `undefined` and all three rows drop out.

Verified on the live dashboard that the rows **do** render for an ordinary
percentage-ladder deal, so this is specific to those two configurations.

### §5.3 Assumption

The dialog cannot compute the size because it never has the bot's settings —
only a lossy deal shape. The fix is to give it the same ladder projection the
deal-detail view already builds (`useDealSmartOrders`), not to change the
engine.

## §6 Invariants that must not break

- **§6.1** A level is consumed exactly once. The `dealsByMarketProcessing`
  claim and the `IdMute` key still guard against the price-tick triggers.
- **§6.2** A cancel that returns `FILLED` aborts the manual execution.
- **§6.3** A cancelled-and-not-replaced ladder order is restored **by this
  feature's own code**. Established in §2.3: nothing periodic restores it, so
  every path that cancels a ladder order without filling a replacement — user
  cancels the chase, `slippageRetry` exhausted, market order rejected after the
  cancel succeeded — must re-place it. A test must cover each of those three.
- **§6.4** Combo and risk-based deals remain excluded throughout.
- **§6.5** `keep` mode must be byte-identical in behaviour to 1.58.0 — the
  default path is not allowed to change.

## §7 Out of scope

- Editing the **price** of the level (as opposed to choosing market/limit).
- Executing any level other than the next one.
- A webhook action — a webhook that re-fired would walk a deal down its whole
  ladder; unchanged from 1.58.0.

## §8 Open questions

- **§8.1** In `rebase`, does the take-profit percentage still apply to the new
  average (yes, presumably) — and does the stop loss, if it is based on the
  base order rather than the average, move too?
- **§8.2** Should `rebase` be offered when the user did **not** edit the size?
  It is meaningful (deviation compounds from the fill price, which differs from
  the ladder price), but it is a subtler thing to explain.
- **§8.3** Does the public API expose order type / size / mode, or stay
  market-and-ladder-sized? A webhook-free REST endpoint that can chase a limit
  is a long-running side effect with no caller to observe it.
