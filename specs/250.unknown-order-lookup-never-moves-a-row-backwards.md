# 250 — An unknown-order lookup never moves an order row backwards

Bug spec (Definition / Evidence / Assumption).

## 1. Definition

### §1.1 Expected

When the bot asks the venue about an order (`_runUnknownOrderLadder`, reached
from a cancel the venue answered "order not found"), the venue's answer may
only move the local row **forward**:

- A row the bot already holds as `FILLED` stays `FILLED` with its own
  `executedQty` / `cummulativeQuoteQty`, whatever non-`FILLED` status the venue
  answers (`NEW`, `PARTIALLY_FILLED`, `CANCELED`). The lookup returns the row,
  so the caller books it as a fill.
- A row holding a part fill is not reset by a non-terminal answer (`NEW`,
  `PARTIALLY_FILLED`) that reports less executed than the row already has.

### §1.2 Unchanged

- A venue answer that moves the row **up** is still applied: a row the stream
  left at `PARTIALLY_FILLED 0.1` that the venue reports `FILLED 17.86` takes the
  venue's status and fill size (spec `207`).
- A terminal `CANCELED` answer for a row that is not `FILLED` is still applied,
  and so is the venue's fill size on it (spec `235` §4.2).
- A row the bot wrote off as `CANCELED` that the venue reports as live is
  still taken from the venue.

### §1.3 Actual

On a futures venue whose REST order read lags its own user stream, a grid exit
reported `FILLED` by the stream is rewritten to `PARTIALLY_FILLED` by the
lookup. The deal's ledger (`updateDealBalances`) counts only `FILLED` /
`CANCELED` rows, so the exit drops out of it: the deal closes showing the
exit's base as still held, and its profit omits the exit. When the order is
processed again later, the deal is closed, and `sellLateGridFill` logs
"Grid exit … filled … after deal … closed" without booking it.

## 2. Evidence

Production log, combo worker, one Kraken Futures XRP combo grid exit:

```
07:09:02.106Z Processing msg XRP-USD CMB-GR-…, FILLED, 0.9896, base: 37, quote: 36.6152 SELL
07:09:02.106Z Update minigrid … CMB-GR-…
07:09:02.219Z Send cancel request CMB-GR-…. Order not found
07:09:02.219Z Send request to unknow order CMB-GR-…
07:09:02.279Z Real order CMB-GR-… status: PARTIALLY_FILLED
07:09:02.279Z Save order CMB-GR-… with status PARTIALLY_FILLED
07:09:04.559Z Order CMB-GR-… is still PARTIALLY_FILLED after its deal closed. Keep tracking it
08:42:17.013Z Grid exit CMB-GR-… filled 37 after deal … closed: it took its base out of the position, nothing more to trade
```

The deal closed with `currentBalances.base: 37`.

Code path: `core/src/bot/main.ts` `_runUnknownOrderLadder`, the
`if (find.status !== request.data.status)` branch, copies the venue status and
fill size onto the row unconditionally. Then it re-registers the row in the
map with `setOrder`, and returns `null` because the answer is not `FILLED`.

## 3. Assumption (hypothesis)

The overwrite has no ordering check. Any venue answer that differs from the row
replaces it, including one that is older than what the user stream already
delivered. Keeping a `FILLED` row (§1.1) leaves it in the deal's ledger and
returns it to `cancelAllOrder`. `processFilledOrder` dedups it there through
`processedFilled`, so the fill is booked exactly once.

## 4. Requirements

- §4.1 A `FILLED` row answered `PARTIALLY_FILLED` (with a smaller or no fill
  size) stays `FILLED` at its own size in the map and in every DB write, and
  the lookup returns it as `FILLED`.
- §4.2 The same holds for a `NEW` answer and for a `CANCELED` answer.
- §4.3 A `PARTIALLY_FILLED` row answered `NEW` with less executed keeps its row.
- §4.4 A `PARTIALLY_FILLED` row answered `FILLED` still moves up and takes the
  venue's size (spec `207` unchanged).
- §4.5 A `PARTIALLY_FILLED` row answered `CANCELED` still takes the venue's
  answer (spec `235` §4.2 unchanged).

## Invariants

- `deals.combo-closed-books-base-its-fills-sold` (main-app pack
  `specs/invariants/deals.invariants.json`, observe). A LONG combo deal that
  closed holding base while its own FILLED rows net to zero. This is the
  state the downgrade leaves behind once the row is re-marked FILLED after
  the close. On its first prod dry run it found only the originating deal.
