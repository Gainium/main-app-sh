# 188 — A close request re-sends a take-profit that already filled

Bug spec (Definition / Evidence / Assumption). Code: `src/bot/dcaHelper.ts`
`closeDealById`, `cancelAllOrder`.

## §1 Definition

**Expected.** When a request to close a deal finds, while cancelling the
deal's resting orders, that the deal's take-profit has already FILLED on the
venue (its fill event never reached the bot), that fill is the close. The
request finishes without placing another close order.

**Actual.** The request hands the FILLED take-profit to `handleUnknownOrder`
without waiting for it and carries on: it re-reads the deal (still `open`,
because the fill's own close runs in the background), prepares a fresh
take-profit for the whole position, and sends it. The fill's close then marks
the deal `closed`, and the new order sits on the venue with no deal behind it.
When it fills it sells (or buys) the user's own coins, outside any deal.

**Unchanged.** A close of a deal whose sweep cancels its orders normally (no
order comes back FILLED) places its close order exactly as before.

## §2 Evidence

Prod, binance HOMEUSDT, deal `6ad862f1…` (2026-10-21, DCA bot log + Mongo):

| time (Z) | event |
|---|---|
| 14:15:01 | indicator close rests limit TP `TP-uk8j…` for 4387 |
| 14:15:32 | `uk8j` fills on the venue; no user-stream event reaches the bot |
| 14:16:00.717 | indicator close fires again: `Сlose deal 6ad862f1…` |
| 14:16:00.951 | cancel of `uk8j`: `Order not found` |
| 14:16:01.187 | `Real order …uk8j… status: FILLED` → `TP order FILLED` (background) |
| 14:16:01.224 | the close request goes on: `Generate initial deal orders` |
| 14:16:01.228 | deal saved `closed`, trigger tp |
| 14:16:01.419 | new TP `TP-vMYA…` for the full 4387 is saved and sent |
| 14:24:00 | `vMYA` fills on the venue; no deal owns it |

The sentinel invariant `045.fill-outside-deal` caught the `vMYA` row.

## §3 Assumption (root cause hypothesis)

`closeDealById` decides to send its close order from the deal's status alone,
read once right after the sweep. The sweep's FILLED take-profit closes the
deal through `handleUnknownOrder → processFilledOrder → closeDeal`, none of
which the request waits on (`processFilledOrder` itself fires `closeDeal`
without awaiting it), so the status read is stale by construction.

Awaiting `handleUnknownOrder` in `cancelAllOrder` does not close the race on
its own — `closeDeal` is still fire-and-forget inside `processFilledOrder` —
and `cancelAllOrder` is also reached from `rebuildDealOrders`/`processDealClose`
under other per-deal mutex keys, where waiting on `processFilledOrder`'s key is
not provably deadlock-free. The decision therefore belongs where the order is
sent.

## §4 Fix

§4.1 `cancelAllOrder` returns the orders whose cancel came back `FILLED`
(it still hands each to `handleUnknownOrder` as before).

§4.2 Immediately before `closeDealById` sends its close order it re-checks the
deal: gone from memory, no longer `open`, or already in `pendingClose` → send
nothing. And when its own sweep turned up a FILLED take-profit of this deal,
`dealClosedByFilledTp` (the same predicate `placeOrders` uses) decides whether
that fill closed the position — if so, send nothing.

§4.3 A multi-TP target or an under-filled take-profit does not satisfy
`dealClosedByFilledTp`, so the request still closes what is left (unchanged).

## Invariants

Already covered by main-app `specs/045.invariants.json`
`045.fill-outside-deal`; no new invariant.
