# 086 — A combo futures base order is cut down by per-level lot rounding

Bug spec. The behaviour exists and is wrong.

## 1. Definition

### 1.1 Expected

A Combo **futures** bot whose base order is configured as a quote notional must
open a position worth that notional, subject only to the venue's lot step.

The base order is not free to be any size: on futures, `getBaseOrder` re-sizes it
to the sum of the base grid it lays over the position, so the ladder that unwinds
the position and the position itself agree exactly. So the requirement lands on
the grid: **the base grid's level quantities must sum to the budget-derived
target, within one lot step** — not to a value that has lost one step per level.

### 1.2 Actual

Each base-grid level is sized as `budget ÷ Σ(level prices)` and then **floored to
the lot step independently**. With `N` levels the grid loses up to `N` lot steps,
and because the futures branch of `getBaseOrder` then copies that sum onto the
base order, the whole loss lands on the position the user opened.

## 2. Evidence

Runtime, through the real `comboHelper.getBaseOrder` and the real
`MainBot.generateGridsOnPrice` (`src/bot/comboFuturesBaseGridSizing.spec.ts`).
Pair described by its filters only — the reported OKX linear SOL perpetual, lot
step `0.01`, min notional `1`, price `117.56`, base order `10` quote, LONG:

| base grid levels | budget (quote) | base order (SOL) | notional placed | shortfall |
|---|---|---|---|---|
| 2  | 9.4048 | 0.06 | 7.0536 | 2.3512 |
| 3  | 9.4048 | 0.06 | 7.0536 | 2.3512 |
| **5 (reported)** | **9.4048** | **0.05** | **5.8780** | **3.5268** |
| 7  | 9.4048 | 0.07 | 8.2292 | 1.1756 |
| 5, finer step 0.001 | 9.9926 | 0.080 | 9.4048 | 0.5878 |

The five-level row is the reported deal to the cent: five contracts, `0.05` SOL,
`5.878` quote invested, with five base-grid sell orders of `0.01` each whose sum
is exactly the base order.

Controls:

- **Spot**, same settings: base order `0.08` / `9.4048` — correct. The spot
  branch of `getBaseOrder` only ever *raises* the base order from the grid, never
  replaces it, so the per-level flooring does not reach the position.
- **The budget is not the defect.** `getBaseOrder` floors `10 / 117.56` to `0.08`
  = `9.4048` before any grid exists; that is the size the position should have
  opened at, and spot opens at exactly that.

## 3. The reproduction (what the test pins)

§3.1 With the numbers above, the base order's quantity equals the grid sum and
that sum is `0.05`, a 37% shortfall against the budget the base order was sized
from.

§3.2 Every level is a whole multiple of the lot step and at least the venue's
minimum quantity — the venue's constraints are met; only the total is wrong.

## 4. Assumption (hypothesis — this is what the fix acts on)

`MainBot.generateGridsOnPrice` sizes each combo level with
`this.math.round(baseAmount, precision, combo, …)` — `down = combo`, i.e. a floor
per level, taken independently. The truncation residual (`baseAmount − floor`) is
discarded at every level instead of being carried into the next, so the grid sums
to `N × floor(baseAmount)` instead of `≈ N × baseAmount`.

§4.1 Carrying the residual — each level takes the difference between the floored
**cumulative** target and what the earlier levels actually took — makes the grid
sum land within one lot step of `N × baseAmount`, with every level still a whole
multiple of the lot step.

§4.2 It must never commit more than the budget: a cumulative **floor** keeps
every prefix sum at or below the corresponding unrounded prefix, so the total can
only come in at or under the budget-derived target.

§4.3 It holds across level counts and lot steps, not just the reported one.

## 5. What must not move

§5.1 **Spot combo sizing is unchanged.** On spot the per-level floor is what
keeps a sell ladder inside the base the deal actually holds; the defect needs the
futures-only overwrite in `getBaseOrder` to reach the position at all.

§5.2 **Grid bots are unchanged.** `combo` is `botType === BotType.combo`, so a
grid bot never took the floored branch and must not take the carried one.

§5.3 **The venue minimum still wins.** When the budget cannot fund every level at
the venue's minimum quantity the levels are still floored up to that minimum and
the grid still over-commits (11 levels on the fixture: `0.11` / `12.93` against a
`9.40` budget). That is a different defect — the combo base grid has no
equivalent of the grid bot's minimum-budget refusal (spec 068) — and this change
must leave it exactly where it was, neither better nor worse.

## 6. Blast radius note

`generateGridsOnPrice` is the sizing routine for every grid and combo ladder in
the engine and lives in the shared `core/` submodule. The change is confined to
the `profitCurrency === 'quote' && orderFixedIn === 'base'` branch under a
`combo && futures && !coinm` gate, which is exactly the combo-futures linear
minigrid. See plan §Blast Radius.
