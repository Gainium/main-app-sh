# 221 — A safety order refused by the venue is re-sent under the id it was written off with

Bug spec (Definition / Evidence / Assumption). Tests:
`src/bot/dca/writtenOffLevelId.harness.spec.ts`.
Extends spec `161` (spent level ids) to the ids the bot retires itself.

## §1 Definition

A DCA (and combo) safety-order level carries a `newClientOrderId`. When the
venue REFUSES that order (not enough balance after the retry ladder, price band,
min notional, …), `sendOrderToExchange` retires it: it drops the order from the
bot's map and writes its row CANCELED. The level is still due, so a later pass
(a deal restart, an active-orders change, the next fill) places it again.

**Expected.**

- §1.1 A level whose earlier order this bot wrote off as CANCELED after a venue
  refusal is re-sent under a client order id the venue has never been sent, so
  its new order gets its own row and the bot tracks it from placement on.
- §1.2 Unchanged (spec 161 §1.4): a level never sent keeps its own id; a level
  whose order is live or FILLED is skipped; an order refused by a LOCAL guard
  (served from the cooldown, never sent) has its row deleted and keeps its id —
  nothing about it was spent.

**Actual.** The level keeps the refused id. The venue never accepted that id
the first time, so it accepts it now and the order rests on the book. But its
row already exists as CANCELED: the write-ahead insert collides on the unique
`clientOrderId` index ("already saved"), and every later `updateOrderOnDb` is
filtered on `status ∉ {FILLED, CANCELED}`, so the row stays CANCELED. The order
is live only in the bot's memory. The next bot reload (`loadOrders` skips
CANCELED rows) forgets it, the ladder sees its level empty and places a second
order at the same price, and no cancel (restart, deal close, active-orders
change) ever reaches the first one.

## §2 Evidence (prod, read-only: DCA bot worker logs, user-stream logs, the deal's orders)

Coinbase spot long DCA deal, activeOrdersCount 2 at the end.

- §2.1 22:43:04–:27Z: three safety orders (0.017608, 0.01739, 0.017173) each
  `not enough balance, retry - 1..5`, then `Error | Not enough balance Order id:
  …`. Their rows are CANCELED with `updateTime` 22:43.
- §2.2 23:25:42Z the user restarts the deal. 23:25:45–47Z the SAME three client
  order ids are sent again; the user stream reports each `NEW` on Coinbase and
  the bot logs `Save order <id>` for each. The rows still read CANCELED
  (22:43) afterwards — the DB never learned they were placed.
- §2.3 Next day 03:23:40Z, after the bot moved worker (orders reloaded from
  the DB), a new order is placed at 0.017608 under a fresh id. The user stream
  keeps reporting BOTH 0.017608 orders `OPEN` for four days.
- §2.4 Four days later the user restarts again: the restart cancels every order
  the bot tracks (both tracked 0.017608/0.017825 orders are `CANCELLED` by
  "User requested cancel" on the stream) and re-places the two levels — the
  untracked 0.017608 order from §2.2 is still `OPEN`, so the book again shows
  two buys at 0.017608.
- §2.5 Code: the venue-refusal branch of `sendOrderToExchange` (`deleteOrder`
  then `updateOrderOnDb({...order, status:'CANCELED'})`);
  `dcaHelper.reissueSpentLevelId` → `resolveLevelClientOrderId` reads the
  level id's status from the order map only, and an id the map does not hold
  answers `keep`.

## §3 Assumption (root cause — hypothesis)

- §3.1 Spec 161 mints a fresh id for a level only when the bot can SEE its id is
  spent. The venue-refusal write-off removes the order from the map, so the
  spent id looks never-sent and the level is re-sent under it.
- §3.2 Because the id is reused, the accepted order lands on a row the DB
  guard refuses to move out of CANCELED (§1 Actual). The duplicate and the
  untouchable order both follow from that.

## §4 Required behaviour (tests cite these)

- §4.1 After the real venue-refusal branch of `sendOrderToExchange` retires an
  order, the bot reports that client order id as written off.
- §4.2 A level carrying an id the bot wrote off — and no longer holds — is
  placed once under a fresh id, and the level carries that id afterwards.
- §4.3 An order refused by a local guard (never sent) is not reported written
  off.
- §4.4 Unchanged (§1.2): spec 161's placement harness stays green.

## §5 Open questions / not changed

- §5.1 The record lives in the worker's memory. A reload rebuilds the ladder
  with freshly minted ids, so a level cannot carry a written-off id across a
  reload; nothing is persisted.
- §5.2 A row stuck CANCELED by a reuse that happened before this fix is not
  repaired here. The next deal restart, close or reload does not see it either;
  such an order has to be cancelled on the venue.
- §5.3 An order the venue cancels and reports on the stream is also dropped from
  the map; a reuse of that id is refused by the venue as a duplicate and taken
  by the spec 136/145 duplicate branch, so it does not leave an untracked order.
  Not changed here.
