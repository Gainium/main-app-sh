# 161 — A cancelled safety order is re-sent under the id the venue already spent

Bug spec (Definition / Evidence / Assumption). Tests:
`src/bot/clientOrderIdReissue.spec.ts`,
`src/bot/dca/spentLevelIdPlacement.harness.spec.ts`,
`src/bot/duplicateClientOrderId.spec.ts` (§4.4–§4.5 cases).

## §1 Definition

A DCA (and combo) safety-order level is a `Grid` in the deal's ladder carrying
a `newClientOrderId`. When that level's order ends CANCELED with nothing filled
and the level is still due, the bot places it again.

**Expected.**

- §1.1 A level re-placed after its order was CANCELED (or EXPIRED) is sent under
  a client order id the venue has never seen. The level keeps that new id, so
  every later pass and every cancel addresses the order that is actually live.
- §1.2 A level whose earlier order was already re-sent under another id, and
  that replacement is live or FILLED, is not placed again. At most one order
  per level reaches the venue.
- §1.3 When a venue refuses an id as a duplicate and the bot re-sends it under
  a sibling id (`…2` / `…3`), and that sibling already exists in this bot's
  orders (in memory or in the DB) live or FILLED, the bot returns that order and
  sends nothing. A sibling that exists only as CANCELED/EXPIRED is spent too and
  is skipped for the next free one.
- §1.4 Unchanged: a level whose id is live (`NEW`/`PARTIALLY_FILLED`) or FILLED
  is skipped exactly as before; a level never sent is sent under its own id; the
  duplicate branch still asks the venue first (spec 136) and still never re-sends
  the refused id (spec 145).

**Actual.** `placeOrdersHoldingDealLock` treats `status === 'CANCELED'` in the
order map as "free to send" and re-sends the level under the SAME id. Venues
that refuse a reused client order id (Bybit: `Duplicate clientOrderId.`) send it
to `sendOrderToExchange`'s duplicate branch, which re-sends it as `…2`. The
level still carries the original id, so the next pass sends the original id
again, and the duplicate branch computes the same `…2` a second time — even
when `…2` has just filled.

## §2 Evidence (prod, read-only, DCA bot worker logs)

- §2.1 Bybit SHIBEUR short DCA bot, one deal:
  - `01:41:23.862Z Processing msg SHIBEUR D-RO-…Jl65, CANCELED, 0.00000461, base: 0` → saved CANCELED.
  - `01:48:09.171Z Order D-RO-…Jl65 is duplicate` → venue lookup `CANCELED` →
    `01:48:09.805Z Save order D-RO-…Jl62` → `Regular order FILLED D-RO-…Jl62` (1,274,156).
  - `01:48:09.998Z Order D-RO-…Jl65 is duplicate` (the original id sent again) →
    `01:48:10.648Z Error … Duplicate clientOrderId. … Send new order request D-RO-…Jl62, qty 1274156`.
    The only thing that stopped a second 1.27M sell on a level that had just
    filled was that the regenerated id collided; this is the error the user saw.
- §2.2 Bybit PEPEEUR bot: `…jFW` saved CANCELED 11:23:10; re-sent `12:43:08` (→
  `…jF2` placed), re-sent again `13:04:58` → `Duplicate clientOrderId … …jF2`.
- §2.3 Two more Bybit spot cases (STXUSDC, AVAXEUR) have the same shape:
  original CANCELED with 0 filled, `…2` placed, `…2` computed again.
- §2.4 Code: `dcaHelper.placeOrdersHoldingDealLock` —
  `if (get && get.status !== 'CANCELED') skip` and the batch filter
  `!get || get.status === 'CANCELED'` (both since the 2025-07 public import);
  `main.sendOrderToExchange` duplicate branch swaps the last character without
  looking at what this bot already holds under the result.

## §3 Assumption (root cause — hypothesis)

Two halves, both needed:

- §3.1 The placement loop reuses a level's spent id (§2.4). A venue that refuses
  reuse turns every such re-placement into a duplicate round trip, and the
  sibling id the duplicate branch picks is never written back to the level.
- §3.2 The duplicate branch derives the sibling id deterministically and sends
  it without checking whether this bot already placed it, so a level re-sent
  under its original id a second time either collides (the user-visible error)
  or, if the sibling were free, places the level twice.

## §4 Required behaviour (tests cite these)

- §4.1 Pure resolution (`resolveLevelClientOrderId`): given the level id, the
  map of reissued ids and a lookup, answer `keep` (never sent / still live —
  existing checks decide), `adopt <replacement>` (a live or FILLED replacement
  exists) or `mint` (the id, or the end of its replacement chain, is spent).
- §4.2 Harness, SHIBEUR replay: original CANCELED in the map → one pass places
  the level under a fresh id; a second pass carrying the ORIGINAL id while the
  fresh id is FILLED places nothing. Exactly one venue placement, no error.
- §4.3 Harness: a level whose replacement was CANCELED again is re-placed under
  another fresh id (STXUSDC shape) — never the spent replacement.
- §4.4 `sendOrderToExchange`: original refused as duplicate, venue says
  CANCELED, sibling `…2` already FILLED in the map → returns it, one venue call.
- §4.5 `sendOrderToExchange`: sibling `…2` exists only CANCELED (in the DB) →
  re-sent under the next free sibling, not `…2`.
- §4.6 Unchanged (§1.4): existing duplicate-branch tests (spec 136/145) and
  placement harnesses stay green.

## §5 Open questions

- §5.1 Cancels in the diff loop address the level's grid id. With §1.1 the
  level carries the live id from now on; a ladder rebuilt from scratch with new
  ids is unaffected. Not changed here.
- §5.2 Combo shares the placement loop, so §1.1 applies to its `dealRegular`
  levels too; its `dealGrid` minigrid levels are deliberately left alone. A
  separate combo burst of "is duplicate" lines with a different shape was not
  investigated here.
