# 070 — A new hold waits hours for the next REST balance refresh

Bug spec. Plan: `plans/070.a-new-hold-waits-hours-for-the-next-rest-balance-refresh.md`.
Follows spec 069, whose Blast Radius §2 names this as the open follow-up, and
pairs with `exchange-connector-sh` spec 015 (Kraken spot REST reports the hold).

## §1 Definition
- §1.1 Expected: after an order rests, fills or is cancelled, the stored
  `free`/`locked` for that connection reflects the new hold within seconds.
- §1.2 Actual: on a venue whose stream carries no `locked` (Kraken spot v2),
  `locked` moves ONLY when `updateUserBalance` calls the connector. That runs on
  connect and on the snapshot cron, so the hold is hours stale in both
  directions: a freshly rested order's funds keep reading as spendable, and —
  since spec 069 subtracts the STORED hold from every streamed total — a hold
  whose order is already gone keeps being subtracted from `free`.
- §1.3 Every other venue streams its own `locked` and is already prompt.

## §2 Evidence
- `src/utils/user.ts` `updateUserBalance` is called from `connectUserBalance`,
  the per-provider polling timers (coinbase/hyperliquid/bitget only) and the
  snapshot path. Kraken spot has no timer: it has a stream.
- `src/utils/balanceWrite.ts` `streamedFree`: the stored hold is the subtrahend
  on every total-only event, so its staleness is now load-bearing.
- Order events already arrive on the same Redis channel as balance events —
  `connectUserBalance` subscribes to `e.uuid` and `processBalanceUpdate`
  discards everything that is not a balance event.

## §3 Assumption
`executionReport` is the event type every venue's order stream normalises to
(`websocket-connector-sh` emits it for Kraken spot executions), and an order
event is the only thing that can move a spot hold.

## §4 Required behaviour
- §4.1 An `executionReport` on a connection whose venue does not stream its hold
  schedules one REST balance refresh for that connection, after a short window.
- §4.2 Further events inside the window ride on the pending refresh: a burst of
  executions costs ONE connector call, and the refresh reads the state the whole
  burst left behind. A later event opens a new window.
- §4.3 Connections are independent — one account's burst never delays another's.
- §4.4 Nothing is scheduled for a balance event, for an event with no type, or
  for any venue that streams its own `locked` (including Kraken futures).
- §4.5 Disconnecting a connection drops its pending refresh.
- §4.6 A refresh that throws is contained and logged; it neither breaks the
  stream handler nor blocks the next refresh.
