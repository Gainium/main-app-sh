# 101 — A Combo base entry the venue cancels part filled is never booked

Bug spec. The behaviour already exists and is wrong.

Spec `048` fixed this exact stranding for DCA bots and listed Combo bots as out
of scope (§5): `comboHelper` overrides `processCanceledOrder` and never reaches
the DCA implementation. This spec carries `048` §4.2 over to Combo. `048`'s
decision (`shouldSettlePartialBaseEntry`), its settle chain
(`settlePartialBaseEntry`) and its restore-row choice (`pickRestoreBaseEntry`)
are reused unchanged.

## §1 Definition

### §1.1 Expected

When the venue ends a Combo deal's base order — `CANCELED` or `EXPIRED` — after
part of it executed, the deal opens on the executed quantity: `startDeal` runs,
the deal leaves `start`, its minigrids are built, and the user is told once that
the entry was cut short. No second base order is placed on top of it — not on
the cancel, and not on the next worker start.

### §1.2 Actual

1. **`comboHelper.processCanceledOrder`**, for a `dealStart` row, calls only
   `checkUnfilledBaseEntryCancel` (added by `f4416a9`), which by design ignores a
   row carrying a fill. Nothing else hears about the order: a Combo entry is a
   MARKET order and arms no base-order timer, so the queue's cancel callback is
   the only report. The deal stays in `start` with no position, and a `start`
   deal offers no controls in the dashboard.
2. **`comboHelper.restoreWork`** reads the deal's `dealStart` row under
   `status: { $ne: 'CANCELED' }` — the filter `048` §1.2(3) removed from DCA.
   The row is invisible, the deal falls into "not started yet. Place base order
   again", and the entry is re-placed on top of the position the account already
   holds.

### §1.3 Unchanged

A Combo base order cancelled with NOTHING filled still goes through
`checkUnfilledBaseEntryCancel` exactly as today, and a restore of such a deal
still re-places its entry (`pickRestoreBaseEntry` ignores a terminal row with no
fill).

## §2 Evidence

Production, Kraken spot Combo bot, one market entry for 2740.85313 base units:
the stream reported `PARTIALLY_FILLED` up to a cumulative 2728.29486, then
`CANCELED` at the same cumulative quantity, all within 35 ms. The order row was
saved `CANCELED` with that `executedQty`. The worker logged nothing after
`Save order`, and the deal is still `start` with zero balances while the
account holds the executed quantity. (Identifiers are in the private issue.)

## §3 Assumption

The `dealStart` branch of `comboHelper.processCanceledOrder` never asks
`shouldSettlePartialBaseEntry`, and `comboHelper.restoreWork` hides the
terminal row. Everything downstream of `settlePartialBaseEntry` already works
for Combo: `handleUnknownOrder` → `processFilledOrder` (Combo override) →
`startDeal` (Combo override), which builds the deal's orders and minigrids.

## §4 Change

### §4.1 The cancel callback

`comboHelper.processCanceledOrder`'s `dealStart` branch asks the same question
DCA does, with the same inputs, and settles when it holds; otherwise it falls
through to `checkUnfilledBaseEntryCancel`.

### §4.2 The restore path

`comboHelper.restoreWork` reads the deal's `dealStart` rows without the status
filter and chooses with `pickRestoreBaseEntry`, as DCA's does. A chosen terminal
row goes to `checkBaseOrder`, whose `shouldSettlePartialBaseEntry` branch
settles it. `checkBaseOrder` reads the row from the in-memory order map; a
terminal row with a fill is kept there by `processOrderQueue` and survives a
service restart in the Redis snapshot, but a cold load from Mongo excludes
`CANCELED` rows — so the restore puts the row it read back into the map first
when the map does not hold it.

## §5 Out of scope

- The DCA restore path's reliance on the order map (§4.2's cold-load case) — the
  same gap may exist there; not changed here.
- Topping up a Combo entry cut short: `settlePartialBaseEntry` already does
  whatever `topUpSettledBaseEntry` decides, for Combo exactly as for DCA.
