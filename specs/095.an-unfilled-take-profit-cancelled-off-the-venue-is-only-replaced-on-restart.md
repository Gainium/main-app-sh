# 095 — An unfilled take-profit cancelled off the venue is only replaced on restart

## §1 Definition

### §1.1 Expected

A DCA deal that is open, holds a position and closes by a resting LIMIT
take-profit must not be left without that take-profit because someone other
than this bot — the account owner on the venue's own UI, or the venue itself —
cancelled it. Once such a cancel is reported on the user stream, the engine
puts the deal's planned take-profit back on the book within seconds, exactly as
it already does for the same deal when its worker next restarts.

### §1.2 Actual

`processCanceledOrder` handles a cancelled take-profit only when the cancel
carries fills (the partial-take-profit booking). A cancel with **nothing**
filled returns immediately: nothing is logged and nothing is placed. The deal
stays open with a live position and no exit until something reloads the bot.
The only code that notices is the restore path — `checkOrders()` on a service
restart, whose "TP order wasn't found in orders, but must be in grid" branch
re-places the missing take-profit from `deal.currentOrders`.

## §2 Evidence

1. Code: `processCanceledOrder`, `dealTP` branch —
   `if (!isFinite(executed) || executed <= 0) return`.
2. Code: the periodic take-profit coverage check skips deals that hold no
   take-profit at all, by design, and its correction is disarmed by default
   (`BOT_TP_COVERAGE_REPAIR`), so it does not close this gap either.
3. Production: a Hyperliquid perpetual deal's take-profit rows show two
   zero-fill cancels on one day, each followed by the next take-profit row
   only at the instant of the next bot-worker restart — hours later in both
   cases — and the deal later closing normally by take-profit. The engine's
   own cancel-and-replace on the same deal leaves a sub-second gap.

## §3 Assumption (hypothesis)

The gap is entirely that the runtime cancel callback does nothing for a
zero-fill take-profit cancel; the placement logic itself works (the restart
path uses it successfully). Scheduling the restart path's re-placement from the
cancel callback — guarded so it cannot fight the engine's own cancels — closes
the gap without changing anything else.

## §4 Behaviour

- §4.1 **Only cancels the bot did not issue.** Every cancel the engine sends
  (`cancelOrderOnExchange`, and the Kraken bulk cancel that primes it) records
  the order's client id **before** the venue round trip, because the stream's
  CANCELED can arrive before our own HTTP response. A cancel for a recorded id
  is ours and never schedules anything — closes, "leave" closes, settings
  edits, bot stops and take-profit re-sizes all keep today's behaviour exactly.
- §4.2 **Only unfilled cancels.** A cancel carrying fills keeps the existing
  partial-take-profit path and schedules nothing.
- §4.3 **Deferred, and decided under the deal lock.** The restore runs after a
  short delay and takes the same `${botId}${dealId}` lock as `placeOrders`, so
  it is serialised against every placement the engine makes for the deal.
- §4.4 **Places only when the deal provably needs it.** At restore time it
  places nothing when: the process must not trade (dry run); the bot is
  closed or archived; the deal is gone or not `open` (a `start` deal
  has no filled entry to protect); a close is in
  flight (`closeBySl` / `closeByTp`); the deal closes by MARKET (take-profit
  handled by price-level checks, not a resting order); **any** take-profit is
  still resting for the deal; or the deal's plan (`currentOrders`) holds no
  take-profit left to place.
- §4.5 **Defers while a reconcile is running.** While `checkOrders` or the
  reconnect check holds `blockCheck`, or a service restart is still restoring,
  the restore is re-armed rather than run — the restart path works from a
  snapshot of resting orders and would place a second take-profit. The number
  of deferrals is bounded.
- §4.6 **Places what the restart path would**, from `deal.currentOrders`
  (excluding already-filled targets), each with a **fresh** client order id so
  no venue sees a reused one.
- §4.7 One pending restore per deal; timers are cleared with the bot's other
  timers in `clearClassProperties`.
- §4.8 Combo bots are out of scope: `comboHelper` overrides
  `processCanceledOrder` and does not reach this path.

## §5 Non-goals

- No change to the position reconciler or to the take-profit coverage check.
- No schema, GraphQL or dashboard change; nothing is persisted.
- The cause of an external cancel (user vs venue) is not determined — most
  venue streams carry no reason.
