# 061 — Grid bot field presets project paths that do not exist on a grid bot

## §1 Definition

`GET /api/v2/bots/grid?fields=<preset>` returns only the fields named by the
preset for that endpoint type (`bots.grid` in
`core/src/server/v2/fieldConfig.ts`). The preset is turned into a MongoDB
projection verbatim (`parseFieldsParam` → `buildProjection` →
`botDb.readData`), so a path that does not exist on the stored document is
simply absent from the response — there is no error and no warning.

### §1.1 Expected

- `fields=standard` returns the grid bot's **trading pair** and its creation /
  update timestamps, the way the `bots.dca` and `bots.combo` presets do.
- `fields=extended` additionally returns the grid's **price range**, its
  **level count**, and its **take-profit / stop-loss configuration** — the
  settings a caller needs in order to read a bot, change a few values and
  create the adjusted copy through `POST /api/v2/bots/grid`.

### §1.2 Actual

For every grid bot in production, `fields=standard` returns **no pair at all**
and no timestamps, and `fields=extended` adds **no range, no level count and no
TP/SL configuration** — of the settings paths in the two presets only
`settings.name` and `settings.gridType` resolve to a value.

Because `POST /api/v2/bots/grid` merges the request body over
`GRID_FORM_DEFAULTS` (`core/src/server/v2/api.ts:2576`), every settings field
the caller could not read back arrives at the create endpoint as **undefined**
and is silently replaced by the platform default. For the two fields in the
report that means `tpSlAction` and `slAction` are written as `'stop'`
regardless of what the source bot had — the take-profit and stop-loss actions
are reset to "stop and cancel orders" instead of the configured
"stop, cancel orders and close position".

## §2 Evidence

### §2.1 The projected paths exist on 0 of 2 956 production grid bots

Read-only count over the production `bots` collection (2026-09-20):

| path projected by the preset | documents having it | the path the document actually uses | documents having that |
|---|---|---|---|
| `settings.symbol` (standard) | **0** / 2956 | `settings.pair` / `symbol` | 2956 / 2956 |
| `createdAt`, `updatedAt` (standard) | **0** / 2956 | `created`, `updated` | 2956 / 2956 |
| `settings.gridLevels` (extended) | **0** / 2956 | `settings.levels` | 2956 / 2956 |
| `settings.lowerPrice` (extended) | **0** / 2956 | `settings.lowPrice` | 2956 / 2956 |
| `settings.upperPrice` (extended) | **0** / 2956 | `settings.topPrice` | 2956 / 2956 |

`settings.tpSl`, `settings.tpSlCondition`, `settings.tpSlAction`,
`settings.sl`, `settings.slCondition`, `settings.slAction` are present on
essentially every grid bot (2 951 / 2 917 of 2 956) and are named by **no**
grid preset.

### §2.2 The read path reproduces it against a real document

`tests/scratch/bug828-repro.ts` inserts a document with the verbatim settings
shape of a live production grid bot into the local `bots` collection through
the real mongoose model, then calls the exact two functions the handler uses
(`parseFieldsParam('extended', 'bots.grid')` → `buildProjection` →
`botDb.readData`). Observed response:

```
===== fields=extended =====
settings in response : {"name":"MARSCOIN Natural","gridType":"geometric"}
paths that came back EMPTY: settings.symbol, createdAt, updatedAt,
                            settings.gridLevels, settings.lowerPrice,
                            settings.upperPrice, ...
pair in response?          : null
range/levels in response?  : {}
tp/sl actions in response? : {}
```

### §2.3 Where the defaults come from

`POST /api/v2/bots/grid` builds the stored settings as
`applyGridFuturesConstraints({ ...GRID_FORM_DEFAULTS, ...input, ... })`, and
`GRID_FORM_DEFAULTS` (`core/src/server/v2/botDefaults.ts:256`) declares
`tpSlAction: 'stop'` and `slAction: 'stop'`. A body that omits those two fields
therefore stores `'stop'`, with no error to the caller.

### §2.4 What the evidence does NOT establish

The reporter's own client was not observed — the v2 API writes no per-request
log, so which endpoint they call (`POST /api/v2/bots/grid` after a `GET`, or
`POST /api/v2/bots/:botType/:botId/clone`) could not be confirmed from
production. `/clone` spreads `sourceBot.settings` wholesale
(`core/src/server/v2/api.ts:3664`) and would preserve both actions, so it does
not exhibit §1.2. The defect specified here is the one that **is** proven:
the `bots.grid` presets do not return the fields they name.

## §3 Assumption

*Hypothesis, not fact.* The five field names were written from an imagined grid
bot shape rather than from the mongoose schema when the v2 field-selection
feature was first authored, and nothing since has compared them to a stored
document. The fix is therefore to name the paths the schema actually uses, and
to include in `extended` the TP/SL settings that make a read-modify-create
round trip lossless. No behaviour outside `fieldConfig.ts` needs to change.

## §4 Scope

### §4.1 In scope

The `bots.grid` presets only (`GRID_BOT_STANDARD_FIELDS`,
`GRID_BOT_EXTENDED_FIELDS`).

### §4.2 Out of scope

`createdAt` / `updatedAt` are equally dead on the `bots.dca` (0 / 46 047) and
`bots.combo` (0 / 3 430) presets, and `settings.stopLoss`,
`settings.trailingDeviation`, `settings.maxSafetyTradesCount` are dead on
`bots.dca` (0 / 46 047). Same defect, different presets — tracked separately so
this change stays confined to the reported surface.

## §5 Contract

`/api/v2/*` is the public `api.gainium.io` contract (root Danger List #2). The
change is **additive on the wire**: every name removed from a preset is a path
that never resolved to a value, so no consumer can be reading it today; the
names added are paths that resolve on every stored grid bot. Callers of
`fields=full` and of explicit comma-separated field lists are unaffected —
neither goes through the preset table.
