# 121 — The stuck-start sweep cancels resting Terminal limit orders

Bug spec (Definition / Evidence / Assumption). Tests:
`src/bot/dca/oldStartDealsFilter.spec.ts`.

## §1 Definition

§1.1 Expected. A Trading Terminal deal whose entry is a limit order
(`type: terminal`, `settings.useLimitPrice: true`) stays in `start` until the
order fills or the user cancels it. The hourly `closeOldStartDeals` sweep never
selects it.

§1.2 Actual. The sweep cancels it once it is older than 24 h, on the next hourly
run (so ~24 h 10–30 min after placement), with `closeTrigger: auto`.

## §2 Evidence

- Production `Gainium-cron-jobs` log: `Closing old start deals | closing DCA
  deal <id>` for three of the reported terminal limit deals (2026-09-25,
  2026-09-27, 2026-09-29), each ~24 h after creation.
- The filter carries `$not: { type: 'terminal', 'settings.useLimitPrice': true }`
  at the top level. Casting it through the real `dcaDeal` model with
  `strictQuery: true` (set by `MongooseConnect`) yields
  `{ status: 'start', createTime: { $lt } }` — the exclusion is gone.
- Against a real Mongo collection seeded with a terminal-limit, a terminal-market
  and a regular deal, all a day old in `start`, the current filter returns all
  three.

## §3 Out of scope, unchanged

Regular DCA deals, terminal deals with a market entry, and Combo deals that sit
in `start` for more than 24 h are still cancelled by the sweep. Fresh and
non-`start` deals are still left alone.

## §4 Assumption (hypothesis)

`$not` is a field-level operator only; mongoose drops an unknown top-level
operator under `strictQuery` without an error. Expressing the same exclusion as
`$nor: [{ type: 'terminal', 'settings.useLimitPrice': true }]` survives the cast
and restores §1.1 without changing §3.
