# 052 — A market base order the venue replaced with a limit one is never reported

Issue #789. Amends spec-less commits `0c2cdcd` (2026-08-25) and `3f3fa20`
(2026-09-07), both of which shipped for #505 — a limit-only refusal left the
deal with no order on the exchange.

## §1 Definition

A venue whose book is in limit-only mode refuses a MARKET base order. Since
`0c2cdcd` the engine re-places that base order as a LIMIT one instead of
abandoning the entry (#505). That substitution is correct and stays.

### §1.1 Expected

- The substitution **reaches the user**. Their bot is configured to enter at
  market; it entered at limit instead. Nothing the bot does clears that, and
  only the user can change the entry settings, so it is theirs to know about.
- The report says three things: the venue refused the market entry because the
  book is in limit-only mode, the base order was placed as a LIMIT instead, and
  the bot's entry settings should be changed.
- It is written **once per deal per occurrence**, not once per reposition tick.
- The bot is **not** error-stated. The entry succeeded; this is a warning.

### §1.2 Actual

The branch calls `handleLog` — stdout — and nothing else. No `botmessages` row
is written, no `botevents` row, no socket notification. The user's entry type is
silently substituted and the only record is in a log file they cannot read.

Before `0c2cdcd` the same refusal fell through to `handleOrderErrors`, so it
**was** user-visible. The fallback branch was inserted ahead of that `else`, so
fixing #505 removed the notification as a side effect.

## §2 Evidence

### §2.1 The branch fires in production

`Gainium-DCA-bot` logs, live + archived, fixed-string `Re-placing`:

Both bots are `exchange: coinbase`, `settings.startOrderType: LIMIT`, and both

issue was filed from.

### §2.3 Exposed population

`dcabots`, `exchange: coinbase`:

| `settings.startOrderType` | bots | distinct users |
|---|---|---|
| MARKET | 893 | 15 |
| LIMIT | 141 | 16 |

Both entry shapes reach the branch — LIMIT via the `enterMarketTimeout`
forced-market path in `checkBaseOrder`, MARKET because the deal's first base
order *is* a market order. The two production occurrences are the LIMIT shape.

### §2.4 The tick that makes this a spam risk

After the fallback places a LIMIT, the block at `dcaHelper.ts:9403` re-arms the
reposition timer (`sentType === limit`). That timer calls `checkBaseOrder` with
no `forceMarket`, which on a MARKET-entry bot derives a MARKET base order again,
is refused again, and falls back again. So the condition re-enters this branch
once per `orderLimitRepositionTimeout` for as long as the book stays in
limit-only mode — the shape spec `008` exists to stop.

## §3 Assumption

*Hypothesis, not fact.* The defect is exactly the missing report: `0c2cdcd`
inserted an `if` branch ahead of the `else` that called `handleOrderErrors`, and
gave it `handleLog` only. Everything else on the path — the refusal detection,
the `forceLimit` re-place, the termination guard — is correct and must not
change. So the fix is additive: write the user-visible message from inside the
branch, gated so a standing condition reports once per deal rather than once per
tick.

The test must fail because **no `botmessages` row is written**, not because the
fallback misbehaves.

## §4 Solution

### §4.1 The report

Raised by calling `processError` directly with a dedicated subType
(`limitOnlyEntryReplaced`, `bot/utils.ts`), following `closeNotActioned` and
`trailingCloseFailed`: deliberately **not** in `errorDict`, which matches on
message text and would then claim any unrelated message containing the same
words.

`setError: false` — the entry succeeded, so the bot keeps trading.
`sendError: true` — the row is visible.

### §4.2 The rate limit

`ConditionLatch` (`bot/conditionLatch.ts`), keyed by **deal**, exactly as
`tpCoverageDrift` is: two deals have their entries substituted independently.
Reuses the existing `standingConditionLatch` instance on `MainBot`, so a
standing condition re-reports after `STANDING_CONDITION_REARM_MS` (24 h) and is
silent in between. Cleared when the venue accepts an entry for that deal.

`force: true` into `processError`, mirroring `reportTrailingCloseFailed`: the
per-deal latch is the rate limit, and the per-`(bot, subType)` re-raise backoff
layered on top of it would swallow the **first** report of the next deal.

### §4.3 Per-contract coalescing

`limitOnlyEntryReplaced` joins `DEFAULT_PER_SYMBOL_SUBTYPES`. Limit-only mode is
a property of one **product** — Coinbase opens it for a single pair during a
volatility auction — and the user must change the entry settings per affected
pair. Keyed per bot instead, a multi-pair Coinbase bot would own one row naming
whichever pair failed last, which is the spec `007` defect verbatim.

### §4.4 Unchanged

The refusal predicate, the `forceLimit` re-place, the termination guard, the
existing `handleLog` line (operators grep it — §2.1), and the generic `else`
that still handles every non-limit-only refusal.
