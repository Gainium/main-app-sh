# 193 — A placement answer that lands after the stream rewinds the fill

Bug spec (Definition / Evidence / Assumption). The quantity half of a rule
`sendOrderToExchange` already applies to status: its merge keeps a `FILLED`
the user stream delivered first, but takes every quantity from the placement
answer.

## §1 Definition

- **§1.1 Expected.** An order's executed quantity never decreases. When the
  user stream has already moved an order further than the venue's answer to
  its placement says (the stream's reports arrived first), the order keeps
  what the stream delivered: its executed quantity, executed value, average
  price and stream-accrued fee. The deal's books, built from that row, count
  the whole fill.
- **§1.2 Actual.** `sendOrderToExchange` builds the stored row as
  `{ ...held, ...answer }`. It keeps `status: 'FILLED'` when the held row is
  filled, but `executedQty` / `cummulativeQuoteQty` (and any fee fields) come
  from the answer. A limit entry that trades against several resting orders
  the moment it reaches the book, and then fills its remainder, is answered
  `PARTIALLY_FILLED` with the taker part only. If that answer is slower than
  the stream, the engine's row becomes `FILLED` with the taker quantity. Mongo
  keeps the right row (`updateOrderOnDb` will not overwrite a FILLED one), so
  the engine and its own database disagree. The order map is snapshotted to
  Redis and restored from it, so the wrong quantity survives restarts.
  Everything that recomputes from the map then books the fraction: the deal's
  size, average and used quote after the next safety order fill.

## §2 Evidence (prod, Binance spot DCA long, 2026-10-22)

- 00:00:22.237Z `Send base order` (LIMIT, 3085.69).
- 00:00:26.074–.082Z the stream delivers `NEW`, eleven `PARTIALLY_FILLED`
  reports (base 222.63 … 2116.29, quote … 858.027611, all stamped with one
  venue time) and `FILLED` 3085.69 / 1251.119311 one millisecond later. All
  processed in order; `startDeal` books 3085.69.
- 00:00:26.273Z `Save order <the base order>`: the placement answer, 4 s after
  the send and 190 ms after the `FILLED`.
- From 00:00:26.444Z, and after worker restarts at 04:06Z and 05:02Z:
  `holds more than its order rows account for — base order qty 3085.68 taken
  from the position, not the 2116.29 on record`. The engine's base-order row
  says 2116.29; the Mongo row says FILLED 3085.69.
- After the safety order filled (6356.47): deal `size` 8472.76 = 6356.47 +
  2116.29, used quote 3358.03 = 2500.00 + 858.03, against 9442.16 / 3751.12
  actually filled.

## §3 Assumption (hypothesis)

- **§3.1** The placement answer carried the order's state at the moment it
  reached the book: `PARTIALLY_FILLED`, 2116.29 executed. The merge in
  `sendOrderToExchange` wrote those quantities over the streamed `FILLED`
  row. The test in §5 replays the logged burst through the real
  `processOrderQueue`, releases that answer afterwards, and on the current
  code reads 2116.29 back from the order map.

## §4 Required behaviour

- **§4.1** After the venue's figures are converted to the engine's units, if
  the answer states a smaller executed quantity than the row the engine holds,
  the stored row keeps the held row's execution figures (`executedQty`,
  `cummulativeQuoteQty`, `price`, and the fee fields when the held row states
  a fee). Identity fields from the answer (`orderId`, `transactTime`) still
  apply. A line is logged when this happens.
- **§4.2** Unchanged: an answer that states as much as, or more than, the held
  row (the ordinary case: the answer arrives first); status precedence; the
  remainder top-up for market orders; how the take profit is sized at close.
- **§4.3** Pure decision in `staleExecutionReport.ts`, next to the spec `090`
  and `114` rules it completes.

## §5 Tests

- `src/bot/staleExecutionReport.spec.ts` — §4.1/§4.2 for the pure rule.
- `src/bot/placementAnswerAfterStreamFill.spec.ts` — the §2 burst through the
  real `processOrderQueue` and `sendOrderToExchange`.

## Invariants

The wrong state is an open deal whose size is below its own filled entry
rows. main-app `specs/invariants/deals.invariants.json`
`deals.books-below-filled-entry-rows` (observe).
