# 006 — A per-asset fee ledger, and letting a real fee move USD PnL

Part 2 of a three-repo initiative (`websocket-connector-sh` spec `003` is
part 1; app-sh spec `007` — TP-size dust avoidance — is part 3 and depends
on this one). This spec: give every new DCA deal, new combo deal, and new
grid bot a companion fee record that (a) covers every asset a fee was ever
paid in, not just base/quote, and (b) lets a fee paid in a third asset
move `profit.totalUsd` without touching asset-denominated PnL. Existing
open deals/bots are explicitly **not** touched — see §3.

## §1 Current behaviour

### §1.1 `deal.feePaid`/`deal.commission` — base/quote only, already observed-fee-first

As of `eb18ef6`/`fea8577` (1.54.4/1.54.5, shipped 2026-08-27/28), both are
computed from `observedFeeSplit` (`src/bot/orderFee.ts:97-157`), preferring
the venue's reported fee over the stored-rate estimate — but the shape is
still `{base: number, quote: number}` (`dcaHelper.ts:2385-2389`,
`comboHelper.ts:2490-2509`) and a single `Number` (`commission`). Neither
can represent a fee paid in a third asset (BNB, BGB, KCS) as its own line
item; today, when `observedFeeSplit` cannot match a fee to base or quote,
it returns `null` and every caller falls back to the pre-existing
`qty * price * storedFeeRate` **estimate** (`dcaHelper.ts:2276-2284`,
`comboHelper.ts:927-932`) — never a zero, but also never the real number,
and never recorded anywhere as what it actually was.

### §1.2 Grid bots have no fee record at all

`helper.ts:createTransaction` (`:3185-3600+`) computes `comBase`/`comQuote`
from the stored-rate estimate only (`:3220-3222`) — it does not import or
call anything from `orderFee.ts` (confirmed: zero references). The result
is folded straight into `this.data.profit.total`/`totalUsd`
(`:3516-3519,3560-3614`) and a per-transaction `feeBase`/`feeQuote` audit
row (`ClearTransactionSchema`, `:3541-3542`) — never observed, never
persisted as its own field on the bot document. `BotSchema` (`types.ts:2021-2056`)
has no `feePaid`/`commission`/`flags` field of any kind.

### §1.3 The `profitByAssets` precedent this spec follows

`MainBot.profitByAssets?: {asset, total, totalUsd}[]`
(`types.ts:1959`) already exists for a structurally identical problem —
tracking a non-native-currency profit component per asset, in both native
and USD terms — and is already gated behind a creation-time flag,
`BotFlags.newBaseProfit` (`dcaHelper.ts:2350-2384`, set where new bots are
created — analogous flag-setting call to §3's mechanism, e.g.
`DCADealFlags.newMultiTp` at `dcaHelper.ts:1744`). This spec's new field
is deliberately shaped to match — same `{asset, total, totalUsd}` element
shape — so it reads like the existing convention rather than inventing a
new one.

### §1.4 USD-rate lookups that already exist and can be reused

`findUSDRate(asset: string, prices: Prices, exchange?: string)`
(`src/utils/index.ts:71`) resolves a **bare asset ticker** to a USD rate —
exactly what a third-asset fee needs. `BotInstance.getUsdRate(symbol,
'base'|'quote')` (`main.ts:6202-6208`) resolves a **pair side**. Neither is
wired to any fee field today. `fundingProcessor.ts:86-88` is the one
existing precedent in this repo for "convert an amount to USD at the
moment it's captured," for a structurally similar quantity (a funding
payment, not a trading fee).

A third source, new since `websocket-connector-sh` spec `003`'s revision:
some venues compute and report their own USD-equivalent fee — confirmed
for Kraken (`fee_usd_equiv`, forwarded as `feePaidUsd` on the
`ExecutionReport`, per `003` §2). Where present, this is preferred over
either rate-lookup helper for that leg — it's at least as accurate as
anything derived from a separately-fetched price table, and skips a
lookup entirely. §2.3 makes this the first choice, not the only one.

## §2 Target behaviour

### §2.1 New field: `feeByAsset`

`{ asset: string; total: number; totalUsd: number }[]`, added to:
`dcaDealSchema`, `comboDealSchema`, `comboMinigrid` sub-document
(`src/db/schema.ts:1967,2148,2782`), and — new — the grid `BotSchema`
(`types.ts:2021-2056`). One entry per asset a fee was ever observed to be
paid in on that deal/bot, `total` in that asset's own units, `totalUsd`
the USD value **at the time each contributing fee was captured** (§2.3 —
not re-priced at read time, not re-priced at deal close). Every observed
fee is recorded here — base/quote-matched fees included, not only
third-asset ones — so `feeByAsset` is a complete per-asset fee record;
`commission`/`feePaid` (the existing base/quote fields) are unchanged in
meaning and continue to be what PnL subtracts for a base/quote-matched
fee.

### §2.2 A third-asset fee: zero on base/quote, real amount on the ledger, USD only

When `observedFeeSplit` cannot match a fee to base or quote **but the
venue did report one** (`hasObservedFee(order)` true, `observedFeeSplit`
`null` — the BNB/KCS/BGB case), a **new-flagged** deal/bot books
`comBase = comQuote = 0` for that fee (replacing today's estimate
fallback, §1.1) and instead:
- appends `{asset: feeAsset, total: <observed amount>, totalUsd: <observed
  amount * usdRate>}` to `feeByAsset` (merged with any existing entry for
  that asset — same accumulate-by-asset shape `profitByAssets` already
  uses, `dcaHelper.ts:2356-2384`);
- subtracts that `totalUsd` from `profit.totalUsd` only — never from
  `profit.total`/`pureBase`/`pureQuote`, which stay in the deal's native
  currencies and are exactly what §1.1 already computed correctly for a
  base/quote fee.

This is a deliberate departure from today's behaviour (estimate
fallback, §1.1) for the third-asset case specifically, on **new**
deals/bots only (§3): booking a real fee as an honest zero-on-this-side
plus an accurate USD deduction is judged better than booking an
approximate, unverified estimate on a side that isn't even where the fee
was actually charged.

### §2.3 "At capture time" means at the point the transaction/close is processed

Not a new pipeline into `orderFee.ts`'s currently synchronous, I/O-free
`accrueStreamFee`/`observedFeeSplit` (§4 explains why not). It means: the
USD value used for a `feeByAsset` entry is, in order of preference, (1)
the order's own `feePaidUsd` if the venue reported one (§1.4 — Kraken
today), else (2) looked up once, at the moment
`createTransaction` (grid/combo, per fill) or `closeDeal` (DCA, once at
close) processes the fee that produced that entry — using whichever
USD-rate helper (§1.4) fits the asset — not re-derived later from a
different price. Two fills of the same deal, priced minutes apart, can
therefore land two different `totalUsd` contributions for the same asset;
that is intended (each contribution is priced when it happened), and is
why `feeByAsset.totalUsd` accumulates rather than being recomputed from
`total` on read.

### §2.4 Grid parity

`helper.ts:createTransaction` adopts the same `observedFeeSplit`/
`observedFeeOnSide` resolution combo already has (`comboHelper.ts:918-932`)
in place of the stored-rate-only estimate (`:3220-3222`), behind the same
new-bot flag (§3). The 4 base/quote conversion sites already present in
this function (`:3244,3247,3390,3418` — the exact structural sibling of
`comboHelper.ts`'s 4 sites `fea8577` fixed) get the same
`observedFeeOnSide`-first treatment, for the same reason: a raw
base/quote split written directly into `comBase`/`comQuote` without going
through `observedFeeOnSide` can leave the untouched side's later
conversion overwriting a real fee with zero.

### §2.5 Grid gets its own `feePaid`, not just the ledger

§2.4 gives grid an accurate `comBase`/`comQuote` per transaction and, via
§2.1, an accurate `feeByAsset` ledger — but neither is a running
base/quote total on the bot document itself, the thing `deal.feePaid`/
`deal.commission` already are for DCA/combo. Grid has no "close" to
finalize a total at (per §1.2, it runs indefinitely, folding every
transaction straight into `profit.total`) — so this is not "add the same
two fields DCA has," it needs the write pattern combo's `comboMinigrid`
already uses instead: `feePaid: {base: number, quote: number}` on the
grid `BotSchema`, **updated on every transaction** (not once, at a close
that doesn't exist), the same way `comboHelper.ts:2490-2509`
(`updateMinigridFee`) keeps `minigrid.feePaid` current per-fill rather than
only at deal close. A grid bot's `feePaid` is therefore a live running
total for as long as the bot runs, mirroring what `deal.feePaid` already
means for one deal's lifetime.

### §2.6 GraphQL and REST API — exposed in this pass, not deferred

The `006` plan's original blast-radius note flagged the GraphQL/REST
surface as "someone else's follow-up." Revised: do it now, in the same
pass, so this isn't reopened later for a field that already exists on the
underlying schema.

- **GraphQL** (`src/graphql/schema.ts`). New `FeeByAsset` type, mirroring
  the existing `ProfitByAssets` type (`:4401-4405`) field-for-field. Added
  to `dcaDeal`/`comboDeal` (`:4249,4266` — both already have `feePaid:
  FeePaid`/`commission: Float`, gain `feeByAsset: [FeeByAsset]` alongside
  them) and `minigrids` (`:3665-3690` — already has `feePaid: FeePaid`,
  same addition). `fullBot` (the grid type, `:2848-2895`) currently has
  **none** of `flags`/`feePaid`/`feeByAsset` (only `profitByAssets`,
  `:2879`) — gains all three: `flags: [String]`, `feePaid: FeePaid`,
  `feeByAsset: [FeeByAsset]`. No new resolver code needed — every one of
  these types is read straight off the underlying document by GraphQL's
  default resolver (confirmed: no field-level resolver exists today for
  `feePaid`/`commission`/`profitByAssets`/`flags` anywhere in
  `resolvers.ts`), so once §2.1/§2.5's schema fields exist and are
  written, they surface automatically.
- **REST `/api/v2/*`** (`app/CLAUDE.md`'s Cross-service-contracts §, this
  repo owns it). Three files, per the existing pattern:
  - `src/server/v2/fieldConfig.ts` — `feeByAsset` added to
    `DCA_DEAL_EXTENDED_FIELDS`/`COMBO_DEAL_EXTENDED_FIELDS` (`:217-230`,
    already carries `feePaid`). `GRID_BOT_EXTENDED_FIELDS` (`:164-178`)
    currently has none of `flags`/`feePaid`/`feeByAsset` — gains all
    three, same as the GraphQL type.
  - `src/server/v2/openapi-v2.yaml` — mirror into `DCADealExtended`
    (`:2268`)/`ComboDealExtended`/`GridBotExtended` (`:2715-2762`). While
    touching `DCADealExtended`'s `feePaid` property (`:2302-2305`): it is
    currently documented as a scalar `type: number`, which has never
    matched the real `{base, quote}` object shape — a pre-existing
    inaccuracy, not something this spec introduces, but fixing it costs
    nothing extra while the same lines are already being touched for
    `feeByAsset`, so do it in the same edit rather than leaving a second,
    adjacent inaccuracy behind.
  - `src/server/v2/definitions/types.ts` (and `generated.ts`) — the TS
    response types, same three fields, same three places.
  - No response-serialization code changes: `buildProjection`
    (`src/server/v2/fieldUtils.ts:103`) builds a MongoDB projection
    straight from the field-name list, so a field that exists in
    `fieldConfig.ts` and on the underlying document is already exposed —
    confirmed, no separate mapping layer sits between the two.

## §3 Gating — new deals/bots only

- **DCA/combo deals**: new `DCADealFlags.feeByAsset` (`types.ts:1226-1231`),
  set at deal creation the same place `newMultiTp` is
  (`dcaHelper.ts:1744`). Combo minigrids read the flag off their owning
  deal.
- **Grid bots**: new `flags?: string[]` field added to `BotSchema`
  (`types.ts:2021-2056` — it has none today, unlike `DCABotSchema`/
  `ComboBotSchema`, which each already declare their own), **and** to the
  mongoose `botSchema` literal itself (`src/db/schema.ts:609-688` — the TS
  interface alone persists nothing; confirmed this literal has no `flags`
  key today, unlike `dcaBotSchema`/`comboBotSchema`, which already declare
  their own at `:1899`/`:1844`) plus a new `BotFlags.feeByAsset`
  (`types.ts:2319-2325`), set at bot creation the same place
  `BotFlags.kucoinNewFee` is (`src/bot/index.ts:3856`).
- **Existing open deals/bots without the flag**: completely unchanged —
  keep the exact §1.1/§1.2 behaviour (base/quote-only, estimate fallback
  on a third-asset fee, no `feeByAsset`, no grid observed-fee resolution).
  This is the same backward-compatibility shape `newMultiTp`/
  `newBaseProfit`/`kucoinNewFee` already use in this codebase — not a new
  pattern.

## §4 Open questions

- **Is "per-fill USD capture" (§2.3) precise enough, or does it need to be
  the literal fill-time tick price rather than whatever `getUsdRate`/
  `findUSDRate` returns when `createTransaction` happens to run?** Both
  existing helpers read from an already-fetched price table
  (`latestPrices`, `Prices`) that's typically very close to fill time but
  not guaranteed identical to the fill's own execution price. Treated as
  close enough here, matching precedent (`fundingProcessor.ts` does the
  same). Flag if this turns out to matter for reconciliation.
- **`feeByAsset` on `comboMinigrid` vs. `deal` — one authoritative copy or
  two kept in sync?** `feePaid`/`fullFee` today live on both
  (`comboHelper.ts:2490-2509`) as a live mirror. Plan §"contract
  decisions" resolves whether `feeByAsset` follows the same
  mirrored-write pattern or is written once, on the deal, and read by
  reference from the minigrid view.
- **Should a base/quote-matched fee's `feeByAsset` entry use the
  `observedFeeOnSide`-converted amount (one side only, matching
  `comBase`/`comQuote`) or the raw pre-conversion split (both legs, if the
  venue reported both)?** The ledger is meant to be a complete record of
  what was actually paid, which argues for the raw split; the "matches
  what PnL subtracted" argument argues for the converted amount. Resolve
  in the plan.
