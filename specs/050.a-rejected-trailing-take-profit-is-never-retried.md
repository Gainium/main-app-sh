# 050 — A rejected trailing take profit is never retried

Follow-up to spec `049` §6.1/§6.2, which named this and deliberately left it
out of scope.

## 1. Definition

### 1.1 Expected

`trailingMode: 'ttp'` is the armed state of a **trailing take profit**: the
deal has already traded through its take-profit price and the trail exists to
capture more than it while giving back at most `trailingTpPerc` (spec 049
§1.1). When that trail fires, the engine is closing a **profitable** deal, and
the profit only exists while the position is still open at that price. A close
attempt that the venue refuses for a reason **that has nothing to do with the
order itself** — a venue lockout, a rate-limit ban, a 5xx from the venue or
from our own exchange service — is a refusal that will very likely succeed a
few seconds later. The profit is time-limited, so the engine must ask again.

Therefore:

1. A trailing-take-profit close refused for a venue-side, order-independent
   reason is **retried**, on a progressive backoff (30s → 1m), a bounded
   number of times.
2. While those retries are outstanding the deal carries a **persisted** state
   saying so, so that (a) nothing else — a live price tick reaching
   `checkDealsStopLoss`, `checkTrailing` recomputing the level — fires a
   second, overlapping close, and (b) the retry survives a worker restart
   instead of being silently forgotten.
3. A refusal caused by the **order or the account** — not enough balance,
   insufficient margin, a notional/precision/price rejection, a dead API key,
   a compliance block — is **not** retried. Asking again cannot change the
   answer.
4. When every retry is exhausted, the engine **tells the user** that it tried
   to close the deal by trailing take profit and could not, and that the deal
   now needs their attention.
5. Exhausted retries leave the trail **paused**, not armed: an armed level
   outliving the attempt is exactly what spec 049 was written about — a
   restart three days later re-registers it and closes at whatever the price
   has become. The pause lifts, and the whole trail re-arms from scratch
   (including a fresh retry budget), once price has come back over the
   arming line.

This is a DCA-helper concern. Trailing exists only on the DCA engine. Combo is
built on the same mixin but has no trail of its own — its
`checkDealsForStopLossMethods` override never calls `checkDealsForTrailing`, so
`dealsForTrailing` is permanently empty there and no trail can arm — and grid
and hedge have no trail at all.

### 1.2 Actual

Nothing retries, and nothing is remembered.

The one place a terminally refused close is handled is the `else` branch of
`closeDealById` that writes the CANCELED MARKET row through
`handleOrderErrors` (§2.1). Since spec 049 it disarms the trail and returns.
So on the reported production condition — Kraken answering the market SELL
with `EGeneral:Temporary lockout` — the engine:

- makes exactly **one** attempt, then walks away from a deal that was in
  profit at the moment the trail fired;
- keeps `d.closeBySl = true`, which is **in-memory only** (`closeBySl` lives
  on the `FullDeal` wrapper, not on the deal document — it is in neither
  `types.ts`'s `DCADealsSchema` nor `db/schema.ts`), so the "a close is in
  flight" fact is lost on restart and, until restart, blocks the deal from
  being closed by anything at all;
- says **nothing** to the user: `handleOrderErrors` coalesces the venue string
  into a bot error, which for a lockout is worded as an API/venue problem and
  never mentions that a profitable exit was missed.

The deal then survives on whatever other exit is configured. On the reporter's
bot — `useSl: false` (spec 049 §2.1) — there is no other exit at all.

## 2. Evidence

### 2.1 The single terminal-refusal site, traced

`closeDealById` (`src/bot/dcaHelper.ts`) handles a string `result` from
`sendGridToExchange` in three branches, in order:

1. `isNotionalReason(result) && count < this.slippageRetry` — re-enters
   `closeDealById` with `count + 1` after `sleep(250)`. The *only* retry that
   exists on this path, and it is scoped to "the venue says this order is too
   small", i.e. an order-shaped problem.
2. `isPositionAlreadyClosedReason(result)` — books the deal closed with no
   order.
3. `else` — `handleOrderErrors(...)` with a synthetic `status: 'CANCELED'`,
   `type: 'MARKET'`, `executedQty: '0'` row, then (spec 049) `disarmTrailing`.
   **Returns without any further attempt.**

Every venue-side refusal — lockout, 429/ban, 5xx — lands in branch 3.

### 2.2 The production incident is spec 049 §2.3, unchanged

Two Kraken spot deals (SOL-EUR, XRP-EUR), both `closeTrigger: trailing`, both
`useSl: false`, `trailingTp: true`, `tpPerc: '0.800'`,
`trailingTpPerc: '0.200'`. The trail fired **in profit**; the market SELL was
rejected with `EGeneral:Temporary lockout`; nothing retried. Spec 049 fixed
the *consequence* (the stale level later closing at −60.29 / −68.45 EUR) by
refusing a below-break-even close and disarming. It did not, and said it did
not (§6.1), address the *missed profitable exit* or the silence (§6.2).

`EGeneral:Temporary lockout` is exactly an order-independent refusal: it is an
account-wide venue condition, already recognised as its own class by
`isVenueLockout` in `src/bot/authGuard.ts` and described there as clearing on
its own given silence.

### 2.3 `closeBySl` is in-memory, so today's overlap guard cannot be the state

`FullDeal` (dcaHelper.ts) declares `closeBySl: boolean` on the wrapper around
the deal document. `grep closeBySl src/db/schema.ts types.ts` returns nothing.
`checkDealsStopLoss`, `checkTrailing`, `placeOrders` and the restart-time
order reconcile all skip a deal on it, so it is the de-facto "close in
flight" flag — and it is both lost on restart and never released after a
refusal. Any retry scheduled against it would therefore be forgotten by a
restart while the armed level it was retrying survives in Mongo.

### 2.4 There is no existing timer that survives a restart by itself

`dealTimersMap`, `closeDealTimer`, `openNewDealTimer` are all
`setTimeout` handles in process memory, cleared in bulk by
`clearClassProperties` on stop. The only restart-durable timer idiom in the
engine is "persist the deadline on the deal, re-arm the `setTimeout` from it
in `restoreWork`" — which is what `setCloseByTimer(d.deal)` does per active
deal on every restore.

## 3. Assumption (root-cause hypothesis)

The terminal refusal branch of §2.1 treats **every** non-notional,
non-position-flat refusal as final. It has no notion of a refusal being about
the venue rather than about the order, and no state anywhere that could carry
an attempt across either a backoff wait or a process restart — the only thing
resembling that state (`closeBySl`) is in-memory and is never released.

So a classification of the refusal plus one persisted, restart-durable
per-deal retry record, both read at that single branch, is what this needs.
Nothing else on the close path has to change.

## 4. Scope of the retry

### 4.1 Which refusals are retried

**Default: retry.** A refusal is NOT retried only when it is recognised as
caused by the order or by the account. The default is the other way round from
a conservative allowlist on purpose: this repo has been burned twice by
venue-wording allowlists shipping inert (the `notEnoughErrors` comment
documents Kraken and Hyperliquid getting none of four behaviours because their
wording was absent), and the cost of the two mistakes is asymmetric — a
wrongly-retried permanent refusal costs six bounded attempts over four minutes
and then reports to the user, while a wrongly-not-retried transient refusal
costs the user a realised profit and, on a bot with no stop loss, leaves the
deal open indefinitely.

Not retried:

- the not-enough-balance / insufficient-margin family (the engine's existing
  `notEnoughErrors` list, via `matchesNotEnoughBalance`);
- notional / minimum-size refusals (`notionalReasons`) — branch 1 of §2.1 owns
  those and terminates them by booking the deal closed;
- price, precision, lot-size and other order-parameter refusals;
- a dead credential (`isHardAuthFailure`) — only the user can fix it;
- a compliance / jurisdiction block — no retry can ever succeed;
- a Binance Quantitative Rules restriction — re-asking during one is worse
  than pointless: every order sent inside it feeds the unfilled-ratio that
  caused it, which is why `QuantRulesGuard` delays orders instead of failing
  them;
- a duplicate client order id;
- reduce-only / position-flat refusals (branch 2 of §2.1 already returns).

### 4.2 Which refusals are deliberately NOT covered

A refusal whose **outcome is unknown** — a request timeout, `socket hang up`,
`ECONNRESET`, a truncated response — is not classified as retryable here,
because the close may in fact have reached the matching engine and a retry
would be a second market order on a position that is already flat. Those keep
today's behaviour (disarm, per spec 049) and are listed as a known gap. The
per-retry preconditions of §4.4 make the same mistake unreachable for the
refusals that *are* retried.

### 4.3 Budget and backoff

One initial attempt, then up to **5 retries**, with the wait before each retry
stepping progressively from 30s to 1m: `30s, 37.5s, 45s, 52.5s, 60s`
(≈3.9 minutes of total exposure). Progressive rather than fixed for the reason
`RetryBackoff` documents: the first re-probe should be quick because most of
these clear in seconds, while a condition that is still there after four
attempts should not be asked again at the same rate — and a Kraken lockout in
particular is *extended* by every attempt made during it.

Only **5 retries**, not an open-ended backoff: past a few minutes the price
that made this exit profitable is gone, and the honest answer is to stop and
tell the user (§1.1.4) rather than to keep an unbounded loop attached to a
stale decision.

### 4.4 Preconditions re-checked before every retry

A retry is only sent when all of these still hold; otherwise the retry
sequence is abandoned:

- the deal is still `open` (a previous attempt that did reach the venue would
  have closed it — this is what keeps §4.2's double-close off the retried
  paths);
- the bot is still running and still owns the deal;
- the deal is still above break even on the live price, by spec 049's floor.
  A retry four minutes later must not become the below-break-even close 049
  forbids. If the floor now refuses, the retry sequence is abandoned and the
  trail is disarmed exactly as 049 does — no user message, because 049 treats
  that as the ordinary outcome and the trail re-arms above the take profit.

## 5. The paused state and re-arming

### 5.1 Why a plain disarm is not enough after exhaustion

Disarming alone (049's response) would let `checkTrailing` re-arm `ttp` on the
very next tick, because after a refusal the price is usually still above the
arming line — so the deal would fire another close, fail again, and spend
another 5 retries and another user message, every four minutes, for as long as
the venue condition lasts. A lockout's first window is 30 minutes
(`VENUE_LOCKOUT_MIN_MS`) and every attempt inside it restarts that window, so
the loop would also be sustaining its own cause.

### 5.2 What paused means

Exhaustion disarms the trail **and** records that the trail is paused. While
paused, `checkTrailing` must not arm `ttp`. The pause lifts on a real
**crossing** of the arming line (`trailingTpPrice`, the fee-adjusted
take-profit price `checkTrailing` already arms on), not on the price merely
being on the profitable side of it: a tick must first be observed on the
non-arming side, and the tick that then crosses back re-arms.

That crossing rule is the `moveSlArmed` idiom already in this engine and in
this same method's sibling (`checkDealsStopLoss`), and for the same reason:
"price is past the level" is a state that is true on the first tick after any
resumption, while what the rule needs is an event.

### 5.3 What re-arming restores

Re-arming is a full re-arm: the retry record is cleared, so the next trailing
close gets a fresh initial attempt and a fresh budget of 5 retries.

## 6. Acceptance

- §6.1 A trailing-take-profit close refused with an order-independent venue
  reason schedules a retry instead of disarming, and the trail stays armed.
- §6.2 The retry state is written to the deal document, so it survives a
  worker restart: on restore, a deal in `retrying` re-arms its timer from the
  persisted deadline (immediately, if the deadline has passed).
- §6.3 While `retrying`, neither `checkDealsStopLoss` nor `checkTrailing`
  acts on the deal — no overlapping close, no level recomputation — with or
  without the in-memory `closeBySl`.
- §6.4 The waits before the 5 retries are `30s, 37.5s, 45s, 52.5s, 60s`.
- §6.5 A refusal from the order/account families of §4.1 is not retried and
  keeps today's behaviour (disarm, per spec 049). Any outstanding retry record
  is cleared with it — a balance refusal on the third retry ends the sequence,
  it does not pause the trail.
- §6.6 After the 5th retry is refused, the deal is left with: the trail
  disarmed, the trail paused, the retry record in `paused`, `closeBySl`
  released, and a user-visible bot message and event saying the trailing take
  profit could not be executed and the deal needs managing.
- §6.7 A retry is abandoned — no further retries, trail disarmed, no user
  message, no pause — when the deal is no longer open, or when the break-even
  floor of spec 049 now refuses the close.
- §6.8 While paused, `checkTrailing` does not arm `ttp` even when the price is
  above the arming line, until a tick has been seen on the other side of it
  and the price then crosses back. On that crossing the trail arms normally
  and the retry record is cleared.
- §6.9 A paused trail does not block anything else: a configured stop loss,
  the trailing **stop loss** arm, a manual close and the deal's own take-profit
  order all behave exactly as before.
- §6.10 Every retry timer is cleared when the bot stops, and nothing the
  feature adds keeps a reference to the bot after it is closed (no interval,
  no unreferenced closure) — the helper instance must stay collectable.
- §6.11 A `retrying` record can never wedge a deal. It is a **scheduled
  action**, so it only suppresses §6.3 while it is genuinely pending: a record
  whose deadline passed long ago with no attempt made (the worker died in the
  gap, or the re-entered close returned down a path that never reaches the
  refusal site) stops suppressing anything, and the deal is managed normally
  again.
- §6.12 The new deal field is documented in the public v2 REST API
  (`openapi-v2.yaml` plus the generated docs) and served by the v2 deal field
  presets. GraphQL is deliberately not changed — the frontend does not read
  this yet.
- §6.13 **Combo** gets none of this, because it has no trail to refuse a close
  for (§1.1). Its own `restoreWork` override is deliberately left alone: a
  resume call there would be dead code standing in for a state combo can never
  reach.

## 7. Open questions

- §7.1 §4.2's ambiguous-outcome refusals (timeout / hang-up) stay unretried.
  Covering them needs a position reconcile between the refusal and the retry;
  out of scope here.
- §7.2 The paused state is per deal, not per account. Two deals on the same
  locked-out account each spend their own retry budget. A per-account gate
  (`VenueLockoutGuard` is exactly that) could suppress the second deal's
  attempts, but composing it with a *profit-securing* retry needs its own
  decision about which wins; out of scope.
- §7.3 Combo exposes `trailingTp` / `trailingTpPerc` in its deal-settings
  input shape, but no combo code path ever arms a trail (§1.1), so nothing
  here reaches it. If combo ever grows a real trail, this feature has to be
  re-scoped deliberately rather than inherited by accident — the harness pins
  that boundary so the question cannot be answered silently.
