# 229 — The stored deal uPnL lags one sample, and a new deal waits three samples for one

Template: bug spec (Definition / Evidence / Assumption).

The dashboard sorts open deals server-side by the stored fee-inclusive uPnL
(`stats.unrealizedProfitNet` / `stats.unrealizedPercentNet`, main-app spec 019
§5), while each row on screen shows a value priced live. Both use the same
formula, so the order should match the numbers on screen. It does not on quiet
pairs, and newly opened deals sort as "missing".

`DealMonitor.addDealStats` is fed by the bot's price callback: at most once a
minute per symbol (30 s for child bots), and only when the price changed. It
keeps a tracking window per deal and writes the window when it closes.

## §1 Definition

### §1.1 Expected

- **§1.1.1** Every sample is measured into the deal's window. A window that has
  changed (new extreme, profit/loss flip, or the uPnL moved and the last write
  is older than `NET_STATS_REFRESH_MS`) and is older than 30 s is written by
  the sample that measured it. The stored value is the value at that sample's
  price.
- **§1.1.2** A deal that has never been stored (`stats.updatedAt` absent, first
  sample this process sees) is written on its first measurement, once, if its
  uPnL is computable. A deal whose uPnL cannot be computed (no USD rate, …)
  keeps the normal cadence.
- **§1.1.3** The next window starts from the extremes the last one wrote (the
  max of the previous window and the bot's snapshot), not only from the bot's
  snapshot, which does not see the monitor's writes. A deal drifting inside
  an extreme it already wrote is not rewritten every window.
- **§1.1.4** Unchanged: at most one write per window, the 30 s window, the
  10 min refresh of a quiet deal's uPnL (spec 019 §5.4), the flush on deal
  close (spec 064 §4.3), `$max` on the extremes and `$inc` on the times.

### §1.2 Actual

- **§1.2.1** A window closed on the sample AFTER the one that changed it, and
  wrote the previous sample's measurement; the closing sample's price was not
  measured at all. A deal is sampled only on a price change, so on a quiet
  pair the stored uPnL was a full sample interval behind (hours), and the
  dashboard's sort used it against a live value.
- **§1.2.2** A new deal's first sample only opened a window (no measurement),
  the second marked it changed and the third wrote it. Three price changes
  after the open, which on a quiet pair takes hours.
- **§1.2.3** Each new window took its extremes from the bot's snapshot, so a
  deal deeper in drawdown than at bot load re-marked every window changed.

## §2 Evidence

- Open deals on the same quiet pair always carry the same `updatedAt`, so
  writes are driven by the pair's samples; recently opened deals on quiet
  pairs carry no stored stats at all.
- A quiet pair's deals were written 2 s after a trade at 0.004248. Solving
  their stored `unrealizedProfitNet` for the price gives 0.004283, the price of
  the previous trade 23 min earlier. A second pair shows the same (written
  after 0.009494, stored at 0.009485, the trade before).
- Replaying that public trade tape through the real `DealMonitor` reproduces
  the stored value before this change, and stores the value at 0.004248 after.

## §3 Assumption (root cause)

`addDealStats` closed a window in its `else` branch before measuring the
sample that triggered the close, and a fresh window never measured its first
sample. Persisting is gated on the NEXT sample, which on a quiet pair is the
next trade. The fix measures first and closes on the same sample.
