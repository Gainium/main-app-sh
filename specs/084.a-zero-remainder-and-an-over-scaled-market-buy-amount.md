# 084 — A zero remainder, and a market-buy amount past the venue's scale

Bug #871 (finding F819). Bitget spot keeps refusing live orders with
`parameter verification exception …`. Two independent producers in this repo
build an order the venue can only refuse, and both send it anyway.

## §1 Definition

### §1.1 A remainder floored onto the base step is sent as size zero

**Expected.** `sellRemainder` only sends a remainder order when the quantity it
is about to send is a real, tradeable quantity: above zero, at or above the
symbol's minimum base amount, and worth at least the symbol's minimum notional.

**Actual.** The two minimum checks measure `qtyWithoutFee` — the raw, unrounded
remainder — while the quantity actually sent is that value rounded DOWN onto the
symbol's base step. On a coarse-step symbol the rounded quantity is `0` while the
unrounded one still clears both checks, so a MARKET order for zero units is
written ahead to `orders` and sent to the venue.

`baseAsset.minAmount` cannot catch this on Bitget: it is mapped from the venue's
`minTradeAmount`, which Bitget reports as `"0"` for every spot symbol, so
`qty >= minAmount` is `x >= 0` and is true for zero as well.

### §1.2 A Bitget spot market buy is funded to more decimals than the venue accepts

**Expected.** The quote amount sent for a spot MARKET BUY carries no more
decimals than the venue's amount field accepts.

**Actual.** `sendOrderToExchange` rounds the amount to the symbol's own
`quoteAsset.precision` (Bitget's `quotePrecision`). Bitget publishes
`quotePrecision` up to 13 but validates the amount field at 6 decimals, so every
market buy on a symbol whose `quotePrecision` exceeds 6 is refused outright.

## §2 Evidence

All values below are read from production (`orders`, `pairs`, `dcadeals`,
`~/.pm2/logs`) and from Bitget's own public metadata.

### §2.1 The zero remainder

Log, `Gainium-DCA-bot`, three occurrences (2026-08-28, 2026-09-08, 2026-09-20),
all from the same bot:

```
Reason parameter verification exception delegateamount
Method limitOrders() Step Send new order request D-SR-RIgYkWoUcQp15FwDQEQrbd8DIuOwHu,
qty 0, price 108.7, side BUY
```

The write-ahead row is in `orders`:
`origQty: '0'`, `cummulativeQuoteQty: '0'`, `type: 'MARKET'`, `side: 'BUY'`,
`reduceOnly: true`, `typeOrder: 'dealTP'`, `symbol: 'SOLUSDC'`, price `108.7`.

The deal (`6aad4189679acc018fcf623c`, a SHORT spot deal) sold `0.02 + 0.03 +
0.03 = 0.08` SOL and its take-profit BUY of `0.08` filled only `0.07`. The
remaining `0.01` is what `sellRemainder` was asked to buy back, with
`sellNotByOrder` set, so:

- `totalFee = 0.08 × taker(0.002) = 0.00016`
- `qtyWithoutFee = 0.01 − 0.00016 = 0.00984`
- `SOLUSDC`: `baseAsset.step 0.01` → `baseAssetPrecision 2`,
  `baseAsset.minAmount 0`, `quoteAsset.minAmount 1`
- guard 1: `0.00984 >= 0` → passes
- guard 2: `0.00984 × 108.7 = 1.0696 >= 1` → passes
- sent: `round(0.00984, 2, down)` = **`0`**

which reproduces every field of the production row exactly. Any non-zero taker
fee produces the same floor, so the value of `taker` is not load-bearing.

### §2.2 The over-scaled market-buy amount

Log, same service, seven occurrences, all `checkscale=6`:

```
Reason parameter verification exception delegateamount checkbdscale error
value=4.9999286 checkscale=6
Method limitOrders() Step Send new order request D-BO-YjsKfGA4qSkOadggmPF5FKhWHhjZ0Z,
qty 1.6223, price 3.082, side BUY
```

`orders` holds the same number: `origQty '1.6223'`, `price '3.082'`,
`cummulativeQuoteQty '4.9999286'`, `type 'MARKET'`, `side 'BUY'`, `ICPUSDT`.
`1.6223 × 3.082 = 4.9999286` — seven decimals, and `pairs` records
`ICPUSDT quoteAsset.precision: 7`.

Bitget's own metadata agrees with ours and disagrees with its validator:
`GET /api/v2/spot/public/symbols?symbol=ICPUSDT` → `"quotePrecision": "7"`,
while the order the venue refused says `checkscale=6`. `pairs` on Bitget spot:
409 of 2706 symbols carry `quoteAsset.precision > 6` (213 at 7, 134 at 8, and a
tail to 13).

## §3 Assumption (hypothesis, not fact)

- §1.1 — root cause: the guard and the send round differently. Rounding the
  quantity first, then measuring the rounded value, removes it. Verified in
  §2.1 by arithmetic against the production row.
- §1.2 — root cause: Bitget's `quotePrecision` is not the scale its order-entry
  validator enforces on the amount field; the validator caps it at 6. Clamping
  the rounding scale to 6 removes it. The evidence is one symbol's refusal
  naming `checkscale=6` plus the absence of any other `checkscale` value in the
  archive; the clamp is a no-op for the 2297 symbols already at 6 or below.

## §4 Solution

### §4.1
`sellRemainder` rounds the remainder onto the base step ONCE, up front, and
applies both minimum checks — plus an explicit `> 0` — to that rounded value.
The `> 0` is not redundant with `baseAsset.minAmount`: on Bitget that minimum is
zero (§1.1).

### §4.2
The Bitget branch of the market-buy quote conversion in
`sendOrderToExchange` rounds to `min(quoteAsset.precision, 6)`.

### §4.3
`sendOrderToExchange` — the money-safety boundary that already refuses a
non-finite quantity (spec `025` §4.1) — also refuses a quantity at or below
zero, for every venue. No venue accepts a zero-size order, so refusing one here
cannot cost a fill, and it bounds the next producer that floors a size to zero.
Its message is added to `bot/utils.ts`'s `errorDict` as `Order params`, the same
class the non-finite refusal already carries.

## §5 Out of scope

The most frequent refusal on this account is a third, different one:

```
Reason parameter verification exception size 0.000 > 0 … qty 0.001, price 1560.55, side BUY
```

That is a single-base-step MARKET BUY (`ZECUSDT`, `SOLUSDC`) whose quote amount
is `origQty × price` with `price` sitting BELOW the market by the sizing
slippage `getBaseOrder` applies, so the base size the venue derives from the
amount is strictly less than `origQty` and truncates to zero at the symbol's
quantity step. Fixing it means either spending more quote than the order was
sized for or refusing an order that today still opens its deal through
`placeBaseOrder`'s limit-only fallback (Claus #505). Neither is settled here,
and neither belongs in this change.
