# 286 — The fee of an order its placement answer already filled

Bug spec (Definition / Evidence / Assumption). Venue: every venue whose user
stream carries order-level fee totals (`streamFeeFields`), first seen on
Kraken Futures (`krakenUsdm`).

## 1. Definition

### 1.1 Expected

An order the venue filled the moment it was placed is booked by its placement
answer, as today: status, quantities and the deal's fill handling come from
the answer. When the venue's user-stream FILLED report for that order lands
afterwards and states the fee the venue charged, the stored order keeps that
fee (`feePaid`/`feeAsset`/`feeBreakdown`/`feePaidUsd`). This holds whether or
not the bot still holds the order when the report lands. That includes a
take-profit whose fill closed the deal and dropped its orders a few hundred
milliseconds earlier.

### 1.2 Actual

The order row stays FILLED with no fee at all. On Kraken Futures the placement
answer carries no fee, and the stream report is the only place the fee is
stated. Every consumer that reads the stored order then falls back to the
estimate `qty × price × storedFeeRate`. These consumers are the deal's fee
total and profit after a restart, the per-asset fee ledger and order
listings.

### 1.3 Never

- The late write never changes an order's status, quantities, prices or times.
- It never overwrites a fee the row already holds.
- It never books the fill a second time.
- Reports that carry no fee, and statuses other than FILLED, are handled
  exactly as today.

## 2. Evidence

- **A real Kraken Futures MARKET take-profit** (DCA, `krakenUsdm`) is stored
  FILLED with no `feePaid` and no `feeAsset`.
- **Bot log.** There are only two lines: `placement answer is
  PARTIALLY_FILLED with N of N executed. Saving it as FILLED` and `Save
  order`. There is no `Processing msg` line and no `STREAM-DESYNC` line for
  the order.
- **Connector log, ~0.4 s later.** `msg krakenfills{… "cli_ord_id":"<that
  order>","fill_type":"taker","fee_paid":…,"fee_currency":"USD"…}`.
  `websocket-connector-sh` republishes it as a FILLED `ORDER_TRADE_UPDATE`
  carrying `feePaid`/`feeAsset` (`krakenFillFeeFields`).
- **Pattern:** orders that fill on arrival (MARKET, and LIMIT orders that
  cross) are the ones that lose the fee; resting LIMIT orders filled by the
  stream keep it.
- **Code path (core `src/bot`):**
  1. `setOrder` puts the order on the SharedStream route while it is NEW
     (before the venue call). The answer's `setOrder(FILLED)` adds no route.
  2. The take-profit's fill closes the deal, and each order of the deal goes
     through `deleteOrder`, which calls `sharedStream.removeOrder`.
  3. `SharedStream.redisCb` routes a non-liquidation report only through
     `ordersToBotMap`, so the late report is dropped there silently. That is
     why there is no log line at all.
  4. Had it been routed, `accountCallback` drops a report for an id that is
     not in `ordersKeys`.
  5. Had the order still been held (an entry order of an open deal),
     `processOrderQueue` would merge the fee into memory. But
     `updateOrderOnDb` filters `status != FILLED`, so the stored row would not
     take it, and a restart reloads the row without the fee.

## 3. Assumption (root-cause hypothesis)

1. The fee is lost at two independent places:
   - **3.1** The route ends with the order's removal from the bot, so a report
     landing after that never reaches the bot (`sharedStream.ts`
     `removeOrder` / `redisCb`).
   - **3.2** No write path accepts a fee for a row that is already FILLED
     (`updateOrderOnDb`'s status guard, which exists on purpose to stop
     rewinds).
2. Closing either place alone does not fix the bug. A test that sends the late
   report through the real `redisCb` → `accountCallback`, and the real
   `processOrderQueue`, fails on both.

## 4. Required behaviour

- **4.1** After `removeOrder`, SharedStream keeps the removed route for a
  short time (`RETIRED_ROUTE_TTL_MS`). Within that time, a FILLED report
  that carries a fee (`hasObservedFee(streamFeeFields(report))`) still reaches
  the bot that owned the order. Nothing else is delivered through a retired
  route. ~~`removeListener` forgets the bot's retired routes too.~~ Revised
  by §4.6: the bot's stream closing does not end its retired routes.
- **4.2** `accountCallback`, for a FILLED report with a fee for an id the bot
  no longer holds, reads this bot's stored row. If it is FILLED, the bot
  records the fee (§4.4) and stops there: no queue, no fill handling, and no
  `STREAM-DESYNC` line, because the fill is already booked. Any other stored
  state, or no row, falls through to today's behaviour.
- **4.3** `processOrderQueue`, for a fee-bearing FILLED report of an order it
  holds as FILLED with no fee, records the fee (§4.4). Its own processing of
  the report is unchanged.
- **4.4** Recording the fee is one `updateData` on `orders`:
  - **filter:** `{clientOrderId, botId, status:'FILLED', no feePaid, no
    feeBreakdown}`;
  - **update:** a `$set` of only the fields `streamFeeFields` reports.

  It is therefore idempotent and never overwrites a fee. It never touches
  status, quantities or `updateTime`, so the partial `latestOrders_filled`
  index entry does not move. A failure is logged and changes nothing else.
- **4.5** It covers every order type and bot type: `dealStart`,
  `dealRegular`, `dealTP`, combo, and grid.

- **4.6** *(Revision, after the fix shipped.)* A bot's user stream can close
  in the same tick as the fill that closed its last deal. That happens when
  the bot is closing, or the user stopped it with "close deals first", and
  that take-profit was its last order. `closeUserStream` →
  `SharedStream.removeListener` then ran before the late report landed. It
  dropped the bot's listener and retired routes, and unsubscribed the account
  channel when no other bot of that worker listened. The report was then
  dropped at "no route", with no log line.

  From now on, `removeListener` does three things:
  - it retires the bot's live routes like `removeOrder` does, instead of
    deleting them;
  - while any of the bot's retired routes is unexpired, it keeps the bot's
    listener and the channel subscription for `RETIRED_ROUTE_TTL_MS`;
  - when that time is up, it removes them exactly as before.

  An `addListener` for the same bot in that window (a restart) cancels the
  pending removal, so the new listener is never torn down by the old one.
  Nothing else is delivered through a retired route (§4.1 still holds). The
  bot instance stays reachable for at most that window.

  Evidence: three Kraken Futures MARKET take-profits went FILLED with no fee
  after the fix shipped. All three rows are FILLED, `feeBreakdown: []`, no
  `feePaid`, so the §4.4 guard would have matched: the report never reached
  the write. Each bot's log has `Saving it as FILLED` / `Save order`, then
  nothing for the order. The connector logged `krakenfills` with `fee_paid`
  0.3 to 0.5 s after the answer, and it publishes the settled report even when
  the account stream closes in the meantime.
  - Two of them closed the bot's last deal: a stop-loss close (`Set timer 60s
    to send close bot signal` 67 ms after the answer) and a user stop that was
    "closing 1 deal first". That is the case this section fixes.
  - The third was on a bot that kept running and opened its next deal at
    once. The same bot, on the same worker and build, logged `late fee saved`
    for an identical take-profit two hours earlier. Its mechanism is **not
    determined** from the logs, because every exit on the path was silent. §4.7
    makes each exit log, so the next case names its exit.

- **4.7** Every exit that drops a fee-bearing FILLED report is logged at
  info, tagged `LATE-FEE-DROP`, with the order id and the reason:
  - SharedStream: `route expired` and `route present but no listener`.
  - The bot: `no stored row`, `stored row not FILLED (<status>)`, and
    `guard refused (feePaid=…, feeBreakdown=…)`. The guard is the §4.4
    filter that refused the write, or a stored FILLED row that already holds
    a fee.
  - The bot, for an order it still tracks: `tracked but not held` (the id is
    in `ordersKeys` and not in `orders`) and `already processed` (the queue's
    dedupe key was seen, while the held order is FILLED with no fee).
  - `no route` is logged at **debug** only. Every worker subscribed to the
    account sees every report, and in one worker "no route" cannot tell
    "nobody owns it" from "another worker's bot owns it". At info it would
    log once per fill per extra worker.

## 5. Out of scope (recorded, not silently dropped)

- **5.1** Re-deriving `feePaid`/`profit` of deals **already closed** when the
  fee lands. A closed deal booked the estimate at close. For a taker MARKET
  close, the estimate is the venue's taker rate (the account's own rate from
  the venue's fee endpoint, so it equals `fee_paid` for a taker fill). An open deal
  re-reads its held orders at close (`getCommDeal`), so it picks the fee up
  from memory (§4.3) or from the row after a restart (§4.4).
- **5.2** Fills the connector recovered only from REST. These carry no fee by
  design (`feeIncomplete`).
- **5.3** Rows lost before the fix ships are recovered by the one-off
  log-driven backfill `scripts/backfillKrakenLateFillFees.ts`. Running it
  against prod is a separate, approved data write.
- **5.4** Holding a late fee and re-reading when the stored row is not yet
  FILLED (a write-behind race). No case shows it: such a report would have
  logged `STREAM-DESYNC`, and none of the three did. §4.7 logs it as
  `stored row not FILLED (NEW)`. If that line shows up, it is the evidence for
  a hold, and that change goes in its own revision.

## Invariants

- `krakenusdm-filled-order-has-fee` (observe):
  - **What it counts:** a `krakenUsdm` order that has been FILLED for more
    than 10 minutes and still has no `feePaid`/`feeBreakdown`.
  - **Expected after this fix:** close to zero, minus §5.2.
  - **Pack:** `specs/286.invariants.json`.
