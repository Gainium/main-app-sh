# 257 — Merge DCA deals through the public API and MCP

Feature spec. Requested on the community forum (API v2 / MCP: Merge Deals
parity with the UI). Builds on spec 138 (merged deals are one position) —
the engine merge itself is unchanged; this spec only opens a public door to
it and checks the request before it reaches a bot worker.

## 1. Behaviour

### 1.1 Route
`POST /api/v2/deals/:dealType/merge`, `dealType` = `dca`. Header
`paper-context: true|false` selects the trading context, as on every other
v2 deal route. Write permission required (the global API-key check refuses a
read-only key on any non-GET).

Body:

| field | type | meaning |
|---|---|---|
| `dealIds` | string[] (≥ 2 distinct) | open DCA deals to merge |
| `targetDealId` | string, optional | one of `dealIds`; its bot owns the merged deal. Default: the first id |
| `useTp`, `useSl` | boolean, optional | merged deal takes its bot's take profit / stop loss (UI dialog checkboxes) |
| `useDca` | boolean, optional | merged deal restarts its bot's DCA ladder from the merged average |
| `dcaOrders` | integer ≥ 1, optional | levels of that ladder; the engine caps it at the bot's |

`paperContext` in the body is not a selector; the API-key restriction
middleware compares it with the key like on every route.

### 1.2 Pre-validation (synchronous, 4xx)
Refused before anything is sent to a bot worker:
1. `dealType` = `combo` → 400 "Merging deals is not supported for combo
   deals" (the engine refuses combo merges: spec 138 §2.4). Any other non-`dca`
   type → 400.
2. Body shape: `dealIds` not an array of ≥ 2 distinct valid ids, a
   `targetDealId` that is not one of them, a non-boolean option, or a
   `dcaOrders` that is not a positive integer → 400.
3. Any id that is not a deal of the caller → 404 naming the ids.
4. Any deal already merged into another (`child` with a `parentId`) → 409
   naming the deal it was merged into. This is the idempotency answer: a
   repeated call on ids that were merged fails here with a clear error.
5. Any deal not `open` → 409 naming the deal and its status.
6. Any deal in the other trading context than the request (paper vs real)
   → 400.
7. Mixed pair, mixed side (long/short) or mixed exchange account
   (`exchangeUUID`) → 400. The account check is stricter than the engine,
   which would otherwise put another account's orders under the target
   bot's account.

### 1.3 Dispatch (asynchronous, 202)
A request that passes §1.2 is handed to the same `Bot.mergeDeals` the
dashboard's merge dialog uses, with the target deal's bot and the options
above, and the route answers **202** with `{ status: "OK", data: { botId,
targetDealId, dealIds, message } }`. The merge itself runs on the bot
worker. Its result is the merged deal (`GET /api/v2/deals/dca`, the sources
become child deals with `parentId` = merged deal) or, if the worker refuses
(auth-refused key, deal changed meanwhile), a bot error/event on the target
bot. A refusal from `Bot.mergeDeals` itself (bot not found) → 400.

Fees, funding, the merged average and the single-position adoption route
are the engine's (spec 138, spec 139 §5.2); the API computes none of them.

### 1.4 Key restrictions
A key restricted to one bot may merge only deals of that bot (or of its
children); a key restricted to paper or real only deals in that context. The
restriction middleware therefore checks every id in `dealIds` and
`targetDealId`, as it already checks `dealId`.

### 1.5 MCP
`manage_deal` gains `action: "merge"`: `dealId` is the target deal (its bot
owns the merged deal), `dealIds` the other deals to merge into it, plus
`useTp`, `useSl`, `useDca`, `dcaOrders`, `paperContext`. `dealType` must be
`dca`. The tool description states it is asynchronous and DCA-only.

## 2. Documented edge cases (OpenAPI + MCP description)
- An ASAP bot can open a new deal right after the merge.
- TP/SL/DCA of the merged deal can be changed afterwards with
  `PUT /api/v2/deals/dca/{dealId}`.
- `useDca` applies only to plain percentage ladders; indicator, custom,
  ATR/ADR ladders cannot be carried.

## 3. Open decisions (taken)
- 3.1 Pure 202, no bounded wait for the worker: the merge already reports
  its outcome through the deal list and bot events, and a wait would couple
  the API process to worker timing.
- 3.2 `targetDealId` must be one of `dealIds` (otherwise it would be a third
  kind of request: adopt into an outside deal — that is `adoptDeals`).
- 3.3 No `requestId`: §1.2.4 is the idempotency guard.

## Invariants
None new. The route writes nothing itself; every persisted change is the
existing engine merge of spec 138, whose states are already covered there.
