# 192 — A cancel during the pre-send guards writes off an order that then fills

Bug spec (Definition / Evidence / Assumption). Widens spec `155` §4.1: its
in-flight handle covered the venue call only, but the `'-1'` row exists from
the moment `sendOrderToExchange` writes it ahead, before the pre-send guards.

## §1 Definition

- **§1.1 Expected.** For the whole time an order's row carries the `'-1'`
  placeholder because its own placement is still running, a cancel, a
  `getOrder` or the unknown-order ladder waits for that placement to finish
  before acting on the order. If the placement reached the venue, they act on
  the id it returned; if it never did (a guard refused or held it, or the
  placement failed), spec `155` behaviour is unchanged.
- **§1.2 Actual.** The spec `155` handle is registered only when the venue call
  starts. Between the write-ahead (`setOrder` / `saveOrderToDb`) and that call,
  `sendOrderToExchange` awaits its pre-send guards (the not-enough-balance
  check, which may fetch balances from the venue, plus the quant-rules,
  compliance, risk-tier, grid-reduce-only and auth cooldowns in Redis). A cancel
  in that window finds no handle, asks the venue by client order id, gets
  "unknown order" and writes the order off as CANCELED with no exchange id. The
  placement then goes out, the venue fills it, and the reply finds a row that
  says CANCELED.

## §2 Evidence (prod logs, Hyperliquid grid bot, 2026-10-21)

- 13:05:10.123Z the grid take-profit close starts (`Check assets start`); the
  market sell `0xdfcd…` (0.02797 BTC) is written ahead with `'-1'`.
- 13:05:11.078Z `Send cancel request 0xdfcd…. Order not found` →
  `unknownOid, handleUnknownOrder()` → 13:05:11.319Z `Order not found after 1
  lookup(s) … status set to CANCELED`. No `is still being placed, waiting` line:
  the cancel found no handle.
- 13:05:12.485Z `Order 0xdfcd… (581443545717) was written off as CANCELED while
  it was being placed, but hyperliquid executed 0.02797 of 0.02797 BTC-USDC
  (FILLED)` (the spec `155` §4.4 late-reply report).

The cancel came ~1 s after the write-ahead and the venue's FILLED reply ~1.4 s
after the cancel, so the placement had not reached the venue yet when the
cancel ran.

## §3 Assumption (hypothesis)

- **§3.1** The ~1 s between the write-ahead and the venue call was spent in the
  pre-send guards, which the spec `155` handle does not cover. The test in §5
  holds the not-enough-balance balance fetch open while a cancel arrives; on
  the current code the cancel writes the order off.

## §4 Required behaviour

- **§4.1** The in-flight handle for a placement is registered when its `'-1'`
  row is written ahead, before the first pre-send guard.
- **§4.2** It resolves to the venue's order id when the venue call answers
  (unchanged), and to nothing on every path that leaves without sending: a
  guard short-circuit, a quant-rules hold, the zero-quote-amount refusal that
  deletes the row, the split MARKET path, and a throw. It is settled before the
  bail path's own follow-up work (error reporting, deal-start marking), so a
  waiter cannot deadlock on that work (spec `155` §4.1's reason).
- **§4.3** Unchanged: which orders are placed, their sizing and pricing, and
  every pre-send guard's decision.

## §5 Tests

`src/bot/cancelDuringPlacement.spec.ts`, block "spec 192".

- **§5.1** A cancel during the guard await of an order that then fills:
  not written off as CANCELED with `'-1'`; ends FILLED under the venue id.
- **§5.2** A guard that short-circuits the send: the cancel waits, then retires
  the order as before, and no handle is left behind.
- **§5.3** A guard that throws: no handle is left behind.

## §6 Notes

- A waiter can now wait as long as the guards take, including the quant-rules
  inline wait (≤ 60 s, Binance futures only).
- The order in §2 stays booked CANCELED. Re-booking it is a data change and is
  out of scope here.
