# 200 — Closed trades as one server-paged list

## 1. Behaviour

§1.1 The Trades page lists closed trades of every kind together: closed DCA
deals, closed terminal deals, closed combo deals, and stopped grid bots (a grid
bot is both a bot and a trade; the open list already shows the running ones).

§1.2 Closed deal statuses are `closed` and `canceled`. A grid bot counts as a
closed trade when its status is `closed` or `error`.

§1.3 The list is paged on the server as ONE list: a page holds exactly the rows
at its position in the merged order, and `total` counts every match of every
kind. Closed deals of a large account run to tens of thousands, so no client
ever loads them all to page them.

§1.4 Sort is by close time (default, newest first) or open time. Any other
sort falls back to the default. Rows without a sort key come last. Ties break
by id, so no row repeats or disappears across a page boundary.

§1.5 The deal-list column filters (pair, bot name, open/close day, cost) mean
the same thing for every row. A grid bot is read with deal fields derived from
the bot: open time = `created`; close time = the end of its last working shift,
else `updated`; cost = its used quote/base assets; bot name = its own name.

§1.6 Scope matches the per-kind lists: the caller's user, the current
paper/live context, no hedge legs (`parentBotId` unset), no deleted grid bots.

## 2. Contract

`closedTradeList(input: { dataGridInput })` returns `total` and
`data { order { kind id } dca terminal combo grid }`. `order` is the page in
display order; each kind's rows carry the fields of the existing per-kind list
types (`dcaDeal`, `comboDeal`, `fullBot`). Additive; no existing query changes.

## 3. Invariants

None. The query reads only and persists nothing, so it cannot leave stored
state wrong.

## 4. Open questions

- Hedge DCA / hedge combo deals are left out, as they are in the open list.
