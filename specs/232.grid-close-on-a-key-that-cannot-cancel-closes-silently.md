# 232 — A grid close on a key that may not cancel closes silently

Bug spec (Definition / Evidence / Assumption). Owner: grid bot engine
(`src/bot/helper.ts`), with the refusal hook in `src/bot/main.ts`.

## 1. Definition

### 1.1 Expected

When a grid bot is closed and the exchange refuses a cancel because the API
key itself is not allowed to cancel (a permission refusal such as
`EGeneral:Permission denied`, or a dead credential):

1. The close sweep sends no further cancels with that key. Each one is refused
   the same way, and on Kraken each one also extends a lockout of the whole
   key, so the user's other bots on it stop working too.
2. The orders the sweep did not cancel stay as the exchange has them. Their
   rows are not written as cancelled.
3. The user gets one bot message (type `error`) that says the bot closed, that
   N orders are still on the exchange because the key may not cancel them, and
   which ones (their exchange order ids), so that they can cancel them there.

### 1.2 Actual

The sweep sends a cancel for every order. Each refusal is only logged
(`stop()` sweeps with `setErrors = false`), the bot is marked closed and its
user stream closed, and the user sees nothing. The orders keep resting on the
exchange and keep the funds they reserve locked.

### 1.3 Not changing

A close whose cancels the exchange accepts behaves exactly as before: same
calls, same order, same rows, no new message. Refusals that are not about the
key's permissions (rate limit, lockout, unknown order, cancel in progress,
anything else) are routed exactly as before.

## 2. Evidence

Prod logs, `Gainium-Grid-bot-error`, a Kraken spot BTC-USD grid bot:

- 2026-11-05T23:37Z: 35 limit buys placed. `EGeneral:Permission denied Method
  getActiveOrders()` at 23:35:48Z, 23:37:30Z and later: the key cannot read
  orders.
- 2026-11-06T13:32:19.544Z, the user's close: `EGeneral:Permission denied
  Method limitOrders() Step Send cancel request GRID-RO-…`. Within 0.4 s the
  other ~34 cancels come back `Temporary lockout (balancer held this key off for
  another 1200s …)`. The same pattern repeats at 14:55 and 16:50:52.
- The bot is `closed` with no bot message; 35 orders are still open on Kraken
  and hold the account's whole USD balance. The sentinel invariant
  `grid.closed-bot-order-resting` flags the bot.

Code path: `BotHelper.stop()` → `cancelAllOrder(cancelPartiallyFilled, false)`
→ `cancelOrderOnExchange(order, false)` per order. A grid bot never takes spec
`180`'s teardown branch: `cancelIsTeardown()` is `blockPriceCheck ||
cancelRetryWanted()`, and both are false for a grid (`blockPriceCheck` is set
only by the DCA helper). The refusal therefore falls through to
`handleErrors(reason, 'limitOrders()', …, false, false)` — logged, never shown —
and the loop moves to the next order. `stop()` then closes the bot.

## 3. Assumption (hypothesis)

The sweep has no notion of "this key cannot cancel": a permission refusal is
treated like any other per-order failure, so nothing stops the loop and nothing
reaches the user. A refusal that names the key (§4.1) is a property of the
account, not of the order, so it holds for every order of the sweep.

## 4. Behaviour

### 4.1 Key refusal

A cancel refusal is a key refusal when its reason contains `permission denied`
(Kraken `EGeneral:Permission denied`, Bybit `Permission denied, please check
your API key permissions.`) or is a dead credential (`isHardAuthFailure`).

### 4.2 The sweep stops

`cancelAllOrder` (grid) sends no further cancel after the first key refusal of
that sweep. Orders it skipped stay in memory and in the database as they were.

### 4.3 The user is told

`stop()` (the `cancel` close type) and the close-by-limit / close-by-market
path, after their sweep, send one `error` bot message through
`reportUserRefusal` naming the exchange order ids still resting (the orders
still `NEW` / `PARTIALLY_FILLED` in the bot after the sweep). At most 40 ids
are listed, then "and N more".

### 4.4 Successful closes

With no key refusal the sweep is unchanged (§1.3).

## Invariants

None added. The resting orders this leaves are already caught by
`grid.closed-bot-order-resting` (the invariant that found this bug); the fix
makes the state visible to the user, it does not remove it — only the user can
cancel orders their key may not cancel.
