# 033 — on OKX, one safety order in sixty is booked as an addition

`updateDeal` decides whether a filled `dealRegular` order is an add-funds
top-up or an ordinary DCA safety order by looking for `ROA` in its client order
id. On OKX that test is wrong for **1.64%** of safety orders, and the deal's
books are written as though a level the user never added had been added.

Found while wiring the safety-order notification (core 1.59.3) onto the ladder
count spec `031` repaired. Specs `031` and `032` are immune by construction —
they discriminate on `addFundsId` for exactly this reason (`031` §3) — but the
routing that feeds them is not.

## 1. Definition

```ts
const roa =
  order.clientOrderId.indexOf('-ROA-') !== -1 ||
  order.clientOrderId.indexOf('ROA') !== -1
```

### 1.1 Expected

`roa` is true for an order `addDealFunds` created and false for a safety order
the ladder placed. Nothing else is a `dealRegular` order.

### 1.2 Actual

`MainBot.getOrderId` mints `<brokerCode>D-RO-<tail>` for a safety order and
`<brokerCode>D-ROA-<tail>` for an addition, and then — **for OKX only** —

```ts
if (this.okx) {
  idString = idString.replace(/-/g, '')
  idString = idString.length < maxLength ? `${idString}${id(...)}` : idString
}
```

After that a safety order reads `<broker>DRO<tail>` and an addition reads
`<broker>DROA<tail>`. `utils.id`'s alphabet is
`A-Za-z0-9`, so a safety order whose tail begins with `A` **is**
`<broker>DROA…` — and the second arm matches it.

### 1.3 What the deal records

That fill takes the add-funds branch, so for a level the user never added:

- `deal.funds` gains an entry;
- `levels.all` is grown as though the deal gained an entry outside its ladder;
- the `if (!roa)` `currentBalances` update is **skipped entirely** — the deal's
  running record of what it bought is not moved by a fill that really happened;
- `sendSafetyOrderFilledAlert` (core 1.59.0) never fires for that level;
- and the two ladder counts disagree from then on. `nextLadderLevel`
  (spec `031`) does not advance, because the fill increments `levels.complete`
  and `funds.length` together, so "execute next DCA order" and indicator DCA
  both re-target the level that just filled — while `createCurrentDealOrders`
  retires it correctly, `isLadderOrder` being keyed on `addFundsId`.

## 2. Evidence

### 2.1 The rate, measured

200,000 samples through the **real** `utils.id` and the real id shape
`getOrderId` produces (`maxLength` 32 for OKX, a 6-character broker code):

| id form | test | misclassified |
|---|---|---|
| OKX, dashes stripped | `indexOf('ROA')` | **3289 / 200000 = 1 in 60.8 (1.64%)** |
| non-OKX, dashes kept | `indexOf('ROA')` | 18 / 200000 = 1 in ~11,111 |

The non-OKX residue is an interior `ROA` landing in the random tail; it is the
same defect, three orders of magnitude rarer.

### 2.2 No id-based test can fix it

An anchored test — strip the broker code, require the marker at position 0 —
was measured over the same 200,000 samples and misclassifies **3077**, the same
rate. It cannot do better: after dash-stripping, an addition is
`<broker>DROA<tail>` and a false-positive safety order is `<broker>DRO` + `A` +
`<tail>`. Same characters, same length (both pad to `maxLength`), same
distribution after the marker. The two are not merely hard to tell apart — on
OKX the id does not contain the distinction. It is destroyed at generation.

### 2.3 `addFundsId` does contain it, on every path

`addDealFunds` is the only producer of an add-funds order and always sets
`addFundsId`. Traced every route such an order can take into `updateDeal`:

| route | carries `addFundsId` |
|---|---|
| filled on placement — `sendOrderToExchange` → `processFilledOrder` | yes: `orderToPush = {...ord, ...processedOrder}` where `ord = find \|\| order`, both ours; the connector's response type never declares the key, so the spread cannot clear it |
| write-ahead before the venue answers | yes: `setOrder(order)` stores the object `addDealFunds` built |
| rests as LIMIT, fills later on the user stream | yes: `convertExecutionReportToOrder` returns `{ ...find }`, `find` being the row from the order map or, failing that, from `ordersDb` — and returns `null` rather than a synthesised order when neither has it |
| after a restart | yes: persisted (`types.ts` `addFundsId?: string`, main-app `src/db/schema.ts:800`), and whole objects go to Redis |
| REST reconcile | yes: both mappers carry it explicitly (`main.ts:5471`, `main.ts:8225`) |

The one path that synthesises an order rather than loading one —
`checkDCALevel`'s `convertGridToOrder` — builds it from a `Grid`, which has no
such field. That is correct and not a gap: a `Grid` is a ladder or take-profit
row, so this path cannot produce an addition. Its output must route as a safety
order, and with §4 it does.

## 3. Assumption (root cause, stated as hypothesis)

The client order id is being asked a question it cannot answer on OKX, and the
structured field that can answer it is already present at every call site. The
substring test is not repairable, only replaceable.

## 4. Required behaviour

### 4.1
`updateDeal` routes a filled order down the add-funds branch when, and only
when, it carries `addFundsId`. The client order id is not consulted.

### 4.2
An order with no `addFundsId` is a safety order, whatever its id contains —
including an OKX id that reads `…DROA…`, and including an order synthesised
from a `Grid` (§2.3).

### 4.3
Every add-funds order still routes as one, on every path in §2.3's table. This
spec must not trade a false positive for a false negative: an addition booked
as a safety order would corrupt the deal in the opposite direction.

### 4.4 — the limit of this fix, stated plainly
**Deals already corrupted are not repaired.** A misrouted fill has already
written a phantom `deal.funds` entry, grown `levels.all` and skipped its
`currentBalances` update; §4.1 stops new ones, it does not unwind old ones.
`currentBalances` is rebuilt from the deal's own order rows by
`updateDealBalances`, so that leg self-heals on the next rebuild, but the
`funds` entry and the `levels.all` inflation persist for the life of the deal.
Repairing them is a backfill over historical OKX deals — a separate decision
with its own evidence, not something to fold into a routing fix.

## 5. Explicitly out of scope

The same substring style appears elsewhere in the engine — the `D-SR` test in
`processFilledOrder`, and the marker list in `accountCallback` that decides
whether a stream event is ours (`DTP`, `CMBGR`, `DMSL`, `GAF`, …). Each is a
separate question with its own blast radius, and none is on this defect's
causal path. Not surveyed here beyond noting they exist.
