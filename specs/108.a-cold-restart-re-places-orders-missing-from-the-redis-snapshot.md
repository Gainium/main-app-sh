# 108 — A cold restart re-places orders missing from the Redis order snapshot

On a real service restart a DCA or Combo bot restores its order map from the
Redis `orders` snapshot instead of reading Mongo. The snapshot is written
through `@RunWithDelay` (`setOrdersToRedis`). When a process places orders and
is stopped before that delayed write runs, the snapshot does not contain them.
The next start then finds no resting order at those levels and places them
again, so the deal ends up with two identical orders on the venue.

## §1 Definition

### §1.1 Expected

- **§1.1.1** After a cold restart restores orders from Redis, every open
  (`NEW` / `PARTIALLY_FILLED`) order that Mongo holds for the restored deals is
  in the order map, including one the snapshot does not have.
- **§1.1.2** The restart order check (`checkOrders` → `getDiffForCheckOrders`)
  therefore places neither a safety order nor a take-profit that already
  rests in Mongo.
- **§1.1.3** When both sources hold the same order, the more advanced status
  wins (`NEW` < `PARTIALLY_FILLED` < a terminal status). Order status only
  moves forward, so the more advanced status is the fresher one. A Mongo row
  never moves an order backwards.
- **§1.1.4** The Mongo read that the merge adds covers only open orders of the
  restored deals, and uses the `dealId` index. A mass restart does not read
  full order history.
- **§1.1.5** When that Mongo read fails, the snapshot is used as before and
  the failure is logged.
- **§1.1.6** A reload (`secondRestart`) still ignores the snapshot and reads
  Mongo only (the 2026-08-25 guard is unchanged).
- **§1.1.7** How many safety orders a deal places, and at what prices, does not
  change. Only the second copy of an order that already exists is no longer
  placed.

### §1.2 Actual

- **§1.2.1** `_loadOrders` returns the Redis snapshot unchanged whenever it is
  non-empty on a cold restart. An order written to Mongo but not yet flushed
  to Redis is absent from the order map, and `checkOrders` places its level
  again, along with the take-profit.

## §2 Evidence

Production, 2026-09-25, a Coinbase DCA deal:

- 03:19:12Z: the outgoing worker process (up since the previous day) logged
  `Save order` for a safety order at 0.323 × 92.53 and a take-profit at
  0.367 × 488.81 during a deploy's shutdown. Both rows exist in Mongo `orders`.
- 03:20:24Z: the new process logged `Found in redis 11 orders`, then tried a
  new take-profit that the venue rejected for `not enough balance` (the coins
  were already held by the 03:19Z take-profit). The restored set was missing
  it 72 s after it was placed.
- 03:47Z, the next restart: `Found in redis 10 orders`, then a second safety
  order at 0.323 × 92.53 was saved before `Found 1 open deals`, which places it
  inside `checkOrders`. The deal now rests two identical safety orders.

## §3 Assumption (hypothesis)

`setOrdersToRedis` is debounced (×5 on restart) and the pending timer dies
with the process, so orders placed in the last seconds of a process never
reach the snapshot. `_loadOrders` trusts the snapshot alone, so they are
missing after the restart. A test that drives the real `_loadOrders` with a
snapshot lacking an order that Mongo has, and then the real `checkOrders`,
must place that order again while the assumption holds.

## §4 Out of scope

- **§4.1** Deals that already hold a duplicate. Which copy to cancel is an
  operator/user call.
- **§4.2** A snapshot row that Mongo shows as terminal while the snapshot still
  shows it open. The merge reads open rows only (§1.1.4), and the restart
  check's venue lookup already settles those rows.
- **§4.3** Deals missing from the Redis `deals` snapshot.
