# 163 — A Hyperliquid close of part of a shared position is retried in vain

## 1. Definition

### 1.1 — expected

When Hyperliquid refuses a deal's close (stop loss, take profit by market, a
manual close) because its value is under the venue's $10 minimum, and the
venue's position on that pair is **larger than the close** — another deal or
bot on the same account holds the rest — the engine:

- recognises that no order closing only this deal can be accepted, so it
  does **not** run the slippage-retry ladder (more attempts at nearly the
  same size and value cannot change the venue's answer);
- reports the refusal once, through the same terminal path a refused close
  takes today (bot error, notification, trailing disarm, take-profit
  restore), with a message that says why: the close is under $10 and only
  part of the venue position, which Hyperliquid accepts only for a close of
  the whole position; and what the user can do.

### 1.2 — actual

The refusal (`order must have minimum value of $10`) is a notional reason, so
`closeDealById` re-sends the close five more times, the last as a limit,
~1.5 s apart. Each is refused the same way. The sixth refusal stops the bot
with Hyperliquid's raw text classified as a generic order-parameter error.
The deal stays open; a stop loss fires again on the next worker start and the
cycle repeats. The user is not told that the close cannot be placed while the
position is shared, nor what would unblock it.

### 1.3 — unchanged

- A Hyperliquid close whose deal **is** the whole venue position. The venue
  accepts a reduce-only order under $10 that closes the whole position, so
  such closes are sent exactly as today and fill.
- When the venue cannot be asked, or does not answer: today's retry ladder,
  unchanged. No answer is not an answer (spec `005`).
- Every other venue, spot, and any refusal that is not a notional reason.
- Everything the terminal refusal path does besides choosing the reported
  message: the trailing-close classifier, the trailing disarm, the
  take-profit restore and the combo "close without order" branch all still
  see the venue's own refusal text.

## 2. Evidence

- Bot log of a DCA bot (HYPE-USDC long, 3x isolated, $10 base order, stop loss
  −2.5%): `closing by stop loss. SL set: 89.75, SL current: 81.88`, then six
  `Close deal` attempts ~1.5 s apart, each refused, on every worker start for
  a week; the deal is still open.
- Hyperliquid user stream for one of those refusals:
  `"reduceOnly":true … "sz":"0.11" … "status":"minTradeNtlRejected"`.
- Two deals from two bots on the **same** Hyperliquid account were open on
  HYPE-USDC, long 0.11 each, so the venue position was 0.22 (Hyperliquid
  perps are one-way: positions net per pair). Every such refusal happened
  while the other deal was open; every sub-$10 reduce-only close Hyperliquid
  **filled** was a deal alone on its account and pair.
- Code: `notionalReasons` includes `must have minimum value of`;
  `closeDealById` retries a notional refusal while
  `count < slippageRetry` (5) and only then reaches `handleOrderErrors`.

## 3. Assumption (hypothesis)

The retry ladder treats every notional refusal as "the price slipped", with
no notion that on Hyperliquid a sub-$10 close of part of a position can never
be accepted. A test that has the venue refuse a 0.11 close for value while
`futures_getPositions` reports 0.22 fails today with six sends and the raw
venue text reported.

## 4. Open questions

- Unblocking the deal itself (closing the whole position, or holding the stop
  loss until the sibling deal is closed) is a product decision and not
  attempted here.
- Opening a second deal whose share of a shared Hyperliquid position could
  fall under $10 is not prevented.
