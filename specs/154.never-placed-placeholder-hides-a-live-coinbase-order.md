# 154 — The `-1` placeholder hides a live Coinbase order

Bug spec (Definition / Evidence / Assumption). Amends spec `011`'s premise for
Coinbase only.

## §1 Definition

On Coinbase an order is addressed by the venue's own order id, and an order
whose local row still carries the `'-1'` placeholder is treated as one that
never reached the venue.

- **§1.1 Expected.** When the venue DOES hold an order under our client order
  id, the bot learns its real exchange id and keeps the order in step with the
  venue. Cancelling it, as when a DCA take-profit is replaced after a safety
  order fills, cancels it on the venue. The bot marks it CANCELED only after
  that, or once the venue confirms it has no open order under that client id.
- **§1.2 Actual.** The cancel path short-circuits on `'-1'` (spec 011) and goes
  to the unknown-order ladder. The ladder's `neverReachedExchange` fast path
  marks the order CANCELED and drops it from the order map and from
  `SharedStream`. The order stays live on Coinbase and locks its base asset, so
  every replacement take-profit is refused for balance and the deal cannot
  close.
- **§1.3 Actual (origin of the `'-1'`).** A worker restart can land between
  "Coinbase accepted the order" and "the placement response / stream event was
  processed". The write-ahead row then keeps `'-1'`. The restart reconcile
  reads the order back, including the real id, from the stream's Redis order
  cache (`getOrder(..., fromCache=true)`). When the status is unchanged (NEW),
  the "not changed" branch throws the merged order away, so the real id is
  never recorded.

## §3 Assumption (hypothesis)

- **§3.1** The reconcile drops the venue's id when status is unchanged (§1.3).
- **§3.2** On Coinbase, `'-1'` is not proof that the venue does not hold the
  order: the venue can hold it under our client order id. Coinbase has no
  lookup by client id, but its open-orders list (`getAllOpenOrders(symbol,
  true)`, which returns `clientOrderId`) can resolve it.

## §4 Required behaviour

- **§4.1** The reconcile records the venue's exchange id on a `'-1'` row even
  when status is unchanged (memory + DB).
- **§4.2** On Coinbase, before cancelling a `'-1'` order, the bot looks up the
  open orders for the symbol by client order id. If it finds the order, it
  adopts the real id and sends the cancel to the venue with that id.
- **§4.3** On Coinbase, if the open-orders lookup itself fails, the cancel does
  NOT write the order off. The failure goes through the normal cancel-error
  handling (the user sees the error and the order stays tracked, so the next
  pass retries).
- **§4.4** If the venue has no open order under that client id, the behaviour
  of spec 011 is unchanged: the bot sends no cancel addressed to `'-1'`, and
  the order is retired.
- **§4.5** The unknown-order ladder applies the same resolution before its
  `neverReachedExchange` fast path. A live order found there is adopted, not
  written off.
- **§4.6** Other venues are unchanged.

## §5 Open questions

- A `'-1'` order that FILLED while the bot could not see it is not in the
  open-orders list, so it is still retired as CANCELED. This was true before
  this change, and fixing it needs a closed-orders lookup by client id. Out of
  scope here.
- Kraken spot / KuCoin full futures `'-1'` rows keep spec 011's behaviour. They
  were not observed live here, and their open-order payloads' `clientOrderId`
  semantics differ (Kraken spot has no cl_ord_id).
