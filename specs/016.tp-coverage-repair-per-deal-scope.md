# 016 — `BOT_TP_COVERAGE_REPAIR` cannot be armed for one deal

Issue #696 follow-up. Extends spec
`013.tp-coverage-drift-after-partial-tp` §4.2, which introduced the flag.

## §1 Definition

**§1.1 Expected.** The take-profit coverage CORRECTION cancels a resting order
and places a new one on a live venue with real money. §4.2 of spec 013 already
says it must be deliberately armed by an operator. Arming a money-moving
correction responsibly means running it on **one** deal first, reading the
result, and only then widening. So the flag must be able to name the deals it
is allowed to act on.

**§1.2 Actual.** The flag is a plain boolean —
`/^(1|true|yes)$/i.test(process.env.BOT_TP_COVERAGE_REPAIR ?? '')`,
`core/src/bot/dcaHelper.ts:204`. It has exactly two positions:

- **unset** — detect only. Nothing is repaired, ever.
- **`1`** — repair EVERY drifted deal the engine sees, on every pass, fleet-wide.

Issue #700 measured **184** genuinely drifted deals standing in production. So
the only way to repair the one deal the operator wants to start with
(`6a90e161a76e7fe63ea3118f`, B3-USDC, 110,493 base uncovered) is to arm all
184 simultaneously. There is no first run.

**§1.3 Worse than all-or-nothing: the rejection is silent.** A value that is
neither `1|true|yes` nor unset — an operator typing the deal id he was told to
arm — matches neither branch, so the flag reads `false` and the engine emits
the *unset* line, `correction is not armed`. Nothing in the log says the value
was seen and rejected. The operator's most natural next move is to conclude the
flag does not work and set `1`, which is the fleet-wide run he was trying to
avoid.

## §2 Evidence

Measured by driving the real `dcaHelper.checkTpCoverage` over the three
recorded production deals of spec 013, at each arming value
(`tpCoverageRepairScope.harness.spec.ts`):

| `BOT_TP_COVERAGE_REPAIR` | detected | orders cancelled | deals re-armed |
|---|---|---|---|
| *unset* | 3 | 0 | 0 |
| `1` | 3 | **3** | **3** |
| `6a90e161a76e7fe63ea3118f` | 3 | **0** | **0** |

The third row is §1.3: the id is rejected in silence, and the emitted line is
`deal 6a90e161a76e7fe63ea3118f left as is — correction is not armed`, identical
to the unset row. The second row is §1.2: no subset is reachable.

## §3 Assumption

Root cause is solely the **shape of the parsed flag** — a `boolean` at
`dcaHelper.ts:204` — not the correction logic downstream of it, which is
already per-deal (it runs inside the `for (const findDeal of openDeals)` loop
and acts on one `dealId` at a time). Widening the parse to a scope value and
consulting it per deal is therefore sufficient; the correction body itself
needs no change.

## §4 Solution

**§4.1** `BOT_TP_COVERAGE_REPAIR` parses to a **scope**, not a boolean:

- unset / empty → `off`. Detect only. **Unchanged in every observable way** —
  this is the state the whole fleet runs in and the deploy must not alter it.
- `1` / `true` / `yes` (case-insensitive) → `fleet`. Every drifted deal, the
  meaning it has today, preserved exactly.
- a comma-separated list of **24-hex** deal ids → `deals`. The correction runs
  only for deals in that set; every other drifted deal is detected and reported
  as before, and left alone.
- anything else → `invalid`. Behaves as `off` — never repair on a value that
  was not understood — but says so, loudly, naming the tokens it rejected
  (§1.3).

**§4.2** A token is a deal id only if it matches `/^[0-9a-f]{24}$/i`.
Deliberately stricter than `mongoose`'s `isValidObjectId`, which also accepts
*any* 12-character string: under that check a truncated or typo'd token parses
as a legitimate id, and the run silently scopes to a deal that does not exist —
the operator sees no repair and no error, which is §1.3 again with an extra
step. This module is also pure by design (spec 013), so it may not import
mongoose regardless.

**§4.3** The scope is logged **once at startup**, when the variable is set. An
operator arming a money-moving correction must be able to confirm from the log
that the engine read what he typed. When the variable is unset nothing is
logged — §4.1's no-change requirement covers the log too, and this line would
otherwise appear on every boot of every bot worker across the fleet forever.

**§4.4** The per-deal `left as is` line states **which** reason applies:
correction not armed at all, versus this deal being outside an armed scope that
names other deals. A deal deliberately excluded from a scoped run and a deal in
a fleet that is not armed are different operational situations and must not
share a log line.

**§4.5** Out of scope: detection, the drift decision, the cancel/re-arm body,
and the standing-condition latch — all unchanged. This spec changes only which
deals the already-correct correction is permitted to run for.
