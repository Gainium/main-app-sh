# 187 — A Combo base order that cannot be built strands the deal in `start`

Bug spec. The behaviour already exists and is wrong.

Combo sibling of [`039`](039.a-base-order-that-cannot-be-built-strands-the-deal-in-start.md).
Spec 039 fixed this for DCA bots. A Combo bot overrides `placeBaseOrder` with
its own copy, and that copy never got the fix.

## §1 Definition

### §1.1 Expected

Combo `placeBaseOrder` writes the deal row first (`createDeal`, status
`start`) and then builds the entry order (`getBaseOrder`). If the entry order
cannot be built, the deal must not outlive the attempt. It is cancelled
(`CloseDCATypeEnum.cancel`, `reopen: false`), as a DCA deal is under spec 039.
The reason the order could not be built is still reported to the user, once.

### §1.2 Actual

Combo `getBaseOrder` returns nothing on every path where it cannot size or
price the entry. Two of those paths report through `handleErrors`, which
returns `Promise<void>`:

- `Asset <asset> not found in user balances`: a `percFree` / `percTotal`
  entry whose sizing asset the account does not hold. A spot SHORT sizes in
  base, so an account holding only quote reaches this.
- `Error getting balance: <venue reason>`: the balance read failed.

Combo `placeBaseOrder` guards everything after `getBaseOrder` behind
`if (baseOrder) { … }` with no else. A falsy answer falls through to
`endMethod`, and the deal row is left in `start` holding no order. It counts
against the bot's active-deal limit. The dashboard cannot close it, because
its deal actions need status `open`. `restoreWork` replays `placeBaseOrder`
with `oldDealId` once per worker start and reaches the same silent return.

## §2 Evidence

- Production: a paper spot SHORT Combo bot sized at `percTotal` on an account
  holding only quote. Every worker start logged
  `Reason Asset <base> not found in user balances Method placeBaseOrder`,
  then nothing. The deal created at the next opening stayed in `start` with
  zero order rows. The `deals.start-stuck-nothing-resting` invariant
  flagged it.
- Code: Combo `placeBaseOrder`, the `if (baseOrder)` block after
  `getBaseOrder`, has no else branch. DCA's copy has had the spec 039 guard
  since that spec shipped. The Combo override has kept this shape since the
  first public release.

## §3 Assumption (hypothesis)

The stranding comes only from the missing spec 039 guard in Combo
`placeBaseOrder`. Adding the same `shouldDiscardUnbuiltBaseEntry` decision
there, before the `if (baseOrder)` block, retires the row on both the
new-deal and the `restoreWork` replay paths. The test in §6 fails without
the guard because `closeDealById` is never called.

## §4 Required behaviour

- **§4.1** The decision is spec 039's `shouldDiscardUnbuiltBaseEntry`,
  unchanged and reused: entry not built, deal in `start`, zero order rows of
  any status.
- **§4.2** The `restoreWork` replay (`oldDealId` set) heals a deal that is
  already stranded. No second deal row is written.
- **§4.3** A deal that holds any order row (resting, cancelled or part-filled)
  or is not in `start` is left alone.
- **§4.4** The reason from `getBaseOrder` is reported once. The retirement
  adds no second user-facing error.

## §5 Not changing

- A Combo entry that can be built is sent exactly as before.
- Combo `getBaseOrder` and its messages are unchanged.
- No migration. Stranded rows are healed by §4.2 on the next worker start.

## §6 Tests

`src/bot/comboUnbuiltBaseEntry.harness.spec.ts`, which drives the REAL
Combo `placeBaseOrder` and the REAL Combo `getBaseOrder` over a balance read
holding only quote. The cases are §1.2, §4.2, §4.3, §4.4 and §5.
