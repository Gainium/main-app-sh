# 041 — A bot started as its opposite closes is refused

## 1. Definition

### 1.1 Expected

A long/short pair of bots on the same one-way futures account and symbol can
be flipped by one signal: stop the bot that holds the position (closing it at
market), then start the bot on the other side. The second bot starts once the
first bot's position has closed. It is refused only if a position on the other
side is actually still there.

### 1.2 Actual

The second bot is refused with

> Cannot start when existing position not met bot settings. Side in active
> position is SHORT, but bot will open LONG.

even though the first bot's position closes about a second later. The user
then looks at the venue, sees no position, and reads the error as nonsense.
The bot is left stopped, so the flip never happens.

## 2. Evidence

A TradingView alert posts one `/trade_signal` array:
`[{ action: stopBot, uuid: <short bot> }, { action: startBot, uuid: <long bot> }]`.
The account is a one-way (no hedge mode) perpetuals account, so the venue keeps
one net position per symbol.

Engine logs for one such signal, milliseconds relative to the short bot's stop:

| t (ms) | bot | event |
|---|---|---|
| 0 | short | `Set status closed` → `Close by closeByMarket` → close deal |
| +3 | long | `Set status open` → `Load data start` |
| +312 | long | refused: `Side in active position is SHORT, but bot will open LONG` (`load data` / `check positions`) |
| +1439 | short | closing order `FILLED` |

Every flip in the same direction on this pair was refused the same way; none
succeeded. The opposite flip appeared to work only because the long bot never
held a position, so there was nothing to close before the short bot started.

Traced code path:

- `Bot.webhookProcess` walks the array in order and awaits
  `singleWebhookProcess` for each item, but for `stopBot` that call only posts
  `setStatus(closed, …, closeByMarket)` to the bot's worker and returns. Nothing
  waits for the close to fill, so `startBot` is dispatched immediately.
- `MainBot.loadData` reads `futures_getPositions` once, finds the still-open
  short on the symbol, and — on a one-way account for DCA, combo and
  directional grid — refuses when its side differs from the bot's
  (`main.ts`, "check positions"). There is no second read.

## 3. Assumption (hypothesis)

The refusal is a race, not a real conflict: the single position read happens
while the opposite bot's market close is in flight, and the position is gone
within a couple of seconds. A short, bounded re-read of positions before
refusing on a side mismatch lets the start succeed when the position closes,
and still refuses exactly as today when it does not.

## 4. Solution

### 4.1

When the side check is about to refuse, re-read positions at a fixed interval
for a bounded number of attempts. If a re-read shows the symbol **flat** (no
non-zero position on it), continue starting with that fresh read in place of
the stale one. Otherwise refuse with today's message.

### 4.2

"Flat" means no row for the symbol with a non-zero `positionAmt`. A position
that flips to the bot's own side during the wait is **not** flat: the margin
and leverage checks above were evaluated against the old position, so the
start is refused as today rather than continuing past checks that never saw the
new position.

### 4.3

An unreadable re-read (non-ok status, no response, a thrown error) is not
evidence of flat. It uses one attempt and the wait continues. The re-read never
throws out of `loadData`.

### 4.4

The first re-read happens after one interval, not immediately: the read that
just refused is the immediate one.

### 4.5

The wait applies only when the refusal would actually stop the bot — not when
`skipFuturesError` holds (a DCA/combo bot that already has active deals only
logs the mismatch), and not on a service restart, where a position that is
present was present before the restart and nothing is closing it. A fleet
restart must not spend the wait on every bot.

### 4.6

The re-read has the same scope as the original read. Venues where the engine
reads all positions at once (and reuses that read for every pair of a
multi-pair bot) re-read all positions; the rest re-read the symbol.

### 4.7

Budget: 5 re-reads, 2 s apart — at most 10 s added, and only on a path that
refuses today.

## 5. Out of scope

- Making `stopBot` in a signal array wait for the close to fill. That changes
  what every signal array means and how long `/trade_signal` takes to answer;
  the re-read fixes the observable failure without it.
- The margin-type and leverage refusals. They compare against a position that
  is closing just the same, but they were not the refusal reported, and a
  pair that differs in leverage also differs after the flip.
- Limit closes (`closeType: limit`). A resting limit close can take far longer
  than the budget; the start is refused as today.
- Hedge-mode accounts. The side check is skipped there already.
