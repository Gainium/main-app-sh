# 042 — A trailing take-profit exit is recorded as a stop loss

## 1. Definition

### 1.1 Expected

A deal that ends because its **trailing take-profit** level was hit is recorded
with `closeTrigger: DCACloseTriggerEnum.trailing`. The user sees a profitable
exit attributed to the trailing take-profit, and a per-trigger performance
breakdown counts it as a take-profit outcome.

A deal that ends because a **real stop loss** level was hit keeps
`closeTrigger: DCACloseTriggerEnum.sl` — including on a bot that also has
trailing take-profit enabled but has not yet armed it.

### 1.2 Actual

Every trailing-take-profit exit is recorded as `closeTrigger: sl`. On a bot with
stop loss switched OFF (`useSl: false`) the deal list therefore shows a
profitable exit labelled "stop loss" for a stop loss the user never enabled, and
any per-trigger breakdown counts take-profit exits as stop-loss exits.

`checkDealsStopLoss` decides the label. Its trailing test is

```ts
(trailingSl && !useMultiSl && !moveSL && useSl && dealCloseConditionSL === tp) ||
(trailingTp && useTp && !multiTp && dealCloseCondition === tp)
```

and passes `trailing ? DCACloseTriggerEnum.trailing : DCACloseTriggerEnum.sl`
to `triggerStopLoss`, which forwards it to `closeDealById`, which persists it
(`deal.closeTrigger = closeTrigger`) before the closing order is even placed.

`multiTp` is `MultiTP[]`, an **array** — the multi-take-profit *targets*, not
the toggle. The toggle is `useMultiTp`, which is what the sibling stop-loss arm
uses (`!useMultiSl`) and what `getTrailingSettings` uses (`!useMultiTp`). Both
Mongo schemas declare `multiTp: [multiTP]`, so mongoose materialises it as `[]`
on every bot that has never configured a target. `![]` is `false`, so
`!multiTp` is `false` for every bot in existence: **the trailing-take-profit arm
is unreachable.**

With `useSl: false` the two `else if` arms below it are unreachable as well
(both require `useSl`), so such a close takes no branch at all: no
`Trailing trigger mode:` line, no `closing by stop loss` line, and
`DCACloseTriggerEnum.sl` regardless.

## 2. Evidence

### 2.1 The label is wrong in production, and the shape is exact

Prod `dcadeals`, read-only, window 2026-09-05 → 2026-09-12. Deals matching
"trailing take-profit is the only trailing this bot can do" —
`settings.useSl: false`, `trailingTp: true`, `useTp: true`,
`dealCloseCondition: 'tp'`:

| measured | value |
|---|---|
| closed `closeTrigger: 'sl'` | **755** |
| …of those with `trailingMode` + `trailingLevel > 0` set | **755 / 755** |
| …of those with `useMultiTp: true` | **0 / 755** |

So every one of them was closed at an **armed trailing level**, and none of them
had multi-take-profit on. Sample (live money): `695b18bd526a3d5d1fc441ca`,
`trailingMode: 'ttp'`, `trailingLevel: 0.825516`, `profit.total: +0.0246`,
`settings.multiTp: []`, `useMultiTp: false`, `closeTrigger: 'sl'`.

`settings.multiTp` is **absent on 0 of 52,867 `dcabots`** — `[]` on 46,350 and
non-empty on 6,517. There is no bot for which `!multiTp` is true.

### 2.2 Runtime: the path ran, and the arm evaluated false

Prod `Gainium-DCA-bot` log, deal `6aa4c498d51734021077f059`
(bot `6aa48bf545e325f6000bfd75`, LABUSDT, `useSl: false`, `trailingMode: ttp`,
`trailingLevel: 0.071676`, `profit.total +0.295`, recorded `closeTrigger: 'sl'`):

```
03:18:48.465  Deal created with id 6aa4c498d51734021077f059
03:18:55.350  Trailing: will cancel 4 orders, deal: 6aa4c498…, level: 0.071676, price: 0.0724
03:18:57.349  Сlose deal 6aa4c498…
```

`triggerTrailing` armed the level (03:18:55) and `closeDealById` ran two seconds
later — **and there is no `Trailing trigger mode:` line and no
`closing by stop loss` line for this deal at all**. That is the signature
§1.2 predicts: `checkDealsStopLoss` took none of its three branches, so the
trailing flag was `false` and `triggerStopLoss` was handed
`DCACloseTriggerEnum.sl`. It distinguishes "the arm ran and evaluated false"
from "the path never ran".

(`Trailing trigger mode: TTP` lines *do* appear in the same logs — e.g. bot
`698b09afca48235021e58fa7` — but every such bot has `trailingSl: true` and
`useSl: true`, i.e. the log came from the **stop-loss** arm of the same `||`;
the message merely prints `deal.trailingMode`.)

### 2.3 Onset dates the regression exactly

Same `dcadeals` cohort as §2.1, by month, `trailing` vs `sl`:

```
2025-05 trailing 1577   2025-10 trailing 2563 / sl 1076
2025-06 trailing 1655   2025-11 sl 3729
2025-07 trailing 2956   2025-12 sl 1499
2025-08 trailing 2474   …
2025-09 trailing 2593   2026-09 sl 1508
```

By day, the cutover is inside **2025-10-22** (`trailing 38` then `sl 94`, and
nothing but `sl` after). Before it the cohort was 100% `trailing`; after it,
100% `sl`.

`git blame` puts `let trailing = false` on that same date, commit
**`9092ca79`** — "v1.4.14: Fixed — Market TP wrong trigger when having SL and
multicoin". Before it, `triggerStopLoss` passed
`DCACloseTriggerEnum.trailing` unconditionally, so a trailing take-profit was
labelled correctly *by accident* (and a genuine stop loss was labelled
`trailing`, which is what `9092ca79` set out to fix). `9092ca79` made the label
conditional on a predicate that had been dead since `ea9b1c93` (2025-07-02),
which is where `!multiTp` was written.

### 2.4 Why the naive fix re-opens `9092ca79`'s bug

`getDealStopLossPrice` chooses which price is monitored, and its trailing arm
also requires `deal.trailingMode && deal.trailingLevel`:

```ts
((trailingSl && !useMultiSl && useSl && dealCloseConditionSL === tp) ||
 (trailingTp && useTp && dealCloseCondition === tp)) &&
  d.deal.trailingMode && d.deal.trailingLevel
    ? d.deal.trailingLevel      // trailing
    : /* … */                   // the real stop-loss level
```

`isDealForStopLoss` has the same arm. So a bot with `useSl: true`,
`trailingSl: false`, `trailingTp: true` and trailing **not yet armed** is
registered for its *real* stop-loss level, and a close there is a genuine stop
loss. Repairing only `!multiTp` → `!useMultiTp` would make the trailing arm
true for that deal too and label a real stop-loss loss `trailing` — the same
class of mislabel `9092ca79` fixed. Prod, same 7-day window: **164** deals with
`useSl: true`, `trailingSl: false`, `trailingTp: true` closed `sl` with **no**
`trailingLevel`. They must stay `sl`.

### 2.5 Re-verified independently, and the writing site pinned

Re-checked from scratch on 2026-09-12 08:30–08:45Z against live prod, on deals
chosen fresh rather than reused from §2.1–§2.2.

Read-only `dcadeals`/`dcabots`: the cohort is still producing rows — e.g. deal
`6aa504c0c5acf95100809489` (07:52Z) and `6aa5013dc5acf95100806654` (07:37Z),
both live money, both profitable, both `trailingMode: 'ttp'` with a set
`trailingLevel`, both `useMultiTp: false`, both `settings.multiTp` of
**length 0** — the materialised empty array §1.2 predicts — and both stamped
`closeTrigger: 'sl'`.

`Gainium-DCA-bot` log, same two deals, whole retained archive:

```
07:52:32.174  Deal created with id 6aa504c0c5acf95100809489
08:21:24.415  Trailing: will cancel 20 orders, deal: 6aa504c0…, level: 0.003604392, price: 0.003608
08:22:06.314  Сlose deal 6aa504c0c5acf95100809489
```

Three lines, and **no `Trailing trigger mode:` line and no `closing by stop
loss` line** for either deal. That is the §1.2 signature, and it separates *the
arm ran and evaluated false* from *the path never ran*: `Сlose deal <id>` is the
first thing `closeDealById` logs, so the path demonstrably ran.

**Which write stamps the row.** `closeDealById` is reached here only via
`triggerStopLoss`, whose sole caller is the `if (close)` at the end of
`checkDealsStopLoss` — and that call is made regardless of which branch was
taken, which is why a deal can close with `trailing` never set. `closeDealById`
then does `findDeal.deal.closeTrigger = closeTrigger` from its argument.

The other two writers of `DCACloseTriggerEnum.sl` are excluded: the
`tpOrder.sl ? sl : tp` expression in `closeDeal` is a *fallback* guarded by
`closeTrigger && closeTrigger !== base ? closeTrigger : …`, so it preserves the
value `closeDealById` already set and cannot originate it; and the remaining
site is an indicator-driven `closeAllDeals`, a different trigger that closes
every deal on a symbol at once, which is not the observed one-deal-seconds-after-
arming shape. So the label originates at exactly one expression,
`trailing ? DCACloseTriggerEnum.trailing : DCACloseTriggerEnum.sl`.

## 3. Assumption

**Hypothesis.** The label is decided in exactly one place —
`checkDealsStopLoss`'s `trailing` flag — and it is wrong for two independent
reasons:

1. The trailing-take-profit arm tests `!multiTp` (an always-present array)
   instead of `!useMultiTp` (the toggle), making the arm unreachable; and
2. the flag does not check that the level actually hit *was* the trailing
   level, which `getDealStopLossPrice` requires before it returns
   `deal.trailingLevel`.

Fixing (1) alone re-introduces `9092ca79`'s defect (§2.4); fixing both makes the
flag agree with the arm `getDealStopLossPrice` took, which is the only
authoritative statement of "this close happened at the trailing level".

Nothing upstream is implicated: `closeDealById` persists whatever it is handed
(`deal.closeTrigger = closeTrigger`, then `saveDeal`), and `closeDeal`'s later
`tpOrder.sl ? sl : tp` fallback only applies when `closeTrigger` is unset or
`base` — it never overwrites a set value.

## 4. Required behaviour

- **§4.1** A close at an armed trailing level on a trailing-take-profit bot
  (`trailingTp`, `useTp`, `dealCloseCondition: tp`, `useMultiTp: false`) is
  recorded `closeTrigger: trailing`, whatever `multiTp` contains.
- **§4.2** A close at an armed trailing level on a trailing-stop-loss bot stays
  `closeTrigger: trailing`, exactly as today.
- **§4.3** A close at a **real** stop-loss level stays `closeTrigger: sl`, even
  when the bot also has trailing take-profit enabled — i.e. when
  `deal.trailingMode` / `deal.trailingLevel` are not set. (`9092ca79`'s fix is
  preserved.)
- **§4.4** A bot that genuinely uses multi-take-profit (`useMultiTp: true`) is
  not labelled `trailing`, as today.
- **§4.5** No change to which price is monitored, when a deal closes, or what
  the close does — only to the recorded trigger.

## 5. Out of scope

- The **7,333 already-stamped rows** cannot be corrected by a code change; a
  backfill is a separate decision.
- A second, unrelated collapse in `trailing` labels for *trailing stop loss*
  bots around **2026-08-28** (≈260/day → ≈7/day) is visible in the same data and
  is **not** addressed here. It is a different cohort (`trailingSl: true`,
  `useSl: true`) and a different mechanism.
