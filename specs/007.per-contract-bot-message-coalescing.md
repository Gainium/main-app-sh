# 007 — One bot message stands in for every contract the venue refuses

Issue #643 (`DCA-bot: one bot re-sends an order the venue permanently refuses`).

Scope note: the issue as reported has two halves. The half about *which pair a
message names* — a message labelled with `settings.pair[0]` instead of the pair
that failed — is a different defect with a different cause, already fixed in
main-app (`2.88.12`, `MainBot.handleErrors` dropped core's `symbol` argument) and
awaiting deploy; §2.3 below re-proves it and shows it is not this one. This spec
is about what remains once that fix is live: the message row itself cannot
represent more than one contract per bot.

## §1 Definition

`Agreement required` is the subType for a venue refusing an order because the
account has not signed the agreement that contract requires ("You must sign the
required agreement before trading this contract."). Signing is **per contract**:
signing for `MSTRUSDT` does nothing for `SNOWUSDT`.

### §1.1 Expected

- §1.1.1 A bot blocked on two contracts at the same time produces **two**
  messages, one naming each contract — the user has two agreements to sign and
  needs to be told both.
- §1.1.2 Each contract's first refusal raises its own user notification. The
  re-raise cooldown that stops a *repeat* of the same condition must not swallow
  the *first* report of a different contract.
- §1.1.3 Nothing changes for subTypes whose condition belongs to the bot or the
  account rather than to one contract (a revoked API key, a plan limit). Those
  keep exactly one row per bot per window.

### §1.2 Actual

`processError` (`core/src/bot/main.ts` ~2470–2560) coalesces on

```
{ userId, botId, subType, showUser, bucket }
```

with no `symbol`, and the re-raise cooldown on `[botId, subType]`, also with no
`symbol` — even though the same function already keys the *terminal* cooldown on
`[userId, subType, symbol]` for exactly this reason. `symbol` is `$set` on every
occurrence (`onEvery`), so:

- §1.2.1 Every contract a bot is blocked on shares ONE row. Its `symbol` is
  whichever contract failed most recently — last writer wins — so the row names
  one of N blocked contracts and silently re-labels itself as the others fail.
- §1.2.2 The row's policy is `once` (the default for a visible subType), so
  `firstOccurrence` is true exactly once in the row's life. Every later contract
  is folded in as a `count` increment and raises **no** notification at all.
- §1.2.3 Independently of the row, the first contract's refusal opens a
  `[botId, subType]` cooldown, so a *second* contract's first refusal is
  suppressed into the hidden lane (`showUser:false`) instead of being reported.

## §2 Evidence

Read-only against production, 2026-09-04.

### §2.1 The reported bot is blocked on many contracts, concurrently

Bot `6a68b12a4d587ad420559315` (`Long Future Snipper`, dca, `bybitLinear`,
user `66d6bf5becb6591c9ded5b26`). Taking the 1,535 distinct `clientOrderId`s that
appear on an `Agreement required` log line in the retained DCA-bot logs and
resolving each against `orders`, the refusals cover **20 (bot, contract) windows
over 21 distinct contracts** — Bybit TradFi/stock perps such as `HYUNDAIUSDT`,
`NFLXUSDT`, `MSTRUSDT`, `SNOWUSDT`, `SKHYNIXUSDT`, `AMCUSDT` — and **16 of the 20
windows overlap another**. On 2026-08-18/19 six contracts (`KORUUSDT`,
`CBRSUSDT`, `NFLXUSDT`, `FWDIUSDT`, `BOTUSDT`, `MVLLUSDT`) were being refused at
the same time.

### §2.2 They all share one row

```
db.botmessages.aggregate([{$match:{subType:'Agreement required'}},
  {$group:{_id:'$userId', bots:{$addToSet:'$botId'}, ...}}])
```

returns 4 users / 7 bots platform-wide. For the reported bot there is exactly one
live visible row:

```
_id      6a999b82289a7bb5831f9a96   bucket 0   showUser true
subType  'Agreement required'       count  75   isDeleted false
firstTime 2026-09-03T16:08:34Z      time   2026-09-04T14:50:28Z
symbol   'USELESSUSDT'
```

75 refusals across at least two contracts, one row, one `symbol`, and — because
`count` passed 1 on the second occurrence — one notification ever.

### §2.3 The wrong *name* on that row is the other, already-fixed defect

The row's `fullMessage` names order `D-BO-IEpW7m0LVevKCnP0jPhbTAH0cNvCJj`;
`orders` gives that order `symbol: 'MSTRUSDT'`. The row says `USELESSUSDT`, which
is `dcabots.settings.pair[0]` — the fallback. Driving the real chain
(`handleOrderErrors` → main-app `handleErrors` override → core `handleErrors` →
main-app `processError` override → core `processError`) off the prototype:

- with main-app at `96cf20e^` (what production runs): `_symbol` arrives
  `undefined`, resolved symbol `USELESSUSDT`.
- with main-app at `master`: resolved symbol `MSTRUSDT`.

So the mislabelling is fixed and pending deploy, and everything in §1.2 is what
is left after it lands.

## §3 Assumption

Root cause: the coalescing key and the re-raise cooldown key in `processError`
describe the *bot*, while `Agreement required` describes a *contract*. Widening
both keys by `symbol` for the subTypes whose condition is per-contract — and only
those — makes one row and one notification per blocked contract, and leaves every
other subType's row count exactly as it is.

Corollary the fix must respect: `botMessageCoalesceKey`
(`core/src/db/schema.ts`) is UNIQUE on the un-widened key, so a second row that
differs only by `symbol` cannot be inserted until the index carries `symbol` too.
