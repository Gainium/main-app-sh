# 268 — A combo close sells the base an unsettled grid exit already sold

Bug spec (Definition / Evidence / Assumption). Tests:
`src/bot/comboCloseUnsettledExit.spec.ts`.

## §1 Definition

A combo deal's take-profit (or stop-loss / manual close) runs
`closeDealById`: the close sweep cancels every order of the deal, then
`prepareTpOrder` sizes the close off the deal ledger (`updateDealBalances`),
which counts only `FILLED` / `CANCELED` rows.

**Expected.**

- §1.1 The close sells only what the deal still holds. A grid exit that
  filled at the moment the close started is booked before the close is sized,
  or its executed base is taken off the close.
- §1.2 On a one-way futures account the close therefore never takes base
  from sibling deals sharing the position, and a LONG deal never closes with
  negative base.

**Unchanged (§4.4).** Take-profit / stop-loss triggers, the close price and
the order type stay the same. A close whose sweep leaves no closing-side order
of the deal resting is prepared exactly as before, with no wait. DCA (non-combo)
closes are untouched.

**Actual.** A grid SELL that filled ~40 ms after the take-profit triggered
was answered "order not found" by the sweep's cancel. The venue read-back
(`_runUnknownOrderLadder`) said `PARTIALLY_FILLED`, so the row was put back
as resting and the ladder returned `null`. The ledger left it out, and the
close was sized for the base before that exit (39 instead of 19). The stream's
`FILLED 20` arrived ~1.2 s later, after the close had been sent and filled. The
deal closed with base −20, and the extra 20 came out of a sibling deal's share
of the position.

## §2 Evidence (prod, read-only, 2026-11-25)

Combo worker log, Kraken Futures LONG combo, three sibling deals with
identical fills (base 19 + DCA 20 + DCA 20, one earlier grid SELL 20). Each
had a last grid SELL 20 resting at 0.3094–0.3095, and each was closed by
take profit at 22:54:30.230Z:

## §3 Assumption (root cause)

- §3.1 Nothing between the sweep and `prepareTpOrder` looks at closing-side
  rows the sweep left resting. A `PARTIALLY_FILLED` read-back is not terminal,
  so `cancelAllOrder` does not return it and the ledger does not count it.
  Its base is sold a second time whenever the stream's final report arrives
  after sizing. Spec `250` covered the opposite order (stream first, lagging
  read-back second). This is the read-back arriving first.

## §4 Requirements

- §4.1 After the sweep, a combo close finds the deal's own closing-side rows
  (`SELL` for a long, `BUY` for a short) still `NEW` / `PARTIALLY_FILLED`.
- §4.2 If there are any, it waits (bounded: 5 s, polled every 200 ms) for
  them to settle, so the fill path books the stream's report before sizing.
- §4.3 Rows still unsettled after the wait have the base the venue reported
  executed on them deducted from the close (floored to the base precision,
  never below 0). This is a cap, so it can only close less. Coin-margined
  accounts are not deducted (their figures convert through a price).
- §4.4 Unchanged, as in §1.

## Invariants

- `deals.combo-futures-long-closed-negative-base` (main-app pack
  `specs/invariants/deals.invariants.json`, observe): a futures LONG combo
  deal closed in the last 7 days with `currentBalances.base` below 0. The
  close sold more than the deal held. Scoped to futures because spot hits have
  other causes (fee dust).
