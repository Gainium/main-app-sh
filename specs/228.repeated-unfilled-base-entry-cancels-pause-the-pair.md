# 228 — base orders the venue keeps cancelling unfilled re-open a deal forever, silently

Bug spec. Follows the cancelled-entry check of `263de26`/`f4416a9` and specs
`203`, `205`, `227`, which cancel the deal. This spec is about what happens
after that.

## 1. Definition

### 1.1 Expected

When the venue cancels a deal's base order with nothing filled, the deal is
cancelled (specs 203/205/227, unchanged). When that keeps happening on the
same pair, the bot stops sending the same order: after
`refusedBaseEntryPauseAfter` consecutive unfilled cancels on one bot and pair,
automatic new deals on that pair are paused for a window that grows with each
further refusal, and the user is told once, in a bot message, that the pair
could not be entered and why that usually happens. A base order that fills
ends the run.

### 1.2 Actual

`cancelDealOfCanceledBaseEntry` cancels the deal and returns. Nothing counts the
refusals, so the start loop opens the next deal on its next pass (about every
85 s for an ASAP bot), the venue cancels that one too, and so on with no end.
The only trace is info-level log lines. The user sees no message, and the bot
looks like it is running.

## 2. Evidence

Production, a Bitget spot DCA bot with a MARKET entry on a pair with no
trading volume:

- Each cycle logs `Create new deal` → `Send base order` → `Processing msg …
  NEW` → `Processing msg … CANCELED, base: 0` → `was canceled on the exchange
  with nothing filled, not by the bot. Checking the deal in 15s` → 15 s later
  `Cancelling the deal` → `Open new deal <pair>` again. More than a thousand
  such deals in two days and no bot message.
- Bitget's public symbol config for the pair has `buyLimitPriceRatio: 0.2`.
  Its book showed the best ask more than 50 % above the last price with zero
  24 h volume, so a market buy cannot fill inside the venue's price band, and
  the venue cancels it.

Harness `refusedBaseEntryPause.harness.spec.ts` drives the real
`cancelDealOfCanceledBaseEntry` and the new-deal gate of the DCA and the Combo
helper. Before the fix §4.1 and §4.2 fail: nothing is reported or gated.

## 3. Assumption

The cancelled-entry check is the one place every route (queue report,
placement reply, reconnect check, reposition tick) ends when it cancels a
deal for an unfilled venue cancel. Counting there counts every refusal once.
Counting belongs in `RetryBackoff` (Redis, shared across workers, exponential,
fail-open), the mechanism every other "the venue keeps saying no" gate uses.
The message belongs in the per-pair standing-condition latch (spec 008), so
it is sent once per run, not once per refusal.

## 4. Required behaviour

- §4.1 After `refusedBaseEntryPauseAfter` consecutive unfilled venue cancels on
  one bot and pair, the bot reports one per-pair warning naming the pair and
  the pause, and automatic new deals on that pair are refused until the window
  ends. Further refusals inside the run do not report again (DCA and Combo).
- §4.2 Fewer refusals than the threshold pause nothing and report nothing.
- §4.3 A manual "+ New deal" and a terminal deal are not paused.
- §4.4 A filled base order on the pair ends the run: the count, the pause and
  the latch are cleared.
- §4.5 Other pairs of the same bot are not paused.
- Not changed: a base order that partly filled before the cancel still opens
  the deal on what filled; which deals the cancelled-entry check cancels.
