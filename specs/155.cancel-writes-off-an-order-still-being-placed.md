# 155 — A cancel writes off an order that is still being placed

Bug spec (Definition / Evidence / Assumption). Narrows spec `154` §5: the
`'-1'` orders it left open were not lost responses, they were in flight.

## §1 Definition

- **§1.1 Expected.** When the bot cancels an order whose placement request is
  still waiting for the venue's answer, it waits for that answer. If the venue
  accepted the order, the cancel goes to the venue under the id it returned.
  Only an order the venue refused (or never answered for) is retired locally
  without a venue call, as spec `011` already does.
- **§1.2 Actual.** On the venues addressed by exchange order id (Coinbase,
  Kraken, KuCoin full futures) the cancel reads the `'-1'` placeholder as
  "never reached the venue" and writes the order off at once (CANCELED, dropped
  from the order map and from `SharedStream`). The placement reply lands a few
  hundred ms later, is saved as CANCELED because the local row already says so,
  and nothing cancels the order on the venue. Its stream events no longer reach
  the bot, so when it fills, the deal never sees the fill.
- **§1.3 Actual (late reply).** A placement reply for an order that was already
  retired locally without a venue cancel is saved and otherwise ignored, whether
  the venue says it is open or already filled.
- **§1.4 Actual (log).** The unknown-order ladder's write-off line always reads
  `after 5 attempts 2000 ms`, also on the `'-1'` fast path that asked nothing and
  waited for nothing.

## §2 Evidence (prod logs, Coinbase DCA bots)

- 21:38:45.303Z `base order remainder: resting the other 229.15 of 293.17 as a
  LIMIT` → `addDealFunds` → `sendOrderToExchange(D-ROA-gw7T…)`.

- The Coinbase user stream reports the order OPEN at 21:38:45.894Z and FILLED at

## §3 Assumption (hypothesis)

- **§3.1** Nothing records that a placement request is outstanding, so the
  cancel path cannot tell "still being placed" from "never placed".
- **§3.2** The spec `154` open-orders lookup does not close the gap: at the
  moment of the cancel the venue may not list the order yet (HIGH was listed
  OPEN 232 ms after the write-off).

## §4 Required behaviour

- **§4.1** While the venue call of a placement is outstanding, the bot keeps a
  per-client-order-id handle that resolves to the venue's order id (or nothing
  on refusal / failure). It covers the venue call only, never the
  post-processing, so a waiter cannot deadlock on a lock the placement takes
  afterwards.
- **§4.2** `cancelOrderOnExchange` on a `'-1'` order with a placement in flight
  waits for it. On an id, it records it on the order and cancels on the venue
  under that id. On nothing, spec `011`/`154` behaviour is unchanged.
- **§4.3** The unknown-order ladder does the same before its "no exchange id"
  fast path.
- **§4.4** A placement reply for an order already retired locally as CANCELED
  while it still had no exchange id: if the venue says it is open, the bot
  cancels it on the venue by its real id; if the venue says it has fills, the
  bot logs an error naming the order, the deal and the filled quantity. The
  local row gains the real id either way; its status is the existing merge of
  the local and venue status (CANCELED, or FILLED when the venue says so).
  This also covers a placement re-sent after a balance refusal (Coinbase
  retries those) that the cancel had already retired.
- **§4.5** The ladder's write-off line states how many lookups were actually
  made, and does not claim a wait it did not make.
- **§4.6** Unchanged: how the remainder of a part-filled base order is placed
  or priced; placements with no cancel racing them; other venues' cancels of
  orders that hold a real id.

## §5 Open questions

- A user-stream event for an order retired this way does not reach the bot at
  all (`deleteOrder` unregisters it from `SharedStream`), so §4.4 is the only
  point where the bot hears about it. Not changed here.
- The four orders in §2 filled on the venue while booked CANCELED. Re-booking
  them is a data change, out of scope for a code fix.
