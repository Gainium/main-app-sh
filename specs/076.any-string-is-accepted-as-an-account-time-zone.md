# 076 — Any string is accepted as an account time zone

Bug spec.

## 1. Definition

### 1.1 Expected

An account's `timezone` is the canonical day boundary the backend buckets a
user's profit history by (`getTimezoneOffset` / `getWeek` in
`core/src/utils/index.ts`, consumed by the profit-by-day and profit-by-week
resolvers). A mutation that sets it must accept only a zone the runtime can
resolve, and refuse anything else with `status: notok` so the caller can show
the refusal.

The signup path already holds that line: `createOrUpdateUser`
(`core/src/graphql/handlers/user.ts`) tests the incoming zone with
`Intl.DateTimeFormat` and falls back to `UTC` when it throws. An unset or
empty zone stays accepted — "never chosen" is a valid state, and both
dashboards already treat it that way.

### 1.2 Actual

The two mutations that let a signed-in user *change* the field write whatever
string arrives:

- `setTimezone` (`core/src/graphql/resolvers.ts`) — destructures
  `input.timezone` and hands it straight to `userDb.updateData`, then returns
  `status: ok, reason: 'Timezone saved'`.
- `userSettings` (same file) — `if (timezone) { $set.timezone = timezone }`,
  then the same unconditional write.

Neither resolves the zone first. A value the runtime cannot resolve is stored
as the account's day boundary and reported back to the caller as saved.

## 2. Evidence

### 2.1 The stored field really does hold unresolvable values

Read over the read-only production key. Of the distinct non-empty
`users.timezone` values in use, three are rejected by
`Intl.DateTimeFormat` — a country name, a UTC-offset label, and an
`Area/city` pair whose city does not exist:

    "United Kingdom"    "UTC: +08:00"    "Europe/austria"

None of the three can have come from signup — that path coerces to `UTC`
(§1.1) — so each arrived through a settings mutation, which is the write path
this spec is about.

### 2.2 What an unresolvable value does downstream

`getTimezoneOffset` is `moment.tz(date, timeZone).utcOffset()`. Given a zone
moment-timezone has no data for it warns on stderr and returns offset `0`:

    getTimezoneOffset('Europe/London')  →  3600000
    getTimezoneOffset('United Kingdom') →        0   (+ "no data" warning)
    getTimezoneOffset('UTC: +08:00')    →        0   (+ "no data" warning)

So the account is silently bucketed on UTC day boundaries while its settings
claim otherwise. Nothing in the API response, the UI or the bot logs says so.

### 2.3 `Intl` and `moment-timezone` agree on this field

Every distinct stored value was tested against both: the set
`moment.tz.zone(v) === null` and the set `Intl.DateTimeFormat` throws on are
**identical**. An `Intl`-based guard therefore rejects nothing the backend's
own consumers can resolve, and accepts nothing they cannot.

`Intl.supportedValuesOf('timeZone')` is *not* a usable allowlist here: it is a
canonical-id list that omits widely-stored aliases (`Asia/Calcutta`, `UTC`,
`Europe/Kiev`, every `Etc/GMT±N`), which are in live use on this field. The
`try/catch` resolve test is the correct check, and is the one both the signup
path and the dashboard already use.

## 3. Assumption

Root-cause hypothesis: there is no validation on either write path — not a
validator that is bypassed, mis-ordered, or wrong. Adding the same resolve
test the signup path uses, before the write in both resolvers, is sufficient;
no caller depends on an unresolvable zone being accepted.

Falsifiable: a test that calls each resolver with an unresolvable zone must
see `status: ok` and the raw string reaching `updateData`, and the same call
with a real IANA zone must still be written unchanged.

## 4. Scope

- **In:** refusing an unresolvable non-empty `timezone` in `setTimezone` and
  `userSettings`, and the shared predicate they use.
- **Out:** repairing the values already stored (a data change, not a code
  change); `weekStart`; the signup path's coerce-to-`UTC` behaviour, which is
  correct for a browser-detected value and stays as it is.
