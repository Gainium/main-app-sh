# 128 — A settled part-filled base entry is left out of the deal's average

Bug spec. Extends `017` (base-order qty from the position), `057`/`058`
(top-up of a settled entry), `059` (settle chain) and `125` (asynchronous
cancel).

## §1 Definition

### §1.1 Expected

When a part-filled base order is cancelled and the deal opens on what
filled, that fill is part of the deal's average entry price, and the take
profit sells what the deal actually holds.

### §1.2 Actual

The base order's row is left `CANCELED` in the orders collection with its
fill. `getAvgPrice` averages `FILLED` rows only, so once the order map is
reloaded from the DB (any worker restart) the next recompute — every safety
fill — averages the safety orders alone. `updateUsage` divides the quote the
deal really spent (base order included) by that average, so `deal.size`
over-states the position by `boQty * (boPrice / avg − 1)`. Spec `017`'s
`position` branch of `resolveBaseOrderQty` trusts `deal.size` over the base
row, and the take profit asks for more than the deal holds: the venue rejects
it ("not enough balance") and the deal has NO take profit — or, when the
account happens to hold extra coins, it sells the user's own coins.

The same under-stated average also lowers the take-profit PRICE.

## §2 Evidence

Production, Coinbase spot, LIMIT entry, 2026-10-02/03 (identifiers withheld —
this file is public):

- Deal A: base order executed 1405.4 of 1407.8 @ 0.0711, settled 12:31:49Z
  ("remainder 2.4 … below the exchange minimum"). Orders collection: the row
  is `CANCELED`, `executedQty 1405.4`. Six safety fills 3277.2 for 224.461.
  Deal: `avgPrice 0.068492` = 224.461 / 3277.2 exactly; `cost 324.385`;
  `size 4736.12`; `currentBalances.base 4682.6`. Log 21:58Z, 22:01Z, 04:41Z:
  "holds more than its order rows account for — base order qty 1458.9 taken
  from the position, not the 1405.4 on record", then "not enough balance"
  (requires 4731.3, free 4684.4).
- Deal B (another pair, same bot owner): base `CANCELED` 2006.6 @ 0.0323;
  stored `avgPrice` equals the FILLED-only average to 15 digits; `size 13438.8`
  against `currentBalances.base 13347.7`. Including the base row gives
  `cost / avg = 13347.700000000004`.
- The only `force` writes of an order row in the bot are FILLED promotions
  (`promoteEndedBaseEntry`, `topUpSettledBaseEntry`). A row left `CANCELED`
  therefore means no forced promotion ran: the settle took the branch where
  `cancelOrderOnExchange` itself answered `FILLED` (it promotes a
  CANCELED-with-fills answer), whose write is the default, unforced one — and
  the venue's own `CANCELED` event had already made the row terminal, so the
  filter refused it.

## §3 Assumption (hypothesis)

1. `settlePartialBaseEntryNow`'s `settled.status === 'FILLED'` branch books the
   row without persisting the promotion with `force`, unlike every other way
   that method ends (spec `059` §4.3 names this race for the other branch).
2. `getAvgPrice` disagrees with the deal's own ledgers about which rows are
   the deal's entry: `findBaseOrderByDeal`, `updateUsage` and
   `updateDealBalances` all count a `CANCELED` base row's fill; `getAvgPrice`
   does not. Deals already written in this state are only repaired by the
   reader.

## §4 Required behaviour

### §4.1 Persist the promotion

A settle whose cancel answer is `FILLED` writes the row `FILLED` with `force`,
the same as the other settle branches.

### §4.2 Average what the deal entered

`getAvgPrice` counts a base-order (`dealStart`) row that ended `CANCELED` with
a non-zero fill at its executed quantity and price — on spot and futures —
the same rows `findBaseOrderByDeal` counts. A `CANCELED` base row with no fill
contributes nothing.

### §4.3 Never size a close above what the deal holds

In `resolveBaseOrderQty`'s `position` branch the quantity derived from
`deal.size` is capped at the gross entry the deal's base ledger records
(`currentBalances.base` plus what it has already closed), for spot long deals
— the only case where `deal.size` is derived through the average. The cap
never takes the result below the base row (spec `017`'s one-way rule), and
when the ledger agrees with `deal.size` (spec `017`'s missing-rows case) the
`position` result is unchanged.

### §4.4 Effect on spec `058`'s tests

`baseEntryTopUp.harness.spec.ts` counted every `updateOrderOnDb` call in the
settle chain, the settler's included, because the settler's own write was the
stubbed `cancelOrderOnExchange`'s. §4.1 adds one forced write there, so the
two 058 cases now pin 058's actual rule separately: the top-up writes nothing
when it recovered nothing (§4.3), and the merged row is written, forced,
before the deal opens (§4.2).

## §5 Out of scope

- Re-sizing live orders on deals already affected. §4.2 corrects their average
  and size at the next recompute (next safety fill or usage update); no data
  migration is part of this change.
- `settleBaseEntryRemainderOrder` has the same unforced `FILLED` branch, but a
  remainder fill is booked into `deal.funds`, not averaged from its row.
