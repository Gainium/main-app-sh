# 129 — A restore recomputes the average of a deal holding a settled base entry

Bug spec. Follow-up to `128` (a settled part-filled base entry left out of the
average). Extends `125` §4.4 (restore reads a cancelled entry row the order
book does not hold).

## §1 Definition

### §1.1 Expected

An open DCA deal whose base order ended `CANCELED` with a fill carries an
average entry price (`avgPrice`, `settings.avgPrice`, `displayAvg`) and a
`size` that include that fill. The take profit is then priced and sized from
what the deal really entered.

### §1.2 Actual

Spec `128` §4.2 taught `getAvgPrice` to count such a row, but `getAvgPrice`
only runs on a base fill, a safety fill or an add-funds fill. A deal whose
average was written BEFORE that change keeps the safety-only average in the
database, and every restart restores it as stored. Nothing recomputes it, so
the deal stays under-averaged until its next safety order fills, which may
never happen. Until then:

- its take profit is priced from the low average, so it sells closer to the
  entry than the configured TP%, and can sell below the real entry after fees;
- `deal.size` (quote spent / average) over-states the position. `128` §4.3
  caps the take-profit QUANTITY at the base ledger, but the stored size, cost
  view and anything else that reads the average stay wrong.

## §2 Evidence

Production, read-only, 2026-10-03. Identifiers are withheld because this file
is public.

- Coinbase spot, LIMIT entry. The base row is `CANCELED`, `executedQty 1405.4`
  @ 0.0711. Six safety fills total 3277.2 base for 224.461 quote. The deal
  stores `avgPrice` = `settings.avgPrice` = 0.06849175515684121, which is
  224.461 / 3277.2, the safety fills alone. `size` is 4736.12 against
  `currentBalances.base` 4682.6. The true average is 324.385 / 4682.6 =
  0.06927457. Every take-profit row on the deal is `CANCELED`, so the next one
  is placed from whatever average the deal then holds.
- Fleet sizing (triage, read-only): 16 of 32,540 open live DCA deals hold a
  `CANCELED` part-filled base row. 4 store the safety-only average. 12 are
  already within 0.015% of the recomputed one.
- The DCA order loader's `$or` already loads a `CANCELED` `dealStart`/
  `dealRegular` row with a fill for open deals (`dcaHelper.loadOrders`). The
  premise that "the DB load path never loads the CANCELED base row" is false
  for the DB path. The Redis-snapshot path returns the snapshot plus open
  rows only, so whether the row is present there depends on whether the
  process that wrote the snapshot still held it.

## §3 Assumption (hypothesis)

1. The stored average is never recomputed on restore; only fills recompute it.
2. On the Redis-snapshot path the cancelled base row can be absent from the
   order map, so a recompute from memory alone could miss it.

## §4 Required behaviour

### §4.1 Recompute once on restore

`restoreWork`, for each open (non-split) deal, on a service restart AND on a
user start/reload: when the deal's order map holds a `dealStart` row that is
`CANCELED` with a non-zero fill, recompute `getAvgPrice`. When it differs
from the stored value, write `avgPrice`, `displayAvg` and `settings.avgPrice`,
recompute usage/size (`updateUsage`, without alerts), and rebuild the deal's
`currentOrders` from the new average so any later placement prices the take
profit from it.

### §4.2 Read the row when the order map has none

When the order map holds NO `dealStart` row with a fill for the deal (neither
`FILLED` nor `CANCELED`), read the deal's `CANCELED` `dealStart` rows from the
orders collection once. Put any with a fill into the order map, as `125`
§4.4 does for a deal in `start`, then apply §4.1. A deal whose map already
holds a `FILLED` base row costs no read.

### §4.3 Inert everywhere else

A deal with no cancelled-with-fill base row is untouched: no read beyond
§4.2, no write, no recompute. A recompute equal to the stored average writes
nothing.

### §4.4 Places nothing by itself

The step sends and cancels no order. A resting take profit is not re-priced
on a service restart. Deploying this must not trade on an account by itself;
`checkTpCoverage` follows the same rule. The corrected `currentOrders` are
used by the placements `restoreWork` already makes (the user-start branch
cancels the book and re-places it; a keep-orders reload places a take profit
only when none is resting) and by the next fill.

## §5 Out of scope

- Re-pricing a take profit that is resting at the stale price on a service
  restart (§4.4).
- Combo bots, whose `restoreWork` is an override.
