# 201 — A venue cancel-all leaves a grid bot trading nothing

Grid bot · `core/src/bot/helper.ts` · user-stream `CANCELED` of a grid level

## 1. Definition

### 1.1 Expected

A grid level (`TypeOrderEnum.regular`) that had been resting on the book and
is then cancelled on the venue without the bot asking (the venue's own
cancel-all, or the user cancelling it on the exchange) is a level the ladder
still wants. If it is still in the bot's current ladder (`grids`) and the bot
is running, the bot places it again within seconds. A burst of such cancels
is placed back in one pass, not one pass per cancel.

### 1.2 Actual

The grid bot registers no `onCanceled` callback (`cbFunctions` has only
`sort`, `onFilled` and `onLiquidation`). `processOrderQueue` writes the
cancelled order down and drops it from the live-order index, and nothing
else happens. The ladder in memory still lists every level, `levels.active`
still counts them, and no order rests. Nothing reacts until a fill (there is
none to come) or a service restart (`checkOrders` → "Send order again").
The bot looks running on the dashboard and trades nothing.

## 2. Evidence

Production, Bybit grid bot (Gainium-Grid-bot log, 2026-10-25):

- `00:44:30Z`: 78 `Processing msg … CANCELED` lines for the bot's resting
  BUY levels, venue times within the same millisecond. A sibling bot on the
  same account lost 55 orders in the same millisecond, i.e. an account-wide
  cancel on the venue.
- No placement for the bot after that, until the user closed it at `21:42Z`.
- Sentinel invariant `grid.open-bot-nothing-resting`: the bot document read
  `status: open`, `levels.active: {buy: 78, sell: 0}`, with no `NEW` /
  `PARTIALLY_FILLED` LIMIT order in `orders`.

Code path: `main.ts` `processOrderQueue` calls `onCanceled` only when one is
registered; `helper.ts` constructor registers none.

## 3. Assumption (hypothesis)

The grid bot has no reaction to a venue cancel at all, so any level cancelled
outside the bot is lost until a restart. The order already carries what is
needed to react correctly: `isOwnCancel` (spec 095) separates the bot's own
cancels, and `transactTime` vs `updateTime` (spec 179's
`wasRestingWhenCanceled`) separates a level that rested from an order the venue
refused at placement.

## 4. The fix, and what it must not break

### 4.1 A rested level cancelled on the venue is placed again

The grid bot registers `onCanceled`. For a `regular` grid order that
- the bot did not cancel itself (`isOwnCancel` false),
- had rested (`wasRestingWhenCanceled`, the spec 179 rule: cancel report at
  least 60 s after placement), and
- executed nothing (a part-filled cancel is out of scope, unchanged),

the order is queued for re-placement and the re-placement pass is scheduled.

### 4.2 One pass per burst

Scheduling is debounced per bot (`@RunWithDelay`, 2 s of quiet), so a burst of
78 cancels in one millisecond runs one pass. The pass runs under the same
per-bot mutex as `limitOrders`, so it never interleaves with a ladder rebuild.
For each queued order it places the level again through the path `checkOrders`
uses on a restart: `placeRegularOrder(mapOrderToGrid(o))`, under a fresh
client order id. A level filled during placement goes to `processFilledOrder`,
as in `limitOrders`.

The pass skips a queued order when
- the bot is not `open`/`range`, or is stopping (`blockLimit`);
- its level (side, price, quantity) is no longer in the current ladder
  (`grids`), e.g. a fill rebuilt the ladder meanwhile;
- a live order already rests at that level (`placeRegularOrder`'s own
  `isOrderExist` check).

### 4.3 Unchanged

- The bot's own cancels (ladder rebuild, stop, close) are not re-placed.
- An order refused by the venue at placement (cancel report less than 60 s
  after placement, or no timestamps) is not retried.
- Non-`regular` orders (TP/SL `stop`, `swap`, `fee`) are untouched.
