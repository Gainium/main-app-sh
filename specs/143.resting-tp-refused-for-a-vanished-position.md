# 143 — A futures resting take-profit refused for a position the venue no longer holds

Bug spec.

## §1 Definition

- §1.1 **Expected.** When the venue refuses a futures deal's resting (limit)
  take-profit as un-reducible — the `Futures position` subType, e.g. Kraken's
  `wouldNotReducePosition` — and the venue reports no position for the deal,
  the user is told, on that deal, that the exchange holds no position for it
  and that they should check the exchange and close the deal by hand. The bot
  stops re-sending the identical take-profit on every pass and only retries it
  occasionally.
- §1.2 **Actual.** `placeOrdersHoldingDealLock` sends the take-profit through
  the plain `sendGridToExchange` branch. The refusal is reported by
  `sendOrderToExchange` through `handleOrderErrors`, and `Futures position` is
  `showUser: false, errorsBot: false`, so nothing reaches the user. Every
  later pass over the deal (worker start, user-stream reconnect, orders check)
  sends the same order and gets the same answer, for as long as the deal stays
  open — indefinitely, since nothing else moves it.
- §1.3 **Unchanged.** The deal is never closed by this path and no profit is
  booked for it. Every other refusal, including the rest of the
  `Futures position` group, is reported exactly as today and stays as hidden
  as its subType says. Spot deals, market closes (`checkTPLevel`,
  `closeDealById`) and deals whose position the venue still reports behave as
  today.

## §2 Evidence

- §2.1 Connector log: a LONG BTC-USD deal on a Kraken futures account, its
  take-profit `SELL 0.003 @ 70577`, `LIMIT`, `reduceOnly: true`, refused
  `wouldNotReducePosition` on every pass for weeks, with a sibling deal on the
  same account in the same state. Bot log for the same order:
  `[WARN] … Reason wouldNotReducePosition Method limitOrders() Step Send new
  order request D-TP-…` — the `sendOrderToExchange` tail.
- §2.2 The account's open positions on the venue: `status OK`, empty. Both
  deals are `open` in our records, and the bot's event log for both bots holds
  nothing but restarts.

## §3 Assumption

- §3.1 (hypothesis) The resting take-profit path has no position check behind
  a `Futures position` refusal and no backoff, and the refusal's subType hides
  it. A harness test over the real `placeOrdersHoldingDealLock` fails today:
  with the venue refusing and reporting no position, the position is never
  read, no deal event is written, and three passes send three orders.

## §4 Required behaviour

- §4.1 Only a futures `dealTP` sent from `placeOrdersHoldingDealLock` whose
  refusal classifies as `Futures position` (and is not the leverage case
  `handleErrors` already exempts) triggers a position read.
- §4.2 The read reuses `reconcileDealAgainstVenue`. A position still held, or
  a venue that does not answer, changes nothing: the take-profit is retried as
  today, and an answered "held" clears any open window.
- §4.3 "No position" opens or widens a per-deal backoff (15 min doubling to
  6 h, remembered for a day). While it is open the take-profit is not sent.
- §4.4 The first refusal of an episode writes one deal-scoped warning event
  (`event: 'Deal'`, `deal`, `symbol`, `type: warning`). Later refusals in the
  same episode write none.
- §4.5 The refusal itself is still reported through `handleOrderErrors` as the
  `sendOrderToExchange` tail would have (`limitOrders()`, same flags, nothing
  while the account's auth cooldown is being replayed).
- §4.6 A take-profit the venue accepts ends the episode.
