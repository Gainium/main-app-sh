# 027 — `placeOrders` reads an underfilled take-profit as a close and sweeps the deal's safety orders

Issue #718 (spun off from #717 ledger note F216). Same deal as `026` and `006`:
B3-USDC `6a90e161a76e7fe63ea3118f`, bot `6a8b89e98e06bef801add796`, reporter
`6a8b1db88e06bef801d752bd`, Coinbase spot, long.

Read off production 2026-09-09, not inferred.

---

## §1 — Definition

### §1.1 Expected

A `dealTP` row the venue reports `FILLED` means "the deal closed on its take
profit" **only when the whole order actually sold**. `checkFilledTp` already
encodes exactly that: since core 1.56.3 it refuses to close a deal on a TP whose
`executedQty` falls more than `PARTIAL_TP_TOLERANCE` short of its `origQty`
(`dcaHelper.ts:11014`, `underfilledTpQty(tp) > 0`).

`placeOrders` ends with the same question asked for a different purpose — "did
this deal close while we were placing orders, and should the ladder therefore be
pulled?" It must answer it the same way. A deal that `checkFilledTp` has
deliberately kept **open** still has a live position, and its safety orders are
what that position is being averaged with. They must be left standing.

### §1.2 Actual

`placeOrders`' closing-detection (`dcaHelper.ts:13976-13979`) takes *any*
`FILLED` `dealTP` for the deal as proof of a close:

```ts
const tpAfter = this.getOrdersByStatusAndDealId({ dealId, status: 'FILLED' })
  .find((o) => o.typeOrder === TypeOrderEnum.dealTP && !o.reduceFundsId)
```

and on that basis cancels every resting `dealRegular` / `dealGrid` order on the
deal. It carries no partial-fill guard, so the two paths reach opposite verdicts
about the same order on the same pass: `checkFilledTp` leaves the deal open,
`placeOrders` strips it bare. The deal is left holding an open position with no
take-profit and no safety orders, indefinitely, and nothing in the UI says so.

This is not a regression — the block dates to the first public release. It only
became reachable when 1.56.3 stopped the deal being closed outright, which is
what turns "close on a 6% fill" (bug #696) into "stay open, unprotected".

## §3 — Assumption (hypothesis, not fact)

The closing-detection at `dcaHelper.ts:13980-13982` is missing the partial-fill
guard that `checkFilledTp` gained at `:11014`. Adding
`this.underfilledTpQty(tpAfter) <= 0` to the `tpAfter` disjunct — and **only**
to that disjunct, leaving the `dealAfter.status === closed` disjunct alone, since
a genuinely closed deal must still have its ladder pulled — stops the sweep
without changing any other behaviour.

Gate 2's test must fail because the safety orders are cancelled on an underfilled
TP, and must keep passing for a fully-filled TP and for a genuinely closed deal.

### §3.1 Explicitly NOT claimed by this spec

- **The take-profit is not re-armed by this change.** The cancel branch never
  touched `dealTP` rows (`toCancel` filters `dealRegular`/`dealGrid` only), so
  the missing TP has a different cause. Confirmed live: the replacement TP
  `D-TP-FkkxB3CRNXDceQyJrM1oXzuAOLNVrq` is rejected by the venue —
  `Not enough balance … balance total - 935356 B3, free - 824863 B3, required -
  934119 B3` (2026-09-09T02:48:05Z). That is spec `006`/`026` territory
  (a locked-balance/sizing problem), still open, and out of scope here.
- **F217 is not fixed here.** Two further open deals on the same user,
  `6a9c6d36e93810e4ab1125bd` (FLOKI-USDC, TP `D-TP-PW32Y2…`, 0 of 686296) and
  `6a9ca65ce93810e4ab166d77` (ZRX-USDC, TP `D-TP-137EO6…`, 0 of 237.37538), carry
  a `dealTP` persisted `FILLED` with `executedQty: 0` **and `updateTime: null`** —
  a promotion that never received venue fill data at all. The guard added here
  covers those rows too (`underfilledTpQty` returns the full `origQty`), but the
  write-side defect that produced them is separate and remains open.
- **No prod data is rewritten.** Remedy (a) in the report — rewriting the stale
  `FILLED` row back to `CANCELED` — is an irreversible prod transform and is not
  attempted.
