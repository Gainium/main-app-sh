# 241 — A refused first entry leaves the deal open, holding nothing

Bug spec.

## §1 Definition

### §1.1 Expected

When the exchange definitively refuses a DCA deal's very first order (not
enough balance, an exchange agreement not signed, missing API permissions), the
deal is cancelled right away. The user sees one refused order and one cancelled
deal. No open deal holds nothing.

### §1.2 Actual

`placeBaseOrder` creates the deal and writes its base order row ahead of the
send. When `sendOrderToExchange` returns a refusal string that no retry branch
claims, the final `else` reports it through `handleOrderErrors`, and the bot
may move to `error`. The deal itself is left in `start`. Its only order row is
`CANCELED` with `orderId: '-1'` and nothing executed, and nothing is on the
exchange. It stays like that until the hourly stuck-start sweep
(`closeOldStartDeals`) retires it, which can take up to a day. In the meantime
the dashboard shows it as an open deal.

### §1.3 Not changing

- A deal whose entry the exchange accepted, even partly.
- The automatic retries: the slippage/min-notional ladder, the limit-only
  LIMIT fallback (spec 052) and the Quantitative-Rules deferred retry, which
  re-runs `placeBaseOrder` for the same deal after a cooldown (it stamps
  `startBlocked.retryAfter` on the deal before the refusal string is returned).
- An ambiguous outcome (timeout, transport error, a placement read-back miss).
  The order may exist on the exchange, so the deal is kept.
- Terminal bots, which already `stop()` on this branch.
- Combo bots, which have their own `placeBaseOrder` and do not reach this
  branch.

## §2 Evidence

Production read on 2026-11-14 (read-only, identifiers withheld because this
file is public):

- Of the DCA deals that had been in `start` for more than 30 minutes, the large
  majority carried a `startBlocked` record ("Balance insufficient",
  "Agreement required", "API keys error"). Every one of them held only order
  rows with `orderId: '-1'` and zero executed quantity. None had
  `startBlocked.retryAfter`.
- Three sampled deals of this shape were cancelled by the sweep 5–6 h after
  creation, with no other activity between.
- The combo deal collection held no deal of this shape.

Code path: `dcaHelper.placeBaseOrder` → `sendOrderToExchange(…, true)` returns
the reason string → final `else` → `handleOrderErrors` → method returns. No
statement on that branch changes the deal.

## §3 Assumption (hypothesis)

The final refusal branch has no deal-level follow-up. The machinery to retire
this exact shape safely already exists: `retireStrandedStartDeal` (spec 046),
with its DB-side predicate and a write filtered on `status: start`. It cannot
be used at placement time for two reasons: its 24 h grace (which keeps a
placement in flight out of the sweep), and it does not touch the worker's map
or the bot's `deals.active` counter, because the sweep only reaches deals the
map has forgotten.

`closeDealById` is NOT the right path here. Its `processDealClose` calls
`restoreFromRangeOrError()`, which would put a bot the refusal just moved to
`error` straight back to `open`, hiding the error.

## §4 Required behaviour

- §4.1 `isRetirableStrandedStart` takes an optional grace. The default is
  unchanged (24 h). The order-row test is unchanged.
- §4.2 A pure `shouldRetireRefusedEntry` decides whether a refusal on this
  branch retires the deal. It returns false for an ambiguous reason, a terminal
  bot, a deal not in `start`, a deal with a scheduled retry
  (`startBlocked.retryAfter`), and a deal holding a funding hold (spec 044 beta,
  whose reservation bookkeeping this change does not touch).
- §4.3 `placeBaseOrder`, final refusal branch, after `handleOrderErrors`:
  when §4.2 says so, `retireRefusedStartDeal` runs. It calls
  `retireStrandedStartDeal` with no grace, which keeps both safety checks: every
  row `-1` with zero fill, and the `status: start` filter on the write. Only if
  that write lands does it drop the deal from the worker's map and its per-deal
  sets and timers, and decrement `deals.active`. It runs under the same per-deal
  lock as `closeDealById`.
- §4.4 An ambiguous refusal keeps the deal, unchanged.
- §4.5 A refusal while a Quantitative-Rules retry is scheduled keeps the deal.
- §4.6 If the database shows a row the venue acknowledged, the deal is kept,
  and the map and counter are left alone.
- §4.7 The bot's status is not touched: no `restoreFromRangeOrError`, no
  reopen.

## Invariants

- A non-terminal DCA deal that has been in `start` for more than 30 minutes,
  with a definitive `startBlocked` refusal and no scheduled retry, whose every
  order row has no venue id and nothing executed, should not exist.
  main-app pack `specs/invariants/deals.invariants.json`,
  `deals.refused-entry-still-start` (observe).
