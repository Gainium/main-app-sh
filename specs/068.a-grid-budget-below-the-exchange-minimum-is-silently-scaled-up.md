# 068 — A grid budget below the exchange minimum is silently scaled up

Bug spec (Definition / Evidence / Assumption). Scope: the standalone **grid
bot**. Combo minigrids share the sizing routine but are out of scope (§1.5).

## §1 Definition

A grid bot divides its **budget** across its **levels**. Every exchange also
enforces a per-order minimum (a minimum notional, a minimum quantity, and a
quantity step). When the budget is too small, the budget-derived size of one
level falls below that minimum.

### §1.1 Expected

A grid bot whose budget cannot fund every level at the exchange's per-order
minimum **refuses to start**:

- it places **no order at all** — no start (swap) order, no grid order;
- it tells the user why, naming the configured budget and the **minimum budget
  this range / level count / pair actually needs**;
- it ends in the same stopped state as every other start refusal.

The budget is the user's statement of how much the bot may commit. The engine
must never commit a multiple of it on its own initiative.

### §1.2 Actual

The engine raises every level to the exchange minimum and starts anyway. There
is no error, no warning and no bot message. The grid — and therefore the start
order that funds the sell side — is sized from the exchange minimum instead of
from the budget.

Worked example (synthetic): budget 5, 175 levels, per-order minimum 5. The
budget-derived level is ≈ 0.03; the engine raises each level to 5, so the grid
commits ≈ 875 — about 175× the budget — and the start order alone buys the
whole sell side of that inflated grid.

On spot this is usually masked: the inflated start order fails the balance
check ("Not enough quote to place swap order"). On futures the balance check
compares `required / leverage` with the free balance, so at high leverage the
inflated order passes and executes.

### §1.3 Tolerance

Step rounding legitimately moves a level's size by a fraction of a step, and
the sizing routine carries small fee/rounding factors. A start is refused only
when the minimum budget exceeds the configured budget by more than
**10 %** (`GRID_BUDGET_TOLERANCE = 0.10`). See §5 Q1.

### §1.4 Which starts are guarded

- **Guarded:** a user-initiated start of a grid bot (first start, or start
  after a stop).
- **Not guarded:** a service restart of an already-running bot. A deploy or a
  worker restart must never stop a bot that was running.
- **Not guarded:** a reload caused by a settings edit, whether or not the edit
  asks for a new start order — see §5 Q2.

### §1.5 Non-goals

- The sizing math is **not changed**. The guard observes what the sizing
  routine computed; it does not alter a single quantity. A bot that passes the
  guard is sized exactly as it is today.
- Combo minigrids call the same sizing routine with a per-deal budget. They are
  not guarded here and their behaviour must not change.
- No change to any API, GraphQL, socket or DB shape.

## §2 Evidence

### §2.1 The floor is in the sizing routine, in every branch

`MainBot.generateGridsOnPrice` (`src/bot/main.ts`) derives one level's size
from the budget and then, in each branch, overwrites it with the exchange
minimum when it is smaller:

| profit currency / order fixed in | budget-derived size | the floor that replaces it |
|---|---|---|
| quote / base | `baseAmount = budget / Σ(level prices)` (futures) or `budget / (sellCount·initialPrice + Σ buy prices)` (spot) | `if (round(baseAmount) < quoteMin / lowest) baseAmount = ceil(quoteMin / lowest)`; later `if (qty < baseMin) qty = baseMin` |
| quote / quote and base / quote | `quoteAmount = budget / (…)` | `if (quoteAmount < quoteMin) quoteAmount = quoteMin · f`; per level `if (buyQty·p < quoteMin) …`, `if (buyQty < baseMin) …` |
| base / base | `tempSellQty = budget / (…)` | `if (tempSellQty < quoteMin / firstPrice) tempSellQty = ceil(quoteMin·1.1 / firstPrice)`; `if (sellQty < baseMin) …` |
| coin-margined | `baseAmount = budget / levels` | `if (qty < baseMin) qty = baseMin` |

None of these branches logs, warns or refuses.

### §2.2 The start order is sized from the floored grid

`getQtyToSwap` (`src/bot/helper.ts`) generates the full grid through the
routine above and sums the quantity of the side that must be pre-funded. It has
no access to the pre-floor size, so the start order inherits the inflation.
`swapAssets` then checks only `required / leverage` against the free balance.

### §2.3 Nothing upstream rejects the budget

There is no minimum-budget validation on the create/start path in this repo
(GraphQL `createBot`, v2 `POST /bots/grid`, `BotInstance.createBot`). The
dashboard displays a "Min budget" hint but does not block on it.

### §2.4 Observed in the field

A futures grid at high leverage with a budget far below the per-level minimum
was observed to open a start position many times its budget, with every
subsequent grid order sized at exactly the exchange's minimum quantity. The
engine log for that start contains no warning between "Get qty to swap" and the
filled start order. (Account-level detail is held privately, not in this
repository.)

### §2.5 What the evidence does NOT establish

- Whether the affected bot was created through the dashboard form, the v2 API
  or an assistant. It does not matter for this spec: the engine must refuse
  regardless of which client built the settings.
- How many running bots are currently under-budget. §1.4 keeps them running.

## §3 Assumption (hypothesis)

The start order is oversized **because** the sizing routine replaces a
below-minimum budget-derived level size with the exchange minimum and gives its
caller no signal that it did so; and the start path has no check of its own.

If this is right, a test that feeds the start path a budget whose
budget-derived level size is far below the minimum will observe (a) a grid
whose levels are all at the minimum and (b) a non-zero start quantity — with no
error raised. If the oversize came from somewhere else (leverage applied to the
budget, a wrong level count, a stale price), that test would not reproduce it.

Leverage is explicitly **not** the cause: the engine never multiplies the
budget by leverage. Leverage only lets the inflated order pass the balance
check.

## §4 Required behaviour

### §4.1 The verdict

A pure function decides, from plain numbers only:

- `budget` — the configured budget;
- `wanted` — the budget-derived size of one level, before any floor;
- `minimum` — the smallest size of one level at which **no** level of this grid
  is raised to an exchange minimum, in the same unit as `wanted`, after step
  rounding;

→ `minimumBudget = budget × minimum / wanted` (sizing is linear in the budget),
and **refuse** iff `minimumBudget > budget × (1 + GRID_BUDGET_TOLERANCE)`.

### §4.2 Degenerate inputs

- `wanted` is zero, negative, `NaN` or non-finite while `minimum > 0` → refuse
  (a zero budget is below every minimum). `minimumBudget` is reported as
  unknown.
- `minimum` is zero, negative, `NaN` or non-finite (exchange info missing or
  unusable) → **allow**. Fail-open: exactly today's behaviour.
- `budget` zero / negative / `NaN` with `minimum > 0` → refuse.

### §4.3 What `minimum` is, per branch

- order fixed in **base** (incl. coin-margined): the larger of the exchange's
  minimum quantity and `minNotional / lowest level price`, rounded **up** to
  the quantity step.
- order fixed in **quote**: the larger of the exchange's minimum notional and
  `minimum quantity × highest level price`.

### §4.4 The sizing routine reports, it does not decide

`generateGridsOnPrice` exposes, for the grid it just sized, the `wanted` and
`minimum` of §4.1 for the branch it took. It computes every quantity exactly as
before (§1.5). Callers that ignore the report are unaffected.

### §4.5 The start path refuses before any order

On a guarded start (§1.4) the grid bot evaluates the verdict **before** the
start order is sized or placed. On refuse:

- no order is sent to the exchange;
- the bot reports an error through the normal bot-error channel:
  `Budget <budget> <asset> is below the minimum <minimumBudget> <asset> needed
  to place <levels> levels on <pair> at the exchange minimum order size.
  Increase the budget or reduce the number of levels. Bot will stop`
  (when `minimumBudget` is unknown: `Budget <budget> <asset> is too small to
  place <levels> levels on <pair> …`);
- the bot stops the same way the existing start refusals do.

The message text must not be claimed by any existing text-matched error
classification (`errorDict` in `src/bot/utils.ts` matches on substrings such as
`cannot be lower than` and `less than the minimum amount`). It stays
unclassified, which gives the defaults this refusal needs: shown to the user,
bot flagged in error, message verbatim.

### §4.6 A sufficient budget is untouched

With `minimumBudget ≤ budget × 1.10` the start proceeds and produces the same
grid and the same start quantity as before this change.

### §4.7 Service restart is never refused

With the service-restart flag set, the verdict is not evaluated.

### §4.7.1 A settings-edit reload is never refused

While a reload is in progress the verdict is not evaluated — including the
reload variant that clears the restart flag because the user asked for a new
start order (§5 Q2).

### §4.8 Combo is untouched

Combo minigrid sizing through the same routine yields identical quantities and
never refuses.

## §5 Open questions / assumptions made

- **Q1 — tolerance.** 10 % is proposed: large enough to absorb step rounding
  near the minimum, small enough that the user's commitment stays within a
  tenth of what they typed. On a coarse-step pair a budget only slightly under
  the minimum can round a level from one step to two (≈ 2×); 10 % refuses
  that, which is intended — it is the same defect at smaller scale.
- **Q2 — settings-edit restart.** An edit that lowers the budget or raises the
  level count re-sizes a running bot the same way. Refusing there means
  stopping a bot that holds a position — and by the time `start()` runs, the
  reload has already cancelled its orders. Note the sharpest variant: an edit
  that requests a new start order will size that order from the floored grid,
  i.e. the same defect. **Assumed out of scope** for this
  change and listed as known-not-addressed; the edit path should reject the
  edit rather than stop the bot, which is a separate change.
- **Q3 — upstream validation.** The v2 create endpoint and the dashboard form
  should reject such a budget before a bot exists. Separate changes in their
  own repos; this spec is the engine's last line of defence and does not depend
  on them. The dashboard's "Min budget" hint uses nearest-rounding where §4.3
  rounds up, so the two can differ by one quantity step per level — to be
  aligned when the hint becomes a blocking validation.
- **Q4 — legacy `updatedBudget: false` bots** divide the budget by
  `1 + maker·100` before sizing. `wanted` is reported after that division, so
  the verdict reflects what the engine really sizes from.
