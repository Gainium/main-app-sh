# 241 — A paper order cut off by a restart is never retired

Bug spec.

## §1 Definition

### §1.1 Expected

An order that still carries the `'-1'` placeholder (no exchange order id was
ever recorded) and that the exchange definitively reports as absent is retired
as never placed once it is past the never-placed age floor (spec 177 §1.2), and
the level it stood for is placed again. That already holds on every live venue
whose "no such order" wording `isDefinitiveOrderNotFound` recognises.

On a paper exchange the same must hold. Paper-trading answers a lookup for an
order it does not hold with exactly `Unknown order` (HTTP 400 from
`getOrderByKeySecretExternalIdAndSymbol`, passed through unchanged by the paper
exchange client's error handler). Paper-trading writes an order to its database
before it answers the placement, so a paper `Unknown order` about an order
minutes old is an answer, not propagation lag.

### §1.2 Actual

`isDefinitiveOrderNotFound` does not recognise `Unknown order`. A paper `'-1'`
order is therefore read as "the lookup failed" on every restart check (`Not
enough data to get order …`) and on every reconnect pass (`Reconcile could not
read …`). It is never retired and its level is never re-placed: the bot waits
indefinitely on an order that does not exist.

### §1.3 Out of scope

How real exchanges' "order not found" answers are read does not change. In
particular Kraken spot's `EOrder:Unknown order` keeps today's handling: the
paper wording is matched only for a paper exchange, and only exactly.

## §2 Evidence

Production, paper Bybit USDⓈ-M combo bot, 2026-11-13 (identifiers withheld,
this file is public):

- `03:22:04.270Z` a grid order row is written ahead with `orderId: '-1'`; the
  bot worker restarts at `03:22:05Z`, before the placement's answer is recorded.
- Restart checks at `03:22:28Z`, `04:33:16Z` and `06:12:40Z` each log
  `Not enough data to get order <id>` — the non-definitive branch of
  `checkOrders`. The last two were well past the 5-minute floor.
- Reconnect passes `06:14Z`–`08:37Z` log `Reconcile could not read 1 order(s)`.
- The row is still `NEW` / `'-1'`, untouched since `03:22:04Z`. The invariant
  `184.open-order-without-exchange-id` flagged it.

## §3 Assumption (hypothesis)

The paper client returns `reason: 'Unknown order'` for that lookup, and
`isDefinitiveOrderNotFound` returns false for it, so `noteOrderNotFound` (which
retires a `'-1'` order past its age floor) is never reached. Recognising that
exact reason for a paper exchange makes the existing retire path run.

## §4 Required behaviour

- §4.1 `isDefinitiveOrderNotFound(res, exchange)` is true for a `notok` answer
  whose reason is exactly `Unknown order` when `exchange` is a paper exchange.
- §4.2 The same reason is not definitive for a live exchange, nor when the
  exchange is not given; `EOrder:Unknown order` is not matched on any venue.
- §4.3 A paper `'-1'` order past the never-placed floor that the paper exchange
  answers `Unknown order` about is retired as `CANCELED` by
  `noteOrderNotFound`; one younger than the floor is left alone.
- §4.4 The restart and start checks that retire an order on a definitive
  not-found pass the bot's exchange. Lookups made seconds after a placement
  (the unknown-order ladder, the fee-sizing fallback) do not: there, paper may
  still be creating the order, so their handling of paper is unchanged.

## Invariants

Covered by the existing `184.open-order-without-exchange-id` (main-app pack
`specs/184.invariants.json`); no new invariant.
