# 284 — A running grid bot overwrites a database correction to its profit (bug spec)

The grid counterpart of spec 239. Code: `src/bot/profitCorrection.ts` (pure
`invalidGridProfitCorrection`, `addGridProfitCorrection`, type
`GridCorrectionFill`), `BotHelper.applyProfitCorrection` in
`src/bot/helper.ts`, field `profitCorrections` on the grid bot schema.
Tests: `src/bot/gridProfitCorrection.spec.ts`.

## §1 Definition

- §1.1 Expected: a fill a running grid bot never booked (for example a resting
  sell the engine wrote off CANCELED while the venue filled it, spec 270) can
  be booked after the fact, and the bot keeps it.
- §1.2 Actual: there is no way to do that. The grid worker holds `data.profit`
  in memory, `createTransaction` adds each booking to it and `$set`s the whole
  object; a service restart restores `data` from the Redis `botData` snapshot.
  A database write to a running grid bot's profit is overwritten at its next
  booking. The spec 239 method refuses grid bots, and the grid schema has no
  `profitCorrections` field (a strict `$set` would drop it).
- §1.3 What a grid booking moves (read from `createTransaction`): `profit`
  (`total`, `totalUsd`, `freeTotal`, `freeTotalUsd`; `pureBase`/`pureQuote`
  are written 0), `transactionsCount`, `feePaid` on a `feeByAsset` bot, the
  hourly account profit (`saveProfitToDb`), and on futures `data.position`
  (`calculatePosition`). `currentBalances` is NOT a running ledger: it is
  re-derived from the grid levels and the price (`generateCurrentBalances`),
  so a correction must not write it.

## §2 Change

- §2.1 `applyProfitCorrection(delta, reason, correctionId, fill?)` on the grid
  helper adds `delta.total`/`totalUsd` to `total`/`totalUsd` and to
  `freeTotal`/`freeTotalUsd` (falling back with `||` from a 0 free total, as
  `createTransaction` does), persists with `updateData`, writes the Redis
  `botData` snapshot immediately, and emits `bot settings update`.
- §2.2 The id is appended to `profitCorrections`; a repeat returns `duplicate`
  and changes nothing. A non-zero `pureBase`/`pureQuote`, a malformed fill, a
  non-grid bot, or a bot not yet loaded is `refused: <why>`. It never throws.
- §2.3 With `fill`, the booking counters move once: `transactionsCount[side]`
  +1, `feePaid += fill.fee` on a `feeByAsset` bot, the hourly account profit
  `+delta.totalUsd` at `fill.updateTime`, and the futures position through
  `calculatePosition`, whose once-per-fill guard skips a fill the start-time
  rebuild already summed.
- §2.4 It places, cancels and re-prices nothing.

## §3 The start path given a row repaired to FILLED in the database

A repair sets the written-off row FILLED in the database. `loadOrders` (start
and every restart) then:

- §3.1 never hands it to `processFilledOrder`: FILLED rows are not re-read
  from the venue (reconcile reads only NEW / PARTIALLY_FILLED rows);
- §3.2 takes `lastFilled` (the grid's anchor) from the newest FILLED regular
  row, so the repaired row moves it only if no later fill exists — a repair
  must check that;
- §3.3 folds the row into the rebuilt futures position once and records it as
  booked (spec 089);
- §3.4 seeds a FILLED regular row with no transaction into the order map as an
  unpaired fill (`newProfit` / base-profit bots). A repair writes the
  transaction the booking would have written, keyed by the row's
  `clientOrderId`, so the row is not seeded.
