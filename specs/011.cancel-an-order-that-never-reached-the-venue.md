# 011 — Cancelling an order that never reached the venue still asks the venue

Bug spec (existing behaviour is wrong). Issue #671. Sibling of spec
`010.kraken-spot-client-order-id-length.md` §5.2, which deliberately left
`cancelOrderOnExchange()` alone; this spec revisits the one case §5.2 did not
consider — the order that has no exchange id at all.

## §1 Definition

`MainBot#cancelOrderOnExchange(order)` must not ask a venue about an order the
local row already proves never reached it.

### §1.1 Expected

On the venues addressed by **exchange order id** — `coinbase`, `kraken` spot and
KuCoin full futures (`kucoinLinear` / `kucoinInverse`) — an order whose
`orderId` is still the `'-1'` placeholder has no venue-side identifier. The
cancel must resolve locally, exactly the way {@link MainBot#getOrder}
(`core/src/bot/main.ts:4540`) and the unknown-order ladder
(`core/src/bot/main.ts:4753`) already resolve it: `returnBad()` carrying
`'Order not found: no exchange order id'`, which routes to
`_handleUnknownOrder` and retires the order. Zero venue round trips.

### §1.2 Actual

`cancelOrderOnExchange` (`core/src/bot/main.ts:7973`) builds the request as

```ts
newClientOrderId:
  this.data?.exchange === ExchangeEnum.coinbase ||
  this.data?.exchange === ExchangeEnum.kraken ||
  this.kucoinFullFutures
    ? `${order.orderId}`
    : order.clientOrderId,
```

with no `noExchangeOrderId` check, so the literal string `'-1'` is sent to the
venue as the order's identifier. Both siblings that build the same identifier
apply that check — `venueOrderId()` (`:1048`) returns `null`, and the ladder
(`:4749`) sets `neverReachedExchange` — so the cancel path is the only one left
that spends a private-REST round trip to learn what the local row already says.

### §1.3 What the round trip costs

1. **A rate-limited private call, per cancel.** On Kraken `'-1'` is free-text
   shaped (2 chars, printable ASCII), so the connector skips the legacy
   `userref` scan, does the exact `cl_ord_id` lookup, misses, and answers
   `Order not found in open orders` — an ERROR line in the connector for a
   question with a known local answer.
2. **A user-visible bot error when that call fails transiently.** The reason is
   matched against `unknownOrderMessages` (`:211`); a timeout / rate-limit /
   5xx matches nothing, falls through to
   `handleErrors(reason, 'limitOrders()', 'Send cancel request …', true, true)`
   and error-states the bot — for an order that provably never existed at the
   venue. The order is also **not** retired, so the phantom row survives and the
   next cycle repeats the whole thing.

## §3 Assumption (hypothesis)

The root cause is a missing `noExchangeOrderId` check on the one identifier
builder that lacks it. Adding it — short-circuiting to the
`orderNeverReachedExchange` `returnBad()` the other two paths already produce —
removes the round trip and makes the outcome deterministic, without changing
which orders are retired: that message contains `'Order not found'`, which
`unknownOrderMessages` (`:211`) matches, so the request still routes to
`_handleUnknownOrder` exactly as the venue's own "not found" does today.

## §4 Required behaviour

- **§4.1 No venue call.** On `coinbase`, `kraken` and KuCoin full futures, an
  order with `orderId === '-1'` produces **zero** `cancelOrder` calls.
- **§4.2 Same retirement.** That order still reaches
  `_handleUnknownOrder(order.clientOrderId, order.symbol)` and ends `CANCELED`,
  identically to today's venue-answered path.
- **§4.3 The failure is deterministic.** Because no call is made, the
  transient-failure branch of §1.3.2 cannot fire: no `handleErrors`, no
  surviving `NEW` phantom.
- **§4.4 Venues addressed by client order id are untouched.** Every other
  exchange — including `krakenUsdm` / `krakenCoinm` and KuCoin **spot** — keeps
  sending `order.clientOrderId`, `orderId === '-1'` or not. There the client id
  is a legitimate venue-side identifier and the order may exist under it, which
  is the same reasoning the ladder states at `:4779` for keeping its first round
  trip.
- **§4.5 An order that holds a real exchange id is untouched.** A Kraken order
  carrying a txid still cancels by that txid (bug #535 / commit `2b765a0`).
- **§4.6 Reuse, not a new helper.** The guard uses the existing
  `noExchangeOrderId` constant and the existing
  `this.exchange.returnBad()(new Error(orderNeverReachedExchange))` shape from
  `:4753`. No new utility, no new error string, no new message in
  `unknownOrderMessages`.

## §5 Open questions / non-goals

- **§5.1 Why the rows exist at all is NOT fixed here.** Issue #671 names a
  second, upstream defect: a placement the venue rejected is persisted as
  `status: NEW` with `orderId: '-1'` instead of being written off, which is what
  produced 39 Kraken rows and is still producing Coinbase rows daily (§2.1).
  That is a different code path (`sendOrderToExchange`'s rejection handling) with
  its own blast radius, and the triage brief scopes this change to the cancel
  path. It stays open.
- **§5.2 `venueOrderId()` is deliberately not reused here.** It looks the order
  up in the local map by client id and *falls through to the client id* when the
  order is not in the map. `cancelOrderOnExchange` is handed the order object
  directly and must keep addressing it by its own `orderId` — routing it through
  `venueOrderId()` would send a client id for any order not currently in the
  map, which is exactly the bug #535 regression. Only the `'-1'` check is
  shared, via the constant both already use.
- **§5.3 Not verified against a live venue.** No Kraken or Coinbase credentials
  on this host and production is out of bounds. Verified against the real method
  with a recording transport (§2.4) and against the prod population and logs
  (§2.1–§2.3).
