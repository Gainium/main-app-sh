# 186 — A grid level refused as un-reducible is re-sent on every rebuild

Bug spec (Definition / Evidence / Assumption).

## §1 Definition

§1.1 Expected. A futures grid bot whose reduce-only grid level (a long grid's
SELL, a short grid's BUY) is refused by the venue because there is no position
left for it to reduce asks the venue again at a widening interval — not on
every grid rebuild. The refusal reaches the user the way it does today, at that
same interval.

§1.2 Actual. Every grid rebuild (`limitOrders()` runs after every fill, and
`checkOrders` re-places missing levels) finds the refused level missing from
the book and sends it again under a fresh client id. The venue refuses it again
and the bot reports it again. This continues until someone stops the bot.

§1.3 Not changed. Normal grid placement (any level the venue has not refused
this way), refusals for any other reason (balance, min-notional, quantitative
rules, risk tier, auth, compliance), non-reduce-only orders, grid stop / close
orders (`TypeOrderEnum.stop`), and every DCA / combo order type are outside the
gate and behave exactly as before.

## §2 Evidence

§2.1 Production log, Binance USD-M grid bot on IOSTUSDT, long strategy:
420 lines `ReduceOnly Order is rejected. Method limitOrders() Step Send new
order request x-…GRID-RO-<fresh id>, qty 21780, price 0.0011583, side SELL`
between 2026-10-20T20:56:34Z and 2026-10-21T03:11:29Z, up to 27/min, each with
a new client order id. The bot ended only when it was archived.

§2.2 Throughout that window the same bot kept trading other levels normally
(`FILLED` BUYs and SELLs at 0.00104–0.00107 every few seconds to minutes), and
every refusal follows a fill: the cadence of the refusals is the cadence of the
rebuilds, not a timer.

§2.3 Code path. `BotHelper.limitOrders` → `findDiff(this.grids, this.prevGrids)`
→ `placeRegularOrder` (`reduceOnly: true` for the closing side of a long/short
grid) → `MainBot.sendOrderToExchange` → `exchange.openOrder`. A refused level
is filtered out of `this.grids`; the next rebuild regenerates it from settings,
`prevGrids` (the filtered list) lacks it, so it is "new" again. No pre-send gate
in `sendOrderToExchange` covers this refusal; the risk-tier gate is the same
shape for DCA safety orders but excludes reduce-only and grid orders.

## §3 Assumption (hypothesis)

§3.1 The loop exists because nothing remembers the venue's refusal of the
LEVEL between rebuilds. Remembering it — a cooldown keyed on bot, symbol, side
and price, opened only by a real venue refusal matching the
position-already-closed reasons — turns N rebuilds inside the window into one
venue call.

§3.2 The position-already-closed reason list already exists (DCA close path,
`dcaHelper.ts`). It moves to a shared module so the grid path matches the same
venue texts (Binance -2022 `ReduceOnly Order is rejected` among them).

## §4 Required behaviour

§4.1 Six rebuilds of the refused level inside the window → exactly one venue
call; every caller still receives the venue's refusal text.

§4.2 The refusal is reported once per real venue answer; suppressed attempts
report nothing and leave no order row behind.

§4.3 After the window the level is re-probed; a repeat refusal widens the
window (exponential, `RetryBackoff`). An acceptance drops it.

§4.4 A different price, side or bot is a different key and goes to the venue.

§4.5 Outside the gate (§1.3): another refusal reason, a non-reduce-only grid
order, a grid stop order, a DCA close, or a spot bot never open a window.

§4.6 Fail-open: a Redis error means no cooldown (shared `RetryBackoff`).
