# 058 — A topped-up base entry is never persisted

Follows spec `057`, which made `settlePartialBaseEntry` buy back the part of a
cut-short base entry the venue never executed. The buy-back works. What it
writes down does not.

## §1 Definition

### §1.1 Expected

`buyRemainder` merges a successful remainder order back into the row it is
completing — the `dealStart` row — at the blended quantity, quote and average
price. That merged row is the deal's record of its own entry: every ledger the
deal keeps is derived from it.

The merged row must therefore reach the `orders` collection. After a settle
that topped an entry back up, `dealStart.executedQty` /
`cummulativeQuoteQty` / `price` must describe the WHOLE entry — the part that
filled on the book plus the remainder bought at market — so that

- `updateDealBalances` → `initialBalances` / `currentBalances`,
- `updateUsage` → `usage.current` → `cost` / `value`,
- `getAvgPrice`, `computeObservedFeeLedger`, `closeDeal`'s realised profit,

all of which recompute from the order rows and all of which deliberately
EXCLUDE `typeOrder: br` rows (because a remainder belongs to its parent, not to
the ledger in its own right), see the whole entry rather than a fraction of it.

### §1.2 Actual

The merge is made in memory only. `topUpSettledBaseEntry` calls
`fillPartiallyFilledOrder` and hands what comes back straight to
`handleUnknownOrder`; nothing writes it. Both of the other callers of
`fillPartiallyFilledOrder` (`main.ts`, the user-stream consumer and the
synchronous placement-response path) persist the row they get back with
`updateOrderOnDb(order, origExecutedQty < newExecutedQty)` — the `force`
argument being required because the row is already in a terminal status and the
default filter refuses to touch a `FILLED`/`CANCELED` row.

So the deal opens correctly on the merged copy, and then, the first time the
bot reloads its orders from Mongo, the merged copy is gone. Every ledger
recompute reverts to the fraction that filled on the book, while the remainder's
own `br` row is excluded by design — the quantity is booked nowhere at all.

## §2 Evidence

Production, Coinbase spot, a DCA base entry for 816.74 units, 2026-09-19:

| source | value |
|---|---|
| engine log, 16:29:39.562Z | `base order … stopped at 34.66 of 816.74 … opening the deal on what filled` |
| engine log, 16:29:41.573Z | `Buy remainder executed …, base - 780.85, quote - 95.841529` |
| engine log, 16:29:41.574Z | `Total order …, 0.12273, base: 815.51, quote: 100.0894586 BUY` ← the merge |
| `orders` row `dealStart` | `status CANCELED, executedQty 34.66, cummulativeQuoteQty 4.2479296` ← never updated |
| `orders` row `br` | `status FILLED, executedQty 780.85, cummulativeQuoteQty 95.841529` |
| deal `initialPrice` | `0.12273` ← proof the deal DID open on the merged copy |
| deal `cost` | `37.2473296` = `4.2479296 + 32.9994` — the remainder's 95.84 is absent |
| deal `currentBalances.base` | `-779.76` = `34.66 + 271.6 − 1086.02` — a short position the deal never held |
| engine log, 19:24:50Z | `holds more than its order rows account for — base order qty 814.33 taken from the position, not the 34.66 on record` |

The last line is the reload: hours later the in-memory row is the unmerged one
again, and only a position read stopped the take profit from being sized at a
quarter of the position.

`updateDealBalances` reproduces `-779.76` exactly from those rows, and its
filter is the reason: it admits `FILLED`/`CANCELED`-with-fills rows and drops
`br` and `rebalance`. `updateUsage` reads the same `dealStart` row through
`findBaseOrderByDeal`. Both are correct given a correctly persisted parent row.

## §3 Assumption (hypothesis)

The root cause is a missing write, not a wrong read: `topUpSettledBaseEntry` is
the only caller of `fillPartiallyFilledOrder` that does not persist its result.
Adding that write — forced, because the row is terminal by the time the
remainder settles — makes every downstream ledger agree, with no change to any
of them.

Two independent writers already race to make the row terminal before the
remainder even comes back, which is why the write has to be forced:

- `cancelOrderOnExchange` promotes the part-filled row to `FILLED` and writes it
  (unforced) at ~16:29:39.9Z;
- the venue's own user-stream event for the cancel writes `CANCELED` (unforced)
  at 16:29:39.847Z.

Whichever lands first wins, and the second is silently filtered out. The
observed row is `CANCELED`.

## §4 Solution

### §4.1

`topUpSettledBaseEntry` persists the row the top-up returns, with
`updateOrderOnDb`, whenever the top-up actually recovered quantity — the same
condition and the same helper the user-stream path already uses.

### §4.2

`force` is passed so the write is not refused by the terminal-status filter.
The write is awaited, so the row is on disk before `settlePartialBaseEntry`
opens the deal from it.

### §4.3

A top-up that recovered nothing — the venue refused the remainder, or it was
below the venue minimum — writes nothing. `cancelOrderOnExchange` /
`promoteEndedBaseEntry` have already recorded that row, and a forced rewrite of
an unchanged row would only widen the race those two are already in.

## §5 Out of scope

`getAvgPrice` (`dcaHelper`) does NOT exclude `typeOrder: br`, unlike
`updateDealBalances` and `updateUsage`, so while a merged parent row and its
`br` row are both in the order map it counts the remainder twice. That is a
separate defect on the same invariant, with its own reproduction, and it is
unaffected either way by §4: the double count already happens at `startDeal`
today, and `loadOrders` excludes `br` rows, so it cannot happen after a reload.
