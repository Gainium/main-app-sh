# 297 — OKX USDT-swap open positions with contract value 1 and a fractional lot read too small

Bug spec (Definition / Evidence / Assumption). Follows spec 296, whose §1.3 /
§4.1 left these pairs out of scope.

## 1. Definition

§1.1 `getAllOpenPositions` reports every `okxLinear` position's `quantity` in
base coin: the venue's contract count `pos` × the contract value `ctVal`
(`baseAsset.multiplier`), for every pair, `ctVal = 1` included. 50 contracts
of LINK-USDT (ctVal 1, minSz 0.1) read 50.

§1.2 `closePositionOnExchange` converts that coin size back to contracts with
the bot engine's own `getOKXDenominator` rule for every pair. For `ctVal = 1`
the denominator is 1, so "Close position" sends a reduce-only MARKET order for
the whole position.

§1.3 Not changing: pairs whose `ctVal ≠ 1` keep spec 296's behaviour. How bots
size and place orders (`getOKXDenominator`) is not touched.

Actual: for `ctVal = 1` the read still divided by the step denominator
(`step > 1 ? 1/step : 10^decimals(step)`, with `step = ctVal × minSz = minSz`),
so a pair with `minSz` 0.1 / 0.01 read `pos/10` / `pos/100`, and the close
divided again: `pos/100` / `pos/10000` contracts.

## 2. Evidence

§2.1 Connector mapping (exchange-connector-sh `okx/index.ts`): `step =
ctVal × minSz`, `multiplier = ctVal`, `positionAmt = pos`.

§2.2 Production pair rows: `okxLinear` LINK-USDT `{step 0.1, multiplier 1}`,
SOL-USDT `{step 0.01, multiplier 1}`. Many OKX Europe X-Perps have the same
shape (e.g. GOOGL-USD_UM_XPERP `{step 0.01, multiplier 1}`), so spec 296
§2.2's "every X-Perp has minSz = 1" does not hold.

§2.3 Runtime: an account's open X-Perp DCA deal of size 1.47 GOOGL read
`quantity: "0.0147"` from `getAllOpenPositions`, and a 5.1 CRCL deal
(step 0.1) read `0.51`. Those are the ÷100 and ÷10 this spec predicts.

§2.4 The engine's `getOKXDenominator` prefers `multiplier` on `okxLinear`, so
it uses 1 for these pairs and the bot order path is unaffected.

## 3. Assumption (root cause)

§3.1 The step-denominator conversion predates `baseAsset.multiplier`. `step`
is the lot size in coins, not a unit, so dividing by its decimals was never a
unit conversion. Spec 296 kept it for `ctVal = 1` only to limit scope.

## Invariants

None: the defect is a misread of live venue state in a query response, and
the resulting close order is a live venue order. Nothing wrong is written to
the database for a sentinel to find.
