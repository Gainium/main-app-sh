# 005 — A deal whose venue position is gone is never reconciled

Issue #630. Sibling of `004.tp-level-close-terminal-rejection.md` (#627): 004
stopped the *retry flood*, this one stops the *deal staying open forever*.

## §1 Definition

### §1.1 Expected

When a DCA futures deal has reached a take-profit level and the engine cannot
get a closing order onto the venue, the engine must eventually establish
whether the position it is tracking still exists. If the venue reports **no
position** for that symbol/side, and still reports none when asked again, the
deal is tracking something that is gone:
it must be booked closed (keeping the P&L already realised by the take-profit
targets that did fill) and the user must be told, once.

### §1.2 Actual

Nothing ever asks the venue. `checkTPLevel` has exactly two endings when a
close leaves nothing in flight:

- the venue refused with a `Futures position` reason → open/extend
  `tpCloseBackoff` and re-try at 1 → 2 → 4 → 8 → 15 min, **forever**;
- anything else (including `not placed`, where the order never left the
  process) → release `closeByTp` and re-arm on the next price tick.

Neither ending can ever terminate. The deal stays `status: 'open'`, keeps its
funds accounted as in-use, keeps arming take-profit checks and keeps emitting
orders against a position the venue closed months ago.

## §2 Evidence

Production, read-only (`mongo` on stdin over the forced-command key, and the
`logs` helper).

### §2.1 The deal

`dcadeals` `69f1b27faeba7a4880365abb` — bot `69de6e9e10716872ece23ce8`, user
`64e7a7f46c579b9917b1978a`, `paperBitgetUsdm`, XAUTUSDT, `strategy: SHORT`,
`flags: ['newMultiTp']`, 5 multi-TP targets of 20 % each.

- `status: 'open'`, `createTime` = `updateTime` = 2026-04-29.
- `tpSlTargetFilled` holds exactly one target; `tpFilledHistory` is a single
  `{ qty: 0.01, price: 4524.72 }`. Four of five targets never filled.

### §2.2 The venue closed the position on the same day

`paperFutures` (the collection paper-trading actually keys positions on — the
report's `paperHedge` query was against the wrong collection):

```
entryPrice 4570.72  closePrice 4524.94  positionAmt 0.01
status CLOSED  fee 0.0727644  profit 0.8450356
updatedAt 2026-04-29T13:39:55.002Z
```

The fee decomposes exactly — `0.02·4570.72·0.0004` (open) `+ 0.01·4524.72·0.0004`
`+ 0.01·4524.94·0.0004` = `0.0727644` — and the profit reproduces to the tenth
decimal from those same three legs. So the venue took the full 0.02 back in two
0.01 closes, and has held **no** XAUTUSDT position since 2026-04-29T13:39:55Z.

The paper account was **not** reset: the same paper user
(`692739ebecb61a548e27c01b`) still holds 25 open (`status: 'NEW'`) positions.
None of them is XAUTUSDT, BARDUSDT or MINAUSDT — the three symbols whose deals
are stuck open on this bot.

### §2.3 The loop is still running today

`Gainium-DCA-bot-out.log`, 2026-09-04, one deal, one worker:

```

             (not placed) — releasing closeByTp and re-arming TP level check
```

3601 matching lines in the window searched, ~1 attempt every 15 s, four months

Note the outcome is **`not placed`**, not `refused by the exchange`: today the
attempt does not even reach the venue, so 004's `terminalRejection` branch —
the only ending that backs off — is never taken. Earlier in the deal's life it
did reach the venue: 86 of its order documents are `CANCELED` carrying
paper-trading's `Reduce order is rejected` (`order.service.ts:230`), dated
2026-08-06 … 08-08.

### §2.4 It is not one deal

The same bot has three deals in this state — XAUTUSDT, BARDUSDT (4 of 5 targets
filled) and MINAUSDT — all opened 2026-04-29, all still `open`, none with a
matching open venue position.

## §3 Assumption (hypothesis)

The root cause is a **missing** path, not a wrong line: no code in the DCA
engine ever compares an open deal against the venue's position list. The
existing "the position is already closed, book the deal closed" reconciliation
(`dcaHelper.ts:5993-6006`, keyed on `isPositionAlreadyClosedReason`) is wired
**only** into `closeDealById` — the single-TP / full-close path. A multi-TP
deal closes through `checkTPLevel`, which has no equivalent, so the venue's
answer is used to schedule a retry and never to settle the deal.

Corollary, and the reason §2.3 matters: keying the new reconciliation on the
venue's *refusal text* would not rescue these deals, because the attempt that
is actually looping never gets a refusal. The check has to be driven by "a
take-profit close left nothing in flight", and then go and **ask** the venue.

### §3.1 Which side caused the divergence — NOT in scope for the fix

The brief asks this to be settled before choosing a fix site. It is settled,
and the answer is "neither of the two candidates named":

- **main-app is not under-decrementing `currentBalances.base`.** Every sibling
  deal on this bot that closed *normally* also ends with
  `currentBalances.base === initialBalances.base` (BATUSDT 1031.9/1031.9,
  BUSDT 892/892, KMNOUSDT 4859/4859, …). For these futures shorts `base` is not
  the running position size, so 0.02 staying 0.02 is the normal shape, not the
  defect.
- **paper-trading is not over-closing a partial `reduceOnly`.** The clamp at
  `order.service.ts:1462-1490` is reached only when `positionAmt - order.amount
  <= 0`, i.e. when the order asks for **more** than the position holds; clamping
  down is what `reduceOnly` means. A 0.01 order against a 0.02 position takes
  the partial branch at 1534, which decrements correctly.

What actually happened is a **second** 0.01 close (§2.2) that main-app has no
order document for. Explaining that duplicate is a separate investigation with
a separate owner; it is deliberately left open. The reconciliation guard is
correct either way — that is exactly why the brief asks for it — and this spec
scopes to the guard.

## §4 Out of scope

- The origin of the duplicate close (§3.1).
- Back-filling the deals already stuck. This fix stops new ones and settles
  existing ones the next time their take-profit level is reached; it is not a
  migration.
- `closeDealById`'s reconciliation, which already works and is untouched.
