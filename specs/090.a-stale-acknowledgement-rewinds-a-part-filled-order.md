# 090 — A stale `NEW` acknowledgement rewinds a part-filled order

Bug spec. The behaviour already exists and is wrong.

Fourth reader of the same row as specs `038`, `048`, `057`–`059` and `088`. All
of those decide what to do with a base entry the venue ended part filled. This
one is about the step BEFORE any of them run: what the engine believes the row
says at the moment they are asked.

## §1 Definition

### §1.1 Expected

The user stream delivers one execution report per state change of an order. An
order's state moves forward only — a venue acknowledges (`NEW`), then executes
(`PARTIALLY_FILLED`), then ends (`FILLED` / `CANCELED` / `EXPIRED`) — and its
cumulative executed quantity never decreases. Reports can be delivered out of
order; what the engine holds for the order must still be the NEWEST report it
has seen, never an older one replayed over it.

This is the temporal half of the rule `fillEvidence.ts` already states for
payload content ("what the venue did not state cannot overwrite what we know")
and `settledBaseEntryFill` states for the cancel response (spec `059`: "an
order's executed quantity never decreases, so a response that reports less than
we already read is an ABSENCE of information, not a correction").

### §1.2 Actual — the acknowledgement overwrites the fill

`convertExecutionReportToOrder` (`main.ts:5691-5725`) merges the report onto the
row it holds with no reference to which one is newer:

```ts
if (msg.orderStatus === 'CANCELED' || … || msg.orderStatus === 'NEW' || …) {
  order.status = msg.orderStatus          // ← whatever this report says
}
order.executedQty = …msg.totalTradeQuantity…
order.updateTime  = updateTime
```

So a `NEW` acknowledgement delivered AFTER the `PARTIALLY_FILLED` it precedes
rewinds the row to `status: 'NEW', executedQty: '0'`, and `processOrderQueue`
then `setOrder`s that back into the order map.

Every guard written for a part-filled base entry reads that map and is blinded
by it:

- `shouldSettlePartialBaseEntry` (spec `038`/`048`) accepts `PARTIALLY_FILLED`
  or a terminal row carrying a fill. A row that says `NEW` is neither, so the
  settle is declined;
- `checkBaseOrder`'s reposition branch then falls through to its
  `status !== 'FILLED' && status !== 'PARTIALLY_FILLED'` arm — *"not filled.
  Create new one"* — which cancels the entry and **re-places a base order on
  top of a position the account already holds**. That re-placement is precisely
  what spec `048` §1.2(3) exists to remove from the restore path; this reaches
  it from the live path instead;
- `cancelOrderOnExchange`'s promotion guard reads the same zero, so on a venue
  whose cancel response is not a fill report (spec `059` §4.1, Kraken spot) it
  declines too.

The one thing that still works is the venue's own terminal report arriving
afterwards — it is newer, so it lands, and whatever settles the row settles it
from there. The defect is therefore a RACE the engine wins or loses by
milliseconds, not a permanent stranding, which is why it leaves so little
behind.

`1789907750864 < 1789907750866`: the two `NEW` reports are OLDER than the
`PARTIALLY_FILLED` they overwrote, by the venue's own timestamps. Ten seconds
later the reposition timer read `NEW`/`0` and took the re-place arm; only the
venue's `CANCELED`, 115 ms after it, rescued the deal.

The row in `orders` and the deal in `dcadeals`, read read-only:

| | |
|---|---|
| `dealStart` | `CANCELED`, `origQty 27.66356687`, `executedQty 27.66356` |
| deal | `closed`, `cost 100.25`, `size 27.5944011`, `levels.complete` **0** |

`levels.complete: 0` on a deal that traded is the residue: of the 54,786 deals
that closed in the six days to 2026-09-23, this is the ONLY one — every other
one counts its base order. The deal closed at a profit, so nothing was lost
here; what was lost is the engine's guarantee. A base order genuinely was
cancelled and genuinely was about to be re-sent.

### §2.1 Relationship to the issue this was found under

This is the one post-deploy row in the harm query for issue #774 (a `dealStart`
row `CANCELED` with `executedQty > 0` whose deal never counted a level, 14 days
to 2026-09-23: four rows — the original on 09-14, two on 09-18, this one).
The two on 09-18 are a DIFFERENT defect, already fixed: they are the Kraken
cancel-response shape spec `059` was written for, and both predate it (last
`could not be settled (CANCELED)` in production: 2026-09-19T10:45:44Z; `059`
landed 2026-09-19T20:54Z). This row is the shape none of `038`/`048`/`059`
covers, because all three read a row that had already been rewound.

## §3 Assumption (root-cause hypothesis)

The root cause is that `convertExecutionReportToOrder` has no notion of report
order. It is not venue-specific and not about the settle machinery: the stream
consumer applies whichever report it dequeues last, and two reports for one
order can be dequeued in either order.

## §4 Solution

### §4.1 The decision

A pure predicate, `executionReportRewindsOrder`, over the row the engine holds
and the report as converted. It answers true only when BOTH:

1. the report is dated STRICTLY EARLIER than the row we hold — both timestamps
   finite and positive, so a row that cannot be dated (a REST-written
   `updateTime: -1`, which production holds) disables the rule rather than
   guessing; and
2. the report is an acknowledgement — `status: 'NEW'` — for a row whose status
   is anything else.

Deliberately NOT part of the rule: a report that merely states a smaller
`executedQty`. That is the same monotonicity principle and it is true, but it
also describes the venue cancel report spec `088` deliberately routes through
`fillPartiallyFilledOrder`'s post-mutex re-read after a top-up has inflated the
row past what the venue ever executed. Widening this predicate to quantity
would silently take that report away from `088`'s path, so it stays at the one
shape §2 evidences.

### §4.2 Where it is asked

`convertExecutionReportToOrder`, once the report has been merged onto a copy of
the held row — so the comparison is between two values in the same units, after
the coin-margined / contract conversion, never between a raw
`msg.totalTradeQuantity` and a converted `executedQty`. A rewind returns `null`,
which is the converter's existing "there is nothing to process here" answer
(`main.ts:5659`, `:5679`); `processOrderQueue` moves to the next message.

Gated on `process`, like the existing already-filled guard above it, so the
`getOrder` / Redis-cache caller that converts a report in isolation is
untouched.

### §4.3 Nothing downstream loses a callback it needed

A dropped report is a `NEW`, and `onNew` is the only callback a `NEW` reaches:

- DCA's `processNewOrder` is a no-op;
- combo's override cancels the order when its minigrid is already closed —
  which for a row that has since filled or ended is a request the venue would
  refuse anyway.

The report also no longer reaches `updateOrderOnDb`, which is the point: it is
the write that put `NEW`/`0` over a fill.

### §4.4 It is logged where it can be seen

`handleLog`, not `handleDebug`: the bot services do not run at debug level
(spec `088` §4.3 records the same trap), and this is the only trace the
condition leaves once it stops causing harm.

## §5 Out of scope

- Ordering the user stream itself. websocket-connector forwards what it
  receives; a consumer that cannot be rewound is the cheaper guarantee.
- The quantity-monotonicity rule in general (§4.1).
- `levels.complete` on the deal in §2. It is a fold over the order map, correct
  for the map it was given; the map is what was wrong. Repairing deals already
  closed is not attempted.
- The `checkBaseOrder` re-place arm itself. With the row no longer rewound it is
  reached only by an entry that really is unfilled, which is what it is for.
