# 080 — Coverage subtracts a withdrawal that is already out of the size

Bug spec. Found while fixing spec 079, which is the same field read the other
way round.

## 1. Definition

### 1.1 Expected

`trackedPosition` (`dca/tpCoverageReconcile.ts`) answers "how much base does
this deal still hold?", and is the measure three things depend on: the
coverage reconcile's drift verdict, the cap on how far a close may be raised
to clear a venue's minimum notional, and `dealOwnBasePosition`.

It must agree with `getTPOrder`, which sizes the close. A measure that
disagreed with the sizer would report drift on healthy deals forever — the
failure mode spec `014` already had to fix once.

### 1.2 Actual

It subtracted BOTH the executed and the pending reduce-funds from
`|deal.size|`:

    |size| - soldViaHistory - soldViaFilled - reduceFundsBase - pendingReduceFundsBase

`deal.size` is already NET of an executed withdrawal. Spec `026` §2.3
established that from production, over every open deal that had used reduce
funds — `|size| = entry - reduceFunds`, to the unit:

    DOGEUSDT    size 4141     entry 9073     rf 4932    -> 0
    TRUST-USDC  size 6162.7   entry 7259.1   rf 1096.4  -> ~0 (-9e-13)

So the executed amount came off twice, and the position read low by exactly
what had been withdrawn.

`getTPOrder` does not have this problem: it adds the executed withdrawal back
onto `deal.size` to reconstruct the gross entry volume
(`grossEntryVolume`) and subtracts it once downstream in `add`. The two
balance. `trackedPosition` only has the subtraction.

## 2. Consequence

For any deal that has used reduce funds, on a measure that is supposed to
agree with the sizer:

1. **Coverage drift.** The close `getTPOrder` rests covers the position the
   deal really holds; `trackedPosition` believes the deal holds less, so a
   fully covered deal reads as OVER-covered by the withdrawn amount. That
   verdict is not only a log line: `over` collects the deal's
   PARTIALLY_FILLED take-profits as residue to cancel. On a deal whose only
   "excess" is the arithmetic error, a partially-filled close that is doing
   its job is what gets cancelled.
2. **The minimum-notional cap** (`dcaHelper.ts`, spec `043`/`047`) caps a
   raised close at the tracked position. Capped low, a close that the deal
   can afford can be held under the venue's floor — the exact failure that
   cap was introduced to prevent, reappearing on deals that used reduce funds.
3. **`dealOwnBasePosition`** (spec `053` §4.3) under-reports for the same
   reason.

The pending half is correct and stays: a queued withdrawal has not happened,
is still inside `size`, and is deliberately not something a close may cover.

## 3. Solution

`trackedPosition` takes only `pendingReduceFundsBase`; the executed term is
gone from the signature, so it cannot be passed back in by accident. The three
call sites in `dcaHelper.ts` drop it, including the contract-space conversion
that existed only to convert it.

This spec and spec 079 are one pair and must ship together. 079 makes
`deal.size` net of a withdrawal at the instant the fill is booked rather than
at the next usage refresh; with that in place, "already net" is true at every
instant, which is exactly the premise this change relies on.

## 4. Tests

`dca/tpCoverageReconcile.spec.ts`

- the executed/pending test is replaced: a size of 1000 with 100 executed and
  50 pending now tracks 950, not 850. The old expectation encoded the
  double-subtraction.
- a deal that entered 60.3 and withdrew 25.63 tracks the 34.67 it holds.

The rest of the coverage suite — drift verdicts, repair scope, contract units,
the fee-band tolerance from spec `014` — is unchanged and still passes, which
is the point: nothing but the withdrawal term moved.

## 5. Out of scope

`getTPOrder`'s own arithmetic. It already balances the add-back against the
subtraction, and spec `026` verified that pairing against production.
