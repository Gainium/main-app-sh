# 118 — "Change DCA levels" is a no-op on indicator and custom ladders

Bug spec. The behaviour already exists and is wrong.

## §1 Definition

### §1.1 Expected

On an open DCA deal whose safety orders are triggered by indicators
(`dcaCondition: indicators`) or by a custom list (`dcaCondition: custom`),
the deal's "Change DCA levels" action changes how many safety orders the deal
can still place:

- lowering it to N stops the deal after its N-th safety order — `levels.all`
  becomes `N + 1` and no further safety order is placed or fired;
- raising it again restores levels, up to the ladder the bot defines (one
  level per `startDca` indicator / custom row — there is nothing to place
  beyond that);
- `0` turns DCA off for the deal (unchanged path, `useDca: false`);
- a deal whose DCA was turned off gets its remaining levels back, exactly as
  the bot defines them, when the action is used again with a higher value —
  the ladder is rebuilt from the indicators / custom rows, not from a copy;
- "Reset to bot settings" removes the limit along with the deal's other
  overrides.

### §1.2 Actual

Both dashboards send the action as a deal-settings patch — V2
`{ useDca: true, ordersCount: N }`, V1 `{ ordersCount: N }` (plus
`useDca: true` when it was off). `updateDealSettings` stores `ordersCount` on
the deal and rebuilds the ladder, but `createInitialDealOrders` and
`dcaLadderSize` size an indicator/custom ladder from the indicator / row count
and never read `ordersCount`. The ladder, `levels.all` and the next indicator
signal are all exactly what they were: the save succeeds and does nothing.

## §2 Evidence

- Prod deal (GraphQL `getDCADeals`, 2026-09-28): `dcaCondition: indicators`,
  bot with 3 `startDca` indicators, `settings.ordersCount: 2`,
  `settings.changed: true` (the user's edit was stored), `levels: {complete: 3,
  all: 4}` — two safety orders filled and a third still armed. Expected
  `levels.all: 3` with nothing left to place.
- The bot's own stored `ordersCount` is `8` against 3 indicators, so the stored
  value is unrelated to the indicator ladder and cannot be read as a limit.
- Harness `src/bot/dca/changeDcaLevelsIndicatorLadder.harness.spec.ts`, before
  the fix: after `updateDealSettings({ useDca: true, ordersCount: 2 })`
  `levels.all` stays 4 and signal 3 still fires level 3.

## §3 Assumption (root cause)

Indicator/custom ladders have no deal-scoped limit at all, so there is nothing
for the action to set. `ordersCount` cannot be that limit: in these modes it
holds values unrelated to the ladder on existing bots and deals.

Fix: a deal-only setting `dcaLevelsCap`, written by `updateDealSettings` only
for the action's patch shape (keys ⊆ `{ordersCount, useDca}`, `ordersCount`
present) on an indicator/custom deal, and applied as
`min(indicator or row count, dcaLevelsCap)` in `dcaLadderSize`, which
`createInitialDealOrders` now uses for its ladder size, and
`createCurrentDealOrders` for a custom ladder's "levels left" count — else a
spent capped custom ladder still counts levels left and re-rests a filled one
(the spec `115` hazard). Everything downstream
(`levels.all`, the indicator signal's level lookup, the spent-ladder check in
`updateUsage`, the safety-order alert total) reads one of those two.

## §4 Scope

- §4.1 Changed: an indicator/custom deal the action was used on is limited to
  `min(count, cap)` safety-order levels.
- §4.2 Not changed: an indicator/custom deal nobody used the action on keeps
  one level per `startDca` indicator / custom row — no cap is ever derived from
  the bot's or the deal's existing `ordersCount`.
- §4.3 Not changed: percentage / dynamic ladders (`ordersCount` already is
  their size), and `0` → `useDca: false`.
- §4.4 Not changed: other deal edits (Edit Deal drawer, mass edit, API) that
  carry `ordersCount` alongside other keys do not set the cap.
