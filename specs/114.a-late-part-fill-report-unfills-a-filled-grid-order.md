# 114 — A late part-fill report un-fills a filled order

Bug spec. The behaviour already exists and is wrong.

Sibling of spec `090`, which refused a stale `NEW` acknowledgement dated before
the row it would overwrite. This is the same rewind reaching the engine through
the one door `090` deliberately left open: a report with the SAME timestamp.

## §1 Definition

### §1.1 Expected

An order's status only moves forward (spec `090` §1.1). Once the engine holds
an order as `FILLED`, no later report can make it live again: a venue never
un-fills an order. The Mongo write already enforces this —
`updateOrderOnDb` filters `status: { $ne: 'FILLED' }` — so the in-memory order
map must agree with the row it is persisted as.

### §1.2 Actual — the part-fill lands on top of the fill

`convertExecutionReportToOrder` merges any report onto the held row. Its only
guards against a backwards move are:

- the "already filled" drop, which is limited to Binance `MARKET` orders and
  the Bitget family;
- spec `090`'s `executionReportRewindsOrder`, which needs the report to be
  `NEW` AND dated strictly earlier (equal timestamps are excluded on purpose,
  because several venues stamp every report of an order with one order time).

A `PARTIALLY_FILLED` report delivered after the `FILLED` one, carrying the same
timestamp and the full executed quantity, passes both. `processOrderQueue` then
`setOrder`s it, which puts the order back into the `PARTIALLY_FILLED` status
index. Mongo keeps `FILLED` (its filter refuses the write); memory now says the
order is still resting.

On a combo deal grid that is a ghost level. `isOrderExistInDeal` reads the
`NEW`/`PARTIALLY_FILLED` index to decide whether a level is already on the
book, so the next time the ladder wants a BUY at that price and size it logs
`Order already exist` and places nothing — while the regenerated ladder
(`minigrid.currentOrders`) records the level as resting. When price later
falls through that level the ladder flips it to its counter SELL, which is
placed: a sell for base that was never bought. The following sell the ladder
genuinely needs is then refused by the venue for insufficient balance.

## §2 Evidence

Production, Kraken spot, combo deal grid, 2026-09-26, `Gainium-Combo-bot`
fixed-string search (UTC; trailing field is `updateTime`):

```
21:50:03.103  Processing msg … CMB-GR-<a>, FILLED,           0.08215, base: 506.53547 … BUY, 1790459402861
21:50:03.103  Update minigrid … CMB-GR-<a>
21:50:03.104  Processing msg … CMB-GR-<a>, PARTIALLY_FILLED, 0.08215, base: 506.53547 … BUY, 1790459402861
…
22:16:10.298  Update minigrid … (sell at 0.08252 filled — its counter is a BUY at 0.08215)
22:16:10.307  Order already exist qty: 506.53547, price: 0.08215, side: BUY, type: dealGrid
```

The deal's orders read over the dashboard API: the only order ever at
0.08215 × 506.53547 BUY is `<a>`, `FILLED` at 21:50:03. No BUY was placed at
0.08215 at 22:16; four of the five counter-buys of that burst were placed.
At 23:19 five buys filled together and SIX sells were placed — the five
counters plus one at 0.08252, the counter of the ghost level. At 23:48 six
buys filled, six counter-sells were sent, and the sixth was refused by Kraken
(`EOrder:Insufficient funds`), because the ghost sell still locked one grid
order's worth of base.

## §3 Assumption (root-cause hypothesis)

The ladder, `findDiff` and `isOrderExistInDeal` are each correct for the order
map they are given; the map is what is wrong. The root cause is that
`convertExecutionReportToOrder` lets a non-terminal report overwrite a row the
engine holds as `FILLED` on every venue except the three families the old guard
names.

Refuted alternatives (from the same evidence): the burst fills were processed
one at a time under the deal mutex, in price order, each regenerating the
ladder once — no level was computed twice; the 0.08235/0.08168 prices that
looked like near-duplicate levels are the average FILL prices of orders placed
at 0.08236 and 0.08149.

## §4 Solution

### §4.1 The decision

A pure predicate, `executionReportUnfillsOrder(held, report)`, in
`staleExecutionReport.ts` next to `090`'s: true exactly when the held row is
`FILLED` and the report is `NEW` or `PARTIALLY_FILLED`. No timestamp condition —
the status pair alone is impossible on a venue, so it is stale by construction,
and it is exactly the write `updateOrderOnDb` already refuses.

Deliberately NOT included:

- `CANCELED`/`EXPIRED` over `FILLED`: a different question (which terminal state
  is right), with its own promotion paths (specs `028`, `088`). Unchanged.
- Any rule over a held `CANCELED`/`EXPIRED` row: a venue cancel response is not
  always a fill report (spec `059`), so a later part-fill report can be the
  first news of a fill.

### §4.2 Where it is asked

`convertExecutionReportToOrder`, beside `090`'s check, gated on `process`, and
answering `null` — the converter's existing "nothing to process" result. Logged
with `handleLog` (bot services do not run at debug level, spec `090` §4.4).

### §4.3 Nothing downstream loses a callback it needed

A dropped report is `NEW` or `PARTIALLY_FILLED` for an order whose `onFilled`
already ran. `onNew`/`onPartiallyFilled` for a filled order have nothing left to
do; the Mongo row never received the write anyway.

## §5 Out of scope

- Repairing ladders or orders already desynchronised in production.
- Ordering the user stream itself (spec `090` §5).
