# 053 — A refused deal close leaves the position with nothing on the book

Issue #784. Follows #696 / #700 / #702 (the tp-coverage family), which built the
DETECTION this spec finally wires to an action on the path that CREATES the gap.

## §1 Definition

### §1.1 Expected

Closing a deal is a *replacement*: the take-profit resting on the book is pulled
and a close is sent in its place. Whatever the venue answers, an **open deal must
never be left with no close on the book**. If the replacement is refused, the
deal keeps a close it can fund **from its own position** — and if even that
cannot be placed, the deal is marked as needing attention and the user is told,
rather than the engine going quiet.

### §1.2 Actual

`dcaHelper.closeDealById` cancels first and places second:

```
await this.cancelAllOrder(0, dealId, true)     // dcaHelper.ts:6634 — pulls the resting TP
…
const tpOrder = await this.prepareTpOrder(findDeal, slSource, sl)
result = await this.sendGridToExchange(…)      // venue refuses: "Not enough balance"
→ handleOrderErrors(…)                          // report, then RETURN
```

The refusal branch reports and returns. Nothing restores a close. The deal stays
`status: open`, holding its whole position, with **zero resting orders** — and
because coverage is only ever re-established as a side effect of `placeOrders`
(which runs on a *fill*), and there is now nothing left that can fill, the deal
cannot recover on its own.

Once `notEnoughBalance.thresholdPassed` latches, later attempts are served from
the local cooldown instead of the venue, and `main.ts:8044` **deletes** the
write-ahead order row — so the deal ends up with no trace of the close at all.
To the user the deal looks like an ordinary open deal.

## §3 Assumption (hypothesis, not fact)

The root cause is **ordering with no restore**: `closeDealById` pulls the resting
take-profit *before* it knows whether the replacement will be accepted, and its
refusal branch has no path back. Therefore:

- **§3.1** Making the refusal branch restore a take-profit **sized from the
  deal's own position** closes the hole, because the position the deal owns is
  exactly what the pulled order was covering.
- **§3.2** When even that restore leaves nothing on the book, the deal is
  genuinely unfundable from its own allocation; that is a user condition, and the
  correct response is to mark the deal and report it, not to retry silently.
- **§3.3** `adaptiveClose` sizing off `find.free` — the WHOLE wallet's free base
  — is the same account-wide accounting in a second place, and must be clamped to
  the deal's own tracked position.

### §3.4 Explicitly out of scope (code owner, 2026-09-17)

Making base-asset accounting wallet-aware across an account's bots and deals is
**rejected**. A bot accounts against its own isolated allocation; cross-side
contention on one spot wallet is user misconfiguration and the platform must not
silently compensate. In particular, siblings' reservations are **not** subtracted
— the venue's `free` is already net of resting orders, so subtracting them again
would double-count.

## §4 Solution

### §4.1 Restore a close the deal can fund from its own position

In `closeDealById`'s terminal-refusal branch (the `else` reached after the
slippage-retry and position-already-closed branches have returned), re-arm the
ordinary take-profit through the path the engine already uses for exactly this —
`getTPOrder` + `placeOrders`, the same pair `tpCoverageReconcile`'s correction
calls (`dcaHelper.ts:10955-10985`).

Guarded by the invariant itself, re-read from live state:

- the deal is still `open`;
- it has **no** resting (`NEW`/`PARTIALLY_FILLED`) order left.

If either is false there is nothing to restore and nothing is placed, so the
restore cannot duplicate a live order or resurrect a closed deal.

`getTPOrder` sizes from the deal's own position, satisfying §3.4: the restore
never reads a wallet total.

Place-then-cancel was rejected as the alternative the brief offers. On spot the
resting take-profit *holds the base*, so sending the replacement first would be
refused for funds by construction — it would turn an intermittent failure into a
universal one.

### §4.2 Surface it instead of going quiet

When §4.1 runs and the deal STILL has nothing on the book, the close is
unfundable from the deal's own allocation. Then:

- report it to the user through the existing `processError` path with
  `force`, so it is not collapsed into the daily-coalesced `Not enough balance`
  message that the latched guard has already stopped refreshing;
- emit one distinct, greppable line naming the deal and what it holds.

### §4.3 Clamp adaptive close to the deal's own position

`Math.min(find.free, tpOrder.qty)` at `dcaHelper.ts:6790` gains the deal's own
tracked position as a third term, computed with the existing pure
`trackedPosition` helper (already imported in this file for the reconcile pass).

The branch is spot-only (`!this.futures`), so no contract conversion applies and
the plumbing is the base-denominated case alone. Being a third term of a
`Math.min`, it can only ever make the close SMALLER — it cannot refuse an order
that is fundable today.
