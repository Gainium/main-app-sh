# 092 — String-literal-union fields lose their enum in the public OpenAPI spec

## §1 Definition

### §1.1 Expected

For every bot settings field whose value set is closed, the published OpenAPI
document (`src/server/v2/openapi-v2.yaml`, served publicly at
`https://api.gainium.io/api/v2/openapi.yaml`) must describe that field as
`type: string` with an explicit `enum:` listing exactly the values the `POST
/api/v2/bots/*` validators accept, and its `example:` must be one of those
values.

Concretely for grid bots (`components.schemas.BotSettings`):

| field | accepted values (validator) |
|---|---|
| `tpSlCondition` | `valueChanged`, `priceReached` |
| `tpSlAction` | `stop`, `stopAndSell` |
| `slCondition` | `valueChanged`, `priceReached` |
| `slAction` | `stop`, `stopAndSell` |
| `prioritize` | `gridStep`, `level` |
| `gridType` | `geometric`, `arithmetic` |

### §1.2 Actual

All six are published as `type: object` with **no** `enum:`, and four of them
carry an `example:` that the validator rejects outright:

```yaml
prioritize:      { type: object, example: volume }     # not in [gridStep, level]
gridType:        { type: object, example: arithmetic } # valid value, wrong type
tpSlCondition:   { type: object, example: any }        # not in [valueChanged, priceReached]
tpSlAction:      { type: object, example: close }      # not in [stop, stopAndSell]
slCondition:     { type: object, example: price }      # not in [valueChanged, priceReached]
slAction:        { type: object, example: closeAll }   # not in [stop, stopAndSell]
```

An integrator who copies the documented example into `POST /api/v2/bots/grid`
gets `Field <name> must be one of ...` back. `type: object` also breaks
generated clients, which model the field as a nested object rather than a
string.

## §2 Evidence

1. **Live production serves the defect.** `curl -sL
   https://api.gainium.io/api/v2/openapi.yaml` → lines 899–932 contain exactly
   the six blocks above.
2. **The committed YAML is byte-identical to the generator's own output.**
   On a clean `origin/main`, `npm run generate:schemas` rewrote
   `openapi-v2.yaml` and `git diff` was **empty**. So the YAML is not
   hand-edited drift — the generator deterministically produces it, and
   regenerating alone changes nothing.
3. **The validator really rejects those values.**
   `src/server/v2/validators/bots/config.ts` `gridBotSchemaConfig`
   (≈ lines 2210–2245) declares `ValidatorsEnum.shouldBeValidEnumValue` with
   the enum arrays in §1.1; `src/server/v2/validators/bots/schema.ts:97` passes
   `config.enum` to that validator, which pushes an error for any value outside
   it.
4. **Origin is latent, not a regression.** `git blame` puts the
   `fieldMetadata` examples (`generate-openapi-schemas.ts:485,582,583,585,586`)
   and the `return { type: 'object' }` fallback (`:1155`) all on `f036f2d`
   (2026‑02‑17, *"wip: api v2"*) — the commit that created the file. The union
   type aliases themselves predate it (`0e08c6c`, 2025‑06‑30) and the validator
   enums arrived after it (`a4a43c2`, 2026‑02‑20). The published spec has never
   been correct for these fields.

## §3 Assumption (hypothesis)

`SchemaGenerator.parseTypeNode` resolves a `TypeReferenceNode` against three
things only: TS `enum` declarations collected by `parseEnum`, the `typeMapping`
primitives, and `referenceableSchemas`. A **string-literal union type alias**
(`export type TpSlAction = 'stop' | 'stopAndSell'`, `types.ts:287–313`) matches
none of them, so it falls through to the `// Complex types` branch and is
emitted as `{ type: 'object' }` with no `enum`.

`parseTypeAlias` does not rescue them either: its name filter only admits
aliases containing `Backtest`/`Request`/`Result`/`Payload` or a fixed list, so
`TpSlAction`, `TpSlCondition`, `Prioritze` and `GridType` are skipped entirely.

Because no `enum` is ever attached, nothing constrains the hand-written
`fieldMetadata` examples, and four of them drifted away from the validator
without any signal.

## §4 Scope

§4.1 The generator must resolve a type alias that is a union of string literals
(or a single string literal) to `{ type: 'string', enum: [...] }`, the same
shape it already produces for a TS `enum`. This is field-agnostic: it fixes
every generated schema (`BotSettings`, `DCABotSettings`, `ComboBotSettings`,
`BaseSettings`, …), not only the six grid fields.

§4.2 The four invalid `fieldMetadata` examples must be corrected to a member of
the field's enum.

§4.3 The committed `openapi-v2.yaml` must be regenerated, because the YAML —
not the metadata map — is what users and generated clients read.

§4.4 A test must fail if the published enum for a grid TP/SL field ever drifts
from `gridBotSchemaConfig` again, and if any documented example is not an
accepted value.

## §5 Out of scope

§5.1 Changing any accepted value. The validators are correct; the docs are wrong.

§5.2 The generator's `$ref`/intersection/array handling.

§5.3 Deploying. The published spec only changes once `main-app` ships.
