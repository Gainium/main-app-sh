# 034 — enough additions report an untouched ladder as fully spent

`updateUsage` caps a deal's reported maximum usage once its ladder is
consumed. It decides "consumed" by comparing two level counters, and add-funds
fills move one of them without moving the other — so on an indicator ladder,
three additions make a deal that has fired **no** safety order at all report
that it will never spend another unit.

Third and last of the `levels.complete` readers surveyed while fixing specs
`031` and `032`. The other, `getDealDCALevelToCheck`, turned out not to be
reachable — §5.

## 1. Definition

```ts
if (
  findDeal.deal.levels.complete > 0 &&
  findDeal.deal.levels.complete === findDeal.deal.levels.all
) {
  if (maxQuote > 0 && maxQuote > currentQuote) maxQuote = currentQuote
  if (maxBase > 0 && maxBase > currentBase) maxBase = currentBase
}
```

### 1.1 Expected

The cap means "this deal has no configured level left to place, so the most it
will ever use is what it has used". It must be true only when the ladder is
actually spent.

### 1.2 Actual

`levels.complete` counts add-funds fills (`updateDeal`'s add-funds branch
increments it), and `levels.all` does **not** grow with them on an indicator
ladder. `updateDeal` recomputes `levels.all` as

```ts
Math.max(complete, 1 + initialOrders(dealRegular).length, 1 + funds.length)
```

whenever `currentOrders` holds no `dealRegular` — always true for
`dcaCondition: indicators`, whose safety orders fire on signals rather than
resting (spec `032` §1.3). So with `k` levels consumed and `n` additions,
`complete = 1 + k + n` climbs while `all` stays at `1 + ladderSize`, and the
two meet at `k + n = ladderSize` — reachable on `n` alone.

On the percentage ladder `levels.all` grows with each addition too
(`… + pendingAddFunds.length + funds.length`), so the two stay apart. This is
an indicator-ladder defect.

## 2. Evidence

Paper stack, LINK/USDT, `dcaCondition: indicators`, three `startDca`
indicators, `orderSize` 20 quote, `volumeScale` 2 — deal
`6aa27259393202032e5754d9`. Three additions of 10 USDT, and **no safety order
fired at any point** (an indicator ladder rests nothing; the deal was waiting on
signals throughout):

| step | `levels` | `usage.max.quote` | `usage.current.quote` | headroom |
|---|---|---|---|---|
| deal opened | 1/4 | 80.1822 | 20.0481 | 60.13 |
| add 10 | 2/4 | 90.2062 | 30.0722 | 60.13 |
| add 10 | 3/4 | 100.2303 | 40.0962 | 60.13 |
| add 10 | **4/4** | **50.1202** | **50.1202** | **0** |

The first two additions raise both figures and leave the headroom untouched at
60.13, which is right — an addition spends money and reserves none. The third
makes `complete === all` true and the cap fires: reported maximum usage drops
from 100.23 to 50.12, below where it stood two steps earlier, and the deal now
claims it will never spend again while all three indicator levels are still to
come.

## 3. Assumption (root cause, stated as hypothesis)

`levels.complete === levels.all` is being used as a proxy for "the ladder is
spent", and it is not one: the two counters count different things and treat
additions differently. The question has a direct answer — how many configured
levels the deal has consumed, against how many it was configured with — and
both terms already exist (`nextLadderLevel` from spec `031`, `dcaLadderSize`).

## 4. Required behaviour

### 4.1
The cap applies when the deal has no configured ladder level left to place:
`ladderSize - (nextLadderLevel(deal) - 1) <= 0`, where `ladderSize` is
`dcaLadderSize(settings)` — `ordersCount`, the custom-step count, or the
`startDca` indicator count, whichever the deal's `dcaCondition` uses.

### 4.2
Add-funds fills do not bring the cap closer, on any `dcaCondition`.

### 4.3
A deal with DCA switched off has no ladder, so the cap applies as soon as its
base order has filled — as it does today, where `levels.all` is 1 and
`complete` reaches 1.

### 4.4
A deal that has never taken add funds is capped exactly when it is today. This
is the case every existing deal is in, and the one that must not move.

### 4.5
No migration. `usage` is recomputed by `updateUsage` on every fill and every
balance change, so a deal capped early reports correctly again on its next
recomputation.

### 4.6 — a difference this exposes, deliberately
On the indicator path, `levels.all` is built from `initialOrders`, whose
`dealRegular` rows `createInitialDealOrders` generates from `ordersCount` —
NOT from the number of `startDca` indicators, which is what can actually fire.
A bot with 3 indicators and `ordersCount: 5` therefore compares against 5
today. §4.1 compares against 3, the ladder the deal really has. That is a
correction, not a side effect, and it only shows on bots where the two
disagree.

## 5. The sibling that is NOT a defect

`getDealDCALevelToCheck` reads the same counter as a ladder position —
`lastLevel = levels.complete` for a non-combo deal, filtering
`currentOrders` for `o.dcaLevel && o.dcaLevel > lastLevel` — and was carried
into this survey as a suspect. It is not reachable:

- `createInitialDealOrders` builds a DCA ladder row with `number` and
  `levelNumber` and **no `dcaLevel`** (`dcaHelper.ts:15725`), and
  `mapOrderToGrid` only copies `dcaLevel` from an order that has one, so a
  plain DCA deal's `currentOrders` carry `undefined` throughout;
- the filter's `o.dcaLevel &&` guard therefore rejects every row, the method
  returns its default, and the level check never arms — whatever `lastLevel`
  is;
- `dcaLevel` is populated only by `comboHelper`, and a combo deal takes the
  `lastFilledLevel` branch instead. Combo also returns early from
  `addDealFunds`, so it has no additions to be inflated by.

So the `levels.complete` arm of that method is unreachable dead reasoning
rather than a live miscount. Left alone: it is not on any defect's causal path,
and removing dead code in a 23k-line shared file is its own change.
