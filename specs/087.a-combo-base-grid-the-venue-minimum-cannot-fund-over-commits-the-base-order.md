# 087 — A combo base grid the venue minimum cannot fund over-commits the base order

Bug spec. The behaviour exists and is wrong. Spinoff from spec 086, which
deliberately left this exactly where it was (086 §5.3 pins it as a control).

## 1. Definition

### 1.1 Expected

A Combo **futures** bot must never open a position larger than the base order
notional the user configured.

Its base grid divides one budget — the base order's own notional — across
`baseGridLevels` levels, and on futures `comboHelper.getBaseOrder` re-sizes the
base order to the sum of those levels so the position and the ladder that
unwinds it agree (spec 086 §1.1). So when the budget cannot fund every level at
the venue's per-order minimum, there is no size the grid can take that is both
placeable and within budget: the only correct outcome is to **refuse to open the
deal and tell the user the budget the level count actually needs** — the answer
grid bots already have in spec 068 (`gridBudgetGuard`,
`BotHelper.refuseStartBelowMinimumBudget`).

### 1.2 Actual

`MainBot.generateGridsOnPrice` raises every below-minimum level to the venue
minimum (`if (qty < symbol.baseAsset.minAmount) qty = symbol.baseAsset.minAmount`
and the min-notional clamp below it). Nothing reconciles the resulting sum
against the budget, and the futures branch of `getBaseOrder` copies that inflated
sum onto the base order. The bot opens a materially larger position than
configured, silently — no warning, no refusal.

The sizing routine already records what it wanted against what the minimum
forced, on this exact path (`MainBot.lastGridSizing`). **Nothing on the combo
path consults it** — `BotHelper.refuseStartBelowMinimumBudget` (grid bots) is its
only reader.

## 2. Evidence

Runtime, through the real `comboHelper.getBaseOrder` and the real
`MainBot.generateGridsOnPrice` — the spec 086 harness, no venue, no Mongo, no
Redis. Reported fixture: OKX-style linear SOL perpetual, lot step `0.01`, min qty
`0.01`, min notional `1`, price `117.56`, base order `10` quote, LONG. Budget
after the base order's own lot floor is `9.4048` quote.

| base grid levels | base order | notional placed | ratio to budget | `lastGridSizing` wanted / minimum | `gridBudgetVerdict` |
|---|---|---|---|---|---|
| 3  | 0.08 | 9.4048  | 1.000× | 0.026479 / 0.01 | no refusal |
| 5  | 0.08 | 9.4048  | 1.000× | 0.015897 / 0.01 | no refusal |
| 8  | 0.08 | 9.4048  | 1.000× | 0.009940 / 0.01 | no refusal |
| **11** | **0.11** | **12.9316** | **1.375×** | 0.007230 / 0.01 | refuse, needs 13.01 |
| 20 | 0.21 | 24.6876 | 2.625× | 0.003977 / 0.01 | refuse, needs 23.65 |
| 50 | 0.51 | 59.9556 | 6.375× | 0.001591 / 0.01 | refuse, needs 59.11 |

Three things this settles:

- `lastGridSizing` **is** populated on the combo futures base-grid path, in base
  units, with a usable `minimum` — the guard has the numbers it needs.
- `gridBudgetVerdict` refuses **exactly** the rows that over-commit and no
  others. The 8-level row is the boundary: `wanted` is already under `minimum`,
  and the 10 % tolerance plus spec 086's residual carry keep the placed notional
  at exactly the budget, so the verdict correctly declines to refuse it.
- The refusal message's `minimumBudget` (13.01) tracks what the grid actually
  committed (12.93), so the figure shown to the user is the real one.

## 3. Assumption (hypothesis, not fact)

The root cause is the **missing reader**, not the clamps. The clamps are correct
in isolation — a level below the venue minimum cannot be placed — and spec 086
deliberately does not reconcile them, because reconciling downward would make the
grid unplaceable. The defect is that the combo path never asks the question grid
bots ask: *can this budget fund every level at the venue minimum, and if not,
should this deal open at all?*

Therefore the fix adds a reader on the combo new-deal path and changes no
quantity. The test must fail because no refusal happens, not because a size is
wrong.

## 4. Scope of the refusal

Decided against the bot-level, start-time refusal grid bots use (spec 068), for
three reasons that are properties of combo bots rather than preferences:

§4.1 A combo bot holds a **pair list**. The needed budget is per-pair
(`≈ levels × max(minQty × price, minNotional)`), so stopping the bot would halt
pairs that are correctly funded because one pair is not.

§4.2 The condition is **price-dependent**. A pair that is fundable at start
becomes unfundable as its price rises, and a screener-added pair is never seen at
start at all. A start-time-only check is incomplete by construction.

§4.3 The refusal must reach bots that are **already running** in this state. A
start-time check does nothing for them until someone restarts them; a per-deal
check catches them on their next deal.

So: refused **per pair, at new-deal time**, in `comboHelper.openNewDeal`, beside
the existing per-pair "not enough balance" refusal and with the same
once-per-(pair, condition) latch (spec 008). The bot keeps running; the pair that
cannot be funded does not open a deal.

## 5. What the test pins

§5.1 **The refusal.** With 11 levels on the fixture above, the new-deal path
refuses and reports a message naming the budget the level count needs. No base
order is placed.

§5.2 **The message.** It names the configured budget, the needed budget rounded
up, the level count and the pair, and — because this is a per-pair refusal, not a
bot stop — it does not claim the bot will stop.

§5.3 **Reported once per pair.** A second refusal for the same pair reports
nothing; the latch clears when the pair becomes fundable again.

§5.4 **A correctly funded pair is untouched.** At 3, 5 and 8 levels the guard
does not refuse, and the sizes spec 086 produced are unchanged.

## 6. What must not move

§6.1 Spec 086's residual carry: at 2, 3, 5 and 7 levels the placed notional stays
within one lot step under the budget and never over it. This change alters no
quantity anywhere, so 086's whole suite must stay green unmodified except for the
control named below.

§6.2 Spot combo base orders are untouched — the guard is on the futures
new-deal path only, and the spot branch never copies the grid sum onto the base
order.

§6.3 Grid bots are untouched: `gridBudgetVerdict`, `gridLevelMinimum` and
`BotHelper.refuseStartBelowMinimumBudget` keep their present behaviour and
`gridBudgetRefusalMessage` renders identically for them.

§6.4 Spec 086 §5.3 pinned today's over-commit as a control ("left exactly as it
was"). That control is now the defect this spec fixes; it is inverted here, and
086's §5.3 is retitled to point at this spec. The *sizing* it observed is
unchanged — 11 levels still size to 0.11 — what changes is that no deal now gets
that far.

## 7. Open questions

§7.1 The combo **minigrid** goes down the same sizing routine and populates the
same `lastGridSizing`, so a minigrid whose budget cannot fund its levels
over-places in the same way. Out of scope here: the minigrid places resting limit
orders rather than the position, so it is not the "opens a position larger than
configured" defect. Asked separately.

§7.2 Whether a bot-level, start-time refusal should be added on top, for the
louder "this configuration is wrong" signal. Raised with the operator; §4 stands
either way, since a start-time check cannot replace the per-deal one.
