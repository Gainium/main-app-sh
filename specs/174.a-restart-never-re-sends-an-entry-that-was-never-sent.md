# 174 — A restart never re-sends a deal's entry when the order it holds was never sent

`sendOrderToExchange` puts an order in the order map first, then awaits its
write-ahead row (`orderId: '-1'`), then sends it. If the process stops after
the map change has reached the debounced Redis `orders` snapshot but before
the row lands, the snapshot holds an entry (`dealStart`) order that Mongo never
received and the venue never saw.

On the next cold restart, `restoreWork` walks the deal, which is still
`start`. Mongo has no `dealStart` row for it, so the deal takes the "never
started" branch, which logs `not started yet. Place base order again` and calls
`placeBaseOrder`. `placeBaseOrder` finds the snapshot's entry in the order map
(`currentBase`), logs `already have and active base order`, and returns. Nothing
is bought. Every later restart restores the same snapshot and refuses the same
way. The only exit is the 24 h quarantine floor of `noteOrderNotFound`.

This is spec 172 §4.1, which that spec left out of scope.

## §1 Definition

### §1.1 Expected

- **§1.1.1** On the service-restart pass of `restoreWork`, a `start` deal that
  reaches the "never started" replay (no `dealStart` row in Mongo, not a funded
  entry, ASAP start condition) first checks each entry order the order map
  holds for it that still carries the `'-1'` placeholder. Such an order is
  removed from the map when the venue definitively answers that it does not
  exist (`getOrderForReconcile` + `isDefinitiveOrderNotFound`) and
  `MainBot.retireUnsentOrder` agrees. That means Mongo has no row for its
  client order id and it is older than `unsentOrderMinAgeMs`. `placeBaseOrder`
  then places the entry, exactly once.
- **§1.1.2** An entry order the venue reports as existing, or for which the
  lookup is not a definitive not-found (a timeout, a rate limit, anything
  ambiguous), stays in the map. `placeBaseOrder` refuses as before, and nothing
  is sent.
- **§1.1.3** An entry order that has a Mongo row is never retired by §1.1.1,
  even if the venue says it does not exist.
- **§1.1.4** An entry order with a real exchange id is not looked up by
  §1.1.1. `placeBaseOrder`'s refusal is unchanged for it.
- **§1.1.5** §1.1.1 runs only on a service restart. A user start or a settings
  reload does not reach it.

### §1.2 Actual

- **§1.2.1** `restoreWork` calls `placeBaseOrder` straight away. The
  `currentBase` guard returns on the snapshot's `'-1'` entry without asking the
  venue, so a deal whose entry was never sent stays `start` with nothing bought.

## §2 Evidence

Production, 2026-10-18. This is the same congested Binance DCA worker as spec
172 §2.

- 14:50:59Z: `Deal created with id …`. The deal's base order first shows up
  2 s later, in `Reconcile could not read 1 order(s) after 1 lookup attempt(s)`.
  The lookup stopped after one attempt, which is the definitive not-found stop
  of `reconcileLookup`. The same line repeats every 5–7 min until 16:15Z.
- Restarts at 14:54:37Z, 16:29:44Z and 17:01:12Z each log
  `… not started yet. Place base order again` and, in the same millisecond,
  `Deal … already have and active base order`.
- Mongo now: the deal is `start` and has no rows in `orders`. No
  `Error saving order` line exists for the base order's client order id.

## §3 Assumption (hypothesis)

The worker stopped after the base order was put in the order map and the
`orders` snapshot had flushed, but before its awaited write-ahead insert
landed. Under that assumption, a test that drives the real `restoreWork` and
the real `placeBaseOrder` with such a snapshot entry never builds a new base
order.

## §4 Out of scope

- **§4.1** An entry row stuck at `orderId: '-1'`, `NEW` in Mongo. That deal
  takes the `checkBaseOrder` branch, not this one, and such a row can stand for
  an order that did fill on the venue. §1.1.3 deliberately leaves it alone.
- **§4.2** Changing the `currentBase` refusal in `placeBaseOrder`. It is the
  double-entry guard for every other caller.
- **§4.3** Combo deals (`comboHelper`), which have their own restore path.

## Invariants

The stuck state is already covered by `deals.start-stuck-nothing-resting` in
main-app `specs/invariants/deals.invariants.json`. It flags a `start` deal older
than 30 minutes with nothing resting, which is exactly the Mongo-side picture
of §1.2. This spec adds no new invariant.
