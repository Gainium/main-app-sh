# 208 — the placement answer opens the deal before the top-up merges

Bug spec. Touches the DCA base-entry placement (`dcaHelper.placeBaseOrder`,
its `FILLED` answer branch) and, through it, the remainder top-up that
`MainBot.fillPartiallyFilledOrder` / `buyRemainder` already own.

## 1. Definition

### 1.1 Expected

A base order the venue fills short of what was asked is topped up by
`buyRemainder` (the difference, or the venue minimum when "Remainder full
amount" is on), and the top-up is merged into the base-order row. Whichever
path opens the deal, it opens on that merged row: the deal's size, initial and
average price, balances and take profit count every unit the entry bought.

### 1.2 Actual

Two paths read the same `FILLED` base order: the user-stream consumer
(`processOrderQueue`, which runs `fillPartiallyFilledOrder` on every report)
and the placement answer (`placeBaseOrder`, which calls `startDeal(result)`
directly). On a venue whose placement answer is not the one that tops up, the
answer opened the deal on the part-fill while the stream's top-up was still in
flight. When the merge landed a moment later, `startDeal` found the deal
already `open` and booked nothing. The base-order row then says more than the
deal holds; the top-up's coins are in the account and in no ledger.

### 1.3 Not changing

Whether a top-up is sent, its size, and which quantity it is sized from are
unchanged: every `FILLED` base order already passes through
`fillPartiallyFilledOrder` on the stream path, and its per-order mutex plus
`partiallyFilledFilledSet` make it run `buyRemainder` once per order whoever
arrives first. A base order that filled in full opens its deal exactly as
before, with no wait.

## 2. Evidence

Production, a Bitget spot LONG DCA deal (SUSHI/USDT), MARKET base order for
7.2923, venue minimum 5, "Remainder full amount" on. Bot log, one worker:

```
11:58:31.090  Send base order
11:58:31.460  Processing msg … D-BO-…, FILLED, 0.2069, base: 7.2571
11:58:31.460  Order D-BO-… not BUY full qty: executed - 7.2571, total - 7.2923, … increased to exchange minimum 5
11:58:32.719  Save order D-BO-…                     ← the placement answer
11:58:32.720  Base order FILLED                     ← startDeal on 7.2571
11:58:33.079  Buy remainder executed - GA-BR-…, base - 5
11:58:33.079  Total order D-BO-…, base: 12.2571     ← merge, deal already open
```

The deal's `size` is 7.2571; its `dealStart` row has `executedQty` 12.2571
against `origQty` 7.2923, and the `GA-BR` row is `FILLED` for 5.

Code: `placeBaseOrder`'s branch `else if (result.status === 'FILLED') await
this.startDeal(result)` never consults `fillPartiallyFilledOrder`. The answer
path inside `sendOrderToExchange` calls it only for Bybit CANCELED-with-fill
and Kraken USD-M reduce-only closes. `startDeal` acts only on a deal in
`start`.

## 3. Assumption (hypothesis)

The deal is booked short because the answer branch opens it without going
through `fillPartiallyFilledOrder`, so it neither waits for a top-up the
stream already has in flight nor merges one itself. Routing a short `FILLED`
answer through `fillPartiallyFilledOrder` and persisting what grew — the same
two steps the stream consumer takes — makes the deal open on the merged row in
both orders of arrival, with one top-up.

A test that drives the real `placeBaseOrder`, `fillPartiallyFilledOrder` and
`buyRemainder` must see `startDeal` receive the part-fill today, for exactly
this reason.

## 4. Behaviour

- **§4.1** Stream first (the production order): the answer branch waits for
  the in-flight top-up and opens the deal on the merged row.
- **§4.2** Answer first: the answer branch runs the top-up, opens the deal on
  the merged row and persists it; the stream's later report of the same order
  sends no second top-up.
- **§4.3** One top-up per order, of the same size as before, in both orders of
  arrival.
- **§4.4** A base order that filled in full opens its deal on the answer as
  is: no top-up, no extra database write.

## Invariants

- An open DCA deal whose entry rows (base row included, uncapped — a merged
  top-up legitimately lifts it above `origQty`) filled more than 1% beyond its
  size. Owned by main-app `specs/invariants/deals.invariants.json`,
  `deals.books-below-filled-entry-rows`.
