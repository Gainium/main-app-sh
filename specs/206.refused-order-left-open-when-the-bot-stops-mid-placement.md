# 206 — a refused order is left open when the bot stops while it is being placed

Bug spec. Follows spec `013` (a locally refused order must not be left open)
and spec `189` (one grid close per bot).

## 1. Definition

### 1.1 Expected

An order the venue refuses outright, or one a local guard refuses, never
leaves an `orders` row at `status: 'NEW'`, `orderId: '-1'`. A venue refusal
retires the row as CANCELED, a local refusal deletes it (spec `013`). This
holds even when the bot stops between the moment the order is written ahead
and the moment the answer arrives.

### 1.2 Actual

`sendOrderToExchange` writes the order ahead (`saveOrderToDb`) and puts it in
`this.orders` before asking the venue. If `stop()` runs while the request is
in flight, `clearClassProperties` replaces `this.orders` with an empty map.
The refusal branch then reaches its write-off, which is gated on
`this.orders.size > 0`, finds the map empty and skips both the CANCELED write
and the delete. The row stays `NEW`/`'-1'` with nothing logged. The dashboard
shows it as an open order and `loadOrders` reloads it on the next start.

## 2. Evidence

Production, a Hyperliquid spot grid with stop-loss "stop & sell":

- Its stop-loss close filled, then a second close was placed 13 ms after the
  first close's `stop()` started (the re-arm spec `189` §6 now prevents).
- `Set timer 60s to send close bot signal` (the end of `stop()`) is logged
  13 ms after that second close was written ahead. The venue refusal
  (`Not enough balance … order type: grid close`) is logged about 1.1 s later.
- No CANCELED write and no delete follow. The row is still `NEW`/`'-1'` and
  the sentinel invariant `184.open-order-without-exchange-id` raised it.

## 3. Assumption (hypothesis)

The write-off is gated on the in-memory map being non-empty. `stop()` wipes the
map while the placement is in flight, so the gate skips the DB write-off for a
definitive refusal. Nothing else retires the row.

## 4. Required behaviour

- §4.1 A definitive venue refusal whose answer arrives after the bot's order
  map was cleared retires the row as CANCELED.
- §4.2 A local-guard refusal in the same situation deletes the row (spec `013`
  §4.1).
- §4.3 An AMBIGUOUS failure (`isAmbiguousOrderFailure` /
  `isPlacementReadBackMiss`) in the same situation is not written off: with
  the map gone the venue cannot be asked first, and writing off an order the
  venue may hold is the orphan this branch exists to prevent. The row stays
  for the next start's reconcile, as before.
- §4.4 With the map still populated nothing changes.

## Invariants

Covered by the existing `184.open-order-without-exchange-id` (main-app pack
`specs/184.invariants.json`). No new invariant.
