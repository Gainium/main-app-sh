# 010 — Kraken spot client order ids are too long for the venue to carry

Bug spec (existing behaviour is wrong). Issue #657, main-app half of the
end-to-end change. The connector half is `exchange-connector`
`core/specs/003.kraken-spot-native-cl-ord-id.md`, amended in the same change.

## §1 Definition

`MainBot#getOrderId(prefix)` must generate, for a **Kraken spot** bot, a client
order id that Kraken can carry verbatim as the order's native `cl_ord_id`, so
the id stored on the Gainium order row **is** the id the exchange knows the
order by.

### §1.1 Expected

For `exchange === ExchangeEnum.kraken`, `getOrderId()` returns at most **18
characters** of ASCII alphanumerics and `-`, which is Kraken's documented
free-text `cl_ord_id` form. `submitOrder` then sends that id unchanged, and
`orders.clientOrderId` in Mongo is directly usable to address the order at
Kraken.

### §1.2 Actual

`getOrderId()` (`core/src/bot/main.ts:5191`) branches for hyperliquid (`0x` +
16 random bytes), okx/mexc (32 chars, dashes stripped) and the Binance family
(broker-code prefix). There is **no Kraken branch**, so a Kraken spot bot falls
through to the 36-char default and emits a 35-character id:

```
D-RO       -> D-RO-LxoBulKtAO9GzBEqwjFXSMVHbaHM2H          len=35
GRID-STAB  -> GRID-STAB-zT5628Chkapir3xyA2iQWOpYw          len=35
```

Kraken accepts a `cl_ord_id` in exactly three forms — long UUID (8-4-4-4-12
hex), short UUID (32 hex, no dashes), or **free ASCII text of at most 18
characters**. 35 mixed-case alphanumerics is none of them, 17 characters over
the free-text ceiling, so the connector cannot pass the id through: it hashes
it to `sha256(id).hex.slice(0,32)` (the short-UUID form) before sending it
(`exchange-connector core/src/exchange/exchanges/kraken/index.ts:1985`).

### §1.3 Why the hash is not a fix on its own

The hash is deterministic and injective, so lookups work. What it costs is that
**the identifier in our database is not the identifier at the venue**:

- `orders.clientOrderId` (`D-RO-LxoBulKtAO9…`) and the `cl_ord_id` Kraken holds
  (`9210419c98bf80ee8e9366af653de77f`) are different strings, related only by a
  hash nobody can invert.
- Any read that starts at Kraken — an operator looking at the account, a support
  query, `getAllOpenOrders`' open-orders panel, a future reconciliation from the
  venue side — cannot get back to the Gainium order without re-deriving sha256
  over every candidate client id.
- Every new call site that wants to address a Kraken order has to remember to
  apply the same encoding, which is the class of coupling that produced the
  original `userref` defect.

Making the generated id legal free text removes the encoding entirely.

## §2 Evidence

### §2.1 The generated id, measured

Driving the real `MainBot#getOrderId` on a `kraken` bot over every prefix used
in the codebase (`GA-F`, `GA-BR`, `GA-BAL`, `D-BO`, `D-RO`, `D-ROA`, `D-TP`,
`D-TPR`, `D-SR`, `D-MSL`, `D-MTP`, `CMB-BO`, `CMB-RO`, `CMB-GR`, `CMB-H`,
`GRID-BO`, `GRID-RO`, `GRID-TP`, `GRID-STAB`), 2026-09-05:

```
longest generated kraken-spot client order id: 35 chars (Kraken ceiling: 18)
over ceiling by: 17 chars
D-RO      -> len=35  legalKrakenFreeText=false  cl_ord_id sent=9210419c98bf80ee8e9366af653de77f
GRID-STAB -> len=35  legalKrakenFreeText=false  cl_ord_id sent=7eb4ed2cb6647fe0e346a47858b54414
```

Every prefix produces exactly 35 characters — the default arm computes the
random tail as `36 - prefix.length - 2`, so the total is constant.

## §3 Assumption (hypothesis)

The root cause is that `getOrderId()` has no Kraken arm, so it emits an id 17
characters longer than the only free-text form Kraken accepts. Give Kraken spot
its own arm — `${prefix}-${random}` truncated to 18 characters — and the
connector can send the id verbatim, at which point the stored id and the venue
id are the same string and no encoding exists to keep in sync.

The load-bearing risk of shortening is **uniqueness**: the id must stay
collision-free across a bot's concurrent orders after losing 17 characters of
tail.

## §4 Required behaviour

- **§4.1 Length.** For `ExchangeEnum.kraken` (spot only — not `krakenUsdm`,
  `krakenCoinm` or any `paperKraken*`), `getOrderId(prefix)` returns at most 18
  characters.
- **§4.2 Shape.** `${prefix}-${tail}`, so the id keeps the prefix every existing
  reader greps for (`D-`, `CMB-`, `GRID-`, `GA-`). The prefix is never truncated.
- **§4.3 Alphabet.** Only characters Kraken's "free format ascii text" accepts.
  The existing `utils.id()` generator emits `[A-Za-z0-9]` and the prefixes add
  only `-`; both are ASCII, so no new generator is needed.
- **§4.4 Entropy bound.** The longest prefix in the codebase is `GRID-STAB` (9
  chars), leaving `18 - 9 - 1 = 8` random characters — 62^8 ≈ 2.18 × 10^14
  combinations, ~47.6 bits. A bot holds tens of concurrent orders, so a
  collision within the population that matters is not a practical risk. This
  bound is a **test**, not a comment: a future prefix long enough to starve the
  tail must fail the suite rather than silently shorten it.
- **§4.5 No other venue changes.** Every non-Kraken-spot arm of `getOrderId()`
  returns exactly what it returns today.
- **§4.6 Legacy ids keep working.** The 369 live 35-character ids are untouched;
  nothing rewrites or migrates them. Which resolution path a Kraken spot order
  takes is decided by the *shape of its own id*, in the connector (spec 003 §4.9).

## §5 Open questions / non-goals

- **§5.1 `venueOrderId()` is deliberately NOT changed.** The operator brief asked
  for `ExchangeEnum.kraken` to be removed from `venueOrderId()`
  (`core/src/bot/main.ts:1029`) so Kraken lookups are addressed by client id
  again. Measured, that is a regression today, twice over:
  1. All **361** live orders on multi-order bots (§2.2) carry 35-char legacy ids
     and, as of the 06:39Z 2026-09-05 connector deploy, **0** carry a native
     `cl_ord_id` — they are resolvable *only* by txid. Removing the kraken arm
     routes every one of them off the exact `QueryOrders` lookup and onto the
     legacy `userref` scan, where they are ambiguous by construction and are
     refused (connector spec 002 §4.2).
  2. `venueOrderId()` is also what keys `primeReconcileBatch()`
     (`core/src/bot/main.ts:1057`), and the connector batches **txids only**
     (`getOrdersBatch`, `kraken/index.ts:2110`). Client ids are not batchable, so
     the arm's removal silently disables the Kraken reconcile prefetch added
     2026-08-31 — the fix for 50.5% of Kraken order placements being parked
     behind reconcile bursts.

  It also buys nothing: `venueOrderId()` already *falls through* to
  `clientOrderId` whenever the order is not in the local order map, and
  `main.ts:7230`'s post-execution retry re-asks with the raw client id. Those are
  precisely the paths §4 and connector spec 003 §4.9 repair. Preferring the txid
  when we hold it is strictly more exact, not less.

- **§5.2 `cancelOrderOnExchange()` is not changed either.** Its kraken arm
  (`core/src/bot/main.ts:7929`) already sends `${order.orderId}` — the txid —
  and has since 2026-08-27 (`2b765a0`, bug #535). Same reasoning as §5.1.

- **§5.3 The `krakenSpot` branches audited, not moved.**
  - `main.ts:5021` — the user-stream fallback that looks an execution report up
    by `msg.orderId` (the txid) when the client-id lookup misses. It runs only
    when the primary lookup found nothing, so a stream report that now carries
    our own client id resolves on the primary path and never reaches it. Correct
    as a fallback either way; unchanged.
  - `main.ts:5166` — `clientOrderId: o.clientOrderId` on the reconcile merge,
    which stops an exchange-echoed id from re-keying the local order. Still
    load-bearing: a txid-addressed lookup comes back with the txid in
    `clientOrderId`. Unchanged.

- **§5.4 Not verified against a live Kraken account.** No Kraken credentials on
  this host and production is out of bounds. The id is verified to satisfy
  Kraken's documented free-text grammar and to survive the connector's
  discriminator (spec 003 §4.9); it is not verified by a real AddOrder.

- **§5.5 Paper Kraken keeps the 35-char id.** `paperKraken` never reaches
  Kraken, and paper-trading has no id-length constraint.
