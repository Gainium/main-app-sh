# 071 — The add-exchange failure line writes the API key down

Bug spec. Plan: `plans/071.the-add-exchange-failure-line-writes-the-api-key-down.md`.
Same class as the `exchange-connector-sh` credential-in-logs work (spec 011,
key-id log lines), and shares its fingerprint helper byte for byte.

## §1 Definition
- §1.1 Expected: a log line that needs to tell two add-exchange attempts apart
  identifies the credential without recording it. An operator reading the log
  must not come away holding a usable API key.
- §1.2 Actual: the `addExchange` resolver's failure branch interpolates the raw
  key — `key: "${key}"` — into a `logger.error` line. It fires on a FAILED
  verification, which is not the same as an invalid key: a key refused for an
  IP restriction, a missing trade permission or a wrong regional origin is a
  live credential, written to disk in the clear.

## §2 Evidence
- `src/graphql/resolvers.ts` `addExchange`, the `!verifyResult.status` branch;
  the cloud parent overrides the resolver and carries its own copy of the line.
- Prod census, main-app pm2 **error** logs, live plus every archive back to the
  oldest retained (2026-08-05): **682 lines, 307 distinct keys, 170 distinct
  users**, across kraken, bybit, coinbase, binance, bitget, okx, binanceUsdm
  and hyperliquid. Out logs: 0 lines.
- The same census found **no line carrying a secret value** — the venue error
  text names the word "secret" in 16 lines of guidance but never a value. The
  exposure is the key only.

## §3 Assumption
A fingerprint is enough for every operational use this line has ever served:
telling repeat attempts apart, and matching a main-app line to a connector line
for the same credential. Nothing reads the key out of the log.

## §4 Required behaviour
- §4.1 The failure line names the key as `key#<fingerprint>` and never contains
  the key, in both the core resolver and the cloud parent's override.
- §4.2 The fingerprint is stable per key and differs between keys.
- §4.3 The fingerprint is short, alphanumeric, and shares no 4-character run
  with the key it describes.
- §4.4 A missing or empty key fingerprints instead of throwing.
- §4.5 The fingerprint equals `exchange-connector-sh`'s for the same key, so
  one credential correlates across the two services' logs.

## §5 Out of scope, deliberately
- `core/src/exchange/verify.ts` `verifyPaper` puts its key and secret in a
  query string. Those are Gainium-generated paper credentials, not venue ones,
  and the URL shape is paper-trading's HTTP contract — changing it is a
  cross-service change, not a log fix. The census found no such URL in the logs.
- Scrubbing the 682 existing lines is a write to production log files and needs
  its own authorisation; this spec only stops new ones.
- Rotation advice for the 307 keys needs a credential mapping this change does
  not have.
