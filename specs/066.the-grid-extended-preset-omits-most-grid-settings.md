# 066 — The grid `extended` preset omits most grid settings, so a read-modify-create copy is not the bot that was read

## §1 Definition

`GET /api/v2/bots/grid?fields=extended` and
`GET /api/v2/bots/grid/details?fields=extended` both resolve the `bots.grid`
preset (`core/src/server/v2/fieldConfig.ts`) and turn it into a MongoDB
projection verbatim (`parseFieldsParam` → `buildProjection` → `botDb.readData`).
`POST /api/v2/bots/grid` builds the stored settings as
`{ ...GRID_FORM_DEFAULTS, ...input }` (`core/src/server/v2/api.ts:2576`).

The two are a round trip: **a settings field the caller cannot read back is a
settings field the create endpoint silently replaces with a platform default.**

### §1.1 Expected

`fields=extended` returns every setting `GRID_FORM_DEFAULTS` declares, except
the ones `POST /api/v2/bots/grid` refuses to accept (`GRID_EXCLUDED_FIELDS`),
so that reading a grid bot, changing a few values and creating the adjusted
copy preserves the bot's budget, grid step, take-profit / stop-loss thresholds,
and its futures configuration.

### §1.2 Actual

`GRID_BOT_EXTENDED_FIELDS` names **13** of the **38** settings
`GRID_FORM_DEFAULTS` declares. The other **25** are unreadable, so a copy comes
back on platform defaults:

- `tpPerc`, `tpTopPrice`, `slLowPrice` are unreadable while the TP/SL **flags,
  conditions and actions** (`tpSl`, `tpSlCondition`, `tpSlAction`, `sl`,
  `slCondition`, `slAction`) are readable — so the copy is created with its
  stop-loss **armed** and its **threshold** reset to `tpPerc: 20`,
  `tpTopPrice: 0`, `slLowPrice: 0`. A flag without its threshold is not a
  configuration.
- `marginType`, `leverage`, `strategy`, `futuresStrategy` unreadable means a
  cross-margin 5× LONG futures grid is copied as an isolated 1× NEUTRAL one.
  (`futures` and `coinm` are re-derived from the connected exchange by
  `addAditionalFields` on create, so those two are a fidelity gap on the read
  rather than a loss on the write — they are named for completeness, and
  because the create endpoint accepts them.)
- `budget`, `gridStep`, `ordersInAdvance`, `sellDisplacement`, `orderFixedIn`
  unreadable means the copy trades a different size on a different grid.

Nothing errors and nothing warns on the read; `meta.fields` honestly reports
the preset it used.

### §2.4 Two of the 25 must NOT be added

`validateCommonSchema` (`core/src/server/v2/validators/bots/schema.ts:213`)
rejects any field named in `GRID_EXCLUDED_FIELDS` with
`Field <name> is not supported`. For grid that is `updatedBudget` and
`newProfit`. Returning them at `fields=extended` would make the naive
read-modify-create body a **400**, which is the opposite of lossless. Neither
the `bots.dca` nor the `bots.grid` preset names an excluded field today.

### §2.5 What the evidence does NOT establish

The v2 API writes no per-request log, so no production log line shows a
specific caller losing these settings. The mechanism is proven by executing the
real preset/projection/merge code over a real stored document, not by observing
a user's request.

## §3 Assumption

*Hypothesis, not fact.* `GRID_BOT_EXTENDED_FIELDS` was hand-curated when the v2
field-selection feature was authored (`f036f2d` "wip: api v2", 2026-02-17) and
was never tied to `GRID_FORM_DEFAULTS`, which is the list
`POST /api/v2/bots/grid` merges against. The fix is to name the remaining
settings in the preset and to add a test that fails whenever the two lists
drift apart again. No behaviour outside `fieldConfig.ts` needs to change.

## §4 Scope

### §4.1 In scope

`GRID_BOT_EXTENDED_FIELDS` only. It is shared by `GET /api/v2/bots/grid` and
`GET /api/v2/bots/:botType/details?botType=grid` — both resolve `bots.grid`
through `parseFieldsParam`, so the change applies to the two surfaces
identically.

### §4.2 Out of scope

- `bots.dca` / `bots.combo` cover 10 of 169 declared settings — same class of
  gap, far larger blast radius, tracked separately.
- `settings.pair` is stored without a separator (`ARBUSDT`) while
  `POST /api/v2/bots/grid` requires the underscored form (`ARB_USDT`), so the
  read-back body is rejected on `pair` no matter how wide the preset is. A
  distinct defect with its own cause and fix; raised separately.

## §5 Contract

`/api/v2/*` is the public `api.gainium.io` contract (root Danger List #2) and
`fieldConfig.ts` is in `core/` (Danger List #11). The change is **purely
additive on the wire**: no name is removed, no name is renamed, and every added
name is a path that resolves on stored grid bots. A caller reading
`fields=extended` receives a superset of what it receives today. `fields=full`
and explicit comma-separated field lists do not go through the preset table and
are unaffected.
