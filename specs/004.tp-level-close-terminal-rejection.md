# 004 — `checkTPLevel` re-arms a market take-profit close at price-tick rate after a terminal venue rejection

Bug type spec (existing behaviour is wrong). Issue #627. Sibling of #617
(`49f085bc` / `fdf82410`, deploys 170+171), which made this failure *visible*
and *retrying* rather than silently latching the deal — the retry is the part
that is now wrong.

## §1 Definition

`DCABotHelper.checkTPLevel` (`core/src/bot/dcaHelper.ts`) is the price-tick
callback that turns a reached take-profit level into a MARKET close for deals
whose `closeOrderType` is `MARKET`. On the multi-TP branch it sends the close
with `sendGridToExchange`, then decides whether a close is "in flight".

### §1.1 Expected

When the venue refuses the close, the engine must:

- **§1.1.1** know *why* — the venue's own rejection text must reach the log line
  that reports the failed attempt, not be collapsed into a placeholder;
- **§1.1.2** distinguish a **terminal** refusal (the venue states there is no
  position to reduce — the `Futures position` subType in
  `core/src/bot/utils.ts`, e.g. `Reduce order is rejected`, `ReduceOnly Order`,
  `current position is zero, cannot fix reduce-only order qty`) from a
  **transient** one. Re-sending the same order cannot change a terminal answer;
- **§1.1.3** on a terminal refusal, **back off** — the next attempt must be
  gated by a growing cooldown, not by the next price tick;
- **§1.1.4** on a terminal refusal, **say so on the deal**. The `Futures
  position` subType is configured `showUser: false, errorsBot: false` in prod
  `boterrorsubtypes` (verified 2026-09-04), so the bot-level notification path
  tells the user *nothing*: a deal whose take-profit is not executing must
  raise a deal-scoped message instead;
- **§1.1.5** keep today's immediate re-arm for genuinely transient outcomes
  (`not placed`, `already processed`, a non-terminal refusal) — that is the
  #617 fix and it must not regress;
- **§1.1.6** never re-introduce the #617 latch: `closeByTp` must still be
  released, or every later tick short-circuits at the `already closing by TP`
  guard and `placeOrders` refuses every settings edit for the life of the
  process.

### §1.2 Actual

The call passes no `returnError`, so `sendGridToExchange` returns `void` for
*every* venue refusal and the outcome is recorded as the placeholder
`not placed` (§1.1.1 fails). Nothing classifies it (§1.1.2 fails), so the
`!closeInFlight` branch unconditionally releases `closeByTp`, re-arms the
level check, and the next price tick — throttled only to one per 500 ms per
symbol — sends the identical order again (§1.1.3 fails). The user is told
nothing (§1.1.4 fails).

## §3 Assumption (hypothesis)

The root cause is a **missing classification**, not a missing retry.
`checkTPLevel` discards the venue's answer (`returnError` defaults to `false`)
and therefore treats every failed close identically: as a transient miss that
should be re-armed immediately. A `futuresPosition` refusal is the venue
stating the position is not there; re-arming it against a price tick produces
an unbounded resend loop that can never succeed, costs the venue's rate budget,
and — because the subType is user-invisible — leaves the deal's take-profit
silently unexecuted.

Corollary the fix must respect: the *release* of `closeByTp` is correct (§1.1.6
/ #617). What must change is what gates the **next attempt**.

## §4 Open questions

- **§4.1** Cooldown bounds. Chosen: `minMs` 60 s, `maxMs` 15 min (factor 2), a
  shorter ladder than the 5 min → 1 h siblings (`nb`, `cr`, `er`) because this
  gates a *close*, and an over-long window on a position that reappears delays
  realising profit. Resolved in the plan, not by the spec.
- **§4.2** Whether the cooldown should also gate the single-TP
  (`closeDealById`) branch of the same trigger. Resolved in the plan.
