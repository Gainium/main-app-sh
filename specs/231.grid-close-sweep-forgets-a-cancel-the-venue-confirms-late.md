# 231 — A grid close sweep forgets a cancel the venue confirms late

Bug spec (Definition / Evidence / Assumption). Grid bots only.

## 1. Definition

### 1.1 Expected

When a grid bot closes (stop, stop-loss / take-profit "stop and sell", close by
limit / market), every resting order its close sweep cancels ends with its row
recording the venue's final state: `CANCELED` (or `FILLED` if it filled first).
A closed bot keeps no row `NEW` for an order the venue no longer holds.

### 1.2 Actual

On a venue whose cancel answer is a read-back of the order (Hyperliquid), the
answer can still describe the order as resting (`open` → `NEW`) although the
venue accepted the cancel. `cancelOrderOnExchange` then writes `NEW` and, because
nothing executed, drops the order from local tracking (`deleteOrder`: the order
map, `ordersKeys`, the shared stream route). The venue's own `canceled` report
arrives on the user stream a moment later and `accountCallback` discards it
without a log line: the id is no longer in `ordersKeys`. The row stays `NEW`
for good on a closed bot.

## 2. Evidence

- A long perp grid on a Hyperliquid builder-dex pair hit its stop-loss
  ("stop and sell"). The sweep cancelled ten reduce-only sells one at a time.
  The venue's user stream reported `canceled` for all ten (status timestamps
  ~1.3–1.7 s apart, each report ~0.85–1.1 s after its status time).
- The first six were processed (`Processing msg … CANCELED`, row `CANCELED`,
  `updateTime` = the venue's status time). The last four have no line at all
  after their placement: no `Processing msg`, no `Send request to unknow order`,
  no cancel error. Their rows are still `NEW` with the placement `updateTime`.
- The only branch of `cancelOrderOnExchange` that logs nothing and leaves the
  row `NEW` is the OK branch with an answer of `NEW`: an answer of `CANCELED`
  would have been written, and every error branch logs. Hyperliquid's
  `getOrder` maps only `open` to `NEW`.
- The bot's in-flight answer and the stream report race: for the processed six
  the stream won (the order was still in the map); for the four it lost.
- Found by the sentinel invariant `grid.closed-bot-order-resting`.

## 3. Assumption (hypothesis)

The read-back that forms Hyperliquid's cancel answer can lag the cancel itself,
so a successful cancel is answered `NEW`; deleting the order from local
tracking on that answer is what makes the venue's later confirmation
unreachable. Tests in §5 fail on exactly that: the stream report for the
cancelled order is not routed to `processOrderQueue`.

## 4. Required behaviour

- §4.1 During a grid close sweep, a cancel the venue accepted whose answer
  still says `NEW` keeps the order tracked (map, `ordersKeys`, stream route),
  so the venue's own report reaches `processOrderQueue` and the row.
- §4.2 At the end of a close sweep, each order whose answer said `NEW` and
  that is still held as resting is cancelled once more. The venue's answer to
  that second cancel ("already cancelled" → the unknown-order lookup, or
  `CANCELED`) records its state before the user stream is closed.
- §4.3 Unchanged outside a grid close sweep: `start`/`reloadBot` cancel sweeps,
  running-bot cancels, DCA and combo keep today's delete-on-zero behaviour.
- §4.4 Unchanged inside the sweep for answers that are terminal (`CANCELED`
  with nothing executed is deleted as before; spec 220's kept fills still
  hold).

## 6. Invariant

None added: the defect's wrong state is exactly what
`grid.closed-bot-order-resting` (main-app `specs/invariants/deals.invariants.json`)
already detects — that is how it was found.
