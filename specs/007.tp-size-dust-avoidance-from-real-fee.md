# 007 — Let a whole-deal third-asset fee skip the TP quantity gross-up

Part 3 of the fee-accuracy initiative (`websocket-connector-sh` spec `003`,
`app-sh` spec `006`). Depends on `006` — this needs `feeByAsset` and the
new-deal flag to know, cheaply, whether a deal's fee was ever paid
on-pair. Also depends on spec `008` (a new integration-test harness this
repo doesn't have yet) for §7's gate-2/6 tests — see §10. **This spec is
deliberately narrow.** The wider idea in the original ask — "know the
real fee, size the TP to avoid dust" — turns out, on tracing the code, to
collide with two explicit, dated warnings against exactly that kind of
change. §1 explains why; §2 is the one piece that survives the warning
intact; §4 is what this spec is *not* attempting, and why that's a
separate, harder piece of work. §6-§9 were added on review: what happens
when the fee signal §2's predicate trusts is itself wrong, not because of
a third asset, but because of a silent reporting failure — and the
two-stage TP placement that catches it.

## §1 Current behaviour — one account-wide rate, applied twice, and warned about twice

TP sizing is not per-order. `getBaseOrder` (`dcaHelper.ts:7622-7627`) grosses
up the entry by one account-level `fee.taker`/`fee.maker` (`feeFactor`);
`getTPOrder` (`:13232,13251-13252`) grosses the close by the same
account-level `worstFee(fee)` (`maxFee`) in the opposite direction. Both
already skip the gross-up entirely on futures (`:7622-7624`,
`:13096-13101` — futures charges margin in quote, never takes the fee out
of the position, so there is no base-quantity dust to avoid there; only
the TP/SL *price* leg still needs the fee, via `priceFee`/`tpFees.ts`).

Both sites carry a dated (2026-08-27, referencing bug #396) comment
explaining that the gross-up is not "the fee we'll pay," it's "the exact
headroom the CLOSE side's own fee needs" — and that this holds for
different, venue-specific reasons on Binance-shaped venues (fee taken from
the asset received) versus Kraken (fee-currency defaults `fciq`/`fcib`
differ by side) — and that the two sites are "one mechanism and only
balance as a pair" (`:13249`). Both comments end with an explicit warning
not to "fix" this without re-deriving the venue-specific reasoning.

**Read literally, this means the account-level `fee.taker`/`maker` is not
simply "our best guess at the cost" — on at least one venue it is load-
bearing for a mechanism unrelated to accuracy.** Replacing it with each
order's real per-order observed fee is therefore not a drop-in
accuracy upgrade; it risks removing headroom the close side genuinely
needs, for reasons this spec's author has not re-derived per venue. That
re-derivation — done properly, the way bug #396's fix was — is real work
this spec does not attempt (§4).

## §2 What's safe to do now: an all-third-asset deal needs no quantity gross-up at all

One case does not touch that mechanism and is safe to reason about on its
own: **a deal every one of whose fees, for every filled order so far, was
paid in a third asset** (BNB/BGB/KCS) never had base or quote debited for
fees at all — the entry credited the full fill, and the close will too.
For that deal, `feeFactor` (entry) and `maxFee` (close) should be `0`, the
same way futures already zeroes them (`:7622-7624`, `:13096-13101`) — not
because the venue is futures, but because the same precondition that makes
futures' zeroing correct (nothing base/quote-denominated is taken out of
the quantity) happens to also hold here. This is a **new, third**
precondition for the existing zeroing, not a new mechanism.

`006`'s `feeByAsset` makes "every fee so far was third-asset" cheap to
check: on a **new-flagged** deal, if `feeByAsset` is non-empty and
`commission`/`feePaid.base`/`feePaid.quote` are all still `0`, every
observed fee so far was off-pair. A deal that mixes on-pair and off-pair
fees across its orders (a BNB balance that runs out mid-deal, mentioned as
already-handled per-order in `orderFee.ts:accrueStreamFee`'s "second
fee-currency mid-order" fallback) does **not** qualify — it falls through
to §1's existing behaviour unchanged, gross-up included, because for that
deal the "no base/quote fee headroom needed" precondition is false for
some of its orders.

## §3 The "must not break TP size" constraint

Whatever this changes, a TP order must still never ask for more than the
deal's own filled quantity provides — the concern raised alongside the
original ask ("obviously not possible when tp size more than all deal
filled orders"). `getTPOrder`'s `_qty = filledQty + boQty` (`:13231`)
already sums exactly what's been filled before any fee adjustment is
applied, and `prepareTpOrder` (`:5532-5543`) already caps a short spot
TP's notional against `currentBalances.quote`. Setting `feeFactor`/
`maxFee` to `0` for the §2 case can only ever **reduce** the grossed-up
quantity relative to today's behaviour (removing a gross-up removes an
addition) — it cannot make a TP ask for more than it does today, **as
long as the only change is zeroing the multiplier**. §8 item 1 is the
reason this can't be left as an informal argument: a corrupted/mis-signed
fee value feeding a future, less-conservative version of this mechanism
could push the multiplier the other way. Confirm the zeroing-only claim
against `prepareTpOrder`'s cap and any other qty-vs-balance check this
deal type has before implementing (gate 2 target — not traced
exhaustively here), and enforce it as a hard clamp in code (§7's
`quantityFeeIsThirdAssetOnly`-gated qty must never exceed what today's
`feeFactor`/`maxFee` would have produced) — not just an argument that
happens to be true for the one case this spec implements.

## §4 Explicitly out of scope for this spec

- **Per-order real fee replacing the account-level rate**, for a deal that
  mixes on-pair and third-asset fees across its orders, or where the
  on-pair real fee differs from the stored rate. This is the accuracy
  improvement the original ask was really after, and it is real — but §1
  means it requires the same per-venue economic re-derivation bug #396's
  fix did (what does "the entry's real fee" mean for *funding the close's
  own fee* on Kraken specifically, versus Binance), not a mechanical
  swap of `fee.taker` for an observed number. Recommend a dedicated
  follow-up spec once that venue-by-venue reasoning exists, written with
  the same rigor as the `:7601-7621`/`:13242-13250` comments it would be
  replacing.
- **Grid/combo TP sizing.** This spec traced DCA's `getBaseOrder`/
  `getTPOrder` only. Whether combo's TP path (`getTPOrder` is shared,
  per `006` §2.4) has the same all-third-asset opportunity, or a
  different one given `feeBalance`'s separate combo-only bookkeeping
  (`006` §1, item 5d in the original research), is not traced here.

## §5 Open questions (§2's mechanism)

- Is "commission and feePaid.base/quote both still 0" the right way to
  detect "every fee so far was third-asset," or does a deal that has had
  no fills yet (both legitimately 0, no fee observed at all either way)
  need to be excluded explicitly so it doesn't get miscategorized as
  "all-third-asset" by vacuous truth? Resolve in the plan.
- Should this be a live-recomputed check on every TP build, or a flag set
  once and revoked the moment an on-pair fee is first observed (cheaper,
  but needs a write at the point that happens)? Resolve in the plan.

## §6 The failure this spec was reopened to address: a silently-wrong fee signal

The question that reopened this spec: what if a venue or `websocket-connector-sh`
reports a fee of `0` — or reports nothing — not because the fill was
genuinely free, but because of a silent failure somewhere in the pipeline
(a parsing bug, a dropped field, a transient gap)? §2's predicate,
`quantityFeeIsThirdAssetOnly`, is **not** naively vulnerable to the
simplest version of this: it requires **positive evidence** of a
third-asset fee (`feeByAsset` non-empty), not merely "commission is 0" —
a deal with no fee data at all reads `false` (§5, already resolved), not
"all-third-asset."

**It is vulnerable to a narrower, real version of the same worry:** a deal
that had a genuine third-asset fee on an early order (so `feeByAsset` is
correctly non-empty) and then, on a *later* order, an on-pair fee that
silently failed to report — that later order's `commission`/
`feePaid.base`/`feePaid.quote` contribution stays `0` not because nothing
was charged, but because the report was lost. `quantityFeeIsThirdAssetOnly`
cannot tell "no on-pair fee was ever charged" apart from "an on-pair fee
was charged and we never heard about it" — both look identical from the
deal document's own fields. Zeroing the gross-up on that deal would then
be wrong: real base/quote fee headroom the close needs would be missing,
exactly the dust/rejection risk raised. **This is the concrete failure
mode §7's two-stage placement exists to catch** — not by making the
predicate smarter (there is no field on the deal that would tell it
apart), but by treating the zeroed-gross-up TP as a *hypothesis to test
against the venue*, with a defined fallback when the venue disagrees.

## §7 Two-stage TP placement: try the real-fee size, fall back to the estimated-fee size on rejection

### §7.1 The shape, anchored on an existing precedent

`closeDealById`'s "adaptive close" (`dcaHelper.ts:5903-5987`, described in
full in the research this spec is built on) already does exactly this
shape for a *different* input (TP qty capped by a fresh balance read
instead of the account's stored fee): try the computed TP → on a
balance-classified rejection → recompute from fresh state → resend once,
with a derived `clientOrderId` suffix (`ac`) so the two attempts are
distinguishable in logs/on the venue. §7 is the same skeleton, applied to
*which fee multiplier produced the size* instead of *which balance
reading bounds it*:

1. `quantityFeeIsThirdAssetOnly` says zero the gross-up → build and send
   the TP at that (smaller) size, `newClientOrderId` suffixed to mark it
   as the real-fee attempt (e.g. `...rf`, mirroring `...ac`).
2. **Rejected**, classified as a size-shaped rejection (§7.2 — deliberately
   wider than just `isErrorNotEnoughBalance`) → recompute the SAME TP with
   today's §1 behaviour (the account-rate gross-up restored) and resend
   once, suffixed `...ef`.
3. Whether step 2 succeeds or fails, **do not attempt a third size for
   this placement** — a step-2 failure falls through to whatever generic
   handling already exists for that rejection shape (§1/existing code,
   unchanged). This is one extra attempt composed onto the existing
   chains (§7.4), not a new retry loop.

### §7.2 Classifying the rejection — wider than the existing balance check

The research pass flagged this explicitly: `isErrorNotEnoughBalance`/
`notEnoughErrors` (`main.ts:2774-2781,283-296`) — the classifier the
"adaptive close" precedent already gates on — catches a *balance*
rejection. A TP under-sized by a missing fee gross-up could just as
plausibly be rejected as an *invalid quantity/lot-size* rejection if the
venue rounds the (too-small) requested size below its step size before
ever reaching a balance check — a shape `isErrorNotEnoughBalance` does
not recognize (confirmed: substring-matched against `notEnoughErrors`
only). §7's trigger must check both `isErrorNotEnoughBalance` **and**
`isNotionalReason` (`dcaHelper.ts:5450-5457,243-250`, the existing
min-notional/lot-size classifier) — resolve the exact boolean in the
plan, but it is `isErrorNotEnoughBalance(...) || isNotionalReason(...)`
at minimum, not the balance check alone.

### §7.3 The sticky flag — deal-level for DCA/combo, bot-level for grid, set once, read many times

The core of the original ask: placing a fresh TP is not a one-time event
on a DCA/combo deal — a new safety-order fill places a new TP, repeatedly,
for the deal's whole life; on a grid bot it happens continuously,
indefinitely. Retrying step-2-on-rejection *every single time* would
silently double every TP placement's exchange traffic and log noise for
the rest of that deal's/bot's life once the underlying cause is already
known. So: the **first** time §7.1 step 2 fires for a given deal (DCA/
combo) or bot (grid), persist that fact — a new field, sibling to
`Deal['startBlocked']` (`types.ts:1399-1425` — the closest existing
precedent for "an attempt of kind X failed, remember it, DB-persisted,
restart-safe" — but scoped, per its own comment, to the opening order
only, so this is a new field, not a reuse) — and every **subsequent** TP
build for that deal/bot reads the flag first and skips straight to the
estimated-fee size, without ever re-attempting the real-fee size or
touching the exchange twice. `quantityFeeIsThirdAssetOnly`'s own §2
predicate is still evaluated (so the flag doesn't have to be unset if a
later deal legitimately has no third-asset fee at all — see §5's
resolved answer), but this new flag, once set, overrides it to "use the
estimated size" regardless of what the predicate says.

### §7.4 Chain-specific wiring

Per the research pass's two placement chains:
- **Chain A** (`placeOrders`/`sendGridToExchange` without `returnError`,
  the routine per-fill/per-tick path — the one "every new TP" is about):
  currently has **no** rejection-classified retry of any kind for a TP
  (§1/research: falls through to generic `handleOrderErrors`). §7 adds the
  first one, specifically for this trigger — not a general retry
  mechanism for Chain A.
- **Chain B** (`prepareTpOrder`/`closeDealById` with `returnError: true`,
  whole-deal close): already retries on other reason-shapes (§1 research —
  adaptive-close, notional-bounded slippage retry). §7's check is a new
  branch alongside those, checked before them (a real-fee-sizing rejection
  should fall back to estimated sizing before falling into the existing
  notional-retry-with-recompute loop, since that loop would just
  recompute the same too-small size again without §7's flag).

## §8 Other failure modes considered

Beyond §6's core scenario:

1. **A corrupted or wrong-signed fee value could enlarge, not just
   shrink, the requested size.** §2/§7 only ever zero a multiplier that
   would otherwise gross UP the quantity — a genuine bug in a captured
   fee (wrong sign, wrong decimal scale, a rebate parsed as a fee) can't
   make *this* mechanism ask for more than today's behaviour, because
   nothing here reads the fee's magnitude, only whether one was
   observed off-pair at all (§2). This stops being true the moment
   anyone extends this to size *by* the fee's magnitude (§4's explicitly
   out-of-scope wider idea) — flagging now so that follow-up spec
   inherits this constraint explicitly rather than rediscovering it: any
   magnitude-based sizing needs the §3 clamp (never exceed what the
   account-rate gross-up would have produced) enforced in code, not
   assumed from the input being "real."
2. **Fee-observation race**: `placeOrders` runs on every fill/tick;
   `quantityFeeIsThirdAssetOnly` reads whatever `feeByAsset`/`commission`
   the deal document holds *at that moment*. If a fee for an
   already-filled order is still in flight (observed asynchronously,
   after the fill itself), the predicate can flip from `true` to `false`
   (or vice versa) across consecutive TP builds for the same deal before
   settling — risking a cancel/replace churn on the TP order. Not solved
   by §7 (which only reacts to a rejection, not to flapping); worth a
   plan note on whether TP (re)placement already debounces on unchanged
   inputs, and if not, whether this adds a new source of churn.
3. **Ambiguous placement outcome, not just rejection.** §7.1 assumes a
   clean reject-then-retry. A network timeout on the real-fee attempt
   (request sent, response lost) is not a rejection — retrying with the
   estimated-fee size could then place a SECOND live TP while the first
   also landed, over-selling. The distinct `...rf`/`...ef`
   `clientOrderId` suffixes (§7.1) make the two attempts distinguishable
   after the fact, but §7's plan should say explicitly whether the
   estimated-fee retry checks for the real-fee order's actual fate first
   (a status lookup) or fires blind the way the existing duplicate-id
   retry (`main.ts:7335-7383`) already tolerates for other cases.
4. **The sticky flag never resets — fine for a deal, a real risk for a
   grid bot.** A DCA/combo deal is bounded; a stale §7.3 flag costs that
   one deal some accuracy for the rest of its life, which ends. A grid
   bot can run for months — a flag tripped once by a transient,
   unrelated venue hiccup (misclassified by §7.2's substring match)
   would downgrade that bot's fee accuracy indefinitely, with nothing to
   ever re-arm it. Whether grid needs a reset/expiry path DCA/combo
   don't is an open question, not resolved here (§9).
5. **Substring-classifier drift.** §7.2's rejection classification, like
   every other rejection classifier in this codebase (§1 research), is
   free-text substring matching, not an error code. A venue changing its
   rejection wording (this codebase has precedent for exactly that
   shape of surprise — the 86ex01wye promo-pricing regression in
   `tpFees.spec.ts`) would make §7 silently stop firing for that venue,
   with no error, just a reversion to §1's pre-existing (harmless, just
   less accurate) behaviour. Not preventable in general; worth building
   the classifier list from venues actually observed rejecting a
   real-fee-sized TP rather than a speculative superset.
6. **Combo's untraced TP path (already flagged in §4).** §7's mechanism,
   if applied to combo, inherits §4's open item about `feeBalance`'s
   separate combo-only bookkeeping. Restated here because §7's retry
   adds a second order-placement attempt where combo's TP path currently
   makes one — worth re-confirming `feeBalance` handles two clientOrderId
   suffixes cleanly before wiring combo in, not assumed from DCA parity.

## §9 Open questions (§6-§8)

- Grid's sticky-flag reset/expiry (§8 item 4) — resolve in the plan or
  explicitly defer to a follow-up.
- §7.4's ambiguous-outcome handling (§8 item 3) — status-check-before-retry

- Does TP (re)placement already debounce on unchanged inputs (§8 item 2),

## §10 Tests: pure-function unit tests are not enough here

§2's predicate (`quantityFeeIsThirdAssetOnly`, already specced/tested in
`006`'s `tpFees.spec.ts`) is a pure function and stays unit-tested there —
nothing new needed for it here. §7 is a different kind of thing: a
sequence — send, get rejected, classify, resend, persist a flag, and
every later call read that flag — living *inside* `sendOrderToExchange`/
`placeOrders`/`closeDealById`, none of which are pure, none of which this
repo can drive without a DB and a stubbed exchange response. §7.2's
classifier turns out to be a private method on the same class (the plan
corrects an earlier assumption that it could be a standalone pure
function — `isErrorNotEnoughBalance`/`isNotionalReason` are both private,
and pulling their backing data into a pure module would drag `main.ts`'s
side-effecting imports along with it), so it has no isolated unit test
either — it, and the `clientOrderId` suffixing, are only provable as part
of the same sequence: "the second attempt used the estimated size," "the
flag got written," "the next TP for this deal skipped straight to
estimated sizing without touching the exchange twice."

That's what spec `008` exists for. Once it lands, this spec's gate 2
needs, at minimum, three `tests/processing/` scenarios (exact filenames/
DAO calls to be pinned in the plan once `008` ships, not guessed here):
1. Real-fee TP rejected (balance-shaped) → resend at estimated size
   succeeds → deal's sticky flag is now set.
2. A second fill on the same deal → new TP build reads the sticky flag →
   estimated size sent directly, exchange stub asserts it was called
   exactly once (not twice) for this TP.
3. Real-fee TP rejected for an UNRELATED reason (not balance- or
   notional-shaped) → §7 does not fire at all → existing generic error
   handling runs unchanged (a regression guard against §7.2's classifier
   being too broad).

Until `008` ships, §7 has no gate 2 to point to — this spec's own
traceability table (plan) marks those rows blocked rather than pretending
a unit test covers them.
