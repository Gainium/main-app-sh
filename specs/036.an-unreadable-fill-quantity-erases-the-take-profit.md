# 036 — One unreadable fill quantity erases the whole take-profit

Bug spec (Definition / Evidence / Assumption).

Third sibling of specs `023` (#714) and `025` (#715). Those two stopped a NaN
quantity from *reaching the venue* and from being *write-ahead persisted*. This
one is about where the NaN is born on the sizing side: `getTPOrder` sums the
deal's fills with unary `+`, so a single order row whose `executedQty` cannot
be read as a number poisons the sum, and the deal is left with **no take-profit
at all** — the outcome `023`'s guard turns the bad order into.

## §1 Definition

### §1.1 Expected

`getTPOrder` sizes the close from the quantities it can actually read. A row
that reports no readable `executedQty` contributes **0** to the fill sums —
never `NaN` — so the rest of the deal's books still produce a finite quantity
and a take-profit is armed. This is already how the same subsystem measures the
same position: `dca/tpCoverageReconcile.ts` `trackedPosition` and
`restingTpQty` both read a row as `parseFloat(\`${o.executedQty}\`) || 0`.

Under-counting a fill is safe by construction here: `resolveBaseOrderQty`
(spec `017`) derives the base order's contribution as
`grossEntry - filledQty`, so whatever the fill sum fails to see is picked back
up from `deal.size`, the deal's own persisted books.

### §1.2 Actual

`core/src/bot/dcaHelper.ts`, inside `getTPOrder`:

```js
// line 14374 — the already-closed quantity, inside `add`
filledCloseOrders.reduce((acc, v) => acc + +v.executedQty, 0)
// line 14377 — the entry fills
const filledQty = filledOrders.reduce((acc, v) => acc + +v.executedQty, 0)
```

`+undefined` is `NaN`, and `NaN` propagates through every arithmetic step and
survives every comparison:

1. `filledQty` → `NaN`.
2. `resolveBaseOrderQty` — `Math.max(0, grossEntry - NaN)` is `NaN`, and
   `NaN > floor(boFromOrder)` is `false`, so the *position* branch cannot fire
   and the base order's own row is returned unchanged. The base order quantity
   therefore looks perfectly healthy in the log line while the fill sum is NaN.
3. `_qty = filledQty + boQty` → `NaN`, and so is `qty`.
4. Spec `023`'s guard (`dcaHelper.ts:14622`) refuses the order and returns `[]`.
   That is the right thing to do with a NaN quantity — but it is a refusal, not
   a repair: **no take-profit is placed**, and the funded position rests on the
   venue with nothing covering it.

`023` closed the *outbound* hole. The arithmetic that produces the NaN is
untouched, so the guard fires again on every subsequent tick and the deal stays
uncovered indefinitely.

## §2 Evidence

### §2.1 Production — the refusal repeating for 23 hours

`Gainium-DCA-bot-error`, bot `6a93a10c6c5d2ca41bec4c7c` (coinbase, still
`open`). **19** occurrences between `2026-09-08T17:44:33.094Z` and
`2026-09-09T16:52:39.845Z` — every one of them says `counted fills NaN`:

```
2026-09-08T17:44:33.094Z  Close order qty is not a number. Deal 6a9f9973f4865661cbb62960
                          qty NaN, price 0.014602, base order qty 233.6, counted fills NaN
                          Method getTPOrder
2026-09-09T16:52:39.845Z  Close order qty is not a number. Deal (new)
                          qty NaN, price 0.045888, base order qty 74.37, counted fills NaN
                          Method getTPOrder
```

Two shapes, both the same defect:

- **A named deal** (`6a9f9973f4865661cbb62960`, CHZ-USDC) refused 7 times at an
  unchanging `base order qty 233.6` — its own base order row, read fine, while
  the fills next to it read `NaN`.
- **`Deal (new)`**, 12 times across many different pairs. `getTPOrder` is called
  before the deal exists, so `dealId` is empty, and
  `getOrdersByStatusAndDealId` falls back to a status-only lookup
  (`main.ts:1591` — the deal index is only intersected when `dealId` is truthy).
  The sum then spans **every** `FILLED` `dealRegular` row the bot holds, so one
  unreadable row anywhere in that bot's order map refuses the take-profit of
  every new deal it opens. That is why the same bot keeps reappearing.

Pre-`023`, the same arithmetic sent the NaN to the venue instead:
`2026-09-08T13:18:28.477Z … Send new order request D-TP-wNa2CKPAwo3IEmZ9So23q2zVHTNTH2,
qty NaN, price 0.000001, side SELL`.

### §2.2 The unreadable row is in memory, not in the database

Read-only production query over all **3,402** order rows of that bot:

```js
db.orders.find({ botId: '6a93a10c6c5d2ca41bec4c7c',
                 executedQty: { $not: /^-?[0-9]/ } })   // → []
```

Every persisted `executedQty` is a numeric string. Deal `6a9f9973…`'s own rows
include three `origQty: 'NaN'` take-profits (the spec `023`/`025` casualties)
and they all carry `executedQty: '0'`. So the poison is in the **in-memory
order map**, which is what `getOrdersByStatusAndDealId` reads — the field is
assigned straight from a venue payload (`order.executedQty = msg.totalTradeQuantity`
and its per-venue variants, `main.ts:5320`) with no numeric validation, and
`Order.executedQty` is typed `string`, so an absent field is `undefined` at
runtime with nothing to object. A `RequiredString` schema and mongoose's
"skip undefined on update" then keep it out of the database, which is why the
persisted rows look clean and a DB query alone cannot find this.

### §2.3 The deal that was left uncovered

`6a9f9973f4865661cbb62960` — CHZ-USDC, `size: 233.60000000000028`,
`tpHistory: []`, `reduceFunds: []`. Its one successfully-armed take-profit
`D-TP-9Tia9sxBQ8TJTjUOSfWfvvWFCjXrEU` (`origQty '230.7'`, `price '0.014602'`)
was cancelled at `updateTime 1788874561118`, and the three replacements built
after that are the `origQty: 'NaN'` rows. The deal ran on with no live sell
order until it was cancelled.

## §3 Assumption (hypothesis, not fact)

The root cause is the unary-`+` coercion at the two sum sites named in §1.2 —
**not** the price inputs (`023`/`025`), and **not** `resolveBaseOrderQty`, which
behaves correctly given a finite input and cannot sanitize NaN because
`Math.max` and `>` both pass it through silently.

The test in §4 must therefore fail *because* one order row's `executedQty` is
unreadable, with every price input healthy — if it fails for a price reason, the
assumption is wrong.

## §4 Required behaviour

- **§4.1** A deal whose order map holds one entry row with an unreadable
  `executedQty` still gets a take-profit, sized from the rest of its books.
- **§4.2** That take-profit is the one the deal should have had: for
  `6a9f9973…` it is `qty 230.7 @ 0.014602` — the exact row the venue accepted
  before the poisoning, reproduced to the digit.
- **§4.3** The same holds for the close-side sum (`filledCloseOrders`): an
  unreadable `executedQty` on a `FILLED` take-profit row contributes 0 rather
  than erasing the whole quantity.
- **§4.4** A healthy deal is unchanged, to the unit, on both sums.

## §5 Out of scope

- **The venue-payload assignment itself** (§2.2). Sanitising
  `order.executedQty` at ingestion touches every exchange, every order type and
  every consumer of the order map; it is a separate, much wider change, and it
  would not retroactively clean an order map already holding a bad row.
- **The `Deal (new)` fill sum spanning the whole bot** (§2.1). Passing an empty
  `dealId` into a deal-scoped lookup is its own defect — it over-states the
  fills of every new deal on a bot with history — but it is not what turns the
  quantity into NaN, and narrowing that lookup changes sizing for every DCA
  deal on the platform.
- **Re-arming the take-profits already cancelled.** `dca/tpCoverageReconcile.ts`
  owns that, and its repair is armed per deal by `BOT_TP_COVERAGE_REPAIR`
  (spec `016`).
