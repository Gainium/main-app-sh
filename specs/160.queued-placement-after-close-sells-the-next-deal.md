# 160 — A placement queued before a close sells the next deal's coins

Bug spec (Definition / Evidence / Assumption). Tests:
`src/bot/dca/releasedDealPlacement.harness.spec.ts`.

## §1 Definition

`placeOrders` is serialised per deal (`${botId}${dealId}`). A call queues on
that lock carrying the ladder its caller built at that moment, including a
take-profit sized for the position as it was then.

**Expected.**

- §1.1 A queued placement whose deal has already been released (closed by
  `processDealClose`, so no longer in the bot's deals) places nothing.
- §1.2 A placement that is part-way through its orders when the deal closes
  (the deal is released, or its single take-profit fills in full) places none
  of the orders it has not sent yet. It logs the drop.
- §1.3 Unchanged: an underfilled take-profit (spec 027) is not a close, so the
  remaining orders are still placed. The refused-close restore (spec 083) still
  places into a deal whose take-profit row reads FILLED. A simple terminal deal
  is not affected.

**Actual.** `processDealClose` drops the deal from memory (`deleteDeal`) before
its own order sweep (`cancelAllOrder`), and drops the deal's order rows
(`removeOrdersByDeal`) only after the sweep. On venues where a cancel resolves
through the unknown-order lookup, that sweep can hold for minutes. A placement
queued behind the deal's lock then runs with the deal gone and its rows gone:
the closed-deal pre-check (1.70.4) reads both, finds neither, and lets it
through. It sends its stale ladder, take-profit included, for a deal that no
longer exists. On spot that take-profit sells coins the account holds for the
NEXT deal on the same pair. That deal's own take-profit is then refused for
balance and the deal is left with no sell order.

The order loop also never re-reads the deal between sends, and a single send
can take tens of seconds there, so a close landing mid-loop is not seen either.

## §2 Evidence (prod logs and orders, read-only, 2026-10-13, Coinbase spot)

Times UTC, one DCA bot, one pair:

- 08:44:16 base order fills. The placement it starts sends four safety orders
  and the TP, each send resolving through the 32 s "order not found after
  execution" lookup.
- 08:45:50 the first safety order fills. Its re-size placement (one more
  safety order plus a TP for base + safety = full size) queues on the deal lock.
- 08:46:55 the first placement's TP (base-order size) is sent. 08:47:17 it
  fills; the close sweeps the remainder at market (08:47:20, fully sold) and
  `processDealClose` starts cancelling the four resting safety orders — about
  nine minutes through the lookup ladder. The first placement's end-of-method
  check (`was closed during place orders. Cancel orders: 4`) cancels the same
  four and holds the lock for the same nine minutes.
- 08:56:27.421 the last cancel resolves. Both waiters resume:
  `processDealClose` removes the order rows and opens the next deal
  (08:56:28, base filled 08:56:28.8); the lock passes to the queued re-size.
- 08:56:27.425 it sends a safety order row for the closed deal (cancelled
  08:56:28.1). 08:56:59.150, after that send's lookup, it sends the TP for the
  closed deal: full old size, LIMIT. It fills by 09:00:45. The sold coins were
  the new deal's.
- From 08:59 every TP of the new deal is refused `Not enough balance`: the
  wallet holds the new deal's size minus the old deal's size.

## §3 Assumption (hypothesis)

The pre-check treats "deal not in memory" as "nothing to say" instead of "the
deal is gone", and nothing re-checks between sends. A check that the deal is
still held, run at the start and again before each send, drops the stale
ladder.

Test must fail because a released deal still receives orders, and because a
close landing between two sends still lets the second through.
