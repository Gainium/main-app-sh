# 243 — A limit order that fills on arrival is stored as MARKET

## 1. Definition

### 1.1 — expected

An order we send as LIMIT is stored as LIMIT, whatever happens when it
reaches the book. When its price has already been crossed, it trades at once
against resting orders. Its stored `price` is then the average fill price,
and it carries `filledOnArrival: true`.

### 1.2 — actual

When the placement answer showed the order trading, `placedOrderType`
(`src/bot/placedOrderType.ts`) classified it MARKET. That classification was
written to the order's `type`. A split take profit whose slices were sent as
LIMIT at the take-profit price, with the market already above it, was stored
as one LIMIT slice (it rested and filled later) and three MARKET slices
(they filled on arrival, at better prices than the limit). The record
contradicted both the settings and the venue, which reports all four as
LIMIT orders.

### 1.3 — unchanged

- The stored `price` is still chosen by how the order traded. An order that
  traded on arrival is priced from its fills (`cummulativeQuoteQty /
  executedQty`, then `avgPrice`, then the fills). One that did not is priced
  at the requested price. Deal average price, P&L and fees read this price.
- An order sent as MARKET is classified exactly as before.
- Everything that used the MARKET label as "this order took liquidity on
  arrival" still sees it, through `tradedAsTaker`: the estimated fee rate
  when the venue reported no fee (taker, not maker), the combo minigrid
  fee displacement, the time a fee is valued at, the full-size
  PARTIALLY_FILLED answer treated as FILLED, and the Binance guard that drops
  a stream report arriving after the placement answer already filled the
  order.

## 2. Why the relabel existed

The relabel did not come from a decision about the order's type. It
came from the price.

- **2022-08** (main-app, "Update base order check for market"). The DCA
  base order switched between the requested price and the average fill price
  by its type. A limit base order that filled on arrival needed the fill
  price, so any fills in the answer set the type to MARKET, and the price
  followed the type.
- **2023-12** ("start price"). A reply price other than the requested one
  also counted as MARKET, so the deal's start price would be the real fill.
- **2024-02** ("recognize order as market"). An average fill price other
  than the requested one also counted as MARKET.
- **2026-10** (spec 181). The test was moved into `placedOrderType` unchanged,
  with a guard for a resting order reported at price 0.

One value did two jobs: choosing the price and labelling the order. Only the
price needed the classification. The label was a side effect.

## 3. What reads the stored type, and what changes

| Reader | Meaning it needs | After this spec |
|---|---|---|
| Fee estimate when no fee was observed (`dcaHelper` close + ledger) | took liquidity | `tradedAsTaker`, so still taker |
| Combo minigrid sell displacement (`comboHelper`) | took liquidity | `tradedAsTaker`, so still taker |
| `feeTimeOf` (`feeAssetPrice.ts`) | filled at placement | `tradedAsTaker`, so the same time |
| `isFullyExecutedMarketPartial` | answered for its whole size | `tradedAsTaker`, so the same |
| Binance stale-stream guard (`main.ts`, stream update) | filled by the placement answer | `tradedAsTaker`, so the same |
| Fill-failsafe resting index (`type: 'LIMIT'`, NEW/PARTIALLY_FILLED) | resting limit | A limit that filled only part of its size on arrival is now watched for the rest. Before, it was hidden from missed-fill recovery. |
| Slippage (`orderSlippage.isMarketOrder`, spec 050) | sent as MARKET | A limit that fills on arrival is no longer counted as market slippage. Its fill can only match or beat its limit. |
| Kraken futures reduce-only remainder, Bybit IOC CANCELED handling, KuCoin cancelled limit safety order, TP/SL close-by type | the venue behaviour of the type that was sent | The type that was sent |
| Dashboards, API, trade details | the type that was sent | LIMIT, matching the bot settings and the venue |

## 4. Fees: what the order was charged

An order that fills on arrival is the taker in each trade, so the venue
charges its taker rate. On accounts where maker and taker rates are the same,
the charge is the same either way. Where they differ, the observed fee
(`feePaid`, from the fills) is the venue's real charge, and this spec
does not touch it. The estimate used when no fee was observed stays taker.

## 5. Assumption

Every placement-path reader of `order.type` that meant "took liquidity"
appears in §3. A reader that checks the type against `'MARKET'` before the
order is sent is unaffected. Supported by a search of every comparison of an
order's type against MARKET or LIMIT in `src/`.
