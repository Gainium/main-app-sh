# 012 — Reconcile's unresolved-order WARN reports the attempt BUDGET as the attempt COUNT

Bug #676. Log-only defect in the reconcile pass's aggregate warn.

## §1 Definition

### §1.1 Expected

When a reconcile pass finishes with orders it could not read, the warn it
emits must describe **what the pass actually did**. An operator reading the
line must be able to tell how much work was spent on those orders — i.e.
whether the lookup ladder actually ran, or stopped on its first answer.

### §1.2 Actual

Both reconcile loops emit:

```
Reconcile could not read <N> order(s) after <reconcileLookupAttempts> attempts: <ids>
```

`reconcileLookupAttempts` (`src/bot/main.ts:388`) is the module-level
**budget** constant (default 3, `BOT_RECONCILE_LOOKUP_ATTEMPTS`). It is
interpolated unconditionally. The pass never measures what it spent, so the
line reads "after 3 attempts" even when every order stopped after one
`fetch()` — which is the common case, because `reconcileLookup`
(`main.ts:501-508`) breaks out on `last?.data`, `isDefinitiveOrderNotFound`,
or `isTransportRetryExhausted` before the loop ever sleeps.

Call sites:
- `src/bot/helper.ts:1209` (grid `checkOrdersAfterReconnect`)
- `src/bot/dcaHelper.ts:9443` (DCA/combo `checkOrdersAfterReconnect`)

### §1.3 Why it matters (impact is diagnostic, and it has already fired)

The number is the one an operator uses to decide whether a warn is a retry
storm. Reading "3 attempts" as spend implies 3 venue round trips per order —
and since `Exchange.apiCall` retries a connector 5xx six times internally,
a reader multiplies further. A triage session did exactly that on
`Gainium-Grid-bot-error.log 2026-09-05T00:30:09.444Z` (bot
`6a212785ce236bfdf885bada`, 39 orders) and filed a defect against a code
path that was behaving as designed.

## §2 Evidence

### §2.1 Every prod occurrence prints the constant

Read-only prod log search (`logs -n 400 Gainium-Grid-bot Reconcile`,
2026-09-05): **853 matching lines**, order counts 1–45, and every single one
says `after 3 attempts`. A value that never varies across 853 samples with
45× spread in order count is not a measurement.

### §2.2 The timing rules out a real 3-attempt ladder

Two consecutive passes from the same log:

```
00:30:09.444Z  bot 6a212785ce236bfdf885bada  39 order(s) after 3 attempts
00:30:09.989Z  bot 6a4fc3a7ebbae511721e10ef   9 order(s) after 3 attempts
```

545 ms apart. `reconcileLookupBackoffMs` is 750 with ±50% jitter, so a
single order that truly spent 3 attempts sleeps at least
`750*0.5 + 1500*0.5 = 1125 ms` — more than the entire second pass took for
nine orders. The second pass therefore spent **one** attempt per order, and
still logged 3.

### §2.3 The code path that produces one attempt

`reconcileLookup` runs `fetch()` once before the loop, then breaks on the
first of three conditions at the top of each iteration. A definitive
not-found (Hyperliquid `unknownOid`, Kraken `Order not found`, and the
synthesized `Order not found: no exchange order id` an order with
`orderId === '-1'` gets without any round trip at all) exits at attempt 1.
The unresolved order then lands in `unresolved` via `!getOrder.data`, so
the warn's own population is biased toward the exact orders that spent the
fewest attempts.

## §3 Assumption (hypothesis)

The root cause is that **`reconcileLookup` does not report how many attempts
it spent**, so the two call sites have no truthful number available and
interpolate the only one in scope — the budget constant. Fixing the wording
alone would remove the false claim but leave the diagnostic question ("did
the ladder run?") unanswerable, which is what the misreading was trying to
answer.

Therefore: give `reconcileLookup` an **optional, additive** way to report
attempts spent, thread it through `MainBot.getOrderForReconcile`, and have
both loops sum it **for the unresolved orders only** — the ones the message
is about.

## §4 Constraint — Danger List #11

`reconcileLookup` is an exported symbol of `main-app-sh` (`core/`), shared
platform-wide. Its **return type must not change** and its `opts` shape must
stay backward-compatible: the new reporting channel is an optional callback
field, so every existing caller compiles and behaves identically.
`getOrderForReconcile` is a `protected` member with four call sites in this
repo (§5.3); only the two reconcile loops pass the new option.

## §5 Required behaviour

- §5.1 `reconcileLookup` invokes an optional `opts.onAttempts(spent)` exactly
  once before returning, with the number of `fetch()` calls it made
  (≥ 1, ≤ `max(1, opts.attempts)`).
- §5.2 `reconcileLookup`'s return value, stop conditions, sleep schedule and
  call count are unchanged whether or not `onAttempts` is supplied.
- §5.3 `getOrderForReconcile` accepts an optional `onAttempts` and reports
  through it on **both** of its branches — including the no-exchange
  early return, which spends exactly 1 attempt without calling
  `reconcileLookup`.
- §5.4 Both warns report the attempts actually spent on the unresolved
  orders, and label the budget separately so neither number can be read as
  the other:
  `Reconcile could not read N order(s) after M lookup attempt(s) (budget B/order): …`
- §5.5 No behavioural change to reconcile: same lookups, same order
  resolution, same quarantine accounting. Log text only.
