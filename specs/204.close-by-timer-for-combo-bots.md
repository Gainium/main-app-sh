# 204 — Close by timer for Combo bots

Feature (catalog #1408). DCA bots can close each deal a set time after it
opens ("Close by timer": `closeByTimer`, `closeByTimerValue`,
`closeByTimerUnits`). Combo bots, single-pair and multi-pair, get the same.
Hedge Combo and Hedge DCA are out of scope and must behave exactly as today.

The settings already exist on the Combo bot and Combo deal schemas, the
GraphQL create/change inputs and the deal-settings snapshot taken when a deal
opens (`DCAUtils.getInitalDealSettings`). The Combo engine inherits the
timer methods from the DCA helper. What it lacks is listed in §2.

## 1. Behaviour

1.1 A Combo bot with take profit on and Close by timer on closes each deal
    `closeByTimerValue × closeByTimerUnits` after that deal's base order
    filled. One timer per deal: a multi-pair Combo with N open deals holds N
    timers.

1.2 The timer only runs while take profit is on (`useTp`), as for DCA. A
    Combo bot with take profit off never closes by timer.

1.3 The close is a full deal close with trigger `timer`: resting DCA and
    minigrid orders are cancelled and the whole position, base-minigrid coins
    included, is sold (bought back for a short). It is the same close a
    manual "close by market/limit" runs (`closeDealById`), so a deal that is
    part-way through a grid fill is frozen by the spec-120 close tracking
    exactly as a manual close freezes it.

1.4 The close uses the Combo deal's own "Deal close type" (`comboTpLimit`):
    limit → `closeByLimit` without forcing market; market → `closeByMarket`.
    DCA keeps today's behaviour: its own `closeDealType`, forced to market.

1.5 The timer is armed when the deal opens (Combo `startDeal`, base order
    filled) and re-armed for every open deal when the bot loads
    (`restoreWork`: service restart and user start alike). A deal whose
    deadline passed while the bot was down closes as soon as loading
    completes. Editing a deal's settings re-arms it (inherited
    `rebuildDealOrders`).

1.6 Default off. Nothing changes for an existing Combo bot on deploy: every
    Combo bot saved so far has `closeByTimer` false or unset (the dashboard
    forced it false for Combo forms).

1.7 The public REST/v2 API accepts `closeByTimer`, `closeByTimerValue`,
    `closeByTimerUnits` on a Combo bot update, a Combo bot clone override and
    a Combo deal update (they were rejected as "not supported in combo
    deals"). A Hedge Combo clone override still rejects them.

1.8 Backtests: the shared backtester strategy loop already applies the timer
    to Combo (`checkCloseTimer`, close at the open of the candle after
    expiry). No change; the dashboard's limitations panel flags it as
    partial for every bot type.

## 2. What changes

2.1 `dcaHelper.closeByTimer` asks an overridable `timerCloseOrder(settings)`
    for `{ closeType, forceMarket }` instead of hard-coding
    `settings.closeDealType` + `forceMarket: true`. Combo overrides it (§1.4).

2.2 Combo `startDeal` arms the timer after the deal is saved open (§1.5).

2.3 Combo `restoreWork` arms it for each open deal (§1.5).

2.4 `onlyDcaSettingsKeys` drops the three timer keys; `hedge.ts` rejects
    them on a Hedge Combo leg override (§1.7).

## 3. Edge cases

3.1 Deal closing when the timer fires: `closeDealById`'s own lock and close
    tracking apply; the timer adds nothing beyond the call.
3.2 Paper trading: same code path, paper venue.
3.3 Deadline already passed at load: `setCloseByTimer` calls `closeByTimer`
    at once; `closeDealById` queues itself until loading completes.

## Invariants

- An open Combo deal with take profit and Close by timer on, whose deadline
  passed more than 15 minutes ago, must not still be open. Pack:
  `main-app/specs/204.invariants.json`, observe.
