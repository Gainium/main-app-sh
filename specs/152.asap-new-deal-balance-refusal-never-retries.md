# 152 — An ASAP bot refused for balance right after a close never tries again

Bug spec (Definition / Evidence / Assumption). Fixture ids in tests are synthetic.

## §1 Definition

### §1.1 Expected

1. An ASAP-start DCA or Combo bot whose next deal is refused for balance keeps
   checking for a bounded time, and opens the deal as soon as the exchange
   shows the funds (for example the funds freed by the deal that just closed:
   its take-profit proceeds and its cancelled safety orders).
2. Those re-checks read the balance from the exchange. The stored,
   stream-maintained balances are what refused the deal, so asking them again
   cannot tell a settled balance from an unsettled one.
3. A bot that genuinely lacks the funds still opens nothing. After the bounded
   re-checks it stops checking, exactly as today.
4. The user still gets one "Not enough balance to start new deal" warning per
   standing condition (spec 008 latch), not one per re-check.
5. Unchanged: indicator / webhook / timer bots (their own trigger re-runs the
   gate), terminal deals (one-shot, the bot stops), manual opens (answered on
   every click), the reduce-to-available path, and the stored-first gate for every
   check that is not a re-check.

### §1.2 Actual

An ASAP bot's new deal is attempted only when a deal closes, on bot start/restart
or reload, or on a cooldown timer. A balance refusal releases the pending slot
and arms nothing, so the bot sits idle until the user restarts it. Since the
balance gate decides a shortfall from stored balances, both the first check and
its 5 s re-check refuse when the stored row lags the exchange right after a
close.

## §2 Evidence

- A DCA short bot on Binance spot. The take-profit filled at 00:05:32.976.
  All five unfilled safety-order sells were reported cancelled by the user
  stream between 00:05:33.3 and 00:05:34.4. `openNewDeal` ran at 00:05:34.4
  and again at 00:05:39.4 (the 5 s re-check). Each logged one `Check assets
  start`, meaning a stored-only decision with no live confirmation. Both
  refused with 85.69 available against 257.78 required. 85.69 is the earlier
  free balance plus the take-profit fill, with none of the 200.00 the cancels
  freed.
- After that the worker logged nothing that reaches `openNewDeal` for that bot
  for 33 minutes. The next attempt was a worker reload at 00:39:14. It did two
  balance reads (stored pass, live confirm) and opened the full 257.78 deal at
  once, with no change to that asset in between.
- The same account logged "Not enough balance to start new deal" warnings on
  several bots from 2026-10-07 on. That is the day the gate began deciding
  shortfalls from stored balances (1.83.0).
- Code: in `dcaHelper.openNewDeal` and `comboHelper.openNewDeal`, the refusal
  branch calls `resetPending` and returns. ASAP is re-attempted only from
  deal close (`closeDeal` → `openNewDeal`), `restoreWork`, the cooldown timers and
  approval-hook retries. None of these runs after a balance refusal.

## §3 Assumption (hypothesis)

Root cause: for an ASAP bot, a balance refusal is terminal. Nothing
re-schedules `openNewDeal` for the pair (triage option (a) holds). Since 1.83.0
the 5 s re-check also reads the same stored row that refused, so a balance that
settles on the exchange a few seconds after a close is never observed. A test
that drives the real `openNewDeal` through a stored-shortfall / live-pass refusal
on an ASAP bot must show no retry scheduled and no live read today.

## §4 Fix shape (decided in plan 152)

§4.1 On a non-terminal, non-manual balance refusal of an ASAP bot, schedule a
re-attempt of `openNewDeal` for that pair on a bounded back-off.
§4.2 While a re-attempt is pending for the pair, the balance gate reads live.
§4.3 A passing gate ends the sequence. So does running out of attempts.
§4.4 The latch is untouched, so re-checks report nothing new.
