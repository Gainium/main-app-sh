# 223 — The unknown-order ladder loses the venue's FILLED answer on venues queried by exchange id

Bug spec (Definition / Evidence / Assumption). Test:
`src/bot/unknownOrderByIdVenueDbFallback.spec.ts`.

## §1 Definition

`_runUnknownOrderLadder` asks the venue what happened to an order the bot could
not settle. On venues that can only be queried by exchange order id (Kraken
spot, Coinbase, KuCoin full futures) it swaps the client order id for the
stored exchange id before asking.

**Expected.**

- §1.1 When the venue answers, the order is resolved even if the bot's order
  map no longer holds it: the row is read by its client order id and returned
  (FILLED → returned), exactly as on every other venue.
- §1.2 A row that lags the venue is updated under its client order id.

**Actual.** The DB fallback reads the row by the EXCHANGE id, which no row is
keyed by, so it finds nothing and the ladder returns `null`. Its caller in
`sendOrderToExchange` (the placement read-back-miss branch) then treats a
FILLED order as one the venue does not have: it writes it off and raises an
"Order processing" warning to the user about an order that filled.

## §2 Evidence (prod, read-only: DCA bot worker logs)

Kraken spot DCA bot, market take-profit at the top of the hour:

- §2.1 09:00:01.20–.21Z the user stream reports the TP NEW → PARTIALLY_FILLED
  → FILLED; the deal closes and drops the order from the map.
- §2.2 09:00:04.05Z the placement answer arrives: the connector's QueryOrders
  read-back had not indexed the txid yet (`Order not found: QueryOrders has no
  record of txid …`). `Ambiguous outcome … asking kraken` → `Send request to
  unknow order`.
- §2.3 09:00:04.19Z `Real order … status: FILLED` — the venue answered.
- §2.4 09:00:04.20Z `Warn | … Reason Order not found: QueryOrders has no record
  of txid … Method limitOrders()` — the answer was lost and the user warned.
  The order row stays FILLED (the write-off filter skips FILLED rows).

## §3 Assumption (root cause — hypothesis, confirmed by the test going red)

- §3.1 `id` is reassigned to `local.orderId` in the by-id branch; the ok-branch
  fallback `ordersDb.readData({ clientOrderId: id })` therefore queries by the
  exchange id. It must use `origId`. The exhaustion branch's read happens
  before the reassignment and is already correct.

## §4 Out of scope

- The connector's read-back window (QueryOrders lag at busy minutes) is not
  changed: main-app already treats a read-back miss as ambiguous and asks
  again (spec for `isPlacementReadBackMiss`); that second ask succeeded here.
