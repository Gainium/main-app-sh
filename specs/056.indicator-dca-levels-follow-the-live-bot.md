# 056 — indicator-DCA levels follow the live bot, not the deal

Bug spec.

## 1. Definition

### 1.1 Expected

A bot-settings save applies to **new deals only**. A deal that is already
running keeps the settings it opened with — including the size and the price
distance of every safety order it has not filled yet.

On an indicator ladder (`dcaCondition: indicators`) each `startDca` indicator
is one ladder level, and two of its fields define that level:

- `orderSize` — the size of the safety order;
- `minPercFromLast` — how far price must move from the deal's last fill before
  the level may fire.

§1.1.1 Those two values, for every level, are fixed when the deal opens.

§1.1.2 Which indicator conditions *trigger* a level stays live: editing an
RSI threshold is expected to apply to deals already running. Only sizes and
distances are frozen.

§1.1.3 A deal opened before this change carries no frozen values and keeps
today's behaviour (the bot's live indicators).

§1.1.4 A level the bot gained after the deal opened has no frozen value; it
uses the live one.

### 1.2 Actual

Raising a bot's indicator order sizes resizes the unfilled safety orders of
every running deal on that bot. A deal opened at a small base order fills its
next safety order at the size configured for new deals — an order an order of
magnitude larger than the one the deal was planned with. The deal-details
"next DCA order" figure shows the same live value.

## 2. Evidence

### 2.1 Reported

A running short deal on an indicator ladder, opened with a base order of 50
(quote) and a first safety order of 75, filled its first safety order at
~1,154 (quote) after the bot was saved with a base of 770 and indicator sizes
1155 / 2310 / 4620 / 9240. The deal's own `settings.baseOrderSize` was still
`50` — the per-deal snapshot for base size worked; the safety order size did
not come from it.

### 2.2 Traced code path

- `getAggregatedSettings(deal)` returns `{ ...botSettings, ...deal.settings }`:
  any field the deal snapshot lacks is read from the **live** bot.
- `DCAUtils.getInitalDealSettings` — the snapshot written at deal open —
  copies `orderSize`, `dcaCustom`, `volumeScale`, … but **not `indicators`**.
- `createInitialDealOrders` sizes indicator level `i` from
  `settings.indicators.filter(startDca)[i - 1].orderSize` and prices it from
  the same entry's `minPercFromLast`.
- `addDCAOrderByIndicator` gates the signal on
  `this.data.settings.indicators.filter(startDca)[index].minPercFromLast` —
  the bot's live value, not even the aggregated one.

`percentage` and `custom` ladders are unaffected: their per-level values
(`orderSize`/`volumeScale`/`step`, `dcaCustom`) are in the snapshot.

### 2.3 Reproduction

`main-app` `tests/dcaIndicatorLevelsFrozen.ts` drives the real
`createInitialDealOrders` and `addDCAOrderByIndicator` over the §2.1
configuration. Against the pre-fix engine the first level is sized `1155`
where `75` is expected, and a 5 % move is refused against the live 10 %
distance where the frozen 2 % allows it.

## 3. Assumption

The per-deal settings snapshot omits the indicator ladder's per-level sizes
and distances, so the engine resolves them through the bot overlay. Freezing
them into `deal.settings` at open and reading the deal's copy first fixes both
the order sizing and the signal gate. (Confirmed by §2.3: the red tests fail
with the live values and pass once the snapshot is read.)

## 4. Required behaviour

§4.1 `getInitalDealSettings` records `dcaIndicatorLevels: [{ orderSize,
minPercFromLast }]`, one entry per `startDca` indicator, in ladder order.

§4.2 The deal schemas (DCA and combo) persist `dcaIndicatorLevels`.

§4.3 Ladder sizing and ladder pricing for level `i` read the deal's
`dcaIndicatorLevels[i - 1]` when present, otherwise the live indicator
(§1.1.3, §1.1.4).

§4.4 The indicator-signal distance gate reads the same value as §4.3.

§4.5 The GraphQL deal-settings types expose `dcaIndicatorLevels`, so a
dashboard can show the frozen values.
