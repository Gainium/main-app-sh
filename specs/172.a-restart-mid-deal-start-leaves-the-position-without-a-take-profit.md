# 172 — A restart in the middle of opening a deal leaves the position without a take-profit

When a DCA base order fills, `startDeal` does three things in order. It marks
the deal `open` in memory, which the debounced Redis `deals` snapshot picks
up. It writes `status: open` and the opening balances to Mongo, and that write
is not awaited. Then it places the take-profit (and safety orders) through
`placeOrders`, which puts each order in the order map, so the Redis `orders`
snapshot picks it up too. Only after that does it write the order's
write-ahead row (`orderId: '-1'`) and send it.

If the process stops between those steps, the snapshots can hold an `open`
deal and a take-profit that Mongo never received and the venue never saw. The
next cold restart trusts the snapshot for every deal it holds (spec 151 §1.1.3).
The deal comes back `open`, so `restoreWork`'s filled-base branch never sees
it. The phantom take-profit comes back as resting, and the restart order check
asks the venue about it. The venue says it does not exist. Because the order
is younger than the 24 h quarantine floor, nothing happens. The deal then holds
a filled position with no exit on the venue, Mongo shows it as never started,
and every later restart restores the same snapshot.

## §1 Definition

### §1.1 Expected

- **§1.1.1** On a cold restart, a deal the Redis snapshot shows as `open` while
  Mongo still shows it as `start` is loaded from Mongo, not from the snapshot.
  This applies when the order map holds a FILLED entry (`dealStart`) order for
  it and no other order of the deal carries a real exchange id. The deal
  therefore reaches `restoreWork` as `start` with no generated orders, and the
  filled-base branch starts it (`startDeal`). That places the take-profit and
  writes the opening state to Mongo.
- **§1.1.2** A deal the snapshot shows as `open` keeps the snapshot copy
  (unchanged behaviour) when Mongo agrees it is `open`, or when any non-entry
  order of the deal carries a real exchange id. An order the venue accepted is
  never re-placed by §1.1.1.
- **§1.1.3** In the restart order check, a take-profit is treated as never
  placed when all of these hold:
  - it still carries the `'-1'` placeholder id;
  - the venue definitively answers that it does not exist;
  - Mongo holds no row for its client order id;
  - it was created before this check started, more than
    `unsentOrderMinAgeMs` ago.

  The write-ahead row is written before the send, so a missing row means the
  send never happened. Such an order is removed from the order map, and the
  missing take-profit is placed again from the deal's current grid through
  `placeOrders`. It is not left to collect quarantine strikes.
- **§1.1.4** A take-profit with a Mongo row, or with a real exchange id, gets
  the existing not-found handling unchanged (strikes, quarantine, spec 109's
  24 h retirement).
- **§1.1.5** The check in §1.1.3 runs only on the service-restart pass of
  `checkOrders`, not on the partially-filled pass.

### §1.2 Actual

- **§1.2.1** `loadOrders` restores every non-closed snapshot deal as it is in
  Redis. It never compares the snapshot's status with Mongo.
- **§1.2.2** `checkOrders` sends a definitive not-found to `noteOrderNotFound`.
  For an order younger than `orderQuarantineMinAgeMs` (24 h), that returns
  without doing anything. The `tpOrdersInCurrent` comparison that follows
  still counts the phantom as a resting take-profit at the grid's price and
  quantity, so it places nothing.

## §2 Evidence

Production, 2026-10-18, two Binance DCA bots on one worker process. That
process was congested: lock timeouts and `costServiceActionsQueue` timeouts
from 14:21Z on.

- A short deal's MARKET base order was sent at 14:46:07Z. Its row was saved
  FILLED at 14:49:07Z (`Save order …-BO-…`).
- The worker restarted at about 14:54Z. At 14:54:50Z it logged
  `Found in redis 1 deals` and then `Found in redis 2 orders` (the base order
  and a take-profit). It never logged `in status start, but found filled base
  order`. At 14:56:02Z it logged `Found 1 open deals`, so the deal was
  restored as `open`.
- 14:56:02Z: `Order …-TP-… not found on exchange: Order does not exist.` The
  order has no row in `orders` in Mongo. Between restarts the reconcile sweep
  logged `Reconcile could not read 1 order(s)` for it four times
  (15:23Z to 16:16Z).
- At the next restart (16:30:11Z) the same snapshot was restored, with the same
  `Found 1 open deals` and the same not-found.
- Mongo now: the deal is `start` with a FILLED `dealStart` order. The deal has
  no take-profit row, and nothing rests on the venue for it.
- A second bot of the same account shows the same sequence on another pair
  (restart at 14:52:48Z, take-profit not found at 14:52:50Z and 16:29:26Z).

## §3 Assumption (hypothesis)

The process stopped after `startDeal` had set the deal `open` and put the
take-profit in the order map, and both debounced snapshots had flushed, but
before the deal's Mongo update and the take-profit's write-ahead insert
landed. Under that assumption:

- a test that drives the real `loadOrders` with such a snapshot leaves the
  deal `open` and never calls `startDeal` from the real `restoreWork`;
- a test that drives the real `checkOrders` with the phantom take-profit and
  a definitive not-found places no take-profit.

## §4 Out of scope

- **§4.1** A deal whose base order has no row at all while the snapshot holds
  it in memory (the bot logs `already have and active base order` and never
  re-sends). It is a different order type in a different `restoreWork` branch,
  and is tracked separately.
- **§4.2** An entry row stuck at `orderId: '-1'`, `NEW` that was never sent.
- **§4.3** A deal whose take-profit did reach the venue but whose `open` status
  write failed. §1.1.2 deliberately keeps it on the snapshot, so its venue
  orders are not touched.
- **§4.4** Making `startDeal` await its Mongo write, or flushing the snapshots
  synchronously. Both are wider changes to a hot path.
- **§4.5** Combo deals: the same `loadOrders` code runs for them. Their
  restart TP check is in `comboHelper` and is not changed here.

## Invariants

The stuck state is already covered by `deals.start-stuck-nothing-resting` in
main-app `specs/invariants/deals.invariants.json`. It flags a `start` deal
older than 30 minutes with nothing resting, which is exactly the Mongo-side
picture of §1.2. This spec adds no new invariant.
