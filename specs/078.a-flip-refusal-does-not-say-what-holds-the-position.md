# 078 — A flip refusal does not say what holds the position, and gives up after ten seconds

Follow-on to spec 041. Bug spec.

## 1. Definition

### 1.1 Expected

On a one-way futures account the venue keeps ONE net position per symbol, so a
bot whose direction fights an existing position cannot start: its reduce-only
exits would be refused and its deal would strand. `MainBot.loadData` ("check
positions") therefore refuses the start. That guard is correct and stays.

What the user gets from it must be actionable. A refusal should say **what is
holding the position** — an open deal on a named bot, or nothing at all — and
should only spend time waiting when waiting can change the answer.

### 1.2 Actual

The refusal names the direction and nothing else:

    Cannot start when existing position not met bot settings. Side in active
    position is SHORT, but bot will open LONG. Symbol: <pair>

Spec 041 added a re-read of up to 10 s before refusing, for the case it was
written for: a flip sent as one webhook array, `[stop A, start B]`, where A's
close is still in flight when B starts. Two shapes are still unserved:

1. **The opposite bot is not closing anything.** It is running and holding an
   open deal on that side. The 10 s elapse, the refusal repeats, and the text
   sends the user to the venue to look at a position whose owner is a bot on
   the same screen they started from. Observed on a Hyperliquid one-way
   account: five refusals in three minutes, four of them after the full 10 s
   wait, while the opposing bot's own log line in the same window read
   `Found 1 open deals`.
2. **The close never happens at all.** `stopBot` over `/trade_signal` falls
   through to `CloseDCATypeEnum.leave` when the payload carries no
   `closeType`, so the bot stops and the position stays. No wait of any length
   fixes that, and the refusal gives the user no hint that the stop they sent
   was a stop-without-closing.

A third, smaller gap sits on the sending side: `webhookProcess` awaits each
item of the array, but a close item only `postMessage`s the worker and
returns. "Awaited" means the message was posted, never that the position is
flat, so the start that follows always races the close by design — the start
side is left to discover it.

## 2. Why the 10 s window cannot simply be raised

Waiting longer is free only when something is unwinding the position. When a
running bot holds an open deal on the opposing side, the position is not going
anywhere: a longer window buys the same refusal, later, with the bot inert in
between. The window has to be chosen from **who holds the position**, which
means the refusal path has to look that up — and once it has, it can also say
so.

## 3. Solution

### 3.1 Name the holder (`core/src/bot/opposingPositionOwner.ts`)

`MainBot.findOpposingDealHolder(symbol)` reads the DCA and combo deal
collections for an OPEN deal on this symbol, this user, this paper context, a
bot other than this one, and resolves that bot's name and status. Matching on
`exchangeUUID` happens in code, not in the filter: it is a newer field, and a
deal that predates it must not be reported to the user as "no holder".

`opposingPositionRefusal` then appends one of three explanations. **The first
sentence is unchanged and must stay that way** — `findConflictingFuturesPosition`
(`core/src/server/v2/helpers.ts`) answers the terminal-deal API with the same
sentence, and the bot-error rules classify on it.

| Holder | Added text |
|---|---|
| open deal, bot running | names the bot, says both bots share one net position |
| open deal, bot stopped | names the bot, says "leave position open" does not close it |
| none | says nothing here will close it; flatten on the exchange |

The lookup is best-effort: it runs on the refusal path, and `loadData`'s caller
awaits it OUTSIDE its try/catch, so an unreadable deals collection degrades to
the old wording rather than throwing out of the bot.

### 3.2 Wait only when waiting helps (`settleWindowFor`)

- Running bot with an open deal → spec 041's window, unchanged (10 s). It
  still covers the case where that bot's close filled a moment ago and the
  deal row has not caught up.
- Stopped bot, or no holder at all → park: ~61 s total, at a 3 s interval,
  because every attempt is a venue call. A close in flight lands inside it;
  a leftover does not, and the refusal that follows now says so.

### 3.3 Let the close finish first (`core/src/bot/closeSettle.ts`)

After dispatching a close that is meant to flatten — `close`, `closeSl`, or
`stopBot` with `closeType` `market`/`limit` — `singleWebhookProcess` waits for
that bot's open deals to reach zero before returning, so the next item of the
payload starts against a settled account. Bounded at ~15 s and best-effort: a
close that has not landed inside the window falls through to the start-side
settle, i.e. exactly today's behaviour.

`leave` is deliberately not settled. It closes nothing by design; waiting for
it would spend the window on a position that is staying where it is.

Counting deals rather than re-reading the venue keeps this off the exchange
rate limit: a deal is booked closed when its closing order fills, which is the
event the next action is waiting for.

## 4. Tests

`core/src/bot/opposingPositionOwner.spec.ts`

- the base window is used for a running holder; the park window for a stopped
  holder and for no holder, and totals at least a minute
- the original first sentence survives verbatim in all three shapes
- each shape names what the user has to act on; an unnamed bot does not render
  empty quotes

`core/src/bot/closeSettle.spec.ts`

- returns on the first read when there is nothing open, waits until the count
  reaches zero, gives up after the bounded window
- an unreadable or throwing count is never read as a completed close
- the window stays inside its intended bound

Spec 041's own tests are unchanged and still pass: its constant is defined in
one place and re-exported, not copied.

## 5. Out of scope

- The terminal-deal API path (`findConflictingFuturesPosition`) keeps the
  short wording. It answers a synchronous HTTP call with no bot to name yet.
- Reconciling a deal whose recorded size is smaller than the venue position.
  That divergence makes the opposite side unstartable for as long as it lasts,
  and it is its own defect, tracked separately.
