# 272 — A bot saved without a close condition places no take profit

Bug spec (Definition / Evidence / Assumption).

## §1 Definition

`dealCloseCondition` and `dealCloseConditionSL` are optional in the bot
settings schema and in the GraphQL `createDCABot` input. The dashboard, the
notification cards and the plan text all read a missing value as `tp`.

- §1.1 Expected: a DCA/Combo bot or deal with `useTp: true` and no
  `dealCloseCondition` places its percentage take-profit order exactly as one
  saved with `tp`. Actual: no `dealTP` order is ever placed, and nothing is
  logged.
- §1.2 Expected: with `useSl: true` and no `dealCloseConditionSL`, the stop
  loss is armed as for `tp`. Actual: every SL branch compares `=== tp`, so
  the stop loss is never armed.
- §1.3 The engine's merged settings (`getAggregatedSettings`) give a missing
  condition the value `tp`.
- §1.4 An explicit choice (`techInd`, `webhook`, `manual`, `dynamicAr`) on
  the bot or on the deal is kept unchanged. A deal-level value still
  overrides the bot, and a deal that lacks the field still inherits the bot's
  value.
- §1.5 A bot created from now on is stored with `tp` in both fields when the
  client sends neither.
- §1.6 A stop loss that is armed only because of the §1.3 default is armed
  by a live tick on the safe side of its level, never by the first tick. A
  deal already past that level when the default first reaches it is not
  market-closed at the current price; it is protected once the price has
  come back to the safe side. A new deal sees its first tick on the safe
  side and is protected at once. An explicit `tp` (bot or deal) still
  closes on the first tick. The safe-side tick is persisted on the deal
  (`defaultSlArmed`, the `moveSlArmed` idiom), so a worker restart cannot
  disarm a stop that was already protecting the deal. Each held deal logs
  `stop loss not armed` once per worker, so held deals can be counted.
  This is the only behaviour; there is no switch to arm on the first tick.
  Whether a stop is "armed only by the default" is decided on the STORED
  documents (lean reads of the deal's and the bot's `dealCloseConditionSL`
  and the deal's `defaultSlArmed`), not on the worker's in-memory view: a
  deal restored from the worker's Redis snapshot reached the check with a
  condition neither Mongo document had, and the in-memory test armed it on
  the first tick. The stored read runs only when a stop that this worker has
  not seen on its safe side is about to close, and its verdict is reused for
  a minute; it can only add a hold, never remove one.
- §1.7 Nothing defaults `useTp` or `useSl`. A DCA or Combo bot created
  without `useTp` keeps it off and places no take-profit order.

## §2 Evidence

- Code: `getAggregatedSettings` (dcaHelper) spreads bot and deal settings
  with no default. `createCurrentDealOrders` computes
  `useTp = settings.useTp && (dealCloseCondition === tp || === dynamicAr) …`
  and then drops every `dealTP` when `useTp` is false. The SL filter and the
  SL checks compare `dealCloseConditionSL === tp`. There are no schema
  defaults.
- Data (read-only prod read, 2026-11-25): non-deleted DCA bots with
  `useTp: true` and no `dealCloseCondition` exist on live and paper venues.
  Their open deals with `useTp: true` carried only a FILLED `dealStart` and
  no `dealTP` row. In a control of 40 recent open deals saved with `tp`, 39
  carried one.
- Runtime: the bot log for one such deal shows `Base order FILLED` →
  `Save order D-BO-…` and nothing more. After each restart it logs
  `Found in redis 1 orders`, which is the base order only. No TP was ever
  sent.
- Origin: GraphQL `createDCABot` passes the client's input to
  `prepareDCABot` without defaults. The comparisons date from the first
  public release, so this is latent, not a regression.

## §3 Assumption

The missing TP is caused by `undefined !== tp` in the engine's checks, and
by nothing else. A default in `getAggregatedSettings` makes all of them see
`tp`, and gate 2's test fails without it for exactly that reason.

## Invariants

- `deals.open-no-take-profit-missing-close-condition` (main-app
  `specs/invariants/deals.invariants.json`, observe). It finds an open DCA
  deal with `useTp`, no saved condition on the deal, no explicit non-tp
  condition on its bot, and no `dealTP` resting. The existing
  `deals.open-no-take-profit` filters on `dealCloseCondition: 'tp'` and could
  not see this state.
