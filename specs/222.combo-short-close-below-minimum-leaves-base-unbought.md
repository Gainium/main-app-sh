# 222 — A combo SHORT close below the venue minimum leaves its base unbought, every deal

Bug spec (Definition / Evidence / Assumption). Tests:
`src/bot/dca/comboShortCloseCarry.spec.ts` (pure carry rules),
`src/bot/dca/comboShortCloseCarry.harness.spec.ts` (real `getTPOrder` /
`prepareTpOrder` / `closeDealById` / `closeDeal`).

## §1 Definition

A combo SHORT deal on a SPOT venue with profit in quote sells base as it
averages in and buys the same base back when it closes. Its close is sized from
the deal's own books: `initialBalances.base − currentBalances.base` (what it
sold minus what it already bought back), less any base entry fee.

When that buy-back is worth less than the venue's minimum order
(`quoteAsset.minAmount`, or below `baseAsset.minAmount`), the venue would refuse
it, so `getTPOrder` returns no order and the deal is closed without one
(`Close without TP order`). That skip is correct and stays: the order cannot be
placed.

**Actual.** The base the skipped buy-back should have bought is forgotten. The
next deal sizes its close from its own books only, so nothing ever buys it back.
The bot's base inventory shrinks by up to one minimum order on every such close,
without limit, and nothing reports it.

**Expected.**

- §1.1 When a combo SHORT spot quote-profit close is skipped because the
  buy-back is below the venue minimum, the base it did not buy (the deal's own
  shortfall, never negative) is added to a per-bot, per-symbol carry.
- §1.2 The next close of a deal on the same bot and symbol sizes its buy-back as
  its own shortfall PLUS the carry, BEFORE the venue-minimum check. So several
  small shortfalls that together clear the minimum are bought back by whichever
  close gets them over it. The carry added is limited to what the deal's own
  quote balance can pay for beyond its own buy-back. `prepareTpOrder` already
  caps a SHORT spot buy-back at that quote, and a cap that cut a carry-inflated
  order back under the minimum would send an order the venue refuses. What
  does not fit stays carried.
- §1.3 When a close order fills, the base it bought beyond the deal's own
  shortfall (the deal ends with `currentBalances.base > initialBalances.base`)
  is subtracted from the carry, floored at 0. A close that bought only part of
  the carry (e.g. the existing quote-balance cap in `prepareTpOrder`) leaves the
  rest carried.
- §1.4 Consequence: at any moment the carry is worth less than one minimum
  order at the price it was last skipped at (it only grows inside a skip, and a
  skip means own + carry was under the minimum). Only the bot's final deal can
  be left short, by less than one minimum order.
- §1.5 Unchanged:
  - LONG combo closes, including the fee-dust sweep (`backedFeeDust`).
  - Combo SHORT with profit in base, and every futures combo.
  - Plain DCA SHORT (spec 043's floor block).
  - Every `getTPOrder` caller that is not the close path (open-deal order
    creation in `createCurrentDealOrders`, asset reservation, TP coverage,
    remaining-quantity checks, reduce-funds). The carry is applied only when
    `prepareTpOrder` sizes the close.
  - Closes without an order for other reasons (slippage retries exhausted,
    position already gone, liquidation, no exchange info) do NOT add to the
    carry. Only the below-minimum skip does.

## §2 Evidence

- §2.1 Code path, `src/bot/dcaHelper.ts`: the combo branch of `getTPOrder`
  overwrites `qty` with the books expression for SHORT/quote profit, then
  `return []` on `qty < baseAsset.minAmount` or
  `qty * tpPrice < quoteAsset.minAmount` (debug log only). `prepareTpOrder`
  returns `undefined`, and `closeDealById` takes the `No tp order. Close without
  order` branch. `closeDeal` without an order books the deal `closed` and writes
  only `profit`/`status`. No field anywhere records the unbought base.
- §2.2 Read-only data check: on a spot combo SHORT bot, the closed deals that
  have no close order all end with `currentBalances.base <
  initialBalances.base`, and each residual is worth less than the venue's
  minimum order at the deal's last price. The deals that did place a close
  order net to approximately zero.
- §2.3 The closed-deal residuals cannot be reused to derive the carry. They also
  hold drift from other mechanisms (both signs appear), and nothing on a closed
  deal records that its close was a below-minimum skip. Summing them would send
  a buy for the bot's whole historical drift on the first close after
  deployment. So the carry is a new persisted bot field that starts at zero.

## §3 Assumption (hypothesis)

The leak is entirely the forgotten shortfall of §1: a skipped close's own
residual is never carried. If the carry is applied to the next close's size
before the minimum check, and cleared by what a filled close buys beyond its own
need, a bot's base nets to within one minimum order across any run of deals.

## §4 Storage

`shortCloseCarry: [{ symbol, base }]` on the combo bot document. It is an array
rather than a `Map` so a symbol never becomes a Mongo key. It is absent, and
read as 0, on every existing bot.

## Invariants

UI-free, no prod error is logged, but the defect is per-close and bounded: no
invariant pack is added. The carry itself is the record the sentinel would need,
and it did not exist before this change.
