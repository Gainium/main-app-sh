# 149 — the first settings save after a restart re-applies leverage to every pair

Bug spec. Closes the gap spec 148 left open as §4.2.

## 1. Definition

### 1.1 Expected
After a bot worker restart, the first settings save (a keep-orders reload) of a
futures DCA/Combo bot behaves like any later one. It asks the venue to set
leverage and margin only for symbols whose requested values differ from what the
bot already runs with. A manual close queued behind it waits seconds, not minutes.

- §1.1.1 A service-restart load records each pair's
  (leverage, margin type, position side) as applied, computed exactly as a
  load that ran the venue calls would compute it. The previous process applied
  those settings and the persisted settings did not change across the restart.
- §1.1.2 The first keep-orders reload after a restart makes no
  `changeLeverage` / `changeMargin` call for unchanged pairs.
- §1.1.3 That reload still applies a changed leverage, margin type or position
  side, and a newly added pair, exactly as spec 148 §1.1.2.
- §1.1.4 That reload still corrects a symbol the venue's positions response
  reports at other values (spec 148 §1.1.1).
- §1.1.5 The service-restart load itself still makes no venue calls, and a user
  start still re-applies every pair (spec 148 §1.1.3). The values requested from
  the venue are unchanged (spec 148 §1.1.4).

### 1.2 Actual
`loadData` clears `appliedFuturesSettings` on every load that is not a reload.
A service restart (`serviceRestart && !secondRestart`) then `continue`s before
the apply block, which is the only writer of the map. After every bot-worker
restart the map is empty, so the first save makes two venue round trips per
pair inside the `methodBot<botId>` lock.

## 2. Evidence

- Code: `src/bot/main.ts` `loadData` futures loop. `this.appliedFuturesSettings
  = new Map()` runs when `!this.reload`. `if (skipFutures) continue` comes before
  `appliedFuturesSettings.set`.
- Production logs, one Bybit linear Combo with several hundred pairs, on one
  worker process: the restart load logged `Skip futures positions check`, so it
  took the skip path. Later saves on the same process logged `Set leverage 5 for
  …` for each pair, about 0.55 s apart, so the loop ran on the reload path.
- Reproduction: `src/bot/settingsReloadLeverage.spec.ts`, a service-restart load
  followed by a keep-orders reload, gives 40 + 40 venue calls for 40 unchanged
  pairs.

## 3. Assumption (hypothesis)
The map is empty after a restart only because the skip path never writes it.
Seeding it on that path from the persisted settings, with the same key the
apply block uses, makes the first reload skip unchanged pairs. The venue
mismatch guard and the key comparison still force a call for anything that
changed or that the venue disagrees with.

## 4. Out of scope / residual

- §4.1 A pair whose apply failed in the previous process is not known to this
  one. It is seeded like the others and is not retried by the first save after a
  restart. Before spec 148 it was not retried on the restart either. It is still
  retried by a user start, and by any save that changes its values.
- §4.2 The ~77 s between `Reload bot` and `Load data start` on the same reload
  (suspected indicator unsubscribe RPCs) is not addressed here.
