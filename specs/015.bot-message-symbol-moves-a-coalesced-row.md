# 015 — A bot-level bot message re-labels itself onto its sibling and is dropped

Issue #643 follow-up (log-triage check #215, 2026-09-07). Spec 007 widened
`botMessageCoalesceKey` by `symbol` so a PER-CONTRACT subType can own one row per
contract. This spec is about what that widening did to every OTHER subType.

## §1 Definition

`Futures position` is the subType for a venue refusing a reduce/close order
("Order failed because you don't have any positions in this direction for this
contract to reduce or close."). It is NOT in `isPerSymbolSubType`'s allowlist, so
it is treated as a bot-level condition: one `botMessages` row per (bot, subType,
visibility, window).

### §1.1 Expected

- §1.1.1 Every occurrence is recorded. A bot-level subType's row absorbs the
  occurrence as a `count` increment whichever contract it came from — the row is
  the bot's, and the write must not fail because the contract changed.
- §1.1.2 A bot-level subType keeps ONE row per bot per window (spec 007 §1.1.3),
  and that row names a contract the condition actually happened on.
- §1.1.3 Nothing changes for per-contract subTypes (`Agreement required`): one
  row per contract, one notification per contract (spec 007 §1.1.1–§1.1.2).

### §1.2 Actual

`processError` (`core/src/bot/main.ts` ~2655–2705) builds the upsert filter
WITHOUT `symbol` for a non-per-symbol subType, but `$set`s `symbol` on every
occurrence (`onEvery`). `botMessageCoalesceKey` is
`{userId, botId, subType, showUser, bucket, symbol}` UNIQUE, so:

- §1.2.1 A multi-pair bot's sibling children share one `messageBotId`
  (`this.data.parentBotId || this.botId`) but hold separate `processError`
  mutexes (`@IdMute` keys on the CHILD `botId`), so two children can reach an
  unset key concurrently. Both inserts succeed — the index tolerates them
  because their `symbol`s differ — leaving TWO rows the filter cannot tell
  apart, which §1.1.2 says must not exist.
- §1.2.2 From then on, for the rest of that window, the filter matches whichever
  sibling row it finds and `$set: {symbol}` tries to MOVE that row onto the
  other's index position → `E11000`. The `upsert` fails, and the E11000 fallback
  re-runs the same `$set` against the same key, so it fails too: the occurrence
  is DROPPED and only `Cannot record bot message <subType>` is logged.

## §2 Evidence

Read-only against production, 2026-09-08.

### §2.1 The dropped writes

`logs -n 2000 Gainium-DCA-bot Cannot record bot message` →
**119 lines, all identical in shape**, one per ~30s from 2026-09-06T04:00:44Z to
the end of the hour:

```
[WARN] Worker 8 | Bot (dca) 6a847d1a56c67bb39341fbb4 (6a847d1a56c67bb39341fbbb)
| Cannot record bot message Futures position | MongoServerError: … E11000
duplicate key error collection: gainium.botmessages index: botMessageCoalesceKey
dup key: { userId: "6a8476b256c67bb39334d9f0", botId: "6a847d1a56c67bb39341fbbb",
subType: "Futures position", showUser: false, bucket: 496852, symbol: "ETC-USDT" }
```

`bucket: 496852` × 3_600_000 ms = the 04:00–05:00Z hour of 2026-09-06, i.e. the
whole window. Zero such lines in Combo-bot, Grid-bot, Hedge-DCA-bot,
Hedge-Combo-bot or Frontend-stream.

### §2.2 The two rows the filter cannot tell apart

The one duplicate group in the whole collection is exactly this window:

```js
db.botmessages.aggregate([{$match:{bucket:{$exists:true}}},
  {$group:{_id:{u:'$userId',b:'$botId',s:'$subType',v:'$showUser',k:'$bucket'},
           n:{$sum:1}, syms:{$addToSet:'$symbol'}, ids:{$addToSet:'$_id'},
           cnt:{$addToSet:'$count'}}},
  {$match:{n:{$gt:1}}}])
```

```
_id  { u: 6a8476b256c67bb39334d9f0, b: 6a847d1a56c67bb39341fbbb,
       s: 'Futures position', v: false, k: 496852 }
n    2      syms [ 'ETC-USDT', 'BTC-USDT' ]
ids  [ 6a9ce54e289a7bb5831fc6d4, 6a9ce54e289a7bb5831fc6d3 ]
cnt  [ 1, 120 ]
```

Both `_id`s carry the SAME ObjectId timestamp (`6a9ce54e`) and consecutive
counters — two inserts from one driver process in the same second, i.e. §1.2.1's
concurrent insert, not two ordinary sequential writes.

The arithmetic closes: `120 + 1` recorded + `119` dropped = `240`, which is the
two children's `2 × 120` occurrences in that hour. **Exactly half the window's
occurrences were lost** — the half whose contract was not the one the filter
happened to match.

### §2.3 The two sibling children

`logs -n 2000 Gainium-DCA-bot 6a847d1a56c67bb39341fbbb` resolves the parent to
two live child bots, `…fbb4` (ETC-USDT) and `…fbb8` (BTC-USDT), both still
erroring every 30s as of 2026-09-08T00:02Z. Neither their log line nor the row's
`fullMessage` names the contract — `Reason Order failed because you don't have
any positions in this direction … Method limitOrders() Step Send new order
request <clientOrderId>, qty 0.8, price 7.886, side SELL`. The row's `symbol`
field is the ONLY place the failing contract is recorded.

## §3 Assumption

Root cause: `symbol` is a MUTABLE field of a row whose index position it is part
of. For a per-contract subType that is safe — `symbol` is also in the upsert
filter, so `$set` can only ever rewrite it to the value it already has. For every
other subType the filter has no `symbol`, so `$set` moves the row inside
`botMessageCoalesceKey`, and a move collides with any sibling row that already
occupies the destination.

Fix: for a non-per-symbol subType, pin `symbol` at insert (`$setOnInsert`)
instead of refreshing it on every occurrence (`$set`). The row then never moves
inside the unique index, so no occurrence can be lost, and it names the contract
the window's first occurrence actually failed on rather than silently re-labelling
itself as the others fail (which spec 007 §1.2.1 already called out as wrong).

Not chosen, and why: widening the coalesce identity by `symbol` for ALL subTypes
that carry one is the other way to remove the collision, but it is the row-per-pair
flood `DEFAULT_PER_SYMBOL_SUBTYPES` exists to prevent (a 50-pair bot short of
balance would own 50 rows for one condition) and it contradicts spec 007 §1.1.3.
Dropping `symbol` from the write entirely would make the identity collision-free
too, but §2.3 shows the row is the only record of the contract.

Residual, deliberately out of scope: §1.2.1's concurrent double-insert can still
leave two rows for one bot-level window. After this fix that is inert — neither
row moves, every occurrence is recorded, and each row names its own contract
correctly — so closing it would need `symbol` out of the index key (a `syncIndexes`
drop-and-rebuild of a unique index on a 108k-row collection, against a bug that has
produced one duplicate group in the index's lifetime).
