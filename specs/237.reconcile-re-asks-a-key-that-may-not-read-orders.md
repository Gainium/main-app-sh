# 237 — A reconcile pass re-asks a key that may not read orders

Bug spec (Definition / Evidence / Assumption). Owner: the reconcile pass of the
grid (`src/bot/helper.ts`) and DCA/combo (`src/bot/dcaHelper.ts`) engines, and
its retry policy `reconcileRetryDecision` in `src/bot/main.ts`.

## 1. Definition

### 1.1 Expected

When the exchange answers an order lookup of a reconcile pass
(`checkOrdersAfterReconnect`) with a refusal of the KEY itself — a permission
the key lacks (`EGeneral:Permission denied`, Bybit's `Permission denied, please
check your API key permissions.`) or a dead credential (`isKeyPermissionRefusal`):

1. The lookup is not retried.
2. The pass asks about no further order. Every one would be refused the same
   way, and on Kraken every refusal counts toward a lockout of the whole key.

### 1.2 Actual

Each order is asked `reconcileLookupAttempts` (3) times with backoff, and every
order of the bot is asked: a bot resting N orders sends 3N refused lookups per
pass, on every pass.

### 1.3 Not changing

- The orders and their saved status stay as they are: a refused lookup writes
  nothing, cancels nothing, books nothing.
- The orders are still reported as unread by the pass's aggregate warn.
- The user's API-key messages from the other paths are untouched.
- Any other failed answer (rate limit, transport, lockout, unknown) keeps its
  existing retry policy.

## 2. Evidence

Connector log, a Kraken spot BTC-USD grid bot whose key can place but not read
orders: `{"error":["EGeneral:Permission denied"]} getOrder called with params:
[{"symbol":"BTC-USD","newClientOrderId":"<id>"}]`, three lines per resting order
per pass, in clusters one pass apart, every pass since the bot was started.

Code: `reconcileRetryDecision` returns `retry` for any non-OK answer it does not
classify; a permission refusal reaches its default branch. Both
`checkOrdersAfterReconnect` copies `continue` to the next order on any
unanswered lookup.

## 3. Assumption

The refusal is classified as retryable because `reconcileRetryDecision` never
consults `isKeyPermissionRefusal` (added for the cancel sweep, spec 232), and
the per-order loop has no account-level stop. Hypothesis confirmed by the
harness: 3 resting orders cost 9 venue lookups before the change.

## 4. Tests

- §4.1 A `Permission denied` answer costs exactly one lookup per pass, on the
  grid and the DCA pass, and again one on the next pass.
- §4.2 Nothing about the orders is written.
- §4.3 Every order is still reported unread.
- §4.4 Any other refusal keeps its per-order retries.
- `reconcileRetryDecision` answers `stop` for a key refusal.
