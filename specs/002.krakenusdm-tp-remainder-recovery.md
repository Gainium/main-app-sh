# 002 — Recover the remainder of an underfilled krakenUsdm reduce-only close

## Definition

**Expected.** When a krakenUsdm reduce-only MARKET order (a take-profit or
any other position-reducing close) comes back from the venue with
`status: FILLED` and `executedQty < origQty`, the engine must attempt to
close the real remaining exposure itself — the same recovery it already
performs for underfilled BUY/entry orders via `buyRemainder` — before the
deal is allowed to close. That recovery must apply no matter which of the
engine's two internal consumers is the one to first observe the order's
terminal state.

**Actual.**

1. `buyRemainder` (`src/bot/main.ts:5014`) unconditionally returns the order
   unchanged for any `order.reduceOnly === true`
   (`src/bot/main.ts:5041-5043`), so no recovery is ever attempted for a
   krakenUsdm TP/close, regardless of how large the shortfall is.
2. Even if (1) were fixed, the fix would only reach the order on ONE of the
   engine's two paths that can observe a terminal order status:
   - The WS-driven order-status consumer (`src/bot/main.ts:5325-5389`) calls
     `fillPartiallyFilledOrder` → `buyRemainder` unconditionally
     (`src/bot/main.ts:5348`) before dispatching `onFilled`.
   - The synchronous placement-response path — `closeDealById` →
     `sendGridToExchange` → `sendOrderToExchange` — calls
     `this.processFilledOrder(result)` directly on the raw response
     (`src/bot/dcaHelper.ts:6016-6018`), with NO call to
     `fillPartiallyFilledOrder` in between, because the corrective hook
     inside `sendOrderToExchange` that would call it
     (`src/bot/main.ts:7436-7442`) is scoped to `ExchangeEnum.bybit` only.

   Whichever of these two paths observes the order first decides deal
   closure (`processFilledOrder`'s own dedup, keyed by `clientOrderId`,
   makes the second observation a no-op). For krakenUsdm today, neither
   path has a chance to recover the remainder, so the outcome is a race
   between two ways of stranding the position, not a race between recovery
   and stranding.
3. The deployed guard against this (`underfilledTpQty` / `partialTp.ts`,
   1.56.3/1.56.9) does not gate either of the two paths above. Its only two
   call sites are the bot-restart reconciliation sweep
   (`src/bot/dcaHelper.ts:10139`) and a branch documented, in its own
   comment, as unreachable (`src/bot/dcaHelper.ts:14711-14723`:
   `setFilledInsteadOfCanceled`'s only caller requires
   `status === 'CANCELED'`, while the guard requires `status === 'FILLED'`).
   So a running bot receiving a genuine krakenUsdm FILLED-with-shortfall
   event is unaffected by that fix.

Net effect: a krakenUsdm reduce-only close that the venue only partially
executes strands the unfilled remainder as a position no bot tracks — no
take-profit, no stop-loss — consuming margin until new base orders are
rejected `Not enough balance` and the bot loops create-deal → rejected →
cancel indefinitely (confirmed prod case: three bots, 84/80/85 loops,
$4,233 of $4,258 account margin stranded).

## Evidence

- Code reading (this session, `main`/HEAD at commit `5856158`):
  - `buyRemainder`'s reduceOnly bail and its own in-place comment
    (`src/bot/main.ts:5018-5043`) documenting the 1.56.9 → 1.56.11
    revert: narrowing the bail to let `dealTP` through and deriving the
    remainder from `order.origQty - order.executedQty` produced 15
    reduce-only remainder orders over 18.3h across
    binanceUsdm/krakenUsdm/bybitLinear/bitgetUsdm, ALL rejected
    (`executedQty: 0` — `wouldNotReducePosition` on krakenUsdm,
    `ReduceOnly Order is rejected.` on binanceUsdm).
  - `underfilledTpQty`'s two call sites (`src/bot/dcaHelper.ts:10139` and
    `:14738`) and the dead-branch comment at `:14711-14723`, which records
    its own verification: 0 log lines fleet-wide in 25.5h post-deploy while
    underfilled TPs kept arriving.
  - `dcaHelper.ts:6016-6018`'s direct `processFilledOrder(result)` call,
    unconditional on exchange, bypassing `fillPartiallyFilledOrder`.
  - `main.ts:7436-7442`'s `[ExchangeEnum.bybit]`-only scope on the hook that
    would otherwise route a synchronous response through
    `fillPartiallyFilledOrder`.
  - `isPositionAlreadyClosedReason` (`src/bot/dcaHelper.ts:5969-5982`) is
    used only on the manual close flow's FIRST TP placement, where
    `sendGridToExchange` is called with `returnError: true` and a rejection
    comes back as a string reason. `buyRemainder` calls it with
    `returnError: false` (`src/bot/main.ts:5082-5116`), where a rejection
    comes back falsy, not a string — so this check does not apply to
    `buyRemainder`'s own sub-orders, and none is needed: the existing
    `if (buyRemainderOrder && (...))` gate (`main.ts:5118-5124`) already
    only merges and recurses on an actual fill, and falls through to
    `return order` — carrying every prior successful merge — on a falsy
    (rejected) response.
  - `partialTp.spec.ts`'s own commit history (`11f7a7d`) records the
    originating incident: an account whose three bots opened nothing for
    weeks, $4,233 of $4,258 USD margin in stranded positions, ~$24 free,
    bots looping create-deal → rejected → cancel 84/80/85 times.
  - `types.ts:133`: `ExchangeEnum.krakenUsdm` confirmed as the exchange
    identifier used throughout `main.ts`/`dcaHelper.ts`.
- Domain knowledge supplied by the reviewer (verified against this repo's
  own exchange-connector convention, not re-derived here): Kraken futures
  has no true market order type — its `mkr` order is IOC with a 1% price
  protection band. A close that cannot fill within that band at the time
  it is sent is filled for whatever the band allowed and the rest is
  cancelled by the venue itself, which is why Kraken reports `FILLED`
  rather than `PARTIALLY_FILLED`: there is never a resting remainder order
  on the book to report against. This is also why a fixed-percentage
  tolerance (`PARTIAL_TP_TOLERANCE`) cannot be the mechanism that decides
  whether recovery is needed — the shortfall size is a function of book
  depth against the protection band at send time, not a stable "real
  stranding vs. rounding dust" signal. `partialTp.ts`'s tolerance still has
  a legitimate, narrower job: deciding whether a *residual after recovery
  has been attempted* is small enough to abandon.

## Assumption

Root cause is two omissions, both confined to `src/bot/main.ts` (the class
both grid and DCA bots share, so a shared-file fix covers both bot types
without a second, DCA-specific patch):

1. `buyRemainder`'s reduceOnly bail has no carve-out for krakenUsdm MARKET
   orders specifically — it treats every reduce-only order on every venue
   identically, even though the 1.56.9 measurement shows the *general*
   reduce-only case is unrecoverable (binanceUsdm/bybitLinear/bitgetUsdm all
   rejected) while krakenUsdm's rejection reason (`wouldNotReducePosition`)
   in that same measurement is consistent with "the position was smaller
   than the remainder we asked for" — which is recoverable by retrying with
   a smaller ask, not evidence recovery is impossible for this venue.
2. The corrective hook inside `sendOrderToExchange`
   (`main.ts:7436-7442`) that routes a synchronous placement response
   through `fillPartiallyFilledOrder` is scoped to bybit's specific
   CANCELED-with-partial-fill shape and never fires for krakenUsdm's
   FILLED-with-shortfall shape, so the synchronous `closeDealById` path
   never gives `buyRemainder` a chance to run regardless of (1).

Fixing both eliminates the race stated in Actual/(2): whichever path
observes the order first, it has already been through the same
`buyRemainder` call and sees the same (recovered, or genuinely exhausted)
final state.

Design assumptions gate 2's tests must confirm:

- **No position-size lookup is required.** The remainder buyRemainder
  computes and re-sends stays `order.origQty - order.executedQty` (order-
  based), unchanged from today. When that ask exceeds the real open
  position, the venue's own reduce-only rejection comes back falsy (per
  `returnError: false`), and the existing fall-through-and-return-order
  behavior naturally stops the recursion while preserving every quantity
  successfully merged so far. (Reviewer's own worked example: TP wants 1
  BTC; first fill 0.001; first remainder attempt fills 0.5 more (order now
  0.501, `FILLED`); second remainder attempt is rejected outright (falsy);
  final returned order is 0.501 `FILLED` — not 0, not an error.)
- **No exchange-message parsing is required.** `isPositionAlreadyClosedReason`
  is out of scope for this fix (see Evidence) — a rejected `buyRemainder`
  sub-order needs no reason inspection, only the existing falsy check.
- **The 20-attempt cap on `buyRemainder`'s recursion
  (`main.ts:5015-5017`) is left unchanged.** Confirmed with the reviewer:
  each successful iteration only recurses on a strictly shrinking diff, and
  a rejected iteration stops recursing immediately rather than retrying, so
  the existing cap is not expected to bind in practice and is not being
  special-cased for krakenUsdm.
- **Scope is krakenUsdm reduce-only MARKET orders specifically** — not
  reduce-only orders in general (binanceUsdm/bybitLinear/bitgetUsdm/
  okxLinear remain excluded per the 1.56.9/1.56.11 measurement) and not
  other krakenUsdm order types.
