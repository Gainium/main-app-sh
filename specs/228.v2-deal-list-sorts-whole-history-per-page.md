# 228 — v2 deal list sorts the account's whole deal history for every page

Bug spec (Definition / Evidence / Assumption).

## 1. Definition

1.1 **Expected.** A page of `GET /api/v2/deals/:dealType` (`dca`, `terminal`,
`combo`; with or without `status`) costs work proportional to the page it
returns: `skip + limit` index keys plus the few rows the endpoint's
non-indexed predicates (`isDeleted`, `type`, `paperContext`) discard.

1.2 **Actual.** Every page reads every deal of the account that matches the
indexed prefix (`userId`, or `userId` + `status`), sorts all of them in memory,
then applies `skip`/`limit`. Page 1 and page 100 both pay for the whole history.

1.3 **Unchanged.** Rows returned and their order (`createTime` desc, then `_id`
desc — the spec 065 tiebreaker) stay exactly as they are. The response shape and
the page size (20) stay the same.

## 2. Evidence

2.1 `explain("executionStats")` of the exact filter and sort
`core/src/server/v2/api.ts` sends, run against an account with a large deal
history:

| case | plan | docs examined |
|---|---|---|
| `status=closed`, page 1 | SORT ← FETCH ← IXSCAN `{userId, status, createTime}` | every closed deal of the account |
| `status=closed`, deep page | SKIP ← SORT ← FETCH ← IXSCAN (same) | every closed deal of the account |
| no status, page 1 | SORT ← FETCH ← IXSCAN `{userId}` | every deal of the account |
| no status, deep page | SKIP ← SORT ← FETCH ← IXSCAN `{userId}` | every deal of the account |

Each returned 20 rows, and latency grew with the size of the history, not with
the page.

2.2 This is the same shape the slow-query monitoring attributes to deal
reads (`{userId,status,…}` with sort `{_id,createTime}`). Only `core/src/server/v2/api.ts` sorts deals by
`{createTime:-1,_id:-1}`.

2.3 `combodeals` declares no `createTime` index at all, so the combo listing
takes the same SORT over `userId_1`.

## 3. Assumption (hypothesis, checked by §5)

No declared index ends in `createTime, _id`, so the planner cannot deliver the
`_id` tiebreak order inside a `createTime` tie off an index and falls back to a
blocking sort over the whole indexed prefix. The status-filtered and no-status
variants need different index prefixes; one index cannot serve both.

## 4. Non-goals

- Cursor pagination: deep pages still cost O(skip). Changing that changes the
  public `/api/v2` contract.
- The `botId` filter variant, and the GraphQL deal lists (they sort without the
  `_id` tiebreaker and are served by the existing indexes).
- Dropping the indexes the new ones make redundant
  (`userId_1_status_1_createTime_-1`, `userId_1`): `syncIndexes()` drops an
  undeclared index at boot, before its replacement is guaranteed to be built.
  That cleanup is a separate, later change.

## 5. Acceptance

5.1 For DCA and combo, with `status=closed` and with no status, at page 1 and a
deeper page, the query the real handler sends executes with no blocking sort
stage, and examines at most about `page × 20` documents.

5.2 For the same cases, the rows and their order equal the `createTime` desc,
`_id` desc order computed independently of the database.
