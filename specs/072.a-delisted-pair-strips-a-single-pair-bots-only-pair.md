# 072 — A delisted pair strips a single-pair bot's only pair, and nothing can put it back

Bug spec (Definition / Evidence / Assumption). Scope: the **engine's
delisted-pair pruning** (`dcaHelper.checkSettingsPairs`) and the **pair-change
refusal** in `changeDCABot` / `changeComboBot`. The dashboard side of the same
defect (the read-only pair chip and the invented default pair) is a separate
change in `main-dash-sh` — see §1.6.

## §1 Definition

`settings.pair` is the user's statement of what a bot trades. A bot with
`useMulti: false` has exactly one, chosen at creation and — by product design —
not editable afterwards.

Separately, the engine syncs each venue's symbol list hourly. When a pair
disappears from that list, `checkSettingsPairs()` treats it as delisted and
prunes it from `settings.pair`.

### §1.1 Expected

Pruning a delisted pair must never leave a bot with **no pair at all**.

- A multi-pair bot that loses **some** of its pairs keeps trading the rest, and
  the lost ones are pruned (this is what the pruning was built for and must not
  regress).
- A bot that would lose **every** pair is **stopped** — and keeps its
  `settings.pair` — so that:
  - the bot can be restarted unchanged if the contract comes back;
  - the editor still shows what the bot is configured to trade;
  - the user is never asked to repair state the engine broke.

### §1.2 Actual

`checkSettingsPairs()` prunes unconditionally. A `useMulti: false` bot whose
only pair vanishes is persisted with `settings.pair: []`, and only then does
`start()` stop it. The bot is left in a state that:

- can never open a deal — no pair to trade;
- is **not editable**: `changeDCABot` answers
  `Cannot change pair for non-multi pairs bot` to any pair change on a
  `useMulti: false` bot, regardless of what the stored pair is;
- still costs the user a bot slot while `status: open`;
- keeps a fully-populated `symbol` map naming the pair it used to trade, so the
  document is internally inconsistent.

The only remedy available to a user today is to delete the bot and build a new
one — losing its statistics and history.

### §1.3 Evidence

**Production data (read-only).** `dcabots`, not deleted, `settings.useMulti:
false`, `settings.pair: []` — **220 bots across 24 users**, every single one
with a **non-empty `symbol` map** (i.e. all were configured with a pair and
then stripped, none were born empty): 13 `open`, 92 `closed`, 115 `archive`,
spread over `bitgetCoinm`, `binance`, `binanceUsdm`, `bybit`, `bybitLinear`,
`bitget`, `bitgetUsdm`, `kraken`, `hyperliquid` and the paper venues. The same
shape in `combobots`: 15 bots, 14 users.

**One traced instance.** A `bitgetCoinm` `useMulti: false` bot reads
`settings.pair: []` with `symbol: { BTCUSD: {symbol: BTCUSD, baseAsset: BTC,
quoteAsset: USD} }`, while a sibling bot of the same user, same venue and same
pair still reads `settings.pair: ["BTCUSD"]`. The bot-error log for the damaged
bot carries, at the hour Bitget dropped the COIN-M `BTCUSD` contract from the
symbol list, `Cannot set margin for BTCUSD: the symbol has been removed` and,
two seconds later, `Exchange info not found. Bot will stop` — the
`checkSettingsPairs` → `start()` sequence above.

**Code path.** `dcaHelper.ts` `checkSettingsPairs()` filters `notFound` out of
`settings.pair` and calls `updateData` before returning; `start()` (both core's
and main-app's override) then reads `pairsNotFound` and, because the bot is not
`useMulti`, takes the `Bot will stop` branch. The persist happens first, so the
stop always finds an already-emptied `settings.pair`.

### §1.4 Assumption (root-cause hypothesis)

Two independent defects, either of which alone would have made this recoverable:

1. **`checkSettingsPairs()` has no floor.** It applies the multi-pair pruning
   rule to a bot that has nothing to prune down to. The caller already knows
   how to stop a bot whose pairs are all missing; the prune adds nothing there
   except the data loss.
2. **The pair-change refusal is keyed on `useMulti` alone.** It exists to
   protect a *configured* single-pair bot from a pair swap. A bot with no
   stored pair is not configured, so the refusal is protecting nothing and only
   blocks repair.

### §1.5 Non-goals

- **No migration.** Bots already emptied are not repaired by this change. It
  stops the damage and unblocks repair; putting a pair back is the user's
  (or a follow-up backfill's) action.
- **No change to multi-pair pruning.** A multi-pair bot that loses some of its
  pairs must keep losing them, exactly as `081566a` intended.
- **No change to the single-pair product rule.** A single-pair bot that HAS a
  pair still refuses a pair change. The only case unlocked is the empty one.
- **Grid bots** are out of scope: `changeBot` ignores `pair` entirely and grid
  has its own pair handling.

### §1.6 Out of repo

The dashboard still renders a read-only pair chip for an empty-pair bot and
fills it with an invented default (the first BTC contract on the venue), and
its update mapper strips `pair` from the payload for any `useMulti: false` bot.
Until that changes, the backend permission unlocked here is not reachable from
the bot editor. That is a `main-dash-sh` change and is tracked separately.

## §2 Behaviour

### §2.1 `checkSettingsPairs()`

| Bot | Pairs missing | Pruned | `pairsNotFound` | Persisted |
|---|---|---|---|---|
| §2.1.1 multi, 3 pairs | 1 | that 1 | that 1 | yes |
| §2.1.2 multi, 3 pairs | all 3 | none | all 3 | no |
| §2.1.3 single, 1 pair | that 1 | none | that 1 | no |
| §2.1.4 any | none | none | none | no |
| §2.1.5 single, 1 pair, open deal on it | that 1 | none | none | no |

§2.1.2 and §2.1.3 are the change. In both the caller's stop branch still fires,
because `pairsNotFound` is populated whether or not anything was pruned —
§2.1.5 is the pre-existing open-deal guard and is untouched (a pair with a live
deal is not even a candidate).

### §2.2 `changeDCABot` / `changeComboBot`

| Stored bot | Requested `settings.pair` | Outcome |
|---|---|---|
| §2.2.1 `useMulti:false`, pair `["BTCUSD"]` | anything | refused — `Cannot change pair for non-multi pairs bot` |
| §2.2.2 `useMulti:false`, pair `[]` | `["BTCUSD"]` | accepted; `symbol` map rebuilt from `pairs` |
| §2.2.3 `useMulti:false`, pair `[]` | `[]` | refused — `Need to specify at least one pair` |
| §2.2.4 `useMulti:false`, pair `[]` | 2+ pairs | refused — a single-pair bot takes exactly one |
| §2.2.5 `useMulti:true` | unchanged from today | unchanged from today |

§2.2.2's `symbol` rebuild matters: the map is what every read path resolves
`baseAsset` / `quoteAsset` through, and today it is only rebuilt on the
`useMulti` branch.

## §3 Origin

Latent. The prune is `081566a` (2025-10-07, "Remove delisted pairs from the
bot") — a deliberate feature whose multi-pair behaviour §1.5 preserves. The
refusal is `0e08c6c` (2025-06-30, first public release). Neither is inside the
onset window; the trigger was a venue retiring a contract.

## §4 Open questions

- **Q1 — should a stopped, emptied bot be repaired automatically when the
  contract returns?** Not here. This spec's floor means the pair is still
  there, so a restart is enough; a backfill for the 220 already-damaged bots is
  a separate decision with its own blast radius.
- **Q2 — should §2.2.2 also require the bot to be stopped?** No. An empty-pair
  bot cannot hold an open deal on the missing pair (the prune skips any pair
  with one, §2.1.5), so there is no position for a pair change to strand.
