# 190 — A restart revives a closed deal from the Redis deal snapshot

Bug spec. Related: `151` (a cold restart loads the live deals the snapshot
lacks), `047` §2.3.7 (a combo funds change makes the stored copy win), `172`
(a snapshot `open` deal that Mongo still holds `start`), `182` (a close sweep a
restart interrupted is resumed), `173` (a reload during a combo close).

## §1 Definition

### §1.1 Expected

- **§1.1.1** A cold service restart never brings back a deal that Mongo holds
  as `closed` or `canceled`, whatever the Redis deal snapshot says about it.
- **§1.1.2** Whatever such a deal still has live after its close is cleaned up
  on that restart: its resting orders are cancelled on the venue, and a combo
  deal's minigrids end `closed`.
- **§1.1.3** Deals that Mongo still holds as live (`open` / `start` / `error`)
  restore from the snapshot exactly as before. When the check cannot read
  Mongo, the restart keeps the snapshot as it does today.

### §1.2 Actual

- **§1.2.1** The snapshot (`deals` in the bot's Redis hash) is written through
  `@RunWithDelay`. A deal close removes the deal from memory, and the pending
  write that would drop it from the snapshot dies with the process if the
  process stops before it fires.
- **§1.2.2** The next cold restart (`loadOrders` with `serviceRestart`) seeds
  every snapshot deal whose own `status` is not `closed` / `canceled`. It never
  asks Mongo about those deals: the spec `151` read is for the deals the
  snapshot lacks, and spec `047`'s stale check reads only live deals.
- **§1.2.3** The revived deal is held `open` in memory. The bot trades it, and
  every later snapshot write saves it `open` again, so each later restart
  revives it again. The close happened, the user sees the deal as closed, and
  the bot keeps placing grid and DCA orders for it.

## §2 Evidence

Production, two combo bots on paper Bybit, same pair (UTC):

- 10-20 05:07:49 both deals close on their take-profit. Mongo has held both
  `closed` ever since (sentinel `deals.combo-closed-with-open-ladders`, first
  seen 05:20).
- Around 05:07:50 the combo worker process is replaced.
- After every combo worker restart since, the bot's log reads
  `close refused | Deal … is open with no close order on the exchange`, and its
  TP sell is refused for balance. The position was already sold.
- 10-22 04:07:24 one of the bots restarts: `Read bot data from redis`,
  `Found in redis 1 deals`, `Found in redis 9 minigrids`, and no
  `Get deals from DB` line. That is the snapshot path.
- Prod Mongo, read-only, 10-22: neither bot has any deal `open` / `start` /
  `error`. Both deals are `closed`. 18 of their minigrids are not `closed`,
  and 82 of their orders are `NEW`.

## §3 Assumption

The revival is the snapshot-restore branch of `loadOrders`, which trusts the
snapshot's status for deals it restores. One Mongo read of the restored deal
ids (`{status: 1}`) after seeding is enough to drop the ones Mongo holds as
`closed` / `canceled` before anything else is derived from them.

The cleanup reuses spec `182`'s close-sweep record. A dropped deal is
recorded in `closeSweeps`. `restoreWork` already resumes recorded sweeps for
deals this process does not hold: it reads their `NEW` / `PARTIALLY_FILLED`
rows from Mongo, cancels them on the venue, and (Combo) closes the deal's
minigrids in memory and in Mongo.

The write side (§1.2.3) needs no separate change. The bot re-saved the deal as
`open` only because it held a revived copy. Once a restart no longer revives
it, there is nothing left to re-save.

## §4 Solution

- **§4.1** In `loadOrders`, after the snapshot deals are seeded, read their ids
  from Mongo (`botId`, `_id ∈ restored`, `status ∈ {closed, canceled}`,
  projection `{status: 1}`). For each hit, drop the deal from memory and from
  the restore list, and record a close sweep for it (awaited, as in spec `182`).
- **§4.2** On a failed read, log a warning and keep the snapshot (§1.1.3).
- **§4.3** Combo inherits this through `super.loadOrders()`. The minigrids
  restored from the snapshot for a dropped deal are removed by the sweep
  resume (`afterCloseSweepResumed`), as for any spec `182` sweep.
- **§4.4** Amends spec `151` §1.1.3: snapshot deals still keep the snapshot's
  state, but only while Mongo holds them live. The spec `151` read of live
  deals is unchanged. Its test now selects that read among the deal queries
  instead of counting all of them.
- **§4.5** Spec `183`'s fixture is this defect's own scenario: a deal closed
  in Mongo and `open` in the snapshot. Its test asserted the ghost being loaded
  (`active: 2`) and closed a second time. Its §1.1.1 contract (`active` = the
  live deals the bot manages) now reads `1` straight after the load, and the
  test asserts that. Spec `172`'s "no extra Mongo read" test selects its own
  read the same way as §4.4.
