# 060 — A merged remainder is counted twice in the deal average

Spec `058` §1.1 lists `getAvgPrice` among the ledgers that "recompute from the
order rows and all of which deliberately EXCLUDE `typeOrder: br` rows (because
a remainder belongs to its parent, not to the ledger in its own right)".

That sentence is true of every ledger it names except `getAvgPrice`, which has
no such exclusion. This spec makes it true.

## §1 Definition

### §1.1 Expected

`buyRemainder` (`src/bot/main.ts`) merges a successful remainder order back
INTO the row it is completing, at the blended quantity, quote and price:

```
order.executedQty        = parentExecuted + remainderExecuted
order.cummulativeQuoteQty = parentQuote    + remainderQuote
order.price               = totalQuote / totalBase
```

The remainder's own row — `typeOrder: br`, written by `sendGridToExchange` and
registered in the in-memory order map by `setOrder` — is therefore a DUPLICATE
of quantity that now also lives in its parent. It is a receipt for a fill, not
a second fill.

`getAvgPrice(dealId)` must fold each unit of the deal's entry exactly once. A
`br` row must not contribute to either branch:

- **spot** (`§4.1`) — the `executedQty` / `executedQty × price` reduce.
- **futures** (`§4.2`) — the `calculateAbstractPosition` fold.

### §1.2 Actual

Both branches take every row `getOrdersByStatusAndDealId({status:'FILLED',
dealId})` returns — the spot branch additionally filtered only on `o.side`.
While the merged parent AND the `br` row are both in the order map, the
remainder's quantity is folded twice and the average is pulled toward the
remainder's MARKET price.

The window is bounded but real: `loadOrders` (`main.ts`) restores with
`typeOrder: {$nin: [liquidation, br]}`, so a `br` row survives only until the
bot next rebuilds its map from Mongo. Every `getAvgPrice` call before that
reload is wrong.

## §2 Evidence

Production, Coinbase spot, DCA deal `6aaeb84fa54072cab53e993a` (`OP-USDC`),
2026-09-19 — the same deal as specs `057`/`058`. Rows on the deal, read
read-only from `orders`:

| row | status | side | executedQty | price |
|---|---|---|---|---|
| `dealStart` (as persisted) | CANCELED | BUY | 34.66 | 0.12256 |
| `br` | FILLED | BUY | 780.85 | 0.12273999999999999 |
| `dealRegular` | FILLED | BUY | 271.6 | 0.1215 |
| `dealTP` | FILLED | SELL | 1086.02 | 0.12403 |

The engine logged the merge at 16:29:41.574Z:
`Total order …, 0.12273, base: 815.51, quote: 100.0894586 BUY` — so the row
`getAvgPrice` saw in memory was `815.51 @ 0.12273` (34.66 + 780.85 units;
`0.12273` is `100.0894586 / 815.51` rounded to `priceAssetPrecision` 5).

Folding that map through the spot branch:

| fold | base | avg |
|---|---|---|
| merged parent + `br` + `dealRegular` (what the code does) | 1867.96 | **0.12255533914002442** |
| merged parent + `dealRegular` (each unit once) | 1087.11 | **0.1224227008306427** |

`dcadeals.avgPrice` and `dcadeals.settings.avgPrice` on that deal are
`0.12255533914002442` — the double-counted value, matching to all 17 digits.

The correct base, 1087.11, is also the only one the deal itself corroborates:
`deal.size` is 1086.02, the quantity the take-profit actually sold.

Fleet measurement over the 400 most recent FILLED `br` rows on spot deals, of
the 45 deals where the two computations differ: 16 stored the with-`br` value,
29 the correct one — the split being whether the `br` row was still in the map
when `getAvgPrice` last ran.

## §3 Impact

`avgPrice` / `settings.avgPrice` are the basis for the safety-order ladder
(`createCurrentDealOrders`) and for the take-profit price. On a long an
overstated average puts the TP above where the user configured it, so the deal
holds longer than asked. The magnitude is the remainder's share of the entry —
0.11 % on the deal above, materially more on a deal that filled a few percent
on the book and bought the rest at market.

## §4 Assumption (root-cause hypothesis)

The defect is the ABSENCE of a `typeOrder` filter in `getAvgPrice`, and nothing
else. Specifically:

### §4.1 Spot branch

`filledDealOrder` is filtered on `o.side` only. Adding
`o.typeOrder !== TypeOrderEnum.br` makes the fold count 1087.11 units at
`0.1224227008306427`.

### §4.2 Futures branch

The same gap, with the same cause: the fold that builds `PositionInBot` walks
every FILLED row. A futures `br` row is produced by the same
`fillPartiallyFilledOrder` → `buyRemainder` path (`buyRemainder`'s only
venue-specific gate is `canRecoverReduceOnlyRemainder`, which bears on
reduce-only orders, not on whether a `br` row is written). Nothing on this
branch reads `typeOrder` at all today.

### §4.3 `rebalance` is NOT part of this defect — it must stay in the fold

The sibling filters at `dcaHelper.ts:2661` / `:6440` and `comboHelper.ts:1660`
exclude `[br, rebalance]` together, but they are FEE ledgers, not cost-basis
folds. The cost-basis fold for combo bots, `comboHelper.avgPrice`, is an
allow-list — `dealRegular | dealStart | dealGrid | fee | rebalance` — which
deliberately INCLUDES `rebalance` and, by omission, already excludes `br`.

That is the correct reading. A `rebalance` order (`comboHelper.manageBalanceDiff`)
is a real, un-merged trade that changes what the deal holds;
`buyRemainder` returns early on it (`main.ts`, `if (order.typeOrder ===
TypeOrderEnum.rebalance) return order`) so it never has a parent to be a
duplicate of, and `processRebalanceOrder` exists precisely to refold it into
`deal.avgPrice`.

`getAvgPrice` is moreover unreachable from a combo bot — all three of its call
sites are inside `dcaHelper.startDeal` / `dcaHelper.updateDeal`, and `ComboBot`
overrides both — so a `rebalance` row can never appear in the map it folds.
Excluding it here would be dead code that contradicts the one cost-basis fold
that does see those rows.

**Therefore: exclude `br`, and only `br`.**

## §5 Non-goals

- `liquidation` rows. `loadOrders` excludes them from the restore, but a
  liquidation is a real position change, not a duplicate; the futures branch
  models a position. Out of scope for this spec.
- The display average (`display`). It is derived from
  `currentBalances`/`profit`, not from this fold, and falls back to `avg` — so
  it is corrected by the same change without a separate one.
- Repairing already-stored averages on closed or open deals. This spec changes
  what is computed from here on; it does not migrate history.
- Spec `058`'s persistence fix (`55c10f2`) is unaffected: it writes the merged
  parent row, which this spec keeps counting. Only the `br` row stops being
  counted a second time.
