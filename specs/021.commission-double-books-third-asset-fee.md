# 021 — `commission` books the full estimate for an off-pair observed fee

Bug spec.

## 1. Definition

### 1.1 Expected

`getCommDeal` (`dcaHelper.ts:2166-2204`, feeds `deal.commission`) is
meant to apply the same real-fee-first rule spec 014/015 already
established elsewhere on this exact question: an order whose fee was
genuinely observed — even if it's entirely off-pair (BNB/BGB/KCS-style,
or this session's `PAPER_FEE_ASSET_SYMBOLS` test tool) — must not have
the flat account-rate estimate applied on top of it. `feePaid` (via
`closeDeal`'s loop) and TP sizing (`getTPOrder`'s
`ordersFeeIsThirdAssetOnly` gate) both already get this right: an
all-third-asset fee contributes 0 to base/quote, never the estimate.

### 1.2 Actual

`getCommDeal` only checks `observedFeeSplit(v, base, quote)` per order.
That function returns `null` both when NOTHING was observed and when
something was observed but entirely off-pair (it has no way to
distinguish the two — that's `observedFeeLegs`' job, not its). Either
way, `getCommDeal`'s fallback applies the full flat-rate estimate. For
an order whose fee was fully observed and fully off-pair, that's wrong
in the same direction the pre-014 estimate always was — it's not "we
don't know, use the estimate," it's "we know, and it wasn't this."

## 2. Evidence

- **Live reproduction.** A closed paper deal
  (`dealId 6aa00795aa9a30fe7fe8c8da`) with both fills reporting a
  third-asset fee (`feeAsset: 'GNM'`, spec 004 in `paper-trading-sh`):
  `commission: 0.20094481920000004`. Each order's OWN
  `feePaid`/executed-qty/price independently priced through the flat
  estimate comes out close to half that (`0.1`-scale each), consistent
  with `getCommDeal` summing the full per-order estimate for BOTH
  fills instead of booking 0 for either.
- **Code trace.** `getCommDeal`'s `else` branch (`:2194-2202`) applies
  `parseFloat(v.executedQty) * (...) * feeRate` (or the quote-scaled
  form) whenever `observed` is `null` — with no check for whether
  `observedFeeLegs(v, base, quote)` found something off-pair.
- **Contrast — the same repo already solved this exact question
  twice.** `closeDeal`'s loop (`:2340-2367`, spec 014): `if
  (feeByAssetGated && legs.length) { continue }` — skip the estimate
  when the off-pair legs were found, book 0 on base/quote instead.
  `dca/tpFees.ts`'s `ordersFeeIsThirdAssetOnly`/
  `quantityFeeIsThirdAssetOnly` (spec 015): the same "all observed fee
  was off-pair ⇒ don't apply the rate" gate, for the TP quantity
  gross-up. `getCommDeal` predates both and was never brought in line.

## 3. Assumption (hypothesis)

`getCommDeal`'s fallback branch needs the same off-pair check
`closeDeal` already applies inline: when `observedFeeLegs(v, base,
quote)` is non-empty (an off-pair fee WAS observed for this order), add
0 for this order rather than the estimate — the observed information
says something concrete, and this repo's own convention (spec 014 §2.2)
is that an off-pair fee's cost moves USD/ledger accounting, never
base/quote/commission math. Nothing else about `getCommDeal` needs to
change: the `observed` (on-pair) branch is already correct, and the
"nothing observed at all" case correctly keeps the estimate.

Behind the same `feeByAssetGated`-equivalent flag question spec 014
raised: `getCommDeal` has no `deal.flags` gate today (it's called from
several places, not just the gated `closeDeal` ledger path — grep
before assuming). Gate 3's plan resolves whether to gate this fix the
same way or apply it unconditionally.

## 4. Out of scope

- Backfilling `commission` on deals already closed with this defect.
- `getCommDeal`'s callers beyond `closeDeal` (grepped in the plan) —
  the fix is inside `getCommDeal` itself, so every caller benefits
  uniformly; no caller-specific work is anticipated, but the plan
  confirms.
