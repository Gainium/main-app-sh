# 040 — A liquidated deal records no closing order

## 1. Definition

### 1.1 Expected

A futures deal that ends because the venue liquidated the position is closed
like any other deal: its order history contains the closing order, and the deal
chart draws a sell marker (long) / buy marker (short) at the price the position
went away at. The user can see *what* ended the deal.

### 1.2 Actual

The liquidation order IS recorded — `MainBot.convertExecutionReportToOrder`
builds it (`typeOrder: liquidation`, `status: FILLED`, side opposite the
position) and `processOrderQueue` persists it with `saveOrderToDb` — but it is
persisted with **no `dealId`**. Every per-deal read is keyed on `dealId`
(`Bot.getDealOrders` matches `{ dealId, botId, status: 'FILLED' }`), so the row
is invisible from the deal: the deal's order history shows only the entry
orders, and the V2 chart — whose markers come from
`dealCompletedOrdersToTransactions` over exactly that list — draws no close
marker at all.

The deal itself ends up `status: closed`, `closeTrigger: liquidation`, with a
loss, and from the user's side nothing on the deal explains it.

## 2. Evidence

Reporter's paper DCA bot, `BOME-USDC` on `paperHyperliquidLinear`,
`LONG`, `leverage: 25`, `marginType: isolated`, `ordersCount: 20`.

Read live over the dashboard GraphQL as the reporter (read-only):

- deal `…12c9e7`: `status: closed`, **`closeTrigger: "liquidation"`**,
  `levels.complete: 6` of `21`, `avgPrice 0.000892`, `lastPrice 0.000859`,
  `profit.total −6.27`, `closeTime 1788991724111`.
- `getDealOrders` for that deal returns **6 orders, all `BUY`** — one
  `dealStart` and five `dealRegular`. No `SELL`. Nothing to draw a close marker
  from.
- `getBotOrders` for the same bot returns **10 orders with
  `typeOrder: "liquidation"`, every one of them `dealId: null`** — including
  `liquidation_1c2e6317-…`, `SELL`, `FILLED`, `price 0.000859`,
  `updateTime 1788991723365`: the same price as the deal's `lastPrice`, 746 ms
  before the deal's `closeTime`. That row *is* the close of the deal above; it
  is simply not linked to it.

So the closing order exists in the database, on the right bot, at the right
price and time, and the deal cannot see it.

Two supporting facts that place the defect in the link and not elsewhere:

- The frontend already understands the type: `mapOrderName` renders
  `'liquidation'` as `Liquidation order`, and `Bot.getDealOrders` excludes only
  `TypeOrderEnum.br`, so a liquidation row carrying a `dealId` is returned and
  rendered without any dashboard change.
- Nothing in the engine consumes it: `loadOrders` and `dcaHelper`'s order load
  both filter `typeOrder: { $nin: [liquidation, br] }`, and
  `processOrderQueue` returns before `setOrder`, so a liquidation row never
  enters the in-memory order map whether or not it has a `dealId`.

Out of scope — checked and NOT a defect on this report: the liquidation itself.
`isolated` margin at 25× liquidates ~1/leverage from the average entry
(paper's `liquidationPrice()` = `entry · (1 − 1/L) · (1 − fee)` ⇒ 0.0008559 for
this deal), and the ladder's later levels sit far below that, so the position
was always going to be liquidated with orders left unfilled. Account balance is
irrelevant to an isolated position. This spec does not change liquidation
behaviour.

## 3. Assumption (hypothesis)

The liquidation `Order` is constructed in `MainBot` — shared by grid, DCA and
combo — at a point where the deal it will close is not known yet, so it carries
no `dealId`; and the DCA path that *does* know (`processLiquidationOrder` →
`closeAllDeals(… DCACloseTriggerEnum.liquidation)`) never writes the link back.
Attaching the persisted row to the deal(s) that liquidation closed is
sufficient and necessary to make the close visible.

## 4. Solution

### 4.1

`processLiquidationOrder` already reads the bot's open deals on the symbol
before closing them. After `closeAllDeals` returns, the deals that stopped
being open are exactly the deals this liquidation closed. Link the persisted
liquidation row to them.

### 4.2

One venue liquidation can end more than one deal (a DCA bot may hold
overlapping deals on the same pair). The persisted row can only name one deal,
so:

- the first closed deal **claims the existing row** — no new document, no
  duplicate in the bot-wide order list, which is the only case that occurs when
  a bot holds one deal per pair;
- each further closed deal gets a **copy** of the row under a derived,
  deal-scoped `clientOrderId`, because `clientOrderId` is uniquely indexed.

### 4.3

The copy is a copy: same price, side, status, times and
`origQty`/`executedQty`. In particular the quantities stay `'0'`, exactly as
`MainBot` writes them today. A liquidation is not an order Gainium placed, and
every quantity-bearing consumer either excludes `typeOrder: liquidation`
outright or filters on `executedQty > 0`; inventing a quantity here would put a
number into ledgers that have never counted it. This spec changes *visibility*
only.

### 4.4

A deal that is still open after `closeAllDeals` is not linked. The link must
describe what happened, not what was attempted.

### 4.5

The link is written after the close, not instead of it: a failure to write it
must not affect the close. It is logged, not raised.

## 5. Out of scope

- The liquidation trigger and price (§2, last paragraph).
- Paper trading's margin model. The simulator has no margin-mode concept and
  treats every position as isolated; the reporter's bot *is* isolated, so that
  gap is not what this report is about and is left open.
- Grid and combo bots. `processLiquidationOrder` is DCA's; combo inherits the
  DCA helper and is covered by the same change, grid has its own path and is
  untouched.
