# 236 — An automatic grid stop leaves a part-filled order resting

Bug spec (Definition / Evidence / Assumption).

## 1. Definition

### 1.1 Expected

When a grid bot stops **itself** — its take profit or stop loss fires with the
action `stop`, its futures position is liquidated, its close order fills, or it
cannot find the pair's exchange info while starting — every order it has
resting on the exchange is cancelled, `NEW` and `PARTIALLY_FILLED` alike.
Nothing the bot placed is left for a closed bot that no longer manages it.

### 1.2 Actual

Those stops call `stop()` with no arguments. `stop()` passes
`cancelPartiallyFilled = undefined` to `cancelAllOrder`, which then selects only
`NEW` orders. A level that is part-filled when the bot stops keeps resting on
the exchange. When it fills, it opens or grows a position (on futures, at the
bot's leverage) that no bot manages, while the dashboard shows the bot closed.

The `stopAndSell` branch of the same take profit / stop loss already calls
`cancelAllOrder(true, …)`, so only the plain `stop` action and the other
automatic stops are affected.

### 1.3 Not changing

A **manual** stop still follows the user's choice for part-filled orders: the
`setStatus('closed', …, cancelPartiallyFilled)` path passes the user's flag
through unchanged, and any other user-initiated stop keeps its current
argument. Start-time refusals that run before the bot loads its orders
(archived, exchange unassigned, hedge-mode neutral, under-funded budget) are
left alone: there is nothing loaded for them to cancel.

## 2. Evidence

A production futures grid closed on take profit (action `stop`). Its log, in
order:

- 23:05:21Z — a grid BUY level placed `NEW`.
- 23:08:56Z — that level `PARTIALLY_FILLED` (24 of 80).
- 00:07:41Z — `TP trigger`; cancel requests sent for three other `NEW` BUY
  levels only; no `GRID-TP` order placed (so the `stop` branch, not
  `stopAndSell`).
- 00:08:42Z — bot closed.

The part-filled level never received a cancel request; its order row is still
`PARTIALLY_FILLED` for a closed bot. The `grid.closed-bot-order-resting`
invariant raised it.

Code: `closeBotByTp` (core `helper.ts`, and the parent repo's override that
production runs) calls `this.stop()`; `stop()` →
`cancelAllOrder(cancelPartiallyFilled, false, true)` →
`getOrdersByStatusAndDealId({ status: cancelPartiallyFilled ? this.orderStatuses : 'NEW' })`.

## 3. Assumption (hypothesis)

The automatic stop call sites omit `cancelPartiallyFilled`, so the close sweep
filters to `NEW`. Passing `true` at those sites makes the sweep include
`PARTIALLY_FILLED`. A test that drives the real `closeBotByTp` → `stop()` →
`cancelAllOrder` with one `NEW` and one `PARTIALLY_FILLED` level fails before
the change because no cancel is sent for the part-filled level.

## 4. Behaviour

### 4.1 Take profit / stop loss with action `stop`

A take profit (or stop loss) with action `stop` sends a cancel for every
resting level, including a part-filled one.

### 4.2 Other automatic stops

A liquidation stop and a filled close order stop the bot with
`cancelPartiallyFilled = true`. So does the stop for missing exchange info at
start.

### 4.3 Manual stop unchanged

`stop()` called the way a manual stop without "cancel part-filled" calls it
still leaves a part-filled level alone.

## Invariants

None added. The state this leaves is already caught by
`grid.closed-bot-order-resting` (the invariant that found this bug).
