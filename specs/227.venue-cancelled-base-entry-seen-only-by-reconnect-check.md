# 227 — a base entry the venue cancelled, seen only by the reconnect check, leaves the deal in `start`

Bug spec. Third route of the cancelled-entry check after `263de26`/`f4416a9`
(the order queue's cancel report), spec `203` (the reposition tick) and spec
`205` (the placement reply).

## 1. Definition

### 1.1 Expected

When the bot learns that a deal's base order was cancelled on the venue with
nothing executed — whichever way it learns it — and the bot did not ask for
that cancel, the deal is cancelled about `canceledBaseEntryDelayMs` later and
the bot is free to open a new one.

### 1.2 Actual

`checkOrdersAfterReconnect` (DCA; Combo inherits it) asks the venue about every
order it holds open. When the answer for a `dealStart` row is CANCELED it drops
the row from the order map and writes CANCELED to the DB — and nothing else.
`checkUnfilledBaseEntryCancel` is reached only from `processCanceledOrder`,
`placeBaseOrder` and the reposition tick. When the user stream drops the cancel
report and the reconnect pass is what sees it, the deal stays in `start` with
nothing on the venue until the old-start-deals cron cancels it up to 24 h
later. Nothing is logged at info level and the user is told nothing.

## 2. Evidence

Production, a Bitget DCA bot with a MARKET entry:

- `Deal created`, `Send base order`, `Processing msg … NEW`, `Save order …`,
  then 10 s later `Subscribed to user …` / `Check order after user stream
  reconnect`. No `Processing msg … CANCELED` and no `was canceled on the
  exchange` line for that order, ever. The row is CANCELED with 0 executed —
  written by the reconnect pass.
- Every other entry of the same bot in the same hour got its cancel report
  through the stream and was cancelled 15 s later by the queue route.
- The sentinel invariant `deals.start-stuck-nothing-resting` raised the deal
  30 min later.

Harness `reconnectCanceledBaseEntry.harness.spec.ts` drives the real
`checkOrdersAfterReconnect` of the DCA and the Combo helper over a venue that
answers CANCELED / 0 for a resting entry. Before the fix §4.1 fails in both: no
check is armed.

## 3. Assumption

The reconnect answer is one more report of the same venue cancel, and the check
it should arm already exists and is idempotent: `armCanceledBaseEntryDealCancel`
keeps one pending check per deal, and `cancelDealOfCanceledBaseEntry` re-reads
the deal status, the own-cancel record and the live entries before it acts. The
row has already been removed from the map when the check is called, so it does
not count itself as a live entry. Calling `checkUnfilledBaseEntryCancel` with
the merged row is enough; no new decision is needed.

## 4. Required behaviour

- §4.1 A `dealStart` row the reconnect pass finds CANCELED with nothing
  executed, on a `start` deal, not cancelled by the bot, with no other live
  `dealStart` row, arms the cancelled-entry check, and the deal is then
  cancelled — DCA and Combo.
- §4.2 The stream's late report of the same cancel leaves one pending check;
  the deal is cancelled once.
- §4.3 An answer that is still resting (NEW), carries a fill (spec 048 / the
  reconnect FILLED path own it), names a cancel the bot recorded, or concerns a
  deal that already left `start`, arms nothing.
- §4.4 A non-entry row (a take-profit or safety order) answered CANCELED arms
  nothing.
- Not changed: which orders are placed, re-placed or retried; what the
  reconnect pass books for FILLED / PARTIALLY_FILLED answers.
