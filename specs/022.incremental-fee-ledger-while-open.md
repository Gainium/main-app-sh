# 022 — accrue the observed-fee ledger on every fill, not just at close

Feature spec.

## Behaviour

A deal's `feeByAsset` and the on-pair portion of `feePaid` reflect
every fill observed SO FAR, updated after each one — base order,
every safety/DCA order, every partial or reduce-funds TP fill — not
only once, retroactively, when the deal fully closes. A user watching
an open deal can see what it has actually paid in fees up to that
point, the same way `currentBalances`/`avgPrice`/`levels` already
update incrementally today.

This is visibility only: it does not change what `closeDeal` computes
or persists at close (spec 014/020 stay authoritative there, estimate
fallback included) — it fills the gap where an OPEN deal has nothing
at all in these fields, which is what surfaced spec 020 and prompted
this ask.

Gated the same way the ledger already is: only deals carrying
`DCADealFlags.feeByAsset` (spec 014, "new deals only") get it; nothing
changes for deals without the flag.

## Design

**Recompute fresh from every filled order each time, never
incrementally accumulate onto the previous value.** `accrueFeeLedger`
(`feeLedger.ts`) ADDS an amount onto whatever ledger it's handed — safe
within one pass over a fixed order list (today's only caller,
`closeDeal`), unsafe if called from multiple places across a deal's
life, where the same order could be folded in twice (once when it
filled, again when `closeDeal` re-walks every order at the end). Both
this new incremental path and `closeDeal`'s existing one build their
result by walking `getOrdersByStatusAndDealId(..., status: ['FILLED',
'CANCELED'])` for the WHOLE deal every time — the fix is idempotent by
construction as long as each call seeds its ledger from empty, not from
whatever the deal currently has stored.

A new shared method, `computeObservedFeeLedger(deal)`, extracts the
OBSERVED-only portion of `closeDeal`'s existing loop — the
`observedFeeSplit`/`observedFeeLegs`/`accrueFeeLedger`/
`resolveLegUsdRate` machinery — with no estimate fallback and no
`offPairFeeUsd`/profit interaction (both are close-specific and
untouched by this spec). Called from `startDeal` and `updateDeal`
(single insertion point common to the regular/dealTP/roa branches — see
plan), it returns what the deal has actually paid, in whichever assets
it was actually paid in, as of the most recent fill.

`closeDeal`'s own loop keeps its estimate fallback and `offPairFeeUsd`
exactly as spec 020 left it, with one addition: it seeds
`findDeal.deal.feeByAsset` from an empty array rather than the deal's
current value, so its full recomputation can't double what an earlier
incremental update already added.

## Open questions

- Should the estimate-fallback (currently close-only) also run
  incrementally, so `feePaid` never has an "unobserved" gap while the
  deal is open? Proposed: no — `commission`/`fullFee` (via
  `getCommDeal`, spec 021) already gives an incremental ESTIMATE-based
  view today; duplicating that logic into `feePaid` while open would
  make one field mean two different things at two different times
  (pure-observed while open, observed+estimate-blend at close). Revisit
  if that turns out to read as a bug rather than a known progressive-
  refinement quirk.
- `updatePartiallyFilledTP` (a TP order that's PARTIALLY filled, still
  resting) is NOT touched — `getOrdersByStatusAndDealId`'s `FILLED`/
  `CANCELED` filter already excludes a partially-filled order
  everywhere else in this file, so there is nothing new for it to
  observe until the order is fully filled or canceled.
