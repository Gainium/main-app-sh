# 096 — The credential rate limiter keys on a header the caller chooses

## §1 Definition

### §1.1 Expected

The standalone server's limiters (`authLimiter`, 10 credential attempts a
minute; `apiLimiter`, 50 requests a minute) bound requests per real client.
A caller cannot reach a fresh bucket by changing a request header, and the
address recorded for a login (`ApolloContext.ip`) is one the caller cannot
choose.

### §1.2 Actual

All three sites read the leftmost `X-Forwarded-For` value raw. Any client can
set it, so varying it per request gives every request its own bucket, and the
recorded login address is whatever the caller wrote. The server never sets
Express's `trust proxy`, so there is no notion of which forwarding hops are
trusted.

## §2 Evidence

1. Code: `src/server/index.ts` keyGenerators and the Apollo context read
   `req.headers['x-forwarded-for']` before the socket peer.
2. Reproduction on the real server booted locally: 30 `token` mutations with
   wrong credentials, each with a different `X-Forwarded-For` — 30 allowed,
   0 throttled. The same 30 with one fixed header — 10 allowed, 20 throttled.

## §3 Assumption (hypothesis)

The bypass is entirely the raw header read; the limiter itself (window, max,
skip rule) is correct. Keying on Express's trust-proxy-aware `req.ip` removes
it.

## §4 Required behaviour

- §4.1 `TRUST_PROXY` unset: `X-Forwarded-For` is ignored; the socket peer is
  the client.
- §4.2 `TRUST_PROXY=<hops>`: the address is resolved through that many trusted
  proxies; entries a client prepends are ignored.
- §4.3 All three sites use one resolver (`getClientIp`).
- §4.4 Nothing else about the limiters changes (window, max,
  `AUTH_RATE_LIMIT_MAX`, the auth-operation skip rule).
