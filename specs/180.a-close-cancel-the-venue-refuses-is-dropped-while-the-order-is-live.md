# 180 — A close or stop cancel the venue refuses is dropped while the order is still live

Bug spec. Related: `112` (a late fill after close is sold), `134` (a teardown
cancel refused for rate is re-sent; this spec narrows its §4.5), `178` (a
cancel refused as transient gets a deferred re-send; this spec reuses that
ladder).

## §1 Definition

### §1.1 Expected

- **§1.1.1** A cancel is a *teardown* cancel when the bot is stopping, or when
  the order's deal is no longer open. `processDealClose` drops the deal before
  its order sweep, so this covers the close sweep. If the venue refuses a
  teardown cancel for any reason other than "unknown order", "cancel already
  in progress", rate limit or lockout, the bot sends the cancel once more
  after a short back-off.
- **§1.1.2** If the venue refuses that second cancel too, the bot asks the
  venue for the order's real state through the unknown-order lookup
  (`_handleUnknownOrder` / `getOrder`). The bot does not raise a bot error
  for the refusal.
- **§1.1.3** If the refusal says the order can never be cancelled (Coinbase
  `RFQ_ORDERS_CANNOT_BE_CANCELLED`), the bot skips the re-send and looks the
  order up straight away.
- **§1.1.4** The bot records the lookup's answer the usual way:
  - `CANCELED` retires the order.
  - `FILLED` goes back to the close sweep, which passes it to
    `handleUnknownOrder` → `processFilledOrder`. A late fill is sold as spec
    `112` describes.
  - `NEW` or `PARTIALLY_FILLED` puts the order on spec `178`'s deferred
    re-send ladder. That ladder keeps asking until the venue says the order
    is cancelled or filled. A ladder step that ends `FILLED` is also settled
    as a late fill.
- **§1.1.5** At the end of a deal close, `removeOrdersByDeal` drops only the
  orders that are no longer live. An order still `NEW` or `PARTIALLY_FILLED`
  after the sweep stays in memory and stays registered on the user stream, so
  its later fill or cancel still reaches the bot.
- **§1.1.6** Cancels on a running deal do not change. A take-profit re-size, a
  ladder rebuild or a settings change still sends a single request and keeps
  today's error reporting. Rate and lockout refusals keep their spec `134` /
  `178` handling.

### §1.2 Actual (before)

- **§1.2.1** `cancelOrderOnExchange` sends a refusal that matches neither
  `unknownOrderMessages` nor the in-progress list only to `handleErrors`.
  Nothing re-sends the cancel and nothing asks the venue. Spec `178` added a
  deferred re-send, but only for rate and lockout refusals.
- **§1.2.2** `dcaHelper.cancelAllOrder` ignores that result. `processDealClose`
  then calls `removeOrdersByDeal`, which calls `deleteOrder` on every order of
  the deal. That removes the order from memory and from `SharedStream`, so
  the venue's later events for it no longer reach the bot. The order can fill
  outside any deal, and its row stays `NEW` or `PARTIALLY_FILLED` for good.

## §2 Evidence

Production, Coinbase spot DCA deals. Identifiers are shortened because this
file is public.

- **§2.1** HONEY-USDC deal. Its safety order `D-RO-a68Fn…` was sent 1.6 s
  before the take profit filled. The close sweep logged
  `Reason COMMANDER_REJECTED_CANCEL_ORDER Method limitOrders() Step Send cancel
  request D-RO-a68Fn…`, and the deal closed. The order row is still `NEW`
  (0 of 4252.9 executed). Nothing re-sent the cancel.
- **§2.2** POND-USDC deal. The close sweep logged
  `RFQ_ORDERS_CANNOT_BE_CANCELLED … D-ROA-jyxMv8…`, and the deal closed. The
  row is still `PARTIALLY_FILLED` (739 of 5241 executed), on a closed deal.
- **§2.3** Both rows were read back through the dashboard API after the close.
  Both are `dealRegular` BUYs, so a later fill is coin that the closed deal no
  longer tracks.

## §3 Assumption (root cause, hypothesis)

- **§3.1** A teardown cancel is the last chance to learn the order's outcome:
  the deal is gone, and `removeOrdersByDeal` unregisters the order from the
  stream. So a refusal that is not "unknown order" is a dead end at close. The
  cancel is not re-sent, the venue is not asked, and the order is forgotten.
- **§3.2** Whether `COMMANDER_REJECTED_CANCEL_ORDER` is transient is
  unverified (here it came 1.6 s after placement). Each case has its own
  cover:
  - transient: the single re-send;
  - terminal: the lookup;
  - neither settles it: the deferred ladder, plus keeping the order tracked.

## §4 Fix

- **§4.1** `MainBot.cancelIsTeardown(order)` is `blockPriceCheck`, or spec
  `178`'s `cancelRetryWanted(order)`. In the DCA / Combo helper that is "its
  deal is no longer open".
- **§4.2** In `cancelOrderOnExchange`, for a teardown cancel that the batch
  did not serve and that did not fail its `-1` lookup, a qualifying refusal
  (§1.1.1) is re-sent once after `refusedCancelRetryDelay()`, unless it is
  uncancellable (§1.1.3). If the answer is still such a refusal, it goes to
  `_handleUnknownOrder` (§1.1.2). If the order is still live after that, it
  goes on `queueCancelRetry` (§1.1.4). Any other answer goes through the
  existing routing.
- **§4.3** `runCancelRetry` hands a `FILLED` result to
  `settleLateCancelFill`. The DCA helper implements it as
  `handleUnknownOrder`.
- **§4.4** `removeOrdersByDeal` keeps orders whose status is still live
  (§1.1.5).
- **§4.5** Spec `134` §4.5 is narrowed. A non-rate refusal is not put on
  `134`'s rate ladder, and §4.2 above applies to it instead.

## §5 Out of scope

- Rows that past closes already left `NEW` / `PARTIALLY_FILLED`. That needs a
  data repair.
- Cancels on running deals (§1.1.6).
