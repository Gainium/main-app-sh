# 039 — A base order that cannot be built strands the deal in `start`

Bug spec. The behaviour already exists and is wrong.

Sibling of [`038`](038.a-partly-filled-base-order-strands-the-deal-in-start.md).
That one is a deal stranded with a base order that *exists* and stopped
part-filled. This one is a deal stranded with **no order document of any kind** —
the entry was never built, so nothing was ever sent to the venue.

## §1 Definition

`placeBaseOrder` is the only way a DCA deal comes into existence. It writes the
deal row first (`createDeal`, status `start`) and only then builds the entry
order for it (`getBaseOrder`) and sends it.

### §1.1 Expected

The deal row exists to hold an entry order. If the entry order cannot be built,
the deal row must not survive the attempt: it must be retired (`canceled`) so it
does not count against the bot's active-deal limit, and so the account is left
exactly as it was before the attempt.

### §1.2 Actual

`getBaseOrder` returns `undefined` on every path where it cannot size or price
the entry. Its own balance branch does so explicitly — for
`orderSizeType: percFree` / `percTotal` it reads the account balance from the
venue and, if that read fails, returns
`handleErrors('Error getting balance: …', 'placeBaseOrder')`, whose return type
is `Promise<void>` (`dcaHelper.ts:8575-8580`).

`placeBaseOrder` guards its entire remainder behind `if (baseOrder) { … }`
(`dcaHelper.ts:8860`). When `baseOrder` is falsy every one of those statements is
skipped, the function falls through to `endMethod` and returns. **The deal row
written moments earlier is never rolled back.**

The result is a deal in `start` with zero order documents:

- it counts as an active deal (`deals.active`), so it consumes one of the bot's
  slots permanently;
- it is unclosable from the dashboard, whose deal actions require status `open`;
- it is not covered by any reaper — there is no periodic sweep for `start`
  deals, exactly as §1.3 of spec `038` records.

### §1.3 The one recovery path re-creates the same state

`restoreWork` walks `start` deals on every bot start. For a deal with no
un-cancelled `dealStart` row and an **ASAP** start condition it logs
`… not started yet. Place base order again` and re-enters `placeBaseOrder` with
`oldDealId` (`dcaHelper.ts:11241-11255`). If the entry still cannot be built —
and for a dead API key it cannot — that call takes the same silent early return.
So the deal is re-examined on every restart, forever, and never resolved.

(Non-ASAP deals are already cancelled by that loop, one branch above, because
replaying a stale trigger would open a trade the signal never asked for. The
ASAP branch is the gap.)

## §2 Evidence

Read-only production, 2026-09-10.

**State.** `dcadeals` with `status: 'start'`, `createTime` within 30 days and
older than 1 hour, `$lookup`-joined to `orders` on `dealId`: **213 deals, every
one of them with an order count of exactly 0**, across 18 accounts. One account
holds 145 of them (Binance spot, `paperContext: false`), created in bursts:


Each burst is a bot-worker process start (each carries a distinct pm2 pid), not

This separates the two hypotheses the issue left open. The entry was **not**
"never attempted": `placeBaseOrder` ran, reached `getBaseOrder`, and
`getBaseOrder` refused. Nor did it fail **at** the venue: `sendOrderToExchange`
persists its row before any short-circuit (spec `013`), so an attempt that
reached it would have left an order document — and there are none.

The bot's own record agrees: `status: 'error'`, `statusReason: 'API keys error'`,
`deals.active: 29`, of which 20 are these order-less `start` rows and only 9 are
real open deals.

**Why the bot did not simply refuse earlier.** `openNewDeal` calls `checkBalance`
first, but `checkBalance` itself builds a trial base order and, when that comes
back empty, bypasses the check and answers "affordable"
(`dcaHelper.ts:12873-12876`, `Cannot get base order, bypass check balance`). So a
venue that cannot answer "what is your balance" produces an *approval*, and the
deal is created.

## §3 Assumption (hypothesis, not fact)

The stranding is caused by the missing rollback at `dcaHelper.ts:8860`, not by
anything upstream of it. A deal reaching that point with a falsy `baseOrder`
holds no order and is inert; the fix is to retire it there, through the same
`closeDealById(…, cancel, reopen = false)` the restore loop already uses for a
stale non-ASAP deal one branch above.

Specifically NOT assumed, and deliberately out of scope:

- that the balance read should succeed (it cannot — the key is the user's to
  fix, and `AuthFailureGuard` already rate-limits the re-probe);
- that `checkBalance`'s bypass is wrong (it is a separate decision, and making it
  refuse would report a *balance* shortfall for an *auth* failure).

## §4 Required behaviour

### §4.1 Retire a deal whose entry could not be built

When `placeBaseOrder` cannot build a base order, and the deal it is placing for
is in `start` and holds no order document at all, the deal is cancelled before
the function returns.

### §4.2 The restore path heals what is already stranded

The same condition is reached through `oldDealId`, so the once-per-bot-start
replay of an already-stranded deal retires it instead of logging and returning.
No migration is needed for the deals stranded before this ships.

### §4.3 Never touch a deal that holds anything

A deal that holds any order row — resting, cancelled, part-filled or filled — is
left exactly as it is. Whatever position or history it carries is not this
change's business, and destroying it would be far worse than the stranding.
Likewise a deal not in `start` is never touched.

### §4.4 The user is told once, by the existing report

No new user-facing error. `getBaseOrder` has already reported the real reason
(`Error getting balance: …`) through `handleErrors` on the way out; a second
message would say nothing new. The cancellation itself is logged.

## §5 Unchanged

- A base order that *is* built keeps every existing behaviour: slippage retry,
  limit reposition, enter-market timer, `startDeal`.
- The non-ASAP branch of the restore loop keeps cancelling stale triggers.
- Pending-deal accounting is untouched: `createDeal` already releases the
  reservation when the row is written.
