# 184 — A placed Kraken order is retired as "never placed" and its fill is lost

Bug spec. Related: `154` (the Coinbase lookup by client order id this extends),
`155` (an order still being placed), `177` (retiring a `'-1'` order the venue
reports absent).

## §1 Definition

### §1.1 Expected

- **§1.1.1** When a venue accepts a placement, the order is recorded under the
  client order id the bot sent, with the exchange id the venue returned. This
  holds in memory, in the Redis order snapshot and in its `orders` row. Whatever
  `clientOrderId` the venue's answer echoes does not change which order the
  answer is about. The request named exactly one order.
- **§1.1.2** On the venues that are addressed by exchange id (Coinbase, Kraken
  spot, KuCoin full futures), an order still carrying the `'-1'` placeholder
  is looked up on the venue by its client order id before the bot treats it as
  "never placed":
  - Kraken spot: the exact `cl_ord_id` lookup, which covers the open AND
    closed orders, so a filled order is found too.
  - Coinbase and KuCoin full futures: the open-orders list, which is the only
    client-id view their connectors expose.
- **§1.1.3** When that lookup finds the order, its exchange id is adopted
  (memory + DB) and the order is then resolved through the ordinary
  exchange-id lookup. A fill is booked as a fill.
- **§1.1.4** When the lookup itself fails (timeout, rate limit, an ambiguous
  answer), the result is not a definitive not-found. The order is not retired
  and takes no quarantine strike. A later pass asks again.
- **§1.1.5** A `'-1'` order is retired by `noteOrderNotFound` only on a
  not-found the venue actually gave. The bot's own synthetic
  "no exchange order id" answer, given without asking anyone, never retires an
  order.
- **§1.1.6** Unchanged: an order the venue was asked about and does not hold
  is still retired after the spec 177 age floor (bugs #369 / #671 / spec 154
  §4.4).

### §1.2 Actual

- **§1.2.1** Kraken spot `openOrder` reads its own placement back by txid
  (QueryOrders, three tries). When all three miss, it falls back to
  `getOrder({ newClientOrderId: <txid> })`, and that answer carries the
  **txid as its `clientOrderId`**. `sendOrderToExchange` builds the saved order
  as `{ ...ord, ...processedOrder }`, so the saved copy is keyed by the txid:
  - `setOrder` files it under the txid,
  - the real client id keeps the `'-1'` write-ahead object in memory and in
    the Redis snapshot,
  - `updateOrderOnDb` filters on the txid and, with no upsert, writes nothing.
- **§1.2.2** `getOrder` on Kraken / Coinbase / KuCoin full futures answers a
  `'-1'` order with the synthetic `Order not found: no exchange order id`
  without asking the venue. Spec 154 covered the cancel and unknown-order
  paths for Coinbase only. The restart probe reads that answer as definitive,
  and `noteOrderNotFound` retires the live order as CANCELED. The user stream
  then routes nothing for it, so its fills never reach the deal.

## §2 Evidence

Production, combo bot on Kraken SOL/USD, 2026-10-20 UTC (order ids replaced by
placeholders):

- 14:16:32 the connector logs `Kraken broker | spot | SOL-USD |
  OAAAAA-BBBBB-CCCCCC`. The `orders` row for the grid order is created at
  14:16:32.934 with `orderId: '-1'`.
- 14:16:35.295 `Save order CMB-GR-aaaaaaaaaaa`. Same millisecond, the
  `botevents` row reads `Order created, orderId: OAAAAA-BBBBB-CCCCCC`. That
  field prints `orderToPush.clientOrderId` (§1.2.1). No `orders` row carries
  that txid as its `orderId`.
- 14:47:24.318 after a worker restart (`Found in redis 27 orders`):
  `Order CMB-GR-aaaaaaaaaaa not found on exchange: Order not found: no exchange
  order id`, then `… never reached the exchange and the exchange confirms it
  does not exist … — retiring it as CANCELED` (§1.2.2). 14:47:24.596
  `Order already exist qty: 1.77499981, price: 106.26` is the txid-keyed twin
  occupying the level.
- Kraken user stream: `new` at 14:58:13, `filled` 1.77499981 @ 106.26 at
  15:12:45. The bot logs nothing, and the deal is missing the buy.
- Earlier Kraken spot placements on other bots wrote the same txid-shaped
  `clientOrderId` into `botevents`.

## §3 Assumption (hypothesis)

1. `sendOrderToExchange` trusts the `clientOrderId` echoed in the placement
   answer instead of the one it sent (§1.2.1). The connector's fallback is what
   makes the echo wrong, but any echo that differs splits the order the same
   way.
2. `getOrder`'s `venueOrderId() === null` short-circuit is the only reason the
   restart probe never asked Kraken (§1.2.2). Kraken's client-id lookup
   already resolves this order, open or filled.

## §4 Fix

- **§4.1** `sendOrderToExchange`: an accepted placement's answer is pinned to
  the client order id that was sent. A differing echo is logged as a warning.
- **§4.2** `resolveNeverPlacedOrder` covers Kraken spot (the exact client-id
  `getOrder`, open + closed) and KuCoin full futures (open orders, as Coinbase).
- **§4.3** `getOrder` calls it before answering for a `'-1'` order. A failed
  lookup is returned as that failure, and an adopted id is resolved normally.
  A venue that answered "not held" yields a not-found worded as the venue's
  answer, not as the synthetic one.
- **§4.4** `noteOrderNotFound` refuses to retire on the synthetic reason.

- **§4.5** This supersedes spec 011 §4.2's "no venue call" for Kraken spot,
  as spec 154 already did for Coinbase. A `-1` order is looked up by its client
  order id, never sent as `-1`. Spec 011's own goal still holds: no cancel is
  addressed to `-1`, and a lookup that fails is never read as "not found". The
  premise that "the local row already says" the order never reached the venue
  is what §2 refutes.

## Invariants

Pack: `main-app/specs/184.invariants.json` (observe).

- `184.open-order-without-exchange-id` — an `orders` row still `NEW` /
  `PARTIALLY_FILLED` with `orderId: '-1'` 15 minutes after it was created.
  Placement answers arrive in seconds, so such a row is an order whose answer
  was never recorded (§1.2.1, or a worker stopped mid-placement). Windowed by
  `_id`, since `orders` has no full `created` index. The structural guard is
  §4.1; the invariant catches any other path to the same state.
