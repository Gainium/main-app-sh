# 183 — A restart restores a stale deal counter and never corrects it

Bug spec. Related: `151` (a cold restart loads the live deals the Redis deal
snapshot lacks), `172` (a deal restored `open` that Mongo still holds `start`).

## §1 Definition

### §1.1 Expected

- **§1.1.1** After any start, including a cold service restart, a DCA or combo
  bot's `deals` counter agrees with the deals the start loaded: `all` is the
  number of deals the bot has in the database, and `active` is the number of
  `open` + `start` deals the bot now manages. The same numbers
  `calculateBotDeals` already writes on a non-restart start.
- **§1.1.2** The corrected counter is persisted, so the next increment or
  decrement starts from it and writes a correct absolute value.
- **§1.1.3** A bot whose counter already agrees is not written: a service
  restart starts thousands of bots and must not issue one write each.
- **§1.1.4** If the database count fails, `all` keeps its stored value; `active`
  is still re-derived from the loaded deals.
- **§1.1.5** A DCA deal's creation finishes its counter increment before
  `createDeal` returns, as the combo `createDeal` already does.
- **§1.1.6** Not changed: the max-open-deals gate (`checkDealsAllowed`) counts
  the deals in memory and does not read this counter.

### §1.2 Actual

- **§1.2.1** On a cold restart the bot's data, `deals` included, is restored
  from the Redis `botData` snapshot. The snapshot is written through
  `@RunWithDelay`, so it can predate the last counter write. A deal that closed
  and a new one that opened seconds before the stop leave a snapshot counter
  that counts neither the new deal in `all` nor in `active`.
- **§1.2.2** `restoreWork` skips `calculateBotDeals` on a cold restart, and
  `loadOrders` only refreshes the in-memory `allDeals`. Nothing re-derives
  `deals`, so the next `updateBotDeals` writes the stale counter ± 1 into
  Mongo as an absolute value.
- **§1.2.3** Consumers that read the counter then act on a wrong value: the
  worker-restart and closed-bot sweeps select bots by `deals.active > 0`, so a
  stopped bot holding an open deal with `active: 0` is not reloaded and its
  deal is no longer managed; the bot list shows the wrong deal count.

## §2 Evidence

Production, one live bybitLinear DCA bot (max 1 deal, ASAP reopen),
2026-10-20 UTC, from the DCA-bot service logs and the bot's documents:

- 11:36:53 the previous deal closes; 11:36:54 its take-profit fills and a new
  deal is created (old process).
- 11:36:57 the whole DCA-bot service restarts.
- 11:37:26 `Found in DB 1 deals missing from redis: <new deal>` (spec `151`
  recovery), then the old deal closes a second time (it was still `open` in the
  Redis deal snapshot).
- The bot document now reads `deals: {all: 56, active: 0}` while the bot has
  57 deals, one of them `open`. The invariant
  `bots.active-deal-counter-drift` reports it.

## §3 Assumption (hypothesis)

The restart restored `deals: {all: 56, active: 0}` from the stale `botData`
snapshot (written after the close's decrement, before the new deal's
increment). The second close of the old deal decremented that stale value and
wrote `{56, 0}`. A load-time re-derivation from the database count and the
loaded deals yields `{57, 2}`, and the second close then leaves `{57, 1}`.

## §4 Solution

- **§4.1** `loadOrders`, after the deal count, calls `reconcileBotDeals`:
  `all` = the database count (stored value if the count failed), `active` =
  `getOpenDeals().length`. Written and emitted only when it differs from the
  stored counter, with a log line. It holds the `updateBotDeals` mutex so it
  serialises with increments and decrements.
- **§4.2** DCA `createDeal` awaits `updateBotDeals(…, true)`.

## Invariants

Covered by the existing `bots.active-deal-counter-drift` (main-app
`specs/invariants/deals.invariants.json`); no new invariant.
