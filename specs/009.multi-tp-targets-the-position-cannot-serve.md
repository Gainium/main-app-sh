# 009 — A multi-TP deal waits for targets its position could never serve

Issue #658. The part `005.zombie-deal-venue-position-reconciliation.md` (#630)
deliberately left open: 005 added the *backstop* (ask the venue, book the deal
closed when the position is gone). This is the **cause** of the divergence that
backstop exists to catch.

## §1 Definition

### §1.1 Expected

A multi-TP deal is finished when the position it opened has been fully closed.
The engine may arm fewer take-profit orders than the user configured targets —
lot-size rounding forces that whenever a target's share of the position is
below the venue's minimum order size — but once the last unit is sold the deal
must close, not wait for targets that can never fill.

### §1.2 Actual

`processFilledOrder` decides a multi-TP deal is finished by counting
**configured** targets (`dcaHelper.ts:14899-14913`):

```ts
const filled = new Set([...(deal.deal.tpSlTargetFilled ?? []), order.tpSlTarget ?? '']).size
const total  = useMultiTp && !order.sl ? (multiTp ?? []).length : 0
if (total > filled) { … return this.updateDeal(this.botId, order) }   // re-arm
this.allowToPlaceOrders.delete(dealId)
this.closeDeal(this.botId, dealId, order)
```

`getTPOrder`'s multi-TP splitter (`dcaHelper.ts:13578-13692`) cannot always
produce one order per configured target. Each target's slice is rounded **up**
to `symbol.baseAsset.minAmount`, so on a position only a few steps wide the
first targets consume all of it and the splitter stops (`end = true`). The
deal then holds no position, `filled` never reaches `total`, and every
subsequent price tick re-arms a take-profit against nothing.

## §2 Evidence

Deal `69f1b27faeba7a4880365abb` (bot `69de6e9e10716872ece23ce8`, user
`64e7a7f46c579b9917b1978a`, `paperBitgetUsdm`, XAUTUSDT SHORT, base order 0.02,
five multi-TP targets of 20 % each) — the deal 005 was written from. It has been
`status: 'open'` since 2026-04-29 while `paperFutures` has held its position
`CLOSED` since 2026-04-29T13:39:55Z, and the take-profit loop was still firing
on 2026-09-04 07:22 UTC.

### §2.1 The engine can only arm two of the five targets

Replaying that deal's shape through the real `getTPOrder`
(`src/bot/dca/multiTpCompletion.harness.ts`; XAUTUSDT on bitget USDT-M is
2 decimals on quantity, so `minAmount = step = 0.01`):

```
configured targets : 5
orders emitted     : 2          t1 qty 0.01 · t2 qty 0.01
total qty armed    : 0.02       (= the whole position)
```

20 % of 0.02 is 0.004; `math.round(0.004, 2, /* ceil */ true)` is `0.01`. Two
targets exhaust the position and the splitter's `end` flag drops targets 3-5.

### §2.2 Once both fill, the engine still asks for three more

With both armed targets filled, the deal holds nothing — `getTPOrder`'s own
debug line says so — and it still emits a take-profit order:

```
[debug] TP order. Base order size: 0.02, qty: 0, origQty: 0, qtyBase: 0
orders emitted against a position of 0 : 1     t3 qty 0.01
aggregate remaining qty after both fills : 0
aggregate remaining qty after ONE fill   : 0.01
```

The `0.01` is the `qty < symbol.baseAsset.minAmount → qty = minAmount` floor
firing on a `restQty` of zero. On futures both "too small to place" bail-outs
below it are `!this.futures`-gated, so nothing stops the order being sent.
That is what the venue answers `Reduce order is rejected` — 86 such `CANCELED`
order documents on this deal, dated 2026-08-06 … 08-08 (005 §2.3).

### §2.3 The completion test then cannot terminate

```
filled targets = 2, total = multiTp.length = 5
total > filled -> true  => RE-ARM
```

### §2.4 It is live on a real exchange, not only on paper

Production, read-only, 2026-09-05. Of the 46 open DCA deals with at least one
multi-TP target filled, **5** have order books that say the position is fully
closed — `Σ executedQty(dealStart|dealRegular) === Σ executedQty(dealTP)` — and
are still `status: 'open'`. All five are on `binanceUsdm` (a live venue, not a
paper one) and on one user, `648ea80e8c0a3ae6bdb1de2d`, opened 2026-09-03 …
2026-09-05.

`6a9905dc293c91a1d3473c76`, BIGTIMEUSDT, two targets (31 % at +3.3 %, 69 % at
+5.1 %), base order 1065:

```
09-03T05:30 dealStart FILLED  orig=1065 exec=1065 px=0.006604
09-04T12:31 dealTP    FILLED  orig=1065 exec=1065 px=0.00638   tgt=5c1ad4e9
```

The first target took the whole position, so the second can never fill; every
re-arm since is the `qty < minAmount → qty = minAmount` floor (BIGTIMEUSDT's
minimum is 1) placing an order against nothing, and the venue cancels it.
11 such `CANCELED` take-profits on this deal, 13 on `6a992916…` (PORTALUSDT).
The deals stay `open` with their funds accounted as in use, and `Futures
position` is `showUser: false`, so none of it reaches the user.

### §2.5 The backstop is already deployed, and it is a backstop

005's reconciliation shipped and closed the deal in §2 on 2026-09-05:

```
Deal 69f1b27faeba7a4880365abb (XAUTUSDT) reached its take profit, but
paperBitgetUsdm reports no open position for it — …
Deal closed, id: 69f1b27faeba7a4880365abb, profit: 0.7536194652471998$
```

It fires only when a take-profit level is next reached and only after two venue
probes five minutes apart, so a deal can sit open for months first — this one
did, from April to September. It settles deals that got into this state; it
does not stop them getting there.

### §2.6 Which side caused the divergence

The brief asks this to be settled before choosing a fix site. It is **neither**
of the two candidates it names:

- **paper-trading is not over-closing.** The venue took the position back in
  two 0.01 legs because main-app armed exactly two 0.01 take-profit orders
  (§2.1). The `order.service.ts:1462-1490` clamp is reached only when the order
  asks for more than the position holds, which is what `reduceOnly` means; a
  0.01 order against a 0.02 position takes the partial branch and decrements
  correctly.
- **main-app is not under-decrementing `currentBalances.base`.** For a futures
  short `base` is not the running position size — every sibling deal on this
  bot that closed *normally* also ends with `currentBalances.base ===
  initialBalances.base` (005 §3.1).

The divergence is that the deal's **target count** and the deal's **position**
are two independent numbers that the engine never reconciles.

## §3 Assumption (hypothesis)

The root cause is the completion test's `total`: it is the number of targets
the user *configured*, not the number the deal's position can *serve*. The
quantity that settles the question is already computed by the code that arms
the orders — `getTPOrder` in `aggregate` mode returns the base quantity the deal
still has to close (§2.2: `0.01` after one fill, `0` after two). A deal with
nothing left to close is finished, whatever its configured target count says.

The failing test therefore must be: a deal with two of five targets filled and
an aggregate remaining quantity of `0` re-arms today and must close instead —
and, in the same breath, a deal with one of five filled and `0.01` remaining
must keep re-arming, because closing it would abandon a live position.

## §4 Out of scope

- The `minAmount` floor manufacturing an order out of an empty `restQty`
  (§2.2). With the deal closed on the fill that empties it, that path is no
  longer reached from here; guarding the splitter *instead* would leave the
  deal with no take-profit order at all, which silently disables both
  `checkTPLevel` and 005's reconciliation probe — strictly worse.
- Back-filling deals already stuck. 005's reconciliation settles those.
- Whether five 20 % targets should be *offered* on a position only two steps
  wide. That is a bot-form/validation question, not an engine one.
