# 046 — The stuck-start sweep cannot reach a deal the worker has forgotten

Bug spec (existing behaviour is wrong).

## §1 Definition

### §1.1 Expected

`closeOldStartDeals` (`src/bot/index.ts`) exists to retire deals that have sat in
`status: 'start'` for more than 24 hours. A deal it selects must end up terminal,
or the sweep must stop selecting it.

### §1.2 Actual

The sweep dispatches through `closeDCADeal`, which posts `closeDealById` to the
owning bot worker. `closeDealById` resolves the deal from the worker's in-memory
map only (`this.getDeal(dealId)`). When the map has no entry it logs
`[WARN] Deal <id> not found when close` and returns — spec `030` added a
read-only report on top of that, gated to `manual`/`api` triggers, so the sweep's
`auto` trigger produces nothing at all.

The deal stays `start`, the sweep selects it again an hour later, and the same
warning is written. Forever.

## §2 Evidence

Production, read-only, 2026-09-15.

**The deal.** `6a86d694…` (`dcadeals`): `status: 'start'`,
`createTime === updateTime === 1787221652288` (2026-08-20T10:27:32.288Z) — the
document has never been written to since it was created, 26 days ago.

**Its only order row.** `typeOrder: 'dealStart'`, `type: 'MARKET'`,
`status: 'NEW'`, `origQty: '0.04'`, `executedQty: '0'`, **`orderId: '-1'`** — the
placeholder `main.ts` writes when an order has no venue-side identifier. Nothing
was ever acknowledged by the exchange for this deal. This is the shape
`src/db/migration/list/v45.ts` describes: `sendOrderToExchange` persists the row
before the local guards run, and since `3f7ae42` (2026-08-06) a locally refused
order is no longer retired, so it stays at `NEW`/`-1`.

**The loop.** `Gainium-DCA-bot-error`, live plus archived:

```
2026-08-21T11:15:02.523Z  [WARN] Worker 9 | Bot (dca) 6a46854d… | Deal 6a86d694… not found when close
…
2026-09-15T02:15:01.818Z  [WARN] Worker 8 | Bot (dca) 6a46854d… | Deal 6a86d694… not found when close
2026-09-15T03:15:01.804Z  [WARN] Worker 8 | Bot (dca) 6a46854d… | Deal 6a86d694… not found when close
2026-09-15T04:15:02.158Z  [WARN] Worker 8 | Bot (dca) 6a46854d… | Deal 6a86d694… not found when close
```

654 matching lines for this one deal in the retained window, one per hour at
`:15`, across several worker PIDs — i.e. the sweep has never once succeeded, not
even immediately after a restart.

**Why the map never holds it.** `loadOrders` (`src/bot/dcaHelper.ts`) reads the
deals from Mongo only when `loadFromDb` is true:

```ts
const loadFromDb = !(this.serviceRestart && !this.secondRestart) || !this.deals.size
```

On an ordinary service restart the map is rebuilt from the Redis mirror instead,
and the mirror is then re-written from that same map (`setDealToRedis`). A deal
missing from one snapshot is therefore missing from every later one. The bot's
own log says so directly — every restart of bot `6a46854d…` prints
`Found in redis 5 deals` and never `Get deals from DB`, while Mongo holds one
`open` and one `start` deal for it.

**Scale.** 24,503 `not found when close` lines platform-wide in the retained
window. A second deal, `6aa0f18f…`, has been repeating the same hourly warning
since 2026-09-09 — 133 lines.

**Who is hurt.** The deal is listed in the dashboard as a live `start` deal that
cannot be closed (the deal actions require `open`), on a bot that is otherwise
working normally. The bot's `deals.active` counter reads `1` — the map's view —
so the deal does *not* consume an engine slot; the harm is a permanently wrong
row the user cannot act on, plus the log flood.

## §3 Assumption (root-cause hypothesis)

Two separate causes stack; only the second is in scope here.

1. **Why the map is missing the deal** — the Redis-restore path above. Out of
   scope (spec `030` §5.1, spec `028`). Recorded here because it is the reason
   the fallback below has to exist at all: the worker will never re-learn this
   deal by itself.
2. **Why the sweep is powerless** — `closeDealById` treats "not in my map" as
   "cannot act". For a deal the *database* reports as `start` whose every order
   row carries the no-venue-id placeholder, there is nothing on any exchange to
   cancel, so the only thing standing between the sweep and a correct outcome is
   that it never looks at the database.

## §4 Required behaviour

### §4.1 The predicate

On an in-memory miss, read the deal and its order rows from the database. The
deal may be retired **only** when all of these hold:

| condition | why |
|---|---|
| DB status is exactly `start` | an `open` deal may hold a real position; a terminal one is a duplicate request. Both stay read-only, per spec `030` §3. |
| every order row has `orderId === '-1'` | the placeholder for "no venue-side identifier". One real id means something may be resting on the exchange, and abandoning it would orphan an order or a position. |
| every order row executed nothing | `executedFillQty` (spec `029`) — the combo placeholder row carries `executedQty === origQty` with no venue id, and a row that moved base is not inert. |
| the deal is older than {@link STRANDED_START_GRACE_MS} (24 h) | a placement genuinely in flight wears the `NEW`/`-1` shape for the seconds between the write-ahead save and the venue's answer (the bound `v45` uses for the same reason). The sweep's own filter is already 24 h, so this costs it nothing. |

Zero order rows also satisfies the row conditions, and deliberately so: that is
the shape `shouldDiscardUnbuiltBaseEntry` (spec `039`) already retires at
placement time, and a deal stranded that way before it shipped reaches here.

### §4.2 The action

`status: 'canceled'`, `closeTrigger`, `closeTime`, `updateTime`, written under
the filter `{_id, status: 'start'}` so a deal that moved on in the meantime can
never be clobbered. Plus one `botEvents` row (`event: 'Deal'`, `type: warning`)
naming the deal, its pair and why it was cancelled.

No notification via `processError`: nothing is broken for the user to act on, and
this path can fire for many deals at once when the sweep catches up.

No change to the bot's `deals.active` counter. Measured on production: the
counter tracks the worker's map, which never held this deal, so decrementing it
would corrupt a correct number.

### §4.3 What must NOT change

Spec `030` §5.3 is narrowed, not withdrawn. For every other shape reaching the
`!findDeal` branch — terminal, `open`, `error`, absent, unreadable, or `start`
with a venue-acked order — the branch stays read-only and falls through to
`reportUnactionedClose` exactly as `0ab6f7e` left it.

## §5 Non-goals

- §5.1 Fixing the Redis-restore hole in `loadOrders` (§3.1). It is the producer
  of the map miss and needs its own change; this spec makes the sweep correct in
  spite of it.
- §5.2 Retiring a `start` deal whose entry order DID reach the venue — deal
  `6aa0f18f…` is that shape (a resting `LIMIT` `dealStart` with a real venue id).
  Cancelling it without cancelling the order would orphan a live entry that can
  still fill, and the `!findDeal` branch holds neither the deal nor its orders in
  memory to cancel with. Its hourly warning therefore continues; re-seeding the
  worker's map so the ordinary close path can run is the fix, and it is a
  different change.
- §5.3 Retrying the lost base-order placement (the producer, F289/#761).
