# 063 — The bot details endpoint reads every bot type with the DCA field preset

## §1 Definition

`GET /api/v2/bots/:botType/details?fields=<preset>` returns a single bot with
the fields named by the preset **for that bot type** — `bots.grid` for a grid
bot, `bots.combo` for a combo bot, `bots.hedgeDca` / `bots.hedgeCombo` for a
hedge bot, `bots.dca` for a DCA bot (`core/src/server/v2/fieldConfig.ts`).

The preset is turned into a MongoDB projection verbatim for the non-hedge
branch (`parseFieldsParam` → `buildProjection` → `<db>.readData`,
`api.ts:1327-1341`), so a path the preset does not name is simply absent from
the response — no error, no warning.

### §1.1 Expected

- `GET /api/v2/bots/grid/details?fields=extended` returns the grid definition:
  the **price range**, the **level count**, the **grid type** and the
  **take-profit / stop-loss configuration**, plus the stored `symbol`,
  `initialPrice`, `avgPrice` and level counts — exactly what
  `GET /api/v2/bots/grid?fields=extended` (the list endpoint, spec 061)
  returns for the same bot.
- `GET /api/v2/bots/combo/details?fields=extended` returns the combo-only
  paths its own preset names.
- `meta.fields` describes the fields the caller actually got.
- The DCA response is unchanged.

### §1.2 Actual

Every bot type is read with the `bots.dca` preset, because the route registers
its field-selection middleware once, at registration time, with that preset
hardcoded (`api.ts:1240`).

For a grid bot that means `fields=extended` returns **none** of the grid
definition: no range, no level count, no grid type, no TP/SL configuration, no
`symbol`, no `levels`, no `initialPrice`, no `avgPrice`. What comes back is the
intersection of the DCA preset with a grid document — name, pair, status,
profit and timestamps — plus `settings.slPerc`, which happens to exist under
the same name on both schemas.

For a combo bot `dealsStatsForBot` is dropped. For a hedge bot the response
body is correct (`api.ts:1265-1273` re-resolves the preset for the hedge
branch) but its `meta.fields` still advertises the DCA preset, because the
metadata middleware reads `req.fieldSelection`, which the handler never
updates.

Consequence, same mechanism as specs 061 / 062: `POST /api/v2/bots/grid`
merges the request body over `GRID_FORM_DEFAULTS` (`api.ts:2576`), so a caller
that reads a grid bot through `/details`, adjusts one value and creates the
adjusted copy silently loses the **entire grid definition** — range, level
count and the TP/SL configuration — to the platform defaults.

## §2 Evidence

### §2.1 The endpoint, driven end to end on the local stack

A grid, a DCA and a combo bot with production field shapes were seeded into the
local `bots` / `dcabots` / `combobots` collections under one test user with a
write API key, and the endpoint called over HTTP against a locally running
main-app server (`node dist/src/server/index.js`, port 7503), signed the way
the v2 API requires.

`GET /api/v2/bots/grid/details?botId=<grid>&fields=extended` →

```
data.settings keys : ["name", "pair", "slPerc"]
data keys          : _id, cost, created, exchange, exchangeUUID, paperContext,
                     profit, profitToday, settings, status, statusReason,
                     updated, uuid, workingTimeNumber
settings.levels        : ABSENT      settings.lowPrice  : ABSENT
settings.topPrice      : ABSENT      settings.gridType  : ABSENT
settings.tpSl          : ABSENT      settings.tpSlAction: ABSENT
settings.sl            : ABSENT      settings.slAction  : ABSENT
symbol / levels / initialPrice / avgPrice / feePaid / flags : ABSENT

meta.fields        : ... "deals.all", "deals.active", "settings.baseOrderSize",
                     "settings.useSl", "settings.trailingTp",
                     "settings.trailingTpPerc", "settings.trailingSl",
                     "settings.ordersCount", "settings.activeOrdersCount" ...
```

`meta.fields` is the `bots.dca` extended preset verbatim — the response names
the preset it used, and it is the wrong one. Nine of those paths do not exist
on a grid bot at all; the eighteen paths the `bots.grid` extended preset adds
are never asked for.

### §2.2 The middleware is bound once, at registration

`v2API()` builds the route table once at boot and `src/server/index.ts:371`
spreads `fn.middlewares` into `app.get(...)` — the preset passed to
`fieldSelectionMiddlewares` at `api.ts:1240` can therefore never depend on
`:botType`, which is only known per request. The comment on that line — "field
presets are the same across all bot types" — is false: `ENDPOINT_FIELD_CONFIG`
declares five different bot configs, and `bots.grid` and `bots.dca` differ by
28 paths at `extended`.

### §2.3 Origin

`git blame src/server/v2/api.ts:1240` → `6e370e99` ("v1.14.8: Fixed API v2
bugs", 2026-03-11), the commit that first added the details route, with the
hardcoded preset and the comment already in place. **Latent** — six months
older than the report, and not a regression of any later change. The hedge
re-resolution at `api.ts:1265-1273` was added later and worked around the same
line for hedge only.

## §3 Assumption

The root cause is that the field preset is chosen **at route-registration
time** while the bot type is a **path parameter**, known only per request. Any
fix has to resolve the preset from `req.params.botType` inside the handler (as
the hedge branch already does) rather than correct the presets themselves —
the presets are right: `bots.grid` was corrected by spec 061 and `bots.dca` /
`bots.combo` by spec 062, and the list endpoints that use them return the full
definition from the same documents.

## §4 Solution

Resolve the endpoint key from the bot type for **all** bot types, in the
handler, and write it back onto the request so the response metadata describes
what was actually returned.

### §4.1 One mapping, used everywhere

`core/src/server/v2/fieldConfig.ts` gains `endpointForBotType(botType)` — the
`:botType` path segment → its `EndpointType`. It replaces the two hand-written
hedge ternaries (`api.ts:1127-1131`, `api.ts:1267-1271`), which are the same
mapping written twice for two of the five types.

### §4.2 The details handler uses it for every type

```ts
const endpointType = endpointForBotType(botType)
const fields = parseFieldsParam(req.query.fields as string | undefined, endpointType)
req.fieldSelection = fields
req.endpointType = endpointType
```

Both branches then use `fields`: the non-hedge branch through
`buildProjection`, the hedge branch through `filterFields`, exactly as today.
Assigning `req.fieldSelection` is what makes `responseMetadataMiddleware`
(which reads it when the handler calls `res.send`) report the preset that was
used.

### §4.3 One path the DCA preset was carrying for grid

`settings.slPerc` is named by the DCA `extended` preset and exists under the
same name on a grid bot, so it is the **one** field a grid caller receives
today that the `bots.grid` preset did not name — resolving the preset per type
would have dropped it. The other nine DCA-only paths (`deals.all`,
`deals.active`, `settings.baseOrderSize`, `settings.useSl`,
`settings.trailingTp`, `settings.trailingTpPerc`, `settings.trailingSl`,
`settings.ordersCount`, `settings.activeOrdersCount`) exist on no grid bot.

`GRID_BOT_EXTENDED_FIELDS` therefore gains `settings.slPerc`, and nothing
else. Measured against the pristine presets over the seeded production-shaped
grid document, switching `dca` → `grid` drops exactly that one path at
`extended` and nothing at `minimal` / `standard` — so one entry is the whole
cost of making this fix non-regressive. The §4.3 cases in
`botDetailsFieldPreset.spec.ts` hold that line for every preset. This is the only change to a preset; specs
061 / 062 are otherwise reused as they stand.

The sibling thresholds `settings.tpPerc`, `settings.tpTopPrice` and
`settings.slLowPrice` are *not* added here. They are unreadable today and stay
unreadable — that is §4.4's preset-content gap, not this spec's chosen-preset
bug, and widening the preset for them would also widen the grid **list**
endpoint, which is spec 061's surface rather than this one's.

### §4.4 Still not readable — not this spec's fix

`extended` remains an incomplete round trip for a grid bot. Measured after the
fix, by intersecting the resolved `bots.grid` `extended` preset with
`GRID_FORM_DEFAULTS`: of the 38 settings
`GRID_FORM_DEFAULTS` declares, **13 are readable and 25 are not** — `gridStep`,
`budget`, `useOrderInAdvance`, `prioritize`, `profitCurrency`, `orderFixedIn`,
`sellDisplacement`, `tpPerc`, `tpTopPrice`, `slLowPrice`, `useStartPrice`,
`marginType`, `leverage`, `futures`, `coinm`, `newProfit`, `strategy`,
`futuresStrategy`, `updatedBudget`, `feeOrder`, `ordersInAdvance`,
`tpSlLimit`, `slLimit`, `startPrice`, `skipBalanceCheck` — each of which the
create endpoint replaces with a default.

So this fix takes a grid bot's `/details` round trip from **0 of 38** settings
readable to **13 of 38**; it does not make it lossless. That remaining gap is
in the preset's *contents* and is shared with the grid list endpoint, not in
how the preset is *chosen*, so it is tracked as its own issue rather than
widened into this one.

### §4.5 Out of scope

- The presets themselves (specs 061 / 062) — reused as they stand.
- `fields=full` (projection `undefined`, whole document) and custom
  comma-separated field lists: `parseFieldsParam` ignores the endpoint for
  both, so they behave identically before and after.
- Other `:botType` routes: `/api/v2/discovery/bots/:botType(/sections)`
  register no field-selection middleware, and
  `/api/v2/backtest/:botType/requests` has one config
  (`backtest.requests`) for every type by construction.
