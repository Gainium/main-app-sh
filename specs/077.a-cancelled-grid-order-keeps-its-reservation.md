# 077 — A cancelled grid order keeps its reservation

Combo bot · `core/src/bot/comboHelper.ts` · minigrid ledger + deal assets

## 1. Definition

### 1.1 Expected

A `dealGrid` order that reaches a terminal state on the venue — `CANCELED` or
`EXPIRED` — is no longer on the book. The engine's in-memory ladder for that
minigrid (`minigrid.currentOrders`) is the record of *what is resting*, and it
is the only input to two numbers:

- `minigrid.schema.grids.{buy,sell}` — the level counts shown on the bot;
- `deal.assets.used.{base,quote}` — the funds the deal considers reserved,
  recomputed by `updateAssets()` as
  `sum(minigrid.currentOrders where side=BUY of qty*price)` for quote and
  `sum(... where side=SELL of qty)` for base (`comboHelper.ts:3178-3193`,
  `3216-3223`).

So once the venue reports a grid order terminal and nothing else rests at that
level, the level must leave `currentOrders`, the counts must be recomputed, and
`updateAssets()` must be re-run. `used.quote` must then equal the notional of
the BUY orders that are actually live.

### 1.2 Actual

On a LONG spot combo bot, a cancelled BUY grid order is never removed. The level
stays in `currentOrders` for the life of the minigrid, so `grids.buy` and
`used.quote` stay overstated by that order's notional. The overstatement is
cumulative and permanent: each further cancelled BUY adds to it.

Two consequences, both of which the reporter sees:

- the deal believes it has less free quote than it has, so the levels that were
  cancelled cannot be re-placed — a permanent hole in the BUY ladder;
- the level counts on the bot disagree with the exchange's book.

## 2. Evidence

Production, LONG spot Kraken combo bot, pair `SN64-USD`, one open deal, all
values read 2026-09-21.

### 2.1 The cancels happened, and they are CANCELED (not EXPIRED)

`Gainium-Combo-bot-out.log`, six `dealGrid` BUY orders between 20:42:12Z and
20:42:36Z, each reported `NEW` and then `CANCELED` in the same millisecond:

```
20:42:12.414Z  Processing msg SN64-USD CMB-GR-U302wF0li9M, NEW,      20.415, BUY
20:42:12.415Z  Processing msg SN64-USD CMB-GR-U302wF0li9M, CANCELED, 20.415, BUY
```

…and the same shape at 20.48, 20.545, 20.337, 20.259, 20.181. The `orders`
collection agrees: those rows are `status: "CANCELED"`, `typeOrder: "dealGrid"`,
`side: "BUY"`.

### 2.2 The ladder still counts them

| minigrid | `grids.buy` | live BUY orders | `grids.sell` | live SELL |
|---|---|---|---|---|
| …35c7 | **6** | **3** | 4 | 4 ✓ |
| …35cb | **10** | **7** | 0 | 0 ✓ |
| …35cf | 10 | 10 ✓ | 0 | 0 ✓ |

Six phantom BUYs; each cancelled order's minigrid matches its column. Every
SELL-side count reconciles exactly — only the BUY side leaks, which is the
control for "this is side-specific, not a generic staleness".

### 2.3 The money

`deal.assets.used.quote = 1363.62934536`. The notional of the BUY grid orders
actually live (`orders` aggregate, `status ∈ {NEW, PARTIALLY_FILLED}`) is
`156.95783496 + 365.33611008 + 526.21598400 = 1048.51 USD`.

Leak = **315.1194 USD**, which is the notional of the six cancelled BUYs to the
cent. The ladder below the hole (live BUYs resume at 20.104) is exactly the six
cancelled levels 20.181 … 20.545.

### 2.4 The path

`main.ts:6080-6085` calls `onCanceled(order, order.updateTime, order.status === 'EXPIRED')`
for both `CANCELED` and `EXPIRED`. The combo override
(`comboHelper.ts:2440-2480`) begins

```ts
if (!expired) {
  return
}
```

so for a `CANCELED` order — which is what every one of the six rows is — the
method returns before it reaches anything else. The `positionChanged` gate below
it (`(isLong && side===sell) || (!isLong && side===buy)`) is not reached on this
path at all; on a LONG bot it would additionally exclude a BUY even if it were.

## 3. Assumption (hypothesis)

The defect is the pair of gates in `processCanceledOrder`, in that order:

1. `if (!expired) return` — the *operative* one: it drops every venue
   `CANCELED`, which is the ordinary terminal state for a cancelled order;
2. `positionChanged` — a second filter that would drop a LONG bot's cancelled
   BUY even if (1) let it through.

Neither the level counts (`grids`) nor `deal.assets` are recomputed even on the
narrow path that does prune, so the two numbers §1.1 names would still be stale
there.

## 4. The fix, and what it must not break

### 4.1 Prune on any terminal state, both sides

Remove both gates for `typeOrder === dealGrid`. `EXPIRED` and `CANCELED` are the
same fact — the order is off the book — and the side of the order does not
change that.

### 4.2 Do not prune a level that is still live

`currentOrders` is matched by (price, qty, side), not by client order id: the
ladder is regenerated wholesale on every fill and each entry is given a fresh
`newClientOrderId`, so the id on the entry is not the id of the resting order.
A late `CANCELED` for an order at price P, arriving after the engine has already
re-placed a different order at P, must therefore NOT remove P.

The engine's own live-order index answers this. `processOrderQueue` calls
`deleteOrder(clientOrderId)` *before* `onCanceled` (`main.ts:6053`), so the
cancelled row is already gone from it: if
`getOrdersByStatusAndDealId({dealId, status: ['NEW','PARTIALLY_FILLED']})` still
holds a `dealGrid` order for the same minigrid, side, price and qty, the level
is live and is left alone.

### 4.3 Only grid entries, only this minigrid

The deal-side ladder (`deal.currentOrders`) holds `dealRegular` safety orders.
A price/qty/side match there is not the cancelled grid order, so the match must
also require `type === dealGrid` and the same `minigridId`.

### 4.4 Recompute what the prune invalidates

After a level is removed: `minigrid.schema.grids`,
`minigrid.schema.currentBalances` and `minigrid.schema.assets` from
`calculateMinigridBalances(currentOrders)` — the same three the fill path writes
(`comboHelper.ts:2706-2715`) — persisted with `saveMinigrid`; then
`updateAssets(dealId)`, which is what rewrites `deal.assets.used`.

### 4.5 Unchanged

- SHORT and futures bots: the branch is now side-agnostic, so a SHORT bot's
  cancelled BUY prunes exactly as it did, and its cancelled SELL — which used to
  be dropped by `positionChanged` — now prunes too. Futures deals compute
  `used` from `usedRegular` rather than the minigrids (`comboHelper.ts:3224`),
  so their `used` numbers are unaffected either way; their `grids` counts become
  correct.
- Non-grid orders (`dealStart`, `dealTP`, `dealRegular`, …): untouched; this
  override returns for them exactly as before.
