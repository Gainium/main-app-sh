# 146 — an aligned grid quantity gains a lot in the step alignment

Bug spec.

## 1. Definition

### 1.1 Expected
`MainBot.generateGridsOnPrice` aligns each grid level's size to the venue lot
step (`baseAsset.step`). A size that is already an exact number of lots keeps
its size. A size between two lots rounds up to the next lot. The venue-minimum
raises that follow the alignment are unchanged.

The Bitget futures price alignment in `sendOrderToExchange`
(`priceMultiplier.decimals`) follows the same rule for prices.

### 1.2 Actual
The alignment computes `mod` as `gridQty % step`, or as
`MathHelper.remainder(gridQty, step)` when `newBalance` is set, and when
`mod > Number.EPSILON` it sets `round(gridQty - mod + step, precision, up)`.
For some exact multiples, the float remainder comes back a hair under a whole
step:

- `0.118 % 0.001 = 0.000999…` → `0.118 - mod + 0.001 = 0.11800000000000001`
  → ceiling at 3 decimals → **0.119**.
- `MathHelper.remainder(0.29, 0.01) = 0.00999…` → **0.30**.

The aligned size gains a lot. When precision is finer than the step allows, it
can also leave the grid altogether: 0.12 at a 0.002 step becomes 0.121.

In a combo deal this shows up two ways:

- The base order is sized from the base grid. A bumped pivot level uses part
  of the budget, and the base order comes out one lot short. With a 25-quote
  base order at 201.30 and a 0.001 step, it buys 0.117 instead of 0.118.
- The minigrid laid over the filled base order sells one lot more than was
  bought: 0.119 at 211.58 above the 0.117 buy.

## 2. Evidence

- Code: `src/bot/main.ts` `generateGridsOnPrice`, the `initialGrids` branch
  (`mod` / `gridQty` block), and `sendOrderToExchange`'s Bitget futures price
  block. Both have been unchanged since the first public release.
- The quantity reaching the alignment is already rounded to
  `baseAssetPrecision`, which is derived from the step itself. So with
  ordinary `10^-n` steps, every size the alignment sees is an exact multiple,
  and every bump it makes is spurious.
- Reproduction through the real `getBaseOrder` and `generateGridsOnPrice`, as
  pinned in `src/bot/comboGridLotAlignment.spec.ts` §3. Base order 0.117
  (`newBalance: false`) against 0.118 (`newBalance: true`). Minigrid sell
  0.119 at 211.58.
- Call-site sweep: steps from 10 to 1e-8, including steps the precision does
  not divide, every value at engine precision, both branches, both rounding
  modes. 10.7% of aligned values gained a step. Price ticks: 0.05, 0.01,
  0.005, 0.001 and 0.0001 ticks all bumped some aligned prices.

## 3. Assumption (hypothesis)

The only defect is the on-grid test. A float remainder is not a reliable
"is this an exact multiple" test, and `Number.EPSILON` cannot catch a
remainder that is almost a whole step. `MathHelper.gridRemainder` is a port of
the backtester's helper of the same name, which already makes this decision
for the backtester's order sizing. It returns 0 when `a / b` is within a
scale-aware tolerance of a whole number, and otherwise returns exactly
`remainder(a, b)`. Deciding "aligned" with it, and leaving the remainder used
for off-step sizes untouched, removes the bump and changes nothing else.

## 4. Required behaviour

- §4.1 An exact multiple of the step has no remainder (0.118/0.001,
  0.29/0.01, 0.235/0.001, 0.3/0.1, 2.2/0.05, 4.91e-6/1e-8).
- §4.2 A size just below or just above a lot keeps its remainder.
- §4.3 Every exact multiple reads as aligned, across steps from 10 to 1e-8.

## 5. What must not move

- §5.1 For an off-step value, `gridRemainder` returns exactly `remainder`.
- §5.2 An off-step size that reaches the alignment rounds up as before. The
  outputs are pinned to the unfixed engine's, on both branches.
- §5.3 The venue-minimum raise after the alignment is unchanged.
