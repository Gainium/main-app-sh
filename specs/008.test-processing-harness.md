# 008 — Port `app`'s integration-test harness into `app-sh`

Not part of the fee-accuracy initiative's business behaviour (specs
`003`/`006`/`007`) — a prerequisite for it. Spec `007`'s two-stage TP
retry (§2 there) is exactly the kind of logic a colocated `.spec.ts` pure
function can't exercise: it's a decision made *inside* legacy,
DB/exchange-coupled `createTransaction`/`closeDeal`/`sendOrderToExchange`
code, across multiple fills, with persisted state that must survive a
process restart. Confirmed (research pass): `app-sh` has no integration
test harness today — every `.spec.ts` file in this repo is a colocated,
pure-function unit test (`package.json:8`'s `mocha ... 'src/**/*.spec.ts'`
glob), none imports a DB connection or stubs the exchange client. This
spec ports the harness that already exists, and is proven, in the sibling
repo `app`.

## §1 Current state

`app-sh` (`package.json:8`): `mocha --timeout 20000 --exit -r
ts-node/register --extension ts 'src/**/*.spec.ts'`. `src/db/data.ts`
always builds a real Mongo connection string from env vars — no
test-mode branch:
```ts
const getMongooseConnect = async () => {
  return (
    MONGO_DB_CONNECTION_STRING ??
    `mongodb://${MONGO_DB_USERNAME}:${MONGO_DB_PASSWORD}@${MONGO_DB_HOST}:${MONGO_DB_PORT}/${MONGO_DB_NAME}`
  )
}
```
No `mongodb-memory-server`, no `sinon`, in `package.json`. No `tests/`
directory at the repo root (only colocated `src/**/*.spec.ts`).

`app`'s sibling capability, `app/src/db/data.ts` (full file):
```ts
import { MongoMemoryServer } from 'mongodb-memory-server'
import coreConnect from '../../core/src/db/data'
import { NODE_ENV, TEST_EMAIL, MONGO_DB_URI } from '../config'

const getMongooseConnect = async () => {
  let mongooseConnect = await coreConnect.connection()
  if (NODE_ENV === 'testing' || TEST_EMAIL === 'true') {
    if (MONGO_DB_URI) return MONGO_DB_URI
    const mongoServer = await MongoMemoryServer.create()
    mongooseConnect = mongoServer.getUri()
    process.env.MONGO_DB_URI = mongooseConnect
  }
  return mongooseConnect
}
```
Layered on top of `core/src/db/data.ts` — the embedded copy of this
repo — which is, confirmed, byte-identical to `app-sh`'s own
`src/db/data.ts` above. **The in-memory-Mongo capability has only ever
existed in the outer `app` repo; `app-sh`/`core` never had it.** `app`
also carries `tests/processing/` (5 files, largest 1761 lines) and ~40
flat `tests/*.ts` files, run via dedicated npm scripts
(`processing:test`, `invariants:test`) that are not part of `app-sh`'s
own script set — `app-sh` has no equivalent scripts to run them even if
the files existed here.

`app`'s exchange stub (used throughout `tests/processing/`, e.g. 8 call
sites in `orderProcessing.ts`):
```ts
sinon.stub(ExchangeChooser, 'chooseExchangeFactory').returns(() => ({
  openOrder: (data) => Promise.resolve({ status: StatusEnum.ok, reason: null, data: {...} }),
  getBalance: () => Promise.resolve({ status: StatusEnum.ok, reason: null, data: [...] }),
  latestPrice: (_symbol) => Promise.resolve({ status: StatusEnum.ok, reason: null, data: PRICE }),
  getAllPrices: () => Promise.resolve({ status: StatusEnum.ok, reason: null, data: [...] }),
}))
```
`ExchangeChooser` is imported from `app`'s own
`src/exchange/exchangeChooser.ts` — `app-sh` has a module at the same
path (`src/exchange/exchangeChooser.ts`); this spec does not assume its
interface is identical to `app`'s copy without checking at gate 5.

`app`'s test pattern, one full example read (`orderProcessing.ts:1-340`):
`before` seeds fixed DB rows and starts a real `socket.io`+`http` server
on a fixed port (stream-layer real, not stubbed); `beforeEach` creates a
real user doc via the DAO; each `it` stubs `ExchangeChooser` per-test and
calls a **real production code path** (a GraphQL resolver directly, e.g.
`resolvers.Mutation.createComboBot(...)`) against the real DAOs +
in-memory Mongo + stubbed exchange, then asserts on what actually landed
in Mongo and what the resolver returned; `after`/`afterEach` wipe
collections between tests, sharing one `MongoMemoryServer` per process
rather than spinning one up per test.

## §2 Target behaviour

`app-sh` gains the same three pieces, ported rather than reinvented:

1. **In-memory Mongo, in `app-sh`'s own `src/db/data.ts`.** Since
   `app-sh` has no outer `core/`-consuming repo to layer this in (it *is*
   the core), the `NODE_ENV === 'testing'` branch goes directly into
   `app-sh`'s own connection module — not a wrapper file, because there's
   nothing to wrap.
2. **A `tests/processing/` directory** (new, at the repo root, alongside
   the existing colocated `src/**/*.spec.ts` convention — this does not
   replace colocated unit tests, it adds a second, integration-shaped
   tier for logic that genuinely needs DB + exchange-stub + multi-call
   sequencing to exercise). A new npm script, `processing:test`, mirroring
   `app`'s (`tsc --project tsconfig.json && ... mocha ... 'tests/processing/**.ts'`).
3. **The `ExchangeChooser.chooseExchangeFactory` sinon-stub pattern**,
   ported as-is once `app-sh`'s own `exchangeChooser.ts` interface is
   confirmed to match (gate 5 check, not assumed here).

**Not ported in this pass:** the socket.io server stub. Nothing in spec
`007`'s planned integration tests needs to assert on a stream emission —
only on what lands in Mongo (the deal's sticky retry flag, per `007`) and
what the exchange stub was called with (the fallback-sized order). Add it
later if a test genuinely needs it; don't carry infrastructure nothing
uses yet.

## §3 Open questions

- **Does `app-sh`'s `src/exchange/exchangeChooser.ts` actually expose
  `chooseExchangeFactory` with the same shape `app`'s does?** Not verified
  here — this repo's research pass confirmed the *path* exists, not
  interface parity. If it differs, the stub shape in §2 item 3 needs
  adjusting at gate 5, not silently guessed at now.
- **One shared `MongoMemoryServer` per test process (app's pattern) or
  one per file?** `app`'s reason (avoid the startup cost per test) still
  applies here; default to the same choice unless a specific test needs
  isolation stronger than "wipe collections between tests" provides.
- **Does this repo's `tsconfig.json` need a `tests/` include path added**,
  the way `app`'s `mocha:test`/`processing:test` scripts run `tsc
  --project tsconfig.json` before mocha? Check at gate 5 rather than
  assume the existing config already covers a directory that doesn't
  exist yet.
