# 210 — A restart mid re-price restores the cancelled entry as live

Bug spec. Plan: `plans/210.restart-restores-a-cancelled-entry-as-live.md`.
Test: `src/bot/coldRestartOrderSnapshot.spec.ts` — "an entry re-priced just
before the restart (spec 210)".

## §1 Definition
- Expected: when the bot service restarts while a DCA deal in `start` is
  re-pricing its unfilled LIMIT entry (cancel the resting entry, place a new
  one), the restart ends with exactly one entry placed for the deal.
- Actual: the restart re-prices the newer entry (cancels it) and then refuses
  to place a replacement with "Deal … already have and active base order". The
  deal stays in `start` with nothing on the venue and no message to the user.

## §2 Evidence
- Production, 2026-10-30: a DCA deal re-priced its entry at 03:43:48 (cancel of the old entry, new entry saved),
  the bot service restarted at ~03:44:10, `_loadOrders` logged "Found in redis
  … orders" and "Added 1 open orders from DB missing in redis", the restore
  path logged "<new entry> not filled. Create new one", the venue confirmed its
  CANCELED, and `placeBaseOrder` logged "already have and active base order".
  The invariant `deals.start-stuck-nothing-resting` then flagged the deal.
- Code: the cold-restart branch of `MainBot._loadOrders` trusts the Redis
  snapshot, which is written through a debounce, and merges in only Mongo's
  OPEN rows (spec 109). A row the bot cancelled after the snapshot's last write
  is CANCELED in Mongo but still NEW in the snapshot, and the open read cannot
  correct it. `placeBaseOrder` then finds that NEW `dealStart` row in the order
  map and refuses.

## §3 Assumption
The stale NEW row restored from the snapshot is the whole cause: with it gone,
the restore path's cancel-and-replace places one entry. The test drives the
real `_loadOrders`, `checkBaseOrder` and `placeBaseOrder` and fails on exactly
the production refusal line without the change.

## §4 Required behaviour
- §4.1 On the cold-restart snapshot path, a snapshot row held as NEW with
  nothing executed that Mongo's open read did not return is looked up in Mongo
  by `clientOrderId` (unique index). If Mongo holds it CANCELED or EXPIRED with
  nothing executed, it is not restored — as a cold load from Mongo would not.
- §4.2 Only those rows are read; when every NEW row is confirmed open there is
  no extra read.
- §4.3 Unchanged: rows with a fill on either side (snapshot PARTIALLY_FILLED,
  or Mongo CANCELED with an executed quantity), rows Mongo does not hold, rows
  Mongo holds FILLED, reloads (which never read the snapshot), and re-pricing
  while running.
- §4.4 If the lookup fails, the snapshot is kept as today and a warning logged.
