# 002 — Bots go deaf to their user-stream channel after a concurrent subscribe burst

Bug spec (Definition / Evidence / Assumption). Companion plan:
`plans/002.user-stream-channel-lost-on-concurrent-subscribe.md`.

## §1 Definition

### §1.1 Expected

A bot that holds resting orders on an exchange account is subscribed to that
account's `userStreamInfo<exchangeUUID>` Redis channel for the whole time it
holds them, or it is loudly broken: a greppable warning, a visible bot error,
and an automatic re-subscribe. Every message published on the channel —
`Subscribed to user …` (stream (re)connected, reconcile now), `RECONCILE VIA
SWEEP` (the fill-failsafe found a divergence), `INFORM USERS`, and the new
`PING` liveness probe (§4) — reaches every bot on that account.

### §1.2 Actual

On 2026-09-02 17:11:59 the prod DCA bot worker restarted. Thirteen DCA bots
of one user, all on Kraken account `918d10eb-…`, were loaded on Worker 11
within 10 ms of each other (17:12:33.961–.971). From that moment until the
next worker restart at 2026-09-03 12:53 **none** of them received a single
message on `userStreamInfo918d10eb-…`:

- seven connector reconnects (each publishes `Subscribed to user`) between
  09-02 22:24 and 09-03 08:50 — zero bot log lines;
- twelve `RECONCILE VIA SWEEP` publishes between 07:48 and 12:42, all
  `receivers=1` — zero bot log lines;
- the same worker logged 209 receipts on *other* accounts' channels in that
  window, so its Redis subscriber connection was alive.

The account channel's last healthy receipt was 09-01 18:54, under the
previous worker pid. Bot `6a96dd02…` restarted by the user at 07:45:50
joined the dead channel, opened a deal, placed six orders and then produced
zero log lines for five hours while Kraken filled a safety order it never
saw. No error was logged anywhere; nothing retried. The `receivers=1` was the
API process (`core/src/utils/user.ts:697` subscribes the same channel for
balance handling), not the worker.

## §2 Evidence

- Prod pm2 logs `Gainium-DCA-bot-out*.log` (worker pid 3235606, 09-02
  17:11:59 → 09-03 12:53), `Gainium--fill-failsafe-out.log` (12 sweeps,
  `receivers=1`), `Gainium-----Binance-user-stream-connector-out.log`
  (reconnect timestamps, `User … already exists` on the 12:53 reload).
- `core/src/db/redisPubSub.spec.ts` reproduces the loss deterministically
  against a fake client that mirrors `@redis/client` 5.10 `pub-sub.js`
  bookkeeping: wire order `UNSUBSCRIBE > SUBSCRIBE > UNSUBSCRIBE`, server
  subscription gone, both listeners registered client-side.

## §3 Assumption (root-cause hypothesis)

`setExchangeCredentials` (core `bot/main.ts` and the main-app override) runs
`await redisSubGlobal.unsubscribe(ch, cb)` then `redisSubGlobal.subscribe(ch,
cb)` for a callback that was never registered. In node-redis 5:

1. an `unsubscribe(ch, listener)` for a channel with **no local entry** sends
   a real `UNSUBSCRIBE` (`pub-sub.js`: `if (sets) {…} args.push(channel)`);
2. the local entry for a pending `SUBSCRIBE` is created only when its reply
   arrives;
3. `subscribe(ch, listener)` on an existing, non-unsubscribing entry adds the
   listener **without a command**.

With two bots on one channel inside one round trip: bot 1's `SUBSCRIBE` is on
the wire, bot 2's `unsubscribe` sees no entry and sends `UNSUBSCRIBE`
(server: subscribed → unsubscribed), bot 2's `subscribe` then dedups against
the entry bot 1's reply just created. Client: two listeners. Server: nothing.
`RedisWrapper`'s existing retry only covers "not ready" and rejected
commands; this path succeeds silently. The wrapper's own `subscribeMap`
bookkeeping is also bypassed by the redundant pre-unsubscribe.

## §4 Required behaviour after the fix

- §4.1 `RedisWrapper.unsubscribe(ch, cb)` never sends a command for a
  listener the wrapper did not register.
- §4.2 `subscribe`/`unsubscribe`/`resubscribe` for one channel are serialised
  per channel inside the wrapper, so a channel's wire commands never
  interleave between callers.
- §4.3 `RedisWrapper.resubscribe(ch)` forces a wire `UNSUBSCRIBE` +
  `SUBSCRIBE` for every registered listener, re-establishing the server
  subscription regardless of the client's belief; returns the listener count.
- §4.4 `setExchangeCredentials` no longer unsubscribes before subscribing.
- §4.5 A bot answers every message on its channel by writing
  `HSET gainium:userStreamAck:<exchangeUUID> <botId> <nowMs>` (fire and
  forget). This is the acknowledgement the fill-failsafe (main-app spec 001)
  reads after a sweep or a `PING`.
- §4.6 While holding resting orders, a bot that has heard nothing on its
  channel for `USER_STREAM_SILENCE_MS` (default 6 min) **and** whose
  fill-failsafe prober is alive (heartbeat `gainium:failsafe:heartbeat`
  fresh with `pingMs > 0`) logs a warning, runs `resubscribeUserStream()`
  (§4.3 on both the info channel and the account event channel, plus a
  fresh `open stream` to the connector), and on the first message after the
  repair runs the reconnect reconcile once. After two silent repairs in a
  row it raises a visible, non-stopping bot error.
- §4.7 A DCA bot that is stopped while a deal is open releases its channel
  listeners when the last deal closes (today `stop()` only calls
  `closeUserStream()` when no deal was open at stop time; the instance is
  later deleted with live listeners).
- §4.8 `SharedStream.addListener` must not silently skip the Redis subscribe
  when its client is still connecting.

## §5 Open questions

- §5.1 The connector logged nothing for bot `6a96dd02…`'s 07:45:50
  `open stream` request (it logged `already exists` for every sibling on the
  12:53 reload). Whether that rabbit message was dropped is not established
  and is out of scope here; the stream was already open, so it changed
  nothing this time.
- §5.2 Combo/grid/hedge workers were not measured for the same silence; the
  mechanism is shared code, so they are assumed exposed.
