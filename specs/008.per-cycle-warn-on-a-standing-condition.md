# 008 — A standing, user-caused condition is re-reported every cycle

Issue #652 (`Gainium-DCA-bot-error.log is 93% one WARN: "Not enough balance to
start new deal"`).

`openNewDeal` refuses to open a deal when `checkBalance` says the account cannot
fund the base order. The refusal is correct and the condition is the user's to
fix (add funds, or lower the order size). What is wrong is the *cadence*: the
refusal is reported afresh on every evaluation of a condition that does not
change between evaluations.

## §1 Definition

### §1.1 Expected

- §1.1.1 A bot that cannot fund a new deal on a pair reports that **once**, when
  the condition first holds, not once per evaluation cycle.
- §1.1.2 It reports again when the condition **clears and returns** — a user who
  funds the account, opens a deal, and later runs short again must be told
  again.
- §1.1.3 The user's existing periodic reminder is preserved. `Cannot start deal`
  is configured `logMode: coalesce`, `logWindowSec: 86400`, so a condition that
  simply persists surfaces to the user about once a day; suppressing repeats
  must not turn that into a single lifetime notification.
- §1.1.4 Everything the refusal branch *does* — releasing the pending slot,
  invoking `cbIfNotOpened`, and (terminal DCA only) `this.stop()` — keeps
  happening on every cycle. Only the *reporting* is deduplicated.
- §1.1.5 `Deal symbol <X> not in pairs` is an internal observation that the same
  loop immediately acts on. It belongs at debug level, not in the error stream.

### §1.2 Actual

`dcaHelper.ts:12530` and `comboHelper.ts:5180` call
`this.handleErrors(msg, 'openNewDeal', '', false, true)` unconditionally on each
refusal. Neither `handleErrors` (`main.ts:2701`) nor `processError`
(`main.ts:2393`) suppresses a repeat of a *warning*:

- §1.2.1 `handleErrors` inserts a `botevents` document on every call
  (`setEvent` defaults to `true`, and the subType's `showUser` is `true`, so
  nothing clears it).
- §1.2.2 `processError`'s only repeat gate is
  `status === error && previousStatus !== error && statusReason === subType`.
  The call site passes `setError = false`, so this path never puts the bot into
  `BotStatusEnum.error`; the gate is therefore never satisfied and the log line
  is written every time.
- §1.2.3 The re-raise backoff below it rate-limits the *user notification*
  only. The log write and the `botevents` insert both happen above it.
- §1.2.4 The message text embeds `required` and `price`, which drift with the
  market on every cycle, so no downstream dedupe that keys on message text can
  collapse these either.

### §2.4 `Deal symbol <X> not in pairs` is warn-then-immediately-handle

`dcaHelper.ts:1554` sits in `loadOrders()`. Each hit is pushed to `newSymbols`
and subscribed 20 lines later (`dcaHelper.ts:1573-1578`). `loadOrders` re-runs
periodically, so the same deals re-warn forever:

03:35:31.300Z  Deal symbol VVVUSDT / QUSDT / UAIUSDT not in pairs

No `botevents` row and no user notification — this one is purely a log-level
misclassification.

## §3 Assumption

*Hypothesis, not established fact.*

The root cause is that the reporting helper the two call sites use has **no
notion of a condition that is still the same condition**. `handleErrors` is
built for events; these call sites use it for a *state*. Because the only
existing repeat gate keys on `BotStatusEnum.error`, and a warning never sets
that status, every evaluation of a standing state is reported as a new event.

Therefore the fix belongs at the call sites — the only place that knows the
condition has a lifetime and knows when it ends (`checkBalance.status` becoming
true) — and not inside `handleErrors`, which cannot tell a standing state from
a genuine repeat.

A latch keyed on `(reason, symbol)` per bot instance, set on refusal and cleared
when the balance check next passes for that symbol, must therefore reduce the
per-cycle stream to one report per transition. If a test that drives the refusal
branch N times still reports more than once without the balance clearing, this
assumption is wrong.

## §4 Non-goals

- §4.1 Demoting the balance refusal to `debug`. The DCA terminal branch calls
  `this.stop()` in the same block; a user whose terminal deal was stopped for
  lack of funds must still be told, and terminal bots are excluded from the
  latch for that reason.
- §4.2 Changing `boterrorsubtypes` for `Cannot start deal`. Its `showUser` /
  `errorsBot` / `logMode` are admin-managed data and are correct; the defect is
  the call frequency, not the classification. (Per
  `bot-error-rule-tightening-is-undone-by-seeder`, a rule edit would be
  re-seeded anyway.)
- §4.3 Any change to the balance check itself. `checkBalance` is right to refuse.
