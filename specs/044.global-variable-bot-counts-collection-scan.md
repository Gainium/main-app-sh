# 044 — Counting the bots attached to a global variable scans every bot document

Bug spec (see `.claude/skills/gainium-dev-flow`, Part 0).

## §1 Definition

### §1.1 Expected

Asking "how many bots use global variable V?" — `getBotsByGlobalVar(v)` in
`core/src/bot/utils.ts:757` — must be answerable from an index. The only
selective predicate the question has is `vars.list === V`, and it is an
equality on an array of variable ids, so the database should walk the index
entries for that one variable and examine at most the bots actually attached
to it.

### §1.2 Actual

The query has no usable index. Every call reads **every document in the
collection**, on all three bot collections, and repeats that per variable and
per call site. `dcabots` is the collection where this bites: it is the
largest of the three and holds essentially all of the variable usage.

## §2 Evidence

All four measurements below are live and read-only.

### §2.1 The production slow-query profile (mongo-index snapshot, 2026-09-13T08:15Z)

```
 #    total_s     %  recent_s   last    count     p50     p95      max    ex:ret  plan       ns
 2.     5,572    2%     1,821     9h   12,043     380   1,084    2,755    53,524  COLLSCAN   gainium.dcabots
    command  pipeline[$match,$group] {isDeleted:{$ne},vars.list}
```

12,043 executions, still firing, 1,821s of slow-op time in the most recent
77h, and 53,524 documents examined per document returned.

### §2.2 `dcabots` carries no index this query can use

```
dcabots  _id_ | userId_1 | uuid_1 | parentBotId_1 |
         userId_1_status_1_created_-1 | userId_1_created_-1
```

`combobots` and `bots` likewise have none.

### §2.3 A live production explain of the exact shape

```
plan        : GROUP <- COLLSCAN  filter {vars.list: {$eq: V}, isDeleted: {$not: {$eq: true}}}
docsExamined: 51755      (= the whole collection)
keysExamined: 0
timeMillis  : 95
```

95ms is a single warm-cache run with no competition; the profile above is what
the same shape costs under production concurrency (p50 380ms, max 2,755ms).

### §2.4 The scan is ~39x larger than the answer, worst case

Measured on production `dcabots`: 51,755 documents, of which **9,465** carry a
non-empty `vars.list`, spread over **447** distinct variables and **69,740**
(variable, bot) pairs. Fan-out is 156 bots per variable on average and
**1,320** for the most-used one. `combobots`: 3,760 docs / 69 with variables.
`bots`: 2,895 docs / 0 with variables.

### §2.5 The shape maps 1:1 onto one call path

`countData` (`core/src/db/crud.ts:442`) calls Mongoose `countDocuments`, which
issues exactly the `pipeline[$match,$group]` of §2.1. `getBotsByGlobalVar`
runs it three times — once per bot collection — and
`updateRelatedBotsInVar` runs `getBotsByGlobalVar` once **per variable on the
bot**, from bot create / save / clone / delete
(`core/src/bot/index.ts:3460,3596,3999,4754,4959,6074,6167`), paper reset
(`core/src/graphql/handlers/paper.ts:103`) and user maintenance
(`core/src/utils/user.ts:2058`). At the measured average of 7.4 variables per
bot that is ~22 full-collection scans for one bot save.

## §3 Assumption (hypothesis)

The root cause is a missing index, not a bad plan: `rejectedPlans` is empty
because the planner has no candidate to reject. `isDeleted: {$ne: true}` is an
anti-predicate and cannot bound a scan — the same reasoning already written
down for `parentBotId_1` at `core/src/db/schema.ts:3263-3265` — so
`vars.list` is the only indexable field in the filter. Declaring a
single-field multikey index on `vars.list` on all three bot schemas should turn
the plan into an IXSCAN bounded by that variable's fan-out.

## §4 Required behaviour

- §4.1 `botSchema`, `comboBotSchema` and `dcaBotSchema` each declare an index
  on `{ 'vars.list': 1 }`.
- §4.2 The index is single-field, not compound with `isDeleted` (§3).
- §4.3 With the index present, `{isDeleted: {$ne: true}, 'vars.list': V}` plans
  as an IXSCAN on `{vars.list: 1}` and examines at most that variable's
  fan-out, not the collection.
- §4.4 The answer is unchanged: the index-planned count equals the count from a
  forced collection scan.

## §5 Non-goals

Reducing the *number* of calls (`updateRelatedBotsInVar`'s per-variable loop,
the three-collection fan-out) is a separate change and is not in scope here.
