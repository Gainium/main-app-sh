# 177 — A restart mid-order strands a filled entry and a never-placed take-profit

Bug spec (Definition / Evidence / Assumption). Two defects, one trigger: the
DCA bot worker is restarted while orders are in flight.

## 1. Definition

### 1.1 A start deal whose entry filled before the restart

- **§1.1.1 Expected.** On a cold restart, a DCA deal in `start` whose entry
  order the bot already knew to be `FILLED` (the order map, restored from the
  Redis snapshot, holds it `FILLED`) is booked: the entry is confirmed with the
  venue by its client order id, its row is saved as the venue reports it, and
  `startDeal` opens the deal and places its take-profit.
- **§1.1.2 Actual.** `restoreWork` reads the entry's Mongo row. When the
  `FILLED` write died with the process the row still says `NEW`, so it calls
  `checkBaseOrder`, which reads the ORDER MAP, finds `FILLED`, and matches none
  of its branches. Nothing is logged and the deal stays in `start` holding an
  unbooked position, at every later restart too.
- **§1.1.3** If the venue contradicts the snapshot (answers with a non-`FILLED`
  status), the venue's answer replaces the map copy and `checkBaseOrder` runs
  on it as today. If the venue cannot be read, the map's `FILLED` stands: it is
  the venue's own earlier report and a filled order never becomes unfilled.
- **§1.1.4** A row Mongo already holds as `FILLED` keeps today's path. A
  user start is not a restart and is unchanged.

### 1.2 A take-profit the venue never received

- **§1.2.1 Expected.** An order still at the `-1` placeholder (no exchange id
  ever recorded) that the venue definitively reports as absent is retired after
  a short age floor (`BOT_NEVER_PLACED_ORDER_MIN_AGE_MS`, default 5 minutes),
  and on the restart reconcile its take-profit is placed again.
- **§1.2.2 Actual.** It is retired only after the 24h quarantine floor
  (`BOT_ORDER_QUARANTINE_MIN_AGE_MS`), so the deal goes a day without an exit.
- **§1.2.3 Unchanged.** An order with a real exchange id is never retired and
  is quarantined only past the 24h floor. A not-found the venue cannot be
  trusted on right after placement (KuCoin `orderNotExist`, Hyperliquid
  `unknownOid` — `isNotFoundUnreliableJustAfterPlacement`) keeps the 24h floor.
  An order younger than the short floor is not judged.
- **§1.2.4** A safety order retired the same way on the restart reconcile is
  re-sent through the existing "Send order again" path.

## 2. Evidence

Production logs, a DCA bot worker restarted while orders were in flight:

- Bybit spot MARKET entry: the user stream reported `Filled`, the bot logged
  `Processing msg … FILLED` and then `Save order` (the placement path's
  `setOrder` of the FILLED copy), and the process stopped before either
  un-awaited Mongo write landed. Mongo row: `NEW`, `orderId '-1'`,
  `executedQty '0'`; deal `start`, balances 0. Each later restart logs
  `Found in redis 1 orders` (no "Added … from DB" line, so the snapshot held
  this clientOrderId and, by `mergeOpenOrdersIntoSnapshot`'s rank rule, kept
  its FILLED copy over the DB's NEW), then `Checking for existing deals`, then
  nothing for the deal. Of `checkBaseOrder`'s branches only a map status of
  `FILLED` is silent (`NEW` logs "not filled. Create new one",
  `PARTIALLY_FILLED` settles).
- Binance spot take-profit at `-1`: each restart's reconcile logs `… not found
  on exchange: Order does not exist.`; the row stays `NEW` and the deal has no
  resting take-profit. `noteOrderNotFound` returns at the 24h age guard.
- Reproduction: `src/bot/restartMidOrder.spec.ts` drives the real
  `restoreWork` and restart `checkOrders` over both shapes.

## 3. Assumption (hypothesis)

- §1.1: the restore decides "filled?" from Mongo alone while `checkBaseOrder`
  decides from the map; a FILLED map copy over a NEW row falls between them.
- §1.2: `noteOrderNotFound` applies the 24h propagation-lag floor to `-1`
  orders as well. That floor exists for venues that briefly deny a just-placed
  order; a Binance/Bybit "does not exist" minutes after a placement that never
  returned an id is an answer, not lag. The restart TP check also kept counting
  a retired take-profit as resting, so even a retire would not re-place it.

## Invariants

The existing `orders.phantom-unacked` invariant (main-app
`specs/invariants/deals.invariants.json`) is the state this leaves behind and
already watches it; no new invariant.
