# 074 — A refused close re-arms and re-announces itself on every close attempt

Bug spec. Forward fix on top of spec `053` (the refused-close restore) and spec
`055` (its deal-lock variant), both of which are live.

## 1. Definition

### 1.1 Expected

When a deal close is refused by the venue, the engine puts a take-profit back on
the book so the deal is not left holding its whole position with nothing that
can fill (spec `053` §4.1), and says so when it cannot (§4.2).

Both are **recovery** actions. A recovery action must:

1. only be attempted where it can possibly work, and
2. be attempted a bounded number of times while the condition persists.

### 1.2 Actual

Neither holds.

1. **The restore runs for every refusal reason.** `restoreCloseAfterRefusal` is
   called from the terminal-refusal branch of `closeDealById` with no test on
   what the venue actually said. A re-armed take-profit sells exactly the base
   the refused close was sizing, so the only refusal it can answer is one about
   funding that base — yet it also fires after a revoked API key, an IP
   allow-list rejection and a position that is already flat. Each produces a
   second order the venue refuses for the same reason as the first, and a
   user-facing message that names funding as the cause when funding is not the
   cause.
2. **Neither the restore nor the report is bounded.** The branch they sit in is
   re-entered on **every** close attempt, and a stuck deal's close is retried at
   the price-tick cadence. So a deal whose base has genuinely left the account
   re-sends the same refused order and re-raises the same warning for as long as
   it stays open — days, in the shape spec `053` was written from.

## 2. Evidence

The engine's own `close refused | …` lines, read back from a running deployment
of the spec `053`/`055` code over an eight-minute sample:

- **Unbounded re-entry (§1.2.2).** A single stuck deal re-entered the restore
  **16 times in those 8 minutes** — roughly two attempts a minute, the close
  path's own cadence. Nothing about the deal changed between attempts, and the
  restore sends the quantity the close was just refused for, so every one of
  them was answered the same way.
- **Restores on refusals no order can answer (§1.2.1).** Roughly **one restore
  in sixteen** went out after a refusal that is not about funding — a revoked
  or unpermitted API key, an IP allow-list rejection, or a contract with no
  position left to reduce. Each produced a second refused order and a
  user-facing message blaming funding.
- **The restore almost never covers the deal.** Uncovered reports and restore
  attempts arrive one for one, i.e. essentially every restore in the sample left
  the deal still bare. Where the shortfall is real, the second answer is the
  first answer.

### 2.1 What this evidence also refutes

The hypothesis under investigation was that `covered` is derived from the bot's
in-memory order index, which `sendOrderToExchange` populates *before* the venue
answers, making `reportUncoveredAfterRefusal` unreachable. It is not:

- `sendOrderToExchange` calls `deleteOrder(clientOrderId)` on every definitive
  venue refusal before returning, so the write-ahead row is gone by the time
  `restoreCloseAfterRefusal` re-reads `resting()`; and
- the report has fired 1,973,027 times in 10.6 hours, which is the opposite of
  dead code.

The `covered` derivation is therefore correct and is left alone.

## 3. Constraints

### 3.1 The restore must stay sized from the deal's own position

Unchanged from spec `053` §3.4. Nothing here inspects a wallet total or a
sibling deal's reservation. The code owner's position stands: a bot operates on
its own allocation, and a cross-bot misconfiguration is not something the
platform silently compensates for.

### 3.2 The close's own retry cadence is not touched

The close is the primary recovery; the restore is a fallback for a deal nobody
is closing any more. Bounding the restore must not slow a close down, so the
window applies to the restore/report pair only.

### 3.3 The user must not lose information

The venue's own refusal is already reported by `handleOrderErrors` one branch
above this one, on every attempt, with the reason the venue actually gave. What
§4.2's message adds is the *uncovered position*, which is only meaningful for
the funding case.

## 4. Solution

### 4.1 Gate the pair on the refusal reason

`restoreCloseAfterRefusal` and `reportUncoveredAfterRefusal` run only when the
refusal is a funding refusal (`isErrorNotEnoughBalance`, i.e. the shared
`matchesNotEnoughBalance` venue-string list). Any other reason falls through to
`handleOrderErrors`' accurate report alone.

### 4.2 Bound the pair with a per-deal cooldown

A `RetryBackoff` keyed `(botId, dealId)`, namespace `ucr`, 5 min → 1 h — the
same ladder as `dpp` and `nb`, chosen for the same reason: nothing is waiting on
the restore. A restore that does rest an order `clear()`s the window; one that
leaves the deal uncovered `record()`s it and reports. While suppressed, the
attempt is a debug line naming when the next one lands.

### 4.3 Nothing else changes

`restoreCloseAfterRefusal`, `reportUncoveredAfterRefusal`, the `covered`
derivation, the spec `050` trailing-retry exclusion and the spec `053` §4.3
adaptive-close clamp keep their current behaviour.

## 5. Assumption (hypothesis, not fact)

The re-entry is driven by `closeDealById` being called again — by the price
tick's stop-loss/take-profit close path — not by anything inside the restore
itself. If that is right, a cooldown on the restore costs no recovery speed:
the close keeps asking at its own cadence and a shortfall that clears is picked
up by the close, not by the restore.

Gate 2's tests must fail on the *unbounded re-entry* and on the *reason gate*,
not on some incidental path.

## 6. Out of scope

`Order failed because you don't have any positions in this direction for this
contract to reduce or close.` is a position-already-flat refusal that
`positionAlreadyClosedReasons` does not match (it carries `in this contract`,
the venue says `in this direction for this contract`). Such a deal should be
booked closed, not re-armed. That is a separate change with its own risk —
booking a deal closed is not reversible — and is tracked separately. §4.1 stops
this code re-arming it in the meantime.
