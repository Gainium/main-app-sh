# 242 — Order execution modes for base order, DCA, take profit and stop loss

Feature spec. Phased: §6 says what each phase delivers.

## §1 Summary

A bot has one execution setting per stage — base order (`entryExecution`), DCA
orders (`dcaExecution`), take profit (`tpExecution`), stop loss (`slExecution`)
— each an `OrderExecution` (`core/types.ts`). It says how the order is placed
once the engine decides to trade: `market`, `limit`, `chase` (chasing limit) or
`split` (split order). The dashboard shows the same control in every section.

Until this spec the same choices were spread over unrelated fields
(`startOrderType`, `notUseLimitReposition`, `useLimitTimeout`/`limitTimeout`,
`dcaByMarket`, `closeOrderType`, `closeDealType`, `comboTpLimit`,
`comboSlLimit`), several of which do something other than what their label says
(§3).

## §2 Triggers decide which modes exist

§2.1 A **price-level trigger** is a price the bot knows before it is reached:
percentage or ATR/ADR take profit, scaled/custom DCA levels. A limit order can
rest at that price in advance. `chase` is not offered — a resting limit already
gets that price.

§2.2 A **signal trigger** has no known price: deal start, indicator, webhook,
manual or bot close. Nothing can rest in advance. All four modes are offered.

§2.3 A **stop loss** sits on the wrong side of the price (a limit sell below the
price fills at once), so nothing can rest in advance. Offered: `market`,
`chase`, `split`. A real exchange-side stop order is out of scope.

§2.4 When a stored mode is not offered for the current trigger (the user changed
the take-profit type after choosing), the engine uses the nearest offered one:
`chase` → `limit` on a price-level trigger; `limit` → `chase` on a stop loss
(the only limit a stop can use, and what a combo stop "Limit" always did); any
other → `market`. The dashboard applies the same mapping.

## §3 Legacy settings keep their exact behaviour

When a stage's execution field is absent (`null`/`undefined`), the engine
derives it from the legacy fields, and the result must reproduce what the
engine did before this spec:

| Stage | Legacy | Derived |
|---|---|---|
| entry | `startOrderType` MARKET | `market` |
| entry | LIMIT, `notUseLimitReposition` | `limit`, timeout = Enter Market Timeout or 0 |
| entry | LIMIT | `chase`, reprice 10 s, no cap, timeout = Enter Market Timeout or 0 |
| dca, price level | `dcaByMarket` | `market`, else `limit` timeout 0 |
| dca, indicator | — | `market` |
| tp, DCA, price level | `closeOrderType` MARKET | `market`, else `limit` timeout 0 |
| tp, DCA, indicator/webhook | `closeDealType` closeByLimit | `chase`, timeout = Enter Market Timeout or 35 s; else `market` |
| tp, combo | `comboTpLimit` | `chase`, timeout as above; else `market` |
| sl, DCA, indicator | `closeDealType` closeByLimit | `chase`, timeout as above; else `market` |
| sl, DCA, percentage/ATR/webhook | — | `market` |
| sl, combo | `comboSlLimit` | `chase`, timeout as above; else `market` |
| manual/bot/api close | the close type passed | closeByLimit → `chase`, timeout as above |

The dashboard writes both the new field and the closest legacy value, so an
engine without this spec still behaves sensibly.

## §4 Mode behaviour

§4.1 **market** — one market order, as today.

§4.2 **limit** — price-level trigger: the order rests at the level, as today.
Signal trigger: placed once at the current price and not moved. In both cases,
`timeoutSec > 0` means: once the timeout elapses, whatever is unfilled is
cancelled and executed at market. For a resting order the count starts at the
order's **first partial fill** — the unambiguous evidence that price reached
it (a price-feed touch with no fill is not; the order simply keeps resting).
`timeoutSec = 0` leaves it open.

§4.3 **chase** — placed at the current price, cancelled and re-placed at the
current price every `repriceSec`. The limit price never moves beyond
`maxChasePerc` from the price at which the order was first triggered (`0` = no
cap). Once `timeoutSec` has elapsed since the first placement, the unfilled
remainder is executed at market. The timer arms from the first placement and is
not reset by re-placements.

§4.3.1 **Chase price comes from the top of the book.** A limit at the last
trade price usually crosses: a buy at the last price is at or above the best
ask and fills at once as a taker, so the chase never waits for a fill at the
user's price (observed live on 2026-11-15 for a base order and for split
slices). Every placement of a `chase` order set through the stored execution
setting — base order, close, split slice, re-placements included — asks the
venue for its best bid and best ask at that moment (connector `GET
/bookTicker`, through the balancer; paper trading forwards it to the real
venue) and prices a buy at the best bid, a sell at the best ask, then applies
`maxChasePerc`. No answer within 3 s, an unsupported venue, or an unusable book
(a side missing or ≤ 0, bid above ask) falls back to the last trade. Legacy
limit settings (§3) keep pricing at the last trade, unchanged.

§4.4 A **stop loss** in `chase` always has a timeout ≥ 1 s; an absent or zero
timeout is treated as 35 s.

§4.5 **split** — `slices` equal parts. `pace: iceberg` keeps one slice open and
places the next `sliceIntervalSec` after the previous fills; `twap` places a
slice every `sliceIntervalSec`. `sliceMode`: `limit` (price-level trigger only,
not stop loss — slices are placed at the trigger price once price reaches it;
nothing rests in advance, see §6.3.1),
`chase`, or `market`. `floorPerc > 0`: when price moves more than that against
the trigger price, `onFloor: pause` stops placing slices until it returns,
`market` executes the remainder at market. A split never leaves more than the
position open: the slices sum to the order size, and a final slice below the
exchange minimum is merged into the previous one.

## §5 Invariants

§5.1 A close in `limit`/`chase` with `timeoutSec > 0` never leaves a deal with
an unfilled close order older than `timeoutSec + repriceSec + 60 s` past its
trigger.

§5.2 A `chase` limit price never lies beyond `maxChasePerc` of its trigger
price (when `maxChasePerc > 0`).

§5.3 A stop loss never waits on an unfilled limit for longer than its timeout.

§5.4 A split's executed quantity never exceeds the order quantity.

## §6 Phases

§6.1 **Phase 1** (this change): a pure resolver for §2–§3; indicator and
webhook closes pick limit or market from their own stage's execution instead of
the shared `closeDealType`; bot-driven limit closes (take profit, stop loss,
manual/bot/api) follow §4.3 using the stage's settings — this replaces the timer logic that sent a "close by limit" to market
after one reposition interval (~10 s) instead of after the timeout; DCA stop
loss honours `chase` (§4.4); `maxChasePerc` caps close prices (§4.3).

§6.2 **Phase 2**: resting single-target take profit `limit` timeout from its
first partial fill (§4.2); the base order follows `entryExecution` — order type,
`repriceSec`, `limit`+timeout, `chase`+timeout and the `maxChasePerc` cap
(§4.3). Multi-target take profits keep resting with no timeout (expiring one
target must not close the others).

§6.3 **Phase 3a** (built): `split` for signal-driven and stop-loss closes on
DCA bots — take profit by indicator / webhook, every stop loss. The close
quantity is planned into slices (rounded to the exchange step; a slice below
the exchange minimum is merged into the previous one). Every slice but the last
is a reduce-funds order (market, or a chasing limit with the split's re-price,
cap and timeout); the last is the deal's ordinary close, so the deal's result is
booked once. While a deal is closed in slices nothing new rests on it and its
safety orders are cancelled. `iceberg`: the next slice `sliceIntervalSec` after
the previous fills; `twap`: one per interval, an unfilled rest rolls into the
next. Floor: `pause` re-checks every 5 s, `market` executes the rest at once.
A repeat of the same trigger is ignored; a manual, bot or API close (or any
forced market close) interrupts the split and closes the rest. A restart drops
the split; the deal resumes as an ordinary open deal (its trigger can fire again
for what is left).

§6.3.1 **Phase 3b** (built): a split take profit at a known price is watched
like a market take profit — nothing rests in the order book beforehand — and
the split starts when price reaches the level, each `limit` slice placed at the
take-profit price (`timeoutSec > 0` executes an unfilled slice at market).
Resting the first slice in advance was rejected: a partial take-profit order
next to the full position reads as missing take-profit coverage, and the
coverage repair would place a full-size one beside it (a double sell).

§6.3.2 **Not built, and not offered** (dashboard and engine both narrow to
what executes): split for DCA orders (the ladder counts one order per level); split on combo bots (no partial-close primitive) — combo take profit
and stop loss offer market and chase; DCA-order `limit` timeouts; indicator-DCA
`limit` / `chase` (the engine always sends indicator DCA orders at market);
split and resting timeouts for multi-target take profits.

§6.5 **Base order split** (built): on the base order's first placement the
deal's base quantity is planned into slices and the base order is sent as
slice 1 (market, or limit with the split's re-price and timeout through the
base-order machinery); re-placements reuse the plan. When the base order fills
(`startDeal`), the remaining slices follow as add-funds orders — `iceberg` one
at a time `sliceIntervalSec` apart, `twap` on a timer rolling any unfilled rest
forward — each market or chasing; the floor works against a rising price for a
long entry. Take profit and the ladder are placed from the first fill and
resized by each add-funds fill, as for any add-funds. Only a plain DCA bot
entry splits: not combo, terminal deals, risk/reward sizing, compound reduce,
a deal carrying a fixed size, short spot base funding or single-position mode
(the base size is owned by those mechanisms) — those send one base order. A
restart drops the plan; the deal keeps what it bought.

§6.4 Public v2 REST (phase 1): GET already returns the stored fields, so
create / backtest-validate / import accept them (validated) instead of failing
a GET→POST round trip with "Unexpected field"; grid bots still reject them.
Webhook payloads carry no execution fields — a webhook close uses the bot's
stage execution (take profit or stop loss), like an indicator close.

## §7 Open questions

§7.1 Should a `chase` reprice be skipped when the best price has not moved (as
the base-order reposition already does, spec 103)? Phase 1: yes, reuse that
rule where the code already has it; no new skip logic.

§7.2 Backtests: execution modes are not simulated; backtests keep treating
`limit`/`chase`/`split` as fills at the trigger price. To revisit after phase 3.
