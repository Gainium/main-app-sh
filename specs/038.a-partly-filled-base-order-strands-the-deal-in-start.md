# 038 — A partly filled base order strands the deal in `start`

Bug spec. The behaviour already exists and is wrong.

## §1 Definition

A DCA deal's base order opens the deal. `startDeal` is reached only from
`processFilledOrder`, i.e. only for a base order the engine sees as `FILLED`.
Until then the deal sits in `start`: `avgPrice`, `initialPrice` and `lastPrice`
are `0`, and `cost` / `size` / `usage` are unset.

### §1.1 Expected

When the entry timers have run out and the base order has executed *some* of
its quantity, the deal must stop waiting. The quantity the venue executed is a
real position the account is holding, so the deal must be opened on it — the
resting remainder cancelled, and average price, cost, usage, take-profit and
stop-loss derived from what actually filled.

### §1.2 Actual

`checkBaseOrder` treats `PARTIALLY_FILLED` as "nothing to do" in **both** of its
branches:

- the `id` branch (the limit-reposition timer) at `dcaHelper.ts:8156`, and
- the `dealId` branch (the enter-market timer — the last check any deal gets)
  at `dcaHelper.ts:8218`,

both of which act only when the order is neither `FILLED` nor
`PARTIALLY_FILLED`. The `dealId` branch additionally clears the deal's
reposition timer on the way in (`dcaHelper.ts:8196`) and never re-arms it.

So on the enter-market timer's expiry the engine cancels the only remaining
check and returns. Nothing schedules another one. The deal stays in `start`
permanently, holding an untracked position, occupying one of the bot's active
deal slots, with no take-profit and no stop-loss. The dashboard renders it with
cost `0`, average price `0` and a price that never resolves, and its actions
menu is disabled because the deal is not `open`.

### §1.3 Not covered by any reaper

There is no periodic sweep for deals left in `start`. `restoreWork` is the only
recovery path, it runs once per bot start, and it routes through the same
`id` branch — so it does not recover this shape either.

## §2 Evidence

Production, a `binanceUsdm` LONG DCA deal, 2026-09-10 (times UTC):

```
13:10:12.996  Deal <id> created
13:10:12.998  base order #1 placed, LIMIT 1461 @ 0.1033400
13:10:23.506  base order #1 CANCELED  (reposition timer, 10 s)
13:10:23.508  base order #2 placed, LIMIT 1461 @ 0.10339
13:10:23.780  base order #2 -> PARTIALLY_FILLED, executedQty 109 of 1461
13:10:48.258  Deal <id> enter market price          <- enter-market timer, 35 s
13:10:48.258  Deal <id> clear limit timer
13:10:48.258  Deal <id> found base order with status PARTIALLY_FILLED
              (and nothing further, ever)
```

The deal document, read live 2 h 41 m later: `status: "start"`, `avgPrice: 0`,
`displayAvg: 0`, `initialPrice: 0`, `lastPrice: 0`, `cost: null`, `size: null`,
`levels.complete: 0`, `updateTime` still equal to `createTime`. The order row is
still `PARTIALLY_FILLED`, `executedQty "109"`, `origQty "1461"`, last touched
at 13:10:23.780. The worker process restarted in between and did not recover it.

A second, unrelated account holds the same shape on `binance` spot: a `dealStart`
row `PARTIALLY_FILLED` at 898 of 1175, deal in `start`, untouched for 9.9 h.

Counted across live DCA deals stuck in `start` for more than an hour, this
shape — a deal whose `dealStart` row is `PARTIALLY_FILLED` — accounts for two
deals on two different accounts. (The larger populations in that set are a
different shape: 145 with no order rows at all, 50 whose base order is
`CANCELED`. Neither is this spec.)

The engine's default timers, both confirmed against the timings above:
`orderLimitRepositionTimeout = 10000`, `enterMarketTimeout = 35000`.

## §3 Assumption (hypothesis)

The root cause is that the two `status !== 'FILLED' && status !== 'PARTIALLY_FILLED'`
conditions leave `PARTIALLY_FILLED` with no handler at all, and the `dealId`
branch — the deal's last scheduled check — returns having cleared the only other
timer. It is not a missing reaper: the engine reaches the deal at exactly the
right moment, looks at it, logs its status and does nothing.

## §4 Required behaviour

### §4.1 The decision

A partly filled base order is settled — remainder cancelled, deal opened on the
executed quantity — when **no further check is scheduled for the deal**. Three
inputs decide it:

- the order row's status is `PARTIALLY_FILLED`;
- the deal is still in `start` (an already-open or terminal deal must never be
  re-opened);
- nothing else will look at this order again.

### §4.2 Where "nothing else will look at it again" is true

- The **enter-market check** (`dealId` branch). It is the last check by
  construction: it has just cleared the reposition timer, and it is itself the
  timer that fired. Always terminal.
- The **restore path**, after a bot start. The process holds no timer state for
  the deal at all, so no callback exists to fire.

### §4.3 Where it is NOT true — behaviour must not change

- The **reposition timer**, mid-flight. The process still holds timer state for
  the deal, which means the enter-market check is coming. The partial fill is
  left alone to keep filling, exactly as today.

### §4.4 Settling

Settling reuses the chain the engine already uses whenever a cancel races a
fill: `cancelOrderOnExchange` (which, for a non-take-profit row, promotes a
cancelled-with-fills order to `FILLED` at its executed quantity) →
`handleUnknownOrder` → `processFilledOrder` → `startDeal`. `startDeal` sizes the
deal from `executedQty`, so the deal opens on what filled and not on what was
requested. No new sizing, averaging or fee code is introduced.

A settle that the venue refuses leaves the deal in `start` and logs a warning.
It is retried on the next bot start by §4.2's restore path.

### §4.5 Venue exemption

`hyperliquid` keeps its existing exemption: both branches return early for a
hyperliquid base order carrying any fill, before this decision is reached.

## §5 Out of scope

- A bot configured with `enterMarketTimeout === 0` arms no enter-market check,
  so its reposition timer is its last check — but §4.3 keeps that path
  unchanged, so such a deal is recovered on the next bot start rather than
  immediately. No occurrence of that configuration was measured; narrowing
  §4.3 for it would change repositioning behaviour for every bot on unmeasured
  evidence.
- Topping the entry back up to the configured base order size with a second,
  market order. That moves money on a path with its own failure modes (a
  remainder below the venue minimum among them) and is a separate change.
- The two other `start`-stranded populations named in §2.
