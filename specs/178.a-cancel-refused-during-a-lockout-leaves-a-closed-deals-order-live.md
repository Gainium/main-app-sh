# 178 — A cancel refused during a lockout leaves a closed deal's order live

Bug spec. Related: `134` (teardown cancel refused for rate), `045` in the
private parent repo (venue order probe that found it), `082` (batched
teardown cancels).

## §1 Definition

### §1.1 Expected

When a deal closes, every resting order it meant to cancel ends up cancelled
on the venue — or, if the venue no longer has it, recorded as the venue holds
it. A refusal that only means "not now" (a rate limit, a temporary lockout of
the API key) delays the cancel; it does not abandon it.

### §1.2 Actual

`cancelOrderOnExchange` reports any refusal that is not "order not found" or
"cancel pending" through `handleErrors` and returns. The only re-send is the
spec `134` ladder, which runs only while the bot is stopping and only for
three rate-limit phrasings — not for `EGeneral:Temporary lockout`, which is
what the exchange balancer answers for a Kraken key it is holding off
(`… held this key off for another 405s …`). The deal then closes; nothing
asks for the order again, and it stays `NEW` locally and live on the venue
with no deal managing it.

## §2 Evidence

Production, Kraken spot ETHEUR DCA deal (identifiers withheld — this file is
public):

- `01:43:34.4Z` take-profit FILLED; the close cancels the deal's two resting
  safety orders.
- Both cancels, 11 ms apart, are refused:
  `EGeneral:Temporary lockout (balancer held this key off for another 405s;
  requests during a Kraken lockout extend it) Method limitOrders() Step Send
  cancel request D-RO-…`.
- The deal closes. No further cancel request for either order is logged.
- 80 minutes later both rows are still `NEW`, and the venue probe confirms one
  of them open on Kraken.

## §3 Assumption (root cause)

A lockout / rate-limit refusal is transient, but `cancelOrderOnExchange` has
no second attempt for it outside `stop()`. Re-sending the same cancel after
the hold expires gets an answer the existing routing already turns into the
right row (`CANCELED`, or the unknown-order ladder for "not found").

Retrying inline is not an option: a lockout hold is minutes long, and waiting
inside the close would change when the deal closes. The retry is deferred.

## §4 Required behaviour

- §4.1 A cancel refused as transient — a rate limit (`134`'s phrasings) or a
  venue lockout (`isVenueLockout`) — is reported exactly as before AND
  scheduled for a re-send. The deal close is not delayed.
- §4.2 The re-send waits at least the hold the refusal states
  (`for another Ns`), else a back-off step (~30s / 2m / 10m / 30m, jittered).
  At most four deferred re-sends per order; one pending re-send per order.
- §4.3 When it fires, the re-send reads the order's current row (memory, else
  the database). It is sent only if the row is still `NEW` /
  `PARTIALLY_FILLED` and the order's deal is no longer open. An open deal's
  order belongs to the engine's own passes, which already re-issue the cancels
  they still want.
- §4.4 The re-send is the same `cancelOrderOnExchange` call with the same
  arguments, so a success is recorded as for any cancel, "not found" goes to
  the unknown-order ladder, and a further transient refusal schedules the
  next step.
- §4.5 A refusal that is not transient is not re-sent (unchanged).
- §4.6 The spec `134` teardown ladder is unchanged.

## §5 Out of scope

- Re-sends do not survive a worker restart (in-memory timers). The venue
  probe (`045`) still surfaces a leftover.
- Rows already left live by past closes (operator action).
- Grid bots: their orders have no deal, so §4.3 never re-sends for them.
