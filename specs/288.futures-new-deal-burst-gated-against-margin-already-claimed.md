# 288 — A futures DCA bot opening several deals at once gates each against margin the burst already claimed

Bug spec (definition / evidence / assumption). Follow-up to specs `008`
(standing-condition latch), `152` (new-deal balance re-check) and the
stored-balance gate (`checkBalanceGate`).

## §1 Definition

### §1.1 Expected

A futures DCA bot that starts several deals in one burst opens the ones the
account can fund, and refuses the rest at its own balance gate with the usual
quiet "Not enough balance to start new deal" warning (latched per pair,
spec `008`). It sends no base order to the exchange for a deal the account can
no longer fund.

Unchanged: a deal the account can fund opens exactly as before, at the same
size and under the same max-deals limit. Spot bots, COIN-M aside from the
asset they are measured in, the reduce-to-available path and the scaled
(size-multiplier) re-check behave exactly as before.

### §1.2 Actual

`checkBalance` priced every deal of the burst against a balance read taken
before any of the burst's base orders reached the exchange. Each deal saw the
same free figure and passed; the exchange refused the base orders it could not
fund, and the refusal quoted the free figure from before the burst.

## §2 Evidence

Read-only production logs (bot ids synthetic in this public file):

- A Binance USDT-M bot at 10x: the first base order of a burst filled; the next
  two base orders of the same burst, gated in the same millisecond as the
  first, were refused by the venue 1 s and 2 s later. Both refusals quote the
  same free figure, which was the pre-burst one; the real free after the first
  fill was below the second deal's required margin.
- A second bot: about twenty base orders created within ten seconds, one
  refused while quoting a free figure taken before the burst.
- A deal refused 1.4 s after an earlier deal's fill: the margin was not yet
  out of the free figure the gate read, so an ack or a fill is not a safe
  moment to forget a claim.

## §3 Fix

- §3.1 `NewDealMarginClaims` (`src/bot/dca/newDealMarginClaims.ts`, pure): per
  bot, per asset, the margin each deal took at the gate.
- §3.2 The open-new-deal gate (`checkBalanceGate(symbol, true)`) on a futures
  bot, live read only: subtracts what is still claimed from `available`
  before the shortfall test, and on a pass claims `required / leverage` — the
  figure it just compared. The check and the claim run with no `await`
  between them, so deals gating concurrently see each other.
- §3.3 A claim is released when the deal ends before its base order is sent
  (every early return between the gate and `placeBaseOrder`). It is settled
  by the first live read that STARTED after `placeBaseOrder` returned — that
  read either shows the margin used, or (refused base order) still shows it
  free. It is never released on the ack or the fill alone. A claim stuck in
  `gated` for longer than 10 minutes (a deal that died on an unexpected
  error) is dropped.
- §3.4 Not claimed: the reduce-to-available path (it has its own claim), the
  size-multiplier re-check, the single-position add-entry gate, the stored
  read (it can only refuse).

### §3.5 Accepted trade-off

A read that starts after the exchange took the margin but before
`placeBaseOrder` returned counts it twice. The deal it gates is then refused
once and re-gated by the existing 5 s re-check, which settles the claim and
opens it at the same size if the account funds it.

## §4 Assumption

- Claims are per bot and in memory. Other bots on the same account are seen
  only once their orders land in a read — the burst this fixes is one bot's.
- The venue takes the base order's and the resting safety orders' margin when
  the deal opens; `required` already models that. Safety orders that rest
  later are not claimed, so a refusal of a later safety order is outside this
  fix.

## §5 Invariants

None added. The defect leaves no wrong state in the bot's data: the refused
base orders never existed on the exchange and the deal never opened. What a
user saw was a refusal message and, at worst, an error status on the bot.
