# 083 — The refused-close restore is dropped by the close-in-flight guard

Bug spec. Forward fix on top of spec `053` (the refused-close restore), spec
`055` (its deal-lock variant) and spec `074` (its two gates), all of which are
live.

## 1. Definition

### 1.1 Expected

Spec `053` §4.1: when the venue terminally refuses a deal close, the engine puts
a take-profit back on the book, because `closeDealById` cancelled the resting one
before it sent the close (`cancelAllOrder(0, dealId, true)`). Without that the
deal is left `open`, holding its whole position, with **nothing on the book and
nothing that can ever fill** to put one back.

So a restore that passes spec `074`'s reason gate and repeat gate must actually
reach `sendOrderToExchange`, and `restoreCloseAfterRefusal` must answer truthfully
whether the deal has a close on the book now.

### 1.2 Actual

The restore builds the take-profit, logs that it is restoring it, hands it to
`placeOrdersHoldingDealLock` — and that method returns at its close-in-flight
guard without sending anything:

```
dcaHelper.ts:15067  if (deal?.closeBySl)                     { …Skip place orders }
dcaHelper.ts:15071  if (deal?.closeBySl || deal?.closeByTp)   { …Skip place orders }
```

`closeBySl` / `closeByTp` mean "a close is in flight **in this worker**"
(dcaHelper.ts:1703). The restore's only call site is the *terminal-refusal* branch
of `closeDealById` (dcaHelper.ts:7360), reached only once the close has
**terminally failed** — the slippage-retry, position-already-closed and spec-050
trailing-retry branches have all returned above it. At that point no close is in
flight, so the guard's premise is false and the flag is stale.

Nothing clears it on that path:

- `triggerStopLoss` (dcaHelper.ts:19376) sets `d.closeBySl = closeBySl` before
  calling `closeDealById`, and `checkDealsStopLoss` passes `true` for every arm
  except multi-SL (dcaHelper.ts:20714) — **including the trailing arm**;
- the indicator-unpnl close (dcaHelper.ts:20933) sets it directly;
- `checkTPLevel`'s single-target arm (dcaHelper.ts:21630) sets `closeByTp` before
  its market close;
- the terminal-refusal branch itself never clears either flag.

So `restoreCloseAfterRefusal` reports `restoring take-profit …`, places nothing,
finds no resting order, returns `false`, and spec `074` records a failed restore
and raises the uncovered-position warning. The deal is exactly as bare as it was
before spec `053` shipped.

### 1.3 Which limbs are affected

| limb | flag at the restore | restore reached? |
|---|---|---|
| stop loss (`checkDealsStopLoss` → `triggerStopLoss`) | `closeBySl` true | dropped |
| indicator unPnL close | `closeBySl` true | dropped |
| trailing close, refusal **not** retryable (`insufficient balance`) | `closeBySl` true | dropped |
| trailing close, refusal retryable | — | not reached (`!retrying`) |
| trailing close, retries exhausted | cleared by `pauseTrailingAfterFailedClose` | placed |
| TP-level market close, single target | `closeByTp` true | dropped (see §5.2) |
| manual / API close, worker restart | flag never set / reset | placed |

The trailing/non-retryable row is worth naming separately: it looks excluded by
the `!retrying` test at dcaHelper.ts:7360 and is not. `handleTrailingCloseRefusal`
answers `false` for a reason retrying cannot fix and then calls
`clearTrailingRetry`, which **returns before clearing `closeBySl`** when the deal
has no `trailingClose` record yet (dcaHelper.ts:18644) — i.e. on the first
refusal, which is the only one such a deal ever gets. That is the reference case
below.

## 2. Evidence

Production, read-only, `Gainium-DCA-bot` (not `Gainium-main-app` — the DCA bot
workers are their own pm2 app and the main-app `-bot-*.log` files are empty).

**2.1 The reference deal.** Bot `698b09afca48235021e58fa7`, deal
`6a17b3e42540560f39dfeccd` (BTCUSDC), a trailing take-profit (`TTP`). Seven close
attempts between 2026-09-19T21:10:03Z and 2026-09-22T07:04:03Z. Every one is a
`Trailing trigger mode: TTP` → `Сlose deal` → `refused by the exchange with a
reason retrying cannot fix (insufficient balance). Not retrying` → restore, and
every restore is followed **in the same millisecond** by the skip:

```
2026-09-22T07:04:03.584Z  … close refused | deal 6a17b3e42540560f39dfeccd (BTCUSDC) restoring take-profit 0.000272 after insufficient balance
2026-09-22T07:04:03.584Z  … Deal 6a17b3e42540560f39dfeccd closing by SL. Skip place orders
```

7 of 7. The user is then told the position is uncovered
(`botWarning`, 2026-09-20T21:01:39.712Z).

**2.2 The population.** `Skip place orders` appears **1,288** times in the whole
retained archive — 1,002 `closing by SL`, 286 `closing by TP` — across **275
deals** on **125 bots**, all dated 2026-09-15 .. 2026-09-22 (spec `053` shipped
2026-09-17). Sampling two of the highest-volume deals, the skip carries the same
millisecond as a restore line for 69 of 73 and 51 of 53 events — so the skip log
line is, in practice, the restore being dropped.

**2.3 The restore is not dead for everyone.** `restoring take-profit` appears
~1.06M times; the same two sampled deals show 103 restores against 73 skips and
332 against 53. Restores on a deal whose flag is clear (a worker restart resets
it — it is in-memory only) do reach the venue. This defect removes a subset, and
that subset is exactly the automatic SL / indicator / non-retryable-trailing
closes spec `053` was written for.

**2.4 It also explains spec `074` §2's third observation** — "uncovered reports
and restore attempts arrive one for one, i.e. essentially every restore in the
sample left the deal still bare". That was read as the shortfall being real. For
the deals in §2.2 it is not: the restore never asked the venue anything.

## 3. Assumption (hypothesis)

The stale `closeBySl` / `closeByTp` flag at `placeOrdersHoldingDealLock`
dcaHelper.ts:15067/15071 is the **only** thing standing between the restore and
`sendOrderToExchange` on those events. Remove that one obstruction *for this
caller* and the same fixture places the take-profit.

Falsifiable: a harness that drives the real `restoreCloseAfterRefusal` →
`placeOrdersHoldingDealLock` over a fake venue must place nothing while the flag
is set and place the take-profit once it is not, with nothing else changed.

## 4. Solution

### 4.1 Scope the guard to the callers it is about, not to the deal

`placeOrdersHoldingDealLock` takes an explicit opt-out
(`afterTerminalCloseRefusal`) that skips **only** the two close-in-flight guards.
`restoreCloseAfterRefusal` is the one caller that passes it, and it passes it
unconditionally: it is only ever called from the terminal-refusal branch, so the
premise "a close is in flight" is always false there.

Everything else — `placeOrders` and every caller beneath it — keeps the guards
byte-for-byte. `allowToPlaceOrders`, the exchange-info lookup, the TP re-size
lookup, the `isDealForTPLevelCheck` skip and spec `074`'s two gates are all
untouched.

### 4.2 Why not clear the flag instead

Clearing `closeBySl` on the terminal-refusal path is the other candidate and is
**rejected**: the flag is also what holds `checkDealsStopLoss` off this deal
(dcaHelper.ts:20678). The stale level that just fired is still in
`dealsForStopLoss` — the terminal-refusal branch disarms trailing but never
re-runs `setDealForStopLoss` — and `close` there is a bare level test, so a
cleared flag re-triggers the identical close on the **next price tick**, at the
tick cadence of ~2/s, against a venue that just refused it. That is the
`tpCloseBackoff` flood of spec `005`/issue #630 reproduced on the stop-loss side.
Whether the flag *should* be cleared once nothing is in flight is a real question
about `closeBySl`'s lifetime and needs its own repeat gate; it is not this fix.

### 4.3 What must still hold afterwards

- `e6223db` (issue #617) — `checkTPLevel` sets `deal.closeByTp` before the market
  close, and `checkTPLevel`'s own release of it when nothing ended up in flight.
  Untouched: the opt-out is not passed from there.
- `0f482a6` (spec `074` §4.2) — the `uncoveredCloseBackoff` repeat gate in
  `restoreOrReportRefusedClose`. Untouched: it sits one frame above the change,
  and it now bounds a restore that can succeed rather than one that never could.
- The guard itself for ordinary callers: a settings save, a ladder rebuild or a
  reconnect pass must still refuse to place into a deal that is genuinely closing.

## 5. Out of scope

- **5.1 `closeBySl`'s lifetime.** §4.2. A deal whose automatic close terminally
  failed keeps `closeBySl` set until the worker restarts, which silently suspends
  its stop-loss check. That is a separate defect with its own reproduction.
- **5.2 The `closeByTp` limb stays inert.** A deal in TP-level-check mode has its
  `dealTP` placement skipped further down `placeOrdersHoldingDealLock`
  (dcaHelper.ts:15251, `isDealForTPLevelCheck`), by design — such a deal is
  closed by a market order at the level and rests no take-profit. The opt-out
  gets those deals past the in-flight guard and they are then correctly skipped
  there instead, so the outcome does not change; only the misleading
  `closing by TP. Skip place orders` line does.
- **5.3 The dead second guard.** `if (deal?.closeBySl || deal?.closeByTp)` at
  dcaHelper.ts:15071 can never see `closeBySl` — the line above already returned.
  Left as is: correcting it is a readability change on a hot path with no
  behaviour attached.
