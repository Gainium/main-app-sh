# 081 — A status change is logged as a manual buy

Bug spec (Definition / Evidence / Assumption).

## §1 Definition

### §1.1 Expected

The bot event log records a **manual buy** entry (`Buy dialog`, rendered
"Manual buy" in the current dashboard) only when the user actually chose a
buy mode and that choice was **applied to the bot**.

Applying a buy mode is one single thing in this platform: the grid start
dialog's mode is forwarded to the grid worker as its swap type, which only
happens when a **grid** bot is being moved to **open**.

### §1.2 Actual

`changeStatus` records the entry whenever the optional `buyType` /
`buyCount` inputs are merely *present* on the request, with no regard for

- the **bot type** — a combo/DCA/hedge request records it even though no
  worker on those paths is ever handed the value, and
- the **target status** — a request that stops (`closed`), errors out, or
  archives the bot records it even though the grid stop branch hard-codes
  the three buy arguments to `undefined`.

So stopping a grid bot writes a "Manual buy — Buy type: all" row for an
action that placed no order and in which the value was discarded.

## §2 Evidence

### §2.1 Production state (read-only, `botevents`, 7 days)

Grid `Buy dialog` rows correlated against the `Status` row the same
`changeStatus` call produced on the same bot:

| correlation | rows |
|---|---|
| within 5 s of a `… -> closed` transition | **128** (24 users, 90 bots) |
| within 5 s of a start (`-> open`) | 85 |
| nearest `Status` row within 60 s is `open status is set` (a first start) | 122 |
| no `Status` row within 60 s | 1 |

Sample (live, `paperContext:false`):

```
bot 6a00665b5468f178ecfff992  2026-09-15T10:50:17.903Z  "Buy type: all"  ->  Status "open -> closed"   Δ = 1 ms
bot 6a96d538a3cbf3477359100b  2026-09-15T10:52:22.698Z  "Buy type: all"  ->  Status "open -> closed"   Δ = 0 ms
bot 6aa1bd6ae4e4d4f0b22ee0c8  2026-09-15T14:24:49.930Z  "Buy type: all"  ->  Status "open -> closed"   Δ = 1 ms
bot 6a00665b5468f178ecfff992  2026-09-15T14:31:36.725Z  "Buy type: all"  ->  Status "error -> closed"  Δ = 1 ms
```

A sub-millisecond gap against the `Status` row is the signature of a single
`changeStatus` call: the status row is written by the worker's `setStatus`
and the buy row at the tail of the same request. The bot placed no order.

So the code path did **run** on stops — this is not a "never ran" shape.

### §2.2 Traced code path

1. `src/bot/index.ts` `changeStatus`, grid **open** branch, posts
   `args: [status, undefined, buyType, buyCount, buyAmount]` — positions
   3/4/5 carry the buy mode.
2. `src/bot/index.ts` `changeStatus`, grid **closed** branch, posts
   `args: [status, cancelPartiallyFilled, undefined, undefined, undefined,
   closeGridType]` — the buy mode is hard-coded away.
3. Every non-grid branch (combo, hedgeCombo, hedgeDca, dca) posts
   `args: [id, status, closeType]` / `[id, status, …]` — no buy mode at all.
4. `src/bot/helper.ts` `setStatus` assigns `this.swapType = buyType ??
   this.swapType` **only** inside its `status === 'open'` arm.
5. The tail of `changeStatus` writes the two `Buy dialog` rows under
   `if (buyCount)` / `if (buyType)` and nothing else.

### §2.3 Why a caller supplies a buy mode on a stop

Both dashboards route every grid status change through one call that carries
the start dialog's currently-selected mode, which defaults to `all`. The
legacy dashboard's grid `sendSetStatus` passes `buyType: selectedIndex` for
`'open'` and `'closed'` alike, and the current dashboard's status-toggle hook
defaults a grid request to `all` when the caller supplied none. The caller
is not the defect — the event is written from an input, not from an action.

## §3 Assumption (hypothesis)

The root cause is the **unguarded pair of writes at the tail of
`changeStatus`**: origin is inferred from the presence of an optional input
field rather than from the branch that consumed it. A request is a manual
buy only on the one branch that forwards the mode — grid, to `open`.

Guarding the two writes with that condition removes every false row while
leaving all 207 genuine grid-start rows intact.

## §4 Scope

### §4.1 In scope

- §4.1.1 The `Buy dialog` write for `buyType`.
- §4.1.2 The `Buy dialog` write for `buyCount`, which has the identical
  shape and the identical defect.

### §4.2 Out of scope

- §4.2.1 What the dashboards send. A caller-side change would leave the
  other caller — and any future one — able to write a false row, and the
  legacy dashboard demonstrates the defect is reachable from more than one.
- §4.2.2 A grid start requested on a bot that is **already** open. The
  worker early-returns without applying the mode, yet the request is
  genuinely a start with a genuinely chosen mode; the orchestrator cannot
  observe the worker's early return, and this leaves no user-visible false
  claim of the kind §1.2 describes.
- §4.2.3 The `Buy dialog` → "Manual buy" label itself.

## §5 Behaviour required

- §5.1 A **grid** request whose target status is **open** and that carries a
  buy mode records the entry, unchanged.
- §5.2 A **grid** request whose target status is anything else — `closed`,
  `error`, `archive`, `range`, `monitoring` — records nothing, whatever the
  buy inputs say.
- §5.3 A **non-grid** request records nothing, whatever the buy inputs and
  whatever the target status.
- §5.4 A request carrying no buy input records nothing, as today.
- §5.5 The decision is one predicate, shared by both writes, so the two can
  never disagree again.
