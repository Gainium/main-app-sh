# 075 — A close refusal that names the position DIRECTION is not read as "position already flat"

Issue #845, spun off from #784. Bug spec.

## 1. Definition

### 1.1 Expected

When a venue refuses a deal's closing order **because there is no position
left to reduce**, `closeDealById` must take its
`isPositionAlreadyClosedReason` branch (`core/src/bot/dcaHelper.ts`): book the
deal closed with no order on the exchange. A reduce-only close can never be
accepted against a flat position, so retrying is not a recovery — it is the
deal being left open forever holding a position the venue says is not there.

That branch already exists and already handles this condition for Hyperliquid,
Binance, Bybit, dYdX and one of OKX's two wordings (§3.1).

### 1.2 Actual

An OKX USD-M (`okxLinear`) futures account refuses the close with:

    Order failed because you don't have any positions in this direction for
    this contract to reduce or close.

`isPositionAlreadyClosedReason` does not match it, so the close falls through
to the generic terminal-refusal branch. The deal stays `open`, uncovered, and
every later close attempt is refused identically — a loop with no exit.

## 2. Evidence

Read-only production evidence, gathered over the triage SSH key.

### 2.1 The venue string is real and is not matched

`logs Gainium-DCA-bot in this direction for this contract` over the live and
archived bot logs returns a six-figure line count, the oldest inside the
retained archive window, the newest minutes before this spec was written. The
refusals repeat against the same deals indefinitely — the signature of a loop
with no terminal branch, not of a transient rejection.

The same string appears in the Combo bot log and in the Grid bot log, at much
lower volume (§4.4 covers what each of those means).

### 2.2 The deals really are stuck open

Two deals sampled from those log lines, read from the production database, are
still `status: 'open'` weeks after their first refusal, one of them more than a
month — one LONG, one SHORT, on two different contracts, both on `okxLinear`,
both still carrying a non-zero `size`. Neither has any resting order.

### 2.3 Why the string misses

`isPositionAlreadyClosedReason` normalises through `normalizeReason`
(`core/src/bot/limitOnlyEntry.ts` — lowercase, strip everything that is not a
letter or digit) and then does a substring test against each list entry. The
OKX entry currently in the list is

    You don't have any positions in this contract   →  youdonthaveanypositionsinthiscontract

and the production string normalises to

    …youdonthaveanypositionsinthisdirectionforthiscontracttoreduceorclose

`inthisdirectionforthis` sits between `positions` and `contract`, so the
existing entry is not a substring of it. The match fails, and nothing else in
the list is close.

### 2.4 The user is told nothing useful

Until spec `074` §4.1 the refusal also drove the refused-close restore, which
re-armed a take-profit that the venue refused for the same reason and then
announced the deal as "could not be funded from this bot's own position" —
naming funding as the cause when funding is not the cause. `074`'s reason gate
(`isErrorNotEnoughBalance`) correctly stops that, which means that once `074`
is live the only remaining trace of this condition is the raw venue warning.
The deal itself looks ordinary. See §4.5.

## 3. Assumption

### 3.1 Root cause

`positionAlreadyClosedReasons` (`core/src/bot/dcaHelper.ts`) is an incomplete
list of venue wordings. OKX emits **two** different refusals for "nothing to
reduce" and the list carries only one of them. This is a data gap in a lookup
table, not a defect in the branch the table feeds: the branch is correct and
does exactly the right thing for every venue wording it does match.

### 3.2 Not a regression

The list and the branch were introduced together (`core/src/bot/dcaHelper.ts`,
2026-08-06, "close the deal when the exchange rejects the closing order as
reduce-only", extended the same day with the dYdX wordings). Before that commit
there was no branch at all, so no earlier behaviour closed these deals and
nothing of ours stopped working. The gap is latent: this wording has never been
covered.

## 4. Scope and the safety argument

Booking a deal closed is terminal — a rollback of the code does not re-open it.
So the question this spec has to answer is not "does the string match" but
**"when this string comes back, is the deal's own position certainly flat?"**

### 4.1 The refusal is scoped to the order's own `positionSide`

`closeDealById` builds its close with

    reduceOnly: !!this.futures
    positionSide: this.hedge ? (this.isLong ? LONG : SHORT) : BOTH

so the "direction" the venue is talking about is **the direction this deal's
own bot asked to reduce**, never the account's other leg. On a hedge account
the LONG leg and the SHORT leg of the same contract are two different deals on
two different bots, each sending its own `positionSide`; a refusal on one says
nothing about, and cannot book closed, the other.

This makes the new entry **more** narrowly scoped than several entries already
in the list — Binance's `ReduceOnly Order is rejected` is not direction-scoped
at all.

### 4.2 The branch closes the refused deal and only the refused deal

The branch's terminal action is `this.closeDeal(this.botId, dealId)` for the
`dealId` whose close was refused. It cannot reach a sibling deal.

### 4.3 Requirement — the branch must be taken for this exact string

A regression test must drive the **real** `closeDealById` with the production
string and assert that it books the deal closed with no order, rather than
falling through to `handleOrderErrors`.

### 4.4 Requirement — the other two bot types

- **Combo**: `ComboBot extends createDCABotHelper(...)` and `comboHelper` calls
  `this.closeDealById`, so combo reaches this predicate through the same code.
  Covered by the same fix.
- **Grid**: the grid helper (`core/src/bot/helper.ts`) has no deals and no
  `closeDealById`; it never reaches this predicate. The grid occurrences of the
  string are grid order rejections on a different surface, they do not leave a
  deal stuck open, and this spec does **not** fix them.

### 4.5 Ordering against `074`

`074` §4.1 silences the (inaccurate) uncovered-close report for this reason.
Landing `074` without this spec leaves the deals stuck AND silent. This change
must therefore ship with or before `074`.

## 5. Out of scope

- Probing the venue's live positions before booking closed. That mechanism
  already exists for the multi-TP surface (`reconcileDealPosition` +
  `reconcileDealAgainstVenue`, spec `005`/`047`), where it is needed precisely
  because there is no venue refusal to read. Here the venue has already
  answered the exact question, scoped to this deal's own `positionSide`, and
  adding a probe would make this one list entry behave unlike the other seven.
- The grid-order surface (§4.4).
- Any other unmatched venue wording. Only the one in §1.2 is evidenced here.
