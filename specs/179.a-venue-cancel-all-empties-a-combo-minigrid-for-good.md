# 179 — A venue cancel-all empties a combo minigrid for good

Combo bot · `core/src/bot/comboHelper.ts` `processCanceledOrder` · minigrid ladder

## 1. Definition

### 1.1 Expected

A `dealGrid` order that had been resting on the book and is then cancelled on
the venue (the venue's own cancel-all, or the user cancelling it on the
exchange) is a level the ladder still wants. It stays in
`minigrid.currentOrders`, and the bot places it again. The minigrid keeps
trading: what its filled levels bought still has sell orders, and its
`grids.{buy,sell}` counts still match the ladder.

An order the venue refuses the moment it is placed (acknowledged and
cancelled in the same instant) is not a level that will rest. Spec 077 prunes
it and does not retry it, and that does not change.

### 1.2 Actual

`processCanceledOrder` prunes every venue `CANCELED`/`EXPIRED` grid order that
the bot did not cancel itself (spec 077, narrowed by spec 130 for the bot's own
cancels). After a venue cancel-all, every level of every minigrid leaves its
ladder. The minigrid is left `active` with `grids` 0/0 and no orders. It still
holds what its levels bought, and nothing will ever sell it back. A minigrid
created with `lockClose` (one of the deal's pre-built active minigrids) cannot
reach its close path either, because that path only runs on one of its own
fills, so it holds its active slot for the rest of the deal.

## 2. Evidence

Production, futures combo bot, one open deal with two active minigrids. Bot log
(`Gainium-Combo-bot-out`):

- `13:32:13.141Z` the minigrid's last fill (a SELL), then `13:32:13.772Z` a
  grid BUY `NEW` at 83262.4 (venue time `…733642`).
- From then until `21:40:18Z`, nothing happened apart from price-stream
  messages.
- `21:40:18.536Z`–`.766Z`: 17 `Processing msg … CANCELED` lines for every resting
  grid (`CMB-GR-…`) and safety (`CMB-RO-…`) order of the deal, all with venue
  time `…18410`–`…18412`. That BUY was among them, and it had rested for 8 hours.

The minigrid document then read `status: active`, `grids: {buy: 0, sell: 0}`,
`lockClose: true`, and it stayed that way (sentinel invariant
`combo.minigrid-ladder-empty-on-open-deal`). The safety orders, which
`processCanceledOrder` does not prune, were placed again at the next worker
restart by `checkOrders` → `getDiffForCheckOrders`. The grid levels were not,
because they were no longer on any ladder.

Spec 077's production case, for contrast: a Kraken grid BUY reported `NEW` and
`CANCELED` with the same venue time (`…332404`), before the placement answer
even arrived. It never rested.

## 3. Assumption (hypothesis)

`processCanceledOrder` cannot tell a level that rested from an order that was
refused, so it prunes both. The order already carries what separates them:
`transactTime` (placement) and `updateTime` (the cancel report).

## 4. The fix, and what it must not break

### 4.1 Rested vs refused

An order whose cancel report is at least `GRID_LEVEL_REST_MS` (60 s) after its
`transactTime` had rested (`combo/gridCancelRested.ts`). Anything else
(including a missing timestamp) is treated as refused, which is the behaviour
before this spec.

### 4.2 A rested level is kept and placed again

It is not pruned: `currentOrders`, `grids` and `deal.assets` are left as they
are. If the level is still on the minigrid's ladder, and the deal is `open` and
the minigrid not closed, the level is sent again through `placeOrders` under a
fresh client order id. This is the same thing `checkOrders` does with a
cancelled order on a restart ("Send order again"). The call is not awaited, so
the order queue is not held while it is placed.

### 4.3 Unchanged

- A refused order (§4.1) is pruned exactly as in spec 077 and not retried.
- The bot's own cancels (spec 130) and a level that another live order still
  rests on (spec 077 §4.2) return before any of this.
- Non-grid orders are untouched.

### 4.4 A minigrid already emptied is rebuilt on restart

§4.2 stops new minigrids from being emptied. It does not repair one emptied
before it shipped, and that minigrid has no order left whose fill would rebuild
its ladder. Minigrid ladders are not stored. A load from the database
regenerates each open minigrid's ladder from its own `lastPrice`/`lastSide`
(`prepareMinigrids`). A service restart instead takes the in-memory copy from
Redis, and that copy carries the emptied ladder forward on every restart. This
is why the production minigrid stayed 0/0 through later restarts while its
deal's safety orders were placed again.

On a service restart, an `active`/`range` minigrid whose Redis copy has no
ladder at all is rebuilt through `prepareMinigrids`, the same as a database
load. Its `grids`, `currentBalances` and `assets` are rewritten off the rebuilt
ladder, and `checkOrders` places it as it does any missing level. A minigrid
the database load would leave empty (no `lastPrice` yet) stays empty. A
minigrid that still has any ladder is taken from Redis as before.

This is no retry of a refusal (§4.3) that a restart did not already make: a
database load rebuilds every ladder, refused levels included.

The emptied minigrid is not closed. `closeMinigrid` rewrites the deal's filled
levels, and for a base minigrid it closes the deal at market. Rebuilding the
ladder from the minigrid's own last fill gives back the sells for what it holds
instead.
