# 055 — the refused-close restore deadlocks on the deal lock

Bug spec. Issue #797 ("Combo bot + deals not stopping"). Follow-on defect in
the fix for spec `053` (issue #784).

## 1. Definition

### 1.1 Expected

When a deal's close is terminally refused by the venue, `closeDealById` puts a
take-profit back on the book (spec `053` §4.1) **and then returns**. The deal's
lock is released, and every later operation on that deal — another close, a
bot `stop()`, a take-profit cycle — proceeds normally.

Stopping a bot whose open deal cannot be funded must still stop the bot: the
close attempt may fail, but `stop()` returns, `setStatus` writes the
`open -> closed` bot-status event, and the bot document is persisted as
`closed`.

### 1.2 Actual

`restoreCloseAfterRefusal` never returns. `closeDealById` never returns. The
deal's lock is never released, so:

- the take-profit is never actually restored — spec `053`'s fix does nothing;
- every later `closeDealById` / `placeOrders` for that deal blocks forever;
- a bot `stop()` reaching that deal blocks inside `stop()`, so `setStatus`
  writes no status event and no document write ever happens, while the
  dashboard is answered `OK` and the bot stays `open`;
- the four further stop attempts the user makes never even start, because
  `setStatus` is itself serialised on `setStatusBot${botId}`.

Only a bot reload clears it — `start()` → `clearClassProperties()` →
`mutex.clear(this.botId)` drops the whole key namespace for the bot.

## 2. Evidence

### 2.1 Production, bot `6a8f34085a868d2732938f4c` (combo, Coinbase, SOL-EUR)

`Gainium-Combo-bot`, 2026-09-18, all times UTC:

```
06:25:05.197  Deal: <deal> closing by take profit. TP set: 90.806…, TP last : 92.04
06:25:05.197  Сlose deal <deal>                                  ← closeDealById takes the lock
06:25:08…14   coinbase not enough balance, retry - 1..5 …         ← the close is refused
06:25:15.030  close refused | deal <deal> (SOL-EUR) restoring take-profit 51.204 after Not enough balance
              ← last line this bot ever emits; placeOrders is entered and never returns
06:26:43.513  Set status closed, current status open              ← the user's 1st stop
06:26:43.513  Close by closeByMarket                              ← stop() starts
              ← no "Сlose deal" line: stop() is blocked on the deal lock, forever
```

The five further stops (06:27:04, 06:27:43, 06:38:39, 06:41:50, 06:47:57) log
nothing at all — they are queued on `setStatusBot${botId}`, which the first
stop still holds.

The same shape appears twice earlier the same morning (restore at 06:20:21.951
and 06:21:35.882, each followed by silence until a `Reload bot` at 06:20:38 and
06:24:06 respectively released the namespace).

### 2.2 Fleet

Distinct bots that entered the restore path in the ~11h since spec `053`
deployed (2026-09-17 19:46 UTC, deploy 266): **117 DCA + 12 combo = 129**.
Each one deadlocked that deal's close until the bot next reloaded.

### 2.3 The collision in code

Two methods on the same module-level `IdMutex` in `core/src/bot/dcaHelper.ts`
derive the **same** key:

| line | method | key |
|---|---|---|
| 6616 | `closeDealById` | `` `${botId}${dealId ?? 'closeById'}` `` |
| 14613 | `placeOrders` | `` `${botId}${dealId}` `` |

They are the only two of the ~46 `@IdMute` keys in the file that collide.
`IdMutex` is not reentrant and `mutex` is constructed with no `lockTimeout`
(`core/src/utils/mutex.ts`), so a holder that waits on its own key waits
forever.

`restoreCloseAfterRefusal` (line 1087) awaits `placeOrders` and is called only
from inside `closeDealById` (line 7130).

### 2.4 Why the spec `053` tests did not catch it

`core/src/bot/dca/refusedCloseRestore.harness.spec.ts` overrides `placeOrders`
on its `TestBot` subclass. An own-prototype method shadows the decorated one,
so the `@IdMute` wrapper is not in the path and the harness cannot observe the
lock at all.

## 3. Assumption (hypothesis)

The defect is exactly the self-deadlock in §2.3: a call chain holding
`` `${botId}${dealId}` `` awaits a method guarded by the same key.

It is a **regression**, introduced by core commit `6ed7896` ("dcaHelper
.closeDealById cancels the resting take-profit before…", 2026-09-17), the fix
for spec `053` / issue #784. `restoreCloseAfterRefusal` is that commit's own
new code and is the only caller that reaches `placeOrders` from inside the
deal lock — the pattern it was modelled on, `checkTpCoverage`, runs under
`checkOrdersAfterReconnect`, which holds no deal lock.

The fix must satisfy **both** issues: #784's restore has to keep happening,
with the same sizing and the same guards, so simply deleting the call is not
an option.

## 4. Required behaviour

### 4.1 The restore runs to completion inside the deal lock

`restoreCloseAfterRefusal` must place the replacement take-profit and return.
Mutual exclusion is not weakened: the caller already holds
`` `${botId}${dealId}` ``, which is the same exclusion `placeOrders` would
have taken, so the order path is still serialised per deal.

### 4.2 Every other caller of `placeOrders` is unchanged

Callers that do **not** hold the deal lock — `checkTpCoverage`,
`processFilledOrder`, the combo minigrid paths, `onFilled`, and the rest — must
keep acquiring it exactly as before.

### 4.3 A stop reaching a refused close completes

With §4.1 in place, `stop()` returns, `setStatus` writes the `open -> closed`
event, and the bot document is written `closed`, even when the deal's close
was refused for funds and the position is left open.
