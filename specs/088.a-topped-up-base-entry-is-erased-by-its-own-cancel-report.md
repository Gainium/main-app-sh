# 088 — A topped-up base entry is erased from the order map by its own cancel report

Third in the chain that begins at spec `057`. `057` made a cut-short base entry
buy back what the venue never executed; `058` made the merged row reach Mongo;
`060` stopped the remainder being counted twice. All three hold. What none of
them covers is the copy the ENGINE runs on: on Coinbase the venue's own cancel
report lands after the merge and puts the pre-merge row back into the in-memory
order map, where every ledger that recomputes from the map then reads it.

## §1 Definition

### §1.1 Expected

`buyRemainder` merges the remainder it bought back into the `dealStart` row, and
`fillPartiallyFilledOrder` writes that merged row into `this.orders`. From that
moment the merged row is what the deal's own books are made of. The venue's
cancel report for the same order is OLDER than the merge — it describes the part
that filled on the book, before the market top-up — so it must not replace it.

`fillPartiallyFilledOrder` already owns exactly that rule. Its
`partiallyFilledFilledSet` branch is a POST-MUTEX RE-READ: the per-order mutex
serialises the settle's call and the stream's call, and whoever arrives second
is told "this order has already been through the remainder machinery — take the
row from the map, not the snapshot you are holding". `processOrderQueue` writes
back whatever that call returns, so the re-read is what keeps the map merged.

After a settle that topped an entry back up, therefore:

- `this.orders.get(dealStart)` is the merged row, `FILLED`, at the blended
  quantity/quote/price;
- `orderStatusMap` carries it under `FILLED`, so
  `getOrdersByStatusAndDealId({ status: 'FILLED', dealId })` returns it;
- `getAvgPrice` folds the whole entry, and the `levels.complete` recompute in
  `updateDeal`'s `dealRegular` branch counts the base order as one of the deal's
  orders.

### §1.2 Actual

On `coinbase` the re-read is unreachable. The undocumented `coinbase` early
return sits ABOVE it:

```ts
if (!this.allowToProcessBr(...)) return order
if (!settledBaseEntry && this.data?.exchange === ExchangeEnum.coinbase) {
  return order                      // ← the stream's stale snapshot, verbatim
}
if (this.partiallyFilledFilledSet.has(order.clientOrderId)) {
  const processed = this.getOrderFromMap(order.clientOrderId)
  return processed ?? order         // ← the post-mutex re-read, never reached
}
```

so the stream call returns its own pre-merge copy, and `processOrderQueue`
`deleteOrder`s the merged row and `setOrder`s that copy in its place —
`CANCELED`, at what filled on the book. Mongo keeps the merged row (spec `058`
forced that write), so the engine and its own database disagree until the bot
next reloads its order map.

Everything that recomputes from the map then reads a base order that either is
not there or is a fraction of itself:

- `getAvgPrice` filters on `status: 'FILLED'`, so the base entry is dropped
  ENTIRELY and the average becomes the safety orders' own average;
- the `levels.complete` recompute filters on `o.status === 'FILLED'` and counts
  one order where the deal used two;
- `findBaseOrderByDeal` returns the book fill, and only `resolveBaseOrderQty`'s
  position-derived branch (spec `026`) keeps the take-profit QUANTITY right —
  logging `holds more than its order rows account for` every time it rescues it.

The average is the one that costs money: it is what
`createCurrentDealOrders`/`getTPOrder` price the take-profit and the safety
ladder from.

## §2 Evidence

Production, Coinbase spot, DCA deal `6ab30d46…` (`BIO-USDC`), 2026-09-22.

`Gainium-DCA-bot`, fixed-string search over the live and gzipped archives:

The `100.4 on record` lines are the proof: 29 ms after the merge, and again
twelve minutes later, the order map still holds the pre-merge row.

Rows on the deal, read read-only from `orders` — Mongo has the merged row:

| row | status | side | executedQty | price |
|---|---|---|---|---|
| `dealStart` | FILLED | BUY | 3306.5 | 0.0301 |
| `br` | FILLED | BUY | 3206.1 | 0.0301050272751 |
| `dealRegular` | FILLED | BUY | 1107.4 | 0.0298 |

and `dcadeals`:

| field | stored | what the rows say |
|---|---|---|
| `avgPrice` / `settings.avgPrice` | **0.0298** | 0.030025 |
| `levels.complete` | **1** | 2 |
| `cost` | 132.5261700000001 | 132.52617 — correct, because `updateUsage` reads Mongo |

`0.0298` is the `dealRegular` price to the digit — the base entry contributed
nothing at all — while `cost`, computed from the same rows through the database,
is right. That is the reporter's complaint exactly: the P&L does not line up
with the capital the deal used or with the number of orders it shows.

### §2.1 Scale, and why only Coinbase

Over the window since spec `057` shipped (2026-09-18 → 2026-09-23), of the
settled-and-topped-up deals that went on to fill at least one safety order
(40 deals, 11 venues), the fingerprint "stored `avgPrice` IS the entries-minus-
the-base-order average" appears **3 times, all `coinbase`, all one account** —
and nowhere on any other venue. That is the guard: every other venue reaches the
post-mutex re-read, gets the merged row back, and writes it to the map. The
defect is Coinbase-only by construction and the measurement agrees.

## §3 Assumption (root-cause hypothesis)

The defect is the ORDER of two guards in `fillPartiallyFilledOrder`, and nothing
else. The `coinbase` early return is a "do not SEND a remainder order on this
venue" rule; the `partiallyFilledFilledSet` branch is a "do not overwrite a row
the machinery has already merged" rule. They are unrelated, and the first is
written above the second, so on Coinbase it swallows it.

On Coinbase nothing else can populate `partiallyFilledFilledSet`:
`buyRemainder` has exactly one entry point, and on this venue that entry point
is reachable only with `settledBaseEntry === true`. So the set contains settled
base entries and nothing else, and reading the map for one of them cannot reach
any other caller's order.

## §4 Solution

### §4.1

Move the `partiallyFilledFilledSet` re-read ABOVE the `coinbase` early return.

### §4.2 Spec `057` §4.4/§5 are preserved exactly

The guard keeps its meaning for every caller it was written for: an order that
has never been through `buyRemainder` is not in the set, so on Coinbase the
stream-driven path still returns before any remainder can be sent. The re-read
places nothing and sends nothing — it returns a row that is already in the map.

### §4.3 What the stream path then does with it

`processOrderQueue` writes back what it is given, so the merged row goes through
`updateOrderOnDb(row, force)` (`force` true, because the executed quantity grew
— an idempotent rewrite of what spec `058` already persisted), `deleteOrder` +
`setOrder`, and `onFilled` rather than `onCanceled`. Both callbacks are no-ops
for this row and have been on every non-Coinbase venue since 2026-09-18:

- `processFilledOrder` de-duplicates on `processedFilled`, and the settle's own
  `handleUnknownOrder` → `processFilledOrder` has already put this
  `clientOrderId` in it;
- `processCanceledOrder`'s `dealStart` branch is gated on
  `shouldSettlePartialBaseEntry`, which refuses a deal that is no longer in
  `start`.

## §5 Out of scope

- `getAvgPrice` and the `levels.complete` recompute themselves. They are correct
  folds over the order map; the map is what is wrong. Admitting a
  terminal-but-not-`FILLED` `dealStart` row there would fold the PRE-MERGE
  quantity (100.4 of 3306.5) and produce 0.02982 — a second wrong average, not
  the right one.
- Having `topUpSettledBaseEntry` write the merged row into `this.orders` itself.
  It already does, through `fillPartiallyFilledOrder`; the problem is the write
  that lands AFTER it. A second write from the settle loses the same race —
  the stream call is unblocked by the same mutex release.
- The `coinbase` early return itself. Spec `057` §5 left it alone for want of
  evidence and this spec does not supply any.
- `resolveBaseOrderQty` and take-profit sizing. Untouched. The base-order row it
  is handed becomes the merged one, which its one-way rule (spec `026`) already
  accounts for: it raises the contribution to the position and never lowers it
  below the row.
- Repairing the averages already stored on closed deals.
