# 065 — Paginated v2 listings drop rows on a non-unique sort key

## 1. Definition

### 1.1 Expected

A caller who walks a paginated `/api/v2/*` listing from page 1 to
`ceil(meta.count / limit)` receives **every** matching document **exactly
once**. Page N and page N+1 do not overlap and do not leave a hole.

### 1.2 Actual

`GET /api/v2/user/balances` reads its page with
`{ sort: { asset: 1 }, skip: (page - 1) * limit, limit }` — a **single
non-unique key**. One balance row exists per `(userId, exchangeUUID, asset)`
(the upsert key in `core/src/utils/user.ts`), so `asset` is unique *within* a
connection but ties **once per connection holding that asset** on an
account-wide read.

MongoDB gives tied documents no defined relative order, and each page is an
independent query with its own bounded sort. A tie group straddling a page
boundary can therefore be returned twice on one page and never on the next.

The two halves cancel in every signal the caller can see:

- the page is **full**, so a short-page check does not fire;
- `meta.count` is `countDocuments(filter)` — the **matched** count, not the
  delivered count — so the totals agree;
- a client that de-duplicates by `_id` removes the duplicate and is left with
  the hole, silently.

Offset pagination cannot recover a skipped row on a later page, so the row is
simply never delivered.

### 1.3 Scope

Nine paginated reads in `core/src/server/v2/api.ts` sort on a single
non-unique key with `skip`/`limit`:

| Line | Listing | Sort key |
|---|---|---|
| 315 | DCA bots | `created` |
| 412 | Combo bots | `created` |
| 561 | Combo deals | `createTime` |
| 568 | DCA deals | `createTime` |
| 879 | Balances | `asset` |
| 969 | Global variables | `created` |
| 1070 | Grid bots | `created` |
| 1186 | Hedge bots | `created` |
| 1467 | Backtest requests | `created` |

Balances is the worst case — ties are *guaranteed* and N-deep in the number of
connections. The `created` / `createTime` listings tie only when documents
share a timestamp, which bulk creation does produce.

`core/src/db/crud.ts` `readData` forwards `options` to Mongoose `.find()`
unchanged, so there is no tiebreaker anywhere below the call site either.

### 1.4 Out of scope

The GraphQL balance path (`core/src/graphql/handlers/balance.handler.ts`) reads
the same store with `{}` — no `skip`/`limit` — so it never loses a row. That is
why the dashboard and the public API can disagree about the same account. It
needs no change.

## 2. Evidence

Measured on the real handler (`v2API().get.get('/api/v2/user/balances')`)
against a production-shaped fixture: one user, 10,688 non-paper balance rows,
13 connections, every asset tied across all of them, with the two indexes
`balancesSchema` actually declares.

**Before**, account-wide (no `exchangeId`), 107 pages:

```
total 10688 · delivered 10688 · distinct 10554 · duplicated 134 · lost 134
```

Every page came back full and `meta.count` matched throughout. Stable across
runs. An independent measurement against production data on the reporting
account gave 131 duplicated / 131 lost out of the same 10,688.

**Control**, the same fixture read connection-scoped (`exchangeId` set), 9
pages:

```
total 824 · delivered 824 · distinct 824 · duplicated 0 · lost 0
```

`asset` is unique within one connection, so the tie disappears and the walk is
lossless. This is the decisive discriminator: the loss tracks the *uniqueness
of the sort key*, not the endpoint, the data, or the page size.

The query plan for the account-wide read (`explain`):

```
SORT { asset: 1 } (in memory, limitAmount 100)
  FETCH filter { paperContext: { $not: { $eq: true } } }
    IXSCAN userId_1
```

An in-memory bounded sort over a non-unique key, re-run from scratch for every
page — which is exactly where the undefined tie order comes from.

## 3. Assumption

The root cause is the **absence of a unique tiebreaker in the sort**, not the
skip/limit strategy, not a cache, not a sync lag, and not anything specific to
balances. Appending `_id` to each sort makes the sort key a total order, which
makes `skip`/`limit` deterministic and the walk complete.

Corollary, treated as a separate concern in §4: no declared index can serve
`{ asset, _id }` ordering for an account-wide read, so the sort is done in
memory over every row the user owns, once per page.

## 4. Non-goals

- Replacing offset pagination with cursor pagination. That changes the public
  contract (Danger List item 2 — dashboards, gainium-mcp, n8n-nodes-gainium,
  chrome-extension all consume it) and is not needed to make the walk correct.
- Exposing a delivered-row count in `meta` so a client could detect a
  shortfall. Worth considering, but it is a response-shape change and the
  shortfall is what is being removed here.
- Any change to the GraphQL path (§1.4).

## 5. Acceptance

5.1 An account-wide walk of a tied-key balances fixture returns
`distinct === meta.count`, with zero duplicates.

5.2 The walk still delivers full pages — the assertion must not be satisfied by
pages simply becoming short.

5.3 A connection-scoped walk stays lossless (no regression on the path that
already worked).

5.4 The response shape is unchanged: same fields, same `meta` keys, same page
size. Existing consumers see only a different ordering *within* a tie group,
which was previously undefined.
