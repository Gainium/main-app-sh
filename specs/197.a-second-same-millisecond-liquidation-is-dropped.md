# 197 — A second liquidation in the same millisecond is dropped

Bug spec (Definition / Evidence / Assumption).

## §1 Definition

- **§1.1 Expected.** A hedge-mode futures account runs a long bot and a short
  bot on one symbol. When the venue liquidates both positions, each bot is
  handed both liquidation reports; the bot whose side was liquidated closes
  its deals as liquidated. Only that bot tells the user its deals were closed
  by a liquidation.
- **§1.2 Actual.** Both bots processed the first report (the SELL that closed
  the long) and neither ever processed the second (the BUY that closed the
  short). The long bot closed its deal. The short bot kept an open deal, with
  its grid ladder and safety orders, on a position that no longer existed —
  and still reported "Deals on … closed due to position liquidation", because
  that message was emitted whether or not the side matched.

## §2 Evidence (prod, Binance USD-M, hedge long/short combo pair)

- The user stream delivered, 2 ms apart, two `ORDER_TRADE_UPDATE` FILLED
  reports on one symbol: SELL 59 and BUY 15. Every liquidation on the
  account that second (a dozen symbols) carried the same client order id,
  `autoclose-<n>`; only the venue order id differed.
- Both bots logged `Received liquidation order … will be processed in bot`
  twice, `Processing msg … SELL … !LIQUIDATION!` once, and
  `Liquidation order autoclose-…/<SELL order id>` once. Nothing for the BUY.
- The short bot logged the "closed due to position liquidation" warning
  without closing anything.

## §3 Assumption (hypothesis), and what the tests check

- **§3.1** `processOrderQueue` handles `orderQueue[0]` and, once done, calls
  `next()`, which `shift()`s the queue. While the first report is awaited,
  `accountCallback` pushes the second and re-sorts the queue. Both reports
  carry the same venue time, so the DCA `sortQueue` orders two FILLED reports
  of opposite sides by price, highest first: the BUY sorts ahead of the SELL
  being processed. `shift()` then removes the BUY; the SELL is seen again,
  skipped as already processed, and removed. The BUY is never processed.
  Test: both reports through the real `accountCallback` → each bot receives
  both (red on the old code for the long and the short bot).
- **§3.2** Latent, same path: the de-duplication key is
  `clientOrderId + status + cumulative quantity`. Two liquidations of the
  same size on one symbol (a symmetric hedge) share all three and the second
  is skipped as a duplicate. Test: two 15-lot liquidations, opposite sides,
  equal price → both processed (red on the old code).
- **§3.3** A re-delivered copy of one liquidation report is still processed
  once (green before and after).
- **§3.4** `processLiquidationOrder` emits the liquidation message only when
  this bot's side was the one liquidated and its deals were closed (red on
  the old code for the non-matching side).

## §4 Required behaviour

- **§4.1** `next()` removes the report it just processed, wherever the
  re-sort has put it, not the queue's head.
- **§4.2** For liquidation reports only, the de-duplication key also includes
  the venue order id and side. The key of every other report is unchanged.
- **§4.3** The liquidation message is emitted inside the side-match branch.

## §5 Out of scope

- How ordinary (non-liquidation) fills are de-duplicated: their key is
  unchanged (§4.2). §4.1 changes which entry leaves the queue, not what is
  considered a duplicate.
