# 028 — A venue answer of FILLED carrying no fill evidence closes a deal on nothing

Issue #719. Bug spec (existing behaviour is wrong).

## 1. Definition

### 1.1 Expected

A resting order is promoted to `FILLED` only when the venue's answer actually
states a fill. An answer that says `FILLED` while stating no executed quantity,
no executed value, no fill timestamp and no fills is not an answer about a
fill — the order keeps the state we already know and stays under reconcile.

A deal closes on a take-profit only when that take-profit closed something. A
take-profit whose executed quantity cannot be resolved to a finite, positive
number closes nothing, so the deal stays open and keeps its position.

### 1.2 Actual

1. `MainBot.mergeCommonOrderWithOrder` copies the venue's `status` verbatim.
   A payload of `status: FILLED`, no `executedQty`, no `cummulativeQuoteQty`,
   `updateTime: null`, `fills: []` promotes a resting order to a **terminal**
   `FILLED` row, and `dcaHelper.checkOrders` persists it through
   `updateOrderOnDb`. The only narration of that write is `handleDebug`, which
   the bot services do not run at (`bots:dca` has no `LOG_LEVEL=debug`), so the
   promotion leaves no log line at all.
2. The same payload defeats the merge's price derivation. `quote` and `base`
   are both `NaN` (`+undefined`), and the guard is `+quote !== 0 && base !== 0`
   — true for `NaN` — so `price` becomes `round(NaN / NaN)` = `NaN`, which the
   next line collapses to `0`. The row is persisted with `price: '0'` over the
   real limit price. (`origQty`/`origPrice` survive only because
   `updateOrderOnDb` deletes them from the update.)
3. `checkOrders` then feeds the promoted order to `processFilledOrder`, which
   for a `dealTP` calls `dcaHelper.closeDeal`. There
   `orderQty = parseFloat(tpOrder.executedQty)` is `parseFloat(undefined)` =
   `NaN`, so `qty` is `NaN`, `price` is `NaN/NaN`, `deal.size = qty` is `NaN`
   and `currentBalances` is `NaN` on both sides.
4. Mongoose refuses the whole document — `CastError: Cast to Number failed for
   value "NaN" (type number) at path "size"` — and `saveDeal` only **logs** it.
   The order row is already terminal, so what is left is a permanent split
   commit: the order says the deal closed, the deal document says `open`.
5. `closeDeal` goes on to `processDealClose`, whose `cancel` arm runs
   `cancelAllOrder(...)` over the deal. That is what empties the position of
   **every** live order — the reported symptom — and it is the half of the
   close that succeeds, because it is on the venue rather than in the refused
   document.
6. `processDealClose` also calls `deleteDeal(dealId)`, which removes the deal
   from the worker's map and from the Redis mirror the next restart reloads
   from, while Mongo still says `open`. A later close of that deal id therefore
   cannot find it: `Deal <id> not found when close` (ledger finding F219). The
   two attempts on record are ~8h later and under a different worker PID, so
   the divergence survives a restart.

## 3. Assumption (hypothesis)

The root cause is that **`mergeCommonOrderWithOrder` treats a venue payload's
`status` as authoritative independently of whether the payload says anything
about a fill**, and that `parseFloat(undefined)` then travels undetected from
that payload into `closeDeal`'s close quantity.

Corollaries, all falsifiable by the tests in §5:

- 3.1 A `CommonOrder` with `status: 'FILLED'` and no executed quantity, no
  executed value, no `updateTime` and no `fills` promotes a `NEW` local order
  to `FILLED`.
- 3.2 That merge also returns `price: '0'`, because `+quote !== 0` is true for
  `NaN`.
- 3.3 The merged order carries `executedQty: undefined`, so
  `parseFloat(tpOrder.executedQty)` in `closeDeal` is `NaN`.
- 3.4 `closeDeal` sets `deal.size = NaN` and issues the save regardless, i.e.
  it will close a deal on a take-profit that closed nothing.

## 4. The behaviour being defined

### 4.1 Fill evidence

A venue payload **states a fill** when at least one of these is a finite number
greater than zero: `executedQty`, `cummulativeQuoteQty`, `updateTime`, or the
length of `fills`. A payload where all four are absent, null, empty or
non-finite is **fill-evidence-free**.

Deliberately all four, not the brief's three: a venue that reports the executed
value but not the quantity, or a timestamp but not either, is stating a fill and
must keep promoting exactly as today. Only the payload that says nothing at all
is refused.

### 4.2 A fill-evidence-free FILLED is not an answer about a fill

When the venue answers `FILLED` fill-evidence-free and our own copy is not
already `FILLED`, the merge keeps the local `status`, `executedQty`,
`cummulativeQuoteQty` and `updateTime`, and warns once naming the order and the
payload. The order therefore stays resting, stays polled, and the next answer —
which normally carries real numbers — promotes it properly.

Not `quarantine`: that flag means "stop polling", which is the opposite of what
this order needs.

### 4.3 A payload that states no executed quantity never erases ours

Independently of §4.2, `executedQty` / `cummulativeQuoteQty` that the payload
does not state (absent, null, empty, non-numeric) leave the local values
standing. Same principle, and the same reason, as the `observedFeeOf` carry-over
directly below it: `{ ...co }` rebuilds the order from the payload, so anything
the payload is silent about is silently destroyed. A stated `'0'` is a
statement and still wins.

### 4.4 The price derivation is finite-guarded

`quote / base` is only used when both are finite and non-zero. `NaN`, like `0`,
falls back to the local `o.price` instead of collapsing to `0`.

### 4.5 A take-profit that closed nothing does not close a deal

`closeDeal` refuses a `tpOrder` whose resolved close quantity is not a finite
number greater than zero: it reports the refusal at error level naming the
order, clears `pendingClose`, and returns with the deal untouched — still open
in memory and in Mongo, still holding its position, and visible to
`checkTpCoverage` as uncovered so the existing repair path can re-arm it.

This is the invariant, not just a NaN guard: the quantity being zero and the
quantity being NaN are the same statement — this take-profit sold nothing.

Because the refusal returns before `processDealClose`, it also stops the two
irreversible things that ran on the way past: the `cancelAllOrder` sweep that
emptied the deal of live orders (§1.2 step 5), and the `deleteDeal` that made
the worker and Mongo disagree about whether the deal exists at all (step 6,
ledger finding F219). F219 is a consequence of this defect, not a separate one —
it is addressed here at its origin. It is not separately reproduced: the
assertions in §5 stop at "the deal is not closed", which is upstream of both.

## 6. Out of scope (stays open)

- **`saveDeal` re-driving a refused save.** §4.5 removes the producer of the
  refusal on this path, but a refused deal save is still only logged and still
  leaves memory and Mongo disagreeing. Making the save self-healing is a
  fleet-wide change to every deal write and does not belong in this fix.
- **`BOT_TP_COVERAGE_REPAIR` arming.** The detector named all four deals and
  declined because the flag scoped it to one other deal. Arming it fleet-wide
  cancels and re-places live orders across the fleet; that is an operational
  decision, not a bug fix.
- **The four already-stranded deals.** Nothing here repairs existing state.
  They need the repair path (above) or an operator action.
