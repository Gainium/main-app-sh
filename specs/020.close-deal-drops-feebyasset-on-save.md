# 020 — a closed deal's off-pair fee ledger never reaches Mongo

Bug spec.

## 1. Definition

### 1.1 Expected

When a DCA deal's TP fills and `closeDeal` runs, every observed fee
leg — on-pair or off-pair — is folded into `findDeal.deal.feeByAsset`
(`dcaHelper.ts:2359`, spec 014 §2.1/§2.2, gated behind
`DCADealFlags.feeByAsset`), and that ledger is part of what closing
the deal persists, the same way `feePaid`/`commission`/`profit` are.
This is not a new requirement — the combo equivalent
(`comboHelper.ts:2609-2618`) already saves `feeByAsset` alongside
`feePaid` in its own close/settle path.

### 1.2 Actual

`closeDeal`'s TP-fill branch computes `findDeal.deal.feeByAsset`
correctly (confirmed both by code trace and live test: a paper deal
with every fill reporting a third-asset fee, spec 004 in
`paper-trading-sh`, produced two `Order` documents with `feeAsset:
'GNM'` and non-zero `feePaid`, and `getTPOrder`'s TP-sizing correctly
read them). But the `saveDeal` call that follows
(`dcaHelper.ts:2512-2525`) passes an explicit field list —
`commission`, `profit`, `updateTime`, `status`, `lastPrice`,
`currentBalances`, `size`, `tpHistory`, `feePaid`, `feeBalance`, `ac`,
`closeTrigger` — that does not include `feeByAsset`. `saveDeal`'s
second argument is a literal MongoDB `$set` (`dcaHelper.ts:1689`:
`{ $set: { ...deal } }`), so a field absent from it is never written,
regardless of what changed in memory. The closed deal's Mongo document
keeps whatever `feeByAsset` it had before — `[]` for a fresh deal —
even though a real, observed, off-pair fee was paid on every fill.

## 2. Evidence

- **Live reproduction.** A paper deal (`dealId
  6aa002ce2d5c5a058688f785`) run against a symbol configured for
  third-asset fee testing: both the base (`clientOrderId
  D-BO-zKGsDyPG1ntSrafFbwrmmlrF1yQrGM`) and TP
  (`D-TP-lulVmWylmOAG1MhUldxObzAWYGaqrf`) `Order` documents carry
  `feeAsset: 'GNM'` and a non-zero `feePaid` — confirmed by direct
  Mongo read. The deal's own document, read after close, has
  `feeByAsset: []` and `feePaid: {base: 0, quote: 0}` (the latter is
  CORRECT per spec 014 §2.2 — an off-pair fee books 0 to base/quote by
  design; only `feeByAsset` being empty is the defect).
- **Code trace.** `dcaHelper.ts:2359` — `findDeal.deal.feeByAsset =
  accrueFeeLedger(...)`, inside the per-order loop, gated on
  `feeByAssetGated` (`!!findDeal.deal.flags?.includes(DCADealFlags.feeByAsset)`
  — confirmed true for this deal, `flags: ['newMultiTp', 'feeByAsset']`).
  `accrueFeeLedger` (`feeLedger.ts:67-83`) always appends a leg with a
  positive `amount`, regardless of its resolved USD rate — a fictional
  ticker with no resolvable price still produces a `{asset, total,
  totalUsd: 0}` entry, not an empty ledger.
- **The save call.** `dcaHelper.ts:2512-2525`, grepped and read in
  full — `feeByAsset` is not a key in the object passed as `saveDeal`'s
  second argument.
- **Contrast.** `comboHelper.ts:2589-2618` computes the same ledger
  (`accrueFeeLedger`, same function) and its own `saveDeal` call two
  lines later DOES include `feeByAsset: deal.deal.feeByAsset` in the
  `$set` object. The two paths were not kept in lockstep.

## 3. Assumption (hypothesis)

The whole defect is the missing key in the object literal at
`dcaHelper.ts:2512-2525`. Nothing about the computation is wrong —
`accrueFeeLedger`, the gating, and the loop all behave correctly, and
the in-memory `findDeal.deal.feeByAsset` is correct at the moment
`saveDeal` is called; it simply never reaches the `$set`.

## 4. Out of scope

- Whether `feeByAsset` should ALSO be computed (and persisted) on the
  liquidation/SL close branches in `dcaHelper.ts` (the other
  `saveDeal(findDeal, {...})` calls in this file) — this file only
  computes the ledger on the TP-fill path today (`accrueFeeLedger` has
  exactly one call site in `dcaHelper.ts`), so those branches have
  nothing of their own to drop. Extending the ledger to those branches
  is a feature question, not this bug.
- Backfilling deals already closed with an empty `feeByAsset` — no
  backfill proposed; the amounts involved are the fee-testing deals
  from this session plus whatever real third-asset-fee deals exist in
  production, and rewriting historical ledgers is a separate decision.
