# 059 — A cancel response that reports no fill erases the entry it settled

Third shape of the stranding specs `038` and `048` set out to remove. Both of
those close a base order the engine can already SEE is part filled. This one is
about the answer that comes back from cancelling it: on a venue whose cancel
response does not report fills, the settle overwrites the fill it had just read
with zero, and then declares that it could not settle the order.

## §1 Definition

### §1.1 Expected

`settlePartialBaseEntry` cancels the remainder of a part-filled base entry and
opens the deal on whatever the venue executed. An order's executed quantity
never decreases, so the answer to "how much of this entry traded" is the
LARGEST report the engine has: the fill it read off the user stream before the
cancel, or a larger one the cancel response carries.

A cancel that ENDS the order is therefore a completed settle, not a failure:
the deal must open on the quantity already executed, at the price it executed
at, and continue into `topUpSettledBaseEntry` → `reportBaseEntryCutShort` →
`handleUnknownOrder` exactly as it does for a row the venue had already ended
(spec `048` §4.3).

The warn `could not be settled` must be reserved for a settle that genuinely
got **no answer** — the case where the remainder may still be resting on the
book, so opening the deal on a fraction would double-book it.

### §1.2 Actual

`cancelOrderOnExchange` copies every field of the venue's cancel RESPONSE onto
the order row (`core/src/bot/main.ts`, the `Object.keys(order)` loop). Only
`clientOrderId`, `origQty` and `origPrice` are excluded. `executedQty` and
`price` are not.

Kraken **spot** does not echo the order back on a cancel. Its connector
answers with a CommonOrder it synthesises wholesale
(`exchange-connector` `core/src/exchange/exchanges/kraken/index.ts`
`cancelOrderByOrderIdAndSymbol`):

```ts
this.convertOrder({
  orderId, symbol, clientOrderId: '',
  price: '0', origQty: '0', executedQty: '0',
  status: 'CANCELED', type: 'LIMIT', side: 'BUY',
})
```

So the copy loop writes `executedQty: '0'` and `price: '0'` over the real fill.
The promotion guard immediately below it —

```ts
if (+order.executedQty !== 0 && order.status === 'CANCELED') { … 'FILLED' … }
```

— then reads the zero it has just been given and declines to promote, so
`settlePartialBaseEntry` sees `CANCELED`, falls past its `FILLED` branch and
warns. The deal stays in `start`: no average price, no cost, no usage, no take
profit, no stop loss, and one of the bot's open-deal slots consumed until the
worker restarts.

For a LIMIT base entry on such a venue this makes spec `038`'s settle
**inert** — the settle is the only caller that reaches the cancel with a
`PARTIALLY_FILLED` row, and the only path out is the restore path on the next
bot start, which is what the warn's own text admits.

### §1.3 Actual, second order

`promoteEndedBaseEntry` records the ended row as `FILLED` with
`updateOrderOnDb(promoted)` — unforced. The default filter refuses a row that
is already `FILLED` or `CANCELED`, and the row this runs on is by definition
terminal: the venue's own cancel event has already written `CANCELED` to the
`orders` collection (`processOrderQueue` persists every execution report before
it dispatches the callback). The promotion therefore never reaches Mongo. The
deal opens on the in-memory copy and loses its base-order record at the next
reload — the same mechanism spec `058` fixed one call further down the chain.

The deal's `orders` rows, read from production:

```
D-BO-eqFChHZ36uTqr  CANCELED  executedQty 0         origQty 0.09102048   (repositioned away)
D-BO-uLjcsfW1CZHdp  CANCELED  executedQty 0.02      origQty 0.09093394   updateTime 1789814744650
```

0.02 XMR (11.796 USD) is a position the account holds and no deal is tracking.
The deal stayed in `start`; the bot's `maxNumberOfOpenDeals` is 1, so it opened
nothing else for the rest of the day.

The warn's `(CANCELED)` is the tell: a settle that got no answer prints
`no answer from exchange`, and a settle whose cancel carried the fill prints
nothing at all.

Fleet-wide over the log archive, `could not be settled` appears 7 times; 5 are
this `(CANCELED)` mechanism, across 4 bots, 2026-09-13 → 2026-09-19. The other
2 are the no-answer shape, which §1.1 deliberately leaves alone.

## §3 Not a regression

`f84418a` (2026-09-10, spec `038`) introduced `settlePartialBaseEntry` and
covered the shape where the cancel response promotes to `FILLED`. `85f266a`
(2026-09-16, spec `048`) added the shape where the venue had ALREADY ended the
order. `919deb8c` (spec `057`) added the top-up. None of them closes this
third shape, and none may be undone by closing it.

The mechanism underneath — Kraken spot's synthesised cancel response — predates
all three by six months (`9362ec60`, 2026-02-27). Before `f84418a` this deal
stranded as well; what `f84418a` added was a path that only LOOKS like it
covers it.

## §4 Assumption

The settle throws away a fill it already holds because it re-reads it from the
one report that is allowed not to carry it. Reconciling the two reports —
taking the executed quantity, and the price it executed at, from whichever side
actually states one — is enough to route the row through
`promoteEndedBaseEntry` and the existing chain.

### §4.1 The decision

Given the row as the engine held it before the cancel (`observed`) and the row
the cancel came back with (`settled`):

1. no `settled` at all → book nothing. The remainder may still be live; this is
   the no-answer case and keeps its warn.
2. `settled` is not terminal (`CANCELED`/`EXPIRED`) → book nothing. The cancel
   did not end the order.
3. `settled` states a fill (`terminalEntryHoldsAFill`) → book `settled`'s own
   quantity and price. This is the report that came from the venue itself.
4. otherwise, `observed` states a fill that can be dated → book `observed`'s
   quantity and price. The response ended the order without reporting what it
   had traded, so its `executedQty` is an absence of information, not a zero,
   and its `price` is not a fill price either.
5. otherwise → book nothing.

`updateTime` is carried alongside whichever side supplied the quantity, because
that is the date `shouldTopUpSettledBaseEntry` measures the entry window from
and the date `terminalEntryHoldsAFill` requires in order to trust a quantity at
all (spec `048` §4.1).

### §4.2 The booking

A row reconciled by §4.1 goes through `promoteEndedBaseEntry` and then the
unchanged `topUpSettledBaseEntry` → `reportBaseEntryCutShort` →
`handleUnknownOrder` chain — the same three steps the `FILLED` branch already
runs, and reached from one step later for the same reason spec `048` §4.3
gives: the order is already terminal, so there is no remainder to ask about.

### §4.3 The write

`promoteEndedBaseEntry` persists with `force`, for the reason spec `058` §4.3
gives for `topUpSettledBaseEntry`: the row it is promoting is terminal, and the
unforced filter cannot write over a terminal row. Without it the promotion this
spec exists to make is in memory only.
