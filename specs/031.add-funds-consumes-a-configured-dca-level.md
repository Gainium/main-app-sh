# 031 — an add-funds order consumes a configured DCA level

Adding funds to an open DCA deal cancels the deal's next safety order. The
ladder the user configured shrinks by one level per addition, silently, while
the level counter in the UI grows. Add funds is meant to SIDESTEP the ladder,
not spend one of its slots.

Related: spec `017.execute-next-dca-order-controls` builds the opposite
operation — "execute next DCA" deliberately DOES consume a ladder slot — on the
same counter this spec repairs. §5 is about not breaking it.

## 1. Definition

`dcaHelper.createCurrentDealOrders` decides how much of the configured ladder
is still to be placed. It counts the levels already consumed and keeps that
many fewer:

```ts
const filledRegular = this.getOrdersByStatusAndDealId({
  status: ['FILLED', 'PARTIALLY_FILLED'],
  dealId,
}).filter((o) => o.typeOrder === TypeOrderEnum.dealRegular)
left = dcaOrdersCount - filledRegular.length
```

`orders.sort(byPrice).slice(0, left)` then keeps the `left` levels furthest from
entry, so each unit of `filledRegular.length` retires the level NEAREST the
current price. Everything downstream follows from that list: what rests on the
venue, `assets.required`, and which price the DCA-by-market check is armed on.

### 1.1 Expected

`filledRegular.length` is "how many of the bot's `ordersCount` configured
ladder levels this deal has already consumed". A deal with `ordersCount: 5`
whose base order has filled and whose safety orders have not still has five
levels to place, whatever else the user has done to the deal in the meantime.

An add-funds order is not a ladder level. It is a point-in-time top-up the user
asked for outside the configured ladder — the engine already treats it that way
everywhere else it counts:

- `updateDeal`'s add-funds branch GROWS `levels.all` by one rather than
  spending a slot, and records the fill in `deal.funds`, a list kept separately
  from the ladder;
- `getDealDCAByMarketToCheck` computes the consumed ladder position as
  `levels.complete - 1 - (deal.funds?.length || 0)` — the base order and every
  add-funds fill subtracted back out;
- `reduceDealFunds` builds its order as `dealTP`, so a reduction has never
  entered this count at all.

### 1.2 Actual

`addDealFunds` builds its order with `typeOrder: TypeOrderEnum.dealRegular`
(tagged `addFundsId`, client-order-id prefix `D-ROA`). Nothing in the filter
above excludes it, so every filled add-funds order decrements `left` and the
next configured safety order is cancelled off the venue.

The count is recomputed from the order rows on every rebuild, so the loss is
not a one-off: it re-applies for the life of the deal, once per add-funds fill.

### 1.3 What the user sees

`levels.all` grows by one per addition while the real remaining ladder shrinks
by one, so the level counter moves in the opposite direction to the truth
(`1/6` → `2/7` → `3/8` while the levels still to place go 5 → 4 → 3).

## 2. Evidence

Reproduced on the paper stack (paper Binance spot, `useSmartOrders: false` so
every level rests and is countable, `dcaCondition: percentage`,
`dcaByMarket: false`, no SL, `tpPerc: 50` so nothing closes). The measurement is
`assets.required.quote` — the cost of the ladder orders still to be placed —
against `usage.max - usage.current`, the budget headroom for them.

### 2.1 Each addition costs exactly one level, whatever its size

`ordersCount: 5`, `orderSize: 20`, `volumeScale: 1` (BTC/USDT, deal
`6aa2483a27edfec3e726f941`):

| step | `levels` | `assets.required.quote` | headroom |
|---|---|---|---|
| baseline | 1/6 | 100.4733 (5 levels) | 100.4733 |
| add 10 USDT | 2/7 | 80.2704 (4 levels) | 100.4733 |
| add 12 USDT | 3/8 | 60.2714 (3 levels) | 100.4733 |

Two different amounts, the same ~20 USDT lost each time: the level, not the
money. Headroom never moves, so no budget rule is involved — the deal still has
room for the full ladder it is no longer going to place.

### 2.2 The level lost is the NEAREST one

`ordersCount: 4`, `orderSize: 20`, `volumeScale: 2` — levels cost
20 / 40 / 80 / 160, so the remaining total names which one went (ETH/USDT, deal
`6aa24882fd81bdd118c8e91f`):

| step | `assets.required.quote` |
|---|---|
| baseline | 300.0875 (= 20+40+80+160) |
| add 10 USDT | 280.2002 (= 40+80+160) |

Down 19.89, not 159. The order rows of that deal show the mechanism directly:

```
D-BO-kiYnpJZ…   dealStart     FILLED    origQty 0.0081  executedQty 0.0081  @ 2480.02
D-RO-0lHfAjX…   dealRegular   CANCELED  origQty 0.0081  executedQty 0       @ 2455.22   ← level 1, swept
D-RO-6cMlSuB…   dealRegular   NEW       origQty 0.0165                      @ 2430.42
D-RO-Ic97KiP…   dealRegular   NEW       origQty 0.0333                      @ 2405.62
D-RO-itMx8XF…   dealRegular   NEW       origQty 0.0672                      @ 2380.82
D-ROA-sJLvFco…  dealRegular   FILLED    origQty 0.004   executedQty 0.004   @ 2480.02   addFundsId ad1d4f0c-…
```

One `dealRegular` row is FILLED and it is the add-funds order. The nearest
ladder level was cancelled with `executedQty: 0` — it traded nothing, it was
withdrawn — and the three remaining NEW rows price out at
`0.0165·2430.42 + 0.0333·2405.62 + 0.0672·2380.82 = 280.20`, the figure above.

### 2.3 The level is withdrawn from the VENUE, not only from the plan

`assets.required` is derived from `currentOrders`, i.e. the deal's PLAN, so it
alone cannot tell a cancelled order from an orphaned one. If the venue kept the
order after the plan dropped it, this would be worse than an accounting error:
the deal would think it had four levels while five could still fire, and the
same level could buy twice.

It does not. The 2455.22 row carries a venue-assigned `orderId`
(`6aa2488353d64219d0f13768`, not the `-1` placeholder for "never sent") and
went CANCELED **131 ms after** the add-funds fill — same rebuild:

```
D-ROA-sJLvFco…  FILLED    2480.02  updateTime 1789020311810
D-RO-0lHfAjX…   CANCELED  2455.22  updateTime 1789020311941   ← +131 ms
```

The cancel rides the ordinary `placeOrders` / `findDiff` path, which is
venue-agnostic: whatever leaves `currentOrders` is withdrawn. So the defect is
that the ladder SHRINKS, not that a ghost order survives it, and §4 is a change
to one count rather than to the order lifecycle.

The same evidence closes the loop after the fix — a NEW order id appears at the
restored level:

```
D-ROA-drvn83Yi…  FILLED    2474.24  (second addition, post-fix)
D-RO-WMWM7dp…    2455.22   0.0081   ← re-placed, a different orderId
```

## 3. Assumption (root cause, stated as hypothesis)

The single defect is that `createCurrentDealOrders`'s `filledRegular` filter
discriminates on `typeOrder` alone. `typeOrder: dealRegular` is not a
sufficient test for "a configured ladder level": `addDealFunds` shares that
value. The count needs the discriminator the rest of the engine already uses
for exactly this question — `order.addFundsId`, which `main.ts` picks over
`typeOrder` in the quant-rules retry budget for the same stated reason
("ordinary DCA safety orders are also `dealRegular`").

`addFundsId` and not the `D-ROA` client-order-id prefix: the prefix test that
`updateDeal` uses (`clientOrderId.indexOf('ROA') !== -1`) reads a random id
tail, and on OKX `getOrderId` strips the dashes, so an ordinary `D-RO-A…`
safety order becomes `…DROA…` — a false positive roughly one order in sixty.
`addFundsId` is set at construction, persisted in the order schema, carried
through `sendOrderToExchange`'s write-ahead and every reconcile mapping.

## 4. Required behaviour

### 4.1
`createCurrentDealOrders` counts a filled or partially filled `dealRegular`
order as a consumed ladder level only when it carries no `addFundsId` — unless
the order says otherwise explicitly (§6).

### 4.2
Consequently, after any number of add-funds fills, a deal with `ordersCount: N`
and no safety-order fills still has N ladder levels to place, at their original
prices, with `assets.required` unchanged.

### 4.3
A filled SAFETY order still consumes a level, exactly as before — the ladder
retires nearest-first as price moves through it.

### 4.4
`levels.all` keeps growing by one per addition and is not changed by this spec:
that is the intended "this deal has an extra entry outside the ladder" display,
and with §4.2 in force the counter and the ladder finally agree.

### 4.5
No migration. `left` is recomputed from the deal's order rows on every rebuild,
so an open deal whose ladder was truncated by this defect regains its missing
levels at its next rebuild.

## 5. The counter this must NOT break

"Execute next DCA" (spec `017`) is the deliberate opposite: it fills the next
ladder level early and MUST consume its slot. It already avoids `addFundsId`
and keeps the plain `D-RO` prefix precisely so it counts, so §4.1 leaves it
counting.

But it identifies WHICH level to execute as

```ts
const level = deal.deal.levels.complete   // safety-order number, base order is 1
```

and `updateDeal`'s add-funds branch increments `levels.complete` too. That
identity is only true while no add-funds order has ever filled on the deal.

### 5.1 Expected

The level "execute next DCA" fills is the shallowest safety order the deal has
not consumed, whatever add-funds orders it also holds.

### 5.2 Actual

After one add-funds fill on an untouched ladder, `levels.complete` is 2, so it
targets level 2 while level 1 is the next unfilled one. It cancels level 2 off
the venue, market-fills level 2's size, and leaves level 1 resting — a skipped
level and a wrongly sized fill. The guard `level > ladderSize` also refuses one
level early.

Today this is masked: the very defect in §1.2 has already deleted level 1 from
the ladder, so targeting level 2 looks consistent. Fixing §4.1 alone would
un-mask it. It is therefore in scope, and takes the subtraction
`getDealDCAByMarketToCheck` already performs: `levels.complete - funds.length`.

### 5.3
`opts.expectedLevel`, the stale-confirmation guard, compares against that same
corrected number, so the dashboard and the engine keep agreeing on which level
a confirmation was for.

## 6. Whether an addition spends a level is a property of the addition

A follow-up the same community request asks for — "replace the next available
DCA level" — wants the OPPOSITE of §4.2, on purpose: an addition that
deliberately takes the next ladder slot, with the level count reading correctly
and the resulting average shown before confirming. §4 must not make that a
rewrite of the count it is fixing.

So `addFundsId` decides only the DEFAULT. An explicit `consumesLadderLevel` on
the order, and on the `deal.funds` entry its fill appends, overrides it in both
directions:

| order | `consumesLadderLevel` | counted as a ladder level |
|---|---|---|
| safety order | unset | yes |
| add-funds order | unset | no — §4.1, today's behaviour |
| add-funds order | `true` | yes — the opt-in |
| safety order | `false` | no |
| anything not `dealRegular` | either | no — the ladder is built from `dealRegular` rows |

### 6.1
`executeNextDcaLevel` sets NEITHER field, and must keep counting on the default
— that is why it avoids `addFundsId` and keeps the `D-RO` prefix (§5).

### 6.2
Nothing sets the flag today, and it is deliberately absent from the `Order`
type and the mongoose schema: persisting a field no writer produces would be
speculative, and every §2 measurement is of the unflagged behaviour. The opt-in
that introduces it adds it in three places — the order type + schema, the
`deal.funds` entry `updateDeal` appends, and the call that builds the order —
and `isLadderOrder` / `nextLadderLevel` then need no change at all.

## 7. Explicitly out of scope

`addDCAOrderByIndicator` matches signal `index` against `levels.complete ===
index + 1` and has the same add-funds inflation. It is NOT reached by this
change — for `dcaCondition: indicators` the ladder rows are stripped from
`initialOrders` at the top of `createCurrentDealOrders`, so §4.1 alters nothing
there, and its behaviour is identical before and after this spec. Reported
separately rather than fixed here.
