# 270 — A Kraken Futures order written off as unfilled is checked against the venue fills first

Bug spec (Definition / Evidence / Assumption). Test: `src/bot/krakenFuturesWriteOffVenueFills.spec.ts`.
Companion: exchange-connector-sh spec 053 (the lookup itself).

## §1 Definition

`_runUnknownOrderLadder` re-asks the venue about an order it cannot resolve; after `unknownOrderMaxAttempts`
definitive not-founds it writes the order off (`writeOffStatus`), as CANCELED unless the row already
recorded its full size.

**Expected.** An order the venue executed is never booked as CANCELED with nothing executed. An order the
venue really cancelled or rejected still ends CANCELED.

**Actual.** On Kraken Futures an order leaves the venue's events page within hours. A grid sell that filled
while the user stream was down was answered "Order not found in history" on every lookup and written off as
CANCELED/0. The deal ledger (FILLED / CANCELED rows) kept the units it had sold, and the close booked none of
its proceeds or grid profit.

## §2 Evidence (prod, read-only)

2026-10-30, a Kraken Futures LONG combo deal closed by take profit still holding base in its books. Its exit
grid sells are stored CANCELED, executedQty 0, updateTime equal to their placement time; the account fills, by
our client order id, show each one filled in full, and the base left equals their size. Worker log at the
close: `Order not found after 5 lookup(s), order CMB-GR-… status set to CANCELED`, then `Сlose deal …`.

## §3 Assumption (root cause)

- §3.1 Nothing on the write-off path asks what executed; "not found" is taken to mean "nothing happened".
- §3.2 The connector fix (spec 053) answers such an order from the account fills when the newest fills page
  holds it. It cannot see an older page, and a connector not yet deployed answers as before, so the engine
  needs its own check before the write-off.
- §3.3 Kraken does not report the order size on that fills answer, so it reports what executed as FILLED.
  A FILLED answer short of the row's size can only be a part-filled order the venue no longer holds.

## §4 Requirements

- §4.1 On `krakenUsdm`, before the ladder writes an order off, read the account fills (`getAccountFills`),
  paging back until the page reaches the order's placement, at most `writeOffFillPages` (5) pages. Fills
  against the row's client order id covering its size → FILLED, with that size and the fills' quote.
- §4.2 Fills short of the size → CANCELED with what executed (the venue no longer holds the order).
- §4.3 No fills → written off exactly as before (`writeOffStatus`).
- §4.4 Fills unreadable for a reason that may pass → the row is left alone; the next reconcile asks again.
  A permanent refusal (`authenticationError`, key without the query-trades permission) → written off as
  before, so such a key cannot keep a row unresolved forever.
- §4.5 Other venues: unchanged, no extra call.
- §3.3 In the ladder's success path, a `krakenUsdm` FILLED answer short of the row's size is stored as
  CANCELED with what executed (the same row Kraken's events page gives for a part-filled cancel).
  Only the fills-only answer shape qualifies (its own `origQty` equals its `executedQty`); a venue
  FILLED that carries a larger size of its own is stored as the venue said, as before.

## Invariants

`main-app/deals` `deals.kraken-futures-combo-closed-holding-written-off-exits` (observe): a closed Kraken
Futures LONG combo deal whose leftover base is covered by exit grid rows written off CANCELED/0 and never
updated after placement.
