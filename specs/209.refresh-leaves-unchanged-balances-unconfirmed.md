# 209 — A successful balance refresh leaves unchanged balances looking stale

Bug spec. Plan: `plans/209.refresh-leaves-unchanged-balances-unconfirmed.md`.
Test: main-app `tests/balanceUpdatedOnRefresh.ts` (real `updateUserBalance`,
fake venue, local Mongo).

## §1 Definition
- §1.1 Expected: after `updateUserBalance` gets a successful `getBalance()` for
  an exchange connection, every stored balance row of that connection carries
  the fetch time in `updated`. `updated` means "last confirmed by the venue":
  the dashboard stale-balance marker ("Last fetched from …", spec 003 §1.1 /
  main-dash-sh 2.51.4) and the automations balance leaf both read it that way.
- §1.2 Actual: only rows whose `free`/`locked` changed, new assets, and assets
  the venue stopped reporting are written. A holding whose amount did not change
  keeps the time of its last CHANGE, so it stays marked stale after every
  successful "Refresh balance", for as long as the amount does not move.

## §2 Evidence
- `src/utils/user.ts` `updateUserBalance`: the `else if (free !== || locked !==)`
  branch is the only write for an existing row; `MongoCrud.updateData` stamps
  `updated` only on rows it writes.
- Production: on one KuCoin spot connection a user refresh wrote the changed rows
  within the same minute, while dozens of non-zero rows kept `updated` from
  weeks earlier. The connection has no `updateUserBalance … NOTOK` or `failed`
  log line, so the refresh did not fail.
- The test's unchanged row keeps its seeded `updated` before the change.

## §3 Assumption
The skipped write on an unchanged amount is the whole cause; nothing else
re-stamps a quiet row. Streams emit only on change, and the scheduled REST
refresh for streaming venues is the daily snapshot sweep (`holdRefresh.ts`:
"on connect and on the snapshot cron — hours apart").

## §4 Required behaviour
- §4.1 On a successful `getBalance()` (and a readable stored set), one
  `updateMany` on `{ userId, exchangeUUID }` sets `updated` to now after the
  per-asset writes. One write per connection, not per asset.
- §4.2 A NOTOK refresh writes nothing; other connections are untouched.
- §4.3 Amounts (`free`, `locked`) are written exactly as before.

## §5 Not covered
Between REST refreshes, a quiet asset on a streaming venue (no 2–10 min REST
timer) still passes the dashboard's 15-minute threshold, because no path
confirms an unchanged amount in that window. Fixing that needs a liveness
signal for the stream, not a timestamp change here.
