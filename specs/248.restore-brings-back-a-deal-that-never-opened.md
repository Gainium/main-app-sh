# 248 — Restore brings back a deal that never opened

Bug spec.

## §1 Definition

### §1.1 Expected

Restore returns a canceled deal to its bot as a bare open position. It is only
meaningful for a deal that holds a position: one whose entry the exchange
actually filled, at least partly. Restoring a deal that never bought anything
is refused with a message saying so, and the deal stays canceled.

### §1.2 Actual

`Bot.restoreDeal` (and the `restoreDeal` resolver in front of it) checks only
that the deal is `canceled`. A deal retired by spec `241` — its first order was
refused by the venue, so its only order row is `CANCELED` with
`orderId: '-1'` and nothing executed — is canceled too. Restoring it flips it to
`open` with `avgPrice: 0` and `levels.complete: 0`: an open deal with an empty
ledger, holding nothing, that the bot then manages as if it were a position
(P&L, close, dashboard all wrong). The botevent says "restored as a bare
active position" although there is no position.

### §1.3 Not changing

- Restoring a canceled deal whose entry filled, fully or partly.
- Restoring a terminal import, whose entry row is a synthetic `FILLED` row with
  `orderId: '-1'` and the full `executedQty` (the venue was never called, but
  the position is real).
- The restore write itself, the bot reload, the counters.

## §2 Evidence

Production read on 2026-11-21 (read-only; identifiers withheld, this file is
public). One deal: refused entry (`Not enough balance`), retired by spec 241 as
"never opened", restored by the user the next day, now `open` with
`avgPrice 0` / `levels.complete 0` and a single `CANCELED` `'-1'` row with
`executedQty '0'`. Every other restore in production was of a deal with a
`FILLED` row (`executedQty > 0`), all of them terminal imports with
`orderId: '-1'`.

## §3 Assumption

The restore path has no test for "the deal holds a position". The deal's order
rows answer it: `executedFillQty` (spec `029`) already returns 0 for exactly
the never-reached-a-venue shape (`CANCELED` + `'-1'`) while keeping a real
fill — including a `FILLED` `'-1'` terminal import — at its executed quantity.

## §4 Required behaviour

- §4.1 Pure `dealHoldsPosition({ orders, avgPrice, levelsComplete })`: true
  when any order row of the deal has `executedFillQty > 0`. With no order rows
  at all (legacy deals whose rows are gone) it falls back to the deal's own
  ledger: `avgPrice > 0` and `levelsComplete > 0`.
- §4.2 `Bot.restoreDeal` reads the deal's order rows and, when §4.1 is false,
  returns `notok` with `RESTORE_NEVER_OPENED_REASON` before any write: no status
  flip, no `deals.active` increment, no botevent, no worker message.
- §4.3 A canceled deal with a filled entry restores exactly as before.

## Invariants

The defect's wrong state — an open DCA deal with an empty ledger — is already
covered by main-app `specs/invariants/deals.invariants.json`
`deals.open-zero-ledger`, which is what found it. No new invariant.
