# 024 — `closeDeal` books a full-deal-volume loss when the balance ledger is lost

Issue #716 ("Inaccurate trade history, affecting bots statistics").
Upstream cause of the poisoning is spec `023` (#714); this spec is about what
deal-close accounting does once the ledger has already been lost.

## 1. Definition

A DCA deal's `currentBalances` is a running ledger: it starts equal to
`initialBalances` and every filled order moves it
(`dcaHelper.processFilledOrder`, the `!roa` branch):

```
base  += executedQty * (side === buy  ? 1 : -1)
quote += executedQty * price * (side === sell ? 1 : -1)
```

### 1.1 Expected

When the take-profit fills, `closeDeal` books
`profit.total = currentBalances.quote - initialBalances.quote +
(currentBalances.base - initialBalances.base) * lastPrice - commDeal`.
That figure is only meaningful if `currentBalances` still carries the deal's
fills. **A deal whose in-memory ledger has been lost — reset to zero, or
non-finite — must be reconciled from its own filled orders before any profit
is booked**, because `initialBalances` (the deal's allocated funds) is still
intact and is what the loss is measured against.

### 1.2 Actual

`closeDeal` reads `currentBalances` unconditionally. With the ledger at
`{base: 0, quote: 0}` the arithmetic collapses: line 2384 adds the closing
take-profit's `(-qty, +qty*price)` onto zero, and the two `qty*price` terms
cancel out of `total`, leaving

```
profit.total = -initialBalances.quote - commDeal
```

i.e. **a loss exactly equal to the deal's entire allocated volume**, regardless
of what the deal actually did. This is what the reporter saw and described as
"the maximum value of the trade if all orders were filled". It is then written
to the deal, to the bot aggregate `this.data.profit`, and to the user's profit
history via `saveProfitToDb` — none of which are recomputed later.

### 2.3 How the ledger was lost — the Redis mirror

`setDealToRedis` (dcaHelper ~L652) mirrors the in-memory deals with
`JSON.stringify` (`main.ts` `setToRedis`). **`JSON.stringify(NaN)` is `null`**,
and there is no validation on the way out.

Production, deal `6a9fca447794d53dedbab119`, `Gainium-DCA-bot`:

```
13:18:25.588Z [WARN] Big number error [big.js] Invalid number Method createInitialDealOrders
13:18:25.612Z [WARN] Big number error [big.js] Invalid number Method getTPOrder
13:18:25.615Z [WARN] Error saving deal: 6a9fca447794d53dedbab119.
              Reason: CastError: Cast to Number failed for value "NaN" at path "currentBalances.quote"
13:18:25.628Z [WARN] ... at path "assets.required.base"
13:18:25.631Z [WARN] ... at path "usage.currentUsd"
13:18:25.634Z [WARN] ... at path "usage.maxUsd" Method updateData()
   … same CastError still repeating at 13:46:48.121Z …
```

So for ~28 minutes **mongoose refused every write** (the Mongo document kept
its last good values — the DB was never corrupted) while `setDealToRedis`
happily mirrored the same NaN into Redis as `null`.

Then the worker restarted — the pm2 PID changes from `3591690` (13:46:48) to
`3835323` (13:59:26) — and `loadOrders` (dcaHelper L1322-1358) prefers the
**Redis** copy over the DB whenever `serviceRestart && !secondRestart`. Its
only integrity check is `checkAvg`, which validates `avgPrice` and nothing
else, so the null ledger was seeded straight into memory. `null + x === x` in
JS, so the deals looked like `{0, 0}`. Two seconds later all seven closed.

### 2.4 Not the same defect as #714

Spec `023` stops `getTPOrder` from *creating* the NaN. It does not give
`closeDeal` any defence against a ledger that has already been lost, and does
not stop the Redis mirror from laundering a NaN into a `null`.

## 3. Assumption (hypothesis)

**3.1** `closeDeal` fabricates a loss of exactly `initialBalances.quote`
because it books profit from `currentBalances` without ever checking that the
ledger still holds the deal's fills.

**3.2** The ledger is reconstructible from the deal's own orders, which
`closeDeal` already loads as `dealOrders`. The invariant

```
currentBalances = initialBalances + Σ over filled, non-ROA, non-br/rebalance orders
```

was checked against 30 production closed deals of this user: it reproduces the
recorded `currentBalances` to <1e-6 on all **29 healthy** deals, and fails only
on the corrupted one (off by the whole deal: 51093 base / 2159.484224 quote).
Excluding the closing take-profit legs and then re-applying line 2384's delta
reproduces all 29 equally exactly — that is the exact code path §4.1 adds.

**3.3** The `null` ledger reached memory through the Redis restore in
`loadOrders`, whose `checkAvg` guard covers `avgPrice` only.

## 4. Required behaviour

**4.1** Before `closeDeal` mutates `currentBalances`, if the ledger is
unusable — non-finite (`NaN`/`null`/absent) on either side, or `{0, 0}` — and
the deal has filled orders to reconcile from, rebuild it from
`initialBalances` plus those orders, excluding the take-profit legs that the
close itself accounts for. Report it loudly.

**4.2** A healthy deal must be bit-for-bit unaffected: the reconciliation only
runs on a provably lost ledger, and `{0, 0}` with no filled orders is left
alone.

**4.3** ROA (add-funds) fills move `initialBalances` as well as
`currentBalances` (dcaHelper L7424-7439), so the reconstruction must apply only
the received side for them, or it double-counts the added funds.

**4.4** The Redis restore in `loadOrders` must not seed a deal whose balance
ledger is non-finite; such a set falls back to the DB, exactly as `checkAvg`
already does for `avgPrice`.

## 5. Out of scope

**5.1** Repairing the seven already-corrupted deals and backing the
−$3,576.35 out of the bot aggregates and profit history. That is a **write to
the production database** and is not something this session may do.

**5.2** Spec `023` / #714 (the NaN source).
