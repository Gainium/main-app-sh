# 013 — A locally refused order is stranded at `NEW` and shown as open

Bug spec (existing behaviour is wrong). Issue #673. This is the upstream defect
that spec `011.cancel-an-order-that-never-reached-the-venue.md` §5.1 explicitly
left open: 011 fixed how a phantom row is *retired*, this fixes why it exists.

## §1 Definition

An order refused by a LOCAL guard — before any venue was contacted — must leave
no record describing it as open.

### §1.1 Expected

`sendOrderToExchange` persists the order at `count === 0`
(`core/src/bot/main.ts:6870`) as a write-ahead record, so a crash mid-placement
still leaves a trace of an order the venue might be holding. When one of the
three local guards then serves the rejection itself — not-enough-balance,
compliance, or hard-auth — the venue never saw the order and the write-ahead
record has nothing to describe. It must be **taken back**.

### §1.2 Actual

The cleanup path (`:7640`) drops the in-memory copy and then skips the write:

```ts
if (this.orders && this.orders.size > 0) {
  this.deleteOrder(order.clientOrderId)
  if (
    !notEnoughBalanceShortCircuit &&
    !complianceShortCircuit &&
    !authShortCircuit
  ) {
    this.updateOrderOnDb({ ...order, status: 'CANCELED' })
  }
}
```

`deleteOrder` (`:1636`) is memory + Redis + `SharedStream` only — it does not
touch Mongo. So on a short-circuit the row written at `:6870` is never revisited
and keeps the shape `saveOrderToDb` left it in: **`status: 'NEW'`,
`orderId: '-1'`**. The dashboard renders that as an OPEN order, and `loadOrders`
(`:4022`) reloads it into the bot on every restart:

```ts
{ botId: this.botId, status: { $nin: ['CANCELED', 'EXPIRED'] }, … }
```

### §1.3 How the gate got there

Commit `3f7ae42` (2026-08-06) added it, on this premise:

> `updateOrderOnDb` UPSERTS on a clientOrderId that is freshly minted per
> attempt — so every suppressed retry created a brand new document describing an
> order that never was.

That reads the upsert as the row's CREATOR. It is not; `saveOrderToDb` at
`:6870` is, and it runs unconditionally, before every guard. The upsert's filter
(`clientOrderId` + not already `FILLED`/`CANCELED`) matches that very row, so it
only ever RETIRED it. Removing the retire therefore removed no rows at all — it
converted a correctly-written-off `CANCELED` row into a permanently open `NEW`
one. The change made the symptom worse than the disease it targeted.

### §2.3 The reload loop explains the amplification

Total `orders` rows created per day went from ~50k before the rollout to ~200k
after, while the non-stranded remainder grew only organically (42k → 80k). The
stranded class alone went 20k → 130k. §1.2's `loadOrders` filter is the
mechanism: a `CANCELED` row is excluded by `$nin`, a `NEW` one is not, so every
stray is re-adopted by its bot on every restart and re-enters the reconcile and
`SharedStream` paths it was supposed to have left.

## §3 Assumption (hypothesis)

The root cause is that the short-circuit path skips the only statement that ever
revisits the write-ahead row, while nothing else deletes it. Replacing the
skipped `updateOrderOnDb` with an actual **delete** of that row — scoped to the
untouched placeholder shape — removes the stray without touching any order the
venue has acknowledged, and satisfies what `3f7ae42` was actually after (no row
for an order that never was).

## §4 Required behaviour

- **§4.1 No row survives a local refusal.** When
  `notEnoughBalanceShortCircuit || complianceShortCircuit || authShortCircuit`
  served the rejection, the write-ahead row for that `clientOrderId` is removed.
- **§4.2 Still no venue call.** The short-circuits keep answering locally; the
  fix adds no exchange round trip.
- **§4.3 A venue-answered rejection is unchanged.** An order the exchange
  actually refused is still written off as `CANCELED` and its row is KEPT — that
  is the audit trail for an order the venue saw.
- **§4.4 An acknowledged order is untouched.** The delete is filtered on
  `status: 'NEW'` **and** `orderId === noExchangeOrderId`, so a row that the
  placement response, the user stream or a reconcile has given a real exchange id
  or a terminal status matches nothing and survives.
- **§4.5 Reuse, not a new utility.** The removal uses the existing
  `ordersDb.deleteManyData` (`core/src/db/crud.ts:649`) and the existing
  `noExchangeOrderId` constant, behind a `deleteOrderFromDb` method sitting with
  its `saveOrderToDb` / `updateOrderOnDb` siblings — the missing third CRUD verb
  on the same DAO, not a reimplementation of either.
- **§4.6 The accumulated rows are cleared.** A migration retires what has built
  up since the rollout (main-app `src/db/migration/list/v45.ts`).

## §5 Open questions / non-goals

- **§5.1 The write-ahead save is deliberately kept.** Deferring `saveOrderToDb`
  until after the guards would also fix §1.1 and was the brief's alternative, but
  it removes the crash-safety property the early write exists for: a process that
  dies between `openOrder` and its response would leave no trace of an order the
  venue may be holding. Taking the row back on the one path that provably never
  reached a venue is the narrower change.
- **§5.2 The backfill's residual risk is bounded, not zero.** An order that DID
  reach the venue but whose response was lost also keeps the `-1` placeholder.
  §2.2's pre-regression windows bound that population at ~2-3 per month
  platform-wide, and such a row is already unaddressable — it is the phantom
  spec 011 retires, not a live order anyone can act on. The migration is
  additionally floored at the rollout instant and never touches a row younger
  than 24h.
- **§5.3 Why `orderId: '-1'` rows exist on venues addressed by exchange id is
  spec 011's subject**, not this one. 011 stops the wasted cancel round trip;
  013 stops the row being created in the first place. Both are needed.
- **§5.4 Not verified against a live venue.** No exchange credentials on this
  host and production is out of bounds for writes. Verified against the real
  method with a recording transport (§2.4), against the production population and
  its exact regression boundary (§2.1-§2.3), and the migration against a local
  Mongo seeded with all six boundary cases.
