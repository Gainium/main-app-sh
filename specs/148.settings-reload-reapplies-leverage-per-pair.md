# 148 — a settings reload does not re-apply leverage to every pair

Bug spec.

## 1. Definition

### 1.1 Expected
Saving a futures DCA/Combo bot's settings reloads it (`reloadBot` with
`replaceOrders=false`). A user action queued on the bot while that reload runs,
a manual deal close for example, should wait seconds, whatever the size of the
pair list.

- §1.1.1 A keep-orders reload asks the venue to set leverage and margin only
  for symbols this bot instance has not already set to the same
  (leverage, margin type, position side), or whose last attempt failed. A
  symbol the venue's positions response reports at a different leverage or
  margin type is still corrected, exactly as before.
- §1.1.2 A pair added by the save, or a changed leverage, margin type or
  position side, is still applied on that reload.
- §1.1.3 Any load that is not a keep-orders reload (user start, stop/start,
  service restart) behaves exactly as before: it applies every pair and
  rebuilds what has been applied.
- §1.1.4 The leverage and margin values requested for a symbol are the same
  ones as before. This changes only whether the call is repeated.

### 1.2 Actual
`loadData` calls `changeLeverage` and then `changeMargin` for every symbol in
`settings.pair` on every load. It skips a symbol only when the positions
response already holds a matching row. On venues read per symbol, that
response is fetched once, for the first symbol, and reused for the rest, so
every other symbol misses and pays both round trips. The reload runs inside the
bot's per-bot method lock (`methodBot<botId>`). Every other method call on the
bot waits for it, deal closes included.

## 2. Evidence

- Code: `src/bot/main.ts` `loadData`, futures loop. `zeroPosition` is looked up
  in `positionsRequest`, which is assigned once (`positionsRequest ??
  futures_getPositions(symbol)`). Both venue calls run when it is absent, with
  no memory of the previous load.
- Production logs (Bybit linear Combo with several hundred pairs): each reload
  logged `Set leverage 5 for X` then `Set margin CROSSED for X` for every pair,
  about 0.55 s per pair. `Load data start` → `Load data end` took about
  4m40s per reload. Two back-to-back settings saves held the method lock for
  about 10 minutes, with one `[IdMutex] lock timeout (300000ms) expired for
  id="methodBot…"`. Manual closes requested during the second reload ran only
  after `Load data end`. Each close ran about 3–5 minutes after it was
  requested.

## 3. Assumption (hypothesis)
Almost all of the reload is spent in the per-pair venue calls. Remembering
what each symbol was last successfully set to, per bot instance, and skipping
the calls on a keep-orders reload when nothing changed shortens the reload, and
the queue behind it, from minutes to the cost of the remaining reads.
Restricting the skip to keep-orders reloads leaves every other path unchanged.
That includes the re-assertion of leverage on a user start, which corrects
anything changed at the venue.

## 4. Out of scope

- §4.1 Letting a close jump the `methodBot<botId>` queue. A reload clears and
  refills the bot's in-memory deals and orders. A close running inside that
  window would act on a half-loaded bot. Shortening the reload is the safe way
  to shorten the wait.
- §4.2 The first keep-orders reload after a process restart still applies
  every pair once. A service restart skips the futures loop entirely, so the
  bot has no applied state to trust yet.
