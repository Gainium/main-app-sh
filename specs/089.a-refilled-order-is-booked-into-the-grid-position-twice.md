# 089 — A re-delivered fill is booked into the grid position twice

A futures grid bot maintains `data.position` INCREMENTALLY: every filled order
is folded into it once, by `calculatePosition`. Nothing in that fold is keyed on
the fill, so an order delivered to `processFilledOrder` a second time is added a
second time. The close is then sized from the inflated quantity.

`createTransaction`, which runs on the same line of `processFilledOrder`, has
carried a per-fill guard for exactly this reason since it was written — it reads
the transaction ledger by `index: clientOrderId` and returns if the fill is
already there. `calculatePosition` never grew one.

## §1 Definition

### §1.1 Expected

A filled order is folded into `data.position` **once**, no matter how many times
it is delivered. After the fold, `data.position.qty` equals the signed net of the
fills that compose the position — the same number
`calculatePositionForOrders` computes from the order tape, and the same number
the venue holds.

Concretely, for a position standing at a signed net of `-2820` that then receives
six FILLED buys of `564`:

- `data.position` is `LONG 564` — `-2820 + 6 × 564`;
- re-delivering any or all of those six changes nothing;
- the take-profit close is sized `564`.

### §1.2 Actual

`calculatePosition` folds unconditionally:

```ts
private async calculatePosition(order: Order) {
  if (!this.data || !this.futures) {
    return
  }
  const qty = +(order.executedQty ?? '0') || +order.origQty
  const current = await this.calculateAbstractPosition(
    { qty, price: +order.price, side: order.side, symbol: order.symbol },
    this.data.position,          // ← folded into itself again on a re-delivery
  )
  ...
}
```

so each re-delivery adds the fill's whole quantity again. `createTransaction`,
called on the line above, is refused by its ledger guard and books nothing — so
the transaction ledger stays correct while `data.position` drifts away from it.

The fold has at least three re-delivery sources, all of which hand
`processFilledOrder` an order it has already seen:

1. **the cancel/unknown-order race** — `processSellAtStop` and `closeBotByTp`
   call `cancelAllOrder(true)`, which walks an order snapshot taken earlier.
   An order that filled in that gap is still cancelled; the venue answers
   "Order not found"; `_handleUnknownOrder` re-reads it, finds the local record
   already at the venue's status, logs *"already processed while request was in
   progress"* — and **returns it anyway** because it is FILLED
   (`main.ts:5437-5443`). `cancelAllOrder` passes it to `handleUnknownOrder`,
   which calls `processFilledOrder`;
2. **the reconcile sweep** (`reconcile-sweep caught N missed fill(s)`), which
   replays `filledOrders` through `processFilledOrder`;
3. **`checkOrders`**, which does the same for any order it observes as FILLED.

Because the fold is incremental and the position is not re-derived, the error is
permanent for the life of the position: nothing later corrects it.

### §1.3 Why it costs money

The inflated quantity is what the close is sized from — `processSellAtStop`
(`helper.ts:2848`) and the `closeBotByTp` stop-and-sell path
(`helper.ts:4680`) both read `this.data.position.qty` directly. An oversized
reduceOnly close is truncated by venues that clamp, but **rejected** by venues
that do not — and a rejected close leaves the bot believing it closed while the
position stays open.

The same `data.position` also feeds the `valueChanged` TP/SL trigger, so an
inflated position triggers on a P&L the bot does not have. Sizing the close
defensively would not fix that; the fold has to stop double-counting.

### §2.3 The arithmetic closes exactly

| | booked once | booked twice |
|---|---|---|
| `-2820 + n × 564` | `n = 6` → **564** | `n = 12` → **3948** |

`3948` is the `origQty` the close was placed with. `564` is its `executedQty`.
Twelve folds of `564` from `-2820`, `.slice(-10)`-capped, is also exactly the
`positionHistory` that was written: ten breakpoints, all stamped
`2026-09-21T06:57:48.198Z` (the fills' shared `updateTime`), ramping by `+564`
from `-1128` to `3948`.

### §2.4 Scale

Aggregated over prod `orders`, `clientOrderId ^GRID-(TP|SL)`, FILLED,
2026-09-14..09-21, `origQty/executedQty > 1.01`: **3 of 38 live (non-paper)
grid closes** were oversized, up to `1.21×`; 2 on paper, up to `7.0×`.

## §3 Assumption (hypothesis)

The root cause is the **missing per-fill guard on the position fold**, not the
start-time rebuild and not the close-sizing sites.

Two independent facts refute the rebuild (`calculatePositionForOrders`,
`helper.ts:310`) as the cause here:

- it writes no `positionHistory` — only `calculatePosition` does — yet the whole
  ten-entry trail was written in this incident;
- it runs only from `loadOrders`, i.e. only inside `start()`. PID `2799759` ran
  continuously across the window; there is no `Load data start` in it.

Therefore: adding the same idempotency `createTransaction` already has to
`calculatePosition` — keyed on `clientOrderId` — makes every re-delivery a
no-op and leaves `data.position` equal to the signed net of its fills. Sizing
guards at the two close sites are NOT the fix: they would leave the
`valueChanged` trigger reading the same inflated position (§1.3).

## §4 Solution

### §4.1 The guard

`calculatePosition` records each `clientOrderId` it folds and returns early on
one it has already folded. The check sits after the `futures` guard — a spot
grid bot tracks no position and folds nothing.

### §4.2 The guard is seeded by the rebuild

`start()` runs `loadOrders()` — which rebuilds `data.position` wholesale from a
filtered order slice — and then `cancelAllOrder()`, which is re-delivery source
(1). Every order the rebuild summed is therefore recorded as already folded, or
the teardown at the start of every bot run double-books exactly as §2.2 does.

### §4.3 Lifetime

The record is cleared by `clearClassProperties` — the same place `this.orders`
is emptied and then refilled by `loadOrders` — so it stays in lockstep with the
order map it is derived from. It is NOT cleared when the position resets: a fill
already folded into a position must never be folded into a later one either.

Its size is bounded by the same thing that bounds `this.orders`, which already
retains the whole `Order` document for each of these ids; a `Set` of their ids
is strictly smaller than what is retained today.

### §4.4 What is deliberately not changed

- `_handleUnknownOrder`'s return on the already-processed branch
  (`main.ts:5437-5443`). Its callers across `dcaHelper`/`comboHelper` read that
  return as "the venue settled this order, here it is", and the write-off guard
  in `sendOrderToExchange` depends on it. Returning `null` there to stop the
  re-delivery would change a contract shared by every bot type to fix a grid
  position defect.
- The two close-sizing sites. Per §3 they are reading a value that is wrong;
  clamping them hides the trigger half of the defect.
