# 006. McGinley Dynamic indicator — app-sh slice

Feature spec — new behaviour, no existing behaviour is being changed.
Cross-repo companion to `indicators`' `specs/002.mcginley-dynamic-indicator.md`
(published as `@gainium/indicators` — the math + `IndicatorEnum.mg` +
`IndicatorConfig` member `{ type: IndicatorEnum.mg; interval: number }`,
factory-registered there).

## §1 Behaviour

A bot can add **McGinley Dynamic** as an indicator condition (start deal,
DCA, risk/reward, close deal, bot start/stop), the same as any other
single-value indicator (e.g. `ATR`, `ADR`). Concretely:

- The bot-settings API accepts `type: 'MG'` as a valid indicator type,
  reusing the **existing generic fields** — `indicatorLength` (the `mgLength`
  parameter, called `interval` in `@gainium/indicators`' config),
  `indicatorValue` (the static threshold to compare against), and
  `indicatorCondition` (`gt`/`lt`/`cu`/`cd`, the same generic crossing
  semantics every other threshold-style indicator uses).
- No new bot-settings field is introduced — McGinley Dynamic's config shape
  (`{ type, interval }`, no percentile/trend-filter/bespoke params) is a
  strict subset of what every consumer of the generic `indicatorLength`
  field already provides.
- The live bot engine subscribes to McGinley Dynamic candles through the
  existing generic indicator-subscription path (via `@gainium/indicators`'
  factory — this repo instantiates nothing per-indicator, per
  `src/indicators/{service,worker}.ts`).
- The bot's condition-evaluation path (`dcaHelper.ts`'s
  `checkIndicatorConditions`) must read McGinley Dynamic's streamed value
  (a plain number) into the generic `last`/`prev` comparison against
  `indicatorValue`/`indicatorCondition` — the same mechanism `ATR`/`ADR`
  already use. Without this, `last`/`prev` stay at their `0` default and
  the bot's condition would silently never evaluate correctly against the
  real indicator value.
- The public v2 REST API (`/api/v2/*`) and the in-app AI agent must be able
  to create/update a bot referencing `MG` — this is the `server/v2/`
  contract layer.

## §2 What does *not* need new bot-settings surface (and why)

Investigated (blast-radius grep, see plan) whether McGinley needs its own
bespoke fields, mirroring `LongWick`'s `lwThreshold`/`lwMaxDuration`/
`lwValue`/`lwCondition`. It does not:

- `indicators`' `McGinley` config is `{ type; interval }` only (see that
  repo's plan addendum — deliberately renamed from `mgLength` to match the
  generic `interval` convention `atr`/`adr`/`rsi`/etc. already use here).
- This repo's `src/db/schema.ts` `type` field is `{ type: String, enum:
  IndicatorEnum }` — a **direct reference to the TS enum object**, not a
  hand-maintained list, so it auto-accepts `MG` once the enum has the entry.
  Same for `validators/bots/config.ts`'s `type` validator
  (`Object.values(IndicatorEnum)`).
- `indicatorLength`/`indicatorValue`/`indicatorCondition` are already
  generic, always-present, always-validated fields — not per-type.
- `src/server/v2/botDefaults.ts`'s `indicatorConfigDefaults` **is**
  type-checked (`{ [x in IndicatorEnum]: ... }`), so it's the one place a
  new enum member is *impossible* to silently forget — the build breaks
  without an entry. No bespoke fields needed inside that entry beyond the
  generic ones `ATR`'s entry already uses.

## §3 Open questions

- **GraphQL schema (`src/graphql/schema.ts`).** The `IndicatorsEnum` SDL
  enum is a hand-written string list (not derived from the TS
  `IndicatorEnum`), so it needs `MG` added by hand — confirmed by grepping
  every other enum member (`LW`, `SESSION`, ...) appears there literally.
  No new field entries needed in the `indicatorSettings` input/output types
  (per §2, no bespoke fields). Not really "open" — named here because it's
  the one place in this repo that does NOT auto-derive from the shared
  enum, so it's easy to miss.
- **`server/v2/openapi-v2.yaml` / `definitions/generated.ts` /
  `AI_API_GUIDE.md` / `SCHEMAS.md`.** All four are **generated** from
  `types.ts` (via `npm run generate:schemas`, `generate:ai-docs`,
  `generate:definitions` — confirmed by reading the generator scripts'
  `writeFileSync` targets). Resolved: regenerate, don't hand-edit — this
  wasn't obvious from the new-indicator-integration skill's runbook, which
  describes them as things to "add," not regenerate.
- **`src/indicators/test.ts` manual harness.** The new-indicator-integration
  runbook names this file as a step-8 manual test harness. It does not
  exist in this repo (grepped, confirmed absent) — this repo instead has
  real mocha/chai coverage (`src/**/*.spec.ts`). Resolved: follow this
  repo's actual test idiom (gate 2/6), not the runbook's assumption.

## §4 Non-goals

- No `dcaHelper.ts` change to the **config-building** ternary (the block
  that turns `SettingsIndicators` into an `IndicatorConfig` to subscribe
  with) — McGinley's `{ type, interval }` shape already falls through that
  chain's existing generic default branch
  (`{ type, interval: indicatorLength, percentile, ... }` — the extra
  `percentile*` fields are harmless, `@gainium/indicators`' factory only
  reads `config.interval` for `IndicatorEnum.mg`). Verified by reading the
  default branch and the factory's `create.ts` case.
- No refactor of `checkIndicatorConditions` — see plan's JIT-tier decision.
- No change to `@gainium/backtester` wiring (separate repo, explicitly out
  of scope per the user's 3-repo instruction — named as a gap in the
  `indicators` repo's plan already).
