# 202 — the close-after-X auto-stop deadlocks on the deal-close lock

Bug spec. Same family as spec `055` (a call chain waiting on a non-reentrant
`IdMutex` key it already holds).

## 1. Definition

### 1.1 Expected

A DCA (or combo) bot whose bot controller stops it after X deals — closed,
won, lost, consecutive, or a profit target — stops when the limit is met, and
every close and stop of that bot keeps returning. A bot that is stopping
opens no new deal from a webhook signal.

### 1.2 Actual

`checkClosedDeals` runs inside `processDealClose`, which is serialised on the
bot-wide key `` `${botId}processDealClose` `` of a module-level `IdMutex` that
is not reentrant and has no lock timeout. When a limit is met it awaits
`stop(leave)`. `stop` cancels every deal still in `start` through
`closeDealById` → `processDealClose` — the key the outer close holds. So when
the limit is met while the bot holds a start deal:

- the triggering close never returns, and nor does the stop;
- `` `${botId}processDealClose` `` is never released, so every later close of
  ANY deal of the bot (a user stop, a manual close, a TP fill) logs
  `Сlose deal <id>`, flips that deal in memory, and blocks in
  `processDealClose` — `deals.active`, the bot status and the bot document are
  never updated;
- the bot stays `open` with its price/signal paths live, and the worker's
  `methodBot` lock timeout (5 min) only lets the next queued call in to block
  the same way;
- the bot still reads `open`, so its start paths keep opening deals on a bot
  the user is stopping. In production these came from the indicator start
  condition straight into `openNewDeal`. `openDealBySignal` (webhooks) is
  exposed the same way, and it also runs outside the worker's per-bot method
  queue.

Only a worker restart clears it.

Once a close-after-X limit has been met and the bot is started again, EVERY
deal close re-checks the limit, including the cancel of a start deal, so the
trap is armed on any later stop or start-deal cancel while start deals exist.

## 2. Evidence

Production, a multi-pair Binance USD-M DCA bot with a close-after-X limit
already met and many deals in `start`, DCA worker log, 2026-10-25 UTC:

```
05:31:46.967  Reload bot                                  ← a settings save
05:32:02.958  Bot deals counter 39/65 (active/all) does not match the loaded deals, set to 38/65
05:32:03.004  Checking for existing deals
05:32:12.393  <deal A> (…) never started and its TechnicalIndicators trigger has passed. Cancelling the stale deal instead of replaying it
05:32:12.393  Сlose deal <deal A>                         ← closeDealById → processDealClose holds the key
05:32:12.425  Close deal after X trigger, closed: 1, trigger: 1   ← checkClosedDeals, inside it
05:32:12.425  Close by leave                              ← stop(leave)
05:32:12.425  Сlose deal <deal B>                         ← a start deal; its processDealClose waits forever
05:36:46.968  [IdMutex] lock timeout (300000ms) expired for id="methodBot<bot>", force-releasing
05:36:46.968  Сlose deal <deal C>                         ← the next queued call (a user stop), blocks the same way
05:41:46.967  … force-releasing / Сlose deal <deal D>     ← every 5 minutes until the worker restarted the next day
```

No `Close by …` line ever follows a user stop, no deal close completes, and
the bot document stayed `open` with `deals.active` frozen at its last value
while every deal was cancelled in memory.

Reproduced deterministically in
`src/bot/closeAfterXStopDeadlock.spec.ts`, which drives the real
`closeDealById` / `processDealClose` / `checkClosedDeals` / `stop` on a DCA
helper with real deal maps and the real module-level mutexes: before the fix
the three nested-cancel cases do not settle within 3 s and a signal mid-stop
opens a deal.

## 3. Assumption (root cause)

The stop started by `checkClosedDeals` waits on `` `${botId}processDealClose` ``,
which its own call chain holds. Nothing else in the chain is needed to
explain the hang: with no start deal to cancel, the same stop never reaches
`processDealClose` and returns (§4.4 passes before and after).

## 4. Required behaviour

1. Cancelling a start deal while the limit is met and other start deals
   remain returns; every start deal is cancelled and the bot is written
   `closed`.
2. A later stop of the same bot returns.
3. A user stop that cancels several start deals while the limit is met
   returns, and each start deal is closed exactly once.
4. Unchanged: with no start deal left, the auto-stop runs inline exactly as
   before.
5. No deal opens while a `stop` of the bot is running: `openNewDeal`, the
   entry for every start path, refuses and calls its `cbIfNotOpened`, and
   `openDealBySignal` also tells the user the webhook signal was ignored. On a
   bot with no stop running, both open as before.

## 5. Out of scope

- How deals open, size or close on a bot that is not stopping.
- A lock timeout on the deal-level mutex. Force-releasing a deal or close lock
  lets a second close of the same deal run beside the first — double sends on
  the venue — and `IdMute` would then release the next holder's lock when the
  stuck call finally returns. The worker's `methodBot` timeout shows the
  pattern does not unjam a deadlock: each release let the next call in to
  block on the same key.
- `checkOpenedDeals`' close-after-X-opened stop: it is not awaited from inside
  `processDealClose`, so it queues instead of deadlocking.
