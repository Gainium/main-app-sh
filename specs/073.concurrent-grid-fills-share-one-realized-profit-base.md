# 073 — Grid fills delivered together all book their profit from one stale base

## §1 Definition

A grid bot books each completed round trip through `createTransaction()`
(`core/src/bot/helper.ts`), which writes a `transactions` row and advances the
bot's realized profit. The row carries the running total the ledger is read
from — `cummulativeProfitBase` / `cummulativeProfitQuote` /
`cummulativeProfitUsdt` — and the bot document carries the same total in
`profit`.

### §1.1 Expected

- **§1.1.1** Each fill's `cummulativeProfit*` is the previous fill's
  cumulative plus that fill's own net result. Over a bot's life the sequence is
  strictly a running sum, whatever order the venue delivered the fills in.
- **§1.1.2** The largest cumulative a bot ever wrote equals the sum of every
  leg it booked.
- **§1.1.3** A closing leg booked by `processFilledStop()` or
  `processSellAtStop()` stays in the bot's realized profit — a round trip
  booked afterwards adds to it rather than replacing it.

### §1.2 Actual

- **§1.2.1** `processFilledOrder()` calls `this.createTransaction(order)`
  **without awaiting it**, and `createTransaction`'s `@IdMute` key was
  `${botId}transaction${clientOrderId}` — per FILL. Several grid levels filling
  inside one price message therefore ran concurrently, and every one of them
  read the same `this.data.profit.total` across the awaits that precede the
  insert (`getExchangeInfo`, `getUserFee`, `countData`, `generateCurrentGrids`,
  `getUsdRate`). All of them wrote their cumulative from that one base, so N−1
  legs were absent from the running total.
- **§1.2.2** `processFilledStop()` and `processSellAtStop()` persist the close
  leg with `updateData` — an absolute `$set` — but never assign it to
  `this.data.profit`. The next `createTransaction` builds its own absolute
  `$set` from `this.data`, which still holds the pre-close value, so the close
  leg is silently dropped from the document.

## §3 Assumption

The defect is the mutex KEY, not the absence of a mutex: `createTransaction`
is already serialised, but per fill, which is exactly the granularity that does
not help when the contended state is per bot. Keying it on the bot makes the
read-modify-write of `this.data.profit` atomic with respect to every other fill
on that bot, because there is no `await` between the read at the `data` literal
and the assignment to `this.data.profit`.

A test that fires two `createTransaction` calls for one bot concurrently must
therefore produce two rows sharing one base **before** the change and a running
sum **after** it, and must fail for that reason and no other.

## §4 Solution

- **§4.1** `createTransaction`'s `@IdMute` key becomes `${botId}transaction`.
  No call site awaits it, and nothing it awaits takes that key, so it cannot
  deadlock; the per-fill duplicate guard it used to provide is unchanged, since
  serialising a superset of the calls still serialises the same-fill pair, and
  the real duplicate guard is the unique `index` on the collection.
- **§4.2** `processFilledStop()` and `processSellAtStop()` assign
  `this.data.profit = data.profit` before `updateData`, the way
  `profitAfterPositionClosed()` already does.

## §5 Not in scope

The rows already written cannot be repaired by a code change; the bots that
were affected keep the totals they were given. Repairing them is a data
question for the operator, not part of this fix.
