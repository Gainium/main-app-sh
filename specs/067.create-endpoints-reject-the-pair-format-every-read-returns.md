# 067 — The v2 create endpoints reject the pair format every v2 read returns

## §1 Definition

### §1.1 Expected

`GET /api/v2/bots/{grid,dca,combo}` and `POST /api/v2/bots/{grid,dca,combo}`
are documented as a lossless read-modify-create round trip: read a bot with
`fields=extended`, change a value, post the body back, get an equivalent bot.
The `pair` a read returns must therefore be a `pair` the create endpoint
accepts, and it must resolve to **the same instrument** the bot it was read
from trades.

### §1.2 Actual

A read returns `settings.pair` as the **exchange-native symbol** — the value
stored on the bot (`ARBUSDT`, `BTCUSD_PERP`, `BTCUSDT_260925`,
`AAVE-USD_UM_XPERP`). The create endpoints accept only the documented input
format `BASE_QUOTE` (`ARB_USDT`), so posting the body back is answered with

```
400  [["pair","Field pair contains invalid entries: ARBUSDT"]]
```

The round trip therefore cannot succeed for any bot whose stored pair is the
concatenated form — which is essentially all of them.

### §1.3 Also in scope: the same mismatch in the clone endpoint

`POST /api/v2/bots/:botType/:botId/clone`, called without an explicit `pair`,
rebuilds a grid bot's pair as `` `${symbol.baseAsset}_${symbol.quoteAsset}` ``
(`api.ts:3674`). `Bot.createBot` then looks that value up in `pairs` by its
**native `pair`** field, finds nothing, and stores the bot with
`settings.pair = 'ARB_USDT'`, `symbol.baseAsset = ''`, `symbol.quoteAsset = ''`
— the exact shape the comment above that lookup says "fails order validation
(`quoteAsset is required`) and drops grid orders".

## §2 Evidence

### §2.1 The failure, on the real code path (no DB)

`tmp-repro/pairRoundTrip.repro.ts` drives the real read projection
(`parseFieldsParam` → `filterFields` with the real `extended` preset) and the
real create validators (`validateCreateGridBotInput`,
`validateCreateDCABotInput`) over a verbatim production bot document, with
`pairDb` stubbed by the real production `pairs` rows:

```
GET /api/v2/bots/grid?fields=extended -> settings.pair = "ARBUSDT"
POST /api/v2/bots/grid  -> REJECTED [["pair","Field pair contains invalid entries: ARBUSDT"]]
GET /api/v2/bots/dca?fields=extended  -> settings.pair = ["ARBUSDT"]
POST /api/v2/bots/dca   -> REJECTED [["pair","Field pair contains invalid entries: ARBUSDT"]]
POST grid (delivery BTCUSDT_260925) -> REJECTED [["pair","The pair BTCUSDT_260925 is invalid for exchange binanceUsdm"]]
```

Two distinct gates, one cause:

- **the format gate** — `validateCommonSchema` (`schema.ts:206`) rejects any
  entry for which `!p.includes('_')`. Schema validation short-circuits, so the
  DB-backed check never runs. This is what a concatenated symbol hits.
- **the resolution gate** — the DB-backed lookups
  (`logic.ts:176` for DCA/combo, `logic.ts:621` for grid, `Bot.checkPairs`,
  and `api.ts:4339` for `submitBacktestRequest`) resolve a pair only by
  splitting it on `_` into base/quote. A native symbol that *does* contain `_`
  (`BTCUSDT_260925`, `BTCUSD_PERP`) passes the format gate and dies here
  instead — including on `POST /api/v2/backtest/:botType`, where the settings
  read off a bot are refused with `One or more pairs in payload are invalid
  for the exchange`.

### §2.2 How much of production this covers

Read-only count over production, 2026-09-20, replaying both resolution rules
over every non-archived bot's stored `settings.pair`:

| | bots | accepted today | accepted with native-first resolution | unresolvable |
|---|---|---|---|---|
| grid (`bots`) | 727 | **0** | 709 | 18 |
| dca (`dcabots`) | 16650 | **38** (0.2%) | 16275 | 375 |

The "unresolvable" remainder is delisted pairs (Binance BUSD markets); no
resolution rule can help them, and the bots are archived.

### §2.3 Why the rebuild-on-read fix in the brief is not available

The fix brief proposes normalising `settings.pair` on read to
`` `${symbol.baseAsset}_${symbol.quoteAsset}` ``. Three measurements refute it:

1. **It cannot be computed for DCA or combo bots at all.** Their `symbol` is
   `Map<string, Symbols>` keyed by symbol (`db/schema.ts:1805`, `:1892`,
   `:2935`, `:2985`), not a flat `{symbol, baseAsset, quoteAsset}`. All 16762
   active DCA bots in production have no `symbol.baseAsset` — the expression
   yields `undefined_undefined`. Only grid bots (`db/schema.ts:2119`, `:2297`)
   have the flat shape. DCA + combo are ~96% of the affected bots.
2. **It is ambiguous, and silently selects the wrong instrument.** `BASE_QUOTE`
   is not a key: `binanceUsdm` has three `pairs` rows for BTC/USDT
   (`BTCUSDT`, `BTCUSDT_260925`, `BTCUSDT_261225`) and three for ETH/USDT. A
   grid bot on the September delivery contract reads back as `BTC_USDT`, which
   resolves to the perpetual. 12 of a 500-bot sample sit on an ambiguous
   base/quote.
3. **`api.ts:3674` is not a precedent for it — it is this same defect.** See
   §1.3.

Conversely, the **native symbol is a key**: of 35654 production `pairs` rows,
448 contain `_` (380 X-Perp, 28 delivery, 40 `*_PERP`) and **none** has
`pair === baseAsset + '_' + quoteAsset`. So resolving by native `pair` first
can never shadow the documented `BASE_QUOTE` input, and can never be ambiguous.

### §2.4 The code already knows the native symbol is authoritative

`prepareDCABot` (`bot/index.ts:3716`) resolves a new DCA bot's assets with
`{ pair: { $in: settings.pair } }`, and `Bot.createBot` (`bot/index.ts:3386`)
with `{ pair: settings.pair }` — both exact, native lookups. Both create paths
already require the native form; only the validators in front of them require
`BASE_QUOTE`.

## §3 Assumption (hypothesis)

The defect is **a missing translation direction, not a wrong stored value**.
The stored/returned `settings.pair` is correct and is the only string that
identifies the instrument unambiguously; the validators are wrong to accept
`BASE_QUOTE` *exclusively*.

The root cause is that pair resolution is expressed as "split on `_`" in four
places, with one hand-added exception for X-Perp
(`isXperpPair`, `bot/utils.ts:1492`), rather than as "match the exchange-native
symbol, and fall back to splitting". Generalising that exception to the rule
makes the round trip close at both gates, fixes delivery and `*_PERP`
contracts that the X-Perp exception never covered, and leaves every existing
`BASE_QUOTE` caller byte-identical (§2.3, last paragraph).

## §4 Out of scope

- Changing what a read returns. The native symbol is the correct value; §2.3
  shows the alternative is both impossible and unsafe.
- Delisted pairs (§2.2, "unresolvable"). Those bots cannot be recreated on any
  format because the market no longer exists.
