# 220 — A cancel answer erases the fill the user stream already reported

Bug spec. Generalises `059` (a cancel response that reports no fill erases the
entry) and `217` (a reposition cancel loses the fill the stream reported
meanwhile). Both fixed one caller each. This fixes the shared step they both
describe: the field copy in `MainBot.cancelOrderOnExchange`.

## §1 Definition

### §1.1 Expected

An order's executed quantity never decreases (`059` §1.1). When the bot cancels
an order, the row it keeps in its order map carries the LARGEST executed
quantity it has for that order: the cancel answer's, the row it held before the
cancel, or the venue's own end-of-order report that the user stream delivered
while the cancel was in flight. The quote amount and the fill price travel with
the quantity they belong to.

### §1.2 Actual

`cancelOrderOnExchange` copies the venue's cancel answer onto the row it was
handed, which is the snapshot taken before the cancel. `processOrderQueue`
replaces the map entry with a new object when the stream report arrives, so the
copy then overwrites the stream's report in the map (`setOrder`). When the
answer says `executedQty: '0'`, the row is also deleted from the map
(`removeFromLocal && +request.data.executedQty === 0`).

The Mongo row is unaffected, because `updateOrderOnDb` will not overwrite a
terminal row. Everything that reads the in-memory map loses the fill:
`updateDealBalances` (the combo close sizing and the deal's ledger) and
`getTPOrder`.

## §2 Evidence

Production, Hyperliquid spot, combo SHORT, deal closed by its base minigrid
completing (identifiers withheld, this file is public):

- `06:47:45.598` "Close deal … after base minigrid close". The sweep cancels the
  grid orders one at a time, about 1.1 s apart.
- `06:48:08.779` stream: "Processing msg … CANCELED, 0.050553, base: 41 …
  SELL". This is a grid SELL of 204 that executed 41. The orders collection
  keeps `CANCELED, executedQty '41'`.
- `06:48:16.480` the close is sized and buys 3412.
- The deal's order rows in Mongo: sells 994 + 2285 + 10967 + **41** = 14287 and
  buys 10665 + 3412 = 14077. That leaves 210 short on the account.
- The deal's final in-memory ledger (`currentBalances.base` 14929 against
  `initialBalances.base` 15098) balances against every row except the 41.
  `updateDealBalances` admits CANCELED rows that have fills, and
  `executedFillQty` counts this row (it has a venue id). The row was therefore
  not in the map, or no longer carried its fill, when the ledger was built.
- The connector's cancel answer for Hyperliquid is a `getOrder` read-back, and
  that read-back now takes the executed size from the fill history (exchange
  connector spec 041). A history that does not yet hold the fill answers 0.

## §3 Assumption (hypothesis)

The cancel answer arrived after the stream report and said 0. The copy put the
pre-cancel snapshot, now carrying 0, back into the map over the stream's row,
and the delete-on-zero removed it. If the copy keeps the largest executed
quantity among the answer, the snapshot and the map's current row, the fill
survives, and the close and the ledger both count it.

## §4 Required behaviour

- §4.1 After the answer is copied and converted, if the map's current row for
  the order, or the pre-cancel snapshot, states a larger executed quantity than
  the answer, the row keeps that quantity, with its `cummulativeQuoteQty` and
  `price`.
- §4.2 A row that ends up holding a fill is not deleted from the map, whatever
  the answer said.
- §4.3 The status, the FILLED promotion decision (`026`) and the unit
  conversion are unchanged. They are decided from the answer, as before, and
  the reconciled quantity is already in the map's units.
- §4.4 With no larger report, nothing changes: an untouched order still cancels
  and leaves the map as before.

## §5 Not covered

- Why the connector's fill-history read-back missed a real fill. That is in
  exchange connector spec 041's area and is tracked separately.
- A stream report that arrives after the answer was already applied was never
  affected, because `processOrderQueue` re-adds it.

## Invariants

None new. The wrong state is in memory only (Mongo keeps the fill), so a
sentinel query over the collections cannot see it. The visible symptom, a closed
deal whose order rows do not net to zero, is a venue-divergence check rather
than a single-collection invariant.
