# 182 — A restart during a deal close's cancel sweep leaves the rest of its orders live

Bug spec. Related: `109` (a cold restart merges Mongo's open rows into the
Redis order snapshot), `160` (a placement queued behind a close), `173` (a
reload during a combo close leaves its ladders active), `180` (a refused
teardown cancel is re-sent).

## §1 Definition

### §1.1 Expected

- **§1.1.1** When the engine closes a deal and cancels its orders
  (`processDealClose` with `cancel`), every order of that deal still resting on
  the venue is eventually cancelled, even if the worker process stops in the
  middle of the cancel sweep.
- **§1.1.2** A combo deal closed that way ends with all of its minigrids
  `closed`, even if the process stopped before `afterDealClose` ran.
- **§1.1.3** A placement that is already running for a deal stops sending
  orders as soon as a close is requested for that deal (`closeBySl` /
  `closeByTp`), the same flags that already stop a placement before it
  starts. Spec `083`'s refused-close restore (`afterTerminalCloseRefusal`)
  keeps its opt-out.

### §1.2 Actual

- **§1.2.1** The close sweep is one venue call per order, serial. A combo deal
  with a long grid ladder takes tens of seconds to sweep. The deal is written
  `closed` before the sweep starts. A process stop during the sweep leaves the
  rest of the deal's orders `NEW` in Mongo and live on the venue.
- **§1.2.2** The next cold restart restores the order book from the Redis
  snapshot. The snapshot is written through `@RunWithDelay`, and every order
  mutation resets that timer, so under continuous order churn it is as old as
  the last quiet gap. Spec `109`'s merge reads Mongo's open rows only for the
  deals the snapshot names or that are open in Mongo. A deal that was created
  and closed since the snapshot's last write is in neither set, so its open
  rows are never loaded. The restart's "deal not found, cancel its orders" pass
  in `checkOrders` never sees them, and nothing else does either.
- **§1.2.3** `afterDealClose` never ran, and the restart loads minigrids only
  for open deals, so the closed deal's minigrids stay `active` / `range` for
  good. (Spec `173` covers the in-process reload race, not a process stop.)
- **§1.2.4** A take-profit that triggers while the deal's initial grid ladder
  is still being placed queues its close behind the placement lock. The
  placement checks the close flags only on entry, so it keeps placing the whole
  ladder (tens of seconds), and the close then has to cancel all of it. That
  widens the window of §1.2.1.

## §2 Evidence

Production, one Bybit linear long combo bot, 2026-10-20 (UTC):

- 05:05:48 deal created. Its grid ladder (~180 orders across 5 minigrids) is
  placed one order every ~0.47 s, 05:05:49 → 05:07:16.
- 05:05:51 `closing by take profit`. The close waits on the deal lock.
- 05:07:16 the placement ends, the close runs, the take-profit fills at
  05:07:20, and the close sweep cancels one order every ~0.56 s.
- 05:07:49 last cancel. The worker process is replaced (new PIDs from
  05:07:50). The sweep cancelled 58 orders and left the rest.
- 05:08:20 the bot starts again: `Get deals from DB` (no open deals),
  `Found in redis 257 orders`, no `Added … open orders from DB` line, and no
  cancel for the deal. Mongo still holds the deal's grid orders `NEW`, the
  venue reports them open (main-app spec 045 probe,
  `045.leaked-order-on-closed-deal`), and the deal's 5 minigrids are still
  `active` / `range`.
- No snapshot write was possible after 05:05:37: the order churn on this bot
  never left a 1.5 s gap from 05:05:48 to 05:07:49.

## §3 Assumption

The orders leak because the close sweep is not durable: its progress lives in
memory only, and no restart path can learn that a sweep was interrupted. The
fix records the sweep in Redis before it starts, written immediately rather
than through the debounce, and clears the record once the sweep has finished.
Every bot start resumes recorded sweeps whose deal it no longer holds: it reads
that deal's open rows from Mongo (indexed by `dealId`), cancels them on the
venue, and closes the deal's minigrids (combo). Nothing scans a bot's order
history, so a mass restart costs one Redis field per bot.

`checkOrders`' existing restart pass is not reused. It runs only on a cold
restart, and its gone-deal branch sits behind `!dcaByMarket`, which the
affected bot has set.

## §4 Solution

- **§4.1** `processDealClose` (with `cancel`) adds `{dealId, at}` to the bot's
  `closeSweeps` Redis field and awaits the write before anything is cancelled.
  After `afterDealClose`, the entry is removed when no order of the deal is
  still `NEW` / `PARTIALLY_FILLED` in memory. Otherwise it stays for the next
  start. Spec `180` keeps such an order tracked.
- **§4.2** `loadOrders` merges the stored entries into memory on every load, so
  a later write never drops an entry the previous process left.
- **§4.3** `restoreWork` (DCA and Combo) calls `resumeCloseSweeps` before its
  order checks. For each entry whose deal is neither held nor mid-close in this
  process: read the deal's `NEW` / `PARTIALLY_FILLED` rows, cancel each on the
  venue (a `FILLED` answer goes to `handleUnknownOrder` as in
  `cancelAllOrder`), then run the deal-type hook (Combo: close the deal's
  minigrids in memory and in Mongo, the spec `173` write). The entry is dropped
  when the deal has no open row left. A failed read keeps the entry. Entries
  older than 7 days are dropped unread.
- **§4.4** The placement loop's spec `160` check also stops on the close flags
  (§1.1.3): `closeBySl` (the combo TP/SL close and the DCA stop loss), and
  `closeByTp` unless the bot uses multi-TP, where `checkTPLevel` arms it for a
  single target and the deal stays open.
