# 085 — a minimum-size base order cannot fund its own take-profit

Bug spec. Reported from a spot DCA bot whose deal has sat `open` with no close
order on the book for days, re-reporting `Not enough balance` for its close
every few hours.

## §1 Definition

### §1.1 Expected

When a deal's configured base order is worth less than the venue's minimum
order quantity, `getBaseOrder` raises the entry so the deal will still be able
to rest a close that clears that same minimum. The block at
`dcaHelper.getBaseOrder` that does this states the intent in its own code: it
computes `tpQty = round(qty * (2 - feeFactor), precision, down)` — the quantity
the close will actually be sized at — and, when that is under the floor, raises
`qty` so it is not.

So the invariant that block exists to establish is:

> **§1.1.a** After the raise, `round(qty * (1 - fee), precision, down) >=
> baseAsset.minAmount`, and `round(qty * (1 - fee), precision, down) * tpPrice
> >= quoteAsset.minAmount`.

`qty * (1 - fee)` is load-bearing twice over, and both readings need the same
inequality to hold:

- on a venue that charges the **buy** fee in the asset received (Binance-shaped,
  and the paper-trading simulator for every venue it emulates), it is what the
  wallet is actually **credited**;
- on a venue that charges the **sell** fee in base (Kraken's `fcib` default), it
  is what `getTPOrder` **sizes the close at** — `_qty * (1 - maxFee)`.

### §1.2 Actual

The raise is written `baseAsset.minAmount * feeFactor + baseAsset.step` with
`feeFactor = 1 + fee.taker`, and its quote-notional sibling one branch above is
written `(quoteAsset.minAmount / tpPrice) * feeFactor + baseAsset.step`.

`(1 + f)` is not the inverse of `(1 - f)`:

```
minAmount * (1 + f) * (1 - f) = minAmount * (1 - f²)   <   minAmount
```

so the raise lands the deal `f²` short — one part in 10⁶ at a 0.1 % fee — of
the floor it was raised to clear. `baseAsset.step` is added as headroom but is
orders of magnitude too small to cover it (`1e-8` against a `6e-5` shortfall in
the reported case).

Downstream, `getTPOrder` sizes the close correctly at `qty * (1 - fee)`, finds
it below `baseAsset.minAmount`, and clamps it **back up** to `minAmount`:

```ts
if (tpOrder.qty < symbol.baseAsset.minAmount && !this.futures) {
  tpOrder.qty = symbol.baseAsset.minAmount
}
```

On a buy-fee-in-base venue that asks the venue to sell more base than the deal
was ever credited, so the close is refused for funds. Nothing about the deal
changes as a result, so the next attempt asks for the same quantity and is
refused again — the deal stays open with no close on the book indefinitely.

## §2 Evidence

A spot DCA bot on `paperKraken`, pair `SYN-USD`. `pairs` records
`baseAsset.minAmount: 60`, `baseAsset.step: 1e-8` (⇒ `precision` 8),
`priceAssetPrecision: 4`. Deal settings: `baseOrderSize` 10.8 quote,
`tpPerc` 1, `dealCloseCondition: tp`, account fee 0.001 maker/taker.

1. **The entry is the §1.2 expression, to the unit.** `10.8 / 0.1831 = 59.04`
   base — under the 60 floor — so the raise fires and produces
   `60 * 1.001 + 1e-8 = 60.06000001`. The recorded entry order is
   `origQty: '60.06000001'`, `executedQty: '60.06000001'`,
   `cummulativeQuoteQty: '10.996986001831'`, `status: FILLED`.
2. **The wallet is credited `qty * (1 - f)`.** The simulator books a spot BUY as
   `baseAssetAmount - order.amount * feePerc`. The base wallet reads
   `free: 59.99994006521026`, `locked: 0`, and has not moved since the entry
   filled. `59.99994006521026 < 60`.
3. **The close is clamped back to `minAmount`.** The engine log for the deal
   reads `close refused | deal … (SYN-USD) restoring take-profit 60 after Not
   enough balance` — quantity exactly `60`, i.e. `minAmount`, not the
   `59.99994` the fee-netting produced.
4. **It is refused, repeatedly, and never recovers.** Bot messages for the
   account carry `Not enough balance … order type: deal close, balance total -
   59.99994006521026 SYN, free - 59.99994006521026 SYN, required - 60 SYN` at
   09-17 00:06, 09-18 07:11, 09-19 20:29, 09-20 18:46, 09-21 07:04, 09-21
   15:06, 09-21 21:44, plus `Deal … is open with no close order on the
   exchange` on 09-22 00:41.
5. **Not one pair, and not one deal.** The same `free = N - ε, required = N`
   shape appears on the same account for five further pairs whose
   `baseAsset.minAmount` the configured base order also failed to reach — 90,
   250, 350, 600 and 1400 base units respectively — every `required` an exact
   `minAmount`.

## §3 Assumption

Hypothesis, not fact: the root cause is the fee compensation in
`getBaseOrder`'s close-floor block. It grosses the entry up by `(1 + f)` where
the quantity it is compensating for is shaved by `(1 - f)`, so the block does
not achieve §1.1.a for any non-zero fee. The `getTPOrder` clamp is then doing
what it was written to do — a close below the venue's minimum quantity is not a
tradeable order — and is not itself the defect; it is the messenger.

Consequently the fix is to make the raise the exact inverse of the shave,
`minAmount / (1 - f)` rather than `minAmount * (1 + f)`, at both raises in that
block. `1 / (1 - f) >= 1 + f` for `f >= 0`, so this is a strict increase and
cannot make a previously-satisfied case fail.

A test that drives the real `getBaseOrder` over the §2 fixture and asserts
§1.1.a must fail on the `baseAsset.minAmount` branch — `59.99994 < 60` — and
must fail for that reason, not because the order could not be built.

## §4 Solution

### §4.1

In `getBaseOrder`'s `settings.useTp` close-floor block, express both raises as
the inverse of the close's own `(2 - feeFactor)` shave:

- `baseAsset.minAmount / (2 - feeFactor) + baseAsset.step`
- `(quoteAsset.minAmount / tpPrice) / (2 - feeFactor) + baseAsset.step`

`2 - feeFactor` is already this file's spelling of `(1 - fee)` — it is what the
same block's `tpQty` is computed with three lines above, which is precisely why
it is the right divisor: the two now cannot drift apart.

### §4.2

`feeFactor` is `1` for futures, for a short, for a `terminal` simple deal and
for a deal whose fees so far were all third-asset (spec 015 §2/§3). In every
one of those cases `2 - feeFactor` is `1` and both expressions are unchanged,
so the fix cannot reach any path that was already exempt from the gross-up.

### §4.3

Out of scope, deliberately: the `getTPOrder` clamp of §1.2. Capping it at what
the deal holds (the shape spec `043`/`047` gave the quote-notional clamp) does
not help — the engine's own ledger, `deal.size`, records the **gross** entry
`60.06000001`, not the `59.99994006521026` the wallet was credited, so a
held-capped clamp still clamps to `minAmount`. Removing the clamp instead would
send closes the venue rejects for minimum volume. The floor is real; what has
to change is that the entry clears it.

### §4.4

Also out of scope: deals already stuck. This change prevents new ones. An
existing deal recovers on its own as soon as any safety order fills, since that
raises the position above `minAmount`.
