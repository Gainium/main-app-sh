# 133 — A reposition cancel that races a partial fill opens the deal short and drops the remainder

Bug spec. Extends `038` (settle a part-filled entry), `059` (a cancel answer
that states no fill), `111` (rest the remainder of a short LIMIT entry) and
`125` (wait out an asynchronous cancel).

## §1 Definition

### §1.1 Expected

When the reposition tick of a LIMIT base order cancels it and the order has
part-filled meanwhile, the deal opens on what traded and — on a bot that may
not enter at market — the rest of the requested size goes back on the book as
a LIMIT (spec `111`), on every account type, including contract-sized and
coin-margined ones. No second base order is placed while the first may still
rest. A cancelled order's row does not stay `NEW`.

### §1.2 Actual — the venue still lists the order live

OKX cancels asynchronously. Its connector's `cancelOrder` reads the order back
straight after the cancel is accepted, and the venue still lists it `live` /
`partially_filled` (mapped to `NEW` / `PARTIALLY_FILLED`). The reposition arm
of `checkBaseOrder` acts only on a `FILLED` answer, so it calls
`placeBaseOrder`. With a fill in the answer the row stays in memory as
`PARTIALLY_FILLED`, `placeBaseOrder` logs "already have and active base
order", and the deal stays in `start` until something else re-reads the
order — on a deaf user stream, the periodic reconcile sweep, minutes later.

### §1.3 Actual — the sweep or a FILLED cancel answer books it, unmarked

Both the reconcile sweep (`getOrder` promotes `CANCELED`-with-fills to
`FILLED`) and a cancel answer that is already `CANCELED` with fills
(`cancelOrderOnExchange` promotes it) reach `startDeal` through
`handleUnknownOrder` without the engine-settled mark. On a contract-sized or
coin-margined account `restBaseEntryRemainder` then reads the row as a venue
`FILLED` reading short (spec `111` §4.1.1), refuses it, and warns "Remainder
not placed: the exchange reported the order as filled". The deal holds a
fraction of the base order the user configured, and nothing rests for the
rest.

### §1.4 Actual — an unfilled order the venue still lists live

With nothing filled, `cancelOrderOnExchange` drops the row from memory and
writes the `NEW` answer to the database. The venue's own `CANCELED` event is
the only thing that would correct it; on a deaf stream nothing does, the
sweep never sees a row that is not in memory, and the row stays `NEW` for
good.

## §2 Evidence

Production, OKX USDT-margined perpetual, LIMIT entry, "Enter Market Timeout"
off, repositioning on (identifiers withheld — this file is public):

- Four reposition ticks re-place a 1030 base order as the price moves.
- `07:29:51.969Z` tick: "… not filled. Create new one" on order A; a new
  order B is placed 0.4 s later. Order A's row is still `NEW` in the orders
  collection today, and order A has no later log line.
- `07:30:42.402Z` tick: "… not filled. Create new one" on order B;
  `07:30:42.594Z` "Deal … already have and active base order". Nothing else
  for 5½ minutes.
- `07:36:17.805Z` "reconcile-sweep caught 1 missed fill(s)", "Base order
  FILLED"; `07:36:18.108Z` WARN "base order B filled 40 of 1030. Remainder not
  placed: the exchange reported the order as filled".
- Orders collection: order B `FILLED`, `executedQty 40`, `origQty 1030`. Deal
  `open`, base 40.

Connector: `exchange-connector-sh` `okx/index.ts cancelOrder` calls
`getOrderDetails` as soon as the cancel returns `sCode 0`; `convertOrder` maps
`live` to `NEW` and `partially_filled` to `PARTIALLY_FILLED`.

## §3 Assumption (hypothesis)

The reposition arm treats the first cancel answer as final and has its own
`FILLED`-only branch, separate from the settle chain (`settlePartialBaseEntryNow`)
that already waits out an asynchronous cancel (spec `125`), books a fill a
cancel answer dropped (spec `059`), forces the `FILLED` write (spec `128`) and
sets the engine-settled mark `restBaseEntryRemainder` requires (spec `111`
§4.1.1). Routing the reposition cancel through that same chain fixes §1.2–§1.4.
The sweep path (§1.3) loses the venue's `CANCELED` before the engine sees the
row, so it needs our own cancel record (`isOwnCancel`) to tell the two apart.

## §4 Required behaviour

- **§4.1** A reposition cancel whose answer is not terminal is re-read, as in
  spec `125` §4.1. If the venue ends the order with a fill, the deal opens on
  that fill, the row is persisted `FILLED` (forced), and it carries the
  engine-settled mark, so the remainder rests on contract-sized and
  coin-margined accounts too. No second base order is placed.
- **§4.2** A reposition cancel whose answer is already `FILLED` (promoted
  `CANCELED`-with-fills) is booked through the same chain and carries the
  same mark.
- **§4.3** A reposition cancel that ends the order with nothing traded
  re-places the base order as before. If that was learnt from a re-read, the
  ended row is persisted, so it does not stay `NEW`.
- **§4.4** A venue that never ends the order within the spec `125` attempts:
  bounded, and the row is marked for the venue's own `CANCELED` event (spec
  `125` §4.2). Re-placement is unchanged from before.
- **§4.5** A reconcile that finds a base row `FILLED` that it last held
  unfilled-or-part-filled, and that this bot cancelled itself recently, marks
  it engine-settled when its fill did not shrink. A `FILLED` row this bot did
  not cancel stays untrusted (spec `111` §4.1.1).
- **§4.6** The settle path (`settlePartialBaseEntry`) behaves exactly as
  before.
