# 189 — A grid take-profit close sells again while the bot is stopping

Bug spec. Code: `src/bot/helper.ts` `closeBotByTp`, `processFilledStop`.

## §1 Definition

### §1.1 Expected

When a spot grid bot's take profit (or stop loss) fires with the
`stopAndSell` action, the bot cancels its grid, places ONE closing order for
its own coins and stops. Price ticks that arrive while that close is in
progress do not place another closing order. Once the closing order has
filled, nothing sells again.

### §1.2 Actual

`closeBotByTp` runs under a per-bot mutex. Every price tick that reaches it
while the first close is awaiting the venue queues a fresh call (no
`oldTpSl`). When the first call returns, the queued call runs and:

- re-evaluates `tpSl()` against `this.data.currentBalances` — which the close
  never updated in memory (`processFilledStop` and the placement-reply branch
  only `$set` the new balances in Mongo), so the value is unchanged and the
  take profit fires again;
- skips the "Found close order with status filled" guard, which only runs
  when `oldTpSl` is passed and which reads `allOrders` — where
  `processFilledStop` has already deleted the filled stop order;
- calls `sellBaseAmount()`, whose cap `currentBalances.base` is the same
  stale in-memory value, and sells the full grid amount again.

Each new sell takes another venue round trip, during which more ticks queue,
so the loop repeats until the bot is closed — selling coins that belong to
the user's other bots or holdings.

### §1.3 Unchanged

The take-profit / stop-loss trigger level, and the single close order a
normal close places (including the LIMIT reposition and enter-market timers,
which re-enter with `oldTpSl`).

## §2 Evidence

Production, Hyperliquid spot BTC-USDC grid, `tpSlCondition: valueChanged`,
`tpSlAction: stopAndSell`, 2026-10-21 (identifiers withheld — public file):

- `13:04:42Z` "Initial value: 4011.13796, current value: 4095.36…, diff:
  2.1%, TP trigger"; grid orders cancelled until 13:05:05.
- `13:05:05.407Z` "Check assets start" → first MARKET SELL 0.02797.
- `13:05:06.966Z` stream: stop order FILLED → "Stop order filled. Processing
  stop..." (`processFilledStop`, `stopFilled = true`, `stop(true)`).
- `13:05:07.952Z` placement reply → "Stop order filled. Processing stop...",
  and 10 ms later "Initial value: 4011.13796, current value: 4102.72…, TP
  trigger" → "Check assets start" → another sell.
- The same three lines repeat at 13:05:10, :12, :15, :17, :19 — six MARKET
  SELL 0.02797 stop orders in `orders`, against `initialBalances.base`
  0.02797. The "current value" never drops, because in-memory
  `currentBalances` never reflects the sells.

## §3 Assumption (hypothesis)

`closeBotByTp` has no latch for "a close is already in progress / has
filled": a queued fresh trigger is not stopped by `blockLimit` (set by the
first call) nor by `stopFilled` (set when the stop order filled). Adding that
latch at the top of `closeBotByTp` makes every queued call after the first a
no-op, without touching the trigger or the first close.

## §4 Required behaviour (tests: `src/bot/gridTpCloseSingleShot.spec.ts`)

- §4.1 A second fresh trigger after a close has been placed places no order
  and does not trigger again.
- §4.2 A re-entry (timer, `oldTpSl`) after the stop order has filled places
  no order — even though `allOrders` no longer holds the filled stop.
- §4.3 The placement reply's FILLED branch latches the close the same way the
  stream's delivery does.
- §4.4 Unchanged: a LIMIT close that is still resting is repositioned by its
  timer re-entry (`oldTpSl`), as before.

## §5 Invariants

`main-app/specs/189.invariants.json` — a grid bot has at most one FILLED
`typeOrder: stop` order (observe).

## §6 Amendment — the latch did not survive `stop()`, and the cloud override never had it

### §6.1 Definition

Same as §1.1, for the stop-loss path too: once the closing order has filled
and the bot has stopped, price ticks that were already queued — or that
arrive before the price subscription is torn down — sell nothing.

Actual: the same burst recurred on a stop-loss close (`slAction:
stopAndSell`, take profit off), on the same venue, after §4's fix shipped.

### §6.2 Evidence

Production, Hyperliquid spot grid, stop loss with `stopAndSell`, 2026-10-29
(identifiers withheld — public file):

- `02:05:45Z` "SL trigger"; the grid's orders are cancelled until 02:06:13.
- `02:06:15Z` the first close fills → "Stop order filled. Processing stop...".
- `02:06:19.694Z` "Stop order filled. Processing stop..." and 6 ms later a new
  "SL trigger" → "Check assets start" → another sell. The same pair of lines
  repeats at :21, :23, :25 and :27 — five FILLED closing sells in 12 s, the
  account's whole balance of the coin.

Two mechanisms, both traced in code:

1. The latch of §3 lives on core's `closeBotByTp`. The cloud application
   overrides `closeBotByTp` and `priceUpdateCallback` wholesale (its own
   alerting and dry-run handling), and that override — the copy production
   runs — never received the latch. Nothing stopped a queued trigger there.
2. `stop()` ends in `clearClassProperties(true)`, which reset `stopFilled`
   and `blockLimit` (and `lockTpSlCheck`) on every stop, not just on a fresh
   start. A latched close was un-latched by the very stop it triggered, so
   even core's copy let a tick queued behind the stop sell again.

### §6.3 Assumption (hypothesis)

Keeping `stopFilled` / `blockLimit` latched until the next `start()`, giving
the override the same latch as core, and refusing a close or a price check
once the bot is `closed`, makes every tick after the first close a no-op on
both the take-profit and the stop-loss path.

### §6.4 Required behaviour

Tests: core `src/bot/gridTpCloseSingleShot.spec.ts` (§4.5–§4.6) and the
cloud override's `tests/gridCloseSingleShot.ts` (§4.7).

- §4.5 `clearClassProperties` keeps `stopFilled` and `blockLimit` on a stop
  (`clearClassProperties(true)`) and resets them on a start
  (`clearClassProperties(_, true)`).
- §4.6 With the bot `closed`, `closeBotByTp` places nothing and
  `priceUpdateCallback` never reaches it — take profit and stop loss alike.
- §4.7 The cloud override of `closeBotByTp` holds §4.1–§4.4 and §4.6.

Unchanged (§1.3): the size and type of the one closing order, and the LIMIT
reposition / enter-market re-entries while it is still unfilled.
