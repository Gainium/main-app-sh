# 103 — A LIMIT base entry is repositioned to the price it already rests at

A DCA bot whose deals start with a LIMIT order, with repositioning on and the
"Enter Market Timeout" switch off, repositions an unfilled base order every
10 s, indefinitely (spec `100` §1.1, row 1). "Reposition" is implemented as
cancel + re-place at the latest price, with no comparison against the price
the order already rests at. And a base order that fills PART of the way is
left alone by that same timer forever.

## §1 Definition

### §1.1 Expected

- **§1.1.1** An unfilled LIMIT base order is re-placed only when the
  price it would be re-placed at differs from the price it rests at. While
  the price is unchanged, the order stays on the book and the reposition
  timer is armed again.
- **§1.1.2** A base order that stopped part-filled, with no later check still
  scheduled for its deal, is settled by the reposition timer. That means the
  remainder is cancelled and the deal opens on what executed, with its safety
  orders and take profit. It does not wait for the next bot start.
- **§1.1.3** Nothing in §1.1.1–§1.1.2 sends a MARKET order for a bot whose
  entry is LIMIT with the switch off (spec `100`). The settled entry is not
  topped up at market for such a bot.

### §1.2 Actual

- **§1.2.1** `checkBaseOrder`'s order-id branch cancels every non-filled base
  order and calls `placeBaseOrder`, which derives the same price again. On an
  illiquid pair this happens every 10 s for hours, which spends two
  rate-limited private calls per tick.
- **§1.2.2** In the same branch, `shouldSettlePartialBaseEntry` is passed
  `hasPendingCheck: dealTimersMap.has(dealId)`. That reads "the enter-market
  check at 35 s is still coming". Since spec `100`, a switch-off bot arms no
  enter-market timer. The map entry still exists, though, so the partial fill
  is never settled. The timer fired and did not re-arm, so nothing ever looks
  at the order again until the bot's restore path runs on the next worker
  start.

## §2 Evidence

Production, 2026-09-24, a paper Kraken bot. Entry LIMIT, switch off,
repositioning on.

- One deal's `dealStart` rows: 1286 `CANCELED` rows at one identical price
  over 3 h 36 m, then one `FILLED` row at that same price. The worker log shows
  `<id> not filled. Create new one` for each deal every 10 s.
- Another deal: at 02:00:04Z the stream reported `PARTIALLY_FILLED`, with
  3000 of 3657.86 executed. The next log line about that order came at
  03:05:23Z, from a new worker PID: `stopped at 3000 of 3657.85823041 and
  nothing else will check it`. That is the restore path. Nothing logged
  in between.

## §3 Assumption (hypothesis)

- §1.2.1: the order-id branch has no "price unchanged" check. `getBaseOrder`
  prices a LIMIT entry as `round(latestPrice, priceAssetPrecision)`, so the
  same computation tells in advance whether a re-place would change anything.
- §1.2.2: `hasPendingCheck` in the order-id branch should mean "an
  enter-market timer is armed for the deal", not "any timer state exists".

## §4 Required behaviour

- **§4.1** Live reposition tick (this process holds timer state for the deal),
  deal in `start`, order `NEW` and `LIMIT`, bot `startOrderType` LIMIT, not a
  forced market call, and the latest price rounded to the pair's price
  precision equals the order's price. Then no cancel and no re-place happen,
  and the reposition timer is armed again under the same window rule
  `placeBaseOrder` uses.
- **§4.2** Anything else in that branch behaves as before. That covers a moved
  price, the restore path, a market-entry bot's substituted LIMIT, and an
  unreadable price.
- **§4.3** Order-id branch, a part-filled row, no enter-market timer armed:
  settle it. If an enter-market timer is armed, leave the row alone (spec
  `038` §4.3 is unchanged).
- **§4.4** `topUpSettledBaseEntry` never buys at market when the bot's
  `startOrderType` is LIMIT and `enterMarketTimeout === 0`. Otherwise the
  spec `057` rule is unchanged.
