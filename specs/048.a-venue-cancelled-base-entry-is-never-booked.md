# 048 — A base entry the venue cancels after a partial fill is never booked

Bug spec. The behaviour already exists and is wrong.

Extends spec `038`, which settled the same stranding for a base order left
`PARTIALLY_FILLED`. `038`'s decision and both of its call sites are unchanged
here; this spec adds the shape `038` cannot see — a base order the venue took
to a TERMINAL state while it was part filled.

## §1 Definition

A DCA deal's base order opens the deal. `startDeal` is reached only from
`processFilledOrder`, so only a base order the engine holds as `FILLED` ever
opens one. Until then the deal sits in `start` with `avgPrice` / `initialPrice`
/ `lastPrice` at `0` and `cost` / `size` unset.

### §1.1 Expected

When the venue itself ends a base order — `CANCELED` or `EXPIRED` — after some
of it has executed, the executed quantity is a position the account is holding
and the deal is the only thing that would ever close it. The deal must open on
that quantity (`levels.complete`, `size`, `cost`, `avgPrice`, take-profit and
stop-loss all derived from what executed), the user must be told once that the
entry was cut short, and no second base order may be placed on top of it.

### §1.2 Actual — nothing on the engine looks at that order again

Three independent gaps, each of which alone strands the deal:

1. **`processCanceledOrder` (`dcaHelper.ts:17110`)** is the callback the order
   queue fires for a `CANCELED`/`EXPIRED` report, and for a venue-cancelled
   entry it is the ONLY report that ever arrives. Its first statement is
   `if (order.typeOrder !== TypeOrderEnum.dealTP) return`. A `dealStart` row is
   dropped there, with its executed quantity, unread.

2. **`shouldSettlePartialBaseEntry` (`dca/partialBaseEntry.ts:62`)** accepts
   only `PARTIALLY_FILLED`, so even where `038`'s two call sites DO reach the
   order they decline to settle a terminal one.

3. **`restoreWork` (`dcaHelper.ts:11341`)** — the once-per-bot-start recovery
   for `start` deals — reads the deal's `dealStart` row under
   `status: { $ne: 'CANCELED' }`. The row is invisible, so the deal falls into
   the "never started" branch and the entry is **re-placed**: a second base
   order on top of a position the account already holds.

`038`'s repair lives entirely inside `checkBaseOrder`, and `checkBaseOrder` is
only ever scheduled by the timer block in `placeBaseOrder`, which is itself
behind `startOrderType === limit || sentType === limit`
(`dcaHelper.ts:9283-9291`). **A MARKET base order arms no timer at all**, so for
a market entry `checkBaseOrder` is never called, and the queue callback in (1)
is the engine's whole knowledge of the order.

### §1.3 Nothing tells the user

`processFilledOrder` is never reached, so no `Deal` event and no bot message is
written. The dashboard's order list does not render the row either. The deal
shows `0/12` levels and a cost of `0` for as long as it lives, and the quantity
the venue executed sits in the account outside any deal.

## §2 Evidence

Production, Kraken spot, a LONG DCA deal on ETH-EUR, 2026-09-14 (times UTC):

```
20:12:29  deal created; base MARKET BUY placed for 0.20016002
20:12:30  user stream: trade 0.0360993 @ 2215      (cost 79.95995)
20:12:30  user stream: trade 0.0029    @ 2215.16   (cost  6.42396)
20:12:30  user stream: canceled, cancel_reason "Cannot trade with self",
                       cum_qty 0.0389993, cum_cost 86.38391, avg 2215.01
20:12:30  DCA worker: "... PARTIALLY_FILLED 0.0360993 ... PARTIALLY_FILLED
                       0.0389993 ... CANCELED ... Save order"   (and nothing else)
04:50 / 08:51 (next day)  restoreWork re-placed the base order twice
                          (rows with orderId -1; both refused by the venue)
09:18     deal cancelled when the bot was stopped
```

The deal document read live 2026-09-16 over the dashboard GraphQL API:

```json
{"status":"canceled","cost":null,"size":null,"avgPrice":0,"initialPrice":0,
 "lastPrice":0,"levels":{"all":12,"complete":0},"closeTrigger":"bot"}
```

`updateTime` still equals `createTime` — nothing ever touched the deal after it
was written. `getBotOrders` returns no row for the deal at all, so the user
could not see the order either. 0.0389993 ETH (86.38 EUR) is in the account
outside any deal.

Fleet scan, `orders` rows created in the 14 days to 2026-09-16, `typeOrder:
dealStart`, `status: CANCELED`, `executedQty > 0`: **50 rows, 23 accounts, 8
venues**. 49 of them belong to deals that booked the quantity anyway — those are
LIMIT entries, where `checkBaseOrder`'s reposition timer reached the order and
`cancelOrderOnExchange` promoted it before the stream's cancel report landed, and
the CANCELED status is a later overwrite of an already-booked row. One did not:
the deal above. That is the population this spec is about — a base entry with no
timer armed, i.e. a MARKET entry, or any entry whose cancel report lands while
no worker holds timer state for the deal.

## §3 Assumption (hypothesis)

The root cause is that a terminal order carrying `executedQty > 0` is treated as
a plain cancel everywhere a `dealStart` is judged. It is not a missing sweep and
not venue-specific: the venue reported the executed quantity, in the one message
the engine was guaranteed to receive, and every reader of that message discarded
it because the order's status was `CANCELED` rather than `PARTIALLY_FILLED`.

## §4 Required behaviour

### §4.1 The decision

`shouldSettlePartialBaseEntry` gains a second accepted shape. It settles when
the deal is still in `start`, nothing else is scheduled to look at the order,
and EITHER

- the order is `PARTIALLY_FILLED` — spec `038`, unchanged; or
- the order is TERMINAL (`CANCELED` / `EXPIRED`) with `executedQty > 0` and a
  usable `updateTime`.

`updateTime > 0` is required only for the terminal shape, and for the reason
`processCanceledOrder` already applies it to a cancelled take-profit: a cancel
row written from a REST response rather than a stream event can carry a bogus
`executedQty` alongside `updateTime: -1`, and production holds such rows.
Opening a deal on an invented fill is worse, and silently so, than the
stranding this fixes. A stream event always carries a real timestamp.

No upper bound is placed on `executedQty`. The cancelled-take-profit rule
declines at `executedQty >= origQty` because a full execution is the `FILLED`
path's to close; here the equivalent guard is already the deal's own status, and
refusing a fully-executed-but-only-reported-as-cancelled entry would leave
exactly the stranding this spec exists to remove.

### §4.2 Where the decision is now asked

In addition to `038`'s two call sites (`checkBaseOrder`'s reposition and
enter-market branches, both unchanged):

- **`processCanceledOrder`**, for a `dealStart` row. `hasPendingCheck` is
  `dealTimersMap.has(dealId)` — the same reading `038` uses. It is what keeps
  this clear of a cancel the engine issued ITSELF: a reposition cancels the
  resting base order and re-places it, and while that is in flight the process
  still holds timer state for the deal, so the cancel report is left to the
  timer machinery exactly as today. A MARKET entry holds no timer state, which
  is the case this spec is about.

- **`restoreWork`**, which must stop hiding the row. The `status` filter is
  removed and the choice made in code instead (`pickRestoreBaseEntry`): a
  non-terminal row still wins, exactly as today; a terminal row is used only
  when it carries a fill; a terminal row with no fill is ignored, so a deal whose
  entry was cancelled outright still re-places it and no venue round trip is
  added for it.

### §4.3 Settling a terminal order places no venue call

`settlePartialBaseEntry` cancels the remainder before opening the deal. A
terminal order has no remainder — asking the venue to cancel it answers "unknown
order", which routes to `_handleUnknownOrder`, which returns `null` for anything
that is not `FILLED`, so the settle would report failure and the deal would stay
stranded. It also spends a rate-limited private call per attempt on a venue that
may be in an auth lockout, which is where the re-placement attempts in §2 went.

So for a terminal order the row is promoted locally — `status: FILLED` at the
`executedQty` the venue reported, persisted, emitted — and handed to
`handleUnknownOrder`, which is the same chain `cancelOrderOnExchange` feeds. The
quantity is used verbatim: it has already passed the contract/coin-margined
conversion in `convertExecutionReportToOrder`, and converting again would
double-count it.

### §4.4 The user is told, once

A settle writes one `Deal` event naming the symbol, the quantity that executed
and the quantity that was requested. It is written on the settle, not on the
cancel, so an entry the reposition machinery completes normally stays silent,
and a re-settle of an already-open deal cannot reach it.

The venue's own reason for the cancel (Kraken v2 `executions.cancel_reason`,
e.g. "Cannot trade with self") is NOT available here: websocket-connector does
not parse it onto the execution report, so no field of `Order` carries it.
Surfacing that text is a websocket-connector change and is out of scope; the
event states the mechanism the engine can see.

### §4.5 Venue exemptions

`checkBaseOrder`'s hyperliquid early-return is unchanged, so hyperliquid keeps
its exemption on both of `038`'s call sites. The new `processCanceledOrder` call
site carries no venue exemption: the exemption exists to leave an order that is
still filling alone, which a terminal order by definition is not, and the
deal-still-in-`start` guard makes it a no-op on every hyperliquid row measured
in §2 (all already booked).

## §5 Out of scope

- Parsing `cancel_reason` in websocket-connector (see §4.4).
- Topping the entry back up to the configured size with a second order — §5 of
  spec `038`, unchanged.
- Combo bots. `comboHelper` overrides `processCanceledOrder` and never calls
  the DCA implementation, so nothing in §4.2 reaches them.
- The 49 already-booked rows in §2. Their deals are correct; the CANCELED status
  left on a row the engine already promoted is cosmetic and has its own cause.

## §6 A known, accepted race

`closeDealById` cancels a deal's orders (`cancelAllOrder(…, cancelPartiallyFilled)`)
BEFORE it writes the deal's new status, so a cancel report for a part-filled base
entry can reach §4.2 while the deal is still `start` and be settled — opening a
deal the engine was about to cancel.

Accepted rather than gated. The flag that marks the teardown
(`allowToPlaceOrders`) is cleared in the same statement that follows the cancel,
so it cannot be read reliably from the queue; and in every case that reaches this
window the account demonstrably holds the executed quantity. A deal that tracks
that position — with a take-profit and a stop-loss on it — is strictly better
than a cancelled deal and an orphaned balance, which is the outcome §2 records.
