# 199 — The fee-asset minute-price cache clears itself in the middle of a call

Bug spec (Definition / Evidence / Assumption). Area: `FeeAssetPrices`
(`src/graphql/handlers/feeAssetPrices.ts`), the off-pair fee valuation behind
the trading-costs summary (specs 050, 198).

## §1 Definition

- **§1.1 Expected.** A `prices()` call returns a price for every request whose
  candle the source answered (and that has a route), whatever the process-wide
  cache held before or holds while the call runs. The same account's off-pair
  fees value the same on every load.
- **§1.2 Actual.** `prices()` stores every minute it reads through `setMid`
  into the shared `mids` map and only afterwards looks each request up with
  `midCached`. `setMid` empties the whole map once it holds `MID_CACHE_MAX`
  entries. When that happens while a call is still storing its later days, the
  minutes of its earlier days — already read — are gone, and those requests
  come back `null` (unknown) although the source answered them. Which ones
  depends on what the process cached before (other users' calls, the order bots
  are valued in), so the unknown share of the same account's fees changes from
  load to load.
- **§1.3 Unchanged.** Every price that is a number today is the same number.
  Only prices that were wrongly unknown get a value. Source reads, the
  per-call day cap, the warm memo and the miss/price TTLs are unchanged.

## §2 Evidence

- Replay of one heavy account's off-pair fee minutes (three venue pairs, 186
  pair-days), valued bot by bot through the real `FeeAssetPrices` with a source
  that answers every minute: 116 prices `null`; the correct count is 0.
- An old/new comparison over the same replay with a varying-price source that
  leaves some minutes empty, bot calls in concurrent waves: 0 prices differ,
  0 go from a number to unknown, the only change is unknown → number; minutes
  the source left empty stay unknown.
- The clear has no log line, so production cannot show it firing directly; the
  map never shrinks except on an expired lookup or the clear, so any long-lived
  process that values more than ~138 pair-days reaches it.

## §3 Assumption

- **§3.1** The unknowns are exactly the minutes the clear removed between
  `readWindow` storing them and `prices()` reading them back. A test that
  fills the cache close to the cap and then values days that cross it fails
  with `null` on the old code for that reason only.

## §4 Fix

- **§4.1** A call keeps every mid it found cached or read in its own map and
  answers from it before the shared cache, so no eviction or concurrent call
  can lose them.
- **§4.2** At the cap the shared cache evicts its oldest-stored minutes down to
  a low-water mark instead of clearing everything.
