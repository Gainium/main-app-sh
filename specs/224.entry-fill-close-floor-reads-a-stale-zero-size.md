# 224 — A base-order fill near the venue minimum arms no take-profit

Bug spec (Definition / Evidence / Assumption).

## §1 Definition

**Expected.** When a DCA deal's base order fills, `getTPOrder` builds a
take-profit for what the deal holds. If the fee-netted close misses the venue's
notional floor, the below-minimum branch (spec `035` §4.3, `043`) raises it to
the holding, or raises the price to the lowest one the venue accepts. When
neither is possible, the refusal is reported to the user (`047` §4.4).

**Actual.** On a spot long whose base order paid its fee in the base asset, the
fee-netted close floors one step below the fill (0.09 bought, 0.08991 held,
0.08 sized). The below-minimum branch then measures the holding as **0** and
returns `[]` through the zero-holding settle exit (`91e1950`) as a debug line.
No take-profit is placed and nothing is reported. Nothing rebuilds the
take-profit later either: the next build waits for the next fill, and a deal
whose price never reaches a safety order stays open with no exit.

## §2 Evidence

- §2.1 Prod, 2026-11-04 14:35:47Z, binance PYPLBUSDT (step 0.01, min notional
  5 USDT), base order 5.6 USDT, TP 2 %. Base order FILLED 0.09 @ 59.94, fill
  commission `0.00009 PYPLB`. Seven safety orders were saved within 2 s. No
  `dealTP` row exists for the deal, no `Save order …-TP-` line was logged, and
  there is no error botmessage. The bot's previous deal placed and filled its
  TP normally.
- §2.2 In the base-fill handler (`dcaHelper` "Base order FILLED"),
  `createCurrentDealOrders` → `getTPOrder` runs **before** `currentBalances`
  are booked and before `updateUsage` writes `deal.size`. `size` is written
  only in the `.then` of the later `saveDeal`. When the TP is sized, the
  in-memory deal therefore still reads `size: 0`.
- §2.3 The real `getTPOrder`, driven over this exact state (harness
  `src/bot/dca/entryFillCloseFloor.harness.spec.ts`):
  - `size: 0`, deal touched just now → `[]`, debug `Close order is below the
    exchange minimum … qty 0 at price 61.26 … (deal orders just changed)`.
  - the same deal once `size` has caught up (`0.08999999999999996`) → TP
    `0.08 @ 62.5`.

  The refusal is an artefact of reading the size before it is written.

## §3 Assumption (hypothesis)

The below-minimum branch measures the holding only through `deal.size`
(`trackedPosition`). Right after an entry fill that size has not caught up, so
the holding reads ≤ 0 even though the order rows the same method sizes the close
from show a filled entry. The `91e1950` settle window assumes the zero is a
transient that a later build will repair. For a base-order fill no later build
comes.

## §4 Required behaviour

- §4.1 When the size-derived holding is ≤ 0 but this deal's own **executed**
  entry rows, net of what it has closed, of pending/executed reduce-funds, and
  of the base fee the entry rows report, show a positive holding, the branch
  uses that holding. A close sized from it is exactly what the deal would get
  once its size catches up (§2.3).
- §4.2 Only executed quantity counts. A base order with nothing executed (an
  unfilled LIMIT start, or a `nominal` stopgap) contributes 0, so a deal that
  holds nothing still reads 0.
- §4.3 The `91e1950` settle window and the `047` §4.4 reconcile are unchanged
  for a holding that is zero by **both** measures: a part-filled base order
  being re-placed, a TP that has just filled, or the fully-exited EDU deal
  (`size: 0`, BUY 68 + SELL 68 filled) still behave exactly as before.
- §4.4 A positive size-derived holding is used as before. The order rows never
  override it.

## §5 Out of scope

- Raising the base order so that the fee-netted close clears the floor at the
  configured TP price. That would change the user's entry size, and the
  existing floor branch already yields an acceptable close (§2.3).
- The combo branch's `handleDebug` below-minimum exits. Combo sizes from
  balances, not from `deal.size`, so this defect does not reach it, and its
  SHORT carry (spec `222`) skips below-minimum closes on purpose.
