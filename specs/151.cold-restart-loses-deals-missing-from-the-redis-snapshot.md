# 151 — A cold restart loses deals missing from the Redis deal snapshot

On a real service restart a DCA or Combo bot restores its deals from the Redis
`deals` snapshot. If the snapshot is non-empty it does not read Mongo at all.
The snapshot is written through `@RunWithDelay` (`setDealToRedis`), and the
pending write dies with the process. A deal created in the last seconds before
a process stops is in Mongo but not in the snapshot, so the next process never
loads it. It is never restored, never settled and never closed. Every later
cold restart restores the same snapshot, so the deal stays lost. The bot also
no longer counts the deal against the pair, so it opens another deal on the
same pair. Spec 108 fixed the same gap for orders and left deals out (§4.3
there). This spec closes it.

## §1 Definition

### §1.1 Expected

- **§1.1.1** After a cold restart restores deals from Redis, every deal that
  Mongo holds for the bot in `start`, `open` or `error` status is loaded,
  including one the snapshot does not have.
- **§1.1.2** A deal loaded this way is loaded the same way a Mongo load loads
  it. Its orders are in the order map, so restore treats it like any other
  deal. A `start` deal whose base order is FILLED goes through
  `restoreWork`'s filled-base branch and is started (`startDeal`). An `open`
  deal gets its orders rebuilt.
- **§1.1.3** Deals that are in the snapshot keep the snapshot's state. The
  added Mongo read covers only deals the snapshot lacks (`_id $nin`), so it
  changes nothing for deals that were restored.
- **§1.1.4** When the added Mongo read fails, the snapshot is used as before
  and the failure is logged. A restart is not aborted over it.
- **§1.1.5** A reload (`secondRestart`) and a user start still read Mongo only,
  unchanged. An empty snapshot still falls back to a full Mongo load,
  unchanged.

### §1.2 Actual

- **§1.2.1** `loadOrders` sets `loadFromDb = false` whenever the snapshot is
  non-empty on a cold restart. A deal written to Mongo but not yet flushed to
  Redis is not in `this.deals`, its orders are not loaded (they are keyed by
  the restored deal ids), and `restoreWork` never sees it.

## §2 Evidence

Production, 2026-10-12, a paper Coinbase DCA bot with 198 open deals:

- 02:46:34.384Z: the old worker process logged `Deal created` for a PLUME-USDC
  deal, sent its base order and saved it as NEW.
- 02:46:39Z: the base order filled on the venue (`updateTime` of the order row).
  The worker process was restarting at that time.
- 02:47:54.155Z: the new process logged `Found in redis 198 deals`. There is no
  `Get deals from DB` line for this bot in that log file.
- 02:48:08Z: the restart order check found the base order FILLED on the venue
  and saved it. Then `Found 198 open deals`. The new deal is not among them, and
  its id never appears in the logs again. The filled-base branch of
  `restoreWork` logs `in status start, but found filled base order`, and that
  line was never written for it.
- 02:48:08.490Z: `Open new deal PLUME-USDC` opened a second deal on the pair.
- 02:57:58Z, the next restart: `Found in redis 198 deals` again, still without
  the deal.
- Mongo now: the deal is `start` with initialPrice 0 and 0 of 36 levels
  complete. Its base order is FILLED.

## §3 Assumption (hypothesis)

`setDealToRedis` is debounced (1.5 s, ×5 on a process that started from a
service restart), and every `setDeal` on the bot resets the timer. A deal
created seconds before a process stops never reaches the snapshot.
`loadOrders` trusts a non-empty snapshot alone, so the deal is missing after
the restart. A test that drives the real `loadOrders` with a snapshot lacking
a `start` deal that Mongo has must leave that deal out of `getOpenDeals()`
while the assumption holds. The real `restoreWork` must then never call
`startDeal` for it.

## §4 Out of scope

- **§4.1** A deal that the snapshot still shows as live while Mongo shows it
  closed or cancelled. The added read covers only ids the snapshot lacks.
- **§4.2** Duplicate deals already opened on a pair because of this. Whether
  to close one is a user/operator call.
- **§4.3** The debounce itself. Writing the snapshot on every change, or
  flushing it on shutdown, does not cover a process that dies hard.
