# 185 — A flat deal forgets its first "no position" reading before the second one comes

Spec 005 closes a futures deal whose exchange position is gone, but only after
two readings agree. Spec 175 runs that check when the exchange refuses a combo
deal's closing-side grid order as un-reducible. Those refusals only happen when
the bot re-places its ladders: a worker start, a reload, a reconnect. So the
readings come minutes to hours apart.

The count of readings sat in the probe throttle's Redis key (`dpp`). That key
lives twice the throttle window, which is ten minutes after the first probe.
Any second reading later than that found no first one and started again at
one. The deal stayed open, holding its pair's only deal slot.

## §1 Definition

### §1.1 Expected

- **§1.1.1** The probe throttle (`positionProbeBackoff`, spec 005) is
  unchanged. It still allows one probe per deal per window, 5 min rising to 1 h.
- **§1.1.2** An answered probe that finds the position gone counts as one
  reading. On the second such reading the deal is settled, as in specs 005
  and 175, however far apart the two readings are (up to one day).
- **§1.1.3** An answered probe that finds the position there resets the count.
  A probe the exchange did not answer is not a reading and leaves the count
  alone. One timeout plus one empty answer is one reading, not two.
- **§1.1.4** Settling a deal clears the count.

### §1.2 Actual

- **§1.2.1** The count was `positionProbeBackoff.record().attempt`. Its key
  expires `2 × interval` after each probe (no `memoryMs`), so a reading more
  than 10 min after the previous one is reading number one again.
- **§1.2.2** `record()` runs before the venue is asked, so a probe the exchange
  did not answer also raised the count.

## §2 Evidence

Production, a long bitgetUsdm combo deal (read-only):

- The deal's orders show a base and grid buys filled on its opening day. No
  closing fill was ever recorded. From the next day, every ladder re-placement
  logged a reduce-only grid SELL refused with `no position to close`, about
  140 times over seven days.
- Spec 175's check went live the evening of the sixth day. After that the bot
  logged "waiting for a second reading before closing the deal" seven times,
  at gaps of 6.5 h, 4 h, 39 min, 26 min, 7.8 h and 3 h. Two of those readings
  came from the same worker process, three hours apart, and that was still
  reading one.
- It closed only when two refusals came 5.5 min apart, inside the 10-min key
  life: "(2 readings) — closing the deal instead of re-arming against a
  position that is gone", then base-trigger close, booked without an order.

## §3 Assumption

The second reading is lost because the count lives in a key whose TTL is
shorter than the gap between readings. A count kept in its own key, with
memory well beyond that gap and touched only by answered readings, settles the
deal on the next refusal after the first.

## Invariants

UI-free engine change. The wrong state this spec addresses is the one spec 175
and spec 005 already describe: an `open` futures deal with no venue position.
No new invariant pack. There is no index-backed query for "venue holds
nothing", because the venue's position is not in the database.
