# 076 — Kraken spot pays a private-REST token per order where it could pay one per batch

## §1 Definition

Every bulk order operation in the bot engine is a strictly serial loop: `for
(const o of orders) await cancelOrderOnExchange(o)` for a teardown, `for (const
o of orders.new) await sendGridToExchange(o)` for a placement. Each iteration is
one venue round trip — two, on the venues that re-read an order after acting on
it — and the loop's cost is therefore the sum of its orders' costs plus whatever
the venue's rate limiter adds once the budget is spent.

Kraken spot meters private REST against a published per-key bucket of **20
tokens refilling at 0.5/s**. A cancel spends two of them (the order lookup plus
the cancel); a placement spends two (the add plus the re-read). Kraken also
publishes two batch endpoints, both of which count as **one** call:
`CancelOrderBatch` (up to 50 unique order ids) and `AddOrderBatch` (2..15
orders, one pair, validated as a whole before submission).

### §1.1 Expected

- **§1.1.1** A bulk cancel of N orders on Kraken spot costs O(1) venue calls,
  not O(N), and every order ends in exactly the local state the per-order path
  would have left it in.
- **§1.1.2** A burst of N limit placements on Kraken spot costs O(N/15) venue
  calls, and each order receives its own answer, indistinguishable from the one
  a single placement would have produced.
- **§1.1.3** No order is ever placed twice, and no order is ever written off
  locally while the venue may be holding it.
- **§1.1.4** No other venue, and no un-armed bot, changes behaviour by so much
  as one HTTP call.

### §1.2 Actual

- **§1.2.1** A bulk cancel of N orders makes 2N private calls. The first few go
  out immediately, the bucket empties, and every subsequent call is parked for
  ~4s (two tokens at 0.5/s) — so the loop's duration grows with N far faster
  than the venue's own limits require.
- **§1.2.2** A burst of placements has the same shape, on the path where a
  delay costs the most: the levels nearest the price are placed first, so the
  ones that park are the ones furthest out, and a fill during the burst is
  answered by a ladder that is still being built.

## §2 The exchange client owns the batch, and every fallback from it

Two methods on `core/src/exchange/exchange.ts`, modelled on the existing
`getOrdersBatch`, with declining or sequential defaults on the abstract class so
that nothing else has to know they exist.

- **§2.1** `cancelOrdersBatch({ symbol, newClientOrderIds })` → `POST
  orders/cancelBatch`, private. The ids are the ones `cancelOrderOnExchange`
  already addresses the venue with — on Kraken spot the exchange order id
  (txid), because Kraken has no client-order-id lookup at all. The answer names
  ONLY the orders the call observed as cancelled; anything absent means "I
  cannot vouch for this one" and the caller cancels it as it always has.
- **§2.2** `openOrdersBatch({ symbol, orders })` → `POST orders/openBatch`,
  private, answering **one `BaseReturn<CommonOrder>` per input order,
  positionally aligned** (§6).
- **§2.3** Both decline by default on the abstract exchange, so the paper
  simulator — which mirrors the connector's endpoint surface and does not carry
  these routes — needs no change. The placement default is not a decline but
  the sequential loop itself: a transport with no batch route places the same
  orders in the same order with the same answers, so nothing downstream can
  tell which served it.
- **§2.4** Neither call uses the transport retry ladder (`noAutoRetry`, plus a
  non-retrying catch, exactly as `sendOpenOrder`). The ladder fires on outcomes
  that do not say whether the request arrived and re-sends the identical body:
  for a batch placement that is a duplicate batch, and for a connector that
  predates the route it is five 3s retries to learn nothing.

## §3 Priming a bulk cancel

`MainBot.primeCancelBatch(orders)` cancels the whole list in one call and holds
the confirmations in `cancelBatch` for `cancelOrderOnExchange` to consume. It is
called immediately before a bulk loop, with exactly the list that loop will
walk, and the map is cleared in that loop's `finally`.

- **§3.1** Gated on: the flag (§5), Kraken spot, at least two orders carrying a
  real exchange order id. An order still holding the `'-1'` placeholder is left
  out entirely, so its existing guard still fires on the normal path. Ids are
  grouped by symbol (one call per symbol) and chunked at Kraken's published 50.
- **§3.2** Strictly an optimisation. Every failure — a declining connector, a
  timeout, an empty or partial answer — leaves an id unprimed, and that order is
  cancelled the way it is today. Nothing here decides *whether* an order should
  be cancelled.
- **§3.3** The "unsupported" latch is set only from an answer that cannot be a
  transient: a decline, or the 404 of a connector deployed before the route
  (`isBatchRouteUnavailable`). An empty result or a timeout leaves the path
  armed. The latch has no expiry, so latching on a bad minute would be a
  process-lifetime regression that nothing reports.
- **§3.4** The loops primed are the teardowns: the grid `cancelAllOrder` and
  `limitOrders` cancel phase, the DCA `cancelAllOrder`, the "was closed during
  place orders" cleanup, the closed-deal sweep in `checkOrders`, the
  reduce-funds take-profit pull and the combo minigrid close. **The DCA
  `placeOrders` cancel phase is deliberately excluded**: it can `return` from
  the middle of itself when an order comes back filled, before the remaining
  levels are walked and before the place phase that would replace them. Under a
  bulk cancel those unwalked levels would already be gone from the venue with no
  replacement sent — a live position briefly holding fewer safety orders than
  the deal believes — where today they stay resting until the next pass. Every
  loop that IS primed runs to completion.

## §4 Consuming a primed cancel

In `cancelOrderOnExchange`, where the cancel request is computed:

- **§4.1** A primed entry is looked up by `${order.orderId}` — the same id the
  venue call below would have been addressed with, so the prime and the consume
  cannot disagree about what was asked for — and **deleted as it is read**. A
  venue confirmation describes the moment it was fetched; letting one answer a
  later cancel would report a cancel that never happened.
- **§4.2** Everything after that point is untouched: the field copy from the
  venue's answer, the re-size promotion guard, the CANCELED-with-fills
  promotion, the emit, `setOrder`/`deleteOrder` and the DB write. Those are what
  make an order cancelled as far as the rest of the engine is concerned, and a
  batched order that skipped any of them would be a subtly different order.
- **§4.3** An order with no primed entry takes today's path unchanged.

## §5 Arming

Two environment flags, read once at module load, in the documented opt-in shape
the tp-coverage correction established: `1`/`true`/`yes` for every Kraken spot
bot, or a comma-separated list of bot ids for a careful rollout. Silent while
unset; one line per flag at boot when set, naming what was read.

- **§5.1** `BOT_BATCH_CANCEL` — bulk cancel. `BOT_BATCH_PLACE` — bulk
  placement. Both default OFF, and both are read through a bot-level predicate
  so that the flag and the venue can be seen, and tested, apart.
- **§5.2** A value that is neither a boolean nor a list of bot ids arms nothing
  and SAYS so, at warn level. A typo that silently armed nothing would be read
  as "the flag does not work", and the next thing tried is the fleet-wide value.

## §6 The three outcomes of a batch placement

Told apart by `isAmbiguousOrderFailure` alone — the classifier the single-order
path already trusts — rather than by any new rule about batches.

- **§6.1 `ok`** — the batch reached the venue and every item has a definitive
  per-order answer. An item carrying an order was PLACED and is reported as
  placed even if the venue's re-read lagged; reporting it absent is how a caller
  comes to place it a second time. An item carrying a reason was refused,
  definitively, and is never re-sent. A reply whose length does not match the
  request cannot be matched up positionally, so it is treated as an unknown
  outcome (§6.3) rather than zipped.
- **§6.2 `notok`, definitive** — a declined route, a connector that predates it,
  a whole-batch validation rejection. Nothing reached the matching engine, so
  each order goes down the ordinary `openOrder` path, sequentially, in input
  order. That is today's behaviour exactly, including "place as many as the
  balance allows, nearest level first".
- **§6.3 `notok`, ambiguous** — a timeout, a reset, a 5xx. The batch may have
  landed in full, in part or not at all. Every order therefore goes through
  `openOrder`'s own resolve-then-resend decision, extracted for the purpose:
  ask the venue, adopt what it already has, send only what it definitively does
  not, and report an order as unconfirmed when the lookup is inconclusive too.
  An unconfirmed order is the engine's to resolve — it still holds the id; a
  duplicate live order is nobody's.
- **§6.4** One consequence worth naming: with the transport ladder off, a
  connector with no such route answers 404, which `apiCall` surfaces as
  `Exchange connector | Not Found` — a string `isAmbiguousOrderFailure` matches.
  It is read as route-unavailable (§3.3) before ambiguity is considered, because
  a missing route means no handler ran and nothing was placed. Were that
  classification ever wrong, the arm it selects does the same thing the
  ambiguous arm's fallback does: place each order on its own.

## §7 Coalescing a burst without making the engine concurrent

`core/src/bot/openOrderBatcher.ts`. The saving is entirely in the wire calls, so
only the wire call is shared.

- **§7.1** Participants are named up front. One arriving at the send site in
  `sendOrderToExchange` parks; one that settles without arriving — held back by
  a pre-send gate, refused, or thrown — bails. The flush happens when arrived +
  bailed accounts for everyone, or on a safety timeout, so no burst can be
  parked by a participant that does neither.
- **§7.2** Which orders may take part is decided ONCE, serially, before
  anything is sent (`batchablePlacements`): the caller's own skip checks in the
  caller's own order, plus three refusals that belong to batching. Market
  orders, because the batch route is limit-only. Minigrid orders, because their
  pre-send section rewrites a list shared by the whole minigrid. And — the one
  that matters — **two orders of the same (price, side, qty, type) are never
  batched together**, because that is the tuple the loops' duplicate checks
  match on: run one after another the second sees the first's row and skips, run
  together neither sees the other and both are placed. The twin takes the
  sequential path and meets that check exactly as it does today.
- **§7.3** Answers are delivered **one participant at a time**: resolve i, wait
  for i to report itself settled, resolve i+1. Every post-send continuation —
  the balance latch, the cooldown guards, `countBalances`, the DB writes, the
  emits — therefore runs with nothing else alongside it, in the caller's order,
  as it does today. Chunks are Kraken's 15 and are sent one after another, and
  all of them are sent before any answer is delivered, so no bookkeeping runs
  while another chunk is in flight. A chunk of one is sent as a one-element
  call, which the client serves as an ordinary placement.
- **§7.4** A throw inside the flush is a defect, not a venue outcome — the
  client catches its own transport failures — and a defect after the wire call
  may have left live orders behind. Parked participants are therefore given an
  ambiguous-shaped `notok`, never a refusal, so the engine resolves those orders
  against the venue rather than writing them off (which would drop them from
  `orders` and orphan a live order) or re-placing them.
- **§7.5** The send site is `LIMIT` orders on their first send only. A re-entry
  with `count > 0` is a retry of an order whose burst is long gone (the
  tick-size, quantity-decimals and lot-size branches all re-enter), and it goes
  straight to `openOrder`.
- **§7.6** Two burst loops are wired: the grid `limitOrders` place phase and
  the DCA/combo `placeOrdersHoldingDealLock` place phase, the latter for plain
  ladder orders only — take-profits, market orders, the fee-sizing branch and
  minigrid orders all stay in the sequential loop. In that loop the batch is a
  phase ADDED in front of the existing one, whose body is unchanged but for a
  single skip on the ids already sent. The skip is by id, deliberately: a
  refused order's row is deleted by the error path, so a loop that recognised
  its participants by the presence of their rows would re-send exactly those.
- **§7.7** One behaviour does change for a batched burst, unavoidably. Placed
  sequentially, an order refused for funds can open a not-enough-balance
  cooldown that suppresses the NEXT order before it is sent; placed together,
  all of them have passed that gate before any answer is back, so the venue
  refuses them itself and each records its own rejection. The cooldown still
  arms, one burst later.

## §8 Tests

`npm test` (mocha), specs beside the code, synthetic identifiers only.

- **§8.1** `src/exchange/orderBatch.spec.ts` — the client's per-order contract:
  the ok mapping, a refused item never re-sent, the definitive fallback in input
  order, the declining connector asked once, the 404 read the same way, and the
  ambiguous arm (adopt when found, never send when the lookup is inconclusive,
  send only on a definitive not-found). Plus the abstract defaults.
- **§8.2** `src/bot/cancelBatch.spec.ts` — a primed cancel makes no venue call
  and leaves the order in a state deep-equal to the per-order path's, including
  the DB write, the emit and the local map; an entry is consumed once; a cleared
  map cannot answer a later cancel; `'-1'` is excluded; a single order is not
  batched; symbols are grouped; an un-vouched order is still cancelled; nothing
  happens off Kraken spot or for an un-armed bot; a transient does not latch and
  a missing route does.
- **§8.3** `src/bot/openOrderBatcher.spec.ts` — flush on all-arrived, bails,
  chunking at 15 with no overlap, delivery strictly one at a time, both
  anti-deadlock timeouts, and a throw producing ambiguous-shaped answers.
- **§8.4** `src/bot/batchPlacement.spec.ts` — the eligibility decision, the
  same-shape refusal included. `src/bot/batchFlags.spec.ts` — the flags, whose
  default is off and whose failure mode is loud.
- **§8.5** Not covered: a loop-level test that drives either burst loop
  end-to-end. Both need a bot with an exchange, an order map, a deal and a
  price source; the existing harnesses do not reach `limitOrders` or
  `placeOrders`, and building one that did would be a larger change than this
  one. The parts those loops contribute — the eligibility decision, the
  settle/bail wrapper's contract and the delivery order — are covered above.
