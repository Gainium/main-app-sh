# 169 — An order re-sent under a sibling id after a duplicate refusal loses its own record

Bug spec (Definition / Evidence / Assumption). Tests:
`src/bot/duplicateClientOrderId.spec.ts` (spec 169 §2.1–§2.4).

## §1 Definition

When a venue refuses a client order id as a duplicate and says it holds no
live order under it (Bybit `Duplicate clientOrderId.`, the original cancelled
with nothing filled), `sendOrderToExchange` writes the original off and re-sends
the order under a sibling id (spec 145 / 161).

**Expected.**

- §1.1 The sibling is a placement of its own: it gets its own row in `orders`,
  and that row follows the sibling's life (NEW → FILLED / CANCELED) like any
  other order. The original keeps its CANCELED row.
- §1.2 The sibling starts as a fresh placement (`NEW`, no exchange id). Nothing
  about the original's write-off is carried into it.
- §1.3 A sibling that fills is booked to its deal and is not reported as a fill
  the deal does not hold. A sibling that rests on the book stays live and is not
  cancelled on the venue.
- §1.4 Unchanged: the duplicate branch still asks the venue first (spec 136),
  never re-sends the refused id (spec 145), returns a sibling this bot already
  holds live or FILLED instead of sending (spec 161), and an order genuinely
  retired while its placement is in flight is still cancelled / reported
  (spec 155).

**Actual.**

- The re-send runs at `count === 1`, which skips the write-ahead
  `saveOrderToDb`, and `updateOrderOnDb` never upserts. The sibling's row is
  never created: its FILLED save matches nothing, and the deal's order list
  shows only the original's CANCELED row with exchange id `-1`. The venue order
  probe reads that row as "never placed" while the deal's books (correctly)
  hold the sibling's fill.
- The unknown-order ladder that answered "the venue has it CANCELED" sets
  `status = 'CANCELED'` on the map entry in place, and that entry is the same
  object that is then renamed and re-sent. On the placement reply the order is
  `CANCELED` with exchange id `-1`, which is exactly spec 155's "written off
  while it was being placed" shape: a filled sibling is reported as a fill
  outside the deal, and a resting sibling is recorded CANCELED and cancelled on
  the venue.

## §2 Evidence (prod, read-only)

- A Bybit spot DCA safety order was refused as a duplicate several times over
  hours; each time the ladder logged `Real order … status: CANCELED` and the
  bot logged `Save order …2`, `…3`, `…4`, `…5`. `orders` holds a row for the
  original id only (CANCELED, `-1`) and none for any sibling. When `…5` filled,
  the error log reads `Order …5 (<exchange id>) was written off as CANCELED while
  it was being placed, but bybit executed <full qty> … Deal … does not hold these
  fills`, immediately followed by `Regular order FILLED …5` — the deal did book it.
- Across the retained DCA-bot logs every "written off as CANCELED while it was
  being placed" line names a sibling id (`…2`–`…5`): safety orders that filled,
  and resting take-profit siblings for which the bot then logged `… has it open
  as … Cancelling it there`.
- The harness in `duplicateClientOrderId.spec.ts` reproduces both: no sibling row
  is written (§2.1, §2.3), the exact prod error string is raised (§2.2), and a
  resting sibling is left `CANCELED` in memory and cancelled on the venue (§2.4).

## §3 Assumption (root cause — hypothesis, confirmed by the red tests)

The duplicate branch re-sends the same in-memory object it wrote off, without a
row of its own and with the ladder's in-place CANCELED still on it. The missing
row is latent (the re-send never had a write-ahead); the false orphan handling
became visible with spec 155's `cancelOrphanedPlacement`, which reads exactly
that shape.

## §4 Fix

- §4.1 Before re-sending, reset the renamed order's status to `NEW` (§1.2).
- §4.2 Write the sibling's own write-ahead row (`saveOrderToDb`), with the
  original row's `_id` stripped so it can never collide with it (§1.1). The
  existing refusal paths retire or delete that row exactly as they do any
  `count === 0` write-ahead.
- §4.3 No change to deal sizing, average price or take-profit math; the sibling's
  fill is booked exactly as before.
